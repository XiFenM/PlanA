# `guide-learning`：PlanA 配置层

本文只保存中央 `guide-learning` 在 PlanA 中运行时需要的仓库事实：学习者画像、状态路径、单写者、
实际时长归属和领域透镜。讲解、提问、练习、结课、暂停与恢复行为均由中央 Skill 定义，不在本仓库复制。

## 0. 学习者画像与讲解深度

本节是 PlanA 所有计划共用的只读学习者画像，只描述学习者和讲解偏好，不保存课程状态、授权或进度。同一学习者
在同级仓库 `programming-lab` 的 `docs/learning-profile.md` 另有一份画像；2026-10-20 已把其中不限于某门课
的偏好与背景按原日期并入本节，此后两边各自维护。

### 背景与目标

- AI Infra 工程师，从事非 NV 加速器上的 PyTorch／vLLM 适配、通信与性能优化；具体经历以用户已提供的内容
  为准，不杜撰。
- 目标是高级 AI 框架开发工程师岗位的学习与面试。用户于 2026-09-28 明确要求以理解为中心：讲清机制、设计
  理由和真实系统，检查题考理解而不是计算。

### 目标深度

- 默认讲到中央讲解标准的第 5 层（表达与迁移）。
- 口述题按[八周计划 §5.3](../计划/高级AI框架开发工程师-八周证据冲刺计划.md#53-每周统一验收门)执行：W1–W3 以文字作答，只验收内容，不考口头表现或时长；正式口头验收从 W4 的 Mock 开始。
- 真实系统锚点：优先使用 vLLM、SGLang、PyTorch、DeepEP 等的固定版本源码和公开的真实模型配置；自研芯片
  相关内容按第 3 节的边界处理。

### 讲解偏好

- 先给课程全貌和全流程骨架，再进入局部推导。学习者在 2026-09-24 的 programming-lab Triton 第 06 课指出
  "常规情况下，我有能力理解通用公式"。
- 符号先行：先定义符号、维度与单位，给出符号关系与形状，再按需代入数字；不同维度即使取值相同也用不同
  符号。讲新机制时与下方已有基础对照。
- 节点依赖的 API、dtype、算子语义或抽象，先讲清语义和选择理由，再读用到它们的代码。
- 举例先交代场景。用到例子里的数字之前，先说清例子里有哪些对象、各自的尺寸、分块或切分方式和设备假设，
  以及每个数字的来历，再一步步代入；不用没有介绍过的简称指代例子，"为什么"部分不压缩成一两句。比较几种
  做法时沿用同一个例子。学习者在 2026-10-05 的 programming-lab Triton 第 08 课指出"为什么"部分"过于简略"，
  例子"没有讲清楚例子场景"。
- 名词渐进引入。没有基础的领域里，每个新名词第一次出现时先用平实的话解释，并给出 C/C++ 或 Python 里的
  对应物，之后才使用；还没讲到的名词不拿来解释别的东西，绕不开时当场补一句。学习者在 2026-10-08 的
  programming-lab Rust 第 01 课结课后指出"如果一直有这么多令人疑惑的名词，我感到学习的阻力很大"。

### 检查题偏好

- 优先考理解：解释为什么、比较取舍、从现象诊断、改条件预测、迁移和口述。
- 计算题只用于面试常见的估算（通信量、显存、算力、带宽），并要求解释结论的含义。

### 练习偏好

- 练习服务于学习理解和面试准备，不为某款硬件做真实适配，要求快速。用户于 2026-10-28 指出独立撰写 Change
  Card 的安排"过于耗时"，"只想要的是学习理解和面试准备"。
- Change Card 用问答共建：导师按骨架逐段提问，每轮一到三个问题并给出选项；学习者选择、补充并提供芯片信息，
  导师据此逐段成稿。不要求学习者一次性回答全部问题，也不要求独立写完整卡片。芯片信息只记录可公开的抽象能力。
- 节点讲解中已逐项对照过的横向对照，由导师整理进课程网页，不再单列为学习者练习。

### 已有基础

新内容与以下已有基础对照，不从头讲：

- 工作经验：PyTorch 算子与后端适配、性能剖析与算子融合、集合通信的使用与调试。
- PlanA 已验收：W1 的 vLLM 请求链路与执行边界；W2 单元一的 MoE／EP 数据流与六类并行的基本通信。
- programming-lab 已结课（截至 2026-10-20；之后的进展以该仓库画像为准）：Triton 第 01–09 课（向量加法、
  Fused Softmax、矩阵乘法、Low-Memory Dropout、LayerNorm、Fused Attention、外部函数（libdevice）、
  Grouped GEMM、持久化矩阵乘）；算法面试第 01 课；Rust 第 01–02 课。

没有基础的领域，讲解和练习都不默认学习者认识其中的名词或语法：

- 编译器内部（IR、lowering、链接、内联、编译期分支等）：学习者在 2026-09-30 的 programming-lab Triton
  第 07 课说明"对于编译器的了解非常少"。涉及时先用 C/C++ 里的对应物补最少的前置概念，再配可交互的图解和
  真实的编译产物，然后才检查；图解存入仓库，便于复习。
- Rust：2026-10-08 说明"先前完全没有接触过Rust"；programming-lab Rust 第 01–02 课之外的内容按零基础讲。

## 1. 状态路径

| 逻辑职责 | PlanA 位置 | 路径规则 |
| --- | --- | --- |
| 长期 Program | [`计划/主计划.md`](../计划/主计划.md) | 保存长期目标、范围、候选 Lesson 与总预算；专项计划只引用它 |
| 临时 Program | `计划/` 下由用户明确启动的专项计划 | 只保存该专项的目标、范围、候选 Lesson、预算与返回引用；不记录当前课、已授权范围或逐课状态 |
| 课程账本（Lesson） | `计划/八周冲刺进度/` 下的周进度页 `W1.md` 至 `W8.md`，以及 `历史记录/` 中对应周的学习验收记录 | 周进度页只写"完成了什么、凭什么算完成、还缺什么"；练习约定、阶段事件与详细证据写在验收记录，周进度页只链接；同一事实只写一处 |
| 独立 Session event | 实际任务所属模块已有的记录位置 | 沿用模块已经存在的记录位置 |
| 实际时长 | 实际任务所属模块的 `进度.md` | 只记录用户提供或确认的值 |
| Checkpoint | [`计划/学习断点.md`](../计划/学习断点.md) | 唯一可覆盖恢复游标；当前前台课程只从这里发现，计划与周进度页不重复记录当前课、未启动或不自动推进 |
| 派生 dashboard | [`计划/进度总表.md`](../计划/进度总表.md) | 周日或经批准的周期触点更新，不反向裁决活动状态 |
| 稳定课程与资料范围 | 各模块 `学习指引.md` | 只在获准的资料治理触点修改，不保存当前游标或 Lesson evidence |

JSON 的 `record_mappings` 使用不随课程变化的稳定位置：`lesson` 映射整个 `计划/八周冲刺进度/` 目录（周进度
页及其 `历史记录/` 验收记录都在其中），`program` 映射八周冲刺计划的 Program 小节，`checkpoint` 映射学习
断点。换课、换周都不需要修改配置或重新 materialize；当前课只由学习断点指向。mapping 只是写入上限，不构成
推进或写入授权。

技术成果保存在相应模块，面试成果保存在 `面试准备/自我准备/`；不再用技术设计包承载整周进度。预建的周进度页只是跟踪入口，页面存在不代表 Lesson 已启动。旧设计包路径仅作历史链接兼容，不再作为新证据材料或状态 owner。

## 2. 单写者与时长归属

| 事实 | 唯一活动 owner |
| --- | --- |
| 长期目标、范围与总预算 | `计划/主计划.md` |
| 专项目标、范围、专项预算与候选 Lesson | 相应专项计划 |

| 详细练习约定、需跟踪的问题与阶段事件 | 对应周的学习验收记录；周进度只引用其依据 |
| 当前前台课程、语义位置、唯一下一动作、前进门槛与返回点 | `计划/学习断点.md` |
| 用户确认的实际学习时长 | 实际任务所属模块的 `进度.md` |
| 全局完成度与周期汇总 | `计划/进度总表.md`，仅作为派生视图 |

专项按实际学习内容归账，不建立第二套累计时长：

- vLLM、推理服务、调度、KV cache 与 PD 分离归 [`推理框架/进度.md`](../推理框架/进度.md)；
- PyTorch Dispatcher、custom op、后端接入归 [`PyTorch/进度.md`](../PyTorch/进度.md)；
- collective、P2P、RDMA 与通信数据面归 [`训练框架与分布式/进度.md`](../训练框架与分布式/进度.md)；
- 其他任务归实际所属模块的 `进度.md`。

计划时长与预计投入不是实际时长；实际时长的唯一原始来源是用户确认后写入的模块 `进度.md`。

## 3. PlanA 领域透镜

只在有助于当前节点时，从以下透镜中选择最相关的一项或少数几项，不要求每次全部展开：

- **PyTorch**：Dispatcher、算子 schema、fake/meta、设备与 stream 语义、PrivateUse1 和后端接入；
- **vLLM**：请求生命周期、EngineCore／Scheduler／Worker／ModelRunner 所有权和扩展边界；
- **KV cache 与 PD**：逻辑到物理 block 映射、producer／consumer ownership、传输、ready、cleanup 与失败语义；
- **通信**：collective、P2P／RDMA、内存注册、同步、拓扑与故障边界；
- **自研芯片适配**：框架不变量、设备能力槽位、adapter 边界、正确性证据和性能归因。

自研芯片映射只使用用户已提供或获准公开的能力事实；未披露接口、拓扑、性能数据和内部实现保持
未知，不用 CUDA、ROCm 或其他平台的能力替代。

## 4. 配置边界

- 本文件只提供静态仓库事实，不保存教学步骤或当前状态正文。
- W18/W26/W32 是只读 legacy 资源报告；新的静态目录、动态 registry 与课程 slot 由 `resource-planning` 独立拥有，不进入教学状态。

## 5. 文章产物适配

- 学习文章沿用模块内现有系列目录，不为通用规范创建第二棵文章树；当前受管目标是
  `PyTorch/深入学习理解PyTorch/` 与 `推理框架/深入学习理解vLLM/`。
- 主要语言为中文，使用同伴式技术解释：展示问题、理解变化和证据边界，不采用讲台式命令口吻。
- 领域内容优先连接实际工程、源码所有权、版本锚点、可复核数字、反例与面试迁移；只有已有证据时
  才连接过往经验，不杜撰经历、实验或公司内部事实。
- vLLM 系列包含 Markdown、PNG 与 drawio，文章继续采用 `sequence-topic`，编号以已有 Markdown
  文章序列为准；collection 定位不代表需要读取其中所有材料。
- PyTorch 系列保持现有的精确来源选择，不新增整个目录的可读知识 collection；新文章采用
  `yyyy-mm-dd-topic`，只把用户本轮明确选择的来源与目标纳入写入事务。既有 `0-Index.md` 与
  `1-Internal-Overview.md` 保持历史命名，不为统一文件名而改写。
