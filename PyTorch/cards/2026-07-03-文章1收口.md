问题	答案	锚点	来源
torch.add 走不走 autograd kernel 由什么决定？requires_grad 起什么作用？	keyset 高位有没有 Autograd key 决定路由；requires_grad 只是 autograd kernel 内部"记录还是白过"的开关。我曾连续两轮说成"requires_grad=true 所以 key 最高"——路由与记录是两层判断，别把开关当路由。	keyset 决定路由，requires_grad 决定记录	1-Internal-Overview.md §3.2
native_functions.yaml 里 _ 后缀和 (a!) 注解各管什么？	_ 是纯命名习惯只给人看（提示 in-place 变体，机器不读）；(a!) 才是机器读的真值：a 是别名集标签，! 表示此参数被就地修改并喂 version counter +1。我曾说"! 表示原地、_ 表示修改输入"——把一层含义拆给了两个记号。	_ 管人的预期，(a!) 管机器的真值	1-Internal-Overview.md §4
背出 torch.add 从 Python 到 kernel 的完整七步链	THPVariable_add（codegen 生成的 CPython 原生绑定，性能考虑不走 pybind11）→ at::add → dispatcher 算 keyset → VariableType::add（autograd 记录）→ at::redispatch::add（排除 Autograd key）→ RegisterCPU 挂钩 → native kernel 内 dtype switch。	binding → keyset → autograd → redispatch → backend → dtype switch	1-Internal-Overview.md §3.2
同一算子在同一设备上为什么仍可能走不同链路？	至少四个分叉：requires_grad 开关（走不走记录层）、layout（strided/sparse 不同 kernel）、dtype（kernel 内 switch）、composite 分解（无专用 kernel 的算子拆成 aten 组合，链深不同）。	requires_grad / layout / dtype / composite 四维	1-Internal-Overview.md §读后回顾 Q13
给 PyTorch 新增算子，标准流程动哪两张表、手填哪两个洞？	native_functions.yaml 声明接口，是起点：驱动 codegen 生成整条接线（Python 绑定、C++ API、schema 注册、后端挂钩）；derivatives.yaml 声明反向。手写的只有 kernel 函数体和反向公式。fork 整仓属 in-tree 享受 codegen；真 out-of-tree 插件才手写 TORCH_LIBRARY_IMPL。	两张表接线，人只填两个洞	1-Internal-Overview.md §4
yaml 条目不写 dispatch: 节会怎样？什么情况下是陷阱？	不报错，视作 CompositeImplicitAutograd：函数体纯 aten 组合则前向反向全免费。陷阱：混了裸指针或外部库调用，这些计算对 autograd 不可见——前向照常、反向静默错误，正是"只写前向、训练断梯度"的根。	缺 dispatch = composite；裸指针 → 反向静默错误	1-Internal-Overview.md §4
autograd 为什么对新后端"免费"？边界在哪？	autograd kernel 按算子注册不按后端，反向公式是设备无关的 aten 组合，执行时 redispatch 回后端的前向 kernel——前向注册全了反向白给。边界：fused 单体 kernel 和外部库调用没有 aten 分解，必须自己提供 backward。	backward = aten 组合 + redispatch 回前向	1-Internal-Overview.md §3
PyTorch 有没有现成的自定义算子 vs 标准算子自动对拍机制？	没有现成开关。我们环境变量触发的 CPU 对拍宏是自建的：执行时把输入搬到 CPU 用参考实现重算再比对。__torch_dispatch__ 是实现"影子执行"式通用对拍的现代标准挂点（待验证）。	原生无对拍开关；__torch_dispatch__ 是影子执行挂点	1-Internal-Overview.md §读后回顾 Q8
对拍的参考实现为什么必须用 aten 组合、禁用裸 data_ptr？	校尺必须比工件直：裸指针带连续性假设，遇非连续输入会静默读错数据——校尺自己先弯了，对拍就变成两个错误实现互相认证。参考实现用已有 aten 算子组合，天然 stride 安全。	校尺必须比工件直	1-Internal-Overview.md 〔过往经验〕
对拍宏的容差阈值为什么不能是常数？	容差是两条链硬件精度轮廓差异的建模，要逐算子、逐 dtype 校。实例：向量单元 fp32-only，bf16 升 fp32 算完降回，自研端 bf16 反而比 CPU 准 → 假阳性；矩阵乘单元 bf16-only，fp32 矩阵乘天然比 CPU 差（硬件本底，多次 bf16 矩阵乘可拼精度但耗时）→ 扩容差。	容差 = 两条链精度轮廓差异的建模	1-Internal-Overview.md 〔过往经验〕
