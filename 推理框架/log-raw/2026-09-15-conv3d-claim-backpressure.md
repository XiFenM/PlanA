**027 · 助手 / 正式回答** · `2026-09-14T03:08:28.023Z` · `msg-a1f4981ad2725121a290`

“一个关闭动作”是：为了把某个“待核”字段变成确定结论，下一步要执行的单一、具体核验动作。

推荐写法：

> 核对「哪份证据」中的「哪个字段」；确认并记录「什么结果」后关闭。

例如：

| 待核字段 | 一个关闭动作 |
|---|---|
| 模型版本 | 核对对应项目提交或模型配置；记录准确模型名和版本后关闭。 |
| 框架 commit | 核对当时的部署清单或 Git 记录；记录 commit hash 后关闭。 |
| Shape／dtype | 找回代表性单测或 Trace；记录输入、权重、输出 Shape 与 dtype 后关闭。 |
| Batch／并发 | 核对启动配置或 Benchmark 脚本；记录实际 Batch 和并发值后关闭。 |
| 环境抽象 | 确认允许披露的平台描述；形成脱敏表述后关闭。 |

不要只写“以后确认”或“查资料”，因为它们没有说明查什么、产出什么。

即使资料最终找不到，这个动作也算执行完，但字段应继续标为“待核”，并注明“原始记录缺失，当前不进入 Claim”。

**113 · 助手 / 正式回答** · `2026-09-15T03:21:28.287Z` · `msg-82778d4095308cbe0a77`

反压，也叫背压，就是：**下游处理不过来时，把容量限制反馈给上游，让上游减慢或暂停继续提交，避免任务无限积压。** [概念依据](https://www.reactive-streams.org/)

例如，在某种固定负载下，客户端每秒发送 100 个请求，后端每秒只能完成 60 个。如果全部接收，等待队列每秒就多出 40 个请求，延迟和内存占用会持续增长。

一种反压设计是：

- 后端前面使用有容量上限的队列，满了以后，上游等待空位。
- 客户端限制在途请求数，收到完成响应、释放名额后，再发送新请求。

这样，下游的处理速度会实际影响上游的提交速度。**仅仅把请求放进等待队列，还没有完成这个反馈过程。**

和我们学过的 DPLB 对照：

| 机制 | 主要解决的问题 |
|---|---|
| DPLB 分流 | 这个请求交给哪个副本？ |
| 反压 | 下游还有没有容量，上游现在能继续提交多少？ |

如果所有副本都满了，DPLB 仍能选出一个“相对没那么忙”的副本，但不会凭空增加总处理能力。

在固定版本 vLLM 中，Scheduler 会根据 Token 预算和 `max_num_seqs` 限制本轮调度。这保护的是执行侧的容量；API 是否继续接收请求、等待队列是否有上限，还需要分别检查，不能据此认定已有完整的端到端反压。[调度源码](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/sched/scheduler.py#L617-L622)

用一个小情境检查：**如果 Scheduler 最多运行 16 个请求，但 API 可以无限接收请求并加入 waiting 队列，系统的压力会积在哪里？这算完整的反压吗？**
