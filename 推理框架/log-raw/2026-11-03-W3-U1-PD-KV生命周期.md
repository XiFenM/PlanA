假设只看一层的 K 缓存：

- Scheduler 每块管理 **32 个 Token**。
- backend 每页管理 **16 个 Token**，每页占 **8 KiB**，因此一块对应两页。
- D 的缓存区域起点为示意地址 `0x10000000`。
- 请求 A 的第一个逻辑块，被 D 分配到块池 **ID 7**。

于是映射为：

```text
A 的请求块 0：Token 0–31
→ D 块池 ID 7
→ D backend 页 14、15（7×2、7×2+1）
→ 页 14 起点：0x10000000 + 14×8192 = 0x1001C000
→ 两页覆盖：[0x1001C000, 0x10020000)，共 16 KiB
```

这些步骤分别在哪里完成：

1. **D Scheduler／KVCacheManager，CPU 侧**

2. **D Worker → P Worker**  
   D 通过 `PUSH_REG` 告诉 P：这次请求的目的槽位包括 **block 7**，而不是直接说“Token 块 0 就是地址 7”。

3. **P Worker 的 CPU 侧**

4. **传输后端**  
   把 P 的源数据搬到上述 D 地址范围。假设同一段数据在 P 上分配到 block 2，那么可以是“P 的 block 2 → D 的 block 7”；两端编号无需相同。

   假设同机 GPU 0 已获准访问 GPU 1 的 peer memory：GPU 0 的 kernel 可以读取自己的源数据，直接写 GPU 1 的目标地址，GPU 1 无需配对的 recv kernel。反过来，也可以由 GPU 1 的 kernel 主动读取 GPU 0。NVSHMEM 的单边 `put/get` 也不要求目标端匹配一次 recv。[CUDA peer access](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html#peer-to-peer-memory-access)、[NVSHMEM RMA](https://docs.nvidia.com/nvshmem/api/latest/gen/api/rma.html)

3. **通信 API 要求两端匹配调用。**  
   传统 NCCL `ncclSend/ncclRecv` 确实要求两端分别调用，这是这组 API 的双边契约，但不能简单理解为“一次调用必然对应一个独立 kernel”。而 NCCL 自 2.29 起也提供不要求目标端匹配数据操作的 `ncclPutSignal`。[NCCL 双边与单边通信](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2297/user-guide/docs/usage/p2p.html)

**041 · 助手 / 正式回答** · `2026-11-03T03:04:10.124Z` · `msg-9adeb1bac8a0077517b5`

可以。一个典型例子是：**CPU 尚未处理前一步的停止结果，后一步 GPU 工作就已经提交了。**

假设都发生在 **D 节点**：

- 旧请求 **X** 使用 `block 7`。
- 新请求 **A** 随后需要接收远端 KV。
- 系统允许多个计算步骤在途。

一种可能的执行顺序是：

1. CPU 已为 X 提交 **S1、S2**。S2 可能正在排队，也可能正在执行。
2. CPU 收到 S1 的输出，发现停止 token，例如 EOS，于是标记 **X 已结束**。但这个状态修改不会自动撤回 S2。
3. **假如立即回收** `block 7`，新请求 A 就可能分到它，并通过 connector 将自己的 KV 写进去。
4. X 的旧 S2 随后仍按原来的地址和索引写 `block 7`。它不会重新询问 Scheduler：“这个块现在属于谁？”
5. A 的数据被 X 的旧写入覆盖。**网络传输本身可以成功，但缓存仍然被污染。**

这里不要求 S1、S2 同时运行。它们可以遵守 GPU stream 的顺序；危险来自**新 connector 的写入与旧 GPU 工作之间没有自动建立顺序关系**。

真实保护会这样处理：

**047 · 助手 / 正式回答** · `2026-11-03T03:07:34.112Z` · `msg-6bc007f7e723cd214674`

是的。**GPU 之间的数据搬运可以由 CPU 提交，而且这次搬运可以完全不启动 GPU 通信 kernel。**CPU 负责下达命令，并不意味着数据要经过 CPU 内存。

有两种直观例子：

1. **同一机器内：拷贝引擎搬运。**  
   CPU 调用 `cudaMemcpyPeerAsync`，指定源地址、目的地址和长度。条件满足时，CUDA 利用 GPU 的专用 **Copy Engine（拷贝引擎）**及 NVLink/PCIe 路径搬运。拷贝引擎不是执行 CUDA 线程块的 SM，因此不需要两张卡分别运行 send/recv kernel。[CUDA 官方说明](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html#peer-to-peer-memory-transfers)

2. **跨机器：网卡搬运。**  
   **NIC = Network Interface Card，即网络接口卡，通常就叫网卡。**具备 RDMA 能力的网卡常称为 RNIC。在支持 GPUDirect RDMA 的环境中，CPU 准备并提交操作，网卡可以直接访问 GPU 显存，数据路径是：

   ```text
   源 GPU 显存 → 源端网卡 → 网络 → 目标端网卡 → 目标 GPU 显存
   ```

   这条路径可以由网卡的 DMA 硬件完成，不要求两端 GPU 各运行一个通信 kernel。[GPUDirect RDMA 官方说明](https://docs.nvidia.com/cuda/gpudirect-rdma/index.html)

这里要分清：**CPU 提交命令，拷贝引擎或网卡搬运字节，GPU 的 SM 执行计算 kernel。**目标 GPU 后续计算仍要等搬运完成，并满足内存可见性要求；“不用通信 kernel”不等于“不用同步”。
