**026 · 助手 / 正式回答** · `2026-11-05T05:07:15.388Z` · `msg-9dc82c3e00778ec35fc9`

检查 3 两点都正确，已关闭。

**两张卡仍然可以并行，但中间确实有通信依赖。** 关键在于：本层 K/V 从本层输入生成，不需要等本层 attention 输出。

因此，每层的顺序是：

1. **并行生成**：rank 0 生成第 0、3 段的查询与缓存状态；rank 1 同时生成第 1、2 段的。
2. **交换缓存状态**：通过 gather，让需要的远端数据就绪。
3. **并行计算 attention**：两端分别计算自己负责的查询行。第 3 段需要第 1、2 段的 K/V，此时它们已经生成，不必等待那两段的 attention 输出。[固定源码对应顺序](https://github.com/vllm-project/vllm/blob/d7ada3aace051fecec553c185225db2259c2ac6a/vllm/model_executor/layers/attention/mla_attention.py#L854-L895)

因果 mask 限制的是**查询能看哪些位置**，并不要求同一层按位置顺序算完输出。通信和负载不均衡仍会带来等待，所以加速比需要实测。

**035 · 助手 / 正式回答** · `2026-11-05T07:20:48.224Z` · `msg-e83a6f1cc0410cdbcffe`

这里的**额外预留**，指为这条请求尚未产生有效 KV 的后续位置，提前准备缓存空间。例如，推测解码会为候选 Token 分配 `lookahead` 槽位。[固定版本源码](https://github.com/vllm-project/vllm/blob/d7ada3aace051fecec553c185225db2259c2ac6a/vllm/v1/core/kv_cache_manager.py#L395-L397)

例如每块容纳 16 个位置：

- 已有 32 个有效位置：最少需要 **2 块**。
- 再为后续 8 个位置预留空间：需要容纳 40 个位置，因此占用 **3 块，共 48 个槽位**。
- 此时有效 KV 仍只有 32 个位置；另外有 8 个预留位置和 8 个因块粒度产生的空槽。

所以“本例额外预留为零”就是：**只按当前的 T 个有效位置计算所需块数，即 `ceil(T / block_size)`。** 尾块没填满产生的空槽仍然存在。

这里讨论的是请求占用哪些块；整个 KV cache pool 提前申请显存，是另一层的预分配。

**065 · 助手 / 正式回答** · `2026-11-05T14:39:29.105Z` · `msg-88eeabc7c0f897961fc4`

我们先把“状态”理解成**显存里的一个数组**。下面先只看递推矩阵，卷积尾部稍后再说。

每处理一个新 Token，这个数组里的数值就会被更新。如果现在数组已经包含前 1000 个 Token 的影响，仅把“已处理长度”改成 960，**数组里的数值不会自动恢复到处理完第 960 个 Token 时的样子**。要恢复那个版本，需要之前保存过它，或者从更早的位置重新计算。

接下来把三种额外空间分开看。

**第一种：`1 + num_speculative_blocks`，用于留下几个可能被选中的结果。**

假设模型已经处理完“我今天想吃”，并采样出了“一”。“一”的 Token ID 已经确定，但还没有作为下一步输入送回模型。

drafter 又提出四个候选：“碗”“热”“汤”“。”。这里把每个字或标点当作一个 Token 举例。

这一轮 target 处理“一”和四个候选时，可以保存五个矩阵版本：

```text
槽0：处理完“我今天想吃一”的矩阵
槽1：处理完“我今天想吃一碗”的矩阵
槽2：处理完“我今天想吃一碗热”的矩阵
槽3：处理完“我今天想吃一碗热汤”的矩阵
槽4：处理完“我今天想吃一碗热汤。”的矩阵
```

假设验证后只接受“碗”“热”，拒绝“汤”，并重新采样出“面”。

下一轮应该从**槽 2 的矩阵**继续处理“面”。不能直接用槽 4，因为它已经包含“汤”和“。”的影响。

有了槽 2，就不必回到“我今天想吃”的状态，把“一碗热”重新算一遍。

因此，这个默认 GDN 实现里的数量是：

- `1`：处理普通输入“一”之后的结果。
- `4`：分别处理四个候选之后的结果。
- 合计五个可能的接受边界，所以需要 `1 + 4` 份矩阵容量。

**第二种：`align` 中的 `2`，用于旧状态与新状态之间的安全交接。**

假设 128 正好是这个例子里的状态块边界，旧格子保存着“处理完前 128 个 Token”的矩阵。现在要继续处理第 129 个 Token：

1. 保留旧格子的内容。
2. 把旧矩阵复制到一个新格子。
3. 在新格子上处理第 129 个 Token，得到新矩阵。

此时有两份不同的内容：旧格子对应前 128 个 Token，新格子对应前 129 个 Token。这就是基础规划中的两份容量。

旧版本可能仍用于读取或前缀复用，因此不能在它还被使用时直接覆盖。继续在同一块范围内处理第 130、131 个 Token，可以更新当前运行格子；并不是每个 Token 都复制一次。

**第三种：`num_prefill_checkpoint_blocks`，用于刻意留下一个中途结果。**

假设已经处理完前 512 个 Token，这一轮 prefill 要一直算到第 1000 个。

系统还希望保存“处理完前 960 个 Token”的状态，供以后复用。因此：

- 从“完成 512”的旧状态开始计算。
- 算到 960 时，另外保存一份。
- 继续算到 1000，得到当前请求的最终状态。

“完成 960”的状态就是额外检查点。以后另一个请求拥有相同的前 960 个 Token，且其他层也有匹配的缓存，就可以从这个边界继续，省掉前缀重算。

所以它即使在**没有推测解码**时也有用途。

上面为了讲清楚，只追踪了递推矩阵。实际恢复计算时，**卷积尾部也必须对应同一个前缀**；GDN 用扩展历史窗口来配合选中的矩阵。
