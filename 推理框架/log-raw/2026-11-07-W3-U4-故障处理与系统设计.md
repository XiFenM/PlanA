**023 · 助手 / 正式回答** · `2026-11-07T09:17:29.176Z` · `msg-41dc19042333e16abb34`

因为**“一次读取完成”这个事件，可能对应多次通知发送**。重复通知不代表 A 又读取了一遍 KV。

例如，假设某个通知协议支持应用层确认与重发：

```text
A → P：发送 (R, b, A)
P：收到并记录“A 已结束读取”
P → A：返回确认，但确认丢失或连接中断
A → P：无法确定上次是否送达，于是重发 (R, b, A)
```

P 就可能收到两次相同事件。**重试的是通知送达，读取尝试仍然是 b，所以标识不应该变。**“消息已接收，但确认没有返回”也是官方消息系统文档列出的重复来源。[Azure Service Bus 说明](https://learn.microsoft.com/en-us/azure/service-bus-messaging/duplicate-detection)

另外，进程重启后重放未确认记录，或代码中的两条完成路径都发布同一事件，也可能造成重复。

这里要区分**应用层重新发送通知**与底层报文重传。题目是在假设通知可能重复交付，用来检查幂等处理；我们尚未证明固定 NIXL 的实际通知链会出现这种重复，是否需要这一层判重仍取决于它的交付合同。

**062 · 助手 / 正式回答** · `2026-11-07T13:25:41.179Z` · `msg-78a47e59b656f79c2c19`

**W3 主要准备的是：推理框架中的分布式执行、KV 数据通路，以及加速器后端适配能力。**它把“理解模型和框架”进一步推进到“能设计跨机交接、分析成本，并保证异步执行正确”。

按照[活动计划的岗位定位](/root/workspace/learning/PlanA/计划/高级AI框架开发工程师-八周证据冲刺计划.md:84)，它同时服务于通用框架岗和 PD／通信专项岗，但要求的深度不同。

| 岗位需求 | W3 对应内容 | 希望你具备的能力 |
|---|---|---|
| vLLM／SGLang 框架开发 | 单元一的 Scheduler／Worker、KVConnector、生命周期 | 能追踪一次请求，解释调度、传输和计算怎样衔接 |
| 模型适配与内存优化 | 单元二的 GQA／MLA／hybrid、分页读取、TP／CP | 根据真实缓存表示判断容量、布局及交接条件 |
| 多机推理与性能分析 | PD 取舍、KV bytes、带宽下界、RDMA 路径 | 能判断通信是否值得、瓶颈在哪里、优化应测什么 |
| PD／通信后端集成 | 单元三、四的注册、完成、设备直传、中转与故障 | 能接入新平台，并处理访问依赖、错误传播和资源回收 |

这些对应关系有直接的岗位依据。例如，AMD `87545` 明确要求理解 KV Cache，并诊断多 GPU／多节点的计算、内存和通信瓶颈；专项岗位则直接写出 P/D disaggregation，以及基于 RCCL、RDMA 的多机推理。[框架岗位要求](https://careers.amd.com/careers-home/jobs/87545?iis=Job+Board&iisn=Linkedin&lang=en-us)、[分布式推理岗位要求](https://careers.amd.com/careers-home/jobs/96122)、[推理运行时岗位要求](https://careers.amd.com/careers-home/jobs/96120)。

其中，**重复通知、超时后能否回收、旧 DMA 如何处理**，是我们把“可靠的软件与后端集成”展开后的工程检查项。通用框架岗未必深入到每个细节；明确负责 PD、RDMA 或通信 runtime 的岗位，更值得为这些追问做准备。

面试可以从下面六类问题切入。这些是根据岗位职责推演的代表性问法，并非已核实的公司真题。

| 方向 | 主问与可能的追问 | 主要考察什么 |
|---|---|---|
| **1. PD 的价值与取舍** | “为什么拆 prefill 和 decode？”→“为什么拆完 TTFT 反而变差？”→“什么负载下你会选择合并部署？” | 是否能同时考虑计算干扰、排队、KV 搬运和资源利用率，而不只讲收益 |
| **2. KV 的规模与表示** | “给定模型配置和上下文长度，要传多少 KV？”→“TP 翻倍一定减半吗？”→“换成 MLA 或 hybrid 呢？” | 能否从实际张量和分片方式推导，而不是机械套公式 |
| **3. 框架执行与正确性** | “P 算完后，D 怎样开始 decode？”→“谁发起传输、谁决定可以调度？”→“传输成功但输出错误，你先查什么？” | 能否分清调度状态、传输完成、布局映射和设备消费依赖 |
| **4. 新设备适配** | “给一种新加速器接入 PD，你会改哪些层？”→“只有 Host RDMA 怎么做？”→“CPU 发起是否意味着不能设备直传？” | 能否划清 platform、connector、native backend 和设备 runtime 的职责 |
| **5. 故障与资源生命周期** | “请求超时后，可以立即归还目标块吗？”→“重试用了同一块怎么办？”→“重复完成通知、peer 重启如何处理？” | 是否理解业务失败与后台访问结束的区别，以及身份、幂等和安全回收 |
| **6. 验证与性能归因** | “你怎么证明改造正确且更快？”→“mock 测试能证明什么？”→“网络带宽很高，端到端为什么仍然慢？” | 能否设计有效的断言和分段测量，并准确限定证据范围 |

一条完整的系统设计追问可以这样展开：

> “设计一个跨机 PD 服务。”  
> 接着问：“交接多少数据，成本是否能接受？”  
> 再改条件：“目标芯片不支持设备直传。”  
> 最后制造故障：“D 已经超时，但旧传输还可能写入，你怎么收尾？”

这正好贯穿了 W3 四个单元。面试官可以借同一个案例，逐步检查你的模型理解、框架知识、性能判断和工程可靠性。

**对你而言，最值得准备的表达入口是“新加速器上的 PD/KV 适配”。**它与你已有的 PyTorch／vLLM 适配背景连接最自然。回答时先交代场景和平台能力，再讲数据路径、依赖、失败处理与验证；对这次 W3 形成的内容，明确表达为固定源码学习和方案设计，实际项目经历则引用你真正做过的部分。
