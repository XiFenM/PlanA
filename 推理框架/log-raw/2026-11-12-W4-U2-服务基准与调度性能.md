**009 · 助手 / 正式回答** · `2026-11-10T08:13:08.776Z` · `msg-9f2c09a086b3ee5b9f66`

是的。**一条输出消息可能对应一个 token，也可能合并多个 token 的文本。**模型生成的粒度与服务端发送消息的粒度不必一致。

例如模型依次生成 `T₁、T₂、T₃`，客户端可能收到两条消息：

```text
消息 1：[T₁]
消息 2：[T₂、T₃]
```

这时生成了 **3 个 token**，但客户端只记录到 **1 个消息间隔**。所以本课里的 raw ITL 是相邻输出消息的时间间隔，不能默认等同于逐 token 的生成间隔。

另外，`usage`、`[DONE]` 等元数据或结束消息不携带生成内容；所选适配器不会把它们计入上述输出事件。

**022 · 助手 / 正式回答** · `2026-11-10T15:09:47.133Z` · `msg-a49aa16b4955840398da`

TPOT 能说明：**在本次测量口径下，一条请求从首个输出到最后输出，平均每个后续 token 消耗多少时间。**它衡量的是请求的**平均输出节奏**。

它能支持很具体的性能判断：

- **输出长度相同**时，TPOT 更低，意味着首个输出到最后输出这段时间更短。
- 如果 **TTFT 也相同**，那么这条请求的 E2EL 也更短。

因为：

\[
E2EL=TTFT+(L-1)\times TPOT
\]

沿用刚才每条消息对应一个 token 的例子：

```text
甲的三个间隔：[40, 40, 40] ms
乙的三个间隔：[10, 10, 100] ms
```

两者 TPOT 都是 40 ms。它准确地告诉我们：**两者从首输出到末输出的总耗时相同，平均输出速度相同。**但乙的节奏更不均匀，这需要 raw ITL 才能看出来。

因此，TPOT 适合比较“持续输出阶段平均有多快”；至于速度变化是否由调度优化造成，则需要另外的受控对照和归因证据。

**024 · 助手 / 正式回答** · `2026-11-10T15:13:48.087Z` · `msg-8ceda62605448525041c`

**当你关心“开始输出之后，一条请求平均生成得有多快”时，就要看 TPOT。**尤其适合输出较长的场景。

以一个生成长报告的聊天服务为例：

- **首段很快出现，但完整回答迟迟出不完。**看 TPOT，可以判断后续输出阶段的平均耗时；输出长度相同时，TPOT 越低，这一阶段结束得越快。
- **比较两种服务配置。**固定模型、精度、负载和测量口径后，用 TPOT 比较单请求的平均输出速度，再用其他证据解释变化原因。

- **制定服务目标。**用 TTFT 约束首段等待，用 TPOT 约束后续平均输出速度，再统计同时达标的请求速率，也就是 goodput。

- **本轮有哪些请求参加执行？**结束的请求退出，符合条件的新请求可以加入后续批次——这是 Continuous Batching 的动态组批行为。
- **每个请求本轮处理多少 token 位置？**根据请求进度和预算分配工作量——这是 token 粒度的调度。

例如，一份计划可以是：

```text
{请求甲: 1 个位置, 请求乙: 6 个位置}
```

键表示批次成员，值表示本轮工作量。在普通生成的例子里，甲可能进行一次 decode，乙处理一段 prefill。vLLM V1 的同一个 `schedule()` 会处理已有 running 请求、考虑 waiting 请求准入，并生成这样的逐请求计划。[固定源码](https://github.com/vllm-project/vllm/blob/d7ada3aace051fecec553c185225db2259c2ac6a/vllm/v1/core/sched/scheduler.py#L621-L766)

但**仅仅“按 token 分步执行”还不足以说明采用了 Continuous Batching**：固定的一组请求也能每轮各算一个 token；如果新请求仍必须等整组全部结束才能进入，就缺少连续的动态准入。

因此，把 Continuous Batching 理解为**迭代级动态组批的基本机制**更准确。token 预算是实现它时分配工作量的方式；Chunked Prefill 则进一步让长输入也能分多轮参与这种安排。

```text
矩形表示：[[a, PAD, PAD], [b0, b1, b2]]
```

不是。这里 **ready 表示“已有下一步工作，可以被调度执行”**。

这句话可以读成：

> 在 P 产生首个输出之前，原有 decode 请求一直没有结束；每到一个调度边界，它们仍有下一个 token 需要计算。

**105 · 助手 / 正式回答** · `2026-11-12T06:22:05.540Z` · `msg-be47d00caa789ac80456`

**本次需要的是独立的正确性检查；CPU FP32 是我选择的实现方式，并不是性能实验的必需条件。**

我们比较两档调度预算，希望测到的是“同一个模型任务执行得怎样”。请求返回成功、输出长度一致，还不足以确认计算结果正确。因此用了三个设计：

- **Transformers 作为独立实现**：用同一权重、同一输入，核对 vLLM 的输出概率，避免只让两个 vLLM 配置互相证明正确。
- **FP32 作为数值参考**：减少参考计算自身的舍入误差，再允许 BF16 结果在预定容差内偏离。这里是把原有权重提升到 FP32 计算，并不能恢复权重存储时已经损失的精度。
- **CPU 作为执行位置**：让参考计算不占用服务的 GPU 显存。这是资源安排，并不意味着 CPU 天然比 GPU 更正确。

具体检查的是少量输入、几个生成位置上的概率与贪心选择，**不是评估模型回答质量，也不计入性能时间**。

这次 CPU 路径的耗时确实偏大，是这个方案的工程代价。原则上也可以用分阶段执行的 GPU FP32 参考；关键是参考实现、输入条件和数值判据可靠，并与性能计时分开。

**130 · 助手 / 正式回答** · `2026-11-16T00:39:18.158Z` · `msg-49d8dd94ca70f41ebf5f`

**这两个值可以不相等。** 在课程页引用的 `d7ada3aa` 版本里，调度器会同时遵守它们：

- **`max_num_scheduled_tokens`，记作 S**：这轮最多下发多少个待前向计算的 token 位置。
- **`max_num_batched_tokens`，记作 B**：执行侧输入批次的容量上限，也用于准备输入缓冲区等资源。

两项都作用于混合 batch，prefill 和 decode 共同消耗额度。[配置定义](https://github.com/vllm-project/vllm/blob/d7ada3aace051fecec553c185225db2259c2ac6a/vllm/config/scheduler.py#L48-L60)

我之前那句话需要补完整：**没有额外槽位开销时，不相等也能用 `min(S, B)` 表示有效的 token 上限。设成相等，只是让教学示例更简单。**

先看普通 Chunked Prefill。假设这一轮：

- 没有投机解码，KV 和请求名额充足，其他限制不触发。
- 按给定顺序先安排 64 条 decode，各占一个位置。
- 随后安排一条还剩 6000 个位置需要计算的长 prompt。

那么分配结果是：

| B：执行容量 | S：调度上限 | decode 用掉 | 本轮最多给 prefill |
|---:|---:|---:|---:|
| 4096 | 2048 | 64 | **1984** |
| 8192 | 2048 | 64 | **1984** |
| 4096 | 4096 | 64 | **4032** |
| 4096 | 8192 | 64 | **4032** |

第一行里，执行端虽然准备了 4096 个位置，调度器这轮只准下发 2048 个。所以安排完 `64 + 1984` 就停，剩余执行容量不会自动拿来补更多 prefill。

第二行只增大 B，S 仍然卡在 2048，调度量没有增加。第四行则相反：S 虽然更大，仍被 B 卡住。这是该版本同时检查两个余额的结果。[分配限制](https://github.com/vllm-project/vllm/blob/d7ada3aace051fecec553c185225db2259c2ac6a/vllm/v1/core/sched/scheduler.py#L758-L766)

那为什么不直接只留一个参数？

一个用途是**把执行容量和调度量分开控制**。例如 B 保持 4096，S 降到 2048，可以减少每轮下发的工作量，同时保留原执行容量。但降低 S 不会自动缩小所有按 B 创建的缓冲区；例如这个 ModelRunner 的 `input_ids`、`positions`、`inputs_embeds` 都会参考 B 分配。[缓冲区分配](https://github.com/vllm-project/vllm/blob/d7ada3aace051fecec553c185225db2259c2ac6a/vllm/v1/worker/gpu_model_runner.py#L764-L806)

另一个用途更关键：**某些投机解码路径会额外占用输入槽位，两项预算的扣法就不同了。**

把某条请求本轮安排的前向位置数记作 `q`，额外预留的槽位数记作 `draft_slots`。忽略其他约束，核心记账是：

```python
q = min(remaining, scheduled_left, input_left - draft_slots)
# 请求成功安排后：
scheduled_left -= q
input_left -= q + draft_slots
```

也就是说，S 只扣本轮安排的工作，B 还要扣执行该投机方法所需的额外空间。[初始化与扣账源码](https://github.com/vllm-project/vllm/blob/d7ada3aace051fecec553c185225db2259c2ac6a/vllm/v1/core/sched/scheduler.py#L639-L644)、[成功安排后的扣减](https://github.com/vllm-project/vllm/blob/d7ada3aace051fecec553c185225db2259c2ac6a/vllm/v1/core/sched/scheduler.py#L905-L912)

这个版本有一条很直观的官方测试：**S=B=20，每个选中的请求额外预留 3 个槽位，两条请求各有 10 个位置待处理。**

| 安排过程 | 下发位置 | 剩余 S | 剩余 B |
|---|---:|---:|---:|
| 第一条请求 | 10 | 10 | 7 |
| 第二条请求 | 4 | 6 | 0 |

最终只安排了 **14 个前向位置**，另外 **6 个槽位被预留**。S 还剩 6，B 已经用完，所以不能继续安排。这也说明：**有额外槽位时，即使 S 和 B 数值相等，也不能只记一本账。**[对应官方测试](https://github.com/vllm-project/vllm/blob/d7ada3aace051fecec553c185225db2259c2ac6a/tests/v1/core/test_scheduler.py#L2183-L2204)

这里的额外槽位由具体投机方法决定，并非所有方法都固定为 3；已经作为本轮验证输入的草稿 token，也可能已经计入 `q`，不能把两者重复计算。[额外槽位定义](https://github.com/vllm-project/vllm/blob/d7ada3aace051fecec553c185225db2259c2ac6a/vllm/config/speculative.py#L1949-L1990)

实际规划时，普通 Chunked Prefill 可以让 S 保持 `None`，由它继承 B；如果要保留执行容量、单独收紧每轮调度量，再显式设置较小的 S。开启会追加槽位的路径后，则要分别看两项余额，并继续检查 KV、请求名额等约束。**预算是“最多能安排多少”，不是调度器必须填满的目标。**
