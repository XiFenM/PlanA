## 请求进入、调度与 token 记账

- [要点] **C01：EngineInput、EngineCoreRequest 与内部 Request 有什么区别？**前端输入与参数被整理成跨 IPC 的核心请求，再由 Core 构造可变内部状态；完整转换链见[学习文章](../深入学习理解vLLM/2-Request-Lifecycle-and-Output.md#请求全流程讲述稿)。（用户：`msg-e819ac4c571f46d47008`；澄清：`msg-101f90a3f3dc1bd25874`）

- [高价值问题] **C02：Collector 根据什么创建？**我追问“创建RequestOutputCollector应该也需要有一些依据信息数据的吧”。澄清它可以先用请求 ID 和输出模式创建空接收器，随后注册输出状态，并不依赖模型已经生成结果。先注册再向 Core 提交的依据后来由用户定位到源码。（提问：`msg-f6942eb47b9bc34aecb0`；解释：`msg-0effa80817135f42f9b5`；源码定位：`msg-0b683086ea18cdd7cc81`）

## ModelRunner、映射与 Attention

- [要点] **D01：不在本步 InputBatch，是否意味着请求必须被彻底删除？**不意味着。MRV1 中未结束请求可以退出本步 batch，同时保留 CachedRequestState。恢复时不能凭残留旧 block IDs 推断仍拥有旧 KV 块。（用户：`msg-1075b03d569ff50b4048`；精确说明：`msg-cdcb5a63cc9cd86b34f6`、`msg-9a3057777ef926170a28`）

- [要点] **D02：恢复请求的新块列表为何替换旧列表？**恢复载荷提供恢复后的完整映射；普通继续执行的载荷提供增量块。用户正确区分了旧 4、5 与新 12、13 在两种场景下的处理。（用户：`msg-472ed16d43f17a0e7e6b`；说明：`msg-9a3057777ef926170a28`）

- [要点] **D03：逻辑位置怎样映射到 KV token 槽位？**在普通单组且分配块与 kernel 块大小相同的教学条件下，位置 p 的槽位为 `block_table[p // B] × B + p % B`。它是 token 槽位索引，不是字节地址；物理块换号不自动改变 input_ids 或 positions。（用户：`msg-ccf4c4c5ab87ad27d19e`；说明：`msg-16c3ec7bafe6ce7d8917`、`msg-c3e7491470e940e971e1`）

- [纠错] **D04：slot_mapping 的直接职责是写新 KV。**场景：batch 重排。我说“slot_mapping也需要跟着调整改变……否则会取到错误的历史kv cache”。→ 旧 slot_mapping 会让新 KV 写错槽位；历史上下文的读取则需关注 block table 的请求行与逻辑块映射。原因：写入定位与读取上下文不是同一条映射。（原答：`msg-e0c640e9ee5bad502212`；纠正：`msg-727fda5e3164a401c84f`；反例解释：`msg-4da89d2907b0401b55f9`）

- [高价值问题] **D05：block table 的哪种顺序随 batch 改变？**我说“C和D的block table顺序应该不变”，随后澄清：每个请求行内的逻辑块映射不变，但二维表的请求行必须跟随 batch 从 C、D 重排为 D、C。此处保留“行内顺序”和“批次行顺序”的区别，不把可能的简称当成完全不懂映射。（来源：`msg-e0c640e9ee5bad502212`、`msg-727fda5e3164a401c84f`、`msg-4da89d2907b0401b55f9`）

- [要点] **D06：query_start_loc 与 seq_lens 分别表示什么？**前者描述本步展平 query 的请求片段边界，后者描述对应序列长度。历史长度为 2、6，本步处理 3、1 时，分别得到边界 0、3、4 与长度 5、7；长度为 5 不表示位置 2 的 Query 能看到未来位置 4，也不能跨请求读取 KV。（用户：`msg-6caf70b29eb2e6a2c66b`；说明：`msg-8401f182d8c892a1e9c0`）

- [要点] **D07：相同 shape 是否足以复用旧 Attention metadata 内容？**不足。缓冲可以复用，内容仍要对应本步请求、序列长度与 KV 映射；模型层和预分配 KV tensor 无需因此重建。（用户：`msg-e8bdff5f94f5feca2164`；说明：`msg-73210be9cf9e85c201f4`）

- [要点] **D08：统一 Attention custom op 是否已经确定真实 kernel？**未必；还要追选定 backend、metadata、布局和底层绑定。用户的主要判断正确，但“某个最优的kernel”需收紧为实际选定实现，最优性需要性能证据。（用户：`msg-54b0ed4f9bc93bc18a08`；澄清：`msg-be31c85c3e5a29f42aa5`、`msg-68bb507f1d8d6e1159bf`）

- [要点] **D09：不参与数值计算的 KV 依赖参数能否删除？**不能仅因函数内不使用它就删除。所学 `kv_cache_dummy_dep` 显式表达图中 KV 更新先于 Attention 读取的依赖；它不是通用设备 event／stream 同步机制。（用户：`msg-54b0ed4f9bc93bc18a08`；说明：`msg-be31c85c3e5a29f42aa5`）

- [高价值问题] **D10：execute_model 返回 None 后，sample_tokens 只是领取现成 token 吗？**不是。所学分离路径中，前者计算并暂存 logits，后者应用采样约束并真正采样；可以将模型计算与 grammar mask 准备分别安排。None 表示这个分支尚未产生完整输出，不是执行失败或轮询信号。（提问：`msg-249c2d66ecc6580a5eeb`；解释：`msg-db950a283c4642b8249e`；用户接口回答：`msg-70930dd44b0da8ebe9bf`）

## 设备扩展与契约

- [要点] **P01：选择 Attention backend 会自动替换 Worker 吗？**不会。平台配置中的 Worker 选择与 Attention backend 选择是不同入口，Runner 再由 Worker 构造。HTTP 协议与设备层是否需要修改，要看接口语义，不能只看进程是否分开。（用户：`msg-363ce9217532c5154c2f`；说明：`msg-34ae61b9d256a5f66fda`、`msg-1ce78dd4de073bbc133f`）

- [纠错] **P02：注册是接入动作，不是正确性契约。**场景：适配矩阵的契约列。我填“通过register_oot进行注册”。→ 接入方式是 register_oot／forward_oot；必须保持的契约是数学语义、支持的 shape／dtype／device、输入修改与返回约定以及执行依赖。原因：回答了怎样接入，没有回答接入后必须保持什么。（原答：`msg-85b4dc0a66d1bf0e8bcd`；澄清：`msg-0cc532706b654b4bd6b5`）

- [要点] **P03：torch.ops 注册与 forward_native 各意味着什么？**用户已正确区分：注册底层算子不保证 vLLM 自动采用它，还需接入模型调用路径；forward_native 表示原生 PyTorch 组合，不等于改在 CPU 上计算。（用户：`msg-ab348ebeef5ce1120ccc`；对应知识回查：[六层适配矩阵](../EP-PD自研芯片适配设计与验证包.md#pass-e-adaptation-matrix)）

- [要点] **P04：为什么 collective 要测试多个子组？**用户主动补充：TP=1 可能绕过通信；只有一个组且恰好等于 world 时，错误使用全 world 的实现也可能通过。两独立组中的数值 1、2 与 10、20，正确组内和应分别为 3、3、30、30。（用户：`msg-37b0347a98730a08bfba`；说明：`msg-965e651fc6812891b5af`、`msg-130811180e42d08113f0`）

- [要点] **P05：出现 OOM 是否足以主张修改 Core？**不够。用户正确区分页大小误报与正常池压力：接口能表达真实占用时先修插件；正常压力由既有等待／抢占／恢复处理。只有明确现有接口无法表达所需语义或保证，才有进一步论证核心修改的依据。（用户：`msg-ce5ee79bcb1309e0c71e`、`msg-2ca93a171ca17990b86e`；说明：`msg-8261b27ba87cc5681b4e`）

## KV 账本、前缀缓存与硬件旁支

- [要点] **K01：普通全注意力的每 token KV 字节数如何计算？**在 K/V head 维度相同、无压缩与额外元数据的条件下，单层有效 KV 数据为 `2×Hkv×D×每元素字节数`，尚未计入物理 padding。课堂的 Hkv=8、D=96、BF16 得到 3 KiB；注意使用 KV head 数而不是 Query head 数。（用户：`msg-b53bc597590e6fdb4c84`；讲解：`msg-c0aff2853e5e047139ea`）

- [要点] **K02：末块未用槽位与页 padding 是同一项浪费吗？**不是。用户正确核对 35-token、B=16、3 KiB/token、单层页跨度 64 KiB 的账本：105 KiB 有效数据、39 KiB 未用槽位、48 KiB padding，共 192 KiB。（用户：`msg-b53bc597590e6fdb4c84`）

- [高价值问题] **K03：页跨度是否代表每次设备内存分配的最小粒度？**用户问“每次内存分配至少分配64KiB大小是吗？”澄清了基址对齐、相邻页跨度与分配器取整三个层次；教学 64 KiB 不能自动当作 OS 页或最小分配粒度。48 KiB 已能被 512 B 整除，也不能仅用 512 B 搬运解释为什么补到 64 KiB。（用户：`msg-b53bc597590e6fdb4c84`、`msg-4ed079c7f08310d6f8fb`；说明：`msg-37a9c38e149d44818b0e`、`msg-01f2f394ccc353085b42`）

- [转折] **K04：512 B 与 256 Token 的旁支已有独立记录。**讨论先明确“kernel的搬运单元就是512Bytes”，再核对插件的 head 尾维 padding、BF16 D128 的 K/V 合并，以及 page_size_bytes 两类消费者。具体源码与算术只引用[已有记录](2026-09-07-kv-padding-block-size.md)，不在此重写。（来源：`msg-0002a243c712b9bd9a11`、`msg-d57aacd95873791f0d90`、`msg-bc26a3782f509762ab6b`、`msg-93a31dac3ca78f4935d8`）

- [高价值问题] **K05：统一页大小接口为何需要改消费者？**用户总结“但在其他代码逻辑处需要进行对应的重构调整”。当前插件把物理预算与逻辑 tensor 字节数反推块数分开使用；只换 getter 会混用分子、分母的含义。统一接口可以讨论，但本轮没有实施或验证重构。（用户：`msg-58ca01b5bb4a617507cc`；说明：`msg-93a31dac3ca78f4935d8`）

- [转折] **K06：256 的性能选型原因来自同事反馈，不是本轮实测。**用户转述“kernel内部实际上也可以兼容其他大小的block size”，当前选 256 是为了配合矩阵乘单元与访存。应标明转述来源，不能变成硬件仅支持 256 或所有负载都实测最优；512 B 与 256 Token 也不能直接等同。（用户：`msg-58ca01b5bb4a617507cc`；限定：`msg-076759558532b7b2eda2`）

- [要点] **K07：多个请求如何计块，跨层如何计页？**R35、S17、B16 且无共享时，应先分别取整得到 3+2=5 个 pool IDs，32 层对应 160 个单层页、10 MiB。用户的容量计算正确；“160个blocks”应明确为单层页数，不能与 5 个池内 ID 混称。（用户：`msg-0f5ba2d4385d82109505`；说明：`msg-d9ff0f03f9d6f188d055`）

- [要点] **K08：一个请求结束能否直接覆盖仍共享的块？**不能。用户在 R 使用 7、8、9，S 使用 7、10 的题设中，正确指出 R 结束不影响 S 对 7 的引用。物理池继续持有，活跃占用变化与设备内存分配量变化分开。（用户：`msg-29f52e941f384c2bdcc7`）

- [要点] **K09：为什么局部块 token 相同仍可能不能命中？**用户正确指出第二块不能脱离第一块的前缀身份复用。链式 hash 结合父 hash、当前 token 与额外键；不同 salt 禁止共享，也不意味着 KV 数值必然不同。解释整套模型 KV 对上下文的依赖即可，不扩大成每一层的 K/V 都必然依赖前文。（用户：`msg-f8d3584d7ddd2c3be47f`；说明：`msg-ebb7eb1748514ce33c3b`）

- [纠错] **K10：salt 的策略来自业务，不代表框架无需提供能力。**我说“推理框架本身实际上并无此需求。”→ 模型数值计算不依赖 salt，但服务框架可以提供并执行缓存隔离；业务决定信任边界。原因：计算正确性与多租户安全要求不同，缓存命中的延迟差异可能暴露前缀存在的统计线索。（原答：`msg-863eaec99083e29ca35d`；解释：`msg-bcc67da24252dcfc9a89`、`msg-434a30cb8cf501e75dae`）

- [要点] **K11：salt 是否应该每请求重新随机生成？**同一允许共享范围通常保持稳定，逐请求换 salt 会牺牲跨请求前缀复用。它隔离缓存复用范围，不等于身份认证、KV 加密或独立显存池。（提问及解释：`msg-f8d3584d7ddd2c3be47f`、`msg-bcc67da24252dcfc9a89`）

- [要点] **K12：零引用缓存块能否仍在 free queue？**可以。已有 KV 与可重新分配不冲突；覆盖前需要淘汰旧缓存标识。用户正确算出 6 个空闲块经 2 个正式命中引用和 1 个新分配后剩 3 个；剩余类别的具体拆分依赖未给出的出队顺序，不是用户机制错误。（用户：`msg-e7fad53690ecee8d1ecf`；题设及补充：`msg-2ff4aefdac8123305f85`、`msg-be0dfcf729cdd2198947`）

- [高价值问题] **K13：查到命中为何仍可能不加引用？**我问“如果一个块已经命中缓存，那么复用它肯定会增加计数呀。”随后理解为“仍可能因为资源不足问题而没有真的复用，所以就没增加引用计数。”查询取得候选，容量检查成功后才正式引用；成功路径先保护命中块再分配新块。这里也修正了导师此前将“命中”同时用于查询和占用的歧义。（提问：`msg-f36c5cf7b6cbfb247ebf`；澄清：`msg-ca49a054ad4d4c4d33b7`；理解转折：`msg-2958f34b58f9c6c6693d`）

- [转折] **K14：decode 使用上轮已知 token，计算本轮新 KV。**用户主动连接到“并不是处理即将要生成的那1个新token，而是计算前一步刚生成的那一个旧token”。这与 C05 的记账修正相互印证；刚采样得到 ID 不代表其 KV 已产生。（用户：`msg-2958f34b58f9c6c6693d`；确认：`msg-81b99cd65a8428f98f1c`）

- [要点] **K15：pool 无空闲块，是否所有请求都不能继续？**用户正确区分了末块仍有槽位与必须跨块的情况：B16，47 KV tokens／3 块再处理 1 token 无需新块；32／2 块则需要新块。判断依据是本步新增块需求，不是仅查看 free 数是否为零。（用户：`msg-5650923c5387a450d90e`）

- [要点] **K16：关闭 Prefix Cache 会关闭分页存储吗？**不会。用户准确区分 PagedAttention 的分页访问与 Prefix Cache 的计算结果复用；同 prompt 不能仅因启用分页就跳过重复 prefill。（用户：`msg-436cec094a6f099ba85b`；说明：`msg-9095be26cb5636431f42`）

- [要点] **K17：活跃块容量减少，为什么物理 pool 仍可不变？**用户正确算出两个请求共享首块时占 3 个 ID／6 MiB，关闭共享占 4 个 ID／8 MiB，而物理 pool 均为 20 MiB。随后把“预分配所有可能需要的内存”收紧为按 KV 预算预分配。没有把这处措辞收紧误记成容量算错。（用户：`msg-b259fc84adf29199c4bd`；限定：`msg-0a0609c1af4b11f3b3c8`；确认：`msg-2967365f3f78785d3428`）

## 整段复述中复发的偏差

- [纠错] **R01：Worker 初始化与每步执行分开。**场景：讲述一次 SchedulerOutput 的执行。我说“经过executor下发和worker处理设备环境初始化”。→ 服务已就绪时，Worker 的本步执行入口不重新初始化设备；它再委托 Runner 执行。原因：把启动生命周期的职责放进了热路径。（原答：`msg-38e7de4a5e23f9e77f43`；澄清：`msg-dfe4e64d7fae65874e43`）

- [纠错] **R02：FINAL_ONLY 过滤调用方结果，不延迟 Core 的全部返回。**场景：把 stream 改为 false。我说“EngineCore根据output_kind进行发送结果给前端。应该会等到整个请求完成，才把结果给前端。”→ 前端继续处理 Core 的增量结果，未结束时只抑制交给 Collector／调用方的中间 RequestOutput。原因：混淆了两层输出。早期导师也曾给出不准确的 Core 粒度解释，因此不能将其归为完全由用户独立形成的错误。（原答：`msg-38e7de4a5e23f9e77f43`；复问：`msg-00cf70124e7c503d5873`；正确说明：`msg-dfe4e64d7fae65874e43`、`msg-42ecb4fa8caaed6a04be`；早期误导：`msg-8c70a947169871bbb6a7`、`msg-a0d753e4aaeb1556b129`）

- [要点] **R03：三种 output_kind 的具体交付形态是什么？**CUMULATIVE、DELTA、FINAL_ONLY 的模式表与 Collector 聚合边界统一见[输出专题](../深入学习理解vLLM/2-Request-Lifecycle-and-Output.md#output_kind-与两层输出)，不把模式名称当成 Core IPC 的开关。（提问：`msg-00cf70124e7c503d5873`；解释：`msg-42ecb4fa8caaed6a04be`）

- [纠错] **R05：前端文本判停与 Core 控制操作名称不同。**我说“由前端再向执行层发送finish的信号”。→ 对外为 stop，向尚未结束的 Core 发送 ABORT。原因：用户可见的 finish reason 与内部控制消息不是同一语义；无需把枚举背诵独立设为能力门。（原答：`msg-cdf9d5590016714b4adf`；补充：`msg-ac482efcb222b8e03069`；非流式提前停止的正确判断：`msg-d6aeeeca7686f219e57c`）
