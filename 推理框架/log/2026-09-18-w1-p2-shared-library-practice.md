### P2-02 [要点] 链接时找到 lib-a，是否保证运行时仍加载它？

学习者事前判断会加载 lib-b，并解释 app 已确定需要 `compute(int)`，运行时的库可能不提供该实现。这里的不同点落在三个阶段：编译确定符号引用、链接时由 A 满足引用、运行时按本实验搜索环境装载库。两份库名称相同并不能代替符号核验。

来源：`msg-7ab9456a130e4d4d166d`、`msg-3679de0354dd7a2f9640`。本条为正确预测，不标为纠错。

### P2-03 [要点] 程序已经打印 READY，是否证明目标库函数可用？

学习者正确预测“能到达READY”，但实际调用将出现 undefined symbol。导师提前说明了实验的延迟绑定与停留点：库已装载，目标函数符号在首次调用时解析；因此 READY 只证明程序到达调用前的位置。

本机随后确实先输出 READY，再在 `compute(7)` 处报告 `_Z7computei` 缺失。该观察依赖本实验的延迟绑定设置，不能推广为所有动态链接错误都会延后到调用时。

来源：`msg-3f216fe8a376b8000533`、`msg-7ab9456a130e4d4d166d`、`msg-d0f46537968e94a585dc`。

### P2-04 [要点] 如何用二进制证据区分“需要什么”和“提供什么”？

学习者实际运行 readelf／nm，得到以下证据，而非仅根据源码猜测：

| 对象 | 用户提交的关键输出 | 本条支持的结论 |
|---|---|---|
| app 的动态依赖 | `NEEDED: libw1probe.so`，未出现 RPATH／RUNPATH | 本例依赖项是库名，没有记录 lib-a 的构建目录 |
| app 的动态符号 | `U compute(int)` | app 引用该符号而未在自身定义 |
| lib-a 的动态符号 | `T compute(int)` | lib-a 提供需要的定义 |
| lib-b 的动态符号 | `T compute(double)` | lib-b 提供的是另一个参数签名 |

用户结论：“app 需要的符号与lib-a中的库提供的符号匹配，与lib-b中的库提供的符号不匹配。”在本例中，同名 SONAME 不保证所需符号存在；动态装载也不会重新做 C++ 重载选择，把 `compute(int)` 自动替换成 `compute(double)`。

来源：第一段 `msg-b1b2aeb4848dd08f8d31`，重发及解释 `msg-4e20a3af407a9faf1f61`，导师核对 `msg-196bcacf0b4d67c171bc`。命令入口由导师提供，实际执行与解释由学习者完成。

### P2-05 [要点] ldd 指向 A、目标 PID 的 maps 指向 B，是否矛盾？

用户在 A 查询环境中运行 ldd，同时检查以 B 环境启动、停在调用前的目标进程。ldd 指向 lib-a，PID 102268 的 maps 指向 lib-b。

用户解释：“并不构成矛盾。因为在如上命令执行时，ldd查询的环境变量与app进程启动时的环境变量不一致”。该结论正确：当前查询环境的依赖解析与一个已有进程实际映射的文件，是两个不同观察对象。

后续触发真实调用得到 `_Z7computei` 错误，c++filt 还原为 `compute(int)`，与 app 的引用和 B 的缺失定义吻合。至此文件级证据、进程映射和实际调用错误串在一起。

来源：`msg-d0f46537968e94a585dc` → `msg-04fd609e2148520e9511`；实际进程记录见 `diagnostic_observation`。

### P2-06 [转折] 修复落实到启动入口，再核验新进程与目标调用

学习者提交启动脚本，在传入路径恰为 B 时改为 A，再启动指定 app。导师核对的是这份脚本已有的验收记录及哈希，没有代写脚本或重复运行已经通过的 B 用例。

新 PID 109803 映射 lib-a，实际输出 `RESULT 14`，退出码为 0，stderr 为空。这里同时使用“映射正确”和“目标函数调用正确”两类证据；仅看到程序启动并不足以裁决原故障已修复。

来源：`msg-7c8135757a5ca9eb19d8`、`msg-4b54b6dbb63934d81549`、`msg-3162f40d728373c318da`；实现见头部链接，运行记录见 `learner_run_parent_B`。

### P2-07 [要点] 没有再次执行 export，子进程还会得到已有环境变量吗？

把父搜索路径改为 A，学习者事前回答：“if条件不成立，不会执行export”，但 app 仍使用 lib-a，输出 `RESULT 14`。导师补充原因：脚本已经从父进程收到作为环境变量的 A 路径，后续 app 仍会继承它；这与仅创建一个未导出的 shell 局部变量不同。

同一脚本哈希下，A 变式的目标检查通过，新进程 PID 111409 映射 lib-a、调用返回 14。分支判断来自源码与输入推导，不把未采集的 shell 分支 trace 冒充实际记录。

来源：`msg-71c49c2b945acde0ee6f` → `msg-22bf4540c62fa9fbe68c` → `msg-822d7ed1cf02c2a5ef79`；见 `learner_run_parent_A` 与 `learner_variant_review`。

### P2-08 [要点] 两个父环境都通过，能推广为任意库搜索路径都被修复吗？

不能。本次只验证父 `LD_LIBRARY_PATH` 恰为 A 或 B 的自建程序；启动脚本按完整字符串比较，未验证任意冒号分隔目录列表、真实服务启动链或其他部署条件。分析稿保留了这个边界，未因小用例通过而把整个 C++／Linux 能力描述为已实证。

来源：`msg-822d7ed1cf02c2a5ef79`、`msg-0932322487ffce1040e8` → `msg-11cf11a5d492b08ef072`；分析正文见头部链接。
