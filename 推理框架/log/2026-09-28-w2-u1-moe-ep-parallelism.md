## 学习过程

<a id="input-output-ownership"></a>
### 1. 通信判断先固定输入与输出归属

- [转折] 首题只问把两个专家放到同一张卡，学习者说：“跨卡通信从原本的需要一次跨卡通信变成了不需要跨卡通信”。导师随后补明输入与最终输出的位置；在输入、输出归卡 0、两个专家都在卡 1 的变式中，学习者正确追踪去程与回程，并说：“此时两个专家在同一张卡无法消除跨卡通信。”
- 边界：首题缺少输入／输出归属属于导师题意缺失，不记为学习者概念错误。dispatch 与 combine 是逻辑阶段，不直接等于固定次数的通信调用。
- 来源：`msg-878f982879eff1fcd389` → `msg-59c2313d365bb68e4c34` → `msg-acab5b872f2a30c5a7e5`。

<a id="ep-input-layout"></a>
### 2. EP 与输入激活布局是不同问题

- [高价值问题] 学习者问：“每个卡上面处理的原始输入token是不一样的吗？EP会对输入token激活值进行切分吗？”
- 最小结论：EP 分配专家参数；进入 MoE 前的 Token 布局还取决于 DP、TP、SP 等组合。沿 Token 行分片与沿隐藏维 H 切分必须分开判断。在不叠加专家内部 TP 的算例中，专家消费完整的 H 维向量。学习者随后回答：“送给卡0的是完整的H维x\_2。combine后应归属卡1.”
- 来源：`msg-acab5b872f2a30c5a7e5`、`msg-4eaa7e3fd9985613a088`、`msg-8f3dc3c9064a2d27c5e3`。

<a id="ep-collective-misconception"></a>
### 3. EP 不与 All-to-All 必然绑定

- [纠错] 场景：学习者从输入复制的 TP+EP 路径理解本地专家计算后的结果合并。原话：“我一直以为开启ep之后必定会有all2all通信在moe计算中。”→ 正确：EP 本身不决定唯一通信操作；若各卡已有相同的完整输入、每个逻辑专家只在所属卡计算，且输出要求在各卡完整复制，可以对本地加权贡献做 SUM AllReduce。
- 原因：把专家参数分布与输入／输出激活布局绑定成了同一个结论。某卡没有该 Token 的本地专家贡献时，可在求和模型中贡献零向量；输入复制不等于专家贡献重复计算。
- 版本边界：本轮实现核验限于 vLLM `1dc464d42681d22f38caf1fdc1eb632dc4421c45` 的 Qwen3 MoE 普通路径，DP=PCP=1、TP>1、EP 开启、SP 关闭。它不代表所有框架的 TP+EP 都采用相同路径。
- 来源：`msg-8f3dc3c9064a2d27c5e3`、`msg-ac4a0b369bb0c5f33559`、`msg-1e9297b5995330bc4bb1`、`msg-ac4a42da42e4d65d41d3`。

<a id="task-and-token-counts"></a>
### 4. 原 Token、专家任务与传输向量分别计数

- [要点] 同一卡上的专家任务数，是否等于不同 Token 数？——学习者独立指出：“不同的token只有4个。”并说明：“比如上面例子中t3就同时被E2和E3处理。”一个 Token 可以对应多条 Token–expert 分配。
- 本轮采用每个 Token 选择 K 个不同逻辑专家的规则。在不丢弃时，总分配数为 TK，每个逻辑专家的分配数不超过 T。传输量还需另看来源、目标设备以及去重粒度，不能直接用总任务数乘 H 维向量字节数。
- 来源：`msg-b6687e05557a485f9a78`、`msg-f75bcef20a6b079a5022`、`msg-30191e213a9f0d830e54`、`msg-e295604d20004901569b`。

<a id="expert-output-reuse"></a>
### 5. 相同输入不能直接复用不同专家的输出

- [要点] 打包后的两行同为 x0，能否只算一次专家输出？——这是导师提出的检查方案，学习者没有主张该优化。学习者回答：“虽然二者输入一样，但是进行处理的专家权重不一样。二者最终的结果也很可能不一样，所以不能复用。”
- 最小结论：任务由输入和专家参数共同确定。多个专家可以读取同一份输入存储，但这不证明它们的计算结果等价。
- 来源：`msg-31e29a0702571d3e8791`、`msg-198188beb0d73006221a`、`msg-494ece085ed927fddfa6`。

<a id="permutation-restore"></a>
### 6. 还原时区分打包行号与原 Token 编号

- [纠错] 场景：原 Token t2 对应打包结果第 1、6 行，路由权重分别为 0.4、0.6。学习者写：“对应第1行和第6行。y_1=0.4z_1+0.6z_6”→ 正确左侧应为 y2。
- 原因与范围：定位的两行及加权系数均正确，错误只在输出下标。combine 需要按原 Token 汇合并加权求和，不能仅把展开的结果排回顺序。此处保留为符号笔误，不重写成整个还原机制的误解。
- 来源：`msg-15d70453ead721a4d38e`、`msg-c4547564a6003c635c85`。

<a id="dispatch-dedup-scope"></a>
### 7. 通信去重粒度必须写进题设

- [要点] 一个 Token 被远端同卡两个专家使用，是否需要发两份激活？——在本题明确采用“同一 Token、同一目标 GPU 只发一份”的规则时，一份完整输入即可供两个专家分别计算。若两个专家在远端节点的不同 GPU，且不做节点级去重，两份载荷都要计入节点出口。
- 学习者在后续变式中正确写出：“GPU0需要发送到GPU2和3，需要跨节点”，并把发往两个不同目标的各 4MB 载荷累计为 8MB。这里保留的是计数条件与推导选择，不把题设规则升级为所有通信库的默认行为。
- 来源：`msg-30191e213a9f0d830e54`、`msg-43ec89430872e4b527d8`、`msg-80f63c3e7073570a41eb`、`msg-21d3f876e1b1f16b8030`。

<a id="local-weighted-combine"></a>
### 8. 本地先合并会改变回传份数

- [要点] 多条专家结果必须逐份回传吗？——题设允许在专家所在卡先按原 Token 合并加权贡献，且路由权重已可用。学习者算出逐专家回传四个向量为 64 字节；同一卡上属于 t3 的两份结果先合并后，三份向量为 48 字节。
- 边界：“其他结果不变”只适用于向量数量；采用“回传部分加权贡献”的约定时，单路结果也应乘对应权重，来源卡不能再次重复乘权重。是否采用此方案及回传数据类型都要单独固定。
- 来源：`msg-0789a7e80f49a1c9ce4b`、`msg-5f6fd26f9f67123aa0cf`。

<a id="bandwidth-resource-model"></a>
### 9. 从共享资源推导通信时间下界

- [要点] 为什么不直接用双向总字节数除单向带宽？——学习者说：“两个方向可以同时传输，那么下界就由传输量较大/较慢的一个方向决定。”在每方向独立 16GB/s、分别传输 48MB／16MB 的题设下，阶段下界为 3ms。
- [转折] 跨节点变式改为多张卡共享同向出口后，学习者先将出口载荷聚合，再用 10MB÷2GB/s 得到 5ms，并将严格串行的两个阶段合计为 10ms。独立方向取最大值，共享同向资源先合计载荷；发送与接收是同批数据，不能重复计费。
- 边界：全部使用题设带宽与十进制单位，忽略启动、协议、计算及其他争用；理想下界不等于实测延迟。
- 来源：`msg-a39c4b123c5d5f391f75`、`msg-2874d9b722d94c249c46`、`msg-9471523d6e3ebd0b548f`、`msg-21d3f876e1b1f16b8030`。

<a id="placement-and-routing"></a>
### 10. 放置与逻辑路由各自改变什么

- [要点] 调整专家位置需要改 router 选出的专家吗？——面对任务数 (2,1,3,2)，学习者把 E0/E3 放一张卡、E1/E2 放另一张卡，并说：“不需要改变router选出的逻辑专家。逻辑上选出的计算专家依旧是那几个。”
- 最小结论：这改变“逻辑专家→物理设备”映射，保留 Token 的逻辑专家选择。EP 定义专家的分布；placement 是当前映射；EPLB 可以依据多次 forward 的统计周期性调整映射。不能把每卡专家数相同、任务数相同与实际执行时间相同混为一谈。
- 来源：`msg-2874d9b722d94c249c46`、`msg-7263d78c261da869793a`、`msg-4fb897979021e1d21d1d`。

<a id="expert-replicas"></a>
### 11. 副本分担逻辑任务，不重复贡献

- [要点] 同一专家的两个副本需要都执行同一条任务吗？——学习者说：“某一条计算任务只要在两个副本中选一个进行计算就行了。”在其他专家已占两条任务的一张卡上给副本 a 分两条，另一张卡的副本 b 分四条，可以在该任务计数模型中达到两卡各四条。
- [转折] 导师随后修正了题设：负载 (1,1,6,0) 应明确为八个 Token、top-1，不能沿用四个 Token、top-2。原先漏改条件属于导师问题；学习者的副本分配答案并没有错。增加同参数物理副本不自动增加逻辑专家数或 top-k，但会占用额外权重存储。
- 来源：`msg-195d23e1c4264488b6e5`、`msg-e295604d20004901569b`。

<a id="capacity-padding-counts"></a>
### 12. 有效任务与容量槽位分别核对

- [要点] 八个补齐槽位能证明八条原始任务都被计算吗？——在显式丢弃一条分配的题设中，学习者先答：“此时保留的专家计算任务一共有7条”，再指出 padding 后形状相同“并不代表全部有效的计算任务”。
- 最小结论：保留任务数为 TK 减去丢弃的分配数；padding 可以使物理槽位数重新等于八，却不会恢复缺失贡献。有效计数或来源映射必须阻止填充行参与真实 Token 的 combine。该结论不意味着所有 MoE 都会丢弃任务。
- 来源：`msg-4c9716322f404d36ebaa`、`msg-e965b0dfbabefa7a6575`、`msg-77cf5d41424d32065d2b`。

<a id="swiglu-and-grouped-gemm"></a>
### 13. 动态 Token 行数不改变专家权重形状

- [要点] 专家收到更多 Token 时，哪些维度变化？——在 H=8、F=12、五个 Token 的变式中，学习者给出 P2=[5,8]、U2=[5,12]、Z2=[5,8]，并说：“三组权重的形状不需要改变。”
- 最小结论：按行向量数学约定，gate/up 权重为 [H,F]，down 为 [F,H]；U=SiLU(PW_gate)⊙(PW_up)，Z=UW_down。这里的 gate 是专家内部特征门控，不是 router 的专家选择。grouped GEMM 共同组织各专家独立的矩阵运算，不意味着共享权重，也不保证整个专家链只有一次 kernel 调用。
- 来源：`msg-bb94852a7ee22fa08b72`、`msg-8e3c709ef85c4bbe062a`。

<a id="tp-partial-output"></a>
### 14. 从 TP 分块推导归约，而不看形状猜通信

- [转折] 学习者自行把 gate/up 的数学权重沿相同 F 通道切分、把 down 对应切行，并写出 Z=ΣU_iW_down,i；局部结果与完整输出同为 [4,6]。在 PP+TP 变式中又解释：“因为形状虽相同，但结果只是基于tp rank权重上的计算部分和，不是完整结果。”
- 最小结论：要让所有 TP rank 获得完整同序输出，需要对局部部分和做 SUM AllReduce。数学上的 U 拼接不要求执行时先物化完整 U；gate/up 的通道分区必须一致。权重的数学布局与框架存储转置也不能混用。
- 来源：`msg-d304daa3f98c2c312196`、`msg-9438963935afb965cabb`、`msg-7a58e97120e7cf90f59c`。

<a id="sp-alignment-proof"></a>
### 15. 独立反证“先截行再归约”

- [转折] 导师提出先从每卡的局部 Z_r 截出本卡 Token 行、再 AllReduce 的错误方案。学习者没有主张该方案，而是指出：“这样做虽然形状上确实一致，但数据计算含义发生了改变。”随后解释其他 Token 的权重分片贡献会丢失，而且被相加的行属于不同 Token。
- 最小结论：ReduceScatter 是对齐同一全局元素完成归约后分配结果片段；它不等于各卡先保留不同局部行、再对这些片段普通求和。
- 来源：`msg-9438963935afb965cabb`、`msg-7116e9413589717570e6`、`msg-8d6f0506796fc033248f`。

<a id="tp-sp-layout-cycle"></a>
### 16. 把 TP+SP 的入口与出口接起来

- [要点] Token 分片如何通过一个列并行／行并行 FFN？——学习者在 TP=4、T=12、H=8、F=16 的变式中，先 AllGather 得每卡 [12,8]，推导 U_r=[12,4]、局部 Z_r=[12,8]，再 ReduceScatter 得每卡 [3,8]。
- 学习者说明本地 LayerNorm 可行，因为它“沿H维度的归一化”，且参数本地可用。出口片段包含部分 Token 的完整 H 维结果；这与归约前所有 Token 的部分和不同。该前向布局不等于 Attention 的上下文依赖已经解决。
- 来源：`msg-d5ce1766402076c3ec4a`、`msg-32cf4f16b582fc6ee940`、`msg-f6340cd607aae0e38c46`。

<a id="cp-normalization"></a>
### 17. CP 的局部输出不足以恢复全局 Attention

- [转折] 对导师提出的直接相加局部 softmax 输出方案，学习者正确回答：“直接相加分母不匹配。”导师进一步限定为有效位置 score 的指数和。若 L_A、L_B 都是同一原始 score 标尺上的指数和，全局输出为 (L_Ao_A+L_Bo_B)/(L_A+L_B)。
- 在只给 A 块所有 score 加 ln2 的变式中，学习者说：“不会改变o\_A，但会改变A块在全局attention中占的权重。”局部归一化会约去公共系数，全局则不能。这是对“必须保留归一化统计”的独立说明，不是学习者曾经采用错误相加方案的纠错。
- 来源：`msg-126d453159f90db1fe82`、`msg-5c10adeda7cec5d91a87`、`msg-bcf6b04250b2102fe43a`、`msg-8a1bcd741501d28a88e0`。

<a id="closed-interval-count"></a>
### 18. CP+PP 算例中的闭区间端点漏计

- [纠错] 场景：每卡负责 Token 0～4 或 5～9，H=8，BF16。学习者原答：“每份张量的形状为[4, 8]，字节数为4 \* 8 \* 2 =64字节。”导师只提醒区间包含两端后，学习者自行改为：“token行数为5，那么张量形状为[5,8]”，每份 80 字节。
- 正确差值：闭区间个数为终点减起点加一；两次发送合计 160 字节。原答的 K/V 可见范围、归一化结果、发送方向及不需要额外 AllReduce 的判断均正确，不把整题写成并行概念错误。
- 来源：`msg-5ca59f6c9e3e9624b3ba`、`msg-2b27818a4f547d93044b`、`msg-d76434656b6a4492dda6`。

<a id="dp-group-isolation"></a>
### 19. 相同形状不能跨请求批次归约

- [要点] DP 副本内的 TP 结果都呈现 [T,H]，能跨副本 AllReduce 吗？——学习者说：“前两卡的部分和属于请求批A的输出，后两卡的部分和属于请求批B的输出。”并解释将四卡一起相加“就导致请求之间的信息混杂了。”
- 最小结论：归约组必须对应同一份逻辑输出。一个 DP 副本可以由多张 TP 卡共同持有完整逻辑模型，单一 TP rank 不等于一个完整请求执行副本。
- 来源：`msg-8a1bcd741501d28a88e0`、`msg-fc43d8265ba728176581`、`msg-bd611c651df19cc20ddb`。

<a id="pp-latency-throughput"></a>
### 20. 首批延迟与持续产出间隔分开计算

- [要点] 两阶段分别耗时 1ms、3ms 的前向流水线，两种时间分别是什么？——学习者答：“第一个microbatch最早要4ms完成。进入后续阶段后，最短每隔3ms能完成一个microbatch。”
- 边界：输入充足、每阶段同时只处理一批、忽略通信等开销。首批沿依赖串行经过两阶段，持续产出受较慢阶段限制；这是题设推导，不是 PP 实测收益。
- 来源：`msg-191586845e1b30f8ff9b`、`msg-ab18f68b53d4f247829c`、`msg-9471523d6e3ebd0b548f`。

<a id="replica-admission"></a>
### 21. 副本准入要逐 rank 满足资源需求

- [要点] TP 组内 KV 块能否加起来作为任意共享的总池？——学习者正确说明：“一个新请求需要在每个rank上都预留6个kv块。”在给定队列和资源条件下选择副本 B，入队后其队列长度为 4、各 rank 可用块为 6。
- 当两副本不能准入、路由器的有界等待队列也已满时，学习者回答应拒绝并向上游传递反压，并指出“某一个tp卡上也没有完整的模型权重，无法执行完整的计算”。导师补明：关键是逐 rank 满足需求；即使总块数够，也不保证每个 rank 都够。拒绝结论限于题设所有可用有界容量已满，不泛化为任何资源紧张时都只能拒绝。
- 来源：`msg-c1500e35cbfd34c9c876`、`msg-7fed73f81a4e4867dc76`、`msg-a3bf17fc44a8b648952d`。

<a id="capacity-motivation"></a>
### 22. 为什么“大 GEMM”不自动消除容量问题

- [高价值问题] 学习者问：“一般情况下，输入形状越大，越能打满芯片矩阵乘计算性能。为什么要限制输入token数量？”
- 最小结论：单个 GEMM 的利用率与整个分布式层的完成时间不同。热点专家、缓冲区和中间激活膨胀，以及固定容量下冷专家的 padding 成本，都会影响整体执行。capacity 是某类实现与路由方案的权衡，不是 MoE 数学必须有的限制；支持动态工作量的 dropless 方案也存在。
- 来源：`msg-d83a1880ce32a161e10d`、`msg-2427db4683c25919861c`；一手依据：[GShard v1](https://arxiv.org/html/2006.16668v1#S2.SS2)、[MegaBlocks v1](https://arxiv.org/html/2211.15841v1)。

<a id="drop-changes-output"></a>
### 23. 丢弃后的贡献确实缺失

- [高价值问题] 学习者追问：“如何后续只处理未被丢弃的计算任务，那么最终输出结果就会有问题了。”
- 最小结论：这个担心成立。0.7E0(x)+0.3E2(x) 若丢掉第二路，保留原权重得到 0.7E0(x)，重新归一化则可能得到 E0(x)，通常都不等于原输出。残差可以保留 Token 表示，但不会恢复缺失专家贡献；剩余权重是否重归一化要按模型与实现核对。
- 边界：明确采用容量截断的训练方案，与要求保持原有 dropless 语义的推理不是同一契约。不能将丢弃解释成等价的性能优化。
- 来源：`msg-d83a1880ce32a161e10d`、`msg-2427db4683c25919861c`。

<a id="overload-vs-dropping"></a>
### 24. 从容量玩具算例追问到实际框架边界

- [转折] 学习者追问：“moe的结果在大压力下是有可能有损的。这种做法是主流常见的吗？在vLLM和SGLang里是这么做的吗？”这是一项有待核实的推广，保留导师先前容量示例容易引发泛化的责任，不把整段提问当作已经断言的错误结论。
- 核验后的最小结论：高负载本身不代表自动丢弃专家分配。Megatron Core 0.15 的容量丢弃是可选配置；本轮检查的 vLLM `1dc464d42681d22f38caf1fdc1eb632dc4421c45`、SGLang `78fa921189e3a66c7278733940c60a1e6fe6e467` 代表性路径区分完整分配执行、缓冲超限报错与请求排队／撤回，不把这些机制混为容量裁剪。
- 学习者随后确认：“明白，这是部分训练方案的可选配置项，并不是默认行为。”该表述按本次已核版本和路径理解，不外推所有模型、后端或未来版本；只读源码核验也不等于本机运行验证。
- 来源：`msg-d7b8446ad8543710ea0a`、`msg-63e21729194ea5c0769c`、`msg-4d14886ac5a6f2a5ba56`。框架锚点：[vLLM 重排](https://github.com/vllm-project/vllm/blob/1dc464d42681d22f38caf1fdc1eb632dc4421c45/vllm/model_executor/layers/fused_moe/moe_align_block_size.py#L23-L103)、[SGLang DeepEP v2 超限检查](https://github.com/sgl-project/sglang/blob/78fa921189e3a66c7278733940c60a1e6fe6e467/python/sglang/srt/layers/moe/token_dispatcher/deepep_v2.py#L252-L260)。

<a id="cp-communication-implementations"></a>
### 25. CP 的策略名称不等于唯一通信原语

- [高价值问题] 学习者问：“这里交换kv数据使用的是什么通信操作？一般如何进行该次通信？”
- 最小结论：Megatron Core 0.15 支持 all_gather、环形 p2p、a2a、a2a+p2p。Q 留本地、收集或流式接收 K/V 对应前两类；Ulysses 式 A2A 会交换 QKV，将序列分片转为头分片。TE v2.8 的环形路径可见 isend／irecv，并利用 LSE 统计合并局部 Attention，而不是直接相加局部 softmax 输出。
- 边界：不能由 profiler 中没有 AllGather 名字就判断没有远端上下文交换；也不能预设所有 CP 都先物化完整 K/V、总是 Q 本地或使用同样数量的缓冲区。具体通信方式、峰值显存与性能需按版本及配置核对。
- 来源：`msg-d83a1880ce32a161e10d`、`msg-2427db4683c25919861c`；[MCore 0.15 配置定义](https://docs.nvidia.com/megatron-core/developer-guide/0.15.0/apidocs/core/core.transformer.transformer_config.html#core.transformer.transformer_config.TransformerConfig.cp_comm_type)、[TE v2.8 实现](https://github.com/NVIDIA/TransformerEngine/blob/v2.8/transformer_engine/pytorch/attention/dot_product_attention/context_parallel.py)。
