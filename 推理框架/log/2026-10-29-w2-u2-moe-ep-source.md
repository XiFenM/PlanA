## 学习过程

### 前置回顾与框架接入

- [转折] 以“之前进行到哪里了？”恢复八周计划后，学习者先要求回顾单元一，再进入真实源码。前置问答暴露了输入分布与专家路由分布的混淆，因此保留这段回顾到单元二的过渡，而不把它另写成一门新课。（来源：Claude · `msg-a0b3e5bc9d26d02600f4` → `msg-d6bd7d2f09d432af3181`。）

- [纠错] 在输入数量固定、专家路由倾斜的场景中，学习者原答“allgather_reducescatter可能受影响更大”，把 Token 的原始归属与选中专家的位置混在了一起。反馈指出 AgRs 搬运所有输入，其通信量不随这种路由变化；定向发送则会出现目标热点。随后复述开始区分“输入在哪”和“要送到哪”。（来源：Claude · `msg-b5465a61f417efa7f284` → `msg-6814445ffc63e6772c51` → `msg-63d747af6615628f1c29`。）

- [纠错] 在 Token 集中于一个 rank、路由仍均匀的变式中，学习者由路由均匀推断“all-to-all后端应该是都一样的”，漏掉了源端 Token 数量差异；其“通信量不变”若指总量则是对的。纠正后，学习者区分总量与最忙方向，指出应在“dp 的请求分配上要根据各请求的token数来均匀分配”，通信后端不能消除输入端已经形成的负载倾斜。（来源：Claude · `msg-63d747af6615628f1c29` → `msg-ac04231392bff1854cb0` → `msg-e4082364be91580724fe`。）

- [高价值问题] 学习者追问“一张卡中可能只有某个token选中的部分几个专家”，那么本卡求和如何得到完整结果。答疑把专家卡内的部分和与跨卡合并分开；这也为后面区分 top-k 加权／求和和跨 rank 归约提供了前置。（来源：Claude · `msg-f741ccc4e0e13df46ffe` → `msg-cb15e8d8008304adac61`。）

- [纠错] 在源卡 combine 负责加权求和的题目中，学习者填写“返回Contiguous”与“output_is_reduced()是False”，却又判断不需要额外 all-reduce。反馈改为由 Experts 返回 Delegate，把处理方式交给 P/F；但导师原表对 Contiguous 的简写和复查题遗漏的并行条件也造成了歧义，后续补明题设后才复答。最终口径以[卡片第 2 段](../../面试准备/自我准备/ChangeCard-02-MoE-EP-dispatch-combine.md)为准：Delegate 不固定处理地点，归约标志也不等于任何配置下都要或都不要 all-reduce。（来源：Claude · `msg-28edccb3dbfddc260b04` → `msg-7db3198a85b20708b7f2` → `msg-47e5c36dc37ca92fbd9f` → `msg-59032160e4c9637c8b38` → `msg-dc2975cff7fbb859ad0b`；Codex · `msg-e25b0f9133da7f16192f`。）

- [纠错] 学习者最初认为空闲 rank 会“从prefill的8000tokens向上pad到graph录制的token长度”，把启用 graph 理解成每步都使用最大录图长度。题设的大 prefill 已超出录制范围、导致全组 eager，空闲 rank 此时只需假 Token 行；学习者在变式中改答“实际算1行的假token”。导师承认录制上限此前未讲，这部分信息缺口不归为学习者错误。（来源：Claude · `msg-93c16918cb3c38bebe44` → `msg-a962f34016da9f008c1e` → `msg-8e6587f51eeaf023328f`。）

- [纠错] 对替换通信后端的影响，学习者说“不会改变收到的行数”，依据是 Token 仍选择相同专家；该理由只能证明逻辑专家任务不变。经变式后，学习者区分了 AgRs 收到的全部行、定向发送留下的有用行与有效专家任务。导师还纠正了学习者计算多送比例时采用的百分比分母，并补充不重复选择专家时应按不放回计数。（来源：Claude · `msg-8e6587f51eeaf023328f` → `msg-fc811ff5a4a9ae42bb19` → `msg-63ef9cb738055509e8fa` → `msg-39258735807febc64986`。）

- [纠错] 在 SGLang 新通信库与 GEMM 库的接入题中，学习者认为“最少也要编写一个转换函数”，漏掉了实际调用新库的 dispatcher／runner 及返回路径。复查后补出了双向转换与 dispatcher，并通过格式注册追问明确：数据格式看起来兼容，不等于调用适配已经存在；post-permute 也不能重复 combine 已完成的加权。（来源：Claude · `msg-cd242279ff3dbbe261e0` → `msg-8a47330939f308b5bde7` → `msg-e9933f32a60a0138138c` → `msg-00f78fbfaac95c3d4afc` → `msg-e11af1bd6506dfdf24de`。）

- [转折] 学习者问 SGLang 的 attention DP 是否意味着没有多个实例，并判断“vllm似乎没有这种拆微批的动作”。导师纠正了自己混用“实例”的框架对照，补明 vLLM 也有 DBO，比较应落到数据语义、调度进程与同步位置。此次源码核对已把共享专家重叠窗口从 dispatch 改为 combine，后续卡片却再次写回 dispatch，最终又在 Codex 审稿中修正；这条反复应归为导师文稿问题。（来源：Claude · `msg-cd242279ff3dbbe261e0` → `msg-8a47330939f308b5bde7`；Codex · `msg-e25b0f9133da7f16192f`。）

### DeepEP：完成语义、容量与输出

- [转折] HT 检查中，学习者分别指出输入可能在通信流读取期间被覆写，以及输出尚未接收完就被 GEMM 使用。导师补充 `record_stream` 的分配器生命周期保护与显式执行依赖并非同一件事：保留对象或防止释放后重用，不会禁止调用者主动原地改写。（来源：Claude · `msg-00f78fbfaac95c3d4afc` → `msg-e11af1bd6506dfdf24de`。）

- [纠错] 学习者提出把元数据放到 CPU 统计，理由是“元数据本身很小”，但元数据最初由设备上的前向路由产生。反馈补上 CPU 获取这些数据本身的同步，不能只计算 CPU 上统计的成本；同一轮关于固定容量即可录图的认可又过强，后续审稿已把它收窄为消除某类主机等待的方法之一。（来源：Claude · `msg-00f78fbfaac95c3d4afc` → `msg-e11af1bd6506dfdf24de`；Codex · `msg-e25b0f9133da7f16192f`。最终边界见卡片第 3、5 段。）

- [纠错] 估算 LL 内部存储时，学习者提出“本地专家数 * 2套缓冲区”，漏了来源 rank 容量展开及每套内发送／接收区的区别。导师按尺寸函数补齐这些因素，同时纠正自己前一节把普通 LL 输出说成内部缓冲区视图的错误。容量公式和输出归属是两个问题，不能由“两份轮换”推断返回张量也只活两轮。（来源：Claude · `msg-e2c04623e2ff4484e529` → `msg-ce2ff5f8caa8ec5fcb6b`；导师自纠 `msg-a9938eb7c97900b859b2`。）

- [纠错] 讨论 LL 上限翻倍时，学习者说会“使得通信字节量增大”，把预留容量与实际流量绑定了。换成实际 Token 数不变的复查后，学习者改为区分发送字节与内部缓冲区、输出张量的预留空间；不能仅凭上限变大推断本轮耗时或 ITL 必然上升。（来源：Claude · `msg-213da940761ce5e646da` → `msg-6e5a9b169611d9978992` → `msg-fad05a689bae44ad681d` → `msg-1c493574a996a1f9eca1`。）

- [转折] 学习者对 V2 的 M 追问“我之前以为都是按照这个值来处理”，并担心精确计数会导致重复编译。答疑区分容量／模板参数与运行时实际计数，说明取 2 的幂减少特化种类，不是 CUDA graph 的要求；是否按精确计数分配输出也不能只凭 prefill／decode 标签判断。（来源：Claude · `msg-0307955549c557089157` → `msg-041e584823be555904bd` → `msg-572418169362c2f6c4d0` → `msg-0240f26975e51eee1550`。）

- [纠错] 学习者认为满批 prefill 按初始化上限分配“不会出现多分配的浪费”，忽略了最坏路由分布带来的接收端上界。后来能指出“最坏情况其实是满批情况叠加上极端的不均衡选择”，但仍把 EP 扩大解释为平均接收量必然下降。导师在题设模型中进一步区分平均量与最坏量，修正了浪费比例的归因。（来源：Claude · `msg-bf0e7e9dc9e99b99d374` → `msg-98a2af8a3ef74f623c34` → `msg-f90495fe72c60ff17be6` → `msg-ebc4c632684c6dbab77d`。）

- [纠错] 学习者复述 V2 的 SM 预算模型时，最初只考虑传输段，漏了拷出段；后续又说“只有在开启双微批的场景下才应该打开”。反馈将条件收窄为是否存在实际可重叠工作：单批共享专家也是候选，预算调整是否有效仍要由完整链路验证。（来源：Claude · `msg-0307955549c557089157` → `msg-041e584823be555904bd` → `msg-bf0e7e9dc9e99b99d374` → `msg-98a2af8a3ef74f623c34`。）

### MORI 与 Hybrid-EP：分配、图模式和场景迁移

- [纠错] 比较 MORI 与 V2 时，学习者把 DeepEP 的最坏分配归因于没有远程原子加、接收端不知道实际数量。反馈指出预分配时两者都不知道实际接收量，区别在于发送方分段与全体发送方共用的按需分配池。导师也将自己先前关于计数器位置决定布局的说法收窄为“计数器由谁共用”，避免把物理位置当成根因。（来源：Claude · `msg-399b4eca85d61636702d` → `msg-78be7699af8aa73799fe` → `msg-c20340561955b96c24e4` → `msg-39b7a8578708aa702d95`。）

- [纠错] 学习者把 V2 的发送端计数器理解为按目标卡进行本地 permute，形成紧凑发送张量。源码反馈指出它领取的是目标接收区中、本发送方分段的行号，不能据此补出一份本地重排张量；这也促使区分地址分配与 SGLang 相对 grouped GEMM 命名的 pre-permute。（来源：Claude · `msg-33e36c2e2c87fd37be80` → `msg-1a0623932ebaa48eb562` → `msg-bea785207f46c65c8e24` → `msg-4056ff764821860129b4`。）

- [纠错] 对 `out[:total_recv]`，学习者先想到切片使输入形状变化，漏了设备计数成为 Python 切片边界时更早发生的主机读取。反馈同时要求有效行约束覆盖排序、分组与 GEMM，而非只在最后跳过尾部。改为 CPU 已知上界的变式后，学习者能够分别说明固定形状与设备端有效计数的作用。（来源：Claude · `msg-399b4eca85d61636702d` → `msg-78be7699af8aa73799fe` → `msg-ae8e7e2c3d6e04ff381b` → `msg-7ee4472a87ff13b7d873`。）

- [纠错] 在 EP64 固定的显存受限题中，学习者提出“减少R或者减少M”，并把远程原子加当成降低上限新增的代价。反馈将 R 固定回题设，区分共享池设计本身的成本与压低容量新增的溢出风险；导师也承认题目漏算了 V2 的独立输出张量。后续峰值复查保留了另一点差值：不能把预算减半直接等同于 M 减半，统计峰值也不是硬保证。（来源：Claude · `msg-ae8e7e2c3d6e04ff381b` → `msg-7ee4472a87ff13b7d873` → `msg-2f84628df3faa3134877` → `msg-52450787035431883066`。）

- [纠错] 解释 Hybrid-EP 的 decode 开销时，学习者认为 rank 数不变，所以路由元数据 allgather 的量没有明显减少。反馈指出字节量仍随 Token 数缩小，不能同比缩小的是额外通信、等待与 scan 的固定开销。复查中学习者改用 α–β 模型解释，但又把压缩幅度说成 T 的倍数，随后进一步区分压缩比例与绝对节省字节数。（来源：Claude · `msg-9329c4b20defdb06330a` → `msg-d204afb320840456cb48` → `msg-ae417411fbed2a2d4341` → `msg-4be32abee930fcef52d1`。）

- [纠错] 场景表中，学习者把统一槽位数的增大直接看成常驻 buffer 浪费，并提出使用 decode 上限覆盖 prefill。反馈拆开 M、S、P：常驻容量、本轮槽位和输出容量不能混作一个上限。后续复查已把 M 改为依据调度器每步上限固定，图模式下 P 的处理则继续单独补差。（来源：Claude · `msg-d762ecbfb4d55cff810b` → `msg-4c66311fa7c59210c3f8` → `msg-0b11a3f01d08750d1938`。）

- [纠错] 训练丢弃场景中，学习者写“对于丢弃的token置为overflow_flag”，又把 flag 值填为 −1。反馈区分 rank 级溢出标志与逐个 Token／专家分配的无效映射，前者不能指出哪些贡献没有输出位置。导师还更正了自己给出的容量建议：本地 router 限额不能直接保证全组到达量，原无丢弃上界也漏了专家 padding。（来源：Claude · `msg-d762ecbfb4d55cff810b` → `msg-4c66311fa7c59210c3f8` → `msg-0b11a3f01d08750d1938` → `msg-04357ec5c2c2e17e7571`。）

- [纠错] graph 档位复查中，学习者说 P 每步变化，并认为扩容后已录图会被舍弃。反馈明确每个已捕获档位的形状与地址固定，动态有效行数另存；扩容不会自动使旧图失效。学习者已正确指出 Python 代次检查无法检查图，仍需把这一点落实为调用方阻止扩容或显式使图失效的责任。（来源：Claude · `msg-0b11a3f01d08750d1938` → `msg-04357ec5c2c2e17e7571`。）

- [纠错] 面对固定 P 中的无效行，学习者说可按 `tokens_per_expert` 判断后“不进计算中”。反馈指出 grouped GEMM 的专家分段可能包含 padding，计算范围与最终贡献是否被合回原 Token 是不同责任，后者还依赖映射。导师同步收窄自己先前“只算有效行”的说法，不能把过强讲解造成的推论全部算作学习者错误。（来源：Claude · `msg-adb739e0059a57309fcb` → `msg-015b0394ddbba83d8977`。）

- [转折] 在 Hybrid-EP 重叠方案中，学习者最初笼统要求通信 kernel 等待通信流此前操作。经追问区分共享通信区与独立输出后，复查能说明同流已有执行顺序、跨流需建立 event 依赖，共享同一内存时仍须保证先后。导师补充，拆开内存区域只是条件之一，不能直接当成同时在途的调度已经安全。（来源：Claude · `msg-d762ecbfb4d55cff810b` → `msg-4c66311fa7c59210c3f8` → `msg-0b11a3f01d08750d1938` → `msg-04357ec5c2c2e17e7571`。）

### 综合验收与 Change Card 的形成

- [转折] 假想后端 X 的验收中，学习者提出先按最坏情况设置 C，再结合线上情况调整；导师最初以省空间意义下降否定这一安排。学习者追问“一开始冷启动，不知道线上情况，怎么根据线上峰值和余量来定”，导师收回过重判断。需要核对的是初始显存预算、调低后的峰值监控与超限处理，冷启动的保守策略本身不应记成错误。（来源：Claude · `msg-7ee5e800b67d07025839` → `msg-16962d73a9b7b97a85fa` → `msg-1bc48eb51052a132d3a2` → `msg-d5fe3bde6cd3e4721a77`。）

- [纠错] MORI 双 micro-batch 验收中，学习者指出视图会被覆盖，并提出分实例或取消交错，但对 HT 的解释只提到了不同数据空间。反馈补上独立 handle 的逆向路由状态及 combine 输出的复用边界，不能只检查激活数据。分实例的修法在作答前已由导师答疑提供，不能记录为学习者完全独立提出。（来源：Claude · `msg-c4ed292f691d8c070002` → `msg-73fdd49a13235c672c2f` → `msg-7364d634a002abb3179a` → `msg-1c7a98ed636df2622c44`。）
