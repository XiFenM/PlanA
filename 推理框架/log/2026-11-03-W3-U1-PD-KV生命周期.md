## 学习过程

<a id="pd-latency"></a>

### 1. [转折] 从“传输抵消计算收益”补到首 Token 关键路径

检查 1 中，我把 TTFT 变差解释为新增 KV 交接可能超过 P/D 计算节省，并说“而在后续生成中，cache不再流动，只在d节点上，就不会影响ITL的优化”。导师肯定主线，再补准：归因还要拆开 P 排队、交接等待／搬运和 D 就绪后的排队；同一请求完成交接后通常无需再跨 P/D 搬运已有上下文，但本地 KV 继续增长，其他请求的传输仍可能争用资源。检查 2 中，我进一步把 D 排队长与资源不足区分为观察和假设；具体模型见[节点 1](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#node-1)。（来源：`msg-dcfa557533912ea5d38c`、`msg-8497e2e132331e1665cf`、`msg-567181a30c635728f361`、`msg-5a74394de4b4027c9da8`。）

<a id="ready-stages"></a>

### 2. [要点] 远端有 KV、分配了空间、KV 可被读取，是同一个条件吗？

这轮源码讲解将“远端有 KV”“D 已分配空间”“数据已可消费”拆成不同阶段，而不是用一个 matched/computed 数字替代全部就绪条件。这个拆分成为随后解释异步调用顺序的前置：D 的分配和 metadata 先解决落点与任务安排，等待状态继续隔离未准备好的输入；字段与调用关系见[节点 3](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#node-3)。（来源：`msg-ae32a275c354f5f56807`、`msg-d41d0bfd4138e860b3d5`。）

<a id="request-dependency"></a>

### 3. [要点] 为什么异步 load 出现在本步 forward 之后，不一定是读了未就绪 KV？

检查 3 中，我先按请求区分依赖：“模型计算在处理kv已经就绪的请求B，异步的start_load_kv在读取请求A的kv，二者没有依赖关系”。导师确认这个判断，并将同步分支补准为：A 的 attention 读取前必须满足加载完成与设备可见性，不能仅依据 host 调用先后。原回答被判正确，这里记录的是边界补充，不作为错误卡素材。（来源：`msg-da885b42c75cccd6b398`、`msg-c1e233149d31061ad594`、`msg-3b7bb1819e0eb35655ff`；对应[节点 4](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#node-4)。）

<a id="two-copies-lifetime"></a>

### 4. [要点] P 的源块回收为什么可以早于 D 报告接收完成？

检查 4 中，我解释 P 可能已经处理读取结束通知，而 D 还在进行本地数据准备；两端保存的是不同副本，不能只凭 `finished_sending` 与 `finished_recving` 的观测先后裁定提前释放。我还指出归还块是减少引用，归零后才可复用，缓存内容可能保留供后续前缀命中；导师补上本地在途访问保护与设备可见性条件。传输句柄、P 源块和 D 目的块的职责对照见[节点 5–6](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#node-5)。（来源：`msg-07daada578bbd2934e35`、`msg-b50cb624e2edd7f8119f`、`msg-88774a86936e0f464c18`。）

<a id="push-flow"></a>

### 5. [要点] 从 PULL 换成 PUSH，改变的是哪些责任？

导师把 PUSH 的主要变化落到实际实现：D 先登记目的 blocks，P 将登记与已完成的源 blocks 配对后发起 WRITE；P 根据自己的 WRITE 句柄判断发送完成，D 根据完成通知推进接收。综合核验中，我据此串联 D 的请求／实例／目标块信息、P 的源块保留和 Worker 执行，说明两端收尾不需要固定先后；PULL/PUSH 正常路径对照见[节点 7–8](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#node-7)。（来源：`msg-e81a2c72ece535e9c75e`、`msg-f424700639456790e939`、`msg-4ea8d6bc1910aef7b78a`。）

<a id="correction-notification"></a>

### 6. [纠错] 把 D 的 WRITE 完成通知误认为由 P 的软件状态上报触发

检查 5 的题设只将 P 的 `finished_sending` 改成等待一个 D 不会额外发送的 ACK，其他代码保持不变且不考虑超时；我正确判断 P 会保留源块，却又说：“P节点无法完成finished_sending，可能也就无法发送完成通知。”导师纠正的仅是后半段因果：D 的通知已经附在 WRITE 操作上，不由 P 向 Scheduler 上报 `finished_sending` 触发，所以 D 仍可完成接收收尾并继续，卡住的是 P 的源块回收。这个区别随后在检查 6 的 D 端判断和综合 PUSH 回答中得到体现。（来源：`msg-bf7f9db89316c789c24c`、`msg-79093b3770fdf646f060`、`msg-3859b99b02a61161b49b`、`msg-c3b5e69248d5f2d771d6`；对应[检查 5 参考要点](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#q-5)。）

<a id="correction-report-vs-fence"></a>

### 7. [纠错] 用另一项正确保护条件，替代题设里的直接阻塞原因

检查 6 已明确 P Worker 的完成结果消息上报延迟；我仍把 P 不能回收解释为“因为可能还会有本地在途访问，需要等相关step完成才能归还引用计数”。导师说明“不立刻回收”的判断没有错，但该题首先缺的是 Scheduler 获得完成事实，本地访问是另一道条件；即使本地 GPU 已结束，上报延迟仍会使 Scheduler 保留源块。检查 7 中，我改为明确区分：“甲要等finished_sending，乙要等本地GPU step完成。”（来源：`msg-c3b5e69248d5f2d771d6`、`msg-6db834454e5db23c2b3f`、`msg-79a00e209c2615bb529d`、`msg-35dab6c08dc4f935de2a`；对应[检查 7](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#q-7)。）

<a id="block-address-mapping"></a>

### 8. [高价值问题] 块编号到地址的每一步，分别在哪一端完成？

我要求为“请求逻辑位置 → 块池 block ID → backend 页编号 → 传输地址范围”举例，并说明组件归属。导师沿同一块给出示意：D 为请求块 0 分配池 ID 7，一块对应两页时展开为页 14、15；每页 8 KiB、region 起点为 `0x10000000` 时，两页范围是 `[0x1001C000, 0x10020000)`。关键转折是明确 PUSH 中 P Worker 在 host 侧使用 D 提供的 ratio 和内存描述展开目的页，编号不是硬件物理地址，数据仍位于 D 显存；完整例子见[页内补充](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#add-7-2)。（来源：`msg-e488f4f5d468f8a168a1`、`msg-f7dd71bbc3f07229b281`；数值为导师算例，不是实测。）

<a id="request-registration-vs-mr"></a>

### 9. [高价值问题] PUSH_REG 的请求级登记与 RDMA 内存注册是不是同一件事？

我将两者类比为 Scheduler 的块管理与 Worker 的底层地址管理，导师肯定分层方向，再补准 `PUSH_REG` 携带的是本次请求要使用的池 block IDs 等信息。MR 描述实际内存范围、长度、权限与访问 key，不只是一个地址；这里是入门边界，详细 RDMA 机制仍按单元三展开。（来源：`msg-bf7f9db89316c789c24c`、`msg-e81ca5d38220b635dfb3`、`msg-3859b99b02a61161b49b`；对应[登记与地址补充](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#add-7-1)。）

<a id="read-write-backend"></a>

### 10. [高价值问题] PULL/PUSH 只是 metadata 不同，还是实际数据操作也不同？

我追问底层设备启动的通信操作是否变化，得到的关键区分是：在本课固定 NIXL 路径中，D 发起 READ 或 P 发起 WRITE，数据都从 P 流向 D；这不自动意味着换了网络或一定使用硬件 RDMA。后端还可能使用 TCP，是否运行 GPU 拷贝／重排 kernel 应继续看实际 backend，而不能只凭 READ/WRITE 名字判断。（来源：`msg-bf7f9db89316c789c24c`、`msg-3859b99b02a61161b49b`；对应[操作层级补充](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#add-8-1)。）

<a id="gpu-kernel-vs-data-mover"></a>

### 11. [高价值问题] GPU 通信是否必须两端分别启动 send/recv kernel？

我问“是不是一定要卡0发起一个send kernel，卡1发起一个recv kernel”，随后又确认“gpu之间的通信操作可以由cpu发起是吗？甚至完全不需要启动kernel”。导师把 API 的匹配调用契约、CPU/GPU 上的发起者和实际数据搬运硬件分开：在支持的 peer-copy 或 GPUDirect RDMA 路径中，CPU 可提交操作，由 Copy Engine 或 NIC/RNIC 搬运；目标 GPU 仍需在消费前满足完成与可见性条件。NCCL/NVSHMEM 的接口对照及明确版本见[网页补充](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#add-8-2)，不把这一解释视为本机运行观察。（来源：`msg-63321640e31f9858ede2`、`msg-eb84fdc5b29c1c379402`、`msg-51c329b6c065f1864803`、`msg-6bc007f7e723cd214674`。）

<a id="inflight-reuse"></a>

### 12. [高价值问题] CPU 判定旧请求结束后，GPU 还会怎样污染新请求的 KV？

我要求为“本地在途访问保护”举例，导师沿旧请求 X、新请求 A 和同一个 block 7 展开：CPU 尚未处理 S1 的停止结果时，S2 已提交；CPU 随后结束 X，并不自动撤销 S2。若 block 7 提前回池并交给 A，A 的 connector 写入后，X 的旧 S2 仍可能覆盖同一槽位；延迟释放需等相关 step 完成，再归还引用。该例说明为什么引用计数不能单独代替设备完成条件，具体适用条件与测试边界见[在途步骤示例](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#add-6-2)。（来源：`msg-054e5a0a9ab9bb75827f`、`msg-9adeb1bac8a0077517b5`；为因果示意，不是设备故障复现。）

<a id="identity-correctness"></a>

### 13. [要点] WRITE 和通知都成功，为什么仍需查 connector 的身份／块映射？

在 A/B 目标内容互换的新情境中，我回答“不能排除connector接入问题”，并提出“D分配目标块的所属请求身份与P源块所属请求身份必须一致”的断言。导师确认诊断方向和断言思路，再补准应依据独立的实际分配记录与最终 WRITE 块对，而不是让消息标签自证；两端本地 request ID 也可能不同，应关联同一逻辑请求。最小断言的内容校验补强见[综合核验 2 参考要点](../../课程网页/八周计划/plana-jd-w3-pd-kv-rdma.html#q-a2)，不新增实现任务。（来源：`msg-f424700639456790e939`、`msg-4ea8d6bc1910aef7b78a`、`msg-83f1cf4a5bbb61db1be9`。）

<a id="test-evidence"></a>

### 14. [要点] 如何用一条真实测试支持 PUSH 的完成依赖解释？

综合核验 1 中，我引用 `test_completed_push_send_releases_blocks_without_consumer_notif`，解释它支持 P 的发送结束不依赖 D 额外回传 ACK，因此不存在 D 必须先结束、P 才能结束的一般顺序。导师认可这个源码／测试对应；上游模拟断言支持的是这条控制逻辑，硬件可见性、性能和完整异常恢复仍不能由它替代。（来源：`msg-f424700639456790e939`、`msg-4ea8d6bc1910aef7b78a`；具体结课依据只见[课程账本](../../计划/八周冲刺进度/W3.md#w3-u1-final-mastery-20261103)。）
