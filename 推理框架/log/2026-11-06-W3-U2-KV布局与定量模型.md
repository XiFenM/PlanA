## 学习过程

<a id="u2-p01"></a>
- [要点] **增加查询头，会不会直接增加 KV 容量？** 用户首答“不会翻倍”，从实际 KV 头、层数、头维和元素字节数解释容量；同时指出共享 K/V 的查询头可以产生不同注意力结果。导师肯定核心判断，只把“不同 Q 得到不同输出”补准为“可以不同，并非必然不同”，没有把这次正确回答记为纠错。（来源：codex:01a19a2d，`msg-95ff2604562f018760ff`、`msg-d0b3d5bc2ab5a9436c91`、`msg-889fa44bf7558a43272e`。）

<a id="u2-p02"></a>
- [转折] 在 TP 切分讲解后，用户要求画出“每个张量是怎样切分的，哪些张量会被保存成 kv cache，结果张量又是如何恢复的”。导师据此补入[权重、临时张量、持久缓存与输出恢复图](../../课程网页/八周计划/plana-jd-w3-kv-layout-bytes.html#add-3-tensor)，用 PyTorch 权重维序区分 Q/K/V 的输出行切分与输出投影的输入列切分，并说明各 rank 的完整宽度部分结果经 all-reduce SUM 合并。这次转折是从缩写与分片描述转向可逐步追踪的张量关系。（来源：codex:01a19a2d，`msg-f8d015206a1824927973`、`msg-98e19cd666d99085699d`、`msg-0007e11a8449d9bd07ac`。）

<a id="u2-p03"></a>
- [要点] **P/D 改成不同 TP 后，为什么不能沿用同编号 rank 交接？** 在每 rank 保留完整 KV 头的题设下，用户正确判断 TP 超过 KV 头数后增加的是副本，并指出旧的一一对应会遗漏新 D rank 所需的 KV。用户进一步给出“P0 的 KV 应提供给 D0 和 D1”的映射，解释必须从 D 的查询头需要哪些 KV 出发；容量与映射回答都被肯定，具体题设见[异 TP 节点](../../课程网页/八周计划/plana-jd-w3-kv-layout-bytes.html#node-4)。（来源：codex:01a19a2d，`msg-a575bccb703147a9c60e`、`msg-239aaee266b21f0ca872`、`msg-f14142f60b0e1f16b51f`。）

<a id="u2-p04"></a>
- [要点] **历史按位置分片后，怎样恢复完整 attention？** 用户正确指出，改变本地序列长度不会补齐其他分片的 KV；局部 attention 输出也不能按 Token 数量加权。其理由是各分片的 softmax 分母取决于分数，而不是片段长度，需要利用各自的 LSE 恢复归一化权重后合并；这属于对题目错误方案的正确诊断。（来源：codex:01a19a2d，`msg-c315ad3be0f7b58d14bf`、`msg-cebc4748523b1d6d3dd5`、`msg-d4f2e7fbac0864557290`。）

<a id="u2-p05"></a>
- [高价值问题] 用户追问 PCP 中后段查询依赖其他 rank 的 KV，是否意味着“这两个 rank 其实不能并行，而是先后执行”。导师沿固定 MLA PCP 路径解释：同层查询与缓存状态可以先并行产生，交换后再并行计算各自查询行的 attention，所等待的不是对方的同层 attention 输出。用户随后用“先 Linear 映射、交换 KV、再并行 attention”复述，导师只补上缓存写入前可能还有归一化、RoPE；详见[同层依赖图](../../课程网页/八周计划/plana-jd-w3-kv-layout-bytes-part2.html#add-6-pcp-dependency)。（来源：codex:01a19a2d，`msg-cebc4748523b1d6d3dd5`、`msg-9dc82c3e00778ec35fc9`、`msg-27e6e9c3dcc7421cbba2`、`msg-fe19ce9d108824d65764`。）

<a id="u2-p06"></a>
- [高价值问题] 用户在算例前询问“额外预留指的是什么”，这是对题设口径的澄清。导师用推测解码 lookahead 说明，它是为尚未产生有效 KV 的后续位置预留请求容量，既不同于尾块的粒度空槽，也不同于整个 cache pool 的显存预分配；用户没有在此提交一个被判错的答案。（来源：codex:01a19a2d，`msg-85ba4b4eaf9372f0aaeb`、`msg-e83a6f1cc0410cdbcffe`。）

<a id="u2-p07"></a>
- [要点] **有效 KV、占用块容量和本次 payload 为什么不能互换？** 用户在已声明“搬全部占用块”的算例中，分别计算有效位置的元素量与向上取整后的块容量，并解释新增一个有效位置可能独占一个新块。其 payload 与占用容量相等是该题传输合同的结果，不是普遍等式；没有被选中传输的预留空间或采用不同片段粒度时，应另按实际交接描述统计。（来源：codex:01a19a2d，`msg-9ec29e73b72f4aede7cf`、`msg-ddd0b55163e7e9d59619`、`msg-74e583223c7d2200f0ac`；相关口径见[节点 7–8](../../课程网页/八周计划/plana-jd-w3-kv-layout-bytes-part2.html#node-7)。）

<a id="u2-p08"></a>
- [要点] **多个 rank 并发提交，能否把共享链路的时间下界再除以 rank 数？** 用户先合计四个 rank 的 payload，再除以题设给出的总有效带宽，并明确拒绝额外再除以四。导师确认共享瓶颈已经计入这个下界，同时补准“并发还可能引发竞争”需要测量，不能仅由同时提交推出额外开销。（来源：codex:01a19a2d，`msg-ddd0b55163e7e9d59619`、`msg-74e583223c7d2200f0ac`、`msg-01752d357eb27c5010bd`。）

<a id="u2-p09"></a>
- [高价值问题] 用户要求补充 `page_size_padded` 的用途与效果。导师核对后说明，它在所读版本中还用于协调不同缓存规格的物理页尺寸，不能只解释为硬件对齐，并把页尺寸、stride、分配容量和传输影响分开呈现；这是一项补充讲解，不能写成用户曾把 padding 理解错。（来源：codex:01a19a2d，`msg-6e961a4cb982756ed532`、`msg-58509e4378f17c8b6d2b`、`msg-85ae930124c82b7a8e01`；详见[页 padding 补充](../../课程网页/八周计划/plana-jd-w3-kv-layout-bytes-part2.html#add-7-page-padding)。）

<a id="u2-p10"></a>
- [高价值问题] 同一次追问中，用户希望看清推测解码额外槽位如何分配、使用与归还。导师用跨块过程区分“有效长度回退”“旧槽位覆盖复用”和“物理块归池”，并说明所读普通 FullAttention 路径拒绝候选后通常不会立即把尾块归还；完整过程保留在[槽位生命周期补充](../../课程网页/八周计划/plana-jd-w3-kv-layout-bytes-part2.html#add-7-spec-slots)。（来源：codex:01a19a2d，`msg-6e961a4cb982756ed532`、`msg-58509e4378f17c8b6d2b`、`msg-7e76148c78a973688616`、`msg-85ae930124c82b7a8e01`。）

<a id="u2-p11"></a>
- [高价值问题] 用户要求用真实大规模 PD 部署说明交接时间怎样评估，推动讲解从算术下界扩展到真实数据路径。导师选取 Mooncake，分别讨论公开组件测量、声明条件后的推算与生产请求延迟，并区分传输完成、D 可消费和开始 decode 的时刻；本次记录不把这些阅读与推算改写为用户完成过实测。（来源：codex:01a19a2d，`msg-6e961a4cb982756ed532`、`msg-58509e4378f17c8b6d2b`、`msg-7e76148c78a973688616`、`msg-85ae930124c82b7a8e01`；详见[交接评估补充](../../课程网页/八周计划/plana-jd-w3-kv-layout-bytes-part2.html#add-8-mooncake-eval)。）

<a id="u2-p12"></a>
- [要点] **写入位置和张量 shape 都正确，为什么仍可能读串请求？** 用户正确诊断 batch 从 `[A,B]` 改为 `[B,A]`、块表却保留旧行序的场景：A 的查询会读取 B 的历史，反之亦然。回答还沿 `CommonAttentionMetadata` 到 backend 的传参链指出，应恢复 `block_table` 与本步请求行的对应；导师认可判断与源码定位。（来源：codex:01a19a2d，`msg-01752d357eb27c5010bd`、`msg-e8a50c15193906f7aa9e`、`msg-f5a94f54418b35cce801`。）

<a id="u2-p13"></a>
- [要点] **MLA 减少长期缓存时，实际保存和读取的对象发生了什么变化？** 在同一个已训练 MLA 模型的两种正确实现对比中，用户区分了展开后的各头 K/V 与共享的压缩 `c`、位置 key，并解释这不是按查询头数复制 `c`。导师此前核对的 decode 路径通过运行时变换查询、汇总 latent、再做 value 上投影来重排计算，并非预先把所有大矩阵合成一块；表示与重排的完整图见[MLA 节点](../../课程网页/八周计划/plana-jd-w3-kv-layout-bytes-part3.html#node-11)。（来源：codex:01a19a2d，`msg-5c55921457086aedd1b9`、`msg-8ab06b4d0ef0d480c9af`、`msg-58588bef633400957223`。）

<a id="u2-p14"></a>
- [要点] **避免展开历史 K/V，是否也消除了 MLA 对历史长度的依赖？** 用户明确回答没有消除，并指出历史 `c` 的读取和查询计算仍随历史长度增长。导师肯定后补全了分数计算、softmax 与 latent 加权汇总，区分减少表示展开成本与消除历史 attention 成本。（来源：codex:01a19a2d，`msg-8ab06b4d0ef0d480c9af`、`msg-58588bef633400957223`、`msg-23aca7a804a13d50b68a`、`msg-796be973fd9066f6b737`。）

<a id="u2-p15"></a>
- [要点] **dense MLA 中，TP 和 DCP 为什么不能当成同一个容量除数？** 用户在固定路径下正确区分：没有 DCP 时，各 TP rank 需要完整 latent 历史；DCP 改变的是历史位置的归属，可以减少每 rank 保存的位置数。其字节计算和主要解释得到肯定，导师只把 MB 标签更正为 MiB；这项单位表述不作为概念纠错或独立制卡目标。（来源：codex:01a19a2d，`msg-8a0a5e12af9f64704ac1`、`msg-796be973fd9066f6b737`、`msg-53a832e6f51635927139`、`msg-84f2064034a61f9458fc`。）

<a id="u2-p16"></a>
- [要点] **把 MLA 容量估算迁移到混合模型，为什么不能只替换层数？** 用户用 Qwen3-Next 的 GatedDeltaNet＋full-attention 结构解释，递推矩阵、近期卷积尾部和保留份数都需要单独建账。导师补上 full-attention 层随长度增长的历史 K/V，并要求分别核对各类状态的 dtype、份数与 padding；用户主体分类被肯定，没有被判成把模型类型混淆。（来源：codex:01a19a2d，`msg-796be973fd9066f6b737`、`msg-53a832e6f51635927139`、`msg-84f2064034a61f9458fc`、`msg-7171982cff9a7531844d`。）

<a id="u2-p17"></a>
- [高价值问题] 用户追问递推 attention 只保留最新状态时怎样回到历史，并试探 `1 + num_speculative_blocks` 是否用于“回退到初始位置进行验证”。导师认可“最新状态不能像截短 KV 列表那样直接还原旧前缀”的方向，但解释候选后的状态快照可以直接选出正确接受边界，不必一律退回本轮起点重新验证。这是一段问题驱动的概念澄清，原问句不改写成已经确认的错误回答。（来源：codex:01a19a2d，`msg-e21b4d00fcb7de6e1f04`、`msg-73f60c831527e607d076`、`msg-f3d0274212168cc97f94`。）

<a id="u2-p18"></a>
- [转折] 用户明确说“我没看懂你的话”，要求清晰、详细并结合具体例子；导师承认先前混在一起讲了状态内容、存储槽位和副本用途。改写后的“我今天想吃一碗热汤”例子把各候选后的矩阵逐一列出：只接受“碗、热”时，选择对应前缀的快照，再处理重新采样的“面”，不能沿用已经包含被拒候选的状态。图解同时补明实际恢复还需要与该前缀一致的卷积尾部，数值内容不会因位置计数回退而自动恢复。（来源：codex:01a19a2d，`msg-5d20cf9d2b88fa24a98a`、`msg-9ce9d0b7b3200fad6618`、`msg-aa89fc97ce066a46472c`、`msg-88eeabc7c0f897961fc4`。）

<a id="u2-p19"></a>
- [转折] 在用户要求继续后，导师把 `align` 的两份基础容量具体化为跨块边界时的旧来源状态与新运行状态同时存在。讲解说明旧版本仍被使用时不能覆盖，同一块范围内推进又不意味着每个 Token 都复制一份；导师也将此前“绝对上限”的简称修正为基础规划口径，因为异步在途步骤可能增加临时保留。（来源：codex:01a19a2d，`msg-8d43cd746e77d4d54f54`、`msg-29d652f341a39b69da70`、`msg-2bedc8980b88ec68ee97`、`msg-88eeabc7c0f897961fc4`。）

<a id="u2-p20"></a>
- [要点] **prefill 的中途检查点为什么不等同于当前最终状态？** 在额外槽位追问中，导师用从 512 推进到 1000、另外保留 960 边界的例子，区分用于未来前缀复用的历史版本与当前请求继续使用的最终版本。检查点需要同时对应递推矩阵及卷积尾部，因此即使没有推测解码也可能需要；详见[状态历史与检查点图](../../课程网页/八周计划/plana-jd-w3-kv-layout-bytes-part3.html#add-14-state-history)。（来源：codex:01a19a2d，`msg-e21b4d00fcb7de6e1f04`、`msg-f3d0274212168cc97f94`、`msg-88eeabc7c0f897961fc4`。）

<a id="u2-p21"></a>
- [要点] **统一字节搬运接口以后，上层还要负责什么？** 用户沿 MLA 交接解释了状态类型、地址／布局、P/D 分片映射和消费元数据，明确“数据量对了”不足以证明推理正确。导师认为主体正确，只把时序补准为先准备本次接收区和片段映射，并区分直接写最终 cache 与经过中转后再加载，避免把用户的概括解释误记为完整错误方案。（来源：codex:01a19a2d，`msg-7171982cff9a7531844d`、`msg-23def0840b503d90a794`、`msg-f84047cf55c9502db9a1`、`msg-406811d0c37fa7153ace`。）

<a id="u2-p22"></a>
- [要点] **混合模型要恢复到一个缺失的历史边界时，怎样使用检查点？** 用户正确拒绝把处理完 1200 个 Token 的递推状态标成 1000，并选择从 960 检查点重放到目标边界。导师将输入范围补准为第 961–1000 个 Token，并说明已有 full-attention KV 可以保留，但在没有可直接复用的中间激活时，仍须完成相应前向，使所有层的递推矩阵、卷积尾部和历史 K/V 对应同一个有效前缀；不把编号补准判为概念错误。（来源：codex:01a19a2d，`msg-406811d0c37fa7153ace`、`msg-eb9b21cc57fd198522e0`、`msg-37aa81613b550e5a6940`。）
