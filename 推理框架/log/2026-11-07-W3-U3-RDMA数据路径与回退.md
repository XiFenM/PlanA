## 学习过程

<a id="u3-p01"></a>

- [要点] CPU 忙、报文带 UDP/IP，能否据此排除 RDMA？我答“CPU的活动忙可能是在轮询提交了的传输任务是否完成。UDP/IP 封装可能是RoCEv2做的封装，也使用RDMA”，并主动用实际被访问的 Host／GPU 区域判断是否直传。导师进一步把核查对象收窄到实际注册、后端访问区域和中间 Host 拷贝，避免只看业务张量原本位于 GPU；见[路径判断](../../课程网页/八周计划/plana-jd-w3-rdma-fallback.html#q-1)。（来源：`msg-5bd77d3c691366d5049d`、`msg-20d0182b8534a3057b3c`）

<a id="u3-p02"></a>

- [高价值问题] 我追问“这种做法和我在网上看到的被称为InfiniBand Reliable Connection (IBRC)是一回事吗？IBGDA是直接显存交给网卡吗？”答复把“请求经 CPU proxy”与“payload 经 Host 中转”分开：NVSHMEM 的 IBRC 也可使用 GPUDirect RDMA，典型 IBGDA 改变的是网卡任务提交分工，CPU-assisted IBGDA 又把 doorbell 交给 CPU。这里保留为术语与路径辨析，不把提问记成错误答案；具体版本见[IBRC／IBGDA 补充](../../课程网页/八周计划/plana-jd-w3-rdma-fallback.html#add-2-1)。（来源：`msg-d720c3f4b89d6caabfd8`、`msg-89d6d849088b5f9c2f99`）

<a id="u3-p03"></a>

- [要点] 非 inline WRITE 提交成功后，复用 WR／SGE 与覆盖源数据为什么不能作同一判断？我答“WR/SGE只是描述用的元数据信息，会被复制放到提交队列中，提交成功后可以复用了”，同时保留仍可能被读取的 payload。后续[请求转换图](../../课程网页/八周计划/plana-jd-w3-rdma-fallback.html#fig-4-2)把这句话细化为 provider 依据 WR／SGE 构造 WQE，描述转换与 RNIC 读取源数据是两条不同的依赖链。（来源：`msg-a91652eefd7ca5866b66`、`msg-1f5f0828f07bf73c52fc`、`msg-d972585cfa0f38b66531`）

<a id="u3-p04"></a>

- [转折] 两个 QP 共用 CQ 时，我已指出“一个完成不意味着另一个的完成”，但把“尚未取得A的WC”接成了“A尚未完成”。导师保留核心判断，只把结论补准为“尚无 A 的完成依据”，因为操作实际完成与软件取得对应结果不是同一个时点；见[检查 2](../../课程网页/八周计划/plana-jd-w3-rdma-fallback.html#q-2)。这一条记录证据强弱的措辞差异，不扩写成整题答错。（来源：`msg-a91652eefd7ca5866b66`、`msg-1f5f0828f07bf73c52fc`、`msg-0c5743054028d349c189`）

<a id="u3-p05"></a>

- [高价值问题] 我问“为什么SEND还需要准备缓冲区，这是做什么缓冲用的？”答复沿固定 rping 的两条数据流区分：WRITE 的主体数据进入 `rdma_buf`，SEND 控制消息进入预先登记的 `recv_buf`，CQ 提供完成记录而不是消息存储。导师还补明 WRITE 后另发 SEND 是该示例的通知选择，不能推成所有后端的唯一安排；见[SEND 接收区说明](../../课程网页/八周计划/plana-jd-w3-rdma-fallback.html#add-4-1)。（来源：`msg-a91652eefd7ca5866b66`、`msg-a61894c836964053ac7f`、`msg-0c5743054028d349c189`）

<a id="u3-p06"></a>

- [高价值问题] 我继续问“‘确认数据可见’这个操作我听过很多次了，具体而言，究竟是什么具体操作叫做‘确认数据可见’？”导师承认此前表述笼统，把它落实到生产、网络完成、H2D 与消费的接口依赖，例如 CUDA 同 stream 顺序或跨 stream 的 event 等待，而非凭一个 ready 标志作判断。Host→CPU、Host→GPU、网卡直写 GPU 的差异已放在[具体同步动作](../../课程网页/八周计划/plana-jd-w3-rdma-fallback.html#add-4-1)，本记录不重复整套 API 说明。（来源：`msg-a91652eefd7ca5866b66`、`msg-a61894c836964053ac7f`、`msg-0c5743054028d349c189`）

<a id="u3-p07"></a>

- [要点] Host staging 中，网络写完以后，D Host 槽与设备消费分别还等什么？我答“必须等H2D不再读取它后才能复用”，并要求消费 stream 等拷贝完成。随后把这一判断放回[四区域数据路径](../../课程网页/八周计划/plana-jd-w3-rdma-fallback-part2.html#node-5)：P 设备、P Host、D Host、D 设备分别对应 D2H、网络读取、H2D、计算消费者，不能把一次网络完成当成四处都可回收。（来源：`msg-78b962a76e3b0393fd2c`、`msg-9df03d461ce941c09638`、`msg-bf5cb1d38b3237201f07`、`msg-31b75452dbc548ed7921`）

<a id="u3-p08"></a>

- [要点] 只提供固定四 rank Broadcast 时，怎样承接一个只属于 P、D 的交接请求？我答“四个rank都要按一致的顺序、root、count和dtype参与，2、3也要准备接收缓冲区”，并说明无关 rank 的接收、内存与协调成本。这里的推理从接口参与范围延伸到系统代价，而不是把 collective 当成能任取两个 rank 的点对点调用；见[受限环境检查](../../课程网页/八周计划/plana-jd-w3-rdma-fallback-part2.html#q-3)。（来源：`msg-78b962a76e3b0393fd2c`、`msg-9df03d461ce941c09638`、`msg-bf5cb1d38b3237201f07`）

<a id="u3-p09"></a>

- [转折] 围绕 GPU initiated，我曾追问“所以IBGDA和GPU initiated指的都是”GPU 自己构造并提交网卡任务“？”导师先肯定典型 IBGDA 的分工，最终补明必须区分 GPU 发起 API 请求与向 NIC 提交工作：GPU 请求可交给 CPU proxy，而 GPU 仅生产数据、CPU 主动调用通信接口则是 CPU 发起。GPUDirect RDMA 另描述 RNIC 直接读或写显存；这是连续澄清形成的分层口径，不作为真实错答纠错，见[控制流程图](../../课程网页/八周计划/plana-jd-w3-rdma-fallback-part2.html#add-5-1)。（来源：`msg-a2b97b1227eb5df5a05d`、`msg-891c6b2df8bbb93804eb`、`msg-570497aee000290a25b1`、`msg-1ec4f46dc3a2528125a8`）

<a id="u3-p10"></a>

- [高价值问题] 我问选择 GPU／CPU initiated 是否只是代码安排，“并没有客观条件的制约吗？”导师补上此前省略的可实现性前提：GPU API 或请求通道、proxy 的同步与推进，以及直接驱动 RNIC 所需的队列访问、映射和排序支持，都限制可选路径。只有平台支持多条路径后，才谈消息规模、控制往返与 GPU 资源开销的性能取舍；见[实现条件](../../课程网页/八周计划/plana-jd-w3-rdma-fallback-part2.html#add-5-1)。（来源：`msg-2f2e702debcd3ae0b684`、`msg-de0888b5cffb8dcbabad`、`msg-8295894b1a152c9a21ab`）

<a id="u3-p11"></a>

- [要点] 两端能力不对称、随后 RDMA 又不可用时，怎样只改变必要的数据段？我先选择 P 显存直达 RNIC、D 经 Host→设备，再在 TCP 条件下说明“从原本的RINC直接读取显卡显存改成通过D2H传输到host 内存的中转缓冲区”。导师保留这两条路径与 CPU 发起判断；迁移后的接收端仍须收到完整数据、核对映射并完成 H2D／消费依赖，不能用本地发送返回替代，见[综合题](../../课程网页/八周计划/plana-jd-w3-rdma-fallback-part2.html#q-a1)。（来源：`msg-6390f1571747e5006845`、`msg-6a9309baa3de7a5f1d0b`、`msg-9411c09e5d9253dc8757`、`msg-31b75452dbc548ed7921`）

<a id="u3-p12"></a>

- [纠错] 场景是 P 设备显存经 RC WRITE 写入 D Host，再由 H2D 写入 D 设备目标；我说“先要将P端显存对应位置、D端host中转区和D端设备上显存位置进行注册，形成MR”。正确差值仅在 D 设备目标：本次 RNIC 实际访问 P 显存源区与 D Host 区，D 设备区只参加本地 H2D，不因处在整条数据路径上就必须成为本次 RDMA MR。把中转位置翻到 P 后，我又正确对应 P Host 的地址／lkey 与 D 设备目标的地址／rkey；见[注册范围变式](../../课程网页/八周计划/plana-jd-w3-rdma-fallback-part2.html#q-4)。（来源：`msg-6a9309baa3de7a5f1d0b`、`msg-98d8d245a8edbc7b250e`、`msg-31b75452dbc548ed7921`、`msg-7315aefd6288d301df89`）

<a id="u3-p13"></a>

- [转折] 我问“P的设备源缓冲区和设备源数据区域有什么区别？P端需要从源数据区拷贝到设备缓冲区再让RINC读取吗？”导师说明自己此前换了称呼：原综合题里二者是同一块显存，buffer 只是用途名称，没有额外设备副本或拷贝。随后我复述“只是一个不同视角下的称呼不同，本质是同一块显存”，这属于当场消除措辞歧义，保留过程但不另制纠错卡。（来源：`msg-c25b126f14b58913003d`、`msg-aa580b140e917089c3e9`、`msg-ebee8f8f882f7e0332f3`、`msg-d682c544903c8b1b8657`）

<a id="u3-p14"></a>

- [高价值问题] 我指出“MR、PD、QP、WR、SGE、CQ、CQE、WC等等。这部分很难理清楚”，要求按生命周期画出相互关系。补图把资源关联与单次任务分开：PD 关联 MR／QP，CQ 独立建立后与 QP 关联；WR／SGE 经 provider 形成 WQE，设备完成记录 CQE 再成为应用取得的 WC，payload 独立存在。具体关系回看[资源图](../../课程网页/八周计划/plana-jd-w3-rdma-fallback.html#add-3-1)及[请求与结果转换图](../../课程网页/八周计划/plana-jd-w3-rdma-fallback.html#fig-4-2)，不把图示成稿当成学习者独立推导。（来源：`msg-d21ab77f59d04e90661a`、`msg-d972585cfa0f38b66531`、`msg-33ecb8d96ddb921776a1`）
