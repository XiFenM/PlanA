## 学习过程

<a id="u4-p01"></a>

- [要点] 丢弃旧完成回调，能否让旧目标块安全复用？——用户回答“但不能阻止旧传输继续写入T”，并要求保留 handle、请求／块关联，等待旧访问及其他使用者结束；原答正确。后续整理保留[控制结果与实际访问的区分](../../课程网页/八周计划/plana-jd-w3-failure-system-design.html#node-1)，不把它记录成用户曾误判超时可以立即回收。（来源：`msg-7aa87f9b1cd7670ca9af`、`msg-2e6e1a026e5ac6bb9404`、`msg-43ebcab2d06117f9dc4b`）

<a id="u4-p02"></a>

- [要点] 为什么通知总数不能替代每次尝试的读者集合？——对 `(R,a,A)`、`(R,b,A)`、`(R,b,A)`，用户按尝试与读者身份归属、判重，并指出旧尝试 a 的清理责任仍在；导师补明 b 同样缺少 B 的完成依据。用户也说明软件代际或丢弃旧回调不能阻止 a 写入被 b 复用的物理地址；[身份与访问模型](../../课程网页/八周计划/plana-jd-w3-failure-system-design.html#node-3)是设计要求，不能据此宣称固定 NIXL 已实现同样的 seen-set。（来源：`msg-fc661b9583ed32698458`、`msg-393635bb042df3c52649`、`msg-4e01260eccede70ff2d9`、`msg-7e5dcdd9a5638c87c183`）

<a id="u4-p03"></a>

- [高价值问题] 用户问：“为什么会出现`(R, b, A)`、`(R, b, A)`这种重复通知的情况？”——导师用“接收方已处理，但确认未返回，于是发送方重发同一事件”解释重复交付；重试的是通知送达，不代表重新读取了 KV，也不应自动换成新尝试 ID。该例是允许应用层重发的通知协议模型，与底层报文重传及固定 NIXL 是否重复交付分别判断；当时参考了 [Azure 的重复检测说明](https://learn.microsoft.com/en-us/azure/service-bus-messaging/duplicate-detection)。（来源：`msg-036c6171f9a0de9a1b46`、`msg-f7797da632ce6ce55aca`、`msg-41dc19042333e16abb34`）

<a id="u4-p04"></a>

- [转折] Peer 在原地址重启时，用户正确拒绝直接复用旧描述，但曾说旧请求“要给那些请求进行重新分配”；导师补准，新实例可供新尝试使用，旧在途操作不会自动迁移过去，仍须按旧尝试的访问和引用收尾。服务地址相同不等于实例、注册身份或访问权限相同，详见[新访问与旧清理的分离](../../课程网页/八周计划/plana-jd-w3-failure-system-design.html#node-5)。（来源：`msg-af67667c02da4a9f4353`、`msg-6f77bd409c276b6a56b8`、`msg-693d5887bcf431e79f23`、`msg-9b0ae67b3fa4ee61507c`）

<a id="u4-p05"></a>

- [转折] 租约测试问题中，用户正确判断 mock 不能证明回收安全，但补充“如果心跳通知在租约到期之后才来，那么实际访问还在途中”；导师指出心跳迟到本身也不能推出在途状态。后续用户明确改为“心跳只说明源KV续租，不能说明访存完成”，将控制面保留政策与访问完成证据分开；[租约模型](../../课程网页/八周计划/plana-jd-w3-failure-system-design.html#node-6)不能代替真实后端停止访问合同。（来源：`msg-6f77bd409c276b6a56b8`、`msg-693d5887bcf431e79f23`、`msg-79dea59e4ad7a40137f7`、`msg-099899d734f3e5bb383e`）

<a id="u4-p06"></a>

- [高价值问题] 用户追问“写入操作排队是什么意思”，并怀疑目标块尚未准备好时为何出现心跳续租；导师承认题设省略前提，补明源 S 就绪、目标 T 已分配、任务已被后端受理，但受控队列暂时不推进写入。续租保护的是未来仍需读取的 P 源 KV，提交受理与实际访存开始是不同事件；此处是题意澄清，不登记用户概念错误。（来源：`msg-c5f4bf79c4f54b977efb`、`msg-64f480899cad89fbbfc6`、`msg-7dfabc73f0d189d03129`）

<a id="u4-p07"></a>

- [要点] 故障测试为什么不能只看最终结束／失败集合？——用户独立提出：写入未结束且释放失败时关联仍保留、T 不回池；访问结束且释放成功后只归还一次，后续不重复上报，同时明确受控软件后端不能证明真实 RNIC 的取消、停止访问与设备可见性。这个回答连接了中间安全性和最终收尾；[具体测试规格](../PD-KV故障矩阵与测试设计.md#一个可执行的-b-级测试设计)由导师整理，尚未创建或运行。（来源：`msg-9b0ae67b3fa4ee61507c`、`msg-79dea59e4ad7a40137f7`、`msg-099899d734f3e5bb383e`）

<a id="u4-p08"></a>

- [要点] 接入设备直传与双端 Host RDMA，需要分别打通什么？——用户主动选择分支考虑；导师将两者共用的请求／块映射与完成语义，分别连接到设备内存注册、可见性，以及 Host pool、D2H／H2D 和 copy 完成边界。平台支持表或内存类型声明不实现底层注册与访问；职责、接口与约束集中保存于 [Change Card §1–5](../../面试准备/自我准备/学习设计/ChangeCard-03-PD-KV-transport.md)，属于条件式设计，不是平台已支持的实测结论。（来源：`msg-42d421c050aae3a82f4d`、`msg-556abffd0673d0e3110e`、`msg-a0b6073533c7a2b92073`、`msg-294da391176fd4a7c37e`、`msg-9ebb81c0f6495abc0421`）

<a id="u4-p09"></a>

- [转折] 用户选择“显式配置直传或 Host 中转，并在启动时校验；条件不满足就报错”，并选择 KV 加载已确认失败、旧访问安全收尾后采用 fail。导师将“Host RDMA 可用”保留为此方案的待核验前提，并说明 fail／recompute 属于业务处理策略，不能替代旧访问清理；本次方案没有选择自动重试或运行中静默切路。（来源：`msg-556abffd0673d0e3110e`、`msg-ce26d09f96c84089b06d`、`msg-90129f4babd230b5457c`、`msg-1fa716e61766793ab7f9`）

<a id="u4-p10"></a>

- [转折] 综合题未重新说明 A／B 的传输路径，用户将 A 理解为“Host pool 不变、仅设备 pool 迁移”，回答只需改 D2H／H2D 端点；导师起初将其判成直传分支偏差。用户追问“我还以为是独立的验收题”后，导师撤回该误判并承认题意歧义；原答中正确的 Host 注册更新、旧访问保护和验证边界保留，不能据此制作“用户不懂 MR”的纠错卡。（来源：`msg-e4729396a59b598abece`、`msg-926b9999edb3e31fc722`、`msg-0a499d415eca9d7788a5`、`msg-57e1ecf7980458c0d9a9`、`msg-2fc762b0a8a6956d704f`）

<a id="u4-p11"></a>

- [要点] 明确直传 READ、仅 D 目标从 T 改为未注册的 T_new 时，应改变哪些对象？——用户回答本地接收描述指向 T_new，远端源仍为未变的 P 设备区 S，并让旧 T 等旧写入与相关引用结束再回收；导师补明 T_new 尚未被有效注册覆盖，必须先建立有效注册再用于新操作。描述对应关系和旧区保护来自用户回答，新注册前提是导师补明；具体参考见[澄清后的综合题](../../课程网页/八周计划/plana-jd-w3-failure-system-design-part2.html#q-a2)。（来源：`msg-2fc762b0a8a6956d704f`、`msg-1a166b8c9e4bb9526c78`、`msg-d241677523a6266b5293`、`msg-cdad79823ccea9e0726f`）

<a id="u4-p12"></a>

- [高价值问题] 用户问 W3 主要针对哪些岗位需求、面试官会怎样追问；导师将内容对应到框架与 KV 管理、多机成本分析、PD 后端接入及故障验证，并据岗位职责推演六类问题。用户随后要求单独整理[面试复习页](../../课程网页/八周计划/qa-w3-interview-preparation.html)；这些问法不是核实的公司真题，岗位实时状态不进入记忆卡，参考回答也不充作用户真实项目经历。（来源：`msg-de998dbecd428c198ce5`、`msg-78a47e59b656f79c2c19`、`msg-6880e44ececedacc4bc5`、`msg-fdd096bd468fc6fee1c4`）
