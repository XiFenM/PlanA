## 学习过程

<a id="w4-u1-p01"></a>

- [要点] 同一 GEMM 本体耗时相同，乙每秒搬的字节更多，说明谁算得快？我先固定 shape、输入和精度，两边的有效数学工作量都是 `2MNK`，因此有效数学吞吐相同。乙还有每次调用都要串行做的权重重排，我提出从重排开始计到 GEMM 完成，才和甲的完整投影可比。（消息 `msg-f21a580e03883875640f`、`msg-8b3255e284be786f3a20`、`msg-9dddb625b6aad19f07e7`）

<a id="w4-u1-p02"></a>

- [高价值问题] 为什么一个更慢的实现，相对 Roofline 的百分比还能更高？我追问把两边流量统一换成理想预算 Q₀ 会发生什么。用各自实际流量时，甲多搬的数据会降低实际算术强度和对应的上界。换成共同的 Q₀，两边参考高度相同，较慢一方的比率就较低。（消息 `msg-57ea26f086e19e305ae9`、`msg-a357ab403d1398bad95e`、`msg-2c3a0f1990e90e9a1fc9`）

<a id="w4-u1-p03"></a>

- [要点] 达到甚至超过一次微基准画出的参考线，先核对什么？我先核对精度、shape、访问方式、频率、占用资源和计时区间。特定条件下测出的微基准只能约束可比场景，单凭越线不足以判计时出错。（消息 `msg-57ea26f086e19e305ae9`、`msg-1d330a019bb340553c43`）

<a id="w4-u1-p04"></a>

- [要点] 设备事件测到相同任务稳定变快，报告里能写到哪一步？我认可 GEMM 本体耗时下降、有效数学吞吐上升，并指出还缺实际 HBM 读写量。用 Q₀ 除以实测时间得到按理想流量计算的有效带宽，不能把它当作硬件计数器读数，再据此归因于内存访问优化。（消息 `msg-93a4a06efa93d42b7f7c`、`msg-47b8ac0c3ab0ff5dff6e`）

<a id="w4-u1-p05"></a>

- [转折] 做预测前，学习者确认可选独占的 GPU，再把实验限定为同一块 GPU 和相同精度，仅将 M 从 128 增至 256。我的依据是权重矩阵 B 的尺寸不变，F 翻倍而 Q₀ 只小幅增加，因此若原先受带宽影响，耗时有可能增长不到两倍。若吞吐不升，原先的瓶颈解释就需要重新检查。（消息 `msg-e0c51a9e62747d48a013`、`msg-5e84548bb8cf51a1fe50`、`msg-60318888f872853a6930`）

<a id="w4-u1-p06"></a>

- [要点] 耗时增加与有效吞吐提高能同时成立吗？我算出耗时增至 1.717 倍、吞吐提高约 16.5%，对应的是翻倍的工作量。相对模型上界的比率下降，是因为上界从约 253.39 提高到 312 TFLOP/s，分母增长更快。这个观察支持事前趋势，实际从带宽瓶颈转为计算瓶颈仍需额外证据。（消息 `msg-047b97c1973142e56fc1`、`msg-8faa6defa205ec780c0a`、`msg-ef5066f9edf86d680659`）

<a id="w4-u1-p07"></a>

- [高价值问题] 指标表里的“中位时间”到底对什么取中位数？回看[实践指标的逐项计算](../../课程网页/八周计划/plana-jd-w4-validation-interview.html#practice-metrics)后，口径固定为每轮设备事件总时间先除以 20 次调用，再从五个摊销时间中取中位数。吞吐由该时间和 F 复算，理论上下界则另外用 Q₀ 和硬件参数。（消息 `msg-5cf8ab0dfad1881bca76`、`msg-acc1305cd7e2287dd49f`）
