## 学习过程

<a id="w4-u2-p01"></a>

- [高价值问题] 客户端收到的一个输出消息一定是一个 token 吗？我先追问了发送粒度。服务可以把多个 token 合在一条消息里，读 raw ITL 前要核对究竟打的是消息到达时间，还是逐 token 的时间戳。（消息 `msg-668bc3e10bd56b273efc`、`msg-9f2c09a086b3ee5b9f66`）

<a id="w4-u2-p02"></a>

- [纠错] 在两种 benchmark 的到达方式、统计对象都不同的题里，我说“并没有做所谓的调度工作”。服务端仍然在调度。现有对照隔离不出调度配置的作用。要检验那个作用，应重放同一输入和到达序列，固定设备、模型、并发与计时边界，只改变调度配置。（消息 `msg-bd885583aa593bc273fc`、`msg-6fc169f32e075a5c4d54`、`msg-dfcd607091f279a85001`、`msg-a8fd3e03ef1bf3540a7e`）

<a id="w4-u2-p03"></a>

- [纠错] 我把 TPOT P99 当作请求里较慢的一段，后来明确说“我之前还以为是一条请求里不同时段呢”。每条请求先贡献一个首输出后的平均每 token 耗时，再在请求之间取分位数。P99 是阈值。要找单条请求中断断续续的停顿，还得保留它的原始输出间隔。（消息 `msg-1a9dd554aa401c0aa8d1`、`msg-ddd4cf64da1985e57505`、`msg-7917a3a317632a6d2c31`、`msg-04ffa6939a25f8609934`）

<a id="w4-u2-p04"></a>

- [高价值问题] 什么时候值得专看 TPOT？对长输出，若输出长度相同，它能比较从首个输出到最后输出期间的平均节奏。我把它与首段的 TTFT、请求完成的 E2EL 和定位局部停顿的 raw ITL 并列起来，核对时保留同一请求 ID。（消息 `msg-1a8819d690a4350890c6`、`msg-de0538a5393bb22748f2`、`msg-8ceda62605448525041c`）

<a id="w4-u2-p05"></a>

- [要点] 某条 Host 分支变短，为什么用户可能感受不到？我先找决定两条并行分支何时都完成的慢分支，再查结果组装、发送及客户端到达。开／关 profiler 的差值还含采集开销，我提出补做两组均关闭 profiler 的同负载对照。（消息 `msg-f9ba0bbf4f080d9aa12d`、`msg-bf161c034c7c32c649c8`、`msg-70753d0aee13a52b3e1b`、`msg-16cf80e5d89384584a2e`）

<a id="w4-u2-p06"></a>

- [转折] 我追问 vLLM 既然按 token 调度，还需要什么叫 continuous batching。随后把“这一轮有哪些请求可以进来”与“每个请求这轮给多少位置”分开，又指出 packed 输入更便于拼装不同长度的工作。物理上相邻的 token 仍由各自的元数据和 KV 隔离。某一轮 KV 不够导致新请求等候，也仍然可以是动态组批。（消息 `msg-3073d279caccde95d609`、`msg-8c22f4fddac82a79713c`、`msg-331d10e8ed6b7ca58c7e`、`msg-f2f274c686d05c597bcc`、`msg-5c18498d2348f7135022`）

<a id="w4-u2-p07"></a>

- [纠错] P99 讨论里我问“哪里体现出样本量混用了”。导师澄清要评估的是报告中“两个 P99 都已稳定”的推断，我原先已经分清请求级和间隔级样本。再次回答时我指出稳定性需要多轮重复，指标变好或变差本身不回答稳定性问题。（消息 `msg-c1f213fd45786da9ac60`、`msg-b719a7f38f709f2d4510`、`msg-199b824a5bf1e72a0911`、`msg-66c76c54271e827138bb`、`msg-9ebf553a6f52a0712ff1`）

<a id="w4-u2-p08"></a>

- [要点] 两条 decode 都 ready，缩小一个新 prompt 的 chunk 就能让它插进本轮吗？我核对每步实际可调度量。若两个位置都已被 decode 占用，prefill 仍没有份额。后来又分清 ready 只说明有下一步可做，实际入批须看本轮记录，单步装更多输入带来的 TTFT、ITL 变化也要用实测判断。（消息 `msg-7f52198e78a012fe2c34`、`msg-aa566c9afcada8c481f5`、`msg-c2fb094e234c82a2f88d`、`msg-0db9bc1709aa6a47fae3`、`msg-ac19727ba95b40a822a4`、`msg-d0a5994173a6e6d3f4ee`、`msg-ab81bf476401fb7c4515`）

<a id="w4-u2-p09"></a>

- [转折] 我在结果出来前预测调度预算从 512 提高到 2,048 后，TTFT 可能下降、吞吐可能上升、ITL 可能变长，并追问为什么要用 CPU FP32。这里选择独立参考实现是为了先核对正确性。固定负载每档三轮的中位结果支持 TTFT P50 从 427.90 降到 348.22 ms、输出吞吐从 331.81 升到 381.78 token/s，而 raw ITL P99 从 75.819 升到 141.440 ms。这些是每轮统计量的再汇总。（消息 `msg-14e434bf23d46178a04e`、`msg-f0ca35d6c14672bb5573`、`msg-1bc83a67de7cb54926cf`、`msg-be47d00caa789ac80456`、`msg-f9a92f817252d91a9e2b`、`msg-99854a8d5e835363038c`、`msg-fc10b4278893b0fe5bed`）

<a id="w4-u2-p10"></a>

- [要点] trace 里的 Host 等待时间能与 GPU kernel 耗时直接相加吗？我识别出异步提交和区间重叠。进一步对齐后，Host 在 19.215 ms 已经开始等指定 event，所选 kernel 到 20.913 ms 才开始执行。这一片段还不能单独解释两档配置的性能差值。（消息 `msg-fc10b4278893b0fe5bed`、`msg-59059ac8015afe66b549`、`msg-4db3ba5381a361f20a06`）

<a id="w4-u2-p11"></a>

- [高价值问题] 课后我专门追问 `max_num_scheduled_tokens` 和 `max_num_batched_tokens` 不等时谁起作用。沿当时补充页固定的源码，把每步可下发的工作量和执行侧输入容量分开，在出现推测解码额外槽位时分别核对。[这段补问](../../课程网页/八周计划/plana-jd-w4-benchmark-trace-scheduling-part2.html#add-6-1)发生在 11 月 16 日，接回本单元。（消息 `msg-dbd95a8aa1507494b6e8`、`msg-49d8dd94ca70f41ebf5f`、`msg-9e7ffed726d80d5847fc`、`msg-9dee0f95efdbb0133a74`）
