# 在 M4 MacBook Air 上把复习笔记读出来

项目计划 · 2026-11-23 调研。目标设备为本人的 Apple M4 MacBook Air，使用 macOS 原生 Arm64 CPU。以下是待执行的实验，速度、内存和听感以这台机器的记录为准。

**第一份交付是一篇自己愿意反复听的复习音频。** 第一版选 **Kokoro-82M v1.1-zh 未量化版 + sherpa-onnx**。它已有中文音色、中英词典、可直接加载的 ONNX 图和 macOS Arm64 运行程序。先听技术术语是否清楚、整篇是否漏读，再用同一张模型图做 **Arm KleidiAI** 开关对照，检验 Arm 的 CPU 微内核能否缩短生成时间。[中文模型卡](https://huggingface.co/hexgrad/Kokoro-82M-v1.1-zh) · [中英文模型包与试听](https://k2-fsa.github.io/sherpa/onnx/tts/all/Chinese-English/kokoro-multi-lang-v1_1.html) · [ONNX Runtime 的 KleidiAI 集成](https://onnxruntime.ai/docs/performance/kleidiai/)

选型看三个问题。中英混排的技术笔记能否读清楚？在 M4 上能否明确指定 CPU？为一次试听要下载多少文件、搭建什么环境？下表的 MB、GB 为十进制文件大小，各行注明了统计对象。运行时峰值内存留到真机上另测。

## 2. 第一次在 Mac 上生成声音

**第一段只求听得见。** 在 Mac 本地打开原生终端，执行 `uname -m` 应得到 `arm64`。如果后面用 Python，再用 `python3 -c 'import platform; print(platform.machine())'` 确认解释器也是 `arm64`。记录 `sw_vers -productVersion`、`sysctl -n machdep.cpu.brand_string` 和 `sysctl -n hw.memsize`（字节）。Apple M4 是硬件，macOS 是系统，此处的推理后端是 ONNX Runtime CPU。样例使用预编译命令行程序，首段无需搭建 Python 环境。[Apple 原生 Arm64 说明](https://developer.apple.com/documentation/apple-silicon/building-a-universal-macos-binary) · [sherpa-onnx 的 macOS 支持](https://k2-fsa.github.io/sherpa/onnx/install/macos)

在空的实验目录里运行下列命令。程序固定为 **sherpa-onnx v2.0.3 的 osx-arm64-shared 包**。首次下载约 387 MB，包括程序包 21.9 MB 和模型包 364.9 MB，解压与 WAV 另占空间。校验值来自发布清单。模型、词典、音色与文本规范化文件备齐后，合成可以断网进行。[程序发布页](https://github.com/k2-fsa/sherpa-onnx/releases/tag/v2.0.3) · [模型发布清单](https://github.com/k2-fsa/sherpa-onnx/releases/tag/tts-models) · [音色编号表](https://k2-fsa.github.io/sherpa/onnx/tts/all/Chinese-English/kokoro-multi-lang-v1_1.html)

```sh
(
  set -eu
  tts_bin=sherpa-onnx-v2.0.3-osx-arm64-shared
  tts_model=kokoro-multi-lang-v1_1
  curl -fL --retry 2 -o "$tts_bin.tar.bz2" "https://github.com/k2-fsa/sherpa-onnx/releases/download/v2.0.3/$tts_bin.tar.bz2"
  curl -fL --retry 2 -o "$tts_model.tar.bz2" "https://github.com/k2-fsa/sherpa-onnx/releases/download/tts-models/$tts_model.tar.bz2"
  shasum -a 256 -c <<'HASHES'
14afb4ed15dc4f376c69be5a795039824e47f5ffcfc2488556f796ecaf420d07  sherpa-onnx-v2.0.3-osx-arm64-shared.tar.bz2
b78e1ac42b852e839cceaafbe88f66806bf5860992d1d7b9a3f2ad1198427aed  kokoro-multi-lang-v1_1.tar.bz2
HASHES
  tar -xjf "$tts_bin.tar.bz2"
  tar -xjf "$tts_model.tar.bz2"
  mkdir -p out
  DYLD_LIBRARY_PATH="$PWD/$tts_bin/lib" "$tts_bin/bin/sherpa-onnx-offline-tts" \
    --provider=cpu --num-threads=2 --sid=3 --speed=1.0 \
    --kokoro-model="$tts_model/model.onnx" --kokoro-voices="$tts_model/voices.bin" \
    --kokoro-tokens="$tts_model/tokens.txt" \
    --kokoro-lexicon="$tts_model/lexicon-us-en.txt,$tts_model/lexicon-zh.txt" \
    --tts-rule-fsts="$tts_model/date-zh.fst,$tts_model/number-zh.fst" \
    --output-filename=out/smoke.wav '今天复习推理服务。先看用户等了多久，再去查时间花在哪里。'
  afinfo out/smoke.wav
  afplay out/smoke.wav
)
```

通过标志是 WAV 可播放、时长大于零、采样率为 24 kHz，并能听到完整的两句话。已在 x86_64 环境静态核对上述 macOS 程序包、动态库、命令行参数和归档标识。首次实际合成与试听留给这台 M4。[命令行入口与计时位置](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.3/sherpa-onnx/csrc/sherpa-onnx-offline-tts.cc) · [Kokoro 双语词典参数](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.3/sherpa-onnx/csrc/offline-tts-kokoro-model-config.cc)

## 3. 把真正要复习的一篇笔记做成音频

第一篇取[单元六讲解页](../../../课程网页/八周计划/plana-jd-w4-mock-readiness.html#ref-pd-split)的 PD 拆分两问，只选题干、回答要点和参考口述。复习时先听问题，留出短暂停顿，再播放答案。后续也可输入 Markdown 或纯文本。

| 环节 | 做法与产物 |
| --- | --- |
| 准备朗读稿 | 提取标题和选中段落，去掉导航、链接地址和代码围栏。给缩写和公式配朗读文本。例如 `P99` 读作“第九十九百分位”，`256 MiB ÷ 25 GiB/s = 10 ms` 可读作“四分之一吉比字节的数据，按每秒二十五吉比字节传，理论上需要十毫秒”。原文与朗读文本成对保存，逐项核对数字、单位和否定词。 |
| 分段、合成与合并 | 按标题、问答边界和句末标点分段。过长段落再沿逗号拆开，数值和单位放在一起。首版固定中文音色 3、语速 1.0。每段导出 WAV，根据实际采样数和采样率合并为 `review.wav`。用 `segments.jsonl` 保存段落 ID、原文、朗读稿、音频起止及输入配置指纹，改错时只重新合成受影响段落。 |
| 实际听一遍 | 准备 12 句固定小样，中文普通句、中英混排、数字与单位各 4 句。加入 `vLLM`、`KV cache`、`TTFT`、小数、百分比和很短的标题，再听一篇约 3–5 分钟的完整音频。记录错读的词与时间点，分别判断是朗读稿、词典还是模型音色的问题。 |

建议的听感门槛是 12 句中至少 11 句首听能复述原意，清单里的关键数字、单位和否定词全部读对。听完整篇时，检查顺序、漏段、重复、明显削波和意外长静音。记录一次断网重跑的结果。以后若要接入 `blog-voice`，可直接交给它普通 WAV 与段落索引。

## 4. 让 Arm 工具真正参与推理

**要验证的执行路径**是“朗读文本 → 规范化与音素 → Kokoro ONNX 图 → ONNX Runtime CPU 执行提供程序 → MLAS 数学库 → 符合条件的 Arm KleidiAI 微内核 → 音频采样”。sherpa-onnx 负责模型与音频流程，ONNX Runtime（ORT）执行计算图。**KleidiAI 是 Arm 提供的库**，Apple Instruments 或 LLDB 可用来观察真实调用。上一节的 `--provider=cpu` 只选定 CPU，实际内核由运行时派发。现成的中文 ONNX 图使这条路线可以直接复用原音色和词典。[Arm KleidiAI 源码](https://github.com/ARM-software/kleidiai) · [ORT 的支持范围](https://onnxruntime.ai/docs/performance/kleidiai/) · [Arm 的 MLAS 集成示例](https://learn.arm.com/learning-paths/mobile-graphics-and-gaming/performance_onnxruntime_kleidiai_sme2/kleidiai_integration/)

1. **先检查这台机与实际加载的库。** 保留二进制的 `file` 与 `otool -L` 输出，在一次诊断运行中用 `DYLD_PRINT_LIBRARIES=1` 确认实际加载的 ORT 动态库路径，记录文件哈希。sherpa v2.0.3 的 macOS Arm64 共享构建脚本指向 ORT **1.28.2**。若追 SME2 内核，在本机读取 `sysctl -n hw.optional.arm.FEAT_SME2`。硬件支持、库编入、当前算子实际命中分开登记。[sherpa 的版本选择](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.3/cmake/onnxruntime-osx-arm64.cmake) · [Arm 在 M4 系列上检查特性的示例](https://learn.arm.com/learning-paths/mobile-graphics-and-gaming/gemma4-kleidiai-sme2/setup_workspace/)
2. **固定同一份未量化模型、同一二进制，仅切换会话配置。** 给两组各建一个单行配置文件。在 `kai-off.conf` 中写 `SessionConfig.mlas.disable_kleidiai=1`，`kai-allow.conf` 写 `SessionConfig.mlas.disable_kleidiai=0`。把启动命令里的 provider 分别换成 `--provider=cpu:./kai-off.conf` 与 `--provider=cpu:./kai-allow.conf`。值 0 的含义是允许符合条件的算子调用，实际选择还依赖数据类型、形状、CPU 特性与库的构建选项。[sherpa 配置透传实现](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.3/sherpa-onnx/csrc/session.cc#L302-L329) · [ORT 1.28.2 会话键定义](https://cdn.jsdelivr.net/gh/microsoft/onnxruntime@v1.28.2/include/onnxruntime/core/session/onnxruntime_session_options_config_keys.h)
3. **保存一次能归到实际请求的命中证据。** 用相同句子在诊断轮保存 ORT 节点 profile，再用带符号构建的调用栈或定点计数，将真实的 `Conv`、`Gemm` 或 `MatMul` 热点与执行中的 `kai_…` 微内核对应起来。记录允许组命中的内核、上层算子及其形状，再确认禁用组在相同输入下走了哪条备用实现。ORT 日志中的 `CPUExecutionProvider` 只能定位到执行提供程序这一层。正式计时轮关闭 profiler、断点与诊断计数。[Arm 的算子至微内核调用栈实例](https://learn.arm.com/learning-paths/mobile-graphics-and-gaming/performance_onnxruntime_kleidiai_sme2/kleidiai_integration/)
4. **若两边都走默认内核，先查一个热点。** 核对是否加载错库、符号是否被裁剪、该算子的形状和精度是否受支持。预编译库无法给出证据时，用带符号的优化构建重编 ORT，启用 `onnxruntime_USE_KLEIDIAI=ON`。将 `SHERPA_ONNXRUNTIME_INCLUDE_DIR` 和 `SHERPA_ONNXRUNTIME_LIB_DIR` 指向这份构建的头文件和动态库，重新链接 sherpa，在同一新构建中重做两组。若仍无匹配路径，保留可用的音频工具，截取一个真实 TTS 热点的输入和形状，做默认实现与类型匹配的 KleidiAI 微内核对照，核对输出张量的最大绝对误差和相对 L2。只有接回实际模型并用整篇请求复验后，才能报告整模收益。报告注明“整模实际命中”“仅算子实测”或“本配置未观察到命中”，并保存依据。[ORT 构建选项示例（固定版本）](https://cdn.jsdelivr.net/gh/microsoft/onnxruntime@v1.30.0/cmake/CMakeLists.txt) · [sherpa 接入自编译 ORT 的位置](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.3/cmake/onnxruntime.cmake#L152-L181)

## 5. 怎样测，怎样决定日常用哪个配置

| 要回答的问题 | 实验口径 |
| --- | --- |
| 合成一篇要等多久？ | 冷启动从新进程启动前计到完整 WAV 写出。热测用 API 驱动持有同一个 `OfflineTts` 实例，从提交朗读文本计到最后一个 PCM 样本返回，核对驱动加载的 ORT 与对照组一致。音频秒数 = 样本数 ÷ 采样率，**热 RTF = 热合成秒数 ÷ 音频秒数**，越小越快。另记整篇总等待，包括分段、插入静音样本与落盘。拼接时人为加长的停顿单独记录，计算热 RTF 时使用模型实际生成的音频秒数。CLI 自带的 RTF 在模型初始化之后、写 WAV 之前计时。重复启动 CLI 测到的是每个新进程的首次生成。 |
| 两条路径怎样公平比较？ | 固定语料、朗读稿、音色、语速、模型哈希和线程数。先用 2 线程，每组预热 2 次，对同一组短句和同一长段各测 5 次，交替 A/B 的先后。记录每次生成秒数、实际音频秒数、RTF，以及每组中位数和范围。最后在选定配置上连续处理一整篇，记录插电状态、低电量模式和内存压力。首版热 RTF 的期望值为 **≤1**，以自己的离线复习等待预算决定是否值得继续调优。 |
| 占多少内存、读对了吗？ | 用 macOS `/usr/bin/time -l` 分进程采集最大常驻内存，保存原值并以注明单位的 MiB 汇报。从 API 返回的浮点采样检查 NaN、Inf、异常全静音和过载，再做 WAV 试听。固定可控随机种子。若有不可控的生成噪声，重复听同一短句、比时长和关键字，算子对照则使用同一份张量。独立记录磁盘文件大小、峰值 RSS 与朗读质量。 |
| INT8 是否更合算？ | 放在 KleidiAI 开关实验之后，再单独切换模型精度。重测短句、术语、时长、内存和 RTF，在写 PCM16 之前检查浮点波形。出现非有限值、漏读关键单位或听感明显变差时，日常生成保留未量化版。上游报告提供了短句回归的动机，当前版本能否复现留给本机验证。[报告中的版本、输入与对照](https://github.com/k2-fsa/sherpa-onnx/issues/4086) |

## 6. 里程碑与最后要留下的东西

| 顺序 | 预计主动投入 | 当次可以验收的产物 |
