### Executor

Executor的实现选择源码在`vllm/v1/executor/abstract.py`中`Executor.get_class`方法里。
具体实现类会根据parallel_config.distributed_executor_backend的值进行分支判断，判断流程如下：

1. 判断distributed_executor_backend是否已经是一个类，是否已经是Executor的子类。
   - 如果是类对象但不是Executor的子类，会抛出TypeError报错。直接构造必须是Executor的子类的子类。
   - 如果是Executor的子类，则会直接确认使用这个类，即`executor_class = distributed_executor_backend`。
2. 如果不是一个类，那么就进入字符串判断。
   - 如果是"uni",就会采用`vllm.v1.executor.uniproc_executor.UniProcExecutor`;
   - 如果是"mp",就会采用`vllm.v1.executor.multiproc_executor.MultiprocExecutor`;
   - 如果是"ray",则还会根据VLLM_USE_RAY_V2_EXECUTOR_BACKEND环境变量来判断是否使用V2版本的Ray Executor
     - 启用了环境变量，就采用`vllm.v1.executor.ray_executor_v2.RayExecutorV2`;
     - 未启用，则采用`vllm.v1.executor.ray_executor.RayDistributedExecutor`.
   - 如果是"external_launcher"，则会将实现设为`ExecutorWithExternalLauncher`。
   - 还会根据名称直接导入模块，即使用resolve_obj_by_qualname函数。如果导入的不是Executor子类，同样会TypeError报错。
3. 最后，以上路径都不匹配，则抛出ValueError，提示未知的后端。

### Worker

对于gpu platform的worker，选择逻辑比较简单。
实现源码在`vllm/platforms/cuda.py`中，当parallel_config.worker_cls为"auto"时，会被设为`vllm.v1.worker.gpu_worker.Worker`。
这里未发现其他选择条件与fallback逻辑。

### Runner

对于gpu platform的model runner，选择逻辑也很简单。
实现源码在`vllm/v1/worker/gpu_worker.py`中。
直接根据self.use_v2_model_runner这个变量进行判断选择v1版model runner或是v2版model runner，而这个变量来源于初始config中`vllm_config.use_v2_model_runner`。
于是，准确而言：

1. use_v2_model_runner配置参数设为True时，采用`vllm.v1.worker.gpu.model_runner.GPUModelRunner`，会被`as`视作为`GPUModelRunnerV2`。
2. use_v2_model_runner配置参数设为False时，采用`vllm.v1.worker.gpu_model_runner.GPUModelRunner`，会被`as`视作为`GPUModelRunnerV1`。
   值得一提的是，其中类的路径非常相似，仅在`gpu.model_runner`和`gpu_model_runner`中有差别，V2是点，V1是下划线。需要注意区分。

### Attention backend

对于gpu platform的attention backend的选择逻辑则要比先前几个类的实现选择要复杂得多。
实现源码在`vllm/platforms/cuda.py`中，初始选择入口在`CudaPlatformBase.get_attn_backend_cls`。
如果初始有设置selected_backend，那么会先根据该参数尝试构建attention backend，只要校验可用，就会采用这个backend。如果校验失败，则会直接抛出ValueError。
如果没有设置selected_backend，则会进入自动选择attention backend的逻辑：
先从get_valid_backends方法开始，按照优先级进行排序backend（_get_backend_priorities），然后对优先级backend数组进行有效检查（backend_cls.validate_configuration）。
然后再选取backend列表中优先级最高的backend。
所以，对于自动选择，逻辑重点在_get_backend_priorities方法中，分支选择判断依次会判断use_mla、device_capability.major、kv_cache_dtype、num_heads和use_non_causal这几个变量。具体判断比较复杂，想要看优先级列表到底是怎样的，要看源码进行判断。

## 预测与结果

而后，我们进行了 OutputProcessor 输出的实践练习。用模拟的 EngineCore 输出驱动真实处理器，观察它对外返回什么、是否要求取消，以及是否清理前端请求状态。
实践固定条件如下：

- output_kind=FINAL_ONLY，min_tokens=0，max_tokens=64。
- stop="is quiet"，include_stop_str_in_output=False。
- 内部请求 ID 为 p1-internal，对外 ID 为 p1-public。
- 每次输入的 Core finish_reason 都是 None，表示 Core 尚未判停。

### 首次预测修正

首次预测时，对于request_outputs、include_stop_str_in_output和对RequestState的删除时机，我没有清晰理解。
预测成了request_outputs数量为1 -> 2 -> 2，输出字符串包含了stop str，RequestState也没有及时删除。
实际上根据源码，request_outputs  的语义是可交付的请求结果列表。输出字符串是否包含stop str需要根据include_stop_str_in_output参数进行判断。RequestState也会在请求完成时立即删除，不会等到EngineCore彻底abort该请求。后续前端查不到该请求的RequestState可以直接跳过处理，不会因为没有RequestState而卡住。
于是，修正成0 -> 1 -> 0，输出字符串在固定条件下去除了stop str，RequestState也在第二次处理请求结果时就删除了。

### 两组运行有什么差异

而后，完成固定条件的测试后，再修改了include_stop_str_in_output=True进行第二组运行。
第二组运行的三次输出数量、取消列表和状态清理时机都不变，只有最终输出文本变成The river is quiet，增加了stop str。

### 为什么改变 case 就能切换条件

因为P1_INCLUDE_STOP=1环境变量就能够修改case请求的include_stop_str_in_output参数。测试会在入口读取环境变量 -> 创建 case -> run_case 读取字段 -> 传给 SamplingParams。
