# C++构建实践练习分析

## 实践环境固定版本：
- 操作系统: Linux 5.15.0-119-generic x86_64 GNU/Linux
- g++: g++ (Ubuntu 11.4.0-1ubuntu1~22.04.3) 11.4.0
- ld: GNU ld (GNU Binutils for Ubuntu) 2.38
- readelf: GNU readelf (GNU Binutils for Ubuntu) 2.38
- nm: GNU nm (GNU Binutils for Ubuntu) 2.38
- ldd: ldd (Ubuntu GLIBC 2.35-0ubuntu3.13) 2.35

## 实践代码说明
- api.hpp: 库函数compute声明，输入输出均为int类型。
- library.cpp: 库函数实现。其中定义P2_VARIANT=1时编译int类型输入输出的函数实现；定义P2_VARIANT=2时，编译double类型的函数实现。
- driver.cpp: 主程序app入口。先打印运行时进程的PID，而后从命令行读取指令，指令明确call后再输入compute函数整数int 7，返回值也为int。最后打印返回结果，并程序返回时判断结果是否为预期的14，符合预期正常返回0，否则返回状态码3.

第一次实践：
- 编译出lib-a/libw1probe.so 用 P2_VARIANT=1 构建。
- 编译出lib-b/libw1probe.so 用 P2_VARIANT=2 构建。
- 两份库的 SONAME 都是 libw1probe.so。
- app 构建时链接 lib-a，没有设置 RPATH／RUNPATH。
- 本次运行的 LD_LIBRARY_PATH 只指向 lib-b。

## 诊断证据链

### app 需要什么符号
app构建时只看到int类型输入输出的compute函数，需要的时int类型的compute函数实现的对应符号。

### 两份库分别提供什么
- lib-a仅提供int类型输入输出的函数实现；
- lib-b仅提供double类型的输入输出函数实现。

### 为什么 ldd 指向 A，而目标 PID 映射 B
执行ldd检查命令为 
```bash
LD_LIBRARY_PATH="$PWD/../plana-w1-env/p2-build/lib-a" \
  ldd ../plana-w1-env/p2-build/app | rg 'libw1probe'
```
此时通过环境变量指定了查询库的路径指向lib-a。
而运行时的LD_LIBRARY_PATH 只指向 lib-b，所以目标PID映射B，而ldd指向A。

### 实际错误如何印证预测
实际app运行报错：
"stderr": "/root/autodl-tmp/plana-w1-env/p2-build/app: symbol lookup error: /root/autodl-tmp/plana-w1-env/p2-build/app: undefined symbol: _Z7computei\n",
报错中的 _Z7computei 经 c++filt 还原正是 compute(int)。这与 app 的引用及 lib-b 缺少该定义完全吻合。

## 修复与变式

修复启动脚本：
```bash
if [ "$LD_LIBRARY_PATH" == "$P2_LIB_B" ]; then
    export LD_LIBRARY_PATH="$P2_LIB_A"
fi
$P2_APP
```
通过该脚本启动app，能够正常完成app运行。
变式将环境变量改成LD_LIBRARY_PATH 从 lib-b 改为 lib-a，if条件不成立，不执行export环境变量修改。但环境变量已经符合预期指向lib-a，所以也能正常运行。

### 脚本如何影响新进程

脚本通过判断LD_LIBRARY_PATH是否为不正确的lib-b路径。如果是lib-b路径，则修改程lib-a路径。
所以当路径为不正确的lib-b路径，就通过修改回lib-a路径而正常运行。

### 父环境为 B／A 时，分支和最终结果分别是什么
- 父环境为B时，脚本的if条件成立，修改LD_LIBRARY_PATH回lib-a，最终结果正常运行结束；
- 父环境为A时，if条件不成立，不执行export环境变量修改，但环境变量已经符合预期指向lib-a，所以也能正常运行。

## 证明边界
本次验证的是自建程序，以及父搜索路径恰为 A／B 的两个场景，不能泛化为任意目录列表或真实服务部署。
