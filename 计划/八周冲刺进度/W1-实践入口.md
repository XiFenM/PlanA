# W1 实践入口

本页用于在另一台机器接续 W1 的最后两项实践：P1 运行路径选择与最小输出契约验证、P2 C++／Linux 基线实践验证。它只负责说明如何开始，不另建进度账本或详细子计划。

当前完成情况以 [W1 进度](W1.md)为准，精确恢复位置以[学习断点](../学习断点.md)为准；本次开启的依据见 [2026-09-16 接续记录](历史记录/W1-学习验收记录.md#plana-jd-w1-20260916-practice-handoff)。

## 1. 在新机器上如何开始

先确保目标机器上的 PlanA 副本包含本页及配套进度更新，再在仓库中打开 Agent 会话，发送：

> 接续 PlanA 的 W1 最后两项实践。请读取仓库指令、`计划/学习断点.md`、`计划/八周冲刺进度/W1.md` 和本入口。先只读核对当前机器环境、固定源码及依赖，优先判断 P1 的最小验证路线；暂不安装、下载、创建或执行练习。核对后给出最小准备方案与正式实践约定，由我确认。复用已有概念验收，保留我应独立完成的核心实现和解释任务。

不要直接沿用历史机器配置，也不要为接续自动拉取最新源码或改动子模块指针。路径一律以新机器的实际仓库位置为准。

## 2. 两项分别要做什么

| 实践 | 最小工作方向 | 证明边界与详细依据 |
|---|---|---|
| P1：运行路径与输出契约 | 将配置对应到 Worker／Runner／Attention backend 和 fallback，标明源码依据与实际验证状态；设计并在兼容环境下运行一个最小输出契约用例 | 候选用例为 `FINAL_ONLY` 加跨两次模拟 EngineCore 输出的 stop string，使用真实 OutputProcessor；只证明前端输出、判停与取消列表行为，不证明完整服务时序或 GPU KV 回收。见 [P1 候选约定](历史记录/W1-学习验收记录.md#w1-p1-runtime-output-validation) |
| P2：C++／Linux 实操 | 从生命周期、编译链接／ELF、动态库排查中选择最低充分的一部分，用隔离的小程序或自建库取得操作证据 | 三个方向不是自动全部必做；不重复已通过的整套概念题，不扩展到 W2 并发练习。见 [P2 候选约定](历史记录/W1-学习验收记录.md#w1-p2-cpp-linux-validation) |

P1 沿用教学源码基线 `vLLM v0.26.0 @ 568afb3a13806beb53bb2e6bd518269357b237c0`。源码 checkout、实际安装包和执行环境分别记录；只下载到源码不代表已具备运行条件。Executor 的 `backend=uni` 与 Attention backend 分开记录，不预设新机器的设备或实际选择。

最小前端输出用例本身不要求加载模型权重或 GPU 推理，但导入 vLLM、运行相关 fixture 仍可能依赖完整的兼容软件环境和 tokenizer 资源。不能据此承诺“装一个 pytest 就能跑”。若环境受限，可讨论原约定允许的 B 级设计路径，明确未运行，其完成判定仍需确认。

## 3. 先做哪些只读环境核对

| 核对对象 | 需要确认的事实 |
|---|---|
| 基础环境 | OS、架构、Shell、CPU 指令集、内存与磁盘余量；P2 所需 Linux 环境是否可用。仅在所选路线涉及设备时再核对 GPU／驱动 |
| 仓库与源码 | PlanA 工作区及子模块是否有未提交改动；本地参考源码的位置、当前提交、固定教学提交是否可读；不覆盖用户改动或自动切换版本 |
| P1 运行依赖 | 实际选用的 Python／虚拟环境、已安装的 vLLM、PyTorch、pytest 等版本，以及与固定提交声明的依赖是否匹配；不能只凭目录存在判断可运行 |
| P1 测试资源 | 所选 tokenizer／配置的本地缓存及可用性；缺失时列出需要的下载、网络或访问许可，确认后处理，不下载模型权重作为默认准备步骤 |
| P2 工具链 | C++17 编译器与开发文件；若选择 ELF／动态库方向，核对链接器及 `readelf`、`nm`、`objdump` 等工具；按所选用例核对 sanitizer 或等价检查工具 |
| 操作与文件范围 | 可用的隔离工作目录、实现／测试／证据文件的具体路径，以及哪些由学习者编写、哪些由导师维护；不默认在知识仓库根目录创建工程 |

本轮只读核对先用版本、包元数据、源码及缓存信息列明“已具备／缺失／尚未验证”，不提前运行练习；实际导入、编译和运行是否成功，在约定后的最小试运行中确认。缺失依赖先提出准备方案，不自动安装或改变系统配置，也不在记录中保存凭据。

## 4. 核对后如何进入实践

1. 根据实际环境选择最低充分路线，列出必要准备、受影响文件与不能证明的内容；不用完整服务部署或性能测试替代小型验证。
2. 分别确认 P1、P2 的目的、交付、通过标准、文件归属、允许操作及证据要求，形成正式实践约定。只为已选范围准备环境和验收工具。
3. 导师维护约定内的测试／检查工具，学习者完成约定的核心实现、运行或观察任务，并解释预期、结果与局限；不把模拟结果或上游测试通过当成本机实测。
4. 按约定 Review 并补足必要证据。两项完成后再提请 W1 最终验收，不自动关闭 W1 或启动 W2。

## 5. 实践结果放在哪里

- **当前是否完成、凭什么完成、仍缺什么**：只更新 [W1 进度](W1.md)。
- **实际环境、接受的实践约定、验收结论及证据引用**：写入 [W1 学习验收记录](历史记录/W1-学习验收记录.md)，不改写旧环境和旧契约快照。
- **源码、测试与运行证据**：按新机器上确认的具体路径保存，验收记录链接其位置、版本及必要结果；不把大段运行输出复制到周进度或本入口。
- **暂停与跨会话恢复**：只维护[学习断点](../学习断点.md)中的一个下一动作。

知识文章、结构化学习日志、原始对话归档与复习卡均不随本入口自动生成；Git 暂存、提交、推送也需另行明确请求。
