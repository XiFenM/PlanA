## 2. 四个学习单元

<a id="w2-unit-1-moe-parallelism"></a>

### 单元一：MoE／EP 原理与并行策略

先建立完整的数据流与维度含义，再逐步追踪 Token、expert、rank 和 buffer 的对应关系。

1. 用一个小 tensor 手算 `router → top-k → token count/capacity → permutation → dispatch → grouped GEMM → combine`，恢复 Token 原序并检查 send count 总量守恒。
2. 将同一算例映射到单卡多专家、单机多卡和跨机，区分 EP、EPLB、专家冗余与 placement 的职责和时间尺度。
3. 计算两组 All-to-All 的 per-rank bytes，在给定有效带宽后推导理想通信时间下界，并解释负载倾斜的影响。
4. 完成五个组合题，覆盖 TP／PP／DP／SP／CP／EP 的 shape、collective 和 routing；至少一题涉及推理 DP 的 replica routing 或 backpressure，按总计划要求至少四题无提示正确。

保留贯穿算例与 shape／bytes 推导，供单元二映射真实实现使用；理论下界不写成实测延迟。

<a id="w2-unit-2-source-implementations"></a>

### 单元二：MoE／EP 真实源码实现与横向对照

五部分都纳入源码研究。vLLM／SGLang 关注框架执行组织与接入，后三部分关注通信库或实现分支；不预设两框架都已接入全部三个实现。

| 源码专题 | 研究主线与关键问题 |
|---|---|
| vLLM 的 MoE／EP 路径 | 从具体模型 MoE 层、路由与专家映射，追到 Fused MoE、dispatch／专家计算／combine；核对并行配置、通信后端与 GEMM 后端的独立选择及 fallback |
| SGLang 的 MoE／EP 路径 | 追模型 MoE 层、dispatcher 选择、专家计算与 combine；核对异步完成与计算重叠边界，和 vLLM 对照职责及数据布局 |
| DeepEP 实现 | 从 Python 接口、绑定层进入通信 kernel；追布局与计数、handle、节点内／节点间传输、stream／event 和 buffer 生命周期；按选定版本区分吞吐／低延迟路径或统一接口 |
| MORI-EP 实现 | 以 [ROCm/mori](https://github.com/ROCm/mori) 的 EP 实现为主体，追配置／算子入口、HIP kernel、节点内与跨节点路径、SHMEM、同步和布局；区分库本体与框架适配层 |
| Hybrid-EP 实现 | 明确为 [DeepEP 的 hybrid-ep 分支](https://github.com/deepseek-ai/DeepEP/tree/hybrid-ep)；对照 DeepEP 基线研究分层传输、TMA、warp 流水、dispatch／combine、通信计算重叠与 buffer 管理，并完成下方训练／推理适配对照 |

每个专题选择一条代表性主链，追到决定行为的关键 kernel／同步逻辑；其他模式围绕差异对读。共用单元一的算例，依次回答：输入和布局是什么、元数据在哪里产生、谁发起 dispatch、专家计算消费什么、combine 如何恢复结果、何时能安全复用资源、测试实际覆盖什么。

<a id="w2-hybrid-ep-training-inference"></a>

#### Hybrid-EP：训练与推理场景的差异及适配

以用户指定的 [NVIDIA 文章](https://developer.nvidia.com/blog/optimizing-communication-for-mixture-of-experts-training-with-hybrid-expert-parallel)作为设计讲解入口（2026-02-02 发布，代码分支指向于 2026-09-24 核对）。文章以 Megatron-Core 训练为主要场景；先理解该场景，再对照推理 prefill 与 decode，不把推理视为单一工作负载。

以下是待研究的问题，不是已经成立的性能或兼容性结论：

| 对照维度 | 需要弄清的差异与适配问题 |
|---|---|
| 计算与通信契约 | 训练前向／反向分别需要哪些 dispatch／combine、梯度与元数据？推理保留哪些操作？哪些状态或接口不能直接照搬？ |
| 工作负载与目标 | 训练、prefill、decode 的 Token 数、batch、序列长度与动态变化怎样影响路径选择？训练吞吐／step time 与 TTFT／ITL／尾延迟分别要求观察什么？ |
| 布局、容量与生命周期 | 专家负载倾斜、padding、注册 buffer、预分配与复用有哪些条件？推理请求变化时，容量、元数据及释放时机需要怎样调整？ |
| 同步与计算重叠 | dispatch／GEMM／combine 之间的依赖由谁维护？host 同步、stream／event、CUDA Graph、分块与流水是否适合目标场景，代价是什么？ |
| 数值与硬件条件 | dtype、量化 scale、combine 累加及反向精度要求如何核对？NVLink／RDMA 拓扑与 SM 资源竞争怎样限制方案迁移？ |
| 框架接入与验证 | 回到 vLLM／SGLang，哪些配置、接口、布局或生命周期需要调整？用什么正确性测试与测量边界验证；无环境时哪些结论必须保持待验证？ |

学习产物是源码对照中的一张“场景差异 → 实现位置 → 可复用机制 → 适配调整 → 验证方法／未验证项”表。它属于既有源码证据包，不要求额外实现完整训练栈、部署五套后端或开展训练与推理的全量 benchmark。文章中的训练性能数字不直接作为推理收益结论。

#### 源码阅读边界

- 正式学习时记录每部分的仓库／分支／commit、框架依赖和实际选中接口；区分 DeepEP V1／legacy、V2 与 Hybrid-EP。移动分支和当前 gitlink 不代替已固定的教学版本。
- 文章解释设计，固定源码裁决实现；上游测试说明已有覆盖，本地运行只证明声明环境中的行为。
- 五部分依次研究，形成同一 source/test map、横向对照与 Change Card 证据包；不默认通读全部模式，不扩展完整 SGLang scheduler、全部传输后端或完整 MoE kernel 工程。
- 无多卡／RDMA／AMD 环境时使用 B 级源码与精确测试设计，不把阅读测试写成实际运行。具体环境操作与正式实践范围另行确认。
