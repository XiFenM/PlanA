## 2. 四个单元课

<a id="w3-unit-1-pd-lifecycle"></a>

### 单元一：PD 原理与 KV 生命周期

要解决的问题：为什么把 prefill 与 decode 分开；谁安排 KV 交接，谁执行；什么时候允许消费或回收。

1. 解释 PD 对 TTFT、ITL、尾延迟和吞吐的取舍，沿首 Token 关键路径区分计算、交接与两侧排队。
2. 追固定版本 `KVConnector` 的 Scheduler／Worker 边界、metadata、load/save、ready 与 cleanup；把调度记账、数据传输和计算依赖分开。
3. 以 P/D 相同模型、TP 与 KV 布局为首版基线，沿真实 PULL 实现讲清创建、传输、ready、消费、通知和释放，再对照 PUSH 的发起方、控制流程与 ownership。
4. 区分传输句柄、P 源块、D 目的块的生命周期，以及操作提交、传输结束、本地可见、计算消费与引用归还的条件。

**完成依据**：能用文字和图解释正常 PULL/PUSH 状态机及服务取舍；source map 能回到真实字段、函数和相关测试。异常状态机在单元四补全，单元一不据正常路径推定失败恢复正确。

**源码边界**：以 vLLM 的 connector 链为主；NIXL Pull 是第一条实现锚点，沿用账本已固定的 commit。PUSH 对照在对应节点核验真实接口与实现，不用自创 toy 协议替代。已有 W1/W2 基础直接复用。

<a id="w3-unit-2-kv-layout-bytes"></a>

### 单元二：KV 布局、分页读取与定量模型

要解决的问题：KV 中实际存放什么、每个 rank 保存和传输多少字节，以及 D 的 attention 如何找到并使用这些数据。

1. 从 MHA/MQA/GQA 的缓存张量形状推导每 Token、每请求、每 rank 的 KV bytes，明确 dtype、层数、KV heads、head dim，以及 TP 下的切分或复制。
2. 对比 P/D 相同 TP 与布局、异 TP 重分片，以及 DCP/PCP 对块映射、metadata 和字节量的影响。
3. 从 KV bytes 与假定有效带宽推导理想传输时间下界，解释 metadata、padding、重排与 retry 等实际开销；理论下界与实测延迟分别表达。
4. 追固定版本 attention backend 的分页 KV 读取路径：block table、slot mapping、序列长度等 metadata 在哪里构建，怎样传到 kernel 接口。阅读止于 metadata 与接口参数，不展开 kernel 内部算法。
5. 根据公开 config 整理 Qwen、Llama、DeepSeek、ERNIE、GLM 的模型结构差异，覆盖注意力类型、KV heads、head dim、MoE、位置编码和 MTP；逐项注明来源与版本，并标明哪些实际适配过、哪些只完成资料或源码核验。

<a id="w3-unit-2-mla"></a>

#### MLA 专门节点

MLA 作为独立讲解节点，不仅在模型差异表中列名：

- **机制与设计理由**：解释为什么压缩 KV，以及与 MHA/MQA/GQA 的区别。
- **实际缓存内容**：弄清需要保留的张量及其表示，说明为什么不能直接套普通 KV 的字节量公式；hybrid cache 同样按实际状态分别建账。
- **真实系统与推导**：结合 DeepSeek 的公开配置和固定源码，推导每 Token、每 rank 的缓存与传输量，区分逻辑表示、实际存储布局和交接表示。
- **PD 与分页读取**：说明实际交接什么，D 端怎样通过 metadata 与 attention backend 使用它，以及布局或表示变化带来的限制。

**完成依据**：独立完成有单位、假设和边界的 KV 字节量／时间下界算例；能解释普通注意力与 MLA/hybrid 的公式适用范围；分页读取路径对应真实字段与接口；模型差异表可追溯到公开 config。

**深度边界**：达到解释机制、正确估算和判断系统取舍的程度，不要求实现完整 MLA kernel，也不扩展为独立的训练数学推导课程。

<a id="w3-unit-3-rdma-fallback"></a>

### 单元三：RDMA 数据路径与回退方案

要解决的问题：跨机数据访问由哪些层协作完成；设备缺少某项能力时，哪些路径仍然可用、代价在哪里。

1. 区分 RDMA 与 IB/RoCE 的层次，建立 MR、QP、CQ、WR、doorbell 的职责关系与一次传输的数据路径。
2. 解释 CPU proxy、GPU initiated、GPUDirect 与内存注册、操作提交、进度推进和完成通知的关系；按具体接口与平台核对保证，不靠名称相似推定语义等价。
3. 对照无 RDMA、仅 host staging、仅 collective 三种条件设计 fallback，说明额外拷贝、同步、进度或资源限制。
4. 把这些能力映射回单元一的 connector 契约，区分框架需要维持的不变量与传输后端提供的能力。

**完成依据**：能画出端到端数据路径，正确解释关键对象与层级，针对三类受限环境选择回退方案并说清代价。仅有公开源码时，结论限定为接口与设计依据，不宣称完成目标设备验证。

<a id="w3-unit-4-failure-system-design"></a>

### 单元四：故障处理、验证与系统设计整合

要解决的问题：超时、重复、进程退出时，怎样避免错误消费、提前复用和资源泄漏，并验证设计。

1. 在单元一正常状态机上补全 timeout、duplicate、process failure 等分支，明确 ownership、ack、取消／清理、重试与释放责任。
2. 形成 failure matrix，将故障注入位置、预期状态变化、正确性断言与恢复策略对应起来；回到固定源码与已有测试检查覆盖。
3. 准备可执行 test design，写清 fixture、输入、步骤、断言、失败路径及环境边界；具体执行依据可用硬件和正式练习约定确定。
4. 按既定方式问答共建 PD/KV Change Card：导师逐段提问，学习者判断、选择和补充，导师据此成稿；只使用可公开的设备能力，不要求独立撰写整张卡或完成真实硬件适配。
5. 由导师沿贯穿请求串起生命周期、数据布局、定量代价、RDMA/fallback 与异常恢复，再完成书面系统设计和 W3 综合验收。已有充分证据直接复用。

**完成依据**：异常状态机与 failure matrix 相互对应；验证设计足够具体；Change Card 与书面系统设计能说明依据、取舍及未验证项；最终按[整周技术验收门](../高级AI框架开发工程师-八周证据冲刺计划.md#83-验收门)核对。

**证据边界**：没有目标硬件时，采用 B 级固定源码与精确测试设计，所有性能结果保持待验证。正式口头系统设计仍由 W4 的既定 Mock 承接，不新增 W3 口试或 RDMA 跑分门槛。

## 4. 教学、验收与记录方式

- 以理解、书面推导、源码定位和迁移判断为主；先讲清每课全貌，再推进局部节点，名词与 API 随所需前置逐步引入。
- 课程网页逐段呈现教学，不承担进度或掌握结论。具体页面路径随各课开课确认；单元一沿用已经授权的页面。
- 各课复用同一请求、图、推导和已有证据，不要求重复制作四套完整材料；只有综合检查仍缺实践或实证证据时，才约定最小正式练习。
- [W3 进度](W3.md)维护完成项、依据与缺项；详细练习约定和需长期跟踪的阶段事件沿用仓库验收记录约定。技术产物归实际模块，面试材料归 `面试准备/自我准备/`。
- 每课结课须用户确认。计划保存、单元划分和候选资料不构成后续课程启动、硬件实验、日志／文章／卡片生成、提交或推送授权。
