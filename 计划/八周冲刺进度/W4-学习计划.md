## 2. 六个单元课

<a id="w4-unit-1-roofline"></a>

### 单元一：定量性能模型与 Roofline

要解决的问题：给定一个真实工作负载，在运行之前怎样估计性能上界和时间下界，运行之后又怎样判断实现效率与模型偏差。

1. **任务与测量口径**：选定一个 MatMul 或 Conv3D 案例，明确输入输出、shape、dtype、布局、计算目标与计时范围，区分算子本体、布局转换和端到端路径。
2. **FLOPs 与分项 Bytes**：沿同一案例计算工作量和各项读写，声明存储层级、数据复用与中间结果假设；复用 W2 已有定量基础，把新增工作放在本案例的具体边界。
3. **Roofline 上下界与适用条件**：由 Arithmetic Intensity、算力与带宽建立 attainable performance upper bound 和 execution-time lower bound，解释 cache reuse 或布局变化怎样改变判断。
4. **实测效率与偏差归因**：把同口径测量与模型对应，区分理论峰值、可达到的上界和实际效率；解释额外访存、同步、启动或测量范围为何使结果偏离预测。
5. **完整案例整合**：沿 `FLOPs → Bytes → AI → 性能上界／时间下界 → measured efficiency` 串起结论、反证和适用边界；汇总前面同一案例的依据，不再增加第二个算子或第二套实验。

**完成依据**：算例的单位、读写及 cache reuse 假设可复算；能解释理论界限与测量之间的差距，每个成功结论至少记录一个被否定假设或负结果，尚未解释的偏差另行保留。真实测量、公开结果审计和理论推导按[证据与硬件边界](#w4-evidence-hardware-reuse)分别表达。

**复用与深度边界**：承接 [W2 单元四的 Roofline 证据](W2.md#w2-u4-final-mastery-20261101)，不重新安排已经通过的基础算术验收。第 4、5 节共享同一案例与合格数据；完整 profiler 方法在单元二展开。

<a id="w4-unit-2-benchmark-trace-scheduling"></a>

### 单元二：benchmark、profiler 与调度性能

要解决的问题：怎样得到可比较的性能数字，从 trace 找到约束，并把调度参数变化与请求体验、吞吐的取舍连起来。

1. **指标口径**：区分 TTFT、E2E、TPOT、raw ITL、请求吞吐、Token 吞吐与满足服务目标的 goodput，说明样本对象、聚合方式和统计量；样本不足时不把探索性尾延迟数字当成稳定结论。
2. **benchmark 协议**：优先在可用 AMD 单卡上固定一个受支持的小模型／revision、软件版本、shape、dtype、并发、输入／输出长度、请求到达方式和正确性判据，建立 BF16 服务基线，组织 warm-up、重复运行、raw data 与命令配置，形成一个端到端 benchmark packet。
3. **profiler trace 阅读**：读一条 trace，辨认 Host、Kernel、copy、collective、allocator 和 idle，沿请求关键路径判断各段时间与依赖；profile 用于归因，服务性能另用干净计时，不能把采集开销混入收益。
4. **性能归因**：继续使用同一条 trace 与同一组指标，提出可能原因、检查反证，区分忙碌时间、等待时间与关键路径，不以单个热点直接代替端到端解释。
5. **Continuous Batching**：解释请求如何逐步加入和退出批次，判断执行过程中批次与负载怎样变化；完成一次无提示独立变式，并说明对 TTFT／ITL 的影响。
6. **Chunked Prefill**：解释 prefill 如何按 token 预算切分、怎样与 decode 共享调度机会；完成一次无提示独立变式，并说明 TTFT／ITL 的取舍。
7. **调度参数受控对照**：在本单元 benchmark packet 中选择一组调度参数对比，例如改变 `max_num_batched_tokens`，保持其他主要条件一致，同时报告 TTFT、ITL 与吞吐的绝对值、相对变化和波动。

**完成依据**：benchmark 口径可追溯，trace 分类与归因相互支持；两种调度的独立变式无提示通过；参数对照能说明取舍，不只给出提升百分比。测量方法沿用[活动计划 §15](../高级AI框架开发工程师-八周证据冲刺计划.md#15-性能与验证规范)。

**复用与源码边界**：第 3、4 节共享一条 trace，第 7 节就是第 2 节协议中的受控对照，不另立实验包。调度补验沿一条固定版本 vLLM 调度链，不要求实现调度器、完成多参数扫描，或重考 W1 已通过的请求主链。

**AMD 选材**：采用[增强方案 §5.2](../八周冲刺计划增强方案-AMD岗位.md#amd-single)的小模型服务主题，与单元三共用环境、harness 及口径匹配的 BF16 基线。租用前准备输入和脚本，核对 GPU 型号、显存、ROCm／框架版本、量化支持与 profiler 能力；先用少量代表性负载，只有观测提出新问题时才扩大配置。单卡实验不补写 AMD 多卡／RCCL 或跨节点结果。

单卡主例没有 collective 时，如实说明该类事件不适用，并通过已有固定材料辨认其职责；不为补齐 trace 分类而增加多卡设备或新实验门槛。

<a id="w4-unit-3-precision-quantization"></a>

### 单元三：数值精度与量化对照

要解决的问题：降低表示精度为什么会改变显存、执行路径与误差，以及怎样判断一次量化是否在既定任务上值得采用。

1. **浮点表示与误差来源**：比较 BF16、FP16、FP8 的表示范围、精度与舍入，围绕本例解释溢出、下溢及误差，不扩成完整浮点编码课程。
2. **存储、计算与累加精度**：区分 storage dtype、compute dtype、accumulation dtype 和 opmath dtype，说明数据以某种精度保存不代表每一步运算都使用同样精度。
3. **量化参数与误差**：沿一个小例子解释 scale、zero point、舍入、clipping 与量化误差，比较按张量、通道或分组量化，判断异常值和取值范围如何影响表示与恢复。
4. **AWQ 与 W4A16 执行路径**：区分量化方法与权重／激活精度约定，解释权重表示、反量化及计算路径；联系本次选定方案在实际 AMD GPU、ROCm 与框架版本上的支持，不由量化名称推定后端可运行。
5. **正确性评测口径**：为后续同一组对照选择固定评测集或输出一致性判据，固定输入和配置，说明误差测量方法及其能支持的结论。
6. **与 BF16 基线对照**：优先接续单元二的 AMD 单卡与同一个公开小模型，选择该环境实际支持的一种量化方案，与 BF16 基线比较精度、显存、TTFT、ITL 和吞吐，记录绝对值、硬件、版本、方法与适用边界。调度对照与量化对照分别改变变量，不能同时改动后将收益归给其中一项。

**完成依据**：能解释各类 dtype 与量化误差的来源，区分算法、数值表示和实际执行；对照同时给出精度与性能依据。没有可用硬件时，按[活动计划 §9.3](../高级AI框架开发工程师-八周证据冲刺计划.md#93-验收门)交完整实验设计，不写实测结论。

**实验边界**：第 5 节为第 6 节确定判据，共用一个小模型、一种量化方案和一份对照包。AWQ／W4A16 的基础理解不意味着必须同时跑 AWQ 与 FP8，也不要求独立实现量化 kernel；不额外增加大规模评测或训练任务。AMD 环境或所选方案不兼容时，先核对可运行的受支持方案，再按原计划受限环境分支收缩；未取得的 AMD 实测证据继续保留，不因准备了脚本就记为完成。

<a id="w4-unit-4-multimodal-position"></a>

### 单元四：多模态链路与 RoPE／M-RoPE

要解决的问题：图像或视频怎样进入语言模型，Conv3D 所在的输入处理与计算路径是什么，以及多维位置如何参与注意力计算。

1. **多模态推理总链**：沿一个具体模型梳理 processor、vision encoder、embedding 合并和语言模型的输入输出，先建立全流程骨架。
2. **processor、patch 与 grid**：解释图像／视频预处理、patch 切分和 grid 信息怎样产生张量及位置元数据，明确时间、高、宽等维度。
3. **vision encoder 与 Conv3D shape**：回到视觉编码路径和相关算子输入输出，核对 Conv3D 案例的 shape、布局与算子边界，解释它在多模态链路中的位置。
4. **embedding 合并到语言模型**：追视觉特征怎样与文本侧输入对应、合并并交给语言模型，检查 Token 数量、位置和 shape 的衔接。
5. **RoPE 的位置机制**：解释位置旋转作用于哪些张量、怎样影响注意力中的相对位置信息，为多维位置分解建立必要前置。
6. **M-RoPE 与固定源码对应**：解释时间、高、宽位置的分解及实现位置，沿同一固定模型与源码版本核对位置索引如何流入执行路径，并接回 Conv3D 输入。

**完成依据**：总链、关键 shape 与位置计算能对应固定源码；能说明 Conv3D 案例与视觉路径的关系，以及普通 RoPE 与 M-RoPE 的适用范围。

**源码与实践边界**：全单元只展开一条主模型源码链；公共实现与历史项目之间只声明已有证据支持的对应关系。复用 W3 的模型结构与注意力基础，不重新展开完整模型对照表，不要求新增多模态模型跑分、Conv3D kernel 实现或独立数学课程。

### 单元五：三张 Case Card 的证据审计

要解决的问题：三个项目案例中的数字、根因、修复、验证和个人职责分别由什么支持，哪些结论可以对外说明，哪些仍需保留限制。

1. **证据与披露口径**：区分生产经历、本人补充、原始测量、公开复现、现场录音和导师整理，结合[能力与经历总表](../../面试准备/自我准备/能力与经历总表.md)及[项目索引](../../面试准备/自我准备/projects/README.md)确定各项结论的来源、版本及可披露范围；旧简历或旧诊断不覆盖后来已经确认的事实。
2. **Conv3D 案例审计**：在[已有 Conv3D Case Card](../../面试准备/自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)上核对 workload、baseline、shape、优化机制、性能数字、正确性及模型回归边界，复用单元一与单元四相关依据。
3. **layout 案例审计**：在[已有 layout Case Card](../../面试准备/自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)上核对布局方案、测量起止点、绝对时延、数字冲突、根因判断与个人职责。
4. **V1 异常与 F2 实际回听**：按[Qwen3-32B／vLLM V1 异步 H2D 案例](../../面试准备/自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)的最新确认口径核对根因、定位措施、最终修复和回归范围；依[Host Padding F2 核对卡](../../面试准备/面试问题经验/奕行二面-Host-Padding-回听核对卡.md#yixing-host-padding-listening-check)回听相关片段，分别保留现场原话与后来补充的来源和测试条件。
5. **三卡交叉审计**：检查三张卡是否都区分“我负责／我参与／他人负责”，成功结论是否有反证或负结果，数字、单位、配置与对外表述是否相互一致，并保留无法核实的字段。按[增强方案 §7.2](../八周冲刺计划增强方案-AMD岗位.md#migration)补核已有 GLM 服务指标、通信等待归因、D2H 验证和上游协作线索；这些用于事实补录与问答取材，不增设第四、第五张案例验收。

**完成依据**：三张卡能支持数字、反证、ownership 和限制的追问；V1 异常的现场表达与最新项目事实按来源分别核验。F2 核对清单本身不等于已经回听，也不把未经确认的现场数字并入项目回归统计。

**复用与材料边界**：沿用 W1/W2 已验收的卡片草稿和书面机制证据，只处理本次证据缺口，不要求重写三个项目。F2 属于 V1 异常案例，回听以相关片段为限，不扩成整场录音转写。反证可来自已有可信记录，不自动增加三组新实验；原始资料缺失时保留缺口，不用表述润色代替核验。

**新增取材的判读边界**：[GLM 档案](../../面试准备/自我准备/projects/GLM5-3-flash-project.md)中的最终服务指标与算子／任务评测分开，Host 插桩结果不能换算为服务加速倍数；allreduce 调用中的等待不直接等于网络传输耗时或通信算法优化。[D2H 项目](../../面试准备/自我准备/projects/async-d2h-project.md)与原 H2D 异常是独立工作问题，其生命周期回归、不同并发的正负结果及持续负载缺口分别记录。既有上游线索先核 PR／issue、本人角色、测试与状态，不沿用“没有公开 upstream”的旧诊断作为新结论；原始公司代码和日志留在原环境，只使用获准公开的抽象与脱敏结论。

<a id="w4-unit-6-mock-readiness"></a>

### 单元六：综合 Mock 与投递门槛复核

要解决的问题：怎样在真实口述和追问中，把源码理解、性能模型与项目证据连成能够承担进一步质疑的工程判断。

1. **配置、单位与开场全景**：先主动固定工作负载、配置、计时范围和单位，再说明问题全貌；开场是同一 Mock 的组织环节，不单独设一场验收。
2. **vLLM 主链口述**：承接 W1 的约 15 分钟主链讲解与口头追问，覆盖请求路径、关键组件、执行边界和条件变化。
3. **一个项目／性能案例深挖**：从三张案例中选择一个，围绕 workload、baseline、root cause、ownership、result、regression 和 limitation 追问，并加入一个条件变化或反例；优先使用能承接多模态表达要求的 Conv3D 案例。已核实的 GLM／D2H 素材可用于岗位相关追问与英语表达，不由此再增加一场项目考试。
4. **PD/KV 系统设计题**：承接 W3 的口头系统设计，固定具体配置，解释计算、内存、通信代价，说明布局、生命周期、故障与 fallback 的取舍和证据边界。
5. **反馈与投递门槛复核**：根据真实口述和追问结果定位事实、机制或表达缺口，重答最薄弱的一问；复用[既定能力门与当前岗位映射](#w4-mock-readiness-gate)，按 96121 → 94063 → 96120 的准备优先级说明证据与剩余差距，不把全部 JD 关键词变成本课新验收项。

**完成依据**：在一场既定综合 Mock 中完成主链、一个项目深挖和 PD/KV 系统题，主动说明配置、单位、假设与限制；只记录真实口述与追问结果，文字验收或准备稿不能替代口头证据。

**范围边界**：复用 W1–W3 已通过的文字、源码和设计证据，不将其重新列为未完成，也不要求为口试补跑 W3 的设备测试。三段口头任务合并计入[正式 Mock 总表](../高级AI框架开发工程师-八周证据冲刺计划.md#mock-schedule)的第一场推理 Mock；针对具体缺口补差，不机械重考全部内容。英语按当次安排穿插，语言表现与技术理解分开评价，不默认整场使用英语。

## 4. 证据、硬件与复用边界

- **既有证据**：复用 [W1](W1.md)、[W2](W2.md#w2-u4-final-mastery-20261101)和 [W3](W3.md#w3-week-final-mastery-20261107)已通过的理解、书面推导、源码与设计证据；只补 W4 明确要求的完整性能案例、测量与审计、调度变式及正式口述。
- **每单元范围**：按活动计划，每个能力单元至多展开一条主源码链、一个主要证据包增量和一个定量主题。卡片、图、协议、数据和汇总可以是同一包的不同部分，不按节点数量增加项目。
- **跨单元复用**：单元一的模型可供单元二归因和单元五审计使用；单元二与单元三可以共用环境、harness 和合格的 BF16 基线。复用前核对 workload、版本、计时层次与统计口径，不把 kernel 时间当作端到端延迟，也不把调度与量化同时改变的结果当作单变量对照。
- **增强方案的硬件选择**：单元二、三优先采用[已确认可租用的 AMD 单卡条件](../八周冲刺计划增强方案-AMD岗位.md#resources)，具体型号、版本、可用时间、支持范围和费用仍在实施前核对；可租用不等于已经租用或已实测。AMD 多卡不可用不作为完成前提，公司多机多卡只支持实际运行的后端、拓扑与负载结论；不把跨机可用自动解释为 TP、EP、PD 或 RDMA 已支持，也不把公司跨节点候选直接叠加为 W4 必做实验。
- **运行分工**：本轮采用的 GPU 运行方式及可用性事实见[单元一运行衔接记录](W4.md#w4-u1-progress-20261110)。Agent 提供并维护脚本、相称的测量方法与结果检查说明；学习者运行前给出预测，在自己的 GPU 机执行并解释结果。运行脚本不等于独立实现 harness；尚未确认的核心代码实践另按练习约定划分。当前 Agent 执行机的环境检查不能替代用户机器信息，保存计划也不触发租用或远程实验。
- **性能证据**：按[活动计划 §15](../高级AI框架开发工程师-八周证据冲刺计划.md#15-性能与验证规范)保存方法与原始依据，区分真实实测、模拟、理论推导和待验证。样本规模与统计量相匹配，raw ITL 与每请求 TPOT 分别报告，保留绝对值、相对变化、跨轮波动与负结果。
- **受限硬件**：沿用[活动计划 §16](../高级AI框架开发工程师-八周证据冲刺计划.md#16-硬件分支与返回快照)。可用 CUDA／CPU 路径按其实际支持范围验证；只有公开源码或实验环境受限时，性能部分采用理论下界、公开结果审计与可执行协议。量化对照没有可用硬件时按 §9.3 交完整实验设计。不能填写未验证的目标芯片收益，也不能把模拟、公开结果或历史项目材料记成本轮实测。
- **W3 移交边界**：W3 的真实后端停止访问、设备可见性、目标平台兼容性、适配与性能余项保持原有证明边界，不整体转成 W4 新增完成门槛；PD/KV 口头系统题复用已有设计。
- **项目与录音事实**：三张 Case Card 审计依据各自原始材料和最新确认口径。来源不一致时保留时间、条件与责任差异；F2 回听不能用后来的修复事实倒填现场原话。只记录可披露的抽象能力与结论。
- **资料与记录归属**：固定源码版本和具体材料范围在各课账本中登记；课程网页承载教学正文，技术产物归相应模块，项目材料归既有项目档案。本计划不重复保存完成结论、恢复位置或实际学习时长。

## 5. 第一场推理 Mock、能力门与当前 AMD 目标

按[活动计划 §5.3](../高级AI框架开发工程师-八周证据冲刺计划.md#53-每周统一验收门)使用既定综合 Mock 和预算，将 W1 的主链口述、一个项目／性能案例深挖、W3 的 PD/KV 系统设计组织为同一场的题段。W4 计第一场推理 Mock，W7 的训练场与 W8 的第二场推理 Mock 按[唯一总表](../高级AI框架开发工程师-八周证据冲刺计划.md#mock-schedule)接续；日常练习和局部复测不另计固定场次。事实证据缺口回到相应案例核验；口头表达缺口按真实追问结果补差，两者分别记录。

原 `87545` 编号保留为历史准备参照；复用[活动计划 §13.1 的五项能力标准](../高级AI框架开发工程师-八周证据冲刺计划.md#131-87545-近期投递门槛)，并按[增强方案 §2](../八周冲刺计划增强方案-AMD岗位.md#targets)解释当前目标：

- 简历、项目与自我介绍没有已知数字冲突或 ownership 扩大。
- 已在 W4 或后续 Mock 中脱稿讲清 vLLM 主链和一个多模态案例。
- 至少一个性能案例可以完整复算。
- C++ 基线没有明显红灯，复用已有合格证据。
- 能以具体配置解释多 GPU／多节点的计算、内存与通信瓶颈，缺少真实多节点数据时明确边界。

岗位取材优先级为 **96121 → 94063 → 96120**：96121 侧重完整性能案例、AMD 单卡操作与可追溯代码／贡献；94063 结合真实公司跨节点材料，PD／Large-EP／RL 未实施部分如实保留；96120 作为生产级 Runtime 的拉伸方向，不将有限实验等同长期架构与维护经历。满足上述能力门可以边投边学，但不表示已满足任一 JD 的全部经历要求；投递前核对岗位状态，实际对外投递仍按用户指令执行。
