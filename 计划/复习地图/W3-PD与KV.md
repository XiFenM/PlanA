## 【W3-U1】PD 分离与 KV 生命周期（《请求 R 的跨机搬家记》）

> **自测口令**：线上把混部拆成 P/D 分离，请求 R 在 P 算完 prefill 后要搬到 D 做 decode。从性能权衡、三段就绪、PULL/PUSH 交接，到两端安全删块，整条链怎么走？

<details>
<summary>展开对照（1 屏骨架）</summary>

### 一句话主矛盾

混部时 prefill 和 decode 互抢算力带宽；拆成 P/D 隔离干扰后，怎么把 KV 跨机搬过去，同时不拖垮首字延迟、不读脏数、也不提前把块删坏？

### 主线 5 步（沿请求 R 走到底）

1. **拆机算总账**：D 少了长输入干扰，生成间隔（ITL）变稳；但首字延迟（TTFT）多出了“KV 交接 + 两侧排队”，且总卡数固定时一池先忙满另一池帮不上忙，所以 ITL 改善不自动等于首字更快或吞吐更高。
2. **三段就绪与消息闭环**：D 端“查到 P 有 KV”和“本地分好 blocks”都不算就绪——Scheduler 把任务塞进 `kv_connector_metadata` 下发，Worker 异步拉数据并经 `KVConnectorOutput` 回报完成；数据真正落进 D 显存、布局对得上、GPU 可见之前，R 先挂起，D 照常算别的请求。
3. **PULL vs PUSH**：数据始终从 P 流向 D。PULL 是 D 发 READ 主动拉；PUSH 是 D 先发 `PUSH_REG` 报备目标块，P 配对源块后发 WRITE 主动推（CPU 提交即可，底层由 RDMA / Copy Engine 搬运，不必两边都起 GPU send/recv kernel）。
4. **两端独立收尾**：P 和 D 手里是两份独立副本。PUSH 下给 D 的完成通知直接附在 WRITE 上，P 看自己的 WRITE 句柄收尾、D 看通知收尾，**彼此不等对方软件层回传 ACK**——所以 P 归还源块引用比 D 报告接收完成更早，完全正常。
5. **安全删块过两道门**：搬完只清传输 handle，KV 块回收另看各自最后使用者。引用计数归零不等于立刻安全回池：① Scheduler 先收到 Worker 的完成上报（`finished_sending`）；② 本地 GPU 已提交的在途 step 必须结束，否则把块回池给新请求，旧在途计算会写脏新请求的 KV。

### 4 条核心辨析

- **`PUSH_REG` 登记 vs RDMA MR 注册**：`PUSH_REG` 是请求级的“这次搬到哪几个 block ID”；MR 是底层的内存区域描述（地址范围、长度、权限、访问 key）。
- **四层地址编号别混用**：请求逻辑块位置 → 块池 block ID → backend 页号 → 传输地址范围；`block ID` 不是裸硬件物理地址。
- **异步 `start_load_kv` 排在 `forward` 后面为何合法**：`forward` 算的是已就绪的请求 B，异步 load 拉的是下一轮才算的请求 A，不是同一条请求，没有数据依赖。
- **传输成功 ≠ 结果正确**：就算 WRITE 和通知都成功，仍要用独立分配记录核对源/目的块归属同一条逻辑请求（防把请求 A、B 写串台）。

### 我当时踩过的 2 个坑

- **坑 1（把两段因果绑一块）**：在 PUSH 里以为“P 没向 Scheduler 上报 `finished_sending`，就会卡住给 D 的完成通知”。其实通知附在 WRITE 上，D 照常往下走，卡住的只有 P 自己的源块回收。
- **坑 2（拿另一道门顶掉直接原因）**：Worker 上报延迟时，别解释成“本地 GPU 还有在途访问”。两道门独立——上报慢卡的是调度器不知情，在途访问卡的是 GPU step 没跑完。

## 【W3-U2】KV 布局、分页读取与定量模型（《KV 算账与变形记》）

> **自测口令**：一条长请求在不同并行（异构 TP / DCP / PCP）和不同架构（普通 GQA / MLA / 混合模型 GDN）下，显存和流量怎么算账？跨卡怎么映射与合并？为什么会静默读串请求？

<details>
<summary>展开对照（1 屏骨架）</summary>

### 一句话主矛盾

KV 在不同并行切法和模型架构下形状、归属完全不同——怎么算准“装了多少、占了多大、搬多少”，并保证每张卡读到的是对的请求、对的头和对的前缀状态？

### 主线 5 步（沿一条长请求的 KV 变形走到底）

1. **三笔账与共享带宽下界**：算清“有效 KV（已生成的 token） / 已占块容量（含尾块空槽、预留位、padding） / 本次 payload（选中要搬的片段）”。多 rank 并发走同一条总带宽 `W` 的瓶颈链路时，理想下界是总字节 `ΣS / W`，**不能再除以 rank 数**。
2. **异构 TP 映射**：P 和 D 用不同 TP（如 TP4 → TP8）时不能按 rank 号一一硬发——从 D 每卡查询头“需要哪些逻辑 KV 头”倒推去哪张 P 卡拉分片或副本，再按 D 自己的头顺序拼好。
3. **上下文并行（DCP / PCP）**：DCP 把长历史切到多卡后，合并局部输出必须按 softmax 分母占比 `exp(L_i - logsumexp L_j)` 加权并跳过全 mask 片，绝不能按 token 数加权；PCP 同层只需各卡先算本地投影、gather 交换缓存状态，即可并行算各自查询行的 attention，不必等前段算完本层输出。
4. **分页读取排障**：`slot_mapping` 管本步新 K/V 写进哪，`block_table` 配 `seq_lens` 管历史从哪读。两个等长请求从 `[A,B]` 重排成 `[B,A]` 时维度完全没变，漏改 `block_table` 行序就会静默读串对方的历史 KV。
5. **MLA 与混合架构（GDN）**：DeepSeek-V3 的 MLA 长期只存共享压缩 latent `c` 和位置 key，decode 时把上投影挪到 query 侧和输出侧免去逐位置展开（但历史位置没消失，读与打分仍随长度涨）；混合模型把全注意力层（随长度涨）与递推层（固定矩阵+卷积尾 × 运行时份数）分层建账，推测拒绝或前缀恢复都只能切回早快照重放。

### 3 条核心辨析

- **dense MLA 的 TP vs DCP**：不开 DCP 时每张 TP 卡都存完整 latent 历史（TP 分的是查询计算）；DCP 才真正按历史位置切分每卡缓存，两者不能混成同一个容量除数。
- **递推状态回退 vs 普通 KV 截短**：普通 KV 截短长度即可回退，但递推矩阵已把后续 token 揉进数值里，必须连同近期卷积尾部成对切回对应前缀快照（绝不倒用更晚终态改长度凑数）。
- **逻辑预留 vs 已占显存 vs 网络 payload**：只逻辑预留但未分物理块不算已占显存；若按整块发，尾块空槽也会跟着计入网络 payload。

### 踩坑提醒

- **全注意力 KV 到位 ≠ 混合模型整体到位**：恢复混合模型到前缀 `t` 时，即使全注意力 KV 已有到 `t`，缺中间激活仍要从更早检查点 `s` 重放 `s+1..t`，让全注意力与递推层对准同一前缀。

## 【W3-U3】RDMA 数据路径与回退（《RDMA 走线与降级记》）

> **自测口令**：怎么判断线上到底有没有走显存直传 RDMA？从 verbs 提交到共享 CQ 回收怎么保护源内存？硬件不支持显存直传或彻底没 RDMA 时，数据路径怎么降级才不丢同步？

<details>
<summary>展开对照（1 屏骨架）</summary>

### 一句话主矛盾

从理想显存直传 RDMA 到双端 Host 中转、再到 TCP 或固定组 collective，底层传输可以一层层退化，但每块内存的生命周期和“数据真正可读”的同步契约一条都不能漏。

### 主线 5 步（沿 RDMA 走线与两级降级走到底）

1. **三层排假象**：CPU 飙高可能在轮询、抓包看到 UDP/IP 可能是 RoCEv2、张量在 GPU 不等于网卡直读显存——分别核对 CPU 职责、实际 transport 和 MR（注册内存区）落在显存还是 Host、有无偷偷 D2H。
2. **Verbs 对象与提交生命周期**：`PD`（保护域）管访问权限边界（把 MR 与 QP 圈在一起），`CQ` 独立建立、被 QP 指向专门收完成记录。提交非 inline WRITE 后，`WR/SGE` 发货单已抄进队列（WQE）可立刻复用，但源 payload 必须等对应完成记录（WC）才敢改写。
3. **共享 CQ 与控制通知**：多 QP 共用 CQ 只是共用一个信箱，按 `wr_id` 各认各的；没捞到 A 的 WC 只是“未观察”而非“未完成”，跨 QP 无顺序保证，绝不能凭 B 的 WC 释放 A 的源内存。rping 示例中 `WRITE` 进 `rdma_buf`、`SEND` 通知进预先 `ibv_post_recv` 的 `recv_buf`、`CQ` 只给回执。
4. **双端 Host 中转四区依赖**：网卡碰不到显存时走 `P 显存 → D2H → P Host → RDMA → D Host → H2D → D 显存`，四块内存各认最后读者（D2H / RDMA / H2D / 计算）；RDMA 完只放行 P Host 与触发 H2D，D 的消费 stream 必须用 event 等 H2D 结束。
5. **无 RDMA 时的两级兜底**：退回 TCP/socket 时仍走四段路径，发送端返回不等于 D 可算（D 要收齐、核对归属、H2D、等消费依赖）；若通信库只有固定组 Broadcast（无 P2P），必须由 CPU 协调全组所有 rank 按一致参数陪跑。

### 3 条核心辨析

- **NVSHMEM 3.0 控制面分工（写 WQE / 敲 doorbell）**：`IBRC = CPU/CPU`，`典型 IBGDA = GPU/GPU`，`CPU-assisted IBGDA = GPU/CPU`；控制面经 CPU 不等于 payload 绕 Host。
- **GPU 发起 API vs GPU 直驱网卡**：GPU 只生产数据不叫 GPU initiated；改由 GPU 发起不能只把代码搬进 kernel，还受平台 GPU→CPU 请求通道或直访网卡队列/映射/排序能力制约。
- **集体接口限制 vs 底层传输**：只暴露固定组 collective 是接口限制，不自动代表底层没走 RDMA。

### 我当时踩过的坑

- **MR 多注册了本地拷贝目标**：P 显存经 RDMA 写到 D Host、再本地 H2D 到 D 显存时，D 显存只参加本地 H2D，**不需要注册进这次 RDMA 的 MR**——记住：**网卡真碰哪两头，就只注册哪两头**。

## 【W3-U4】故障处理、验证与系统设计（《PD 故障排险记》）

> **自测口令**：线上同时出现重试、重复通知、对端原地重启、租约心跳迟到或目标换址，PD 传输怎么防止提前删块脏写？写单测和新芯片适配时最容易漏哪两件事？

<details>
<summary>展开对照（1 屏骨架）</summary>

### 一句话主矛盾

异常路径下“业务超时/失败/重算”与“底层网卡还在读写这块显存”是两条异步时间线——任何一步把前者当成后者，都会把正在被写或被读的块提前回池，酿成静默脏写。

### 主线 5 步（沿线上故障排险走到底）

1. **三元组去重防误删**：请求重试叠加通知重发时，按 `（请求、尝试、读者）` 三元组归属并判重——重寄回执不等于重读了一次 KV，重发只算一次，新尝试的通知绝不替老尝试销账。
2. **同址重启隔离新旧实例**：对端在原 IP/端口原地重启后，地址没变但 engine ID 换了——新请求按新实例建描述和 MR，老在途操作不会自动迁过去，按老 handle 和老资源独立收尾。
3. **租约心跳 vs 访存真凭据**：心跳和租约只代表“请继续留着源区”的保留政策（任务已被受理排队、还没开读时也要续租），无论心跳准点还是迟到都不能说明网卡停手了；回收必须拿到访存完成/停止/隔离的真凭据并解除其他引用。
4. **换址重连与失败业务解耦**：直传 READ 把目标换成未注册的 `T_new` 时，先给 `T_new` 建注册再改本地描述（源 `S` 不动），老 `T` 只等老写入结束就回收；加载失败后调度器选 `fail` 还是 `recompute` 只是业务去向，绝不自动等于老传输已停。
5. **故障单测盯两头**：别只断言“最后请求进了失败集合”——必须补两道断言：① 故障中途 handle/块关联保留、目标块没有被提前回池复用；② 结束后只归还和上报一次（真机另验网卡取消与可见性）。

### 2 条核心辨析

- **能力表声明 vs 新芯片真实打通**：在 platform adapter 写上“支持设备内存”只是名片；底层驱动/transport 必须真能识别、注册和搬运这块显存，上层 connector/worker 要接通源可读、进度跟踪与消费流等待。
- **业务选 `recompute` 时的额外风险**：决定重算后，若不先等老传输停手或隔离旧目标块，老写入可能把刚重算出的新 KV 覆盖掉。

### 踩坑提醒

- 共享 MR/pool 还有别的块在用时，回收单个老块 `T` 千万别顺手把整个 MR 注销；受控软件单测只能锁死状态机时序，不能代替真机 RNIC 验证。
