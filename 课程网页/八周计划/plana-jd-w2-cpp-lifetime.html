从“调用结束”走到“数据用完”

上一单元追踪了 EP 通信中的 buffer、handle 和完成信号。这一课把同一个问题放进 C++：主线程准备一批数据，交给后台线程处理，自己继续做其他事。异步让两边有机会重叠执行，却也把两个时刻分开了——提交任务的函数已经返回，后台对缓冲区的访问可能还没有结束。我们要弄清，谁让数据一直存在，谁约束读写顺序，又由什么证明它可以再次使用。

走完这条链，你应该能在一段陌生代码里标出：谁管理缓冲区，哪些指针或引用只是借用，最后一次访问在哪里，析构或下一轮覆写为什么可以发生。你还要能分开回答“对象还活着吗”和“这次读写有正确的同步关系吗”，并用程序里的具体动作说明 happens-before——C++ 用于判断执行先后与跨线程可见性的关系。

1管理对象、元素存储与借用指针

先看一个在 CPU 上运行的函数。它创建一批输入，向队列提交读取这批输入的任务，然后返回。任务会在函数返回以后读取输入并求和。这批输入有 N = 4 个 int32_t 元素，取值依次为 3、5、7、9，由一个 vector 管理。为了判断任务执行时数据是否仍然有效，我们先看准备输入时创建了哪些对象，以及这些对象分别在什么时候结束生命周期。

本课把这个自行定义的函数命名为 submit_borrowed，表示“提交一个借用输入的任务”。它的完整定义放在节点 2；这一节先读函数内部准备数据的三行代码。本例没有扩容或擦除元素的操作，因而可以先集中观察函数返回时的析构行为。它在整堂课中的位置，可回看开课导入的图 0：持有与借用 → 交接与发布 → 异步访问 → 完成与退出 → 复用与释放。

std::vector<std::int32_t> buf{3, 5, 7, 9};
const auto* p = buf.data();
const auto n = buf.size();

第一行创建局部对象 buf。std::vector<T> 是管理连续元素的标准容器；这里的 T 是 int32_t，所以容器管理的是四个连续存放的整数元素。随后，buf.data() 返回第一个元素的地址，buf.size() 返回元素个数。第二行把地址保存在指针变量 p 中，第三行把数量保存在 n 中。

因此，这几行代码中既有负责管理元素的容器对象，也有实际保存数值的元素区，还有保存元素地址的指针变量。表中的“谁负责生命周期”指的是哪条对象管理规则决定它何时结束，并不是说取得地址的一方自动承担了释放责任。

对象它保存什么谁负责它的生命周期
局部 buf 对象管理元素区所需的信息本次函数作用域；正常返回前析构
元素区 B3、5、7、9 这四个实际元素buf；本例中随容器析构销毁元素并释放存储
借用指针 p元素区的起始地址p 自己是局部变量；复制它只复制地址

当函数正常返回时，局部 buf 会析构。对本例的 vector 来说，析构会结束所管理元素的生命周期，并释放它们占用的存储。局部指针 p 也会随作用域结束而消失，不过 p 的消失本身并不执行 vector 的清理工作；清理来自 buf 的析构。假如程序另外保存了一份 p 的值，那份值只是同一个地址，并不会改变 buf 原有的析构时机。

让容器负责分配与清理、让读取函数通过指针借用元素，可以避免每次调用读取函数都复制整批数据。读取函数只要获得有效的起始地址和数量，就能遍历已有元素。相应地，程序必须安排好所有者与读取方的使用时间：如果读取工作会持续到当前所有者的作用域之外，就要让另一个仍存活的所有者接管资源，或者把当前所有者的存活时间延长到读取结束。指针本身没有执行这些安排的能力。

注：“替读取方延迟清理”具体指什么

这里的“清理”指 buf 销毁元素并释放存储；“延迟”指程序把这一步安排在任务最后一次读取之后。仅保存 data() 返回的地址，不会让 vector 的析构函数等待任务。程序可以通过保留所有者或转交管理权，让存储在使用期间继续存在；当释放时机依赖异步任务是否完成时，还要由相应的完成协议告诉负责释放的一方，任务已经结束访问。

W1 的 unique_ptr 与这里有相同的分工：智能指针管理受管对象，get() 返回的裸指针提供借用入口。程序可以把管理权转交给另一个所有者；在转交以后，决定资源何时释放的是新的所有者。分析这类代码时，沿着管理权的去向追踪，才能找到真正的释放位置。

注：栈帧、动态存储与释放责任

元素位于哪里，与哪个对象负责释放它们，是不同的信息。这个例子的元素存储由 vector 动态分配；函数返回时，局部 vector 的析构会主动释放这份存储。上文的判断依据是这个明确的析构动作。知道元素位于动态存储，还不足以确定它可以使用到何时；具体的释放时机要继续看所有者的生命周期。

还有两个条件会影响借用指针的使用。首先，这里的 p 类型是 const int32_t*，它限制的是通过 p 修改元素；这个类型不会替读取方延长元素的生命周期。其次，即使 vector 对象还没有析构，扩容也可能分配新的元素区，令此前的地址失效。正因为本例固定大小、没有扩容或擦除，我们才可以把失效原因准确地定位到函数返回时的析构，而不用同时分析存储位置变化。

本节使用的 data() 语义见 N4861 的 vector.data；容器清理与作用域析构的依据列在下面。

规范依据：N4861 [vector.overview]、容器要求表中的析构规则与 [stmt.dcl]/2。“持有／借用”是对这些规则的解释。

本节要点这段代码里的 buf 管理元素存储，p 保存访问地址，n 保存元素数量。任务能否继续读取，要看实际元素是否仍然有效；保存一个指针值，不会改变容器的析构或释放责任。下一节把任务保存进队列，再沿函数返回前后的时间线检查这些对象。

2提交函数与延迟任务的生命周期

上一节的函数已经准备好了四个输入元素。现在给它补上提交任务的动作：把稍后要执行的读取操作交给一个延迟队列 q。本例约定，q.post(task) 只保存任务，q.run_next() 才调用所保存的任务；调用者会先等 submit_borrowed 返回，再调用 run_next()。队列本身一直存活，因此接下来要检查的是：函数返回以后，队列保存的任务还通过什么对象访问输入。

读取函数 consume(p, n) 从 p 指向的位置开始，读取 n 个元素并求和；调用结束后，它不再保存或使用这个指针。这一节先用同一个线程先后执行“提交”和“读取”，以便单独观察延迟调用与局部对象生命周期的关系。真实后台队列可能在提交函数返回前就启动任务，那是另一种执行时序；本例采用的较晚启动时序也可能出现在真实程序中。

下面的 [p, n] { … } 是一个 lambda 表达式。它创建一个可调用对象，通常称为闭包对象：花括号中的代码在对象被调用时执行，方括号中的捕获指定这个对象保存哪些外部变量。这里的 p、n 都没有使用引用捕获符号 &，所以闭包保存它们各自的值。先看完整函数，再分析这些值是什么。

void submit_borrowed(DeferredQueue& q) {
    std::vector<std::int32_t> buf{3, 5, 7, 9};
    const auto* p = buf.data();
    const auto n = buf.size();
    q.post([p, n] { consume(p, n); });
}

调用 post 时，闭包中的 p 成员取得局部 p 的地址值，n 成员取得局部 n 的数量值。p 是指针，复制它会得到另一个指向同一位置的指针；这个复制动作没有读取并复制四个整数，也没有创建一个新的 vector 来管理它们。队列保存了闭包以后，即使原来的局部 p 和 n 随函数返回而消失，闭包自己的成员仍然存在。

随后函数返回，局部 buf 按作用域规则析构，原来的四个元素及其存储不再有效。队列中保存的闭包与这份元素存储有不同的生命周期：闭包还在队列中，但它的 p 成员已经指向释放后的存储。直到 run_next() 调用闭包、consume 通过这个指针读取元素，程序才触及这里要观察的错误访问。下图逐步保留了管理对象、元素存储和任务对象的状态，可以用来对照这段过程。

造成这个结果的原因，是程序交给队列的任务只携带了读取入口，没有携带这份数据的管理责任。尽管 n 告诉 consume 要读取多少个元素，地址和数量仍然不说明谁负责维持或释放存储。队列按照本例接口保存并调用任务，也就不会因为任务还没有运行而自动延长局部 buf 的生命周期。

可以从两种管理安排考虑修正。第一种是让原所有者继续管理输入，并把释放安排在任务最后一次读取之后；这样可以沿用同一份数据，但负责释放的一方要获得可靠的任务完成依据。第二种是让任务自己持有 vector。若任务获得的是元素副本，它就有独立的存储，原所有者仍可管理原来的数据，代价是复制和额外存储。若任务通过移动构造接管现有存储，就把这一批数据的管理责任转交给任务，原代码也要据此调整后续使用方式。

下面是第二种安排中的移动构造形式。它替换的是前面保存 p、n 的提交语句，任务内部会从自己持有的 vector 取得地址和数量。

q.post([owned = std::move(buf)] {
    consume(owned.data(), owned.size());
});

owned = … 是初始化捕获：它在闭包中建立名为 owned 的成员。std::move(buf) 本身是允许后续操作采用移动语义的类型转换；实际转交资源的动作，由这里的 vector 移动构造完成。原 buf 对象仍然存在，并会按原作用域析构，但这份输入的管理责任已经交给闭包中的 owned。原代码若还要通过 buf 使用输入，就不能再把它当作仍保有原来四个元素的容器。

任务调用 consume 时，地址来自它自己的 owned.data()。队列在调用期间保留这个任务对象，owned 就在读取期间保持存活。这里仍然沿用一个重要条件：consume 返回以后不再访问输入。如果它把地址继续交给别的延迟任务，程序就还要为那个后续使用者安排存储生命周期，不能只以当前这次函数返回作为使用结束的依据。

这一节讨论的是存储在延迟调用期间是否继续存在。若其他线程也持有访问入口并同时修改这些元素，即使任务自身拥有 vector，程序仍要对冲突访问建立正确的同步关系。回到 EP 或 H2D 的场景，负责持有存储的对象与报告最后一次访问完成的事件也要分别找到：前者说明资源由谁管理，后者才给负责释放或复用的一方提供行动时机。

本节要点在原来的 [p, n] 写法中，队列保存了地址和长度，局部 vector 仍按原时机释放元素；在本例规定的时序中，延迟读取发生在释放之后。程序可以保留原所有者直到任务用完，也可以让任务持有副本或接管数据。判断修正是否成立时，最终仍要把实际读取的完整时间段与对应所有者的存活时间对上。

检查 1迁移

调用者用 outer_owner（一个 unique_ptr）管理含两个元素的 vector。submit 只借用这个 owner，将 data() 得到的指针和 size() 得到的长度按值存入任务，不转移所有权。submit 返回后，队列在同一线程执行任务；任务读完后不再使用指针。下面三种情况独立，除所述动作外不改变元素、大小或容量。

  1. outer_owner 保持不变，直接执行任务。
  2. 先调用 outer_owner.reset()，再执行任务。
  3. 先执行 auto keeper = std::move(outer_owner)，再执行任务；keeper 在任务完成后才离开作用域。

分别判断任务能否合法读取原来的两个元素，并指出由谁保证它们仍然存在。局部指针变量已经消失，为什么不能单凭这一点下结论？

参考要点
  • a 可以合法读取：outer_owner 持续管理原 vector；题设没有发生使元素或指针失效的操作。
  • b 不能合法读取：reset() 销毁原 vector，其元素被销毁、存储被释放。任务只留有旧地址；后续解引用属于未定义行为，不保证一定崩溃。
  • c 可以合法读取：移动的是 unique_ptr 的管理权；原 vector 及元素没有因此搬到另一处。任务执行期间由 keeper 保证它们存在。

局部指针变量和任务内部按值保存的指针是两个变量。局部变量消失后，任务仍保存自己的地址副本；但它们都不管理所指元素。应判断实际所有者和元素是否仍有效，而不是只看某个指针变量是否还在作用域中。

3从单线程延迟调用到跨线程读写

前一节让同一个线程先提交、后读取，集中观察数据何时被释放。这一节保留同样的四个输入元素 3、5、7、9，把求和工作交给一个实际工作线程。主线程创建 buf 和保存结果的 sum，工作线程读取 buf 并更新 sum，主线程在工作结束后输出结果。buf 的大小和容量始终不变，两个对象都由主线程所在的作用域管理。

这时有两次跨线程交接：主线程准备的输入交给工作线程读取，工作线程算出的结果再交回主线程读取。除了让 buf 和 sum 在整个过程里保持存活，还要说明输入初始化、工作线程访问以及主线程读结果之间的先后关系。下面先认识负责创建线程和等待线程的接口，再把这两次交接接起来。

std::thread worker(task) 创建一个执行 task 的新线程。创建操作成功完成后，调用者可以继续执行自己的后续语句，而工作线程执行的是传入任务的函数体。下面的任务使用 [&buf, &sum]：这个引用捕获让它访问主线程中的原 buf 和原 sum，不在闭包中另建这两个对象的副本。因此工作线程写入 sum，主线程以后读取的就是同一个结果对象。

worker.join() 等待 worker 所代表的线程结束。工作线程仍在运行时，join 会阻塞调用方，也就是调用尚不返回，调用方暂时无法执行它后面的语句。只有等到工作线程结束、join 成功返回，主线程才会继续下面的输出操作。

std::vector<std::int32_t> buf{3, 5, 7, 9};
std::int64_t sum = 0;
std::thread worker([&buf, &sum] {
    for (const auto x : buf) sum += x;
});
worker.join();
std::cout << sum << '\n';

先看输入怎样交过去。主线程在构造 worker 之前，已经完成 buf 的初始化和 sum = 0。线程构造的完成与新线程开始调用任务之间有标准库规定的同步关系，所以这些此前完成的初始化，位于工作线程读取 buf、更新 sum 之前。这里的依据来自线程启动规则，而不是主线程和工作线程碰巧被操作系统怎样调度。

再看结果怎样交回来。工作线程执行完循环后结束；线程结束与对应 join() 的成功返回同步。主线程的输出语句又在 join 返回之后，因此工作线程写入 sum，先于主线程读取 sum。主线程之后才离开 buf 和 sum 的作用域，也就把这两个对象的析构放在了工作线程最后一次访问之后。

这样连接起来的先后关系称为 happens-before，下文简称 HB。在这个例子里，链的两端是各线程内部的执行顺序，中间由线程启动或 join 的同步规则连接。关系可以传递：初始化先于任务中的访问，任务中的访问又先于 join 返回后的主线程操作。用这样的链来分析程序，才能说明一次写入与另一个线程的读取具有怎样的顺序和可见性保证。

示例在创建线程以后立即调用 join，是为了把这条关系展示得清楚。实际程序可以让主线程在 join 前做别的工作，但要进一步检查那些工作是否访问了工作线程正在使用的数据。例如，在创建 worker 之后、调用 join 之前加入 buf[0] = 11;，就增加了主线程对第一个元素的写入。这个写入与工作线程对该元素的读取之间，并没有因为最后存在一个 join 就自动建立顺序。

原因在于，join 在这里把工作线程的访问排在主线程等待返回后的操作之前。新加入的写入却发生在主线程开始等待之前。主线程的这次写入和工作线程的读取，都会位于 join 返回以前，但“两个动作都先于同一个后续动作”并不意味着它们彼此已经排序。程序仍然缺少一条把写入与读取直接或间接连接起来的同步关系。

对本课这种直接读写的普通整数元素，不同线程访问同一内存位置，至少一次访问是写入，而这些冲突访问之间没有 HB 顺序，就构成 数据竞争data race，其行为未定义。这个判断不要求证明两条指令恰好在同一纳秒执行：即使日志看起来先打印写入、后打印读取，只要程序没有建立相应的同步关系，日志的时钟顺序就不能替代码补上保证。让一个线程睡眠一会儿，同样只是影响某次调度，并没有为这里的冲突访问建立所需关系。

4互斥锁、临界区与读写顺序

沿用上一节的四元素缓冲区 buf，现在让两个线程分别处理它：生产者把每个元素增加 10，消费者读取所有元素并求和。主线程在线程启动前准备好缓冲区和结果变量 total，把 total 初始化为 0；等两个线程都结束后，它才读取结果、销毁这些对象。这样安排了对象的存活时间，接下来还要安排生产者的写入与消费者的读取。

如果生产者正在更新某个普通整数元素，消费者就从同一位置读取，而两次访问之间没有 HB 顺序，就会出现上一节所说的数据竞争。即使主线程最后等待两个线程结束，也没有把这两次较早发生的访问排好顺序。本节加入一个共享的互斥锁对象 m，让这两个线程通过它安排对 buf 的访问。

取得锁与临界区std::mutex m 创建一个互斥锁对象。一个线程调用 m.lock() 并成功返回后，就持有这个锁。在它调用 m.unlock() 之前，另一个线程调用同一对象的 lock，会等待取得锁的机会。由取得锁到释放锁围住的那段代码，称为临界区。

这里的“同一把锁”指同一个 C++ 对象。主线程创建 m，两个线程访问的也都是这个 m。如果两个线程分别创建各自的 mutex，即使变量都叫 m，生产者也可以取得自己的锁，消费者同时取得另一个锁；它们的 buf 访问就没有通过同一个同步对象建立关系。

用对象生命周期管理解锁std::lock_guard<std::mutex> hold(m); 创建一个管理持锁责任的对象。构造 hold 时，它调用 m 的加锁操作；离开 hold 所在作用域时，hold 的析构函数负责解锁。这样，代码按作用域正常退出或提前返回时，解锁动作都有对应的对象生命周期负责。这里使用的是前面已经认识的 RAII：hold 管理持锁责任，buf 的存储仍由原来的 vector 管理。

下面是两个线程各自执行的函数体。页面先列生产者、后列消费者，只是为了便于阅读；线程调度没有因此获得“生产者一定先执行”的约束。两个函数体中的 hold 是两个不同的管理对象，但它们关联的是同一个 m。

{
    std::lock_guard<std::mutex> hold(m);
    for (auto& x : buf) x += 10;
}
{
    std::lock_guard<std::mutex> hold(m);
    for (const auto x : buf) total += x;
}

生产者的 auto& x 是当前元素的引用，x += 10 修改原来的 buf 元素。消费者的循环则每次从 buf 读取一个元素，再把读取的值加到 total。两段循环都位于各自 hold 的作用域内，所以持锁范围覆盖了整批数据的实际写入或实际读取。total 在两个线程运行期间只由消费者修改，主线程等消费者结束后才读它。

锁保护的是参与协议的访问mutex 本身没有登记“这块内存属于我”。它只控制哪些线程能够取得同一个锁。安全性来自程序安排：生产者访问 buf 时先取得 m，消费者访问 buf 时也先取得 m，而且都把需要排序的实际元素访问放在相应持锁范围内。

例如，消费者如果只在锁内调用 buf.data()，然后解锁再沿指针读取，持锁期间完成的只是取得地址。释放 m 之后，生产者又可以持锁修改元素，而消费者的元素读取仍可能在进行。没有其他交接规则时，这种写法没有保证所有执行顺序下的冲突访问都有 HB 关系。指针仍指向原存储，并不表示消费者在后续读取时仍然持锁。

从两段代码得到同步关系先分析生产者先取得 m 的情况。它在临界区里更新整批元素，然后在 hold 析构时解锁；消费者随后成功取得同一个 m，才开始求和。生产者的元素写入在它的解锁之前，消费者的元素读取在它的加锁之后，而同一 mutex 的前次解锁与后续成功加锁建立跨线程同步。三部分接起来，就得到写入到读取的 HB 链。

互斥与同步在这里分别起了作用。互斥使两个受同一锁保护的循环不会同时占有临界区；解锁与后续加锁的同步关系，则让我们能够说明前一个临界区的写入为何对后一个临界区可见。因此，证明过程既包含“哪一段访问先完成”，也包含“后续读取依据什么看到那次写入”。

把另一种取得锁的顺序也算进去消费者也可能先取得 m。它会在锁内读取初始化好的那批元素，完成求和并释放锁，生产者之后才更新 buf。在本例没有其他访问的前提下，这两段循环仍然被同一把锁排序，因而没有这组冲突访问造成的数据竞争；但消费者求和的并不是生产者本次更新后的数据。线程被命名为“生产者”，没有使它获得优先取得锁的权利。

如果业务要求消费者必须读取本次生产完成的数据，就要在互斥以外表达“本批已经准备好”这一条件。消费者取得 m，只能得知自己现在有权进入临界区，不能由此推断生产者已经完成这批更新。下一节会保留这把锁，再加入表示就绪与等待的对象。

使用范围本节把整段读写循环放进临界区，是为了让冲突访问的范围容易核对，并不要求两个线程的所有计算都持锁。与共享 buf 无关的准备或计算可以在临界区之外完成；如果把 buf 的实际读取也移出去，就必须另外建立阻止冲突写入的协议。仅在消费者读取前睡眠一段时间，或观察两条日志的先后，无法代替缺少的同步关系。

本节使用 N4861 中 mutex 的同步规则和 lock_guard 的构造、析构规则，核对两段临界区之间的顺序。

规范依据：C++20 工作草案 N4861 同一 mutex 的解锁／后续加锁同步与 lock_guard 的构造与析构。本节调用范围限于普通互斥锁，不涉及递归锁或 try_lock。

本节要点用 mutex 排序 buf 的冲突访问时，两个线程要访问同一个锁对象，并把需要保护的实际元素访问纳入协议。生产者先解锁、消费者后加锁，可以建立写入到读取的 HB 链；消费者也可能先取得锁，所以仅有互斥还没有表达“必须等待本批生产完成”的业务要求。

参考要点

a 不能保证安全。主线程在两个 join 返回后才销毁 buf 和 m，保证了题设中的访问期间资源仍存在；消费者持锁取得指针时，生产者不能同时持有同一个 m。但消费者解锁后的元素读取没有被这段临界区保护。

需要区分执行顺序：若生产者先完成持锁更新，消费者之后取得锁，再在解锁后读取，这一顺序有相应 HB 链；若消费者先取得指针并解锁，后续读取与生产者更新可能缺少 HB 顺序。因此是“整体安排不保证安全”，不能说所有取得锁的顺序都会出错。

b 把完整求和放进消费者的临界区，可以使这组冲突读写通过同一锁排序，但仍不保证读到新批次。消费者可能先持锁读取初始值；还需要“本批生产已完成”这一业务条件。条件成立前消费者可以先拿锁检查，再释放锁等待，不要求固定两个线程抢锁的先后。

5用条件变量等待数据就绪

现在给上一节的两个线程增加一个明确的业务要求：消费者求和的必须是生产者刚填好的这一批数据。消费者可能较早运行，也可能较早取得 m；让它依赖两次线程启动之间的时间间隔，仍然没有表达这一要求。我们先只交付一批数据，生产者交付后不再覆写 buf，把问题限定为“消费者怎样等到这一次发布”。

主线程在线程启动前创建四元素 buf、互斥锁 m、布尔变量 ready 和条件变量 cv。buf 的存储已经存在；ready 的初值为 false，表示本批输入还没有发布，而不是表示尚未分配内存。ready 的检查与修改全部由同一个 m 保护。结果变量 sum 从 0 开始，只由消费者写，主线程等两个线程结束后再读结果、销毁共享对象。

为什么锁之外还要有状态消费者先拿到 m 时，可以安全地检查 ready。如果它看到 false，此时生产者尚未发布输入，消费者就应等待这一条件改变。但消费者若一边一直持有 m，一边等待生产者把 ready 改成 true，生产者就无法取得同一把锁进入更新。因此，等待期间要把 m 释放出来，消费者继续检查条件之前又要重新取得 m。

std::condition_variable 用来配合这种等待：线程可以通过它进入等待状态，另一个线程可以发出通知，使等待者有机会重新检查。业务条件仍保存在程序自己的 ready 变量里。cv 不含一个供本例使用的 ready 字段，也不会因为收到通知就替程序把 ready 改成 true。

让等待操作能够暂时解锁前一节的 lock_guard 从构造到析构持续管理持锁责任；这里的等待操作却需要中途解锁，然后再加锁。消费者因此使用 std::unique_lock<std::mutex> lk(m)。把 m 传入这一构造形式，会调用 m 的 lock；若锁暂时被其他线程持有，构造过程也要等待。构造成功后，lk 关联 m，并记录自己处于持锁状态。

unique_lock 提供加锁和解锁操作，也相应更新自己的持锁记录。条件变量的 wait 接收这个管理对象，在等待期间通过它释放 m，恢复检查之前再通过它取得 m。最后 lk 离开作用域时，如果仍然持锁，它会负责解锁。这里的管理对象始终是 lk，暂时释放的是它所关联的 mutex。

std::unique_lock<std::mutex> lk(m);
cv.wait(lk, [&] { return ready; });
for (const auto x : buf) sum += x;

[&] { return ready; } 是一个返回 bool 的判断函数，这里称为谓词。它通过引用读取共享 ready，因而每次调用判断函数时，检查的都是那个受 m 保护的状态，而不是创建判断函数时保存的一份旧值。带谓词的 wait 可以按下面四步理解：

  1. 消费者已经通过 lk 持有 m，先计算谓词。若 ready 为 true，wait 就返回，消费者继续执行求和；此时没有必要释放锁去睡眠。
  2. 若 ready 为 false，底层 wait 将“通过 lk 释放 m”和“进入 cv 的等待状态”作为一个原子步骤完成。消费者在等待时不占有 m，生产者才有机会取得它。
  3. 等待可能因为通知而解除，也可能发生没有相应通知的虚假唤醒。解除等待之后，wait 会重新调用 lk 的加锁操作；如果 m 此时仍由生产者持有，消费者还要等待取得锁。
  4. 消费者重新取得 m 后，再计算谓词。若条件仍为 false，就再次释放锁并等待；只有检查到 true，带谓词的 wait 才正常返回。

N4861 将谓词版 wait 定义为反复执行“当谓词为假时调用 wait”的循环。因此，“被唤醒”和“带谓词的 wait 返回”是不同的时刻：前者只使线程离开条件变量上的等待，后者还要求重新持锁，并通过条件检查。上面求和循环位于 wait 返回之后、lk 析构之前，所以它读取 buf 时仍然持有 m。

生产者负责准备这一批输入。它取得 m 后，先把四个元素分别写成 3、5、7、9，再把 ready 设为 true。这两个动作位于同一个临界区，消费者无法在生产者只填了一部分元素时取得 m 并看到发布状态。生产者离开作用域释放 m，随后通知条件变量：

{
    std::lock_guard<std::mutex> hold(m);
    buf[0] = 3; buf[1] = 5; buf[2] = 7; buf[3] = 9;
    ready = true;
}
cv.notify_one();

从检查到等待之间为何没有空档考虑消费者先取得 m，并检查到 ready 为 false 的顺序。检查期间它仍持有 m，生产者无法同时取得 m 去写数据、改变 ready。接下来，消费者通过 wait 原子地释放锁并进入等待；这个步骤不留下“m 已交给生产者，但消费者还没有进入等待状态”的通知空档。生产者之后取得 m，才可能完成发布并发出通知。

这个分析依赖双方使用同一个 m 来检查和修改 ready。如果生产者绕过 m 修改 ready，上述“消费者检查时生产者还无法更新”的推理就失去了依据；ready 又是普通共享变量，程序还会失去对应访问的同步保证。因此，使用条件变量并不免除状态读写所遵守的同锁约定。

如果通知发出时还没有消费者等待另一种顺序是生产者先填完 buf，把 ready 设为 true，释放 m 并调用 notify_one，而消费者之后才开始运行。notify_one 在当前有等待者时解除其中一个的阻塞；此时若没有等待者，这次通知不会作为一张凭证保存下来，供以后进入 wait 的线程领取。

这一顺序仍可以正确工作，因为本例的 ready 会保留为 true。消费者之后取得 m，调用谓词版 wait 时先检查到 true，就直接继续求和，并没有进入睡眠。程序保存的是“本批已经发布”的状态，消费者也正是根据这个状态决定继续。条件已经成立时，生产者不必为这个后来到达的消费者再发一次通知。

同样的重查步骤也处理虚假唤醒：如果消费者没有收到生产者通知就离开了底层等待，重新加锁后发现 ready 仍为 false，它就继续等待。如果消费者仅因为“wait 被唤醒过”而读取输入，就没有确认本批发布是否真的完成。谓词循环把这项业务判断保留在每次恢复执行之前。

已有的本机观察导师此前用 GCC 13.3.0 和 C++20 固定了两种顺序：第一组先完成发布与通知，再启动消费者；第二组先由夹具确认消费者到达持锁检查点，再允许生产者发布。两组都使用上面的 ready 谓词，四个输入均为 3、5、7、9，实际输出如下：

6一块缓冲区的占用、交还与复用

上一节只发布一批数据，生产者填好 buf 后就不再修改它。现在希望一直保留同一块四元素缓冲区，把它记作 B，反复交付多批输入。场景仍限定为一个生产者、一个消费者，同一时刻只有一批占用 B；主线程一直持有 B 的存储。新的问题发生在生产者准备写下一批时：消费者可能已经拿到本批输入，却还没有读完。

原来的 ready 只回答“本批是否已经发布”。生产者填完数据后就把它设为 true，而消费者可能尚未领取，也可能已经开始计算。因此，生产者仅凭 ready 为 true，无法判断旧内容是否已经无人使用。我们要把“已经写好”“已经被领取”“允许再次写入”分开表达，再规定每个角色在什么状态下能够访问 B。

给单槽定义三个状态本节用一个共享状态变量记录下面三种状态。它的所有检查与修改都在同一个 mutex m 的保护下完成。这些状态是程序定义的业务含义，mutex 和 condition_variable 都不会自动替程序转换它们。

状态含义允许的下一动作
FREE上一批对 B 的使用已经结束，或还没有放入第一批生产者取得 m、确认仍为 FREE 后，在锁内写入下一批
READY本批数据已经完整写好，还没有被消费者领取消费者取得 m、确认 READY 后，在同次持锁期间领取本批
READING本批已经被消费者领取，它的内容仍为这次读取工作保留消费者完成本批读取；生产者等待交还，不能把下一批写进 B

FREE 中的“空闲”指本协议允许下一批复用，B 的内存仍然存在，并没有被释放。READY 中的“就绪”指消费者可以领取，尚未表示这一批已经使用完。READING 中的“占用”从领取时就开始，覆盖之后整个读取过程；即使消费者暂时没有执行到读指令，这批内容也仍然要留给它。

生产者怎样发布一批生产者取得 m 后检查状态，只有 FREE 才开始填写 B。如果状态是 READY，本批仍等待领取；如果状态是 READING，本批仍被读取工作占用。这两种情况下，生产者都通过等待操作释放 m，等状态变化后重新取得锁、再次检查，而不是直接覆写旧内容。

检查到 FREE 后，生产者在同一次持锁期间填好四个元素，再把状态改成 READY，最后释放 m 并通知等待数据的消费者。填充过程中没有额外的 FILLING 状态，是因为本节选择让整批写入都在锁内完成：即使状态暂时仍为 FREE，消费者也无法取得 m 去检查或领取；它能重新取得锁时，生产者已经完成本次临界区。

消费者怎样领取后再计算消费者取得 m 后等待 READY。当谓词检查到 READY，它仍然持有 m，在这次持锁期间把状态改成 READING，再释放 m 开始读取和计算。这样，消费者在允许其他参与者检查状态之前，就已经记录了“这批内容正在被我占用”。领取并没有复制 B，也没有把 B 的存储所有权从主线程移走，改变的是这次交接协议中的使用权。

假如生产者此时取得 m，它看到的是 READING。生产者可以检查状态，但依据协议还没有写入 B 的许可；它要继续等待 FREE。因此，消费者的长时间读取即使位于临界区之外，生产者也不会因为恰好取得了 m 就开始覆写。这项保证来自两个条件一起成立：消费者先在锁内记录占用，生产者每次写入前又在同锁下检查是否已经交还。

什么事实允许交还消费者对本批 B 的最后一次读取结束，才有依据宣布这次占用结束。它随后取得 m，把状态从 READING 改成 FREE，释放 m，并通知等待复用的生产者。生产者被唤醒后仍然要重新取得 m、检查 FREE，才开始下一批写入；通知本身没有修改状态，也没有替读取工作完成最后一次访问。

这里区分的是“读取工作已经提交”与“实际读取已经结束”。如果消费者把读取 B 的工作交给一个延迟任务，提交函数返回时，任务可能尚未执行，B 中这一批内容仍然要为它保留。只有能够确认该任务最后一次读取已经完成，负责收尾的代码才有依据按照同锁协议发布 FREE。若消费者在提交后立即交还，生产者就可能改掉那项尚未执行的任务要读的输入。

两个方向的等待各等什么消费者等待 READY，是在等“有一批数据可以领取”；生产者等待 FREE，是在等“上一批已经结束使用，可以写入下一批”。本节可以分别用 cv_ready 和 cv_free 通知这两个角色。两个条件变量服务于同一块 B，不代表有两份缓冲区；它们也不保存状态，能够继续的依据仍然是持有 m 时检查到的状态值。

为什么读取期间可以释放锁长时间持有 m 会让其他需要这把锁的状态检查与协调一起等待。本节把短时间的状态更新放在临界区内，再通过 READING 表示较长时间的数据占用，允许消费者在不持锁时继续只读计算。这样分开之后，参与者就多了一项责任：生产者取得 m 时仍须检查状态，不能把“现在拿得到锁”当作“现在可以修改 B”。否则，它可能在消费者读取期间写入同一批存储。

这与前面“消费者取得 data() 指针就解锁”的情况不同。仅取得指针的写法没有规定生产者此后应当等待什么；本节则在消费者解锁之前登记 READING，并规定生产者看到这个状态时等待 FREE。解锁后的安全理由因此不再是“消费者还拿着锁”，而是“生产者仍受同锁检查的占用状态约束”。

两次交接也各有一条 HB 链。发布时，生产者先写完 B 再解锁，消费者随后成功取得同一把锁并领取，于是写入排在读取之前。交还时，消费者先完成最后一次读取，再在锁内设为 FREE 并解锁；生产者之后成功取得 m、确认 FREE 才覆写，于是上一批读取又排在下一批写入之前。状态规定哪一方获准继续，mutex 的同步规则把对应的实际访问接到顺序上。

把这套判断带回实际系统EP 接收缓冲区或异步拷贝源缓冲区也会面临类似的复用问题：某批内容已经交给后续工作使用，但申请复用的人还要知道它什么时候不再被读取。CPU 单槽模型帮助我们区分这些时刻，却没有给出某个设备的完成接口。若读取发生在设备或外部队列中，应依据那个 API 对任务完成的承诺确认最后一次访问；提交成功、一次通知或提交线程返回，各自只能支持相应接口实际保证的事实。

本节范围这里限定单生产者、单消费者、单槽和正常交接，状态的含义与这一个在用批次对应。如果扩展到多批同时在途，程序还要辨认完成事件属于哪一批，才能决定哪个缓冲区已经具备复用条件。本节没有实现这种扩展，也没有据此规定退出或异常路径。

本节的单槽状态机由导师为教学场景设计；发布和交还时的同步依据来自 N4861 的同一 mutex 加锁、解锁规则。

本节三态协议是导师为单生产者、单消费者、单槽组织的教学设计；顺序依据是 C++20 工作草案 N4861 同一 mutex 的同步规则。没有把该状态机实现或测成某个 EP／设备运行时。

本节要点READY 允许消费者领取本批，READING 为已领取的读取工作保留内容，FREE 才允许生产者写入下一批。消费者即使解锁计算，占用状态仍然有效；生产者依据同锁保护的状态等待交还。只有本批实际最后一次读取结束，收尾代码才有依据发布 FREE，通知则让生产者重新检查这一条件。

7关闭请求、任务收尾与资源析构

前面的例子一直在讨论正常交接：生产者写入一批，消费者读取这一批，然后把缓冲区交还。现在增加一个常见场景：应用准备退出，主线程需要让这条生产—消费流程停止。发出关闭请求时，其他线程可能正在等待，也可能已经开始使用 B；主线程需要知道这些线程接下来还会访问哪些对象。

本节仍由主线程持有 B、互斥锁 m、条件变量 cv_ready 和 cv_free，以及记录槽位状态的变量。消费者在自己的线程中同步完成读取，没有把读取工作提交给另一个队列。本节采用的业务约定是：关闭后不再发布新批次，但已经发布的批次应当按照约定处理完。先明确这项约定，后面的退出判断才有依据。

把关闭请求保存为一项独立状态

主线程可以增加一个初值为 false 的 closing 标志，并用已有的 m 保护对它的检查和修改。把 closing 设为 true，表达的是“应用已经要求关闭”。FREE、READY 和 READING 则继续描述 B 当前是否空闲、是否有待领取数据、是否仍由消费者占用。

两类状态回答的问题不同。例如，主线程发出关闭请求时，消费者可能已经领取了某批数据，并且正在锁外读取 B。此时 closing 可以为 true，槽位状态却仍然是 READING。主线程如果仅因为 closing 为真就把 B 当成空闲内存释放，消费者后续的读取仍会访问已经失效的存储。程序应继续根据实际使用情况维护槽位状态。

让等待者有机会处理关闭请求

生产者平时可能在 cv_free 上等待空槽，消费者平时可能在 cv_ready 上等待新批次。线程阻塞在 wait 中时，不会因为另一个线程修改了 closing，就自动重新执行自己的判断代码。因此，关闭流程除了修改标志，还需要通知这些等待者，让它们重新取得 m 并检查条件。

notify_all() 会解除对应条件变量上所有当前等待者的阻塞。主线程可以按下面的顺序修改状态并发出通知。这里的代码只负责发布关闭请求，还没有等待工作线程退出，也没有销毁共享对象。

{
    std::lock_guard<std::mutex> hold(m);
    closing = true;
}
cv_ready.notify_all();
cv_free.notify_all();

等待谓词也要允许线程观察到 closing。否则，某个线程即使被通知唤醒，重新检查后发现正常工作条件仍然为假，也可能再次睡下，继续等待一个关闭之后不会再出现的正常事件。把 closing 纳入谓词，是让线程有机会执行关闭分支，并不意味着 wait 一返回就可以继续读取或覆写 B。

wait 返回以后，每个线程仍要结合自己的角色、槽位状态和业务约定，决定下一步动作。关闭请求可能要求某个角色停止产生新工作，也可能要求某个角色先完成已经承担的工作。程序设计者应当分别写清这些分支，不能只靠一个布尔标志的名字代替完整的退出条件。

为什么主线程要先释放 m，再等待消费者结束

考虑这样一个具体顺序：主线程取得 m，修改 closing，然后仍然拿着 m 调用消费者线程的 join。与此同时，消费者已经读完 B，准备重新取得 m，把本批的使用状态更新好，再退出线程。

这时主线程被 join 阻塞，正在等待消费者退出；消费者却被加锁操作阻塞，正在等待主线程释放 m。主线程只有离开当前持锁作用域才会释放 m，但它还不能从 join 返回。两个线程都在等待对方先继续，这就是死锁。

所以，在本例中，主线程应先结束对 m 的持有，再调用 join 等待仍需要这把锁才能收尾的线程。这里限制的是这一组存在循环依赖的操作，并不是说调用任何 join 时都绝对不能持有任何锁。判断时应具体追踪：被等待的线程退出之前，还需要取得哪些锁，而这些锁现在由谁持有。

把退出顺序接到对象析构上

如果把 B、m、条件变量和线程对象封装进同一个类，可以让这个类的析构函数体先执行关闭协议和 join。析构函数体完成后，语言规则才会继续销毁相应的成员对象。这样安排的目的，是让工作线程最后一次访问这些成员时，它们仍然存在。

RAII 能让约定的析构动作在相应作用域退出时执行，但程序仍须安排正确的依赖顺序。普通 std::thread 对象尤其不能被当成“析构时自动等待”的容器：如果它仍关联一个尚未 join 或 detach 的线程，析构会调用 std::terminate() 终止程序。即使线程函数已经返回，只要这个关联尚未处理，程序也不能据此跳过 join。

detach() 会解除 thread 对象与执行线程的关联，让执行线程独立继续。它不等待该线程结束，也不会把 B、m 或条件变量的所有权转交给后台线程。如果主线程在 detach 后立刻销毁这些对象，而后台线程稍后还要访问它们，程序仍然存在生命周期错误。对于本课的资源安排，detach 不能代替“确认最后一次访问结束”这项工作。

如果工作失败，或者工作被交给了其他执行者

消费者读取失败时，需要分别说明两件事：这批数据是否处理成功，以及消费者是否已经停止访问这批数据。处理失败不等于访问还在继续，访问结束也不等于处理成功。程序需要保存相应结果，并让其他等待者能够根据实际状态完成退出；不能只写一个“结束”标志，让不同角色各自猜测它表示哪件事。

本节之所以可以用消费者线程的 join 来约束资源销毁，是因为题设明确由这个线程同步完成所有读取。如果消费者线程只是向外部队列或设备提交读取请求，然后自己返回，那么 join 只能确认提交线程已经结束。主线程在释放 B 之前，还需要取得那个外部读取任务本身的完成依据。

本节要点先明确关闭后怎样处理已有工作，再让生产者、消费者和关闭线程分别执行自己的职责。关闭标志决定后续流程，任务完成事实决定使用权何时交还，join 确认相关线程何时结束。共享资源应当保持有效，直到所有仍会访问它们的执行者完成相应工作；RAII 负责执行清理动作，程序负责把清理动作放在正确的顺序上。

导师串讲：沿同一批数据走完生命周期

把前面的各节合到同一个程序中。主线程先创建一块能够容纳四个整数元素的缓冲区 B，同时创建互斥锁 m、两个条件变量、槽位状态和 closing 标志。随后，它启动生产线程和消费线程，让它们访问这些共享对象。B 的所有者始终是主线程所在的作用域；生产者负责填写内容，消费者负责读取内容，这两个角色并没有因此取得销毁 B 的责任。

从空槽开始，建立本批数据的发布顺序

初始状态为 FREE。生产者取得 m，在锁内确认当前允许继续生产，并且 B 已经具备写入下一批的条件。它把这一批的四个元素写进 B，完成整批写入后才把状态改成 READY。直到这一段临界区结束，其他使用同一把锁的线程才有机会重新检查这些状态。

生产者释放 m 后，通知等待 READY 的消费者。消费者如果更早到达，已经在条件变量上等待，就会有机会重新取得锁并检查状态；消费者如果较晚到达，则在第一次持锁检查时就可能看到 READY，直接继续。程序依靠保存下来的状态决定是否可以读取，不依靠消费者是否恰好收到某一次通知。

这次交接还包含数据可见性的依据：生产者先写入 B，再释放 m；消费者随后成功取得同一个 m，再开始领取和读取。写入、解锁、后续加锁和读取共同组成相应的 HB 链。状态表示业务许可，mutex 的同步规则使对应的数据访问具有可依赖的顺序。

消费者领取数据，生产者等待这一批真正用完

消费者在持锁检查到 READY 后，在同一次持锁期间把状态改成 READING，然后释放 m 去读取和计算。这里改变的是这一批数据的使用状态，不是 B 的存储所有权。消费者取得的是访问主线程所持有存储的许可；主线程仍然负责让这份存储保持有效。

在消费者读取期间，生产者可能再次取得 m。它虽然能够访问状态变量，却会看到 B 仍为 READING，因而不能把下一批写进 B。生产者需要通过等待操作释放 m，等待消费者交还。这说明消费者可以不持续持锁计算，但安全性依赖生产者始终遵守同锁检查的占用协议。

当消费者完成本批对 B 的最后一次读取，它重新取得 m，将状态改为 FREE，再释放 m 并通知等待复用的生产者。生产者重新取得 m、确认 FREE 后，才写入下一批。这样，上一批的读取结束、发布 FREE 时的解锁、下一批写入前的加锁，又建立了读取到下一次覆写的顺序。

如果消费者只是把读取工作提交给延迟队列，提交函数返回还不足以执行这次交还。负责收尾的代码必须取得实际读取任务的完成依据。至于“任务刚提交就先通知生产者”这一步，在没有相应状态变化的检查 3 中是冗余动作：生产者重新检查后仍然只能等待。

关闭时，把每个角色的退出责任分开

现在让主线程在某批数据尚未结束使用时发起关闭。主线程在 m 下设置 closing，并通知可能正在等待的线程，让它们有机会重新检查工作条件和关闭条件。这个请求改变的是后续工作安排，不会让已经存在的读取凭空消失，也不会替消费者处理已交付的数据。

本课选择“停止产生新批，处理完已经交付的批次”的策略。生产者确认关闭后停止继续发布；消费者按这项约定完成已经承担的工作，再结束对 B 的访问。每个线程完成自身职责以后可以退出，不要求两个线程在同一时刻退出。

尤其要把退出线程与存储所有者对应起来。在这里，生产者退出不会销毁 B，因为 B 仍由主线程持有。主线程可以先等到生产者退出，同时让消费者继续处理已有数据；但主线程不能仅凭生产者的 join 已经返回，就释放消费者仍会读取的 B。它还需要等待消费者结束相应访问，并完成对相关线程的等待。

工作线程收尾时可能仍要取得 m，因此主线程应在不持有这把收尾所需的锁时执行相应的 join。否则，主线程可能等待工作线程结束，而工作线程又等待主线程释放 m，形成循环等待。等到这些线程确实不再使用共享对象，主线程才销毁 B、状态、条件变量和互斥锁。

下面是本题给定的抽象接口契约，不代表某个真实通信库的保证。主线程持有专家输入缓冲区 B 和路由句柄 H。H 保存路由元数据，使用独立存储，既不持有 B，也不引用 B 内部的内存。另有结果缓冲区 Y，其生命周期始终有效。

一个提交线程依次提交以下工作，并建立好 dispatch → GEMM → combine 的执行依赖：

  • dispatch 写入 B，并填好 H；完成事件 E_D 表示该阶段的写入已经结束，GEMM 可以开始读取 B。
  • GEMM 读取 B，把结果写入独立的 Y；完成事件 E_G 表示它对 B 的最后一次读取已经结束，Y 已经写好。
  • combine 读取 Y 和 H，恢复原 Token 顺序，不访问 B；完成事件 E_C 表示它对 Y 和 H 的最后一次访问已经结束。

除上述访问外没有其他使用者。每个阶段完成后，该阶段的执行者就不再访问它原先处理的对象；其他阶段的访问范围仅以上述清单为准。本题提供一个完成等待接口 wait(E)：它成功返回时，保证 E 对应的阶段已经完成。提交线程只负责提交，不等待这些事件；它提交完 combine 后便返回，主线程随后成功 join 了这个提交线程。

  1. 主线程准备把 B 交给下一批覆写，并销毁 H。分别需要确认哪项完成事实？这两个动作是否必须一起等到 combine 结束后才能进行？
  2. join 成功在这里证明了什么？它是否足以支持上述覆写和销毁？请把已经结束的执行者与仍可能访问对象的执行者分开说明。

只按给定契约推理，不需要猜测具体 GPU API、计算数据量或编写代码。

参考要点与提交语义澄清

题设在作答后补充的接口条件：本题采用可以异步入队的提交模型。执行系统有足够的队列容量，执行者正在处理较早阶段时，提交线程仍可以把后续阶段及其依赖交给执行系统。三个提交调用在本次正常路径中均成功；调用返回表示对应工作已被接收，不以此前阶段执行完成作为返回条件。

dispatch → GEMM → combine 规定的是执行顺序：GEMM 要在 dispatch 完成后才能读取 B，combine 要在 GEMM 完成后才能读取 Y。它不要求提交线程等一个阶段执行完，才允许提交下一个阶段。因此，一种允许的情况是：dispatch 仍在执行，GEMM 和 combine 已经排队，提交线程已经返回，主线程也已经 join 成功。

原题只写了“提交线程不等待这些事件”，没有排除提交 API 自身可能等待较早工作完成。学习者提出这一问题是在核对接口契约，不是理解错误。这里补全题意，不把后来补充的条件追溯成原题已经明确给出的事实。

B 的复用：GEMM 是本题中最后一个读取 B 的阶段。确认 E_G 已完成以后，主线程就可以将 B 交给下一批覆写。combine 明确只访问 Y 和 H，H 又不引用 B 的存储，所以不需要为了这两个对象的后续使用而继续保留 B 的旧内容。

H 的销毁：combine 仍然需要读取 H。主线程需要确认 E_C 已完成，才能销毁 H。E_D 仅说明路由元数据已写好，E_G 也没有结束 combine 对 H 的使用，因此这两个事件各自都不足以支持提前销毁 H。统一等到 E_C 后再处理 B 和 H 是安全的额外等待方案，但不是 B 复用所必需的等待范围。

join 的范围：join 直接确认提交线程已经结束。三个任务已经成功提交，是结合本题正常提交路径得到的事实，不是 join 自身替调用者检查了任务提交结果。按补充后的入队契约，join 不提供 E_G 或 E_C 完成的保证，因此不能仅凭它覆写 B 或销毁 H。

这里也不应把“join 不能证明完成”改写成“join 返回时三个阶段一定都没完成”。执行者可能很慢，也可能已经完成一部分甚至全部工作。主线程缺少的是相应的完成保证；它需要通过题设的完成等待接口及已知依赖关系取得该保证，而不是猜测当前执行到了哪一步。

如果采用不同的提交接口：若另一个 API 明确保证“submit(combine) 只有在 GEMM 已完成后才成功返回”，那么沿本题的正常控制流，主线程可以由这个额外保证推出 B 已结束本次使用，而 H 是否仍被 combine 读取还需要另行确认。若 API 更进一步保证“该调用返回时 combine 自身也已经完成”，则返回保证覆盖的范围又会不同。

所以，“不能在执行者忙时继续提交”本身还不足以选定上述哪一种情况：接口可能等待、拒绝提交，或者采用别的机制。具体的推理依据应当是提交调用成功返回时承诺了什么，而不是程序中是否出现一个显式任务队列。学习者在原回答中已经给出了异步提交条件下的正确判断，这次澄清不要求重答同一个分支。

符号与名词

B、N
B 是存放这一批输入的一维缓冲区，N 是元素个数；元素类型为 int32_t。缓冲区在这里就是供程序读写的一段数据存储。
生产者、消费者
生产者准备输入，消费者处理输入。本课先用主线程和一个后台工作线程承担当中的两个角色。
所有者（owner）、借用者
所有者负责管理资源并安排释放或转交；借用者通过指针或引用访问资源，单有访问地址不等于承担或延长资源生命周期。
RAII
用对象的构造、析构等生命周期动作管理资源；例如一个容器对象管理其元素存储。
happens-before
C++ 中用于判断执行先后与跨线程可见性的关系。后续会用具体同步动作建立它，而不只按日志时间排序。
sanitizer
通过编译器插入检查并配合运行时库检测错误的工具。本课关注非法内存访问与数据竞争。
vector、data()、size()
vector 管理连续元素存储；data() 返回元素区起始指针，size() 返回元素个数。取得指针不转交存储管理责任。
lambda、闭包对象
lambda 表达式生成一个可调用对象；该对象携带捕获的数据，也称闭包对象。[p, n] 按值保存指针与数量，调用时执行花括号里的代码。
post、run_next
本段延迟队列的教学接口：post 只保存任务，run_next 才调用它。真实队列的提交与执行时序要另查其契约。
释放后使用（use-after-free）
对象占用的存储已释放，程序仍试图通过旧指针访问；本段的非法解引用属于未定义行为，不保证具体结果。
std::move
允许后续操作按移动语义取用对象的类型转换；真正的资源转交由接收方的构造或赋值操作完成。
std::thread、join()
带任务构造 thread 对象会创建执行线程；对其 join() 等待该线程结束，成功返回接上线程完成的同步关系。
[&buf, &sum]
lambda 通过引用访问原来的 buf、sum；不复制对象，也不自动延长它们的生命周期。
数据竞争（data race）
本课普通整数场景中，不同线程对同一位置的冲突访问至少一次为写，且没有 happens-before 顺序；其行为未定义。
mutex、临界区
mutex 是互斥锁对象；取得锁到释放锁之间的受保护代码段称为临界区。参与者须使用同一个锁对象并正确界定访问范围。
lock_guard
本课使用的构造形式在建立对象时加锁，作用域退出时通过析构解锁，把持锁责任交给 RAII 管理。
condition_variable、notify_one()
条件变量提供等待与通知。notify_one 在有等待者时解除其中一个的阻塞，不保存业务状态，也不保证等待者立即拿到锁。
谓词（predicate）
返回 bool 的判断函数，例如“ready 是否为真”。带谓词的 wait 在持锁时检查条件，为假才等待，醒来后重新检查。
unique_lock
跟踪 mutex 关联与持锁状态的管理对象。这里的 unique_lock(m) 构造时加锁，允许 wait 暂时释放并重新取得锁；仍持锁时析构会解锁。
虚假唤醒
底层等待可能在没有对应通知时被解除；这不说明业务条件成立，因此正常使用谓词或循环重新检查条件。
FREE、READY、READING
本节单槽协议的三个状态：允许写入、已发布待领取、已领取仍占用。FREE 允许复用，但不表示释放内存；状态转换须符合实际完成事实。
closing
本课关闭请求标志，受同一 mutex 保护。它控制是否继续接受新批，不等同于缓冲区已空闲或任务已完成。
notify_all()
解除对应条件变量上所有当前等待者的阻塞，让它们有机会重新拿锁检查条件；不等于等待者都已退出。
死锁（deadlock）
各方等待对方才能满足的条件，导致谁也无法继续。例如关闭线程持有 m 等 worker 结束，而 worker 又需要 m 才能收尾。
detach()
解除 std::thread 对象与执行线程的关联，执行线程独立继续；不等待任务完成，也不替共享对象延长生命周期。
ThreadPool、worker
ThreadPool 是管理一组工作线程和任务队列的对象；worker 是反复从队列取任务执行的工作线程。本节只读其关闭路径。
