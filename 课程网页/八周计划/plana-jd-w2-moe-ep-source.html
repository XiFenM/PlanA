这一单元要解决什么

单元二读了五份代码：推理框架 vLLM 和 SGLang，通信库 DeepEP 和 MORI-EP，以及 DeepEP 的 Hybrid-EP 分支。它们做的是同一件事：在一层 MoE 里，把每个 token 送到它选中的专家所在的卡上，算完再送回来加权求和。五份代码的分歧，几乎都出在同一个问题上：接收方要收多少行，谁知道、什么时候知道。知道得晚，主机就得停下来等；不想等，就只能按最坏情况预留空间，或者先多做一轮通信把路由告诉所有人。

这一页是本单元的导师串讲。读完以后，你应该能沿这条线，对五种实现中的任意一种说清：它在哪一步计数，接收空间怎么定，交给专家 GEMM 的是什么布局，主机在哪里等 GPU，buffer 和 handle 什么时候能再用；也能在它的代码目录里，找到这条线经过的那几个文件。

前面讲过

九个节点都已在对话里讲过并检查过，各自的详细页面等本单元结课后再补。这里只用一句话挂回每个节点，串讲会把它们接成一条线。

  1. vLLM 路由与专家放置：expert_map 决定专家在哪张卡上；放置改变通信的分布，不改变路由。
  2. 三个独立选择与 modular kernel 约定：并行配置、all2all 后端、GEMM 后端各自选择；prepare/finalize 与 experts 之间约定激活布局和由谁做加权求和。
  3. DP 同步、补齐与 AgRs：各 DP rank 每步先交换 token 数、补齐到同一长度；默认后端用 all-gather 加 reduce-scatter，不需要按接收方计数。
  4. SGLang 的 dispatcher 与 runner：dispatcher 输出带格式名，runner 按“格式 × runner”查表做重排；TBO、SBO 把通信藏到计算后面。
  5. DeepEP 高吞吐（HT）：先由 notify kernel 交换计数，CPU 等到计数后精确分配，再发数据。
  6. DeepEP 低延迟（LL）：每个“本地专家 × 源卡”预留固定槽位，不用 CPU 等待，能录 CUDA graph。
  7. DeepEP V2 与 V2.5：统一成一个 buffer，按“源卡 × 槽位”分段；可以选 CPU 同步拿精确数，也可以按最坏情况分配。
  8. MORI-EP：所有发送方向接收方的共享池按需领槽位，只需设一个总上限。
  9. Hybrid-EP：先把路由全收集给所有卡，之后的布局人人可算；跨节点走 RDMA，节点内走 NVLink。

一、两层分工：框架做什么，通信库做什么

机制推理框架负责模型、路由、量化格式、专家 GEMM 和 CUDA graph；通信库负责收发 buffer、数据在线上的布局、跨卡同步，以及 NVLink、RDMA 这些传输。两者之间有一个固定的交接面。vLLM 里是 PrepareAndFinalize：prepare 做量化加 dispatch，finalize 做 combine，中间的 Experts 只管 GEMM。SGLang 里是 dispatcher 加 MoeRunner：dispatcher 交出一个带格式名的结果，runner 按“格式 × runner 名”查表，决定先怎样重排再做 GEMM。

三、主线：接收方的行数，谁知道、什么时候知道

为什么这样设计接收方要给到来的行准备空间，而行数取决于全组每张卡的路由，本卡事先不知道。办法只有四类，每类都在付代价。

好比多个线程往一个数组里写结果（≈ 接收 buffer）：可以先问清每个线程写多少，再精确 malloc；可以按上限开一个大静态数组；可以让大家对一个共享的 tail 做 fetch_add，各领一段；也可以先把全局计划表发给每个线程，各自算出自己写到哪里。

线程之间问一句只要几纳秒。这里的“问”要跨几十张卡、跨节点，还要经过 CPU：一次等待就是一次主机往返加一次全组同步，录 CUDA graph 时干脆不允许。所以下表的每一种选择，都是在拿等待、显存或额外一轮通信做交换。

实现行数何时、由谁知道接收空间怎么定主机等吗能录 graph
vLLM AgRs不按接收方计数；各源 rank 的行数在每步开头已到 CPU每卡收下全组 ΣTr 行层内不等能
DeepEP HTnotify 之后，CPU 才知道精确的 N_recv每层一次不能；单节点可用 num_worst_tokens 跳过等待
DeepEP LL事先不知道，也不需要每个“本地专家 × 源卡”固定 M 槽不等能
DeepEP V2GPU 先知道；do_cpu_sync 时 CPU 也知道精确，或按 R·M 最坏prefill 等，decode 不等不同步时能
MORI边发边领槽；总数只在 GPU 上共享池，设一个总上限不等能
Hybrid-EP路由全收集后，每卡自己算阻塞：精确 P；非阻塞：调用方给上界仅阻塞模式等非阻塞能

真实系统把贯穿案例代入，看每卡每层 dispatch 要准备多大的接收空间。decode 每卡 32 个 token 时，按最坏情况固定预留只要 112 MiB，可以接受；prefill 每卡 4096 个 token 时，同样的预留就到了 14 GiB，放不下。所以 prefill 只能先拿到精确计数（CPU 等），或者先全收集路由；decode 才付得起“固定预留、不等”。

LL 延迟低，那 prefill 也用 LL，整套系统只留一种 kernel 就好。

LL 快，是因为它按最坏情况固定预留、不等计数。decode 的最坏情况是百 MiB 级，付得起；prefill 的最坏情况是十几 GiB，付不起，只能先计数或先全收集路由。

四、交给专家 GEMM 的布局，以及谁来乘权重

机制通信库交出来的行，不一定能直接喂给 grouped GEMM。差别在三点：行是按源卡排还是按专家排；一个 token 命中本卡多个专家时，是一行还是多行；路由权重在哪一步乘。

五、完成、重叠与复用

机制图 10.2 每个面板的最后一步，写的就是这一家怎样宣告完成、什么能再用。归纳起来只有两条规律。第一，常驻的通信 buffer 只在初始化时注册一次，之后每次调用复用；凡是要按 token 数改大它的（Hybrid-EP 扩容），都会让旧 handle 和已录的 graph 一起失效。第二，输出要么是拷出来的新张量（DeepEP、Hybrid-EP），可以放心交给计算流；要么是这块 buffer 的视图（MORI、LL 的 zero-copy），下一次通信前必须用完。

面试怎么讲约 90 秒

MoE 的专家并行，每层要做一次 dispatch 和一次 combine。难点不在搬数据，而在接收方事先不知道会收到多少行。各家的回答不同：vLLM 默认的 AgRs 干脆让每张卡收下全部 token，省掉计数，代价是通信量放大约 R/K 倍；DeepEP 高吞吐模式先交换计数，CPU 等到后精确分配，适合 prefill，但每层多一次主机同步，不能录 CUDA graph；低延迟模式按最坏情况给每个专家、每个源卡固定槽位，不等计数，能录图，适合 decode，代价是显存按最坏情况预留。

MORI 让所有发送方从接收方的共享池按需领槽，只设一个总上限；Hybrid-EP 先把路由全收集给每张卡，各卡自己算布局，适合 token 多的训练和 prefill。选哪种，取决于 token 数：多的时候付得起一轮同步，少的时候付得起最坏情况的显存。

回答验收 5 后：路由信息分两类

机制dispatch 之后要用到的路由信息分两类。第一类是“这一行交给哪个本地专家算”，专家计算马上就要用；第二类是“算完送回哪张卡的哪个 token”，要一直留到 combine。DeepEP 的两种模式和 MORI 都把第一类跟着 dispatch 的输出交给调用方；第二类的去处不同：DeepEP 装进 handle 交给调用方，MORI 留在 op 对象里。第四节的表讲第一类长什么样，这里补上第二类放在哪。

实现第一类：交给哪个本地专家第二类：送回哪里第二类放在哪
DeepEP HTrecv_topk_idx：本地专家号，别卡的专家记 -1；另给每个本地专家的行数。一个 token 到本卡只来一行，命中本卡两个专家时，这一行带两个专家号每行来自哪个源 token（recv_src_idx）、各源各通道的前缀和、发送槽位表（send_head）handle，调用方持有
DeepEP LL不给专家号：输出的第 0 维就是本地专家，recv_count[e] 是这个专家的有效行数。命中本卡两个专家时，两个专家各有一行每行的源 token 号（src_info）、每个“本地专家 × 源卡”段的起点和行数（layout_range）handle，调用方持有
MORIout_indices：源 token 完整的 K 个全局专家号，原样拷来；框架再按本卡的专家范围过滤每个 token 的每个专家去了哪张卡的哪个槽位、每行来自哪张卡的哪个 token、本卡发出多少 tokenop 内部，下一次 dispatch 改写；return_routing=True 时另给一份交调用方（只支持 IntraNode、InterNodeV1）
vLLM 接口prepare 返回每个本地专家的行数，以及 dispatch 后的 topk_ids、topk_weights；接 LL 时不返回专家号finalize 的参数里没有 handleprepare/finalize 对象内部；接 HT、LL 时按 micro-batch 下标各存一个 handle

HT 和 MORI 交出的行按来源排，不按专家排，框架的 experts 要先按专家号把行分组排好，再做 grouped GEMM；例如 vLLM 的 TritonExperts 用 topk_ids 和 expert_map 算出排序。LL 在接收时已经按专家放好，直接交给 masked grouped GEMM。

为什么这样设计第一类马上被专家计算用掉，格式必须对上 GEMM：要么给专家号让框架分组，要么直接按专家排好。所以它是 dispatch 的输出，框架看得懂。第二类要从 dispatch 一直留到 combine，中间隔着整段专家计算；它描述的是通信库自己的布局，包括槽位、前缀和、跨节点两跳的转发表，框架不需要看懂，只要原样交回。所以第二类要么包成不透明的 handle 交给调用方保管，要么留在库里。留在库里，接口最简单，但一个对象同一时刻只能有一组 dispatch／combine 在飞；交给调用方，才能交错多个 micro-batch。

C 标准库切字符串的 strtok，把“下次从哪接着切”存在函数内部的静态变量里（≈ MORI 的 op 内部状态），两个字符串交替着切，就会互相打乱；strtok_r 让调用方传入 saveptr（≈ DeepEP 的 handle），各切各的，可以交错。

handle 里是 GPU 上的张量，要等 combine 的 kernel 在流上跑完才能释放，不像 saveptr 用完即弃。另外，MORI 收到的数据和 out_indices 本身也在 op 的缓冲区里；只把第二类交给调用方，挡不住下一次 dispatch 覆盖数据，这一层 saveptr 管不到。

回到验收验收 2 的 MORI，两类信息连同收到的数据都在 op 的缓冲区里（out_indices 也是视图），B.dispatch 一并改写，所以 A 的专家计算和 A.combine 都会错。验收 5 的 Y 默认只有第二类留在对象里，所以只有 A.combine 错；如果第一类也留在 Y 里，A 的专家计算同样会错。

补充：双缓冲怎样跨轮复用，快 rank 在哪里等慢 rank

结论A、B 两个槽把相邻通信操作隔开；安全还需要两条顺序：发布本轮信号前，清好本 rank 的下一槽信号；本地本轮 RECV 真正完成后，再执行下一次 SEND。快 rank 可以先进入另一槽，却不能绕过中间那轮的接收，直接覆盖旧槽。

下面只追 DeepEP V1 LL 的正常调用。两个 rank 各有一套 Buffer，其中各含 A、B 两个内部槽；每槽都包括发送区、接收数据区和信号区。两边执行相同调用序列，但 rank 1 的接收较慢。mb0、mb1 是两批不同数据，A、B 是反复使用的内存槽，两者不是一一绑定的。

为什么需要两份在 t3，rank 1 还在读 A，rank 0 已可以写它的 B；若两次操作用同一槽，就可能把正在读的数据覆盖。等到 rank 0 要再次写 A 时，中间操作的信号又证明 rank 1 已读完并清好 A。两份内存提供错开的空间，跨轮依赖限定能错开多远。

清零清的是什么清的是本 rank 下一槽的信号区，不是整块载荷，也不是对端的信号。dispatch 用 0 表示未到达，用 −n−1 表示“已发送 n 行”，因此零行也要发 −1；combine 的正常完成 flag 为 1。A 中上一轮残留的非零信号如果没清，新一轮 RECV 就可能把旧信号误当成新数据已到。

观察到对端本轮信号本轮载荷可按协议读取；对端的下一槽信号已清好对端已经读完它自己的本轮数据

如果跳过等待，具体会在哪里出错？

回到 t3：rank 0 已发送操作 1，rank 1 仍在读操作 0 的 A。若调用方在另一条未建立依赖的 stream 上直接执行操作 2 SEND，就会向 rank 1 的 A 写新载荷，覆盖它还在读取的数据；操作 2 还会清 rank 0 自己的 B 信号，可能擦掉尚未消费的操作 1 通知。索引翻转不会替调用方检测这些冲突。

使用 recv hook 时，也要保证本次 RECV 完成后下一次 SEND 才在设备上执行。CPU 可以提前排队，但同一 stream 的顺序或等价 event 依赖必须保留。各 rank 还须使用匹配的调用顺序，不能因为没有本地 Token 就自行跳过通信。

固定源码：DeepEP d4f41e4。槽位布局与信号区；dispatch 轮换与 hook、combine 共用索引；dispatch 清理、发信号与拷出；combine 清理、发信号与归约。

边界图中是无故障、未屏蔽 rank 的普通 LL 调用，前提是本地依赖和全组调用序列一致。普通 dispatch 的独立输出与内部 A/B 槽分属不同生命周期；zero-copy 视图、CUDA graph 地址复用以及故障恢复须另外核对。这里解释固定源码中的协议，不是设备运行轨迹或性能测量。

面试怎么讲约 60 秒

双缓冲只提供两份交替使用的内存，安全靠顺序。LL 每次 dispatch 或 combine 都翻一次槽；SEND 在发布本轮信号前先保证本地下一槽信号清好，而调用方保证本轮 RECV 完成后才执行下一次 SEND。快 rank 可以在慢 rank 读 A 时先写 B，但必须等慢 rank 的 B 轮信号并完成自己的 B 接收，才能再次写 A。慢 rank 能发 B 信号，就说明它已读完旧 A 并清好了 A。这条跨轮因果链防止追上覆盖，不需要把每一步变成全组同时结束。

验收 1迁移

一个假想的通信库 X（纯属假设，不对应任何真实的库或芯片）这样做 dispatch。全部步骤都在 GPU 上完成，主机不读任何计数；接收区在初始化时按一个总上限 C 行一次分好，之后不再分配。

  1. 第一轮：每个发送方把“发往每张卡多少行”发给对应的接收方，每张卡只收 R 个整数。
  2. 接收方在 GPU 上对各源的行数做前缀和，算出每个源在本卡接收区里的起始偏移；第二轮再把偏移发回各源。
  3. 发送方按收到的偏移，把数据直接写进接收方的接收区。
  1. 在图 0 的“计数”和“接收空间”两站，X 分别更像 DeepEP HT、DeepEP LL、MORI 中的哪一个？各像在哪里、不像在哪里？
  2. 如果某一步实际到达本卡的行数超过 C，X 能在什么时候发现、由谁发现？你会按什么定 C？
  3. X 能录 CUDA graph 吗？在 decode（每卡 T = 32）和 prefill（每卡 T = 4096）下，它比 DeepEP LL、DeepEP HT 分别多付了什么、少付了什么？

说清判断和理由即可，不需要算具体数字。

你的回答

第一题（a）计数方面和接受空间上都更像mori。像在1.计数只在device上完成，不需要host参与。2.按分卡的行数发给接受方。3.发送方按照收到偏移，直接写进接收区。4.接收区一次性根据总上限行数分好。不像在接受方收行数不是远程原子加一个数，而是分在R个数，不需要原子操作。然后由接受方gpu计算前缀和，然后再返回发送方。需要通信-计算-通信这样三步，而不是一步。

（b）如果超过C，那么在接收R个整数之后，做前缀和时就能和C比较发现。由接收端gpu发现。确定C的值可以先按最坏情况预设，这样确保能满足所有情况的需求。然后再根据线上流量情况结合eplb调低C的上限重启服务。

（c）能录cuda graph，通讯部分没有host参与。在decode中，相比deepp ll，多了计数方面的三步走通信计算代价，但可以调低上限来节省缓冲区空间。在prefill中，相比deepep ht，由于依旧需要预分配缓冲区，所以会多付出一定程度的缓冲区浪费；但由于不需要host参与精确分配空间，所有没有host停顿等待且能录graph。

反馈
  • (a) “接收空间”像 MORI，这点成立。“计数”这一站更像 DeepEP HT：先专门交换一轮计数，再做前缀和，得到按源排好的偏移，这正是 HT notify 的顺序；X 只是把 HT 里“主机等计数”那一步，换成在 GPU 上多一轮回传偏移。你列的三条“不像 MORI”，正好是“像 HT”的理由。MORI 发数据前不交换计数，偏移是发送方对接收方计数器做远程原子加领来的（MORI src/ops/dispatch_combine/internode_v1.cpp:55）。
  • (b) 谁发现、什么时候发现都答对了：第一轮之后、数据写入之前，由接收方 GPU 发现。往下调 C 时，要看每步、每卡到达行数的高分位峰值加余量，不看平均；EPLB 能拉平各卡负载、压低峰值，所以能让 C 下调。
  • 你追问：“关于（b）我知道要节省空间，但一开始冷启动，不知道线上情况，怎么根据线上峰值和余量来定？所以我写的是先按最坏情况确保服务正常，然后收集线上情况后再调。”冷启动先保守、再按实测调，是正常的工程做法，我先前说“省空间的意义就没了”说重了。更准确地说：decode 按最坏情况定 C，接收区约 28 MiB，冷启动直接这样定没有问题；prefill 最坏情况约 3.5 GiB，这块显存要从 KV cache 里让出来，未必给得起，这时可以上线前用有代表性的请求离线压测，按高分位峰值加余量给初值。另外，X 能在数据写入之前发现超限，可以把超限做成一条慢路径（这一步改走精确分配，或拆成两次发），有了这个兜底，冷启动就敢用比最坏情况小得多的 C。
  • (c) 能录 graph，decode 和 prefill 两边的取舍也说对了。补两点：能录还因为接收区的地址和形状在初始化时就固定了；prefill 和 HT 比，多付的除了空间浪费，还有超过 C 的风险。
参考要点
  • (a) “计数”站更像 DeepEP HT：先单独交换一轮计数，再做前缀和，得到按源排好的偏移；不同在于全程留在 GPU 上，用多一轮回传偏移代替主机等待。“接收空间”站像 MORI：初始化时按总上限 C 一次分好；不同在于 X 的布局按源有序、可复现，不靠原子操作竞争槽位。
  • (b) 第一轮之后、任何数据写入之前，接收方 GPU 用前缀和得到的总数与 C 比较就能发现，可以置标志或通知各源。定 C：冷启动可以先保守，但最坏情况至少是 R·T 行，和 AgRs 每卡收的一样多（decode 约 28 MiB，可以接受；prefill 约 3.5 GiB，往往给不起），也可以上线前用有代表性的请求压测给初值；之后按每步、每卡到达行数的高分位峰值加余量调整，不按平均。EPLB 压低峰值，C 就能下调。超限要配一条慢路径。
  • (c) 能录：主机不读计数，接收区的地址和形状在初始化时就固定了。decode 和 LL 比：多两轮小消息的延迟，少了按“本地专家 × 源卡”最坏情况预留的空间。prefill 和 HT 比：省掉主机等待、能录 graph，代价是预留 C 和超限风险。

验收 4对比

接着验收 1：把 X 改一处，叫 X′（同样纯属假设）。去掉两轮计数；发送方每要发一行，先对接收方的一个计数器做一次远程 fetch_add，把返回值当作这一行在接收区里的偏移，然后直接写入。接收区仍是初始化时按 C 行分好的。

  1. X′ 的接收方最早什么时候知道本步一共收到多少行？超过 C 时，由谁、在什么时候发现？
  2. X′ 接收区里的行按什么顺序排，两次运行会一样吗？两问都和 X 对比着说。

用自己的话回答，几句话即可。

你的回答

（a）接收方最早需要到所有发送方都完成远程fetch_add之后查看计数器才能知道本步会收到一共多少行。超过C时，由发送方先发现，在远程fetch_add完获得返回值位置偏移与C行上限空间对比时发现。相比原X，接收方发现超限较晚，发现时很可能已经有数据发送到了缓冲区中，那么此时再改成精准分配，浪费的时间就太多了。

（b）接收区里的行按照发送方远程竞争顺序而定，两次运行可能会不一样，因为每次网络波动可能会使得不同发送方的先后顺序不同，就导致接收区的行顺序不同。相比X的计数收集完毕后再X上前缀和计算的做法，X的做法更稳定，多次运行不会顺序不同，为稳定复现提供了条件。

反馈
  • 两问都对。补一点：接收方光看计数器的值，分不清还有没有发送方没加完，所以每个发送方还得发一个“发完了”的信号。MORI 就是这样做的：各源把自己发了多少行写给接收方，当作完成信号，接收方逐个等（MORI src/ops/dispatch_combine/intranode.hpp:278-290）。
  • 再补一点：行的顺序不固定，除了网络的原因，还因为 GPU 上各个 block 的执行先后本身就不固定。
参考要点
  • (a) X′ 的接收方要等所有发送方都发出“发完了”的信号才知道总数；光看计数器的值，分不清是否还有发送方没加完。MORI 就是让各源在数据之后把自己发了多少行写给接收方当完成信号。超过 C 时，由发送方在 fetch_add 拿到偏移的那一刻发现，但它只知道自己这一行越界，没有谁掌握全局；X 则在任何数据写入之前，由接收方掌握每个源的精确行数。
  • (b) X′ 按原子操作的先后排列，受网络和 GPU 上各 block 执行先后的影响，两次运行可能不同；X 按源和前缀和排列，可以复现。这正是 MORI 与 DeepEP HT 在“计数”站的区别。

验收 2诊断

某团队自己写了一个接入层，用一个 MORI op 对象做 dispatch 和 combine。decode 时他们开启了“两个 micro-batch 交错”：同一张卡上依次发出 A.dispatch → B.dispatch → A 的专家计算 → A.combine → B 的专家计算 → B.combine，全部在同一条流上。不交错时结果正确，开了交错后 A 的输出出错。

  1. 指出最可能的原因：是哪一步覆盖了什么？
  2. 给出两种修法，并说出各自的代价。
  3. 同样的交错顺序换成 DeepEP HT，为什么不会出这个问题？

用自己的话回答，指出出错的那一步和被覆盖的东西即可。

你的回答

（a）这种情况下，由于开双缓冲区需要框架接入层主动建立多个instance，所以很可能因为只有一套缓冲区而导致缓冲区被覆盖而出错。比如A dispatch完后数据进入缓冲区，然后B dispatch，就将B的数据覆盖到缓冲区里A的数据了。此时再进行A的专家计算，由于给到的计算参数是来自于缓冲区的视图，就会读取到被覆盖的数据，就出错了。

（b）第一种就是为每一个micro-batch建立一套mori的instance，即建立两套缓冲区。代价是缓冲区空间翻倍。第二种可以放弃交错行为，按照先A dispatch到combine，然后B dispatch到combine的顺序来进行。代价是没有交错收益。

（c）换成deepep ht，不会出现问题是因为他的分配输出行为是每一次获取到精确计数后由host新分配一块输出空间给到通信操作。所以为两个batch，分配的是两个空间，所以不会出被覆盖的问题。

反馈

  • (c) 每次新分配输出只是一半原因；另一半是 dispatch 把布局装进 handle 交给调用方，combine 时再传回来，A、B 各持一份。vLLM 开 DBO 时就按 micro-batch 各存一个 handle（vLLM vllm/model_executor/layers/fused_moe/prepare_finalize/deepep_ht.py:194-196、:379-380）。
参考要点
  • (a) B.dispatch 覆盖了同一个 op 里的两样东西：A 收到的数据（dispatch 返回的是 op 缓冲区上的视图），以及 A.combine 要用的路由状态，即每个 token 的每个专家被发到了哪张卡的哪个槽位、本卡发出了多少 token。A 的专家计算读到 B 的数据，A.combine 又按 B 的布局取结果。
  • (b) 每个 micro-batch 用一个 op，SGLang 开 TBO 时就按 instance_id 建两个，代价是注册缓冲区翻倍。或者让每次 dispatch 与它的 combine 成对，中间不插另一次 dispatch，代价是失去两个 micro-batch 通信之间的交错；MORI 的 combine 输出同样是视图，A 的合并结果要在 B.combine 之前用掉或拷出。只把 dispatch 的数据拷出来不够，路由状态仍会被覆盖。
  • (c) HT 每次按精确行数新分配输出；布局装进 handle 交给调用方，combine 时再传回，A、B 各持一份。vLLM 开 DBO 时按 micro-batch 各存一个 handle。

反馈
  • (a) 你的理解成立。题目默认“这一行交给哪个本地专家”随 Y 的输出一起新分配，Y 内部只存 combine 往回送用的来源信息，但题面没写明这个前提；如果专家号也只存在 Y 内部，A 的专家计算同样会错。
  • 你追问：“验收5的（a）中，专家计算不需要路由情况吗？那怎么知道哪几行对应哪些专家呢？”需要，只是它要的和 combine 要的不是同一类，见补充：路由信息分两类。
  • (b) 按 batch 编号在 Y 内部维护多套路由布局，能修好。“数据区”那一份对 Y 用不着，因为 Y 的输出本来就是新分配的；换成 MORI 才需要。和 HT 的做法比：HT 把布局装进 handle 交给调用方，Y 不必预先知道有几个 micro-batch，布局活多久由调用方手里的 handle 决定；你的做法要预先定好最多几套，调用方还要保证同一个编号在它的 combine 完成之前不被复用。vLLM 的 DeepEP 接入层兼有两种思路：handle 由调用方持有，并按 micro-batch 编号存进数组（vLLM vllm/model_executor/layers/fused_moe/prepare_finalize/deepep_ht.py:194-196）。
  • 你追问：“验收5的（b）中，题设不能有多个y对象。按HT的做法，把布局装进handle交给调用方，调用方就有了多个Y的handle对象了。”handle 不是第二个 Y 对象。题设限制的是通信对象里贵的部分：注册过的大块通信缓冲区，以及所有卡一起参与的初始化。handle 只是几份随 token 数、卡数增长的小整数张量，由普通分配器分配，不用注册，也不用别的卡参与；DeepEP HT 每次 dispatch 都返回一个新 handle，但整个进程只有一个 Buffer。两种改法都有多份路由布局，区别只在归谁管。
参考要点
  • (a) 路由信息有两类：“这一行交给哪个本地专家算”是专家计算要的，“算完送回哪张卡的哪个 token”是 combine 要的。本题默认前一类随 dispatch 输出一起新分配（像 DeepEP HT 返回的 recv_topk_idx），Y 内部只存后一类。按这个前提，A 收到的数据和专家计算的结果都对，错在 A.combine：它用的是 B.dispatch 改写后的路由布局，按 B 的行来源把结果送回。题面没有写明这个前提；如果把“交给哪个专家”也理解为只存在 Y 内部，A 的专家计算同样会错。
  • (b) 两种改法都可以。一是 dispatch 把布局作为 handle 返回，combine 时传回，这是 HT 的做法：Y 不必预先知道有几个 micro-batch，调用方持有每个 handle，直到对应的 combine 完成。二是接口带 micro-batch 编号，Y 内部维护多套布局：要预先定好套数，调用方要保证同一个编号在它的 combine 完成之前不被复用。vLLM 的 DeepEP 接入层按 micro-batch 编号把 handle 存进数组，两种思路兼有。两种改法都会有多份路由布局，区别只在归谁管；“不建第二个 Y 对象”限制的是通信缓冲区这类重资源：注册过的大块显存，以及所有卡一起参与的初始化。handle 只是几份随 token 数、卡数增长的小整数张量，不是第二个 Y 对象。

验收 3口述

面试官问：“DeepEP 的 LL 模式能录 CUDA graph，HT 模式为什么不行？如果一定要让走高吞吐路径的步也进 graph，有哪些办法，各付什么代价？”请写一段 60–90 秒能讲完的回答。

写成一段口述稿，约 250–350 字；本周只验收内容，不考口头表现。

你的回答

HT模式需要每一次计数后由host根据计数精确分配通信输出空间。存在host-device的同步等待计数完成，所有不能录cuda graph。如果一定让HT也进graph，那么就需要提前设定大缓冲区，不能让cpu在运行中间来精确分配缓冲区。而由于HT模式常用在prefill场景，处理的token数量多，采用最坏情况分配缓冲区可能会产生极大的空间浪费。比较好的做法是设置缓冲区空间上限C，然后在超限的时候再退回到精确分配路径。

但超限似乎也需要在graph运行中间才发现，可能也难以退回精确路径。那么就只能承担超限的风险了。

或者就像上面所说，先采用代表性的请求benchmark来压测一遍，记录每步每卡的收到token行数情况，然后根据高分位数和余量给出一个上限C。

反馈
  • HT 为什么不能录、两类办法和代价的方向都对。下面补三点。
  • 不能录的另一半原因是形状：HT 的输出按每步实收行数现分配，形状每步都变。LL 能录，是因为槽位固定、计数留在 GPU 上，输出形状不变。
  • 超限不需要在 graph 中途退回：图里只置一个标志，图跑完后再检查；超限的那一步，由调用方决定报错，或者丢掉结果、改走精确路径重算。Hybrid-EP 的非阻塞模式就是这样：超出上限的 token 被丢掉，handle 的最后一项是 overflow_flag，调用方事后检查（Hybrid-EP deep_ep/hybrid_ep_buffer.py:534、tests/test_hybrid_ep_token_drop.py:89-90）。
  • 还没落到真实开关上：你说的办法是通用推理，没落到本单元讲过的真实开关上。本页“主线”表和“参数对照”表里有 DeepEP V1、V2 和 Hybrid-EP 各自的开关；这一点由验收 6 复查。
参考要点
  • HT 为什么不能录：notify 之后 CPU 忙等计数，再按精确行数分配输出；graph 里不能有主机等待，输出形状也随每步实收行数变化。LL 能录，是因为每个“本地专家 × 源卡”的槽位固定，计数留在 GPU 上，形状不变。
  • 办法与代价：DeepEP V1 单节点给 num_worst_tokens，按最坏行数分配，只限节点内。DeepEP V2 用 do_cpu_sync=False，按 R·M 最坏情况分配。Hybrid-EP 用非阻塞模式，由调用方给上限 P：压低能省空间，但超出的 token 会被丢掉，要事后检查 handle 里的 overflow_flag。HT 传入上一次的 handle、复用缓存的布局，可以跳过 notify，但只在路由完全相同时成立。
  • 共性代价：按最坏情况或上限预留的显存；每步的 batch 要补齐到录好的 graph 档。
  • 超限怎么处理：图里只置标志，图跑完后再检查；超限的那一步由调用方决定报错，或者丢掉结果、改走精确路径重算。

验收 6口述

接着验收 3：把口述稿的后半段，也就是“一定要进 graph 有哪些办法”，重写一遍。至少说出本单元讲过的三个真实机制，每个都点明是哪个库的哪个参数或模式、省掉了哪一步等待、付出什么代价。

写成口述稿，约 150–200 字；可以回看本页。

你的回答

一定要进graph，deepep v1、v2和hybrid-ep给出了三个真实可参考的解决机制办法。

在deepep v1 ht中，对于单节点内通信，可以采用可用 num_worst_tokens来分配最坏情况token数空间，使得跳过cpu等待精确分配，采用相同形状的输出空间使得能够进graph。省去cpu精确分配的等待，但会付出大缓冲区的代价。

在deepep v2中，可以采用设置do_cpu_sync=false的方式，同样采用R*M的最坏情况来分配接收输出空间。省去cpu精确分配的等待，但会付出大缓冲区的代价。

在hybrid-ep中，可以采用非阻塞模式，由调用方给出分配接收空间的行数上限C。从而省去cpu同步等待和固化接收区形状。省去cpu精确分配的等待，但会付出大缓冲区的代价。但可以由调用方调整控制上限C，可以根据实际情况来压低上限C，从而减少浪费缓冲区的代价。

反馈
  • 三个机制都对，“省掉 CPU 等待”也对，V1 只限单节点也说到了。
  • 更正 Hybrid-EP 的代价：上限（本页记作 P）压低以后，代价不再是空间，而是丢 token。超出上限的 token 会被丢掉，调用方要事后检查 handle 里的 overflow_flag（Hybrid-EP tests/test_hybrid_ep_token_drop.py:89-90）。所以第三条的取舍是“空间对丢 token 的风险”，正好和前两条“只付空间、不丢 token”形成对照，口述时说出这层对照更有区分度。
  • 三条结尾都写了“付出大缓冲区的代价”，可以合并成一句共性代价，再补一句：batch 要补齐到录好的 graph 档。
参考要点
  • 三个机制见验收 3 的参考要点。前两条只付空间、不丢 token；Hybrid-EP 的取舍是空间对丢 token 的风险，口述时把这层对照说出来更有区分度。
  • 三条共有的“预留显存”合并成一句共性代价，再补一句：batch 要补齐到录好的 graph 档。

正式练习

练习约定在 W2 学习验收记录·练习约定。

符号与名词

T
本卡这一步实际进入 MoE 的 token 数；prefill 每卡数千，decode 每卡数十。
M
每卡每步最多处理的 token 数，也就是通信 buffer 的容量；各库名字不同，见参数对照表。
N_recv
本卡实际收到的行数；按卡去重时，每个 (token, 本卡) 一行。
P
按本地专家展开并补齐之后交给 grouped GEMM 的总行数，不小于 N_recv。
R、K、H、E_local
EP 组大小（64）、每个 token 选的专家数（8）、隐藏维（7168）、每卡专家数（4）。
handle
dispatch 返回、combine 必须带回的布局信息，记录每一行从哪来、到哪去；像 C++ 里保存下来的迭代器，所指的 buffer 变了它就失效。
