7把“不能提前回收”写成一行可以核验的矩阵

对应单元四的 failure matrix 与 test design。先把已有真实测试拆成一行完整规格，再用同一方法组织其他故障；本段学习设计方法，不要求实现新的测试代码。

前面已经判断了超时、重复、peer 替换与租约的边界。现在要回答更具体的问题：如果有人修改了清理代码，我们怎样发现它把块提前归还，或者把该释放的资源永久留下？只写“测试网络异常，预期处理正确”还不够，因为没有指出异常发生在哪里、怎样控制时序，以及什么行为才算错误。

Failure matrix（故障矩阵）把每种故障对应的前置状态、注入位置、预期状态与验证依据放在一起。这里先完整展开一行：固定测试 test_recv_failure_waits_for_unpollable_handle_to_be_released。它使用一个请求、一项 handle 和一组目标块，刻意让状态查询失败、第一次释放也失败。

这一行必须交代什么本例的具体内容
前置状态／fixture请求 request 有接收 metadata 和 handle 101；目标块记录为 1、2、3。fixture 用 MagicMock 替代后端，不初始化真实设备。
注入点与事件顺序第一次 check_xfer_state 抛异常，随后 release_xfer_handle 也抛异常；下一次状态查询返回 DONE，释放返回成功。
中间必须保持的条件第一次查询后不把请求报告为结束或失败，不返回相应无效块，metadata 仍在。源码还要求无法释放的 handle 继续受追踪。
恢复条件后端允许按其合同结束该 handle 的追踪。不能把“又等了一会儿”或“心跳已收到”当作这个条件。
最终结果保留此前失败判定，同时报告 finished 与 failed；给出相应无效块。后续应收敛到无残留追踪，而不是无限保留。
证据层次与限制验证 worker 的状态、上报与清理规则。没有真实 RNIC，也没有真实 allocator／DMA 访问轨迹，不能直接证明物理内存从未提前复用。

这里的 fixture 就是测试预先搭好的对象、输入和依赖；不变量 是在每个相关中间状态都必须成立的条件。它们要具体到“哪个请求、哪个 handle、哪些块”，而不是只有一句“没有报错”。

下一轮的断言才检查 finished 与 failed 都包含请求、无效块集合正确，以及释放函数调用了两次。两次调用并不违反“引用只归还一次”：第一次释放失败，第二次才成功。函数尝试次数、成功归还次数、最终资源状态，是不同观察量。

如果测试只保留最终断言，那么一个“先错误释放、后又把集合凑正确”的实现也可能蒙混过关。反过来，只检查出错后资源还在，也不能发现以后一直没有回收的泄漏。因此每一行都应同时写清：危险阶段禁止发生什么，以及恢复条件满足后最终必须发生什么。

扩展到其他故障时，仍沿同一结构填写。例如 sibling handle 未结束时不能被另一 handle 的失败带着回收；peer 替换时，新描述建立与旧请求清理分别检查；重复通知要检查事件归属与只生效一次；租约回收要把软件到期策略与真实在途访问分开验证。已有测试覆盖了哪一部分，就只认领那一部分证据。

本例与 fixture：test_nixl_connector.py L2501–2538、L4527–4545；sibling 用例为 L4503–4524。handle 保留的源码依据：base_worker.py L3402–3499。均固定 d7ada3aace05，本节阅读代码与断言，未执行这些测试。

结论矩阵的一行应能回答：准备了什么、在哪一步制造什么故障、过程中什么不能发生、恢复后什么必须发生，以及这项检查究竟证明到哪一层。

8控制面事件与实际访问，要用不同观察点验证

继续测试设计：以心跳、在途访问和回收为主例，把之前的因果边界落实到观察与断言。

一个测试可以把时钟拨到租约截止点，并看到请求进入 done_sending；它检查的是软件计时与状态变更。另一个测试可能观察到旧写入已经排队，却还没有执行。两项观察并不矛盾，也不能由其中一项自动推出另一项。

同样，心跳是否被资源所有者及时处理，说明续期通道的情况；后台读写是否结束，说明数据访问的情况。心跳迟到不必然意味着旧访问还在进行，心跳及时也不必然意味着访问已经完成。测试应当能够独立控制这两条线，而不是把它们绑成一个 fake 返回值。

让时序可控测试可以使用可控的软件后端：提交操作先进入队列，只有测试明确推进时才执行相应访问；心跳交付、状态查询返回值和释放成败分别控制。这样可以安排指定的交错顺序，而不必靠 sleep 猜两个线程会不会碰巧撞在一起。若 fake 在状态报错时自动清空所有旧访问，就已经把“错误一定停止 I/O”偷偷写进测试，无法检验这一点。

真实内存安全检查也要明确观察点。只确认某个结果集合为空，不等于覆盖了 allocator 的所有复用路径；只看到最终数据正确，也可能遗漏期间发生过的非法复用。可以记录块归还与重新分配事件、访问结束事件和对应代际，在所测路径中核对它们的先后关系。数据内容检查用于发现串写等后果，但不能代替资源顺序检查。

同一条结论要分层取证下面三层可以逐步加深证据，不要求每个学习场景都有真实设备：

验证层能直接检查什么仍不能自动推出什么
mock 单元测试指定返回值／异常下的控制分支、追踪集合、调用与结果上报。真实 DMA 是否停止、内存池所有路径是否都遵守同一规则。
可控后端／受控集成把排队访问、清理和 allocator 连接起来，按指定顺序检查中间保护与最终收尾。模型里的“停止”必然与某款 RNIC／驱动的停止保证相同。
真实后端与设备验证在明确版本、配置和故障条件下观察实际完成、数据访问及资源复用，并核对接口合同。有限样本已证明所有平台、所有故障与所有调度顺序都安全。

一个具体 test design 至少应写出：版本与平台假设；请求、handle、块和数据模式等 fixture；故障注入的确切边界；可控的事件推进顺序；中间断言、恢复条件与最终断言；以及清理测试自身资源的方法。设备能力未知时，明确哪项需要后端合同或设备层观察，不把未知项填成“默认成立”。

检查 3 中的 peer 场景也按这个方法处理：新握手结果决定新请求可以使用哪套描述，旧请求的 handle／块关联决定旧资源何时允许清理。需要重试时，应重新建立对应尝试与有效资源的关联；“重新分配请求”不能直接改变已经提交给后端的旧操作。

分层方法是根据前述固定 source/test 边界整理的验证设计，不是新增的已执行结果。具体对照包括 peer 替换与释放失败测试、心跳／到期测试；本课现有证据仍限于源码阅读与明确设计。测试矩阵与最终工件会沿后续问答逐项整理。

结论把心跳、后台访问与资源回收分别观测、按身份关联，再检查中间保护和最终收尾。测试通过的表述必须与它实际观察到的层次一致。

检查 4测试断言与证明范围

一个测试使用可控的软件后端。P 的源 KV 区域 S 已就绪，D 的目标块 T 已分配并由本次传输保留。写任务已提交且被后端接受；测试暂时把它留在软件任务队列，尚未执行读取 S、写入 T。只有测试显式推进，才会执行这些访问。

心跳由 D 发给 P，用来续租仍需读取的源 KV 区域 S；心跳处理与写任务推进可以独立控制。除这次传输外，没有其他使用者持有 T。测试能够观察 handle／块关联、内存池归还与分配事件，以及结果上报次数。

本次运行中心跳已被 P 及时处理并完成续租，但该写任务尚未执行访存。随后状态查询报错，第一次释放 handle 也失败。测试最后推进该写任务完成访存，再让释放成功，并观察到请求同时进入 finished_recving 和 failed_recving。现有测试只断言了这两个最终集合。

  1. 这些最终断言是否足以同时验证“不提前复用”和“最终能够回收”？还需要补哪些中间状态与回收断言？说明心跳状态在这个判断中能提供什么、不能替代什么。
  2. 补齐这些断言后，证明范围到了哪一层？还有哪类真实 RNIC 或设备保证不能据此宣称已经验证？

参考要点

最终集合不足以证明整个过程安全。在旧写未结束、释放失败时，应检查 handle 与块关联仍在，T 仍受本次传输保护，没有回池或分配给新请求，也没有发布成功可消费的结果；对固定 worker 的相应接口，还要检查终结上报没有提前发生。

访问按后端合同结束、释放成功且其他引用已解除后，检查资源最终收尾，T 的成功归还只发生一次，追踪不残留，后续不重复终结上报。释放函数可以先失败再重试，调用两次不等于成功归还了两份引用。心跳只提供源 KV 续租信息，不替代访存结束依据。

这些断言支持受控软件后端与所建集成模型下的控制／资源逻辑，不能代替真实 RNIC 的取消、停止访问、可见性和故障行为保证；真实平台还需对应接口合同与明确条件下的验证。

9失败结果回到调度器以后，怎样继续或结束请求

把前面的资源条件接回真实 Scheduler。对应 worker 的结果输出、Scheduler._handle_failed_recving 和 KV load failure policy；随后用故障矩阵汇总验证。

前面已经确定什么时候允许 worker 结束这次传输追踪。再向上一层看：D 收到失败接收结果后，能否继续使用这些 KV？如果不能，是结束请求，还是重新计算？这属于调度器的恢复策略，不能靠传输线程自行把 failed 改回成功。

固定配置项 kv_load_failure_policy 有 fail 和 recompute，默认是 fail。在本节选定的请求级失败接收路径中：

策略固定实现中的行为需要理解的取舍
fail以 FINISHED_ERROR 结束相应请求，执行请求清理。把失败明确返回上层；不试图在该路径中恢复这一请求的计算。
recompute对等待远端 KV 的失败请求，将 num_computed_tokens 置为 0，并允许后续重新调度。重新获得有效 KV 要付出计算与排队成本；这不是再发送一次同样的网络请求。
if self.recompute_kv_load_failures:
    request.num_computed_tokens = 0
    self.failed_recving_kv_req_ids.add(req_id)

Scheduler._handle_failed_recving，scheduler.py L3442–3444；前提为请求存在且处于 WAITING_FOR_REMOTE_KVS。固定 d7ada3aace05。

test_failed_receive_completion_honors_failure_policy 分别设置两种策略：fail 分支要求请求错误结束、从调度器移除并恢复块池数量；recompute 分支要求已计算进度清零，并在下一次 schedule 中再次出现该请求。这验证了收到失败结果后的调度行为，不能证明 worker 在此之前已让真实 DMA 停止。

本节只描述请求级 failed_recving 路径。其他按无效块处理的分支可能保留可用前缀，因此不能由这里推导出“所有 KV load failure 都必须重算全部 Token”。多 cache group 也不能随意用扁平块 ID 映射请求，需按该实现的请求级错误合同处理。

固定依据：kv_transfer.py L88–92；ModelRunner 输出衔接 L94 起；scheduler.py L3432–3445、L2396–2408；恢复策略测试 L38–70。均为源码／测试阅读，未在本课执行。

结论传输后端解决本次访问的完成与清理，调度器决定业务请求如何恢复或结束。两层通过明确的失败结果衔接；重算、网络重试与旧资源清理是不同动作。

10把已讲的异常路径整理成验证矩阵

以下把前面讨论的故障、断言与固定来源汇成技术草案。它保留了已有实现与拟议设计的区别；后续 Change Card 根据选定的设备能力引用和收敛这些条目。

矩阵中“现有断言”表示源码里的测试要求，不表示本课已经运行测试。“设计要求”表示需要由协议或后续验证满足的性质，不把它冒充固定版本已具备的能力。

展开：一个具体的 B 级受控测试设计

目标与范围。针对 F1，连接固定 worker、可控软件访存队列及单槽资源池模型，验证中间保护与最终收尾。它是拟新增的受控集成设计，不是已存在或已运行的测试，也不代替真实 scheduler／RNIC 集成证明。

Fixture。以 recv_worker fixture 的 recv_worker 为构造参考，做一个单块变式：非 HMA，请求 R，handle 101，目标 T 对应块 ID 1，metadata 的 local_block_ids=([1],)，本用例 remote=None，只测试本地接收清理。将原 fixture 的 request 条目替换为 R，仅保留该请求，接收 handle 列表为 [101]；预置 _pending_recv_notifs["R"] = [("producer", b"R:1")]，核对失败时丢弃待通知项而不发送成功通知。因此预期无效块集合是 {1}，与原测试的三块输入分别陈述。

S、T 各取 4096 byte 软件缓冲区，S 填 0xA5，T 已分配给 R，除此没有其他 T 使用者。队列只有显式 advance_io 才读 S、写 T；状态查询、释放返回及独立 P 端租约桩分别控制。单槽池占用时拒绝新分配；安全收尾后复用 T 并写入 0x5A，再排空剩余事件观察残留写入。advance_io 是测试控制点，不是真实通信 API；这一字节缓冲模型不验证 attention 的 KV 布局。

实现时使用能导入固定 worker 与其测试依赖的环境，尚未创建或运行这个用例。该 fixture 只服务于已记录失败的收尾分支；若增加正常成功对照，需要另行准备合法 remote metadata，不能直接沿用 remote=None。

可重复事件顺序。使用事件序号及可控时钟，不靠 sleep 猜竞态：

  1. 提交并受理操作，保持访存队列未推进；处理一条有效心跳，确认 P 的源保留状态已续期。
  2. 让状态查询抛异常，第一次 release 抛异常，调用真实 worker 的 get_transfer_results()。
  3. 此时尝试分配新请求，记录结果；仍不推进旧访存。
  4. 显式完成该次访存，把下一次状态查询设为 DONE、release 设为成功，再查询 worker。资源池适配器收到终结结果后处理归还；它不额外替 worker 隐藏提前终结。
  5. 再次轮询，复用 T 并写入新模式，耗尽模型中剩余事件，检查没有旧写或旧结果重复生效。

必须观察及断言。记录 (请求、handle、块、分配代际、事件序号)，同时观察返回集合和资源池事件：

  • 步骤 2–3：handle／块关联与必要引用保留，T 没有回池或分给新请求；finished、failed、无效块结果与该固定失败路径的预期一致，不能发布成功可消费。心跳续期记录不代替访存结束记录。
  • 步骤 4：只有指定访问已经结束、release 成功后才允许收尾；报告 finished＋failed，成功通知不发送，待通知项与追踪清除，T 成功归还一次。第一次失败、第二次成功的两次 release 调用，不等于两次成功归还。
  • 步骤 5：终结上报不重复，引用不重复归还，无遗留 handle／metadata；T 的新模式不被残留模型写入覆盖。最终集合正确不能替代步骤 2–3 的中间断言。
  • 测试退出时确认队列为空并释放测试资源；异常退出也由 harness 收尾，不把测试自身泄漏误认为被测逻辑结果。

判据与边界。任一中间保护或最终收敛断言不满足即失败；通过仅支持该受控模型下的逻辑；本用例不替代 F3 的重复通知注入。真实 RNIC 的取消、停止访问、完成与可见性仍需对应版本的合同及设备层证据。没有可靠停止手段时，应明确“无法保证安全复用”，不能把无限等待伪装成恢复成功，也不能用更长 TTL 代替证明。

将矩阵接入方案时，先明确首版使用哪种通路和错误策略，再把不适用的分支标出；保留其中的正确性约束与待验证条件。实际平台的内存注册、拷贝完成和停止访问能力只能来自已确认事实，不能从某个函数名、默认配置或其他通信项目推断。

结论一份可审查的方案要把路径、错误处理、资源生命周期与验证放在同一套假设下。已有证据可以复用，未验证的后端保证则明确留下。

11两条适配分支，共用什么契约，分别补什么能力

对应 Change Card 的平台能力、改造边界和生命周期。完整九段内容见Change Card 03，共用验证规格见故障矩阵与测试设计。

现在把目标定义为：目标平台基础推理已能正确执行，我们为它接入 PD/KV 交接。P/D 使用相同模型、TP、cache 表示、dtype、布局与 block size。两条分支都由 D 侧 CPU 发起 PULL／READ，数据从 P 流向 D；采用哪条数据路径，不改变这一控制方向。

已有 platform hook 能声明设备／buffer 组合和 NIXL memory type，但目标显存如何被 native backend 识别、注册、导出并供 RNIC 访问，可能仍需要底层适配。固定直传路径也没有一个覆盖任意设备的通用同步 hook；生产与消费依赖表达不够时，需要评估 connector／worker 扩展，不能仅靠支持表完成接入。

Host 分支可以复用网络对 DRAM 的支持，但新增的复制不是“调用返回就万事大吉”。平台回调必须保持块索引、布局和既定完成语义；若要改为异步，就要把相应 event 或其他等待条件传到消费和回收处，或者先维持可满足原合同的同步调用方式。

本卡已选定的策略是显式配置 A 或 B，并在启动时验证该路径；不满足就报错，不静默换成另一条路径，也不加入 Host TCP/socket。已确认加载失败、旧访问按合同收尾后，业务层采用 fail。这项选择不会让未知状态的旧访问自动消失。

固定 vLLM d7ada3aace05：平台 hook L1410–1420；实际注册、Host copy 与接收同步 L1514–1630、L1870–1872、L2981–3037、L3337–3344；READ 提交 L554–567。两分支是条件设计，没有据此声明某款实际芯片已完成适配。

结论共用的是框架对请求、数据和生命周期的要求；两分支的工作差别落在实际注册区域、底层访问能力、copy 与完成依赖上。改造在哪一层，由具体缺口决定。

12把异常责任从 PULL 对照到 PUSH

本卡首版仍为 PULL；这里补齐 W3 的 PULL／PUSH 异常职责对照，不将 PUSH 加入首版平台接入范围。

PULL 由 D 发起 READ，D 持有本地读取 handle，P 按通知与协议保留源数据。PUSH 则先由 D 准备目标并发布 PUSH_REG 接收资源信息，P 再发起 WRITE，handle 放在 P 的 _sending_transfers 中；D 主要根据预期写入方的完成通知推进接收。

比较项PULLPUSH
谁持有主要传输 handleD 的 READ 侧。P 的 WRITE 侧。
源区释放的本次访问依据P 需按读取方通知与协议判断源访问结束。P 的正常 WRITE 完成可解除本次发送的源读取依赖；不等于 D 已完成计算。
目标区的保护D 不能在旧读取仍可能写入时复用目标。D 即使没有 P 的 WRITE handle，也不能在旧写仍可能到达时复用目标。

固定 PUSH 实现会记录 _send_failures，避免一个失败 WRITE 被后来成功的 sibling “洗成”整请求成功。无法释放的 handle 继续保留；即使 handle 都已退出追踪，失败请求也不会走正常成功发送分支，而是保留租约跟踪。后续到期进入 finished_sending 是策略终结，不能解释成 KV 已成功交付。

D 也不能因注册消息发送报错就立即回收目标：向多个 agent 发布信息时，前面的发送可能已触发 WRITE。固定代码在这种部分发送失败情形下保留接收 pending。注册 watchdog（调度路径中检查超时的逻辑）删除注册跟踪项，不代表它取消了已发出的 WRITE，或已经完成跨端失败传播。

固定依据：push_worker.py L399–411、L734–847；注册 watchdog L303–327。测试见 test_nixl_push_connector.py L984–1050、L294–327。它们提供本地控制逻辑依据，不补出不存在的 failed_sending 字段，也不证明完整的 D 端失败终结或真实旧写停止；对应待验证项已写入技术矩阵 F8；完整异常状态机分别标出两种模式的责任与待验证边界。

结论两种方向共用资源安全要求，但完成依据与观察者不同。将 PULL 的错误处理迁到 PUSH 时，要重新标出谁持 handle、谁知晓失败、谁拥有目标区域，以及跨端通知能提供什么保证。

导师串讲：把数据路径、失败处理与适配验证接成一个方案

仍沿一条请求：P 完成 prefill 后保留对应 KV，D 为它安排目标块，双方已经核对模型、布局、分片和请求归属。以本卡 PULL 为基线，D 发起读取，数据从 P 流向 D；服务地址或一个内存类型标签都不能代替有效的实例身份与注册描述。

选 A，就需要 native backend 真实访问两端设备内存，并把 P 的生产完成、D 的接收可见性与计算依赖接好。选 B，则让网络访问两端 Host 区域，在前后增加设备拷贝；这降低了网络直接访问目标显存的要求，同时增加 Host 容量、copy 与同步成本。两条路径都要按实际读取者分别保护源、目标和中转区域。

传输成功以后，结果要对应本次请求与尝试，并完成所需后处理，才允许 D 消费。请求失败或等待超时以后，业务可以不再需要结果，但旧访问可能还要继续清理。handle、块关联、peer 描述和引用必须保留到各自条件满足；重复／迟到事件既不能再次归还同一引用，也不能替新尝试完成。

进程与 lease 再增加一层边界：同一地址可能换了实例，同一 ID 的注册描述也可能变化；成功确认新映射不直接结束旧资源责任。心跳与到期决定软件保留策略，旧内存访问是否结束仍需自己的依据。当前源码与 mock 测试能支持到哪一步，就把结论写到哪一步。

如果最终确认加载失败，本卡采用 fail，由调度器结束请求；它不会自动重算、网络重试或切换 A/B。PUSH 对照也保持同样的安全要求，但主要 WRITE handle 在 P，D 的接收与目标回收还需要独立的跨端合同。

回到真实规模，上一课 Qwen3-8B 算例的一份全模型 BF16 KV，在 36 层、8 个 KV 头、head_dim 128、8192 个位置下合计 1.125 GiB；不含额外副本、padding 或共享前缀扣除，并非每个 rank 都固定这么多。中转池、网络和执行队列要处理的是实际分片与并发量，不能只凭一个理想带宽数判断首 Token 延迟或吞吐。

因此验证也要分层：先用明确的 source/test 对应检查控制规则，再通过受控后端把访存、清理和 allocator 连起来，最后在实际平台验证注册、取消／停止访问、可见性和性能。技术矩阵与测试规格规定具体观察；Change Card记录所选边界、改造层次与未验证条件。没有执行的部分继续保持设计层表述。

规模沿用单元二固定 Qwen3-8B 算例，数值已在前课按张量形状用 Python 核算；本段没有新增带宽或设备性能测量。正常生命周期和失败依据分别复用前三课与本课的固定版本说明。

综合核验

用一个注册区域重建的迁移场景评审两条适配分支。这里不要求把在线扩容加入首版实现，也不要求无停顿切换；只检查实际内存、注册描述和资源依赖能否保持一致。

综合核验 1注册重建与生命周期

沿用本卡的 PULL、显式选路和 fail 策略。分别考虑两个维护场景：A 中 P、D 两端的设备 KV pool 重新分配；B 中两端的 Host transfer pool 重新分配。新地址不同且不在旧注册描述的范围内，设备与可注册内存类型不变；模型、dtype、shape、布局和逻辑 block ID 也不变。

新区域的内容与逻辑映射可以在启用前正确准备。旧 handle 仍可能访问旧地址，B 还可能有读取旧 Host 区域的设备拷贝。工程师想只替换 Python 引用、继续使用旧 NIXL 描述，因为“shape 没变”。允许暂停所有相关的新计算、拷贝和传输，等待旧引用结束；不要求无停顿切换。

综合核验 2题意澄清后的注册判断

明确采用设备直传：D 的 CPU 发起 PULL／READ，KV 从 P 的设备源区 S 经 RNIC／网络直接进入 D 的设备目标区 T；没有 Host 中转，也没有 D2H／H2D。

S 的地址、注册及其有效性均不变。只有 D 把目标改为新区域 T_new：它的地址不同，尚未被现有有效注册覆盖，但仍属于后端已支持的设备和内存类型。旧 handle 还可能写入旧 T；允许暂停相关新使用，等待旧操作与其他引用结束。

参考要点

这是一条由 D 发起的 READ。本地接收描述应指向 D 的设备目标区 T_new，远端源描述仍指向 P 的设备源区 S；数据从 P 流向 D。按单次 verbs READ 表达，本地地址／lkey 对应接收区域，远端地址／rkey 对应读取源，具体 key 由实际后端管理。

题设保证 S 的地址、注册及有效性不变，因此其注册与远端源描述可以沿用。T_new 尚未被有效注册覆盖，需要先建立覆盖新区域且权限满足本地接收写入要求的有效注册，再让新操作使用匹配 T_new 的本地描述；仅改变 Python 引用或地址字段不足以建立注册条件。引用旧 T 的预备传输描述也应更新，具体 API 服从后端合同。

旧 T 只有在旧操作已不再写入它、计算消费者及其他引用也已结束后才能回收；判断依据是旧 T 自己的依赖，无须机械等待写入 T_new 的新传输结束。共享 pool 或 MR 仍服务其他区域时，不能因旧 T 不再使用就销毁整份注册。本场景没有 Host 中转，不需要新增 D2H／H2D。

符号与名词

传输句柄 handle
后端用来查询和管理一项传输的软件入口；句柄、传输所访问的内存、请求是否还能交付结果，是不同对象与状态。
等待超时、取消请求、停止访问
分别表示等待期限已过、已提出停止要求、旧操作已不再访问相关内存；三者不能仅凭名称互相替代。
finished_recving、failed_recving
固定 connector 的终结结果集合与失败接收集合；失败接收也进入 finished，以便结束传输等待，但不能因此消费无效 KV。
mock／MagicMock
用可控制返回值或异常的软件对象代替真实依赖，适合验证分支与状态规则；不会自行验证真实网卡、DMA 或设备内存行为。
幂等处理
同一个有效事件重复处理，不重复改变完成状态、扣减引用或执行一次性动作；需要明确事件身份与作用范围。
逻辑请求、传输尝试、块代际
分别标识业务目标、某一次执行，以及同一物理存储的某一次分配；名称或字段可以不同，但不能混淆对应关系。
registration_generation
本课固定 NIXL 实现中的注册元数据版本，不等同于每次传输重试的 attempt 或每个 KV block 的复用代际。
peer、endpoint、engine_id
peer 是参与交接的另一引擎；endpoint 是 host／port 入口；engine_id 是实现用于识别引擎的标识，其跨重启唯一性仍取决于生成与配置规则。
lease、heartbeat、TTL
租约为保留／使用资源约定期限；本例心跳请求续期；TTL 是有效期时长。计时状态不自动等于设备访问已停止。
时钟域与截止点
截止点依赖计算它的时钟；跨机器使用本地单调时钟值时，需要明确转换、偏移及误差条件。
failure matrix、fixture、不变量
故障矩阵把注入与预期行为对应起来；fixture 是测试搭好的对象和输入；不变量是在相关中间状态必须保持的条件。
可控软件后端
由测试控制访问开始／结束、返回值和故障顺序的后端模型；可验证模型下的控制与资源逻辑，不等同真实 RNIC。
