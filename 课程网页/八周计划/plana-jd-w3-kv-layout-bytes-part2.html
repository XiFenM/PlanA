5DCP：把同一个 KV 头的历史位置分给不同 rank

对应主线第 2 项的 DCP；先读本节的数据分工，再对照固定版 Context Parallel Deployment 的 Decode Context Parallel 小节。具体计算路径以本节所引 FlashAttention backend 为准。

回到 Qwen3-8B 的 TP=16 配置。32 个 Q heads 分到 16 个 rank，每个 rank 两个 Q heads；8 个 KV heads 各有两份副本。rank 0、1 都需要 KV head 0，因为它们分别处理该组中的 Q heads 0–1 和 2–3。在一次调用开始前，假设这条请求已缓存 T=8192 个历史位置，两张卡都为同一个 KV 头保存了完整的历史。

如果希望减少这部分复制，可以把 head 0 的历史位置再分给 rank 0、1：一个保留一部分位置，另一个保留剩下的位置。这样每张卡仍使用完整的 128 维头向量，只是拥有的历史位置变少。这就是本例的 decode context parallel，简称 DCP。DCP=2 复用已有 TP ranks，组成 (0,1)、(2,3)…(14,15) 八个组，不额外增加设备。

先固定交错粒度 i=1：按位置轮流保存。图中只画最前面的 8 个历史位置，整个 8192 位置序列沿相同规律继续。K 与 V 使用同一个位置分工。

沿用 36 层、BF16 cache 和每头 128 维，本例每 rank 的有效 KV 从 144 MiB 降到 72 MiB，16 个 rank 合计从 2.25 GiB 降到 1.125 GiB，均按形状用 Python 核算。这个收益来自去掉副本，不包含分页空位。新位置继续按交错规则写入，不需要每一步把全部历史重新切分。

设 DCP 组大小为 c，交错粒度 i 表示每次连续分配给一个 rank 的位置数；t 从 0 开始。某位置的 owner 与该 owner 内的紧凑逻辑位置可以写成：

物理地址还要再经过本地 block table。固定实现对不属于本 rank 的新位置给出 PAD_ID，缓存写入据此跳过。全局长度也不能直接充当每张卡的本地长度：i=1、c=2、T=8193 时，两端分别保存 4097 和 4096 个位置。

为什么还要通信rank 0 的查询不能只看偶数历史位置，否则模型已经换成了另一种 attention。原来在本地可见的完整历史，现在分在两张卡上；系统需要让两边都计算这组查询对本地历史的贡献，再合成为全历史结果。

你在 FlashAttention 中见过“分块计算后修正 softmax 分母”。这里是同一个数学问题，只是历史块放到了不同设备。对于同一个查询头，令 j 表示一个历史分片，st=qkt⊤/ds_t=qk_t^\top/\sqrt dst​=qkt⊤​/d​ 是位置 t 的分数，Zj=∑t∈jestZ_j=\sum_{t\in j}e^{s_t}Zj​=∑t∈j​est​ 是本片的 softmax 分母，λj=log⁡Zj\lambda_j=\log Z_jλj​=logZj​ 就是这里的 LSE。局部输出 Oⱼ 已经除过自己的 Zⱼ，合并时要按各片的分母重新加权：

这两个权重取决于查询与键的相关分数。分片中有多少 Token，并不能单独决定它在全局 softmax 中占多少权重。实现保存 LSE，便于稳定地合并；不需要显式算出可能很大的 Zⱼ。

vLLM d7ada3aace05：本地长度与 slot 归属；Q all-gather、同文件 历史与本次输入区域的计算及合并；默认 ag_rs 合并与 reduce-scatter。公式是这些分片共享的数学依赖，不展开 kernel 内部算法。

边界本例减少 KV 容量，代价是每步的查询交换与结果合并，是否改善延迟要看工作负载和通信条件。该版本普通 GQA 还要求 TP 大于 KV heads、DCP 不超过复制倍数，并满足头数与组大小的整除条件；支持 DCP 的 backend 也有设备条件。它的 NIXL 跨实例限制见下一节点，不能从单实例 attention 路径直接推定。

结论DCP 在本例中沿历史位置拆开原来的 KV 副本；完整 attention 依赖因此跨越设备。需要一起改变的包括位置归属、本地长度、查询分发和带归一化信息的结果合并。

6PCP：分摊 prefill 计算，不等于按同样方式保存缓存

对应主线第 2 项的 PCP 与 metadata；本节先看分工，再对照 PCPManager 与 cache inputs 的 gather。MLA 具体保留的张量将在专门节点展开。

prefill 有许多新输入位置，可以把不同位置上的工作分给不同设备。PCP（prefill context parallel）首先解决的是这部分计算的分工。在 TP 之外加入 PCP 轴，会增加参与模型实例的进程数；只看 PP、TP、PCP 三个轴，该固定版本的 world size 是它们的乘积。DCP 则在既有设备组中进一步安排 decode KV 的位置分工。

先从数学接口看 PCP：一批新输入 X 的行代表不同 Token，把这些行分给两个 PCP rank 后，它们分别计算自己位置的查询。可是后面的查询仍可能依赖前面位置的 K/V。因此，谁计算某些 Q，不能直接决定这个 rank 只保存相同位置的历史状态。计算分工和长期缓存布局要分别设计。

真实系统这个固定版本的 PCP runtime 限于 MLA；MLA 是后面要专门学习的压缩注意力表示，所以不把前面的 Qwen GQA 例子当作 PCP 已支持的运行配置。这里把 MLA 在某个位置实际需要保存的状态暂记为 R[t]，先只追踪位置，不套普通 K/V 的字节量公式。

源码按 2 × PCP 个段做头尾配对，因为靠后的查询通常要读更长的因果前缀。模型计算结束后，再收集并按原位置恢复 hidden states，交给 sampling。这个按 Token 位置恢复输出的过程，与前一页 TP 在 Wo 之后对部分投影求和，也属于不同的合并。

进入 decode 后，PCP-only 的每个 PCP rank 都有完整历史，因此一条请求可以交给其中一个 owner 负责该步的计算。它新生成的缓存输入仍会传给其他 PCP ranks，让副本继续完整。这里并不是到 prefill/decode 边界才突然重拼整个历史缓存。若采用 DCP 把历史真正分成几份，那么一条请求的 attention 就需要这些分片共同参与，不能继续依据“另一张卡也有完整副本”安排计算。

固定源码：prefill 分段与 decode owner；gather 新 cache inputs 维持副本；slot 对齐和 hidden states 恢复。源码中的 MLA 限制见同文件 配置核验；PCP+DCP 在此 runner 中进一步限于 sparse MLA。

把 CP 放回 PD 交接，上一页的“请求、层、KV 头”之外，还要明确源 rank 保存哪些全局位置、它们在本地如何编号，以及 D 要写到哪个位置和物理块。同一个“本地第 7 项”，在两种交错布局下可能对应不同的全局 Token；数据量相等并不能证明映射正确。

例如 DCP=2、物理 block size=16 时，一组对应的本地块可覆盖 32 个全局位置；当 i=1，两端各保存其中 16 个交错位置。物理块里的存储容量和调度层看到的全局位置跨度因而不是一个数。metadata 需要保留或推导 DCP 组、interleave、本地长度与 block table 等关系，不能只把全局序列长度交给本地读取代码。

实现边界本课固定版本的 NIXL PULL 对 DCP>1 限于 MLA，并限制受支持的 DCP 分组；PUSH 直接拒绝 DCP>1。PCP>1 的 NIXL 路径限 producer，consumer 要 PCP=1。因此本节解释的分工是判断交接所需条件的依据，Qwen 的单实例 GQA DCP 能力不等同于该版本 NIXL 的端到端能力。真实 MLA 缓存与交接时再具体对应这些支持组合。

NIXL 限制：PULL/DCP 模型与分组检查；PCP producer/consumer 约束、同文件 PUSH 的 DCP 检查。节点 5 的 i=1 是明确选择的教学配置，不代表 NIXL 自动选择的交错粒度。

结论PCP 的查询计算分工、DCP 的历史存储分工和 PD 的跨实例交接需要逐项对应。判断每个 rank 要存多少、算什么、从哪里接收数据时，先看它实际拥有的状态与依赖，再看实现是否支持这个组合。

补充：两张卡互相需要 KV，为什么仍能并行

这里要把“生成本层的缓存状态”和“算出本层 attention 输出”分开。rank 1 的第 1、2 段需要第 0 段的本层 K/V，rank 0 的第 3 段也需要第 1、2 段的本层 K/V；但生成这些 K/V，本身不需要先得到这些段的本层 attention 输出。

用 ℓ 表示层号，t 表示一个 Token 的全局位置。进入本层时，位置 t 已经有本层输入 XtℓX_t^{\ell}Xtℓ​；第一层来自已知 prompt 的 embedding，后续层来自前一层的结果。查询和可缓存状态都可以先从本地输入生成：

Qtℓ=fQ(Xtℓ),Rtℓ=fR(Xtℓ)Q_t^{\ell}=f_Q(X_t^{\ell}),\qquad R_t^{\ell}=f_R(X_t^{\ell})Qtℓ​=fQ​(Xtℓ​),Rtℓ​=fR​(Xtℓ​)

fQf_QfQ​、fRf_RfR​ 表示投影及所需的逐位置变换。普通 attention 的 R 是准备好的 K/V；本课固定 MLA 路径的 R 是它实际保存的缓存状态。这里两者有相同的关键依赖：R 来自本层输入，不来自本层 attention 输出。注意力输出随后才用本位置的 Q，读取因果范围内各位置的 R。

因此，因果 attention 的约束是“某位置的查询不能使用未来位置的信息”，并不要求“同一层必须先算完前一个位置的输出，再计算后一个位置”。prefill 的整段输入 Token 已知，所以同层可以先并行准备各位置的查询和缓存状态。decode 中尚未生成的未来 Token 没有输入，这才形成了跨生成步的先后依赖。

通信成本仍然存在。在这里的 gather 路径中，一端的投影或传输较慢，会延后相关数据的消费；每层还要付出缓存交换等成本。PCP 把查询位置上的计算分摊出去，能否获得净收益，要比较节省的计算时间与新增通信、同步、负载不均衡的代价，不能只用卡数预测加速比。

固定 vLLM d7ada3aace05：本地 projection、norm、RoPE 后调用 attention；先 gather cache inputs，再更新 cache；cache update 在 attention 前的依赖。交换的是缓存输入，不是其他段的本层 attention 输出；MLA 的具体表示仍留在专门节点。

参考要点

DCP 中每个 rank 只有一部分历史位置。修改本地长度不能创造远端 K/V，反而可能把不属于本地有效历史的槽位当作有效输入。若不取回远端数据，就需要各历史分片共同计算，并把贡献正确合并。

局部输出已经使用各自的 softmax 分母归一化。全局合并需要各分片的 LSE，以恢复局部分母占全局分母的比例，再加权局部输出。Token 数只描述分片长度，无法决定查询与这些键的分数总质量；仅按长度加权不能保证正确。

7一个 Token 的增加，为什么可能占用一整个新块

对应主线第 1、3 项的字节量口径；先读本节，再对照 AttentionSpec 的 page size 与 NIXL descriptor。分页读取的完整调用链在后续节点展开。

继续使用 Qwen3-8B 的普通 GQA 主例，但先固定 P/D 都是 TP=4：36 层、8 个 KV 头、每头 128 维，KV cache 为 BF16。每个 rank 保存两个 KV 头。没有 PP、CP、前缀共享、额外页对齐或预留块，每个物理块容纳 S=16 个位置。现在请求从 T=8192 个已缓存位置增加到 8193 个，系统增加了多少数据，又需要占用多少块？

真实系统固定 AttentionSpec 分别保存本地 KV heads、头维、cache dtype 和 block size。普通 dense 情况下，它按头数、存储位置数和每个 K/V 状态的字节数计算一页；如果缓存规划或 backend 对该 spec 设置 page_size_padded，则使用 padding 后的物理页尺寸。这可以用于统一不同缓存规格的 page，不能只理解为硬件对齐；它与图中的尾块空槽需要分别计数，详细用法见本节点补充。

传输还要再看第三个量：这次到底选中了哪些块。这里把传输库搬运的 KV 数据片段称为 payload，不包含网卡协议头和控制消息。固定 NIXL 路径用 block ID 选择已注册的 descriptors；本例的 descriptor 长度是完整块的 region 长度，不因尾块只有一个有效 Token 自动变短。

因此，若本次明确选中全部 513 个块、传输所有 36 层、每个 head 分片恰好传一次，且无命中、重试或额外页对齐，每个 rank 的 KV payload 才等于 302,579,712 B。若 D 已有部分前缀，可以少选块；若发生重复读取或重试，累计搬运又可能更多。请求长度本身不足以裁定本次传输了多少。

传输依据：descriptor 的长度与块步长；按块选择 descriptors 并准备 READ；请求待接收的块集合。

结论有效 KV 按实际元素算，占用容量按分配块算，传输 payload 按被选择并实际搬运的片段算。这三个量在明确条件下可以相等，但不能互相代替。

补充：page_size_padded 怎样改变物理页

先把本节的“页内对齐”说法补准：page_size_padded 不只用于硬件对齐。它是 KV cache spec 中可选的物理页字节尺寸，通常由缓存规划或平台逻辑设置，用来协调不同缓存规格。默认值是 None；前面的普通 Qwen 主例没有凭空加入这项 padding。

固定源码中的规划函数 unify_kv_cache_spec_page_size 会尝试统一一组 spec 的 page 大小。已经相同就不改；较小 page 能整除最大 page 时，优先增大那一层的 block_size。对于不满足整除关系的普通非 MLA attention，这条路径保持 block_size，改设 page_size_padded。Mamba 的状态大小不随 block_size 增长，也可能走 pad page 的分支。其他 grouping 和 packed layout 仍有各自约束，不能把这条路径推广到所有异构模型。

一个现有回归测试给了具体例子：target 与 draft 的某层都只有一个 KV head、BF16、block_size=16，但 head_dim 分别为 192 与 128。target 每页内容是 12 KiB，draft 是 8 KiB。下面固定为 LBHNC 的逐层存储，没有额外 block stride 对齐或跨层交错。12/8 不是整数倍，这条规划路径把 draft 的物理 page 设为 12 KiB，其内容形状和 16 个 Token 槽位都不变。

使用这个字段时，后续的 page_size_bytes 返回 padded 值，并检查它不小于内容尺寸；layout 计算把它反映到 stride，再用 as_strided 建立张量视图。在上述布局前提下，draft 的缓存仍可表示为 [num_blocks,1,16,256] 的 BF16 视图，但相邻块相隔 12 KiB。访问下一页时如果还按 8 KiB 推进，就会落到错误的存储位置。这也解释了为什么节点 9 的 slot 编号不能直接当字节地址。

每块占用字节增加；相同内存预算能容纳的 pool blocks 通常减少，具体按分组／layout 的实际计费计算。

因此它不是独立的“多预留几个 Token”开关。还有单独的 block_stride_alignment 可能进一步改变物理块步长，排查占用或地址时要看最终 spec、layout 和 tensor stride。

补充：推测解码的预留、使用、失效与归还

推测解码中，drafter 先提出若干候选 Token，target 模型批量验证；接受的是候选的连续前缀。这里先区分两个范围：target 本轮实际要处理的 Token 已计入 num_new_tokens，其中包括本轮待验证候选；num_lookahead_tokens 是在这个查询范围以外，为有缓存状态的 drafter 后续写入留出的容量。它不是把本轮候选数量再算一遍。

设 C 是已计算前缀长度，Nnew 是 target 本轮调度的位置数，Nlook 是额外 lookahead，Nmax 是最大模型长度。本课固定 manager 使用的容量目标是：

Nneed=min⁡(C+Nnew+Nlook,Nmax⁡)N_{\mathrm{need}}=\min(C+N_{\mathrm{new}}+N_{\mathrm{look}},N_{\max})Nneed​=min(C+Nnew​+Nlook​,Nmax​)

在本节普通 FullAttention、无共享等额外情况的模型下，再把 Nneed 除以 block_size 向上取整，与请求已经持有的块数比较，补足不足部分。已有尾块能容纳预留位置时，就不一定再增加物理块。

lookahead 大小由 proposer 路径决定。固定版本中，EAGLE／使用 draft model 的路径通常取配置的候选数量 k；DFlash 和 DSpark 的 fill-in 路径取 k+1；不需要这类 KV 余量的某些方法返回 0。具体仍要看本轮传给分配器的有效参数，不能把这些值当作所有版本、所有方法的统一规则。

下面沿一轮跨块例子看完整过程。限定普通 FullAttention、block_size=16、同步单步验证、无共享；起点有 C=27 个已计算位置，并只持有两个块。位置 27 是上一轮已采样、但 target 尚未处理的 Token；drafter 提出四个候选，位置为 28–31。本例取 Nlook=4。

使用时如何避免读到被拒绝的数据？系统纠正 CPU／GPU 上的已计算位置数，下一轮据此形成 positions、有效序列长度与 slot mapping。它不依赖把旧字节全部清零：被拒绝位置先失去有效前缀身份，再在需要时被正确的新 Token 状态覆盖。未验证候选也不会作为可靠的 prefix-cache 命中内容对其他请求发布；“写进设备 KV”与“登记为可复用前缀”是两件事。

什么时候真的回收？普通 FullAttention 的 allocate_new_blocks 在已有块足够时直接返回，并不顺手缩短请求的块列表。因此拒绝候选后，尾块通常仍归该请求持有。请求释放时，引用计数下降，达到可复用条件的块回到 free queue；这表示池可以重新分配这些块，不是把整片 GPU cache pool 交还给系统。

保留尾块可以直接复用容量，但有效 KV 变少不代表请求当下持有的显存也立刻变少。容量评估要统计实际拥有的 blocks，而不能每步只用 ceil(有效前缀长度 / block_size) 反推。滑窗、Mamba、异步执行和特殊状态管理有另外的回收规则，本段不替它们作统一结论。

8从 payload 到传输时间：带宽属于哪一条路径

对应主线第 3 项的理想传输下界；以下是由字节量和明确带宽预算推导的模型，不是硬件 benchmark。

沿用刚才的 8193 位置请求，并采用已经写明的“全部 513 个块恰好搬一次”条件。四个 rank 各搬运 302,579,712 B，总 payload 为 1,210,318,848 B。现在给一个教学用的有效带宽预算：25 GB/s，其中 1 GB = 10⁹ byte。这里的有效带宽指可用于 KV payload 的字节速率，已将链路协议等折损折算在预算中，不是链路宣传速率或本机测量值。

如果一个资源最多以 BeffB_{\mathrm{eff}}Beff​ byte/s 为本次传输服务，而它必须承载 C byte，则该模型中的纯数据传输时间满足：

tbulk≥CBefft_{\mathrm{bulk}}\ge \frac{C}{B_{\mathrm{eff}}}tbulk​≥Beff​C​

先明确“这个资源”是什么。若每个 rank 各有一条独立的 25 GB/s 路径，而且其他资源都不构成瓶颈，四份数据可以同时走四条路，整体完成时间由最慢的一条决定。若四份数据共用同一条总预算为 25 GB/s 的路径，则这条路径必须服务四份数据的总和。

这些数值用 Python 核算，分别来自 302579712 / 25e9 与 1210318848 / 25e9 秒。换算时要保留单位：本课容量表用 MiB、GiB 时按 1024 的幂换算，带宽中的 GB/s 按 10 的幂换算；若输入给的是 Gb/s，先除以 8 才得到 GB/s。

真实路径可能同时受 P 出口、D 入口、共享链路或内存拷贝能力限制。下界需要同时满足每个资源的“经过它的字节量 ÷ 它的可用速率”，再取其中最强的约束；不能把某张网卡的带宽乘以 rank 数，就当成请求可以使用的聚合带宽。

为什么实际交接更复杂上式只描述所选 payload 占用传输资源的时间。metadata 准备、提交开销、资源排队、重排或格式转换、重试，以及接收后的数据可见性处理，都可能改变完成时间；其中某些阶段也可能重叠。测量时要分别标出提交、传输结束、数据可消费等时间点，才能把差距归因到具体环节，不能仅凭总延迟大于估算值就断定网络带宽不足。

边界25 GB/s 是本例的预算假设。只有在它确实限制本次可用 payload 速率时，算出的值才构成相应的时间下界；如果真实路由、选中块、并行链路或带宽不同，就要重新建模。它也不等于整条请求的 TTFT，P/D 的计算与排队仍按单元一的关键路径判断。

结论先确定这次搬哪些字节，再确定它们共享哪些资源，最后计算时间。报告结果时应同时给出 payload、带宽归属、单位和排除的阶段，让理论下界与实测延迟各有明确含义。

Mooncake 为 Kimi 提供服务，论文报告其生产系统横跨数千节点。为了公开实验结果，作者另外使用匹配 LLaMA3-70B 架构的 dummy model 和请求 trace 做实验，其中有 16 个节点、每节点 8 张 A800 的配置。生产模型、公开模型实验与传输组件测试需要分开看，不能把它们拼成一次请求的测量。

下面是据此制定的评估方法。先按请求记录实际选中的源／目的块、层、表示和 payload。前缀命中、复制、重排与重试都可能改变实际数据量；应累计搬运片段，而非拿整个模型的 cache pool 容量作分子。P 的前缀命中会减少 prefill 计算，但不自动意味着 D 已持有相应 KV；只有实际省掉传入 D 的片段，本次 payload 才会相应减少。每条路径分别核对 NIC、PCIe、内存拷贝的共享资源，聚合带宽也不能自动当成一个请求独享的带宽。

submit→done 是观测到的传输窗口，可能包含后端内部排队与完成通知等待；要分离纯搬运，还需要实际开始事件或带宽计数器。跨机事件相减前要确认时钟误差足够小，否则应使用各端局部时长并结合请求／层／块标识关联。

还应把冷连接与预热后的请求分开观察：内存注册、连接建立可能在初始化时完成并被多次复用，也可能因首次访问或故障恢复而重新发生。测量应说明这些成本落在哪个窗口，不能每次重复加上已经摊销的初始化，也不能把冷启动差距误认为纯网络搬运变慢。

报告的 64 并发测试也不意味着每个请求都能独享全部聚合带宽。本课的 493.7 ms 推算，明确假设这份 payload 可获得 87 GB/s；共享同一出口、入口或内存通路时，应按实际资源竞争重新分配预算。吞吐接近链路上限时，请求排队与尾延迟仍可能很高。

逐层传输可能与后续层的 prefill 重叠，因此要同时看总传输窗口和暴露在关键路径上的尾部。一个有用的指标是“最后一份 KV 可用时刻超过 prefill 完成时刻多久（差值小于零时按零计）”；之后 D 何时获得执行机会还要另计。把每段传输时长全部相加，通常不能得到这个尾部。客户端 TTFT 是否经过完整交接，也要以实际首 Token 回包路径判断。

再按输入长度、命中率、并发、冷热连接及内存路径分桶，比较请求级 p50/p95/p99、TTFT、ITL/TBT 和吞吐。不同阶段的 p99 不能直接相加。若实测高于容量估算，依次用事件间隔定位生成等待、队列、控制面、传输、加载或重排，而不把全部差距归为“网速不够”。

公开证据的边界：这里没有 Kimi 生产模型的完整缓存布局、每请求实际 payload、冷热注册／连接成本和传输尾延迟分布。组件结果可用于建立量级与设计评估方法，不能据此承诺生产交接固定耗时，也不能把本课算出的毫秒数当成端到端 SLO。

9同一段历史，写入看 slot，读取看 block table

对应主线第 4 项的分页 KV；先读本节贯穿请求，再沿下一节点的固定源码链核对。范围止于 metadata 与 kernel 入口，不展开 attention kernel 内部算法。

继续使用普通 GQA、TP=4、每 rank 两个 KV 头、每头 128 维、BF16 cache。现在只看一条请求的一层、一个 rank：此前 32 个位置已经经过模型，本步把位置 t=32 作为新输入。每块 S=16，因此历史占用两个逻辑块，本步需要第三个块。为看清映射，假设分配器给出的物理块编号依次是 7、2、11；cache pool 至少有 12 个块。这些编号是教学选择，不是一次真实运行的记录。

逻辑块号描述该请求序列中的先后次序；物理块号描述本设备缓存池中的存储位置。两者无需相等，也不必连续。对这个请求，block_table=[7,2,11] 表示逻辑块 0 放在物理块 7，逻辑块 1 放在物理块 2，逻辑块 2 放在物理块 11。

先看写入。模型为本步输入生成新 K/V 后，需要把它们存到对应槽位。下面是无 CP、allocator block 与 kernel block 大小一致时的映射逻辑；request_row 表示选中的请求行：

logical_block = t // block_size
block_offset = t % block_size
physical_block = block_table[request_row, logical_block]
slot = physical_block * block_size + block_offset

t=32 时查到物理块 11、块内偏移 0，所以 slot=11×16+0=176。本步只有一个新输入，slot_mapping=[176]。176 是编码“块号＋块内位置”的槽号，不是字节偏移或 GPU 地址；写入算子还要结合 cache 的基址、head 维与 strides，才能写入这个位置的全部本地 K/V heads。

再看读取。单个新查询需要读取位置 0–32 的历史及本次新 K/V，仅知道新位置的 slot 176 不够。attention 需要 block_table=[7,2,11] 找到所有逻辑块，并用 seq_lens=[33] 限定有效范围。三个块可以容纳 48 个位置，但本次只有 33 个位置有效；最后 15 个槽位不能按历史 Token 参与 attention。

还需要区分“全部有效 KV 长度”和“本步查询有几行”。这里本步只有一个输入，所以 query_start_loc=[0,1]，表示这个请求的 Q 占本步打包张量中的第 0 行到第 1 行之前。多请求时，它是各请求本步输入数量的前缀和，不是每条请求完整上下文长度的前缀和。

本步字段本例值回答的问题
positions[32]本次输入在请求中的逻辑位置是什么？也用于位置变换。
slot_mapping[176]本步新 K/V 写到哪里？
block_table[[7,2,11]]这个请求各逻辑块的历史放在哪里？
seq_lens[33]本步 attention 总共有多少有效 KV 位置？
query_start_loc[0,1]每个请求的本步 Q 行在打包张量的哪一段？

为什么这样分工分页让请求按需取得空闲块，序列增长时不必为它寻找一段越来越大的连续空间；代价是计算前必须准备可靠的地址与长度信息。block table 保存按请求组织的历史映射，slot mapping 把本步写入目的直接列出来，两者服务的操作不同。

固定 vLLM d7ada3aace05：GPU slot mapping 的实际计算；positions 与 seq_lens。槽号 176 及边界位置映射已经用 Python 核算。CP 的额外位置归属仍按节点 5 处理，不能直接套本节无 CP 的映射式。

结论slot mapping 管本步的新 K/V 写入，block table 管历史块的定位，seq_lens 管有效范围，query_start_loc 管本步查询行的归属。只有这些信息对应同一请求和同一步，attention 才会读到正确的历史。

10沿固定源码，把这几张表送到 attention 入口

对应主线第 4 项的源码定位；本节选定 MRV2 GPUModelRunner → DefaultModelState → FlashAttention 这一条阅读分支。建议先沿图读职责，再按行号查看相邻调用。

本节继续上一节点的请求，并明确采用 eager、单请求单 Token decode；无 PP/CP、推测解码和跨层 KV sharing，allocator 与 kernel block 都是 16。MRV2 是这个版本的 V2 model runner。这里选择的是一条固定源码路径，不声称当前机器实际启用了它；其他 runner 的文件和调用方式需要分别核对。

Scheduler 负责决定请求持有哪些物理块。新请求发送完整的 block_ids，已有请求通过 new_block_ids 发送本次增量。Worker 的 add_requests 对新请求覆盖写入，update_requests 对已有请求追加；BlockTables.apply_staged_writes 再把暂存更新应用到 GPU 表。

持久表的行由请求状态管理，而每一轮参与计算的请求集合和顺序可以改变。所以 prepare_attn 用本步 idx_mapping 从持久表抽取当前 batch 的行，并用同一请求对应关系计算 slot mapping。query_start_loc 则由本步各请求计划计算的 Token 数做前缀和；seq_lens 使用已计算位置数加本步输入数，本例因此为 33。

定位固定源码
分配／打包块更新Scheduler 调用 KVCacheManager.allocate_slots；同文件 CachedRequestData
持久表覆盖／追加GPUModelRunner → BlockTables
本步行顺序与读写映射query_start_loc；同文件 prepare_attn

接下来 DefaultModelState.prepare_attn 调用 build_attn_metadata，把这些字段放进 CommonAttentionMetadata，再经过具体 backend 的 builder。这个公共对象让调度／runner 层可以提供统一含义的信息，而 backend 组织自己的接口参数。对本例，block table、seq_lens、query_start_loc 为 int32；slot_mapping、positions 为 int64。它们都是索引或长度，不能因为 KV 使用 BF16 就跟着变成 BF16。

Runner 在 set_forward_context 中执行模型。attention layer 根据 layer_name 取到自己的 cache、metadata 与 slot mapping；相同缓存组的多层可以复用映射信息，但各层仍有各自的 KV 数据。固定 Attention.forward 先调用独立的 cache update，再调用 attention；代码用一个依赖占位张量让编译器保留这项先写后读的关系。

构建与交付：DefaultModelState → CommonAttentionMetadata 与 builder → forward context；Attention 写入先于读取。这些是源码依赖，不是本地运行 trace。

现在看传入 backend 的张量。设 BpoolB_{\mathrm{pool}}Bpool​ 为本层 cache pool 的总块数。该普通 cache 张量接口按 [B_pool, Hkv_local, S, 2d] 解释；本例是 [B_pool,2,16,256]。固定代码使用下面的视图操作得到 K 和 V：

key_cache, value_cache = kv_cache.transpose(1, 2).split(self.head_size, dim=-1)

K/V 各成为 [B_pool,16,2,128] 的视图，仍指向原来的存储；strides 描述各维如何寻址。这里没有先把请求的三个历史块复制成连续的 [33,2,128]。写入接口 reshape_and_cache_flash 使用 slot mapping；attention 读取接口则接收以下参数关系：

q = query                         # 本步查询，本例 [1,8,128]
k, v = key_cache, value_cache      # 整个本层 pool 的分页视图
cu_seqlens_q = query_start_loc     # [0,1]
seqused_k = seq_lens               # [33]
block_table = request_block_table # [[7,2,11]]

kernel 据此从本层 pool 找到物理块 7、2、11，并把最后一块的有效范围限制到第一个位置。本节点就在这个接口边界停止：不展开 kernel 如何分块计算、做 softmax 或安排线程。这里也能看出，模型数据、写入位置和历史读取范围是三类相互配合的输入。

固定 backend：cache 写入与 slot mapping；cache 视图与 metadata 字段；最终调用参数。该包装器名称包含 FA4，但这里不据名字推定实际平台选择了哪个 FlashAttention 版本。

结论分配器决定物理块归属，runner 把持久状态转换成本步的地址和长度信息，backend 接收这些信息完成写入与读取。排查错误时，应沿请求身份、本步行顺序、写入槽位、历史块表和有效长度逐项核对。

检查 5源码链诊断

同一模型的两个请求 A、B 长度相同，历史内容不同。本步 batch 顺序从 [A,B] 改为 [B,A]。某次改动后，Q、slot_mapping、seq_lens 都按新顺序准备，新 K/V 也写到了各自正确的位置，但送入 attention 的 block_table 仍保留 [A,B] 的旧行顺序。

“写入位置正确，而且所有张量 shape 都对，所以读取不会串请求”这个判断成立吗？请沿本步输入到 backend 参数的链路，指出可能读错什么，以及应恢复哪组对应关系。

用自己的话解释即可；不需要实现代码，也不需要计算 slot 编号。

参考要点

这个判断不成立。本步 Q 的第 0 行属于 B，但第 0 行块表仍属于 A；第 1 行则相反。attention 按块表定位历史，所以两条请求的查询会读到对方的 K/V。新 K/V 写入槽正确，不能证明历史读取映射正确；相同长度和 shape 更不能证明请求归属。

应恢复本步输入顺序、query_start_loc、idx_mapping、持久请求状态行与导出的 block_table 行之间的对应关系，并让 lengths、positions 与 slot mapping 都使用同一请求身份。CommonAttentionMetadata 和各层 backend metadata 只是承载这些关系，不会从 shape 自动发现行已经错配。

接第 3 页

这一课在第 3 页接着讲，从节点 11「MLA：让多个头的 K/V 来自同一份短表示」开始。

符号与名词

T、L、ℓ
T 是已处理并缓存的输入位置数，单位 Token；L 是层数；ℓ 是层编号。
Hq、Hkv
查询头数与 K/V 头数。K 和 V 各有 Hkv 个头。
d、b
d 是等长 K/V 主例的每头维度；b 是 KV cache 每个元素的存储字节数。一般式分别用 dk、dv 与 bk、bv。
q、K、V、a、o
新位置的查询、可见位置的键和值、注意力权重、加权汇总输出。单头新位置：q/o 为 [1,d]，a 为 [1,T+1]。
Ctoken、Crequest
整个模型一份逻辑 KV 的每 Token 字节量与每请求字节量；尚未加入 rank 复制、padding 或传输额外开销。
MHA、GQA、MQA
每查询头独有 K/V、查询头分组共享 K/V、所有查询头共享一组 K/V 三种结构。
p、r、Hkv⁽ʳ⁾
p 是一个实例的 TP degree；r 是其中的 rank 编号；Hkv⁽ʳ⁾ 是该 rank 实际保存的 KV 头数。
Crequest⁽ʳ⁾
一个请求在 rank r 上的有效 KV 字节量。本段不含 PP/CP、物理块空位和其他显存。
头切片、rank_offset_factor
头切片是在一个源块内按 D 所需头数划分的片段；该固定实现用 rank_offset_factor 指示相应片段偏移，不是全局 head ID。
descriptor、M
descriptor 是传输库使用的地址、长度等说明；M 在节点 4 中表示 D 单层每块的字节数。
N、X、Zᵣ、Yᵣ、Y
N 是本次调用的输入位置数；X 是 attention 投影前的层输入；Zᵣ 是本 rank attention heads 展平的输出；Yᵣ 是本地 Wo 投影的部分结果；Y 是它们求和后的完整 attention 子层输出。
Wq、Wk、Wv、Wo
Q/K/V 投影权重与 attention 输出投影权重；本图采用 PyTorch [输出维,输入维]，线性计算为 XWᵀ。
DCP、PCP
DCP 安排 decode 历史 KV 的位置分片；PCP 分摊 prefill 查询位置的计算。固定版本 PCP-only 维持完整缓存副本，支持范围另受模型和后端限制。
c、i、t、tlocal
c 是 DCP 组大小；i 是交错分配粒度；t 是从 0 开始的全局 Token 位置；tlocal 是所属 rank 内的紧凑逻辑位置，物理地址还需 block table。
Oⱼ、Zⱼ、λⱼ（LSE）
对于一个查询头，Oⱼ 是历史分片 j 内归一化后的局部输出，Zⱼ 是该分片的 softmax 分母，λⱼ=log Zⱼ。合并分片时用 LSE 恢复正确的相对权重。
R[t]
PCP 图中位置 t 的实际注意力缓存状态的占位记法；MLA 中的具体向量留到专门节点解释，不直接套普通 K/V 公式。
S、nblk、cᵣ
S 是一个物理块容纳的位置数；nblk 是请求所需的块数；cᵣ 是某 rank 在全部层中每 Token 的有效 KV 字节数。
Cvalid、Calloc、payload
分别指有效 KV 元素量、请求占用的块容量和本次搬运的 KV 数据片段；payload 口径不包含协议头和控制消息。
Beff、tbulk
Beff 是指定传输资源可用于 KV payload 的有效带宽预算，单位 byte/s；tbulk 是这些 payload 的纯数据传输时间，单位 s。
block_table、slot_mapping
block_table 把请求的逻辑块序号映射到本地物理块号；slot_mapping 为每个本步输入 Token 指定新 K/V 的写入槽号。slot 不是字节地址。
query_start_loc、seq_lens、positions
分别是本步各请求的 Q 行边界、包含本步新增位置的有效 KV 总长度，以及本步输入在请求中的逻辑位置。
req_index、idx_mapping、Bpool
req_index 定位持久请求状态行，idx_mapping 建立本步 batch 行到持久行的对应；Bpool 是某层本地缓存池的总块数。
