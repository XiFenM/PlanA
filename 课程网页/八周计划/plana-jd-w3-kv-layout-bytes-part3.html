11MLA：让多个头的 K/V 来自同一份短表示

对应已约定的 MLA 专门节点。方法看 DeepSeek-V2 v5 §2.1.2–2.1.3，真实尺寸用 DeepSeek-V3 固定 config，实际算子顺序以 vLLM d7ada3aace05 为准。建议先读本节图和公式，再看论文定义。

前面 GQA 用“多个查询头共享较少的 KV 头”减少缓存。现在考虑另一种办法：仍让各个头使用各自的 K/V，但规定这些 K/V 都由同一份较短的向量生成。只要保存这份短向量，需要时就可以按模型定义得到各头的 K/V。这份共享中间表示就是本节的 latent；MLA 把联合压缩 K/V 的结构直接纳入模型训练。

这不是把任意已经训练好的 MHA 缓存随意截短后，还要求原模型输出保持不变。MLA 的各头 K/V 本来就被约束为共同 latent 的不同线性展开。接下来改变的是这个已训练 MLA 模型的计算次序，而不是在推理时替另一种模型发明无损压缩。

主例固定为标准 dense DeepSeek-V3，不含 sparse/index cache；先看 TP=1、无 PP/CP、未启用 MTP 的主干层，并明确采用 BF16 KV cache。公开权重配置含 FP8 量化信息，不能由此推定 KV 每元素只有一个字节。本段按未量化投影分支解释数学数据流，不作设备性能声明。

实际保存什么对本例一层、一个位置，持久状态就是 norm 后的 cⱼ[512] 与已做 RoPE 的 kⱼᴿ[64]。在 BF16 下为 (512+64)×2=1152 B，按维度用 Python 核算。这里没有第二份独立 V cache，也不把 1536 维 Q 中间表示加入历史；128 是查询头数，不能再乘到这份共享状态上。

结论普通 GQA 通过减少 KV heads 缩小缓存；本例 MLA 则保存联合生成各头 K/V 的 latent，加上一份共享的位置 key。计算字节量要从这两个持久张量出发。

12把上投影移到查询与输出一侧，历史就可以保持压缩

继续 MLA 专门节点；本节代数关系由上一节点的模型定义推出，RoPE 设计对照 DeepSeek-V2 v5 §2.1.3，实际实现对照固定 MLA decode 路径。

只保存 cⱼ 虽然省缓存，但如果每一步 decode 都先为全部历史展开 128 个头的 K/V，仍会产生大量中间数据。单 Token decode 的新查询很少，而历史可能很长；我们希望把可移动的线性变换放到本次查询或最终汇总结果上。

先看内容 key。把 kj,iC=UiKcjk_{j,i}^C=U_i^Kc_jkj,iC​=UiK​cj​ 代入点积，再按矩阵结合律改变括号：

(qt,iC)⊤UiKcj=((UiK)⊤qt,iC)⊤cj(q_{t,i}^C)^\top U_i^Kc_j=\left((U_i^K)^\top q_{t,i}^C\right)^\top c_j(qt,iC​)⊤UiK​cj​=((UiK​)⊤qt,iC​)⊤cj​

右边先为这个新查询计算一次 q~t,i=(UiK)⊤qt,iC\widetilde q_{t,i}=(U_i^K)^\top q_{t,i}^Cq​t,i​=(UiK​)⊤qt,iC​，得到 512 维 latent 查询；随后直接与各历史 cⱼ 点积。不必为了这些分数，逐个历史位置生成 128 维内容 key。这个变换每个查询头各做一次，仍使用该头自己的 Uᴷ。

再看 value。注意力权重 a 已经由相同的分数得到，线性变换可以移到加权求和之后：

∑j≤tat,i,jUiVcj=UiV(∑j≤tat,i,jcj)\sum_{j\le t}a_{t,i,j}U_i^Vc_j=U_i^V\left(\sum_{j\le t}a_{t,i,j}c_j\right)j≤t∑​at,i,j​UiV​cj​=UiV​(j≤t∑​at,i,j​cj​)

先把历史 latent 加权汇总成每头 512 维的 u，再对 u 做一次 value 上投影得到 128 维 o。这里省掉的是为了这一轮查询而逐个展开历史 V 的工作；历史 cⱼ 本身依然要参与注意力计算。

为什么要把 RoPE 分离出来？位置 p 决定旋转矩阵 Rₚ。只看内容分支，如果对展开后的内容 Q/K 都施加普通位置旋转，分数中会出现：

(qtC)⊤Rt⊤RjUiKcj(q_t^C)^\top R_t^\top R_j U_i^Kc_j(qtC​)⊤Rt⊤​Rj​UiK​cj​

这里 Rt,RjR_t,R_jRt​,Rj​ 都作用于 128 维内容向量。中间的变换随历史位置 j 改变，一般不能与 Uᴷ 任意交换次序；若移到查询侧，变换就会依赖每个历史 j，失去“新查询只变换一次，再访问全部历史”的形式。低秩表示并非数学上不能使用，但往往需要重新展开或逐位置处理 key，破坏了刚才期望的 decode 路径。

MLA 因而把可吸收的内容项保持为 NoPE，另加一条小的 RoPE 分支。内容项仍可按结合律重排，位置项直接使用本步 qᴿ 与历史 kᴿ。保存 64 维位置 key 的作用就在这里：仅保存位置编号，不能替代输入投影后再旋转得到的那个向量。

固定实现怎样做vLLM 的这个普通 decode 分支，运行时用 BMM 把 Q 的内容部分从 128 维变到 512 维，再调用 MLA decode；kernel 返回每头 512 维的 latent 汇总，随后执行 value 上投影，最后调用原 Wo。“吸收”在这里表示把运算移到等价位置，不等于实现已经离线把 Q、K、V、Wo 全部合成几个巨大权重矩阵。

缓存可以被理解为一条 576 维 key 记录，其中前 512 维也作为 latent value。写入时仍只保存 c 与 kᴿ。具体 backend 会按自身接口解释这些视图；分页 block size、量化格式或额外状态要另行核对，不能自动沿用前面普通 GQA 的 block_size=16。

实现依据：运行时 query BMM 与 decode 调用、同文件 value 上投影；原 Wo 调用。RoPE 的方法理由对照 DeepSeek-V2 v5 §2.1.3；上面的等式是根据模型定义作出的代数推导。

缩放系数也要保留。重排前后的内容点积数值按实数代数相同，因此仍要使用原 attention 的 α。本例基础缩放按 1/128+641/\sqrt{128+64}1/128+64​ 定义，并可能受配置中的 YaRN 修正；不能因为重排后的查询／缓存宽度是 576，就改成 1/5761/\sqrt{576}1/576​。浮点计算次序或量化误差则需要在相应精度下验证。

prefill 与 decode 的取舍固定实现的 prefill 路径会临时展开内容 K/V，再配合位置 key 调用 attention；已有历史也可以分块取到 workspace 后展开。它没有把持久缓存改成完整多头 K/V。设计分析prefill 有许多查询行，可以复用展开结果并利用合适的矩阵计算；decode 查询少、历史长，更关注历史状态读写。哪个路径更快仍取决于形状、kernel 与硬件，不能只凭 latent 更短就断言所有阶段都更快。

prefill 展开：forward_mha；历史 workspace 路径见同文件 L3013–3059。原缩放与 YaRN 见 DeepSeek attention 初始化及该文件 L1129–1136。

结论MLA 不仅保存较短的历史状态，还利用线性运算的结合与分配，把 key 上投影移到查询侧、value 上投影移到汇总之后；解耦的位置分支让内容项保留这条计算路径。减少缓存不等于消除对历史的 attention 工作。

参考要点

A 为每个历史位置保存各头展开后的内容 K、V 和共享位置 key；B 保存每个历史位置的一份共享 c 和位置 key。B 的 128 个查询头通过各自的查询／上投影参数使用同一份 c，不需要持久保存 128 份相同 latent。因此两者的有效状态均随历史位置数增长，但每个位置的表示大小不同。

B 不必为每次新查询逐个展开全部历史 K/V：key 的变换移到本步查询侧，value 的变换移到 latent 加权汇总之后。它仍要读取历史 c 与位置 key、计算分数和 softmax，并按权重汇总历史 latent；这些逻辑工作仍依赖上下文长度。缓存压缩不能推出 decode 与历史长度无关，也不能仅凭表示大小推定所有硬件、所有阶段的实际加速比。

13MLA 放到多卡之后：副本、位置分片与实际交接

继续 MLA 专门节点；字节量从上一节的实际缓存对象出发，分页接口对照固定 FlashMLA，P/D 映射对照 NIXL PULL。

DeepSeek-V3 主例每层、每位置保存 512 维 c 与 64 维位置 key。在 BF16 下，一份完整历史跨 61 个主干层的有效字节量是：

C(T)=61T(512+64)×2C(T)=61T(512+64)\times2C(T)=61T(512+64)×2

设 T=8192，不含 MTP、PP、页 padding 或额外状态，则 C=575,668,224 B，即 549 MiB，已用 Python 核算。现在把 TP 从 1 增加到 8：每个 rank 负责的查询头和上投影矩阵片段减少，但每个 rank 仍需要完整 c，才能用自己的矩阵生成对应头的行为。没有 DCP 时，标准路径保留相同的 latent 副本，而不是把 c 的 512 维按 TP 切开。

固定实现的 A projection 使用 disable_tp=True；MLA spec 标记 num_kv_heads=1、max_tp_shards=1。这里的“一个缓存头”描述 latent 存储接口，不能直接当成普通 MQA 的架构参数。以 TP=8 为例，每 rank 仍为 549 MiB，全部 rank 的副本合计为 8C。

如果再使用 DCP=8，把同一逻辑历史按位置均分，每 rank 只保存 1024 个位置，降为 68.625 MiB；全部 rank 合计回到 C。576 维记录的宽度不变，改变的是每张卡持有哪些位置。长度不能整齐分配时，要按实际归属、尾块和额外分配计算，不能机械做除法。

固定 vLLM d7ada3aace05：A projection 的 TP 设置；MLA cache spec。这些容量是有效状态量，不包含权重和运行 workspace。

再放回 PD。固定 P 使用 TP=4、D 使用 TP=8；两边模型、BF16 cache 表示、布局相容，无 PP/PCP、命中或重试，并明确完整选中所需块。比较两边都不开 DCP，与两边分别使用 DCP4／DCP8 的情形：

复制路径：源 rank 选择及该文件 L158–162 的零 head 偏移；全 DCP 路径：DCP source ranks、位置块列表匹配。配置边界见 MLA DCP 检查；不推广到 PUSH、PCP 或任意 partial-DCP 组合。

D 怎样读取收到的 latent？取固定 FlashMLA 的非量化路径，它的 kernel block size 是 64。通用 cache 视图 [blocks,1,64,576] 绑定到 MLA 层后去掉单头轴，成为 [blocks,64,576]；调用 kernel 时再加为 [blocks,64,1,576]。这些形状变化不复制一份完整历史。

block_table = decode_metadata.block_table

head_dim_v=512 表示 kernel 汇总的是 latent，而非直接输出 128 维 V。DCP 开启时，传给 decode 的长度是本 rank 的本地长度；全局请求长度另行保留。全局位置、本地紧凑位置、本地块表和有效长度必须一致，不能把 GQA 的 K/V 两份布局直接用于这条接口。

14混合模型：历史 KV 与递推状态分别计算

对应本课 hybrid 状态的适用边界；用 Qwen3-Next 的公开配置和固定源码判断保存对象，不展开 GatedDeltaNet 的训练数学或 kernel 算法。

普通 GQA 与 MLA 虽然表示不同，前面的历史状态都按 Token 位置保留。混合模型还可能包含另一类层：每读入一个 Token，就更新一份固定形状的矩阵，后续从这份矩阵使用历史信息；它不为每个历史位置长期留一份 K/V 列表。这是模型本身采用的另一种计算结构，不能当作标准 softmax attention 的无损实现替换。

真实例子 Qwen3-Next-80B-A3B-Instruct 有 48 个主干层，按“3 个 GatedDeltaNet＋1 个 full-attention”重复 12 次。因此它有 36 个状态层和 12 个 full-attention 层。这里先设 TP=1、无推测解码，只看一份当前有效状态。

GatedDeltaNet 的卷积尾部[3,8192]，或其转置布局保留近期输入尾部，当前状态尺寸固定
GatedDeltaNet 的递推矩阵[32,128,128]更新同一份状态，当前状态尺寸固定

递推矩阵的三个轴是 V heads、V 头维、K 头维；后两维本例都为 128，但含义不同。卷积宽度来自 2×16×128 + 32×128 = 8192，尾长为卷积核大小 4 减一。这里的短卷积可以理解为每步还要读取最近几个位置的输入，因此除递推矩阵外，还需要保存这段尾部。

所以有效状态应逐类求和：12 个 full-attention 层按 2×T×Hkv×d×元素字节数 算，36 个状态层按“卷积尾部元素数×对应精度＋递推矩阵元素数×对应精度”算。两个状态的 dtype 由独立配置控制，不能从 full KV 使用 BF16 推定它们也一定是 BF16。

为获得规模感，明确假设三类状态均为 BF16、每个状态层只保留一份当前状态：full KV 为 24 KiB/Token，T=8192 时为 192 MiB；每个状态层另有 48 KiB 卷积尾部与 1 MiB 递推矩阵，36 层合计 37.6875 MiB。这些是按形状用 Python 核算的有效元素量，不包括 page padding、额外状态槽、workspace 或整个预分配池。

公开依据：官方模型说明与 固定 config，revision 9c7f2fbe8446；固定 vLLM 状态形状与同文件 状态 dtype。若仅把递推矩阵改为 FP32，36 层状态合计就变为 73.6875 MiB；运行配置必须逐项确认。

实际占用还要看保留多少份状态。固定实现用 MambaSpec 管理这类状态，名字不表示 GatedDeltaNet 的算法就是 Mamba。max_memory_usage_bytes 按模式给出每请求状态块的基础容量规划：none 为 1 + num_speculative_blocks，align 为 2 + num_speculative_blocks + num_prefill_checkpoint_blocks；推测解码还可能扩大卷积尾部。align 的块表行要覆盖相应的全局位置范围，但表长不等于当前状态副本数。实际持有多少还取决于分配、检查点保留和安全回收；异步在途步骤可能额外保留状态，不能把基础公式理解为任意执行时刻的绝对峰值，详见本节点补充。

PD 交接同样需要按状态类型处理：full-attention 层交付历史 K/V，状态层交付与同一前缀边界相匹配的卷积尾部与递推矩阵。只搬 full KV，无法恢复缺失的状态层历史。具体 connector 是否支持这些缓存组、怎样注册 descriptor、如何处理 padding 或回退，仍须核对实现；本节只确定恢复计算所需的状态。

运行与占用依据：decode 的原位状态更新；MambaSpec 的状态尺寸、模式与块数。本节是公开配置与源码核验，没有目标设备适配或实测证据。

结论混合模型的容量结构是“增长的历史 KV＋当前递推状态与卷积尾部＋策略要求的额外状态槽”。先识别各层实际保存什么，再代入维度、dtype 和副本数，不能仅更换一个总层数就沿用普通 KV 公式。

补充：为什么要多留几份状态——从一个会被改写的数组讲起

先只看一层的递推矩阵，暂时不管卷积尾部。你可以把它理解为一个保存在显存里的数组。每处理一个新 Token，这个数组的数值就会更新，用来反映新增的信息。它不是把每个 Token 的 K/V 一条条追加进去，而是在已有数组上改数值。

假设这个数组已经处理过前 1000 个 Token。你现在想回到“只处理过前 960 个”的位置：仅把长度变量从 1000 改成 960，不会把数组里的数值变回去。要取得那时的矩阵，需要以前保存过一份，或者从某个更早的状态重新计算到 960。这是它与 full-attention KV 列表的主要区别：在相应 KV 尚未被回收的前提下，后者可以直接选择已有的前缀部分。

卷积尾部需要与选中的矩阵对应同一个前缀。GDN 对它采用扩展历史缓冲区：保留一段足够长的近期输入，然后按接受位置选出正确窗口。也就是说，恢复完整状态时，要同时选对递推矩阵版本和卷积窗口；不是每个候选槽里都必须放着一份完整、独立的卷积历史。

固定 vLLM d7ada3aace05：默认 k 个额外状态块；读取正确状态并保存各步矩阵；卷积窗口的接受偏移。文字 Token 是帮助说明的例子，不是模型输出实测。

二、align 的 2：旧数组还要保留，新计算在另一个数组上继续

再看一个不启用推测解码的例子。假设配置允许把 128 个位置作为状态块边界。现在有一个数组，保存“处理完前 128 个 Token”的矩阵。系统希望这份结果可以继续作为前缀缓存使用，同时当前请求还要处理第 129 个 Token。

这时可以把过程分成三步：

  1. 保留旧数组，它仍代表“前 128 个 Token 已处理完”。
  2. 准备一个新数组，把旧数组的内容复制进去。
  3. 在新数组上处理第 129 个 Token，让新数组变成“前 129 个 Token 已处理完”的结果。

复制和推进期间，需要同时放得下旧数组和新数组，所以 align 的基础规划里有两份容量。旧数组供读取、复制或前缀复用，新数组供当前请求继续更新。这个“2”不是“卷积一份、递推矩阵一份”，而是旧运行状态和新运行状态可能同时存在。

继续在同一个状态块范围内处理第 130、131 个 Token 时，可以更新当前运行数组，不必每个 Token 都再建一份副本。更早的数组也不会一直由这个请求占着：当管理器确认复制和相关在途计算已安全推进，就可以归还该请求的旧块引用。如果旧内容已经登记为前缀缓存，它仍可能留在池里供其他请求命中，直到被驱逐或复用。

固定实现对应 MRV2 的状态预处理、跨边界 precopy和安全退休旧状态。128 是这个例子选定的边界，不是所有模型的固定配置。

三、prefill checkpoint：一口气算到 1000，但另外留下算到 960 时的结果

假设请求已经处理完前 512 个 Token。这一轮 prefill 一次处理接下来的输入，直到第 1000 个 Token。系统还希望保存“前 960 个 Token 已处理完”的结果，因为这个位置适合做前缀复用。

如果只保留最后的数组，得到的是“完成 1000”的状态，不能拿它冒充“完成 960”。所以，当计算到 960 这个边界时，要另外保存那时的递推矩阵和对应卷积尾部；当前计算再继续到 1000。

为这个“途中另存的状态”准备的额外块，就是 num_prefill_checkpoint_blocks。本课固定 GDN 的相关 FlashInfer prefill 路径会为此设置一份额外容量，因此该字段为 1。它并不表示把前 1000 个位置的全部中间状态都保存下来，也不是所有 backend 都会设置为 1。

以后来了一个新请求，前 960 个 Token 与已有请求相同；如果其他混合层也有对应的前缀 KV，就可以使用这份“完成 960”的状态继续计算，省去前缀重算。这个用途是前缀复用，即使完全不开推测解码，也可能需要它。

对应 GDN 检查点能力与额外块配置、合法检查点位置和矩阵与卷积尾部的实际导出。这里没有运行GPU测试。
对照源码时，再看这些计数细节

默认 GDN 路径中，若接受 a 个候选，运行器通常传入 num_accepted_tokens=a+1，矩阵槽下标取 a。因此上例接受“碗”“热”时读槽2，而不是槽1。这个计数来自本轮采样结果；新采样的“面”尚未作为target输入处理，不能误以为所选矩阵已包含它。

回到最初的问题：保留多份状态，不只为了笼统的“回退”。推测解码要能选择正确的接受结果；align要让旧状态与新计算安全交接；prefill checkpoint要保留可复用的中途结果。三者需要额外空间的原因不同。

导师串讲：沿一条请求，把表示、分配、传输和消费接起来

我们回到本课贯穿的 Qwen3-8B 请求。设 P 已计算 8193 个有效位置，P/D 都使用 TP=4，KV 为 BF16；没有 CP、前缀命中、额外 page padding 或预留块，物理 block_size=16。本次明确选择全部已占用块，各 head 分片恰好搬一次。下面按这个既定条件串起完整过程，不把它当作真实运行 trace。

先确定 P 留下了什么。模型每层产生 Q/K/V。Q 服务于本步查询，变换后的 K 与对应 V 留在缓存。全模型有 8 个 KV heads，TP=4 时每 rank 保存其中 2 个；36 层合计，每个有效位置每 rank 需要 36 KiB。有效数据量因此为 302,026,752 B。

再确定这些内容放在哪里。8193 个位置需要513个16位置块，因此每 rank 占用302,579,712 B。末块只用一个位置，剩余空槽仍占容量。逻辑位置经 block table 找到物理块；P 和 D 可以使用不同的物理块号，只要它们对应的是同一请求、层、位置和头。

然后确定本次到底搬哪些片段。在本例“全部完整块都被选中”的条件下，payload 才等于上述块容量。若有本地命中、不同传输粒度、重排或副本，必须重新核对被选中的 descriptors。P 保留源块，D 准备目标块，Worker 按传输计划执行；相同的地址或块号不是逻辑身份，复制完成也不替代对数据表示和目标归属的检查。

最后是 D 的读取条件。本层数据达到可消费条件后，D 才能让 attention 使用它。D 后续处理新输入时，先用 slot mapping 写入本步新 K/V，再把对应请求行的 block table、有效 seq_lens、query_start_loc 与 cache 视图交给 backend。shape正确只是接口形状成立，仍要保证这些字段指向同一请求和同一个有效前缀。

把字节量放回性能模型。四个 rank 的本次 payload 总计1,210,318,848 B。如果它们确实共享一条25 GB/s的有效payload路径，纯数据时间下界约48.41 ms。这个数没有把D排队、设备加载、可见性处理都算进去；若各层边算边传，也不能把全部传输窗口直接加到TTFT。实测需要沿同一请求关联生成、提交、完成、可消费和实际执行的事件。

换成 DeepSeek-V3 dense MLA，第一步的对象就改为每位置一份512维latent和64维位置key；普通TP还可能复制这份历史，DCP才沿位置分摊。换成 Qwen3-Next，full-attention层的历史K/V与状态层的矩阵、卷积尾部又需要分别计算；被保留的是哪一个前缀版本，也会影响能否从正确位置继续。

因此，同一条分析路线可以用于不同模型：先确认实际状态，再确认各rank的归属和物理分配，随后核对传输片段与读取metadata，最后在明确资源和计时窗口的条件下评估性能。模型结构、运行时表示和实测证据各回答不同的问题，只有把它们接起来，才能解释系统为什么正确、资源花在哪里。

参考回答

这个接口可以统一“把已确定的字节片段搬到已确定的位置，并报告这次搬运的完成情况”。上层仍要知道这些字节是什么状态、属于哪个请求和哪段前缀，以及接收方怎样解释它们。模型版本、缓存精度、位置编码、shape、stride、padding 和状态边界不能靠地址与字节数自动表达。

以标准 dense MLA 为例，P 为各层各位置生成归一化后的共享 c 和已做 RoPE 的位置 key。上层根据 P、D 两边的 TP／DCP 配置，确定每个源 rank 持有的数据和每个目标 rank 所需的片段；既要处理完整 latent 的副本，也要处理按位置切分的情况。随后选出本次需要的块，建立源／目的请求、层、位置与物理区域之间的对应关系。

每次调用 transfer 前，都需要有合法的接收缓冲区和这次搬运的地址映射。如果直接写入 D 的最终 KV cache，对应块应提前分配；如果先接收到中转缓冲区，最终设备 cache 的加载、重排可以由后续计划完成。传输或消费仍在使用的块，不能被提前回收或重用。

接收后，D 按具体路径完成必要的加载或表示处理，确认设备可见性和就绪条件，再使用与本步请求顺序一致的 block table、slot mapping、有效长度等信息。直接写入 cache 的路径不需要无条件再写一遍。字节数一致与传输完成只证明给定搬运操作完成，不能单独证明模型表示、请求归属、前缀位置或读取映射正确。

关键要点

  • 可统一的底层工作：按已给定的地址与长度搬字节，以及提交／完成观测。
  • 上层必须保留的语义：状态类型、模型与数值表示、请求／层／前缀身份、布局和实际传输片段。
  • 映射要同时看两端：目标需要什么、源分别持有什么，决定如何收集或分发；不能只看 D 的并行度。
  • 接收路径决定后处理：直接落最终 cache 与经中转再加载是不同路径，分配时机和后续工作要对应。
  • 消费条件必须成立：数据有效且可见，metadata 指向正确位置，相关缓冲区仍由正确的请求持有。

综合核验 2混合状态恢复 · 迁移判断

同一个混合模型使用 full-attention 层和递推状态层。P 上的一条旧请求与 D 要处理的新请求，前 1000 个 Token 完全相同；模型权重、精度、位置编码设置及对应 Token 的 position_ids 也一致。假设实现已经支持这些状态的传输与恢复。

  • D 已有 full-attention 层前 1000 个 Token 的正确 K/V。
  • P 可以提供一组“所有递推状态层均处理完前 960 个 Token”的检查点，或一组“所有递推状态层均处理完前 1200 个 Token”的最终状态；两组都包含各层对应的递推矩阵和卷积尾部。
  • 这些 Token 的输入可以重新取得，但没有保存可直接复用的中间激活。
  1. 同事建议使用 1200 的状态，把长度标为 1000，就认为两类层都已恢复到“前 1000 个 Token 处理完”的状态。这个方案是否成立？为什么？
  2. 在尽量复用已有缓存的前提下，你会选择哪个状态，从哪个前缀边界恢复，接下来还要做什么，才能让两类层都对应“前 1000 个 Token 已正确处理完”？

说明状态与数据依赖即可，不要求指定某个重放 kernel 或实现代码；已有 K/V 可以保留，重点是解释怎样恢复一致的计算状态。

参考回答

不能把处理完前1200个 Token 的状态改个长度就当成前1000个的状态。递推矩阵和卷积尾部已经受到后面200个 Token 的更新；修改计数不会撤销这些更新。即使 shape、dtype 和传输字节数都正确，这份状态也不对应题目需要的前缀。

应选择所有状态层的960检查点，并以“前960个 Token 已正确处理完”作为共同恢复边界。D 的 full-attention KV 已覆盖这个前缀，可以继续保留；已经存在的后40个位置的 KV 也不必仅因为状态层落后而无条件删除。

接下来重新取得第961至第1000个 Token，共40个输入，执行恢复实现所需的前向计算。若采用从0开始的位置编号，对应位置960–999。由于题目没有保存中间激活，需要沿必要的模型层生成这些位置的输入和输出，使递推矩阵、卷积尾部一起推进到1000；不能只修改状态层长度，或假定各层所需输入已经存在。

已有 full-attention KV 是否在这段前向中直接复用、是否重复生成或写入，由具体恢复路径决定。本题的正确性条件是：恢复期间的请求身份、查询位置、因果范围与读写映射一致，结束时 full-attention KV、递推矩阵和卷积尾部都表示同一个“前1000个 Token 已处理完”的前缀，然后再继续后续计算。

关键要点

  • 选960，而非1200：从可恢复的较早检查点前进；不能把包含后续输入影响的状态直接改标签。
  • 共同边界是960：完整模型的恢复点要同时满足各类层的状态条件。
  • 重放后40个输入：第961–1000个，或从0编号的960–999；保持计数与位置口径一致。
  • 可以保留已有KV：“状态层需要补算”不等于“所有attention缓存都必须丢掉重建”。
  • 最后检查前缀一致性：两类层及其metadata一起到达1000，而不只是某个长度字段写成1000。

符号与名词

T、L、ℓ
T 是已处理并缓存的输入位置数，单位 Token；L 是层数；ℓ 是层编号。
Hq、Hkv
查询头数与 K/V 头数。K 和 V 各有 Hkv 个头。
d、b
d 是等长 K/V 主例的每头维度；b 是 KV cache 每个元素的存储字节数。一般式分别用 dk、dv 与 bk、bv。
q、K、V、a、o
新位置的查询、可见位置的键和值、注意力权重、加权汇总输出。单头新位置：q/o 为 [1,d]，a 为 [1,T+1]。
Ctoken、Crequest
整个模型一份逻辑 KV 的每 Token 字节量与每请求字节量；尚未加入 rank 复制、padding 或传输额外开销。
MHA、GQA、MQA
每查询头独有 K/V、查询头分组共享 K/V、所有查询头共享一组 K/V 三种结构。
p、r、Hkv⁽ʳ⁾
p 是一个实例的 TP degree；r 是其中的 rank 编号；Hkv⁽ʳ⁾ 是该 rank 实际保存的 KV 头数。
Crequest⁽ʳ⁾
一个请求在 rank r 上的有效 KV 字节量。本段不含 PP/CP、物理块空位和其他显存。
头切片、rank_offset_factor
头切片是在一个源块内按 D 所需头数划分的片段；该固定实现用 rank_offset_factor 指示相应片段偏移，不是全局 head ID。
descriptor、M
descriptor 是传输库使用的地址、长度等说明；M 在节点 4 中表示 D 单层每块的字节数。
N、X、Zᵣ、Yᵣ、Y
N 是本次调用的输入位置数；X 是 attention 投影前的层输入；Zᵣ 是本 rank attention heads 展平的输出；Yᵣ 是本地 Wo 投影的部分结果；Y 是它们求和后的完整 attention 子层输出。
Wq、Wk、Wv、Wo
Q/K/V 投影权重与 attention 输出投影权重；本图采用 PyTorch [输出维,输入维]，线性计算为 XWᵀ。
DCP、PCP
DCP 安排 decode 历史 KV 的位置分片；PCP 分摊 prefill 查询位置的计算。固定版本 PCP-only 维持完整缓存副本，支持范围另受模型和后端限制。
c、i、t、tlocal
c 是 DCP 组大小；i 是交错分配粒度；t 是从 0 开始的全局 Token 位置；tlocal 是所属 rank 内的紧凑逻辑位置，物理地址还需 block table。
Oⱼ、Zⱼ、λⱼ（LSE）
对于一个查询头，Oⱼ 是历史分片 j 内归一化后的局部输出，Zⱼ 是该分片的 softmax 分母，λⱼ=log Zⱼ。合并分片时用 LSE 恢复正确的相对权重。
R[t]
PCP 图中位置 t 的实际注意力缓存状态的占位记法；MLA 中的具体向量留到专门节点解释，不直接套普通 K/V 公式。
S、nblk、cᵣ
S 是一个物理块容纳的位置数；nblk 是请求所需的块数；cᵣ 是某 rank 在全部层中每 Token 的有效 KV 字节数。
Cvalid、Calloc、payload
分别指有效 KV 元素量、请求占用的块容量和本次搬运的 KV 数据片段；payload 口径不包含协议头和控制消息。
Beff、tbulk
Beff 是指定传输资源可用于 KV payload 的有效带宽预算，单位 byte/s；tbulk 是这些 payload 的纯数据传输时间，单位 s。
block_table、slot_mapping
block_table 把请求的逻辑块序号映射到本地物理块号；slot_mapping 为每个本步输入 Token 指定新 K/V 的写入槽号。slot 不是字节地址。
query_start_loc、seq_lens、positions
分别是本步各请求的 Q 行边界、包含本步新增位置的有效 KV 总长度，以及本步输入在请求中的逻辑位置。
req_index、idx_mapping、Bpool
req_index 定位持久请求状态行，idx_mapping 建立本步 batch 行到持久行的对应；Bpool 是某层本地缓存池的总块数。
hⱼ、cⱼ、q_c
hⱼ 是位置 j 的本层输入；cⱼ 是归一化后的共享 KV latent，512维；q_c 是生成查询的1536维中间表示，不是历史 KV。
i、j、t、C、R
i 是查询头编号，j 是历史位置，t 是本次查询位置；上标 C 表示不做 RoPE 的内容分支，R 表示位置分支。
Uᴷᵢ、Uⱽᵢ、kᴿⱼ
各头从共享c展开内容K和V的矩阵，均[128,512]；kᴿⱼ是所有头共享、已施加RoPE的64维位置key。
q̃、u、α
q̃是移入key上投影后得到的512维查询；u是每头对历史c的512维加权汇总；α是原模型规定的attention缩放系数。
C(T)、g
C(T) 是全部主干层一份 latent 历史的有效字节量；节点13中g是全局64-Token块序号。副本、DCP位置分片和实际READ payload分别计算。
GatedDeltaNet、conv_state、ssm_state
本例的线性状态层及其卷积尾部、递推矩阵。ssm_state是实现中的名字；当前状态固定形状，实际保留份数与dtype另查运行配置。
