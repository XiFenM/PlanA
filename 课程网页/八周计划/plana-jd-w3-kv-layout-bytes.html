沿着一次 KV 交接，看清数据本身

上一课已经沿同一个请求走完了 P 生成 KV、D 接收并消费、双方安全回收的正常路径。现在把镜头停在交接处：P 说“这条请求的 KV 已经准备好”，D 得到的究竟是哪几组张量？一条长请求要搬多少数据？即使字节全部到达，D 又怎样知道某个 Token、某层、某个注意力头的数据在哪里？

我们仍用相同模型的 P 与 D 作为起点。先把普通注意力的缓存表示讲清，再把它放到多 rank、分页和传输中；随后单独进入 MLA，检查改变缓存表示后哪些公式必须重写。这里贯穿的矛盾是：模型按逻辑位置使用历史信息，系统却按设备、物理块和传输片段保存它。

沿这条线学完后，你应当能给出带单位和假设的 KV 字节量与传输下界推导，沿固定源码指出 D 读取分页 KV 所需的参数，并解释普通注意力、MLA 和混合模型为什么不能无条件共用一个公式。模型结构对照会以公开配置为依据；有没有真实适配或实测证据，需要另外说明。

1下一步 attention，为什么只留下历史 K 和 V

对应主线第 1 项；真实实现对照 Qwen3Attention.forward，先读本节，检查 1 关闭后再连读完整源码。

假设 P 刚处理完一条有 T 个输入 Token 的请求。这里的“处理完”指这些位置已经经过模型的全部层，而不是只完成分词。P 可以用最后位置的输出采样出一个新 Token；这个新 Token 还要在下一次模型调用中作为输入，才会产生它自己的各层 K/V。D 接手时，需要的是此前 T 个位置已经算出的历史状态。

先只看其中一层、一个注意力头。设每个头的向量维度为 d。D 处理新位置时，从这一层的新输入向量生成查询 qnew∈R1×dq_{\mathrm{new}}\in\mathbb{R}^{1\times d}qnew​∈R1×d、键 knew∈R1×dk_{\mathrm{new}}\in\mathbb{R}^{1\times d}knew​∈R1×d 和值 vnew∈R1×dv_{\mathrm{new}}\in\mathbb{R}^{1\times d}vnew​∈R1×d。查询表示这个新位置要从历史中取出什么信息；每个历史位置的键用于计算相关程度，值用于最后的加权汇总。

此前保存的 Khist,Vhist∈RT×dK_{\mathrm{hist}},V_{\mathrm{hist}}\in\mathbb{R}^{T\times d}Khist​,Vhist​∈RT×d，沿序列维加入新位置后成为 T+1 行。对这个新位置，完整的数学接口是：

Kall=[Khist;knew],Vall=[Vhist;vnew]anew=softmax⁡ ⁣(qnewKall⊤/d)onew=anewVall\begin{aligned}K_{\mathrm{all}}&=[K_{\mathrm{hist}};k_{\mathrm{new}}],\quad V_{\mathrm{all}}=[V_{\mathrm{hist}};v_{\mathrm{new}}]\\a_{\mathrm{new}}&=\operatorname{softmax}\!\left(q_{\mathrm{new}}K_{\mathrm{all}}^{\top}/\sqrt{d}\right)\\o_{\mathrm{new}}&=a_{\mathrm{new}}V_{\mathrm{all}}\end{aligned}Kall​anew​onew​​=[Khist​;knew​],Vall​=[Vhist​;vnew​]=softmax(qnew​Kall⊤​/d​)=anew​Vall​​

方括号中的分号表示按行拼接。注意力权重 anewa_{\mathrm{new}}anew​ 的形状是 [1,T+1][1,T+1][1,T+1]，输出 onewo_{\mathrm{new}}onew​ 是 [1,d][1,d][1,d]。这是逻辑接口：真实实现可以直接读分页存储，不必先复制成连续的 K_all、V_all。位置变换如 RoPE 在这里视为已经作用到对应的 Q/K；分页访问机制留到后面的节点。

为什么这样设计在因果注意力中，旧位置看不到未来新增的 Token。模型权重、前缀和位置规则不变时，新增位置不会改变旧位置已经产生的 K/V，所以可以保存后复用。历史 Q 则只参与生成历史位置当时的输出，下一位置的公式不会再使用它。每次都从头重算旧 K/V，会重复前缀各层的计算；保留 KV 用随序列长度增长的存储，换掉这部分重复计算。

这也解释了复用的限制：缓存并没有让历史信息消失。每个新查询仍要依赖它可见的历史 K/V，序列增长仍会增加注意力的数据访问与计算。具体执行时间还取决于 backend 的分块、数据复用和设备条件。

真实系统固定 vLLM 的 Qwen3 路径先生成 Q/K/V，对 Q/K 做归一化和 RoPE，再调用 attention。下面按原顺序摘录；中间的 Q/K 归一化用注释标明，未展开。

qkv, _ = self.qkv_proj(hidden_states)
q, k, v = qkv.split([self.q_size, self.kv_size, self.kv_size], dim=-1)
# 此处省略按 head 对 Q、K 进行 RMSNorm 的代码
q, k = self.rotary_emb(positions, q, k)
attn_output = self.attn(q, k, v)
output, _ = self.o_proj(attn_output)
实现依据：qwen3.py L156–173，commit d7ada3aace05。这里的 self.attn 封装后续 cache 写入与读取；调用行本身不展示它们的物理布局。

边界这一节讨论 decoder 的普通全因果注意力，且一次只新增一个输入位置。滑窗、MLA 和混合结构会改变实际保留的状态；批量新增位置时会有多行 Q。它们不改变“先按计算依赖决定留下什么”的分析方法。

结论普通自回归注意力保留每层的历史 K/V，因为后续查询会再次读取它们；历史 Q 不在后续查询的依赖里。缓存省掉历史状态的重算，但新查询仍要使用历史状态。

2从注意力头的分工，数到一条请求的 KV 字节量

对应主线第 1 项的 MHA/MQA/GQA 与字节量；公开 Qwen3-8B config 随本节对照，GQA 论文等检查 1 关闭后再读。

现在把单头推广到多头。定义 HqH_qHq​ 为查询头数、HkvH_{kv}Hkv​ 为 K/V 头数。K 和 V 各有 HkvH_{kv}Hkv​ 个头，“KV 头数”不是把两者的头数加起来。先假设每个 K/V 头都是 d 维，查询头均匀分组，HqH_qHq​ 可以被 HkvH_{kv}Hkv​ 整除。

MHA 为每个查询头配一组 K/V，因此两种头数相等；MQA 让全部查询头共用一组 K/V；GQA 则把查询头分组，每组共用一组 K/V。这样可以保留多个查询投影，同时减少需要保留的 K/V 投影数量。共用的是可供查询的键和值，查询向量仍由各个查询头产生。

为什么这种改变能减少缓存？因为 K/V 不必在持久存储中按查询头展开。同一组查询头可以读取同一组历史 K/V。它付出的代价是 K/V 投影的独立性减少，模型表达能力与推理成本之间需要取舍；将已经训练好的 MHA 随意删成 MQA，不保证原模型的结果或质量保持不变。GQA 论文讨论的是相应结构与训练转换方法。

对一层、一个请求，历史逻辑形状因此是：

K:[T,Hkv,d],V:[T,Hkv,d]K:[T,H_{kv},d],\qquad V:[T,H_{kv},d]K:[T,Hkv​,d],V:[T,Hkv​,d]

设每个缓存元素占 b 字节，总共有 L 层，各层结构相同。当前先统计整个模型的一份逻辑 KV，不涉及设备切分、跨 rank 复制和物理块空位。按“每个张量的元素数 × 每个元素的字节数”计算：

系数 2 分别对应 K 和 V。如果两者维度或精度不同，或者各层不一样，就逐层相加：Ctoken=∑ℓHkv,ℓ(dk,ℓbk,ℓ+dv,ℓbv,ℓ)C_{\mathrm{token}}=\sum_{\ell}H_{kv,\ell}(d_{k,\ell}b_{k,\ell}+d_{v,\ell}b_{v,\ell})Ctoken​=∑ℓ​Hkv,ℓ​(dk,ℓ​bk,ℓ​+dv,ℓ​bv,ℓ​)。这里 ℓ 是层编号，k/v 下标指 K/V 的维度和每元素字节数。不要用模型参数量代替这些字段，也不要在已有显式 head_dim 时总用 hidden_size / num_attention_heads 反推。

Ctoken=2×36×8×128×2=147456 byte=144 KiBC_{\mathrm{token}}=2\times36\times8\times128\times2=147456\ \mathrm{byte}=144\ \mathrm{KiB}Ctoken​=2×36×8×128×2=147456 byte=144 KiB

把这个数字放回 PD：如果要把这 T 个位置的全部层、全部 KV 头，以相同 BF16 表示完整交给 D，这就是有效张量数据量的计算起点。实际系统还要回答谁持有哪一部分、是否重复传输，以及是否传完整物理块。后面才能据此讨论网络字节数和带宽下界。

边界本节公式统计有效 KV 元素，不包含权重、工作区、页表、预分配空位或尾块 padding；多个请求是否共享前缀也需要单独处理。FP8 等表示要重新明确元素存储及尺度数据；MLA 的缓存对象不同，将在专门节点重新推导。

结论先确定缓存里实际保留的头数、维度、层数和精度，再数元素。普通注意力的逻辑缓存形状是理解数据量的起点；每 rank 容量、物理分配和传输流量要在它之上加入各自的系统条件。

3TP 增加时，哪些 KV 能继续分，哪些开始复制

对应主线第 1 项的 per-rank 字节量；本节代码来自固定 vLLM 的 QKVParallelLinear 与 Qwen3Attention，讲完后可对照所附行号。

继续使用 Qwen3-8B：32 个查询头、8 个 KV 头、36 层、每头 128 维，KV cache 为 BF16。请求仍有 8192 个已处理位置。现在让一个模型实例使用 p 个 TP rank。rank 是参与计算的进程编号；本例每个 rank 对应一张设备卡。这里没有 PP 或上下文并行，因此每个 rank 都经过全部层，并保存自己负责的头在全部 T 个位置上的 KV。

TP 首先把查询头及其投影工作分给不同 rank。p=4 时，每个 rank 处理 8 个查询头；同一组里的查询要访问相应的 K/V。8 个 KV 头也能均匀分成 4 份：rank 0 保存 KV heads 0–1，rank 1 保存 2–3，依此类推。每张卡只保存完整逻辑 KV 的四分之一。

把 p 增加到 8 时，每个 rank 处理 4 个查询头，恰好配一个 KV 头。继续增加到 p=16，32 个查询头仍能分成每 rank 两个，但是 KV 只有 8 个头。固定源码采用的普通路径没有把一个 KV 头的向量维度再切成两半，而是让两个 rank 各持有这个完整 KV 头。

为什么这样设计当一个查询头及它需要的完整 K/V 头都在本地，rank 就能独立计算这一头的 attention，再参与后续输出投影的通信。如果把单个 KV 头继续沿维度切开，点积和归一化等计算就需要新的跨设备协作；如果只在另一张卡保留完整 KV，这个 rank 又要在 decode 时获取远端数据。这里的实现选择复制，换取本地完整的 attention 输入。这是依据计算依赖作出的设计分析；其他并行方式可以采取不同分工。

真实系统QKVParallelLinear 对本地头数的决定如下。divide(a, b) 会先检查能否整除，再返回商，所以这里不是对任意配置做向下取整。

self.num_heads = divide(self.total_num_heads, tp_size)
if tp_size >= self.total_num_kv_heads:
    self.num_kv_heads = 1
    self.num_kv_head_replicas = divide(tp_size, self.total_num_kv_heads)
else:
    self.num_kv_heads = divide(self.total_num_kv_heads, tp_size)
    self.num_kv_head_replicas = 1

复制还体现在权重加载中：Q 使用当前 tp_rank 选择自己的权重片段，K/V 使用 tp_rank // num_kv_head_replicas。因此，同一个复制组的 rank 加载同一组 K/V 投影权重，处理相同位置的层输入时产生对应同一逻辑头的 K/V；它们负责的 Q 投影则不同。

vLLM d7ada3aace05：本地头数与复制数；Q 与 K/V 权重片段的选择；Qwen3 的整除约束与 head_dim。上述“为什么”是对该数据分工的分析，未据此声称性能收益已实测。

Qwen3 的实际顺序是 qkv_proj → split → Q/K Norm → RoPE → attention。这里画了缓存的逻辑内容和依赖；cache 写入与 attention 读取可以由 backend 融合或分块；编译优化也可能改变实际 kernel 的边界，图中每个框不对应一次独立 kernel launch。

4P 与 D 的 TP 不同，交接时怎样找到正确的头片段

对应主线第 2 项的相同 TP 与异 TP；实现对照 NIXL PULL 的 tp_mapping.py、远端 descriptor 构造及 ReadSpec，先按本节主例读，再定位源码。

上一节只看一个实例怎样分配 KV。现在让 P 与 D 使用相同 Qwen3 模型和 BF16 KV，但采用不同 TP。首先限制为相同块大小、相同且适合按头切片的物理布局，不启用 PP、CP 或特殊量化存储。我们关心的是：D 的每个 rank 去哪里找到自己负责的逻辑 KV 头。

如果 P 与 D 都是 TP=4，而且头分配顺序相同，那么 P0 与 D0 都负责 heads 0–1，P1 与 D1 都负责 heads 2–3；头的对应关系可以按相同 rank 建立。不过两边独立分配物理块，P 的块号和 D 的块号仍可以不同。上一课的请求身份与源／目的块映射仍然需要保留。

现在只把 P 改为 TP=2，D 保持 TP=4。P0 保存 heads 0–3，P1 保存 heads 4–7；D 的每个 rank 只需要两个头。因此一份 P rank 缓存里包含了两个 D rank 所需的数据，交接时需要选择其中正确的一片：

真实系统NIXL PULL 把 D 叫作 local，把 P 叫作 remote。对本例，compute_tp_mapping 根据 D rank 算出源 rank；compute_head_offset 再给出该源块内的切片编号：

# tp_rank / tp_size 是 D；remote_tp_size 是 P
attn_ranks = [tp_rank * remote_tp_size // tp_size]
# 以下分支用于 D 的 TP 大于 P，且 D 的 TP 不超过 KV heads
head_slice = tp_rank % (tp_size // remote_tp_size)

这里得到的 head_slice 是 0 或 1，表示按 D 所需宽度划分后的第几片，不是全局 KV head 编号。实际源码通过 rank_offset_factor 携带这个值。D1 的切片编号为 1，对应源 P0 中的 heads 2–3。

物理布局决定这片数据怎样描述。对于每层按 [块, KV头, 块内Token, K/V内容] 存放的本例，一个头在块内的内容连续，相邻头也连续。设 D 的单层每块需要 M 个字节，那么 P 的单层每块有 2M 字节；D1 的远端 descriptor 可以用“源块起始地址 + M、长度 M”指向后半片。遍历下一个源块时，地址增加的是 P 的块步长，而不是 D 的块长度。

描述符descriptor可以理解为传输库接收的一份地址与长度说明。固定实现的 _build_fa_remote 正是用切片偏移、本地所需长度和远端块步长构造它；随后 ReadSpec 将选定的源 rank 与请求的源／目的块号对应起来。这样不必先把 P 的整块搬到每个 D rank，再丢掉其中不需要的头。

固定 vLLM：source rank 与切片偏移；远端地址、长度与步长；请求级 ReadSpec。对应单元测试核对 D rank2 / TP4 从 P rank1 / TP2 读取。这里只阅读源码与测试断言，未执行设备传输。

反过来，P=4、D=2 时，D0 需要把 P0 的 heads 0–1 与 P1 的 heads 2–3 收集到自己的正确位置，D1 对应收集另外两份。源码中 tp_size < remote_tp_size 的分支会选择多个远端 rank。这里改变的是分片的发送与接收关系，不能仅凭两边卡数变化就认定有效逻辑数据量改变。

为什么映射是正确性条件传输库通常只知道某段地址中的字节已经搬到另一段地址，不知道这些字节应该代表哪个请求、哪一层或哪个 KV 头。如果 D1 错拿 heads 0–1，传输本身可能正常完成，但它负责的查询头将使用错误的历史信息。完成状态和逻辑映射必须同时成立，D 才具备正确的 attention 输入。

边界这不是任意 TP 与布局都能自动互转的保证。模型头数和两边 TP 要满足整除条件；两边的模型、缓存 dtype、backend 与存储表示必须相容。这里直接取头片段还依赖连续布局；固定实现会检查相关条件，只有明确实现的布局转换分支才能执行额外重排。DCP/PCP、布局变化和量化表示在后续节点分别展开。

结论异 TP 的 KV 交接要对齐“请求、层、逻辑位置、KV 头”，再把它们落到源 rank、头切片和目的块。传输完成说明字节搬完，映射正确才说明 D 拿到了自己需要的数据。

张量图：P/D 异 TP 的缓存片段流向

固定一层、同一个请求和它已缓存的 T 个位置，模型仍是 8 个 KV 头、每头 128 维。下面只画已经由 P 计算并保存的 K/V；两边使用相同精度和相容布局。一个彩色竖带表示一个头在 T 个位置上的内容，带内小格只帮助看清切分轴，不与真实元素个数等比例。

  1. P0 → D0 / D1：P0 的 K、V 各为 [T, 4, 128]。分别取全局 heads 0–1 和 2–3，交给 D0 与 D1；每个目的 rank 的 K、V 各为 [T, 2, 128]。
  2. P1 → D2 / D3：同样将全局 heads 4–5 和 6–7 交给 D2 与 D3。请求的逻辑位置保持对应，只有 head 维的归属改变。
  3. D 获得的内容：每个 rank 直接得到后续本地 attention 所需的 K/V。这里的箭头是 cache-to-cache 传输，不是再次经过 Q/K/V 投影权重，也不要求把全部 KV 收到某一张卡上。

把方向改为 P 的 TP=4、D 的 TP=2，每个源 rank 只有两个头，而每个目的 rank 需要四个头。此时恢复的是目的 rank 所需的局部头范围：将两个来源写入对应的 head 槽位，逻辑上相当于沿 head 轴拼接。它不是把相同元素相加。

D0 分别接收 P0 的 heads 0–1、P1 的 heads 2–3，构成自己的 K_cache[T, 4, 128] 与 V_cache[T, 4, 128]；D1 分别接收 P2 的 heads 4–5、P3 的 heads 6–7，形成同样形状。两端的块号分别由各自分配器决定，映射还要携带源／目的物理块号，不能把相同数字的块号当成同一份数据。

参考要点

TP=4 时，每个 rank 持有一个 KV 头；增加到 TP=8 后，每个 rank 仍持有一个完整 KV 头，但每个逻辑头在两个 rank 上出现。因此每 rank 有效 KV 容量不变，D 的全部 rank 合计容量翻倍。

传输要按 D 的查询头所需的逻辑 KV 头重新映射。在本题沿用的顺序分配中，P0 提供给 D0、D1，P1 提供给 D2、D3，P2 提供给 D4、D5，P3 提供给 D6、D7。每个 D rank 都需要正确请求、层、位置和头的数据；相同数字的 rank 或传输完成标志不能替代这项映射。

符号与名词

T、L、ℓ
T 是已处理并缓存的输入位置数，单位 Token；L 是层数；ℓ 是层编号。
Hq、Hkv
查询头数与 K/V 头数。K 和 V 各有 Hkv 个头。
d、b
d 是等长 K/V 主例的每头维度；b 是 KV cache 每个元素的存储字节数。一般式分别用 dk、dv 与 bk、bv。
q、K、V、a、o
新位置的查询、可见位置的键和值、注意力权重、加权汇总输出。单头新位置：q/o 为 [1,d]，a 为 [1,T+1]。
Ctoken、Crequest
整个模型一份逻辑 KV 的每 Token 字节量与每请求字节量；尚未加入 rank 复制、padding 或传输额外开销。
MHA、GQA、MQA
每查询头独有 K/V、查询头分组共享 K/V、所有查询头共享一组 K/V 三种结构。
p、r、Hkv⁽ʳ⁾
p 是一个实例的 TP degree；r 是其中的 rank 编号；Hkv⁽ʳ⁾ 是该 rank 实际保存的 KV 头数。
Crequest⁽ʳ⁾
一个请求在 rank r 上的有效 KV 字节量。本段不含 PP/CP、物理块空位和其他显存。
头切片、rank_offset_factor
头切片是在一个源块内按 D 所需头数划分的片段；该固定实现用 rank_offset_factor 指示相应片段偏移，不是全局 head ID。
descriptor、M
descriptor 是传输库使用的地址、长度等说明；M 在节点 4 中表示 D 单层每块的字节数。
N、X、Zᵣ、Yᵣ、Y
N 是本次调用的输入位置数；X 是 attention 投影前的层输入；Zᵣ 是本 rank attention heads 展平的输出；Yᵣ 是本地 Wo 投影的部分结果；Y 是它们求和后的完整 attention 子层输出。
Wq、Wk、Wv、Wo
Q/K/V 投影权重与 attention 输出投影权重；本图采用 PyTorch [输出维,输入维]，线性计算为 XWᵀ。
