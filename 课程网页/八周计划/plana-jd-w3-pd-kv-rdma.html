同一个请求，为什么要交给两组实例

在 W1 中，一个请求经过 Scheduler 分配计算和 KV blocks，再由 Worker 执行模型。在 W2 中，我们反复追问：异步操作还要访问缓冲区时，谁负责保住它的生命周期？现在把这两个问题放到一起：让一组实例处理输入上下文，另一组实例接着生成回答，中间的 KV 怎样交接，双方又凭什么判断自己可以继续运行或回收内存？

这就是 Prefill/Decode 分离，简称 PD。Prefill 为输入 Token 计算各层的 KV；Decode 在已有上下文上逐步生成新 Token。把两个阶段分开，可以分别安排它们的计算资源和调度策略，同时也引入跨实例的数据传输、等待和故障处理。计算结束、数据可用和存储可回收，必须分别找到成立的条件。

这一课将从服务上的取舍走到真实的 KVConnector，再把 KV 大小、分页读取和 RDMA 数据路径接起来。学完之后，你应能根据固定源码解释一次正常交接和一次失败交接，判断哪些内存可以复用，估算传输的理想下界，并为没有目标硬件的场景写出可执行的验证设计。文字问答和设计证据按既有 W3 标准验收；正式口头 Mock 在 W4。

1从混部的一轮调度看 PD 的动机

资料位置：固定版本 Disaggregated Prefilling 的 Why disaggregated prefilling，讲完本节点再读。

设想同一个服务中有两个请求。请求 B 正在逐 Token 输出回答；请求 A 刚到达，带着一段很长的输入上下文。为了形成下一 Token，B 只需要推进当前一步；A 的 prefill 则要处理整段输入。两者共享实例时，Scheduler 要决定怎样把它们放进计算批次。

先明确两个用户指标。TTFT 是请求到达后，用户等到第一个输出 Token 的时间；ITL 是相邻两个输出 Token 之间的间隔。如果 A 的大块 prefill 插入 B 的生成过程，B 下一 Token 可能需要等待更长的一轮执行。这里没有假定每次混部都会变慢：chunked prefill 可以把 A 分块，调度器也可以控制每轮给 prefill 的预算。问题在于，这些调节会同时影响 A 的首 Token 等待与 B 的连续输出。

PD 把两类工作交给不同实例组：P 接收 A 的输入并计算 KV，D 接收交接的数据后继续生成。这样 P 的批次大小、并行配置和容量可以围绕输入处理调整，D 则围绕连续生成调整。请求 B 不再因为同一个 D 实例突然插入 A 的 prefill 而直接等待那段计算。这里说的是计算阶段隔离；共享网络、前端服务或其他资源仍然可能产生干扰。

你在 W2 学过 PP。PP 按模型层把一次前向计算分给多个阶段；这里的 PD 按一个请求的生命阶段分工。以本课基线为例，P、D 都有完整模型的实例组，每组内部仍可以使用 TP 或 PP。Decode 需要先前上下文的 KV，因此两组实例之间必须增加交接，而不是只转发请求文本。

真实系统中的收益与代价。vLLM 文档把分别调节 TTFT/ITL 和控制尾部 ITL 列为 PD 的动机，并明确提醒不能把该功能当成吞吐提升保证。用固定总 GPU 数部署时，你需要在 P 和 D 之间分配容量；即使一侧空闲，另一侧也可能排队。再加上 KV 传输，端到端路径上可能出现新的等待。

来源：vLLM d7ada3a…，docs/features/disagg_prefill.md 的动机与吞吐说明。固定容量下的队列失衡是由分池结构作出的系统分析，不是本课的性能实测。

测量时应沿一次请求观察：进入 P 前的排队、P 计算、交接等待、D 获得执行机会以及首个结果送达客户端。这些区间可能重叠，也可能由不同组件计时；需要先按实际事件画出关键路径，再判断主导项。某个 kernel 变快，并不自动意味着用户更早看到结果。

本节归纳PD 提供分别安排两个阶段的机会，并能隔离直接的 prefill/decode 计算干扰；它同时引入 KV 交接和两侧容量匹配问题。收益必须按端到端指标及资源成本判断。

2沿请求 A 追踪两份 KV 的生命周期

资料位置：KVConnectorBase_V1.request_finished，以及 NIXL Pull 的完成通知。先理解本节点的因果关系，下一段再逐字段追实现。

继续看请求 A。现在假设 P、D 使用相同模型、相同 TP 和 KV 布局，并且这次是正常成功的复制式交接。P 的本地 KV blocks 保存已经计算好的输入上下文；D 分配自己的本地 blocks 接收这些数据。两端地址和 block ID 可以不同，connector 的 metadata 必须说明从哪里搬到哪里、属于哪个请求。下面不涉及前缀共享，也不把源块回收等同于释放所有可能共享的缓存内容。

这里选择 PULL 路径作为第一条源码主线：D 获得远端位置等信息后，发起对 P 数据的读取。与之对应，PUSH 由发送侧主动把数据写向接收侧。发起方改变了控制流程，但两种方式都要回答相同的安全问题：源数据是否仍被访问？目的数据是否已经完整到达，并且对本地计算可见？

即使 P 已确认 prefill 的设备计算完成，也只说明 KV 的生产阶段已经结束。传输系统可能还没有读完源 blocks，因此 P 不能据此把这些 blocks 交给另一个请求覆写。D 收到 metadata，也只说明它知道要取什么；D 必须等数据成功到达，并满足本地布局和设备可见性要求，才能把它当成 attention 的有效输入。

回到真实框架。基类的 request_finished 允许 connector 返回“延后释放”，让请求计算结束后仍保住 KV。Scheduler 随后分别处理发送侧和接收侧的完成结果。这延续了 W2 的判断方法：先找到最后一次访问与完成依赖，再决定能否回收，不能只看函数是否返回。

还有一个读源码时要保留的区别：这个版本的 finished_recving 表示接收活动已收尾，其中可以包含 failed_recving。所以源码中的“finished”不能只凭名字翻译成“可成功消费”。下一段会沿真实字段说明成功与失败怎样分流。

本节归纳D 需要的是成功传入且本地可用的 KV；P 需要的是源数据已不再被相关传输访问的依据。两端的存储与责任分别结束，不能用一个含糊的“完成”概括整个请求。

参考要点

PD 可以减少 prefill 对正在生成请求的直接计算干扰，但端到端 TTFT 还包含 P 排队、交接等待与数据搬运、D 就绪后的排队及首个输出所需工作。应比较同一计时口径下的首 Token 关键路径变化；不能用后续 ITL 的累计改善抵扣 TTFT，也不能仅凭某段耗时较大就完成根因归属。

本课正常复制交接基线下，同一请求在 D 上继续生成时通常无需再跨 P/D 搬运已有上下文 KV；本地 KV 仍会读写并增长。其他请求的传输、共享带宽及资源争用仍可能影响 ITL。

参考要点

网络带宽提高、实际搬运缩短却没有明显改善 TTFT，说明本次改动尚未缩短端到端主导路径。D 的 KV 就绪后等待很长，应优先调查 D 的准入与调度；P 经常空闲使 P/D 容量失衡成为合理假设。

分别观察两侧排队时间与队列长度、请求到达与实际处理速率、计算及 KV 容量占用，并结合调度预算与限制解释等待。确认 D 的有效服务容量不足后，才有依据调整资源配比；“排队长”本身不保证增加 GPU 就能解决。

3Scheduler 怎样把一次远端命中变成交接任务

资料位置：scheduler.py 的外部缓存查询与分配分支、nixl/pull_scheduler.py 与 base_scheduler.py。先读本节点，再用下一节点的源码浏览器定位原文。

沿用请求 A：P 已产生上下文 KV，现在 D 收到了带远端交接参数的请求。为看清职责，本段把 P、D 各自简化为一个模型实例、一个 Worker，TP=PP=DP=1，使用普通全注意力，暂不启用 speculative decoding、PCP/DCP 或 host staging。D 没有命中本地前缀缓存，需要从 P 读取已有 KV；这是一条源码阅读基线，不是已经运行的部署。

从 W1 的进程边界出发，D 的 Scheduler 管理请求队列、Token 预算和 KV block 分配；Worker 持有用于执行模型的设备缓存、具体传输对象与设备执行环境。Scheduler 可以决定给 A 哪些目标 block ID，却不因此拥有 Worker 中对应的设备地址。因此，KVConnector 在调度侧和 Worker 侧各有一个角色实例，二者通过 metadata 与结果消息协作。

第一步：查询可利用多少外部 KV。Scheduler 先查本地前缀，再调用 get_num_new_matched_tokens。本段 NIXL Pull 的远端 prefill 分支依据请求参数和本地已计算数量，返回可加载的外部 Token 数以及异步标志。这里的 True 意味着“准备跨调度步异步加载”，不是“加载成功”。这段查询没有启动网络读取，也没有在 D 的显存中填入 KV。

第二步：先给数据安排落点。Scheduler 调用 allocate_slots 为 A 安排目标 blocks，把 delay_cache_blocks=load_kv_async 传给缓存管理器。这样分配与内容有效性可以分开处理。若连目标空间都无法分配，这次交接就不能按该路径开始；仅仅知道远端有数据，不能解决本地容量问题。

第三步：登记本次要搬什么。分配后调用 update_state_after_alloc。NIXL 的调度侧实现拿到目标 block IDs、已在本地的前缀范围以及请求中的远端信息，把需要接收的任务放进 _reqs_need_recv。这个字典属于调度侧对象，是“下一次要交给 Worker 的计划”，不是两个进程共享的传输队列。

第四步：发出计划，同时把 A 留在等待状态。build_connector_meta 将暂存任务转成这一调度步的 metadata，并清空已打包的接收任务；Scheduler 把结果放进 SchedulerOutput.kv_connector_metadata。因此该构建函数会消费暂存状态，调试时应检查已有结果，不能为了打印而再次调用它。异步加载中的 A 被标为 WAITING_FOR_REMOTE_KVS，后续就绪的其他请求仍可被安排计算。

有一个容易误读的字段：源码会在 A 仍等待传输时预先更新 num_computed_tokens。这服务于调度记账，并不单独证明 D 的 KV 已到达；等待状态使这个请求暂时不能拿这些缓存做计算。成功、失败以及后续状态转换必须连起来读，不能只拿一个数字判断可执行性。

4Worker 怎样推进传输，再把结果交回 Scheduler

资料位置：传统 gpu_model_runner.py 与 KVConnectorModelRunnerMixin，再进入 NIXL Pull Worker。这里固定这一条 runner 调用链，不混用 gpu/model_runner.py 的另一套实现。

现在 metadata 已随调度输出到达 Worker。Worker 先把它绑定到本地 connector，使接下来这一轮的加载与结果收集使用同一份任务描述。NIXL Pull Worker 根据源/目的块映射构造远端 READ；提交之后记录传输 handle，后续轮次再查询是否完成。handle 可以理解为这次异步 I/O 的句柄，保存它才能跟踪和清理同一项操作。

接下来需要区分“这一轮执行模型”和“为 A 加载 KV”之间有没有数据依赖。假设另一个请求 B 的 KV 已经就绪，可以在本轮继续生成；A 仍处于等待远端 KV 的状态。提交 B 的模型计算不需要先完成 A 的传输，因此本版本可以先提交本轮 forward，再启动 A 的异步加载，减少加载提交工作对已有计算的主机端阻塞。源码明确区分同步与异步两条分支：

        start_after_forward = not scheduler_output.has_sync_kv_loads

        try:
            yield output
        finally:
            if start_after_forward:

这里的 yield output 位于 @contextmanager 定义的上下文管理器中：执行到它时，把控制权交回调用方的 with 代码块，由调用方提交模型 forward；离开该代码块后，再回到 finally。因此顺序判断要同时看调用方与管理器。它不表示 GPU 已完成全部计算，也不表示本轮计算包含所有等待中的请求。

如果是同步加载，而本轮 forward 就要消费加载的 KV，依赖会相反：加载必须先满足该计算的输入条件，代码便在 yield 之前调用加载接口。对于本段的 NIXL Pull 异步路径，A 的计算由 Scheduler 延后到接收成功之后；“先算后搬”指的是本步其他可运行请求与 A 的加载之间的顺序。

还有一个维持进展的细节：若本步没有任何模型 Token 可算，runner 也不能直接让传输停止推进。真实实现保留 kv_connector_no_forward，仍处理 metadata、提交加载并收集结果。否则系统可能因为所有请求都在等 KV，而再也没有一步负责让 KV 传输向前走。

结果怎样返回。Worker 用 get_transfer_results 收集发送完成、接收收尾和接收失败三个集合，将它们放入 KVConnectorOutput，随 ModelRunnerOutput 返回。Engine 再把结果交给 Scheduler。成功接收的请求在后续调度中解除远端等待，然后才参与计算；失败项走修正有效前缀或恢复的分支。这里“结果已回报”与“已经拿到计算机会”仍是两个时间点。

继续使用前面两个请求 X、A 和同一个 block 7。它们都由 D 节点执行，P 只负责向 A 提供远端 KV。为说明问题，假设 X 的两个计算步 S1、S2 已先后提交，S2 仍在途；它可能已排队，也可能正在执行，不要求 S1、S2 的 kernels 同时运行。

为什么会多出 S2？在允许重叠批次的执行路径中，CPU 不必先处理完 S1 的输出，才提交下一步。GPU 上的 S1 结果可能已产生，而 CPU 还没解析停止条件；这时 S2 已经进入执行流水。接下来 CPU 处理 S1，发现停止 token（例如 EOS），于是把 X 标记为完成。这个状态修改不会自动撤回已提交的 S2。

  1. CPU 处理 S1 的停止结果，判定 X 已结束；S2 尚未结束。
  2. 错误实现立即把 X 的 block 7 归还到空闲池，随后把它分给新请求 A。
  3. A 的 connector 将远端 KV 写入 block 7。此时其中某个槽位保存的是 A 对应位置的 K/V。
  4. X 的旧 S2 随后向同一个槽位写入 X 的 K/V。它执行的是先前提交的地址与索引，不会重新查询“这个块现在属于哪个请求”。

这并不要求 GPU 计算流内部乱序。X 的 S1、S2 可以保持正常顺序；危险在于 A 的异步 connector 写入没有自动排在 X 的旧 GPU 写入之后，两条路径之间缺少必要的依赖。

真实保护怎样阻止这个顺序？在本例中，X 的 last_sched_seq=2，CPU 只处理到 processed_step_seq=1。条件 2 <= 1 不成立，所以先把 blocks 留在延迟释放队列，暂不归还 block pool。A 此时不能从空闲池拿到 block 7。

补充：GPU 通信是否必须两端各启动 send／recv kernel

甚至可以不用专门的 GPU 通信 kernel

同机 CUDA peer copy：CPU 可以调用 cudaMemcpyPeerAsync 等拷贝 API。CUDA 在可用条件下利用专用 copy engine 和 NVLink 等路径完成搬运；应用不必为两张卡分别编写 send/recv kernel。Copy engine 是数据搬运硬件，与运行 CUDA 线程块的 SM 不是同一个执行单元。

跨机 GPUDirect RDMA：在内存注册、连接和平台条件满足时，CPU 可以给 NIC 提交 RDMA 操作，NIC 直接访问 GPU 显存。一次 WRITE 可以由源端 NIC 读取 GPU 0 的数据，经网络交给目标 NIC 写入 GPU 1 显存；READ 则由取数端发起。数据移动不要求两边的 SM 各运行一个配对通信 kernel。CPU 控制代码、NIC 进度和 GPU 计算仍是不同角色。

回到我们正在读的 NIXL PULL/PUSH

本课的 Worker 是执行侧进程，其中也有 CPU 控制线程。start_load_kv、make_prepped_xfer 和 transfer(handle) 这些 Python 调用并不是 GPU kernel。PUSH 的 nixl-push-writer 也是 CPU 后台线程：P 的 host 侧提交 WRITE，D 提前提供可写的目的区域并处理完成状态，不需要在 vLLM connector 协议中再配对一个 recv GPU kernel。

同理，PULL 是 D 的 host 侧提交 READ，不等于“D GPU 必须运行一个 pull kernel”。某个 NIXL backend 是否另外执行 GPU 拷贝、重排或其他 kernel，需要结合实际后端与 trace 判断。“谁发起传输”既可能指 CPU 上的提交方，也可能指 GPU kernel 中的发起方；描述时必须把这一层说出来。

固定源码：vLLM d7ada3a… 的 kv_connector_model_runner_mixin.py:79–90 明确说明 host-side submission；pull_worker.py:554–567 提交 READ；push_worker.py:146 启动 CPU writer 线程，:734–745 提交 WRITE。以上是控制流证据，不声称本机测得某后端完全没有 GPU kernel。

CPU 提交命令，拷贝引擎或网卡搬运字节

NIC 是 Network Interface Card，即网络接口卡，通常就叫网卡；具有 RDMA 能力的网卡常称为 RNIC。它是服务器的网络设备，不是执行 CUDA 线程的 GPU SM。Copy Engine 则是 GPU 的专用拷贝引擎，也不同于运行计算 kernel 的 SM。

同机：源 GPU 显存 → 拷贝引擎／peer 链路 → 目标 GPU 显存
跨机：源 GPU 显存 → 源端 RNIC → 网络 → 目标端 RNIC → 目标 GPU 显存

CPU 可以负责准备地址和长度、登记内存、提交操作以及处理进度；这不意味着 CPU 必须逐字节搬运，也不意味着数据一定要经过主机内存。在适用的 CUDA peer-copy 或 GPUDirect RDMA 路径中，纯搬运可以不启动专门的 GPU 通信 kernel。目标 GPU 后续使用数据时，仍须满足完成和内存可见性条件。

参考要点

题设只修改了 P 的发送完成判定，没有改变 WRITE 操作携带的完成通知。D 不会发送新增 ACK，因此 P 一直无法按该判定回报 finished_sending，源块继续被保留；D 仍可收到原有 WRITE 完成通知，在满足本地就绪条件后继续生成。源端保留积累可能降低 P 的可用缓存容量，但不是这次 WRITE 无法完成。

正常 PUSH 的 P 根据自身相关 WRITE 句柄全部成功收尾结束传输责任；Scheduler 收到完成结果后再按本地访问保护与引用规则回收。不能把 P 的软件完成上报误作 D 完成通知的发送触发条件。

参考要点

D 已正常收到 WRITE 完成通知，可以独立完成适用的本地数据处理、可见性确认和后续调度；不需要等 P Scheduler 收到自己的结果消息。

P Worker 已知 WRITE 完成，不等于 P Scheduler 已获得解除传输保留的依据。结果上报延迟时，Scheduler 仍按未收到完成结果的状态保留源块。即使相关本地 GPU step 全部结束，这个软件状态门槛仍存在；本地在途访问保护是另一项回收条件。

导师串讲：沿请求 A 把单元一接成一条链

现在把各节点接起来。请求 A 带着较长输入到达 P，P 完成 prefill，准备好对应上下文的 KV。与此同时，D 上可能已有请求 B 正在生成。PD 让两组实例分别安排工作，但 A 的端到端等待仍取决于 P 排队与计算、交接，以及 D 的可用容量。我们不能只看 P 的计算缩短了多少，就宣布 TTFT 或吞吐已经改善。

先沿 PULL 主线走。D Scheduler 接到 A 后，查询能从远端利用多少 KV，再为 A 分配本地 blocks。远端命中、目标空间分配和数据已到达是不同事实。connector 在分配后登记接收任务，打包进本步 metadata；A 留在 WAITING_FOR_REMOTE_KVS，B 等已就绪请求可以继续参与本步计算。

Worker 的 host 控制代码取得 metadata，依据请求身份和块映射准备传输描述。我们已经看过，池 block ID 还要根据 backend 页粒度与 region 描述映射到地址范围；传输 API 收到的是可定位内存的描述，而不是把数字 block ID 当作地址。D 在 PULL 中提交 READ，保存句柄，并在后续轮次收集结果。即使本步没有模型 Token 可算，也必须继续推进这条通信路径。

数据移动和收尾随后分成两端的责任。D 的相关 READ 成功结束，完成适用的本地处理与可见性要求后，回报接收结果，由 Scheduler 解除远端等待，再安排 attention 读取。P 则根据相关读取方的完成通知结束源端传输保留。两端的回报和调度不需要形成“D 已开始计算，P 才能回收”的固定全局顺序。

源块的实际复用还要走框架的回收规则：完成事实须传到 Scheduler；先前提交的本地 GPU 工作不能继续访问已被复用的空间；最终归还 block 引用，引用归零才允许分配给其他请求。传输句柄、P 源块和 D 目的块是不同资源。D 继续生成时使用自己的副本，P 没有必要为这段消费一直保留源数据。

换成 PUSH 时，我们保留同一份逻辑 KV 和两端各自的存储，只改变控制组织：D 登记目的块，P 将目的登记与已完成源块配对，并发起 WRITE。正常路径的 P 通过自己的 WRITE 句柄判断发送完成；D 通过所需写入方的完成通知进入接收收尾。内存安全条件不因操作名称改变，也不能把一种模式中的额外通知要求直接塞进另一种模式。

这条主线落在真实 vLLM 中，是 SchedulerOutput 向执行侧传递 metadata、Worker 的 connector 管理传输、KVConnectorOutput 向 Scheduler 回报结果的循环。实例里同时存在多个请求，完整缓存横跨多个层与区域；多 Worker 场景还需要汇总相关操作的完成。我们用单 Worker 看清责任，没有把它误当成所有部署只有一个句柄或一条通知。实际搬运可以由 GPU、拷贝引擎或 NIC 等路径承担，所用后端决定实现，框架仍要维持上述依赖。

参考要点

D 的 Scheduler 分配目标 blocks 后，connector 将请求、D 实例和目标块信息打包，经 D Worker 发送目的登记。P 的 Scheduler 在 prefill 正常结束后保留源块，并把完成的源块信息交给 Worker。P 将两者按逻辑请求配对，满足握手与传输描述条件后提交 WRITE。

相关 WRITE 句柄全部成功收尾后，P Worker 回报 finished_sending，P Scheduler 再按本地访问保护与引用规则回收。D 收齐所需 WRITE 完成通知，执行实际路径需要的本地数据准备与可见性处理，回报接收结果并进入后续调度。两条收尾链分别依赖各自的完成证据，没有“D 必须先消费完，P 才能回收”的一般顺序。

综合核验 2身份与映射诊断

请求 A、B 并发走相同布局的 PUSH，二者 KV 内容可区分，P 的源 KV 已分别核对正确。所有 WRITE 和完成通知都成功，但在 D 的模型消费之前，发现 A 拥有的目标块里是 B 的 KV，B 的目标块里是 A 的 KV。能否凭“传输成功”排除 connector 接入问题？你会优先核对哪些身份或块映射关系，并用什么最小断言暴露这种错误？

断言可用文字或伪代码表达，不要求实现 harness；按题设讨论正常数据路径的映射正确性，不扩展超时或进程故障。

参考要点

不能凭传输成功排除 connector 接入问题。传输系统可以正确执行给定的地址与长度，却把请求的数据写到了错误目的位置。应核对逻辑请求身份的关联、实际分配的池 block IDs、backend 页／descriptor 的展开，以及最终 WRITE 源与目的的配对。

学习者提出的“源块所属请求与目的块所属请求一致”可以发现本题互换，前提是 owner 从独立的实际分配记录取得，并检查真正交给 WRITE 的块对；不能只比较同一份可能已经错误的消息中的两个标签。P、D 本地 request ID 可能不同，应判断它们是否关联同一逻辑请求，而非一律要求字符串相等。

可补强的端到端断言是：按请求在 D 实际拥有的目标块读取内容，确认其与该请求的预期 KV 标记或源数据摘要一致。它可以覆盖“metadata 标签正确、地址展开错误”的情形；这是对验证方法的补充，不要求为本题另外实现 harness。

符号与名词

P / D
Prefill / Decode 实例组；分别处理输入上下文与后续逐 Token 生成，各自拥有模型权重和本地 KV 存储。
KVConnector
连接调度决策与 KV 传输实现的接口；可类比由控制代码与执行代码共同实现的异步 I/O 适配器。
TTFT
Time To First Token；从请求到达到客户端收到第一个输出 Token 的时间。
ITL
Inter-Token Latency；客户端相邻输出 Token 的时间间隔。尾部 ITL 指该分布较高分位的延迟。
metadata
描述请求、源/目的位置及块映射等的信息；类似带索引和地址的任务描述，不是 KV 数据本身。
PULL / PUSH
由接收侧发起远端读取 / 由发送侧发起远端写入；两者都需要明确内存访问与完成依赖。
SchedulerOutput
一次调度步发给执行侧的工作描述，包含本步计算安排和 connector metadata；不同字段可以面向不同请求。
transfer handle
一次异步传输的句柄；用于查询、跟踪与清理对应操作，不等于传输完成。
WAITING_FOR_REMOTE_KVS
请求正在等待远端 KV 的状态；调度记账中的 Token 数不单独赋予它消费 KV 的资格。
DONE / PROC
本段传输库轮询中的状态：操作完成 / 仍在进行。它们描述传输操作，不描述整段模型生成。
lease（租约）
有期限的资源保留约定；本课用于源 KV 的保留与续期。到期回收是一条异常政策，不是数据成功到达的证明。
PUSH_REG
NIXL PUSH 中用于传递请求级目的位置的登记通知；包含请求与实例身份、目的 block IDs 等信息，不等于 KV 已写入，也不等同于 RDMA 内存注册。
ACK
确认消息；必须说明确认的是哪一项动作。传输完成、源块可回收和 D 已消费完是不同事实。
Copy Engine（拷贝引擎）
GPU 上执行数据搬运的专用硬件；不同于执行 CUDA 线程块的 SM。
NIC / RNIC
Network Interface Card，网络接口卡；具备 RDMA 能力的网卡常称 RNIC。它可在满足平台条件时直接访问 GPU 显存。
SM
Streaming Multiprocessor，GPU 中执行 CUDA 线程块的计算单元；CPU 提交 GPU 间拷贝不必等于启动 SM 上的通信 kernel。
