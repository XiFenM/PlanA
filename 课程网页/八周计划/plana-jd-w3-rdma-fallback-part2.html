5显存不能被网卡直接访问时，怎样接上整条路径

对应主线第 2–3 项。先沿本节的数据路径读，再看固定 vLLM 的 Host buffer 分支；前页已解释的 IBRC／IBGDA 分工与具体可见性操作在需要时回看即可。

把主例中的 64 KiB 缓存片段移回 P 的设备显存，D 的计算也需要从设备显存读取。假设两端模型、缓存表示和目标映射已经相容，我们现在只改变一项条件：设备显存能否直接参与网络搬运。

先逐项核对三件事：网卡和驱动能否注册、访问这种设备内存；后端是否提供对应的传输路径；完成后怎样把数据交给计算。三项都满足，才可以考虑设备内存直达网卡。CPU 能否提交任务与此是不同的问题：前页的 IBRC 已经说明，CPU proxy 管提交时，payload 仍然可以直接来自 GPU 显存。

现在假设两端都没有显存直传能力，但能够在设备与 Host 之间拷贝，并且 Host 内存可以注册给 RNIC。我们增加 P、D 两个 Host 中转区：先把片段复制到 P Host，再通过 RDMA 写入 D Host，最后复制到 D 设备。D2H 是 Device→Host 拷贝，H2D 是 Host→Device 拷贝。

这里至少涉及四个存储位置。判断某个位置能否重用，要看谁还会读取它，而不能只问“网络完成了吗”。先只考虑这一次正常传输带来的读取依赖：

缓冲区本路径中最后一个读取者解除这次读取依赖的条件
P 设备源D2H 拷贝D2H 已完成；原 KV 是否释放，还要看框架其他引用与保留策略。
P Host 中转区网络传输取得对应传输不再读取源区的完成依据。
D Host 中转区H2D 拷贝H2D 已读完；网络完成只说明它现在有数据可供拷贝。
D 设备目标后续 attention 等计算消费者已用完，并且上层引用允许归还。

这张表不代替完整的回收协议：请求还可能持有其他引用，故障重试也可能要求保留副本。它先回答最基本的问题——一次网络完成不能同时归还整条流水线的所有缓冲区。

为什么这是一条可用的回退路径它把“不支持设备内存注册”的限制，转换成已经支持的 Host 注册与设备拷贝。代价是两端新增的拷贝、Host 内存占用、同步和队列等待；设备↔Host 的拷贝常由 DMA／拷贝引擎执行，不能直接等同于 CPU 逐字节 memcpy。若只有一端缺少直传能力，也可以只让那一端中转。

串行执行时，片段延迟包含 D2H、网络、H2D 及相应调度等待。分块流水可以重叠不同片段的这些阶段，但需要更多中转槽和事件；最慢阶段或共享 PCIe／内存带宽仍会限制吞吐。中转槽耗尽时，应让上游等待或限流，不能覆盖尚未被读取完的槽。这里的“背压”就是把下游容量不足传回上游。

真实系统固定 vLLM 的 NIXL worker 明确保留 host_xfer_buffers。选择 Host buffer 后，注册的是这份 CPU tensor；设备副本仍留在 device_kv_caches。成功接收分支先收集网络完成，再把 Host KV 复制到设备，最后才返回本轮传输结果：

done_recving, newly_failed = self._pop_done_transfers(self._recving_transfers)
# 中间按请求处理，并排除对应失败分支。
if self.use_host_buffer:
    self.sync_recved_kv_to_device(req_id, meta)
# 之后还有必要的后处理／设备同步，再返回传输结果。

该版本在 save_kv_to_host 和 sync_recved_kv_to_device 中按同步调用组织 Host 拷贝，并在 copy 回调返回后才返回接收结果；具体设备写入与后续计算的顺序仍由平台 copy 实现和消费 stream 的约定保证，不能由这段代码推定任意另一条 stream 都可立即读取。如果改变拷贝的异步行为，就必须相应调整 event 或其他消费依赖，不能只改调用方式而沿用原来的“已完成”含义。源码里的 gpu_sync_allowed() 是同步调试许可上下文，本身不是执行拷贝或同步的 API。

固定实现：Host buffer 选择、实际注册对象、同步 H2D／D2H。平台支持表只说明该版本 connector 的允许组合，不代表某类芯片永久的硬件能力。

还要核查谁在推进任务异步 API 返回后，网络、拷贝和通知不一定都由同一执行者推进：RNIC 处理网络，CPU 线程可能轮询或推进通信库，设备任务流执行拷贝和计算。CPU proxy 停止工作、缺少必须的 progress 调用或消费流没有等 event，都可能使上层一直等不到可用数据。具体责任应从后端运行方式与 trace 确认。

配置中的 backends=["UCX"] 只选定软件 backend；实际 transport、设备和内存类型仍取决于构建与运行配置。判断路径应对照实际注册描述、后端日志和拷贝／完成事件，不能只看 backend 名称，也不能由阅读源码宣称已验证目标硬件性能。

结论设备直传与 Host staging 的选择取决于可用能力；提交者、进度推进者和 payload 所在位置要分别确认。新增中转阶段以后，完成、消费与缓冲区回收必须沿新增依赖一起延长。

补充：GPU initiated 的层次、实现条件与交互图

设源端 GPU 已产生一段 KV，要通过网络交给远端。要描述这次通信，至少需要回答两个问题：谁提出并提交通信任务，payload 实际经过哪些内存？如果只说“GPU initiated”，资料可能指 GPU kernel 提出通信请求，也可能特指 GPU 直接驱动网卡。因此，下面把控制职责继续拆为“提出请求、生成 WQE、敲 doorbell”，再单独画实际数据路径。

CPU initiated：由 Host 上的 CPU 程序主动发起这次通信；GPU 可以只负责生产或消费数据。GPU initiated：请求由 GPU 上运行的代码发起，但是否经过 CPU proxy，需要继续查看实现。IBGDA 则是 NVSHMEM 的一种具体传输实现；典型模式由 GPU 生成工作请求并通知网卡，CPU-assisted 模式把 doorbell 工作交给 CPU。

GPUDirect RDMA描述的是数据访问能力：在设备、驱动、映射和权限满足要求时，RNIC 可以直接读取源 GPU 显存，也可以直接写入目标 GPU 显存。它并不规定通信必须由 CPU 还是 GPU 发起。NVSHMEM 同时提供 Host 和 GPU kernel 可用的通信接口，具体数据面还取决于所选后端与平台。

图 B 与图 D 都有 CPU 参与，但 CPU 的任务不同：IBRC 的 proxy 要把 GPU 请求转换成网卡 WQE 并提交；CPU-assisted IBGDA 已由 GPU 生成工作请求，CPU 主要承担 doorbell 通知。比较时应写清这些职责，不能仅凭“有 CPU 线程”把两者归为同一种实现。

实现方式受哪些客观条件约束

把一行调用放在 CPU 还是 GPU 上，并不能自动获得完整通信能力。对于现有硬件、驱动和库栈，先核对可实现的路径，再在可用路径之间做选择：

  • GPU 能否提出请求。需要 GPU 可调用的通信 API，或一套正确的 GPU→CPU 请求通道。若由 CPU proxy 承接，还要有发布／观察的同步规则，以及持续推进的代理线程。Host 上的 ibv_post_send 不能直接搬进 CUDA kernel；自行增加 device 接口或代理协议属于实现工作。
  • GPU 能否直接驱动 RNIC。GPU 生成的工作队列内容必须能被设备正确读取，GPU 还要能够通过平台支持的映射与通知机制发布工作，并满足顺序要求。GPU、NIC、驱动、库后端和运行配置的支持缺一不可。
  • 网卡能否直接访问显存。这取决于实际内存类型、注册／映射、拓扑及互操作能力。它与前两项分别判断；支持 GPU 发起请求不会自动补齐显存直传能力。
  • 完成如何变成可消费。所用路径还要有完成观测、进度推进与消费者同步规则。能够发出请求，不代表已经解决数据可见性、缓冲区复用或失败处理。

CPU-assisted IBGDA 是一项实际适配：NVSHMEM 3.0 把 GPU 生成请求与 CPU 敲 doorbell 分工，放宽传统 IBGDA 的 peer mapping 管理配置约束。能否选用这种方式，仍以该版本和平台是否支持相应模式为前提，不能把它当成任何硬件上都可打开的通用开关。

当多条路径都可用时，再比较性能：GPU 发起可能减少 CPU／GPU 控制往返，并提高大量小消息的提交并行度；也会消耗 GPU 执行与队列资源。CPU 提交在一些大消息或已有 Host 调度的场景中可能已经足够。实际取舍要看消息大小、频率、并发、拓扑和测量结果，不能仅凭发起者给出快慢排序。

6没有 RDMA 或只有 collective，怎样保留交接契约

对应主线第 3–4 项。继续改变同一个 P→D 片段的传输条件；本节区分硬件能力限制与 API 限制，再回到上层 connector 的职责。

刚才只缺少“显存直传”，Host RDMA 仍然可用。现在分别看另外两种环境：第一种没有可用 RDMA，但有常规 TCP/socket 和设备↔Host 拷贝；第二种设备通信库只暴露 collective 操作。它们缺少的能力不同，不能用同一个开关处理。

没有 RDMA：把网络这一段换成消息传输

保留图 5.1 两端的 D2H／H2D，把中间的 Host→Host RDMA 换成 TCP/socket，就得到一条基本可行的通路。D 的网络程序现在要组织接收，把完整 payload 放入指定 Host 缓冲区，然后再复制到设备。此处不再把 remote_addr／rkey 交给网络设备执行远端写，而是由接收方软件根据消息元数据选择目标。

TCP 提供有序字节流，但不替应用保存消息边界。发送一条消息不保证接收方一次 recv 就得到完整内容，也可能把相邻消息的一部分一起读到。协议可以先传固定格式的头，包含请求／代际、布局标识与 payload 长度，再按长度读满正文；消息头自身也必须完整接收并校验。

# 前提：消息头已完整接收，0 < nbytes <= len(host_dst)。
view = memoryview(host_dst)[:nbytes]
while view:
    count = sock.recv_into(view)
    if count == 0:
        raise EOFError("payload 尚未收完整，连接已经结束")
    view = view[count:]
# 到这里正文才已读满；如需 GPU 消费，继续安排 H2D。

Python 3.13 socket 接口示意；阻塞式连接、无其他线程竞争读取。省略协议头、超时与请求清理，它们属于完整实现必须补齐的部分。

发送端可以使用 sendall 处理完整提交，但它成功返回不证明 D 已收到整帧，更不证明 D 已完成 H2D 或计算。需要远端状态时，协议仍须提供相应通知。这个回退通常增加软件协议处理、可能的中间拷贝及 CPU 开销；实际拷贝次数与性能受 socket 优化、平台和实现影响，不能先写死。它换来的是对特定 RDMA 硬件／驱动能力的依赖更少。

只有 collective：先让通信组参与同一轮操作

“只提供 collective”描述的是应用能调用什么 API。通信库内部仍可能使用 RDMA，也可能使用 sockets。以 NCCL 2.25.1 为具体接口例子：如果 P、D 已经处于一个协调好的通信组，组内所有 rank 可以共同调用 Broadcast，把 P 的字节复制到各 rank 的接收区。通信组对象常称为 communicator；其中的 rank 是组内编号。

// 各 rank 都调用；P 的 buf 已准备，其他 rank 的 buf 已分配。
// 各方一致使用 nbytes、ncclUint8、p_rank 和同一轮 comm。
ncclBroadcast(buf, buf, nbytes, ncclUint8, p_rank, comm, stream);
// D 的后续消费与这个 stream 建立正确依赖。

NCCL 2.25.1 Broadcast 接口示意；用 ncclUint8 按字节复制，nbytes 为该片段字节数，p_rank 是 P 的组内编号。省略 communicator 创建及错误检查。

这里发生了与普通点对点交接不同的事：即使某个 rank 不需要这份 KV，它仍是这次 collective 的参与者。各 rank 要匹配操作、count、dtype、root 和调用顺序；动态请求先来后到不同，调度层就必须先协商轮次。不能让各 rank 根据自己本地的请求队列各自发起广播，然后期待库自动把它们匹配起来。

若通信组比实际 P/D 接收集合更大，Broadcast 会带来额外接收、缓冲区和调度协调开销。AllGather 也能搬运数据，但会收集所有 rank 的等长贡献，并把拼接结果交给所有成员；不规则长度往往需要先协商或 padding。AllReduce 还会对元素执行 sum 等规约，不能默认拿它替代原样 KV 复制。

为什么不能只把调用名换掉PD 请求有自己的目标 rank、生命周期与动态到达顺序，collective 却有组参与和操作匹配要求。能够建立并调度合适的小组时，collective 可以成为一种实现选择；如果现有 API 或运行时无法组织所需参与者，就要调整执行安排、补充接口或保留同实例执行，不能把不满足条件的方案叫作已实现的 fallback。创建子通信组本身也可能要求原组成员共同参与。

NCCL 另外提供 ncclSend／ncclRecv 点对点接口，但那是额外能力；“库支持 collective”不足以推出它们也可调用。若这些接口可用，应按其配对与完成合同设计，而不是继续假定只有 collective。

消息通路：Python 3.13 Socket HOWTO、recv_into与 Linux send(2)。collective 基线统一为 NCCL 2.25.1：Broadcast 等接口、匹配顺序与 communicator、独立的 P2P 接口。这些是方案的接口依据，未宣称已为当前 vLLM connector 实现全部回退。

回到 connector：换路径以后，什么条件还要成立

无论采用设备直传、Host RDMA、socket 还是 collective，上层交付目标仍是“把这个请求的正确状态，放到 D 可消费的位置”。因此需要持续维持三类约束：

  1. 对象与映射正确。模型／布局／分片、源目标块及请求代际一致；传了正确字节数不代表传了正确状态。
  2. 消费条件完整。成功结果要覆盖所需的网络、拷贝、重排和可见性依赖；如果通过事件传递等待条件，消费方必须实际遵守。
  3. 资源按依赖归还。源、中转区、目标区与传输句柄分别结束自己的生命周期；容量不足要背压，失败不能被报成成功可消费。

固定 NIXL worker 返回的 KVConnectorTransferResults 同时包含 finished_recving 与 failed_recving；失败请求也可能出现在 finished 集合中。因此，“操作结束”与“数据有效可消费”依然要区分。故障分支如何清理与重试，留在单元四展开。

结论fallback 改变实际数据路径、参与者和成本，connector 仍要维持正确映射、完整消费依赖与安全回收。先证明当前能力能组成一条满足合同的路径，再比较性能，而不是从某个 API 或硬件名称直接跳到可行性结论。

检查 3受限环境中的交接方案

考虑两个相互独立的环境。两者的模型、KV 布局和目标映射都已正确，下面只判断传输与消费安排。

  1. 环境 A：设备显存不能被 RNIC 直接访问，但 Host RDMA、D2H 和 H2D 都可用。某后端采用双端 Host staging：网络已经写完 D 的 Host 缓冲区，随后提交了异步 H2D，但拷贝尚未完成，仍会读取该 Host 中转槽。后端此时归还 D 的 Host 中转槽并上报接收成功；框架收到成功后，立即在另一条没有等待依赖的 stream 上消费设备 KV。请指出两处提前动作，并分别说明需要等到什么条件，或补上什么依赖。
  2. 环境 B：设备通信库只暴露固定四 rank 组的 Broadcast，不能新建子组，也没有点对点接口；CPU 控制通道可以协调所有 rank。P 在 rank 0，D 在 rank 1，rank 2、3 没有这个请求。能否只让 0、1 调用 Broadcast 来完成交接？如果要用现有接口实现，需要怎样组织参与者与调用顺序，又会付出什么代价？

按数据路径和依赖解释即可，不需要计算，也不要求编写实现。

参考要点

环境 A 中，D 的 Host 槽仍被 H2D 读取，必须等这次读取结束才能复用。设备消费者则必须等 H2D 完成，或在消费 stream 上建立对拷贝完成事件的等待；不能把网络完成直接解释成任意 stream 已可消费设备 KV。

环境 B 中，固定通信组的四个 rank 都要参与相同轮次的 Broadcast，匹配调用顺序、root、count 和 dtype，并准备各自需要的缓冲区。只有 rank 0、1 调用不足以形成完整 collective；让 rank 2、3 参与会增加无关数据接收、内存占用与调度协调开销。

导师串讲：从一段 KV 到 D 可以消费的数据

回到贯穿本课的 64 KiB KV 片段：P 已生成正确内容，D 已确定目标块，模型、布局和片段映射相容。现在沿双端 Host staging 的正常成功路径，把前面分开看的对象重新连起来。完整路线仍可对照课程骨架与三段搬运图。

首先准备真实可用的存储位置。P 的设备源、P 的 Host 中转区、D 的 Host 接收区和 D 的设备目标各有自己的归属。注册 Host 区域得到 MR，并准备合法的地址、长度与访问权限；控制协议让 P 知道 D 本次允许写入的目标。MR 管内存访问边界，上层仍负责这段内容属于哪个请求、哪个状态和哪一代块。

然后让网络有一份已经产生的数据可读。P 先完成设备数据的生产，再进行 D2H；这份 Host 副本准备好以后，CPU 才提交会读取它的普通 RDMA WRITE。SGE 描述源地址、长度和 lkey，WR 再加入操作类型、目标地址与 rkey，经 QP 的发送队列提交。固定 mlx5 provider 把所需字段整理为 WQE，并通过 doorbell 通知 RNIC。

实际搬运与软件推进同时存在。RNIC 从 P Host 读取字节并把它们送到 D Host；CPU 可能持续处理提交、轮询和控制通知。用 IB 还是 RoCE 承载这次操作，要看实际网络配置；CPU 仍有活动，不会使硬件 RDMA 自动失效。GPU 发起也不是一个把所有硬件、注册和同步要求一并解决的开关。

完成结果必须对应到具体依赖。P 从 CQ 取得 WC 时，要认领本次 wr_id 并检查状态；提交返回和其他请求的成功完成都不替代它。普通 WRITE 没有自动给 D 的应用产生对应 RECV 完成，后端必须用自己的协议把本批数据就绪这一事实传给接收逻辑。rping 用后续 SEND 演示这件事，它不是所有后端都必须照搬的通知方式。

D 得到 Host 数据后，还要把它交给设备消费者。H2D 的源是 D Host 中转区，目标是 D 设备缓存；复制和消费需要同一 stream 的顺序或明确的跨 stream 依赖。网络完成只结束其中一个阶段。归还资源时，分别检查 P 源、中转区、D 目标和传输对象的最后一个使用者，不用一个“完成”标志同时释放所有东西。故障、取消与重试会增加哪些保留条件，由下一单元展开。

把这条链放大到上一课的 Qwen3-8B 算例：36 层、每层 8 个 KV 头、head_dim=128，明确采用 BF16 KV，并保留 8192 个位置；不考虑切分、额外副本、padding 或共享前缀。一份全模型有效 KV 合计为 1,207,959,552 byte，即 1.125 GiB。这是各层有效状态的合计，不表示实际内存连续，也不是实测分配量。

因此，64 KiB 例子里看似不显眼的阶段，在完整请求与并发负载中都会占用资源：拷贝消耗设备／Host 带宽，中转池占用容量，CPU 提交和进度消耗处理时间。把请求分成多个片段，可以尝试重叠不同阶段，但必须用槽位和事件保持同样的依赖规则。只优化网络阶段，未必能降低整条 KV 交接链或首 Token 的延迟；性能判断要回到真实注册路径、拷贝事件、网络完成和消费开始的测量边界。

规模沿用单元二 Qwen3-8B 算例；配置 revision b968826d9c46已核验，数值按 8192 × 2 × 36 × 8 × 128 × 2 用 Python 复算。RDMA 与 framework 的对应仍依据本课固定 rdma-core 和 vLLM；这条串讲没有新增硬件跑分结论。

本课串起来的判断方式沿数据实际经过的位置，标明谁准备资源、谁提交并推进工作、哪一个完成事件解除哪一条依赖，再确定谁能消费和谁能回收。回退方案改变路径与成本，也必须把这些关系一起调整。

综合核验

下面改变两端的能力组合，再改变网络条件，用完整的方案说明检验这些关系能否迁移。以面试回答的方式组织文字，只讨论正常成功路径；不要求实现代码、性能数字或故障恢复设计。

综合核验 1方案说明与条件迁移

一个 PD 系统的模型、KV 布局和目标块映射已经相容。P 的源 KV 与 D 的最终 KV cache 都在各自设备显存中，能力如下：

  • P 的 RNIC 已验证能够注册并读取 P 的显存；D 的 RNIC 只能写 D 的 Host 内存，不能直接写 D 的显存。
  • 两端设备与 Host 之间的拷贝均可用；CPU 可以提交和推进通信，GPU 不能直接通知 RNIC。
  • 控制通道正常；所用后端已验证能够在两端可注册的内存区域之间执行由 P 发起的普通 RC WRITE。
  1. 请以向面试官说明方案的方式，给出尽量少做中转的正常交接流程。把实际数据路径、CPU／RNIC 分工、需准备的内存描述与权限，以及完成、消费和回收条件串起来；说明这条路径是否必须依赖 GPU initiated。
  2. 现在两端 RDMA 都不可用，但普通 Host TCP/socket、控制通道和设备↔Host 拷贝仍可用。你会怎样修改数据路径？本地发送成功之后，还需要哪些接收端步骤，才能继续满足“D 可以消费正确设备 KV”的上层含义？

用自己的话作答，可以分段；本周只检查表达内容，不计口述时长。

参考回答与关键要点

正常路径。P 的源 KV 显存 → P RNIC → 网络 → D RNIC → D Host 中转区 → H2D → D 设备 KV。P 可以直接提供显存中的源数据，因此这一侧不需要 Host 中转；D 的网络接收目标是 Host 区域。

准备与注册。确保 P 的源 KV 已产生并满足网络读取依赖，D 的接收区与设备目标已按本次交接准备好。本次 RDMA MR 覆盖 P 显存源区和 D Host 接收区；D 最终设备目标只由后续 H2D／计算访问，不需要为这次 RDMA 注册 MR。P 源仅需支持本地读取；D Host 目标需要相应的本地写与远端写权限。交换合法的远端地址、rkey 和可用长度，并维护正确的请求、布局与目标映射。

提交与推进。CPU 可以组织源地址／长度／lkey、目标地址／rkey 等描述，经已准备好的 QP 提交 WRITE；provider 构造设备工作项并通知 RNIC，RNIC 执行 payload 搬运。本方案可以使用 CPU initiated，不要求 GPU 直接驱动网卡。GPU 不能直接敲 doorbell，也不自动排除 GPU 提出请求、CPU proxy 承接的其他实现；本题无需采用那些路径。

完成与消费。软件取得与本次操作对应的成功完成依据，并通过后端协议把本批数据已就绪这一事实接到 D 的接收逻辑；通知不必限定为 SEND。D 确认这批网络写入完成后安排 H2D，再通过拷贝完成或正确的 stream／event 依赖允许设备消费。业务映射正确和数据可见性均不能由一个无归属的完成标志替代。

回收。P 没有 Host 中转区，但保存 KV 的显存本身就是设备源缓冲区；本次传输不再读取它后，可以归还该传输持有的引用，实际释放仍需符合其他引用与保留策略。D Host 区要等 H2D 不再读取，D 设备 KV 要等消费者和相关引用结束。源数据区与源缓冲区在本例是同一块内存的不同用途描述，没有隐含的额外设备内拷贝。

无 RDMA 时。路径改为 P 设备 KV → D2H → P Host → 普通 TCP/socket → D Host → H2D → D 设备 KV。网络发送前要有完整可读的 Host 数据；D 按协议完整收到本批 payload，校验相应请求／布局／目标映射，再建立 H2D 与消费依赖。本地发送成功并不表示这些接收端步骤已经完成。P 若需要知道远端状态，再由协议提供相应回报，而不是默认每次数据搬运都必须使用同一种 ACK。

检查 4注册范围复查

把路径改成：P 设备源区 → D2H → P Host 中转区 → 普通 RC WRITE → D 设备目标区。后端已验证 P Host 区域可注册并由 RNIC 读取，D 设备区域可注册并由 RNIC 写入。

只考虑这次 KV payload 的 RDMA，不讨论控制消息缓冲区：这三处内存中，哪些必须由 RDMA MR 覆盖？P 的源描述中的地址／lkey，以及远端目标描述中的地址／rkey，分别对应哪一处？

说明实际读写对象即可，不需要重写完整传输流程。

参考要点

本次 RNIC 实际读取 P Host 中转区、写入 D 设备目标区，因此这两个区域必须由有效 RDMA MR 覆盖。P 设备源区只参加前面的 D2H，不因这次 RDMA 而需要 MR。

P 源描述的地址、长度与 lkey 指向 P Host 中转区；远端目标地址与 rkey 对应 D 设备目标区。判断依据是本次网络操作实际访问哪些区域，而不是“Host／设备”或“最终 cache”的标签。区域可以由合适的已有 MR 覆盖，不要求每次传输都新建 MR。

符号与名词

RDMA
Remote Direct Memory Access；在约定的地址范围与权限下进行远程内存访问和数据放置的一类能力／操作。
RNIC、Host DRAM、payload
本课 RNIC 指支持硬件 RDMA 的网卡；Host DRAM 是主机内存；payload 是本次实际搬运的数据内容。
内存注册
让通信实现知道哪些内存区域可以被设备访问，以及允许哪些操作；具体对象与权限在后续节点展开。
InfiniBand、RoCE、iWARP
与 RDMA 相关的网络／协议选择；RoCE 在以太网上承载 RDMA，iWARP 可基于 TCP。
opcode、ibv_post_send
opcode 标明操作类型；ibv_post_send 将工作请求提交给选定队列，其名字不限定工作请求必须是 SEND 操作。
NVSHMEM
NVIDIA 面向多 GPU 的通信库，以分区全局地址空间表达跨 GPU 数据访问。
Host staging、GPUDirect RDMA
前者经主机缓冲区中转 payload；后者允许网卡直接访问已注册的 GPU 显存。
IBRC、IBGDA
NVSHMEM 的传输实现；此处比较 CPU proxy 与 GPU 生成、提交网卡请求的分工。IBGDA 还存在由 CPU 代敲 doorbell 的模式。
MR、lkey、rkey
MR 是注册内存区域；lkey 用于本地 RDMA 内存访问，rkey 用于远端访问校验。它们不验证业务数据属于哪个请求。
Protection Domain
保护域，本地 RDMA 资源的访问关联范围；源码常缩写 pd，与 prefill/decode 分离无关。
QP、SQ、RQ、RC
QP 为队列对，包含发送队列 SQ 与接收队列 RQ；RC 是 Reliable Connection（可靠连接）传输类型。本课普通 WRITE 由发起方 SQ 提交。
WR、SGE、WQE
WR 是软件工作请求；SGE 描述一个本地缓冲区片段；WQE 是设备工作队列项。描述结构与其指向的 payload 有不同生命周期。
provider、doorbell
provider 是对接具体 RDMA 设备的实现；doorbell 用来通知设备有工作可处理。
CQ、CQE、WC、wr_id
CQ 是完成队列，CQE 是其中的完成条目；软件 poll 后取得 WC，用 wr_id 识别请求、status 判断结果。
signaled、inline
signaled 请求一条完成报告；inline 将 payload 随任务内联提交。本例只使用前者，主体数据保留在源缓冲区。
数据可见性、DMA 一致性
可见性指特定消费者后续读取能观察到应当读取的写入；Host DMA 一致性、完成处理、线程交接和 GPU 同步分别处理不同边界，不能互相替代。
CUDA stream、event、H2D
stream 是有序设备任务流；event 标记其中的完成边界，可供 Host 或其他 stream 等待；H2D 是 Host 到 Device 的数据拷贝。
D2H、中转槽、背压
D2H 为 Device→Host 拷贝；中转槽是可复用的临时缓冲区；背压表示下游容量不足时让上游等待或限流。
collective、communicator
collective 是通信组成员按匹配约定共同参与的操作；communicator 保存通信组及其组内 rank 等信息。
fallback
在能力受限时选择另一条可用执行路径，并继续满足上层的正确性合同；不自动保证性能等价。
GPU initiated、CPU initiated
描述通信请求的发起方；还需明确谈的是 API 请求层还是网卡提交层，分别标注 WQE 生成者和 doorbell 执行者。
DBR（doorbell record）
内存中的工作队列进度记录；与 NIC 上用于通知设备的 doorbell 不是同一对象。
