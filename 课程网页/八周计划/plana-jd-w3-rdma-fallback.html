从一段缓存的搬运，看清网络这一层

前两课已经确定了 P 要交付什么状态、D 应当把它放在哪里，以及何时允许消费。现在往下看一层：程序提交“把这段字节搬过去”之后，CPU、驱动、网卡和内存分别做什么？为什么有时 CPU 仍在忙，却没有亲自搬运主体数据？如果设备不能直接让网卡访问它的显存，这条交接链又该怎样继续？

本课仍沿 P→D 的一段缓存展开。先看两台主机之间的 Host 内存搬运，再逐步加入注册内存、任务队列和完成结果，最后回到设备显存、GPU 发起与能力受限的回退路径。我们要解决的核心问题是：让数据搬得出去，还要让软件准确知道它从哪里来、何时完成、接下来谁能使用。

学完后，你应该能画清一次正常传输的数据路径，说明资源准备、提交和完成分别由谁负责；能把设备能力映射到真实接口，并针对没有 RDMA、只能经 Host 中转或只有 collective 接口的环境，说明可行路径及代价。本课以书面解释、固定源码对应和方案判断形成依据，不要求先拥有 RDMA 硬件或完成某款设备的真实适配。

1CPU 下达搬运任务，谁把字节放进目标内存

对应主线第 1 项的 RDMA 数据路径；先看这个具体例子，再对照固定 rping 的 WRITE 阶段。内存注册和队列对象将在后面的节点展开。

假设 P 已经准备好一个连续的 64 KiB 缓存片段，放在 P 的 Host DRAM 中；D 也准备了同样大小的 Host 接收缓冲区。64 KiB 就是 65,536 byte，是为了看清路径选取的一段数据，不是一个完整请求的全部 KV。此处先不放入 GPU，让“网络怎么搬字节”这件事独立可见。

两台机器都有支持硬件 RDMA 的网卡，下面简称 RNIC。两端软件已经建立通信关系，并声明了网卡可以访问的内存范围和权限，这一步叫内存注册。D 的允许访问地址和相应凭据也已经交给 P。因此，接下来讨论的是一段已准备好访问条件的、正常成功的 RDMA WRITE。

P 的 CPU 提交一个任务：“从本地这段源内存取 65,536 byte，写到 D 允许访问的这个目标位置。”本例提交的是任务描述，不把整段内容塞进提交指令中。之后 P 的 RNIC 读取源缓冲区，把数据发到网络；D 的 RNIC 按允许的目标位置，把数据写入 D 的缓冲区。

这就是 Remote Direct Memory Access 中“远程内存访问”的含义：操作针对对方已经授权的内存位置。目标应用不必为每次普通 WRITE 执行一次“收下 payload，再由 CPU 复制到最终缓冲区”的过程。地址和权限仍然必须合法，它并不是让发送方随意写入另一台机器的任意内存。

为什么要这样安排在频繁或大批量搬运时，中间拷贝、逐消息的软件处理会消耗 CPU 和内存带宽。硬件 RDMA 把数据放置等工作交给网卡，软件更多地负责准备、提交与协调。相应的代价是：软件必须准确管理注册区域、地址权限和缓冲区生命周期，不能提交任务后就立刻改写或归还还在使用的数据。

普通网络设备也会使用 DMA，所以不能把区别说成“只有 RDMA 网卡能访问内存”。这里要观察的是：数据是否直接进入约定的应用缓冲区，以及哪些处理由硬件或软件完成。常规 socket 路径也有零拷贝等优化，不能把所有 TCP 通信都简化成固定次数的 CPU memcpy。

CPU 轮询不等于 CPU 搬数据。一个线程可以反复询问“任务完成了吗”，同时由 RNIC 执行真正的 payload 搬运。轮询会消耗 CPU 时间，但这份时间与逐字节复制 64 KiB 是两类工作。判断优化效果时，要分别看控制开销、数据移动和整体延迟，不能只看 CPU 是否空闲。

真实系统rdma-core 的 rping 示例先交换远端地址、访问凭据和长度，再执行 READ／WRITE；其 WRITE 阶段明确设置操作类型并提交：

cb->rdma_sq_wr.opcode = IBV_WR_RDMA_WRITE;
/* 请求中已放好源缓冲区、长度和远端访问资料 */
ret = ibv_post_send(cb->qp, &cb->rdma_sq_wr, &bad_wr);

这里 opcode 决定执行 WRITE；ibv_post_send 是把工作请求交给发送队列的接口，cb->qp 先理解为已经准备好的队列对象即可。具体对象为何叫 QP、工作请求怎样描述内存，下段再讲。这个函数名里的 send 不代表此处操作类型变成了普通 SEND 消息。

rping 中还有 CPU 完成处理及额外控制消息，整个示例的远端 CPU 并非一直空闲。普通 WRITE 本身也不会自动告诉 D 的应用“现在可以消费”：软件仍要按协议把完成观测与后续动作接起来。前课区分的“提交成功、搬运完成、数据可消费”在这里继续有效。

接口依据：rdma_post_write；固定示例 控制／数据流程概览、WRITE 与之后的通知。rping 的 server/client 是示例角色，本课仅借其 WRITE 操作说明 P→D 分工；未运行 64 KiB 硬件测试。

边界本图限定硬件 RNIC。Linux 也有 RXE 等软件 RDMA 实现，使用相同类别的接口不自动证明获得了硬件卸载。当前片段只涉及 Host 内存；若 KV 原先在设备显存，是否需要先复制到 Host，是另一项路径选择。后面会据此区分 GPUDirect 与 Host 中转。

结论先把“安排和观察搬运”与“实际移动 payload”分开。硬件 RDMA 可以由 CPU 提交、由 RNIC 搬数据；CPU 仍有活动，并不能据此否定这条路径。

2RDMA、InfiniBand 与 RoCE，回答的是不同问题

继续主线第 1 项的层次区分；对应 DOCA 3.5.0 指南 §3.4 和 RoCE Modes，检查 1 关闭后再对照原文。

把图 1.1 中间的“网络”展开。有人可能会问：“这套系统用的是 RDMA，还是 InfiniBand？”这两个名称没有落在同一层：RDMA 描述我们要执行的远程内存操作，InfiniBand 则是实现通信的一套网络技术。

可以把部署问题拆成三句：软件请求什么操作？网卡通过什么网络实现？数据存放在哪种内存？本例的操作是 WRITE，网络可以是 InfiniBand，也可以是 Ethernet 上的 RoCE；数据此刻放在两端 Host DRAM。换其中一项，不会自动决定另外两项。

名称在这里回答什么与本例的关系
RDMA是否提供受控的远程内存访问与数据放置操作本例请求把字节写入指定远端缓冲区
InfiniBand（IB）一种网络与传输体系可以承载本例的 RDMA 操作
RoCE在 Ethernet 上实现 RDMA 的方式仍可执行 RDMA 操作，底层使用以太网
iWARP另一种可在 TCP 上构建 RDMA 的协议体系说明“用了 TCP”也不是排除 RDMA 的充分条件

RoCEv2 把 RDMA 传输封装进 UDP/IP，能够经过 IP 路由。因此，在网络侧看到 UDP/IP 报文，并不说明应用是通过普通 sendto 接口搬运 payload。应用使用什么内存访问操作，与报文外层用什么封装，需要分别判断。RoCEv1 的承载方式不同，使用专用 Ethernet 类型；本段不把两种版本混为一条路径。

为什么要分清层次排查 PD 性能或设计回退方案时，选了一个高层通信库，并不能直接说明它最后用了什么路径。例如 NIXL、UCX 可以封装下层实现；实际选择还受到设备、配置和资源的影响。同样，IB／RoCE 网络可用，也不自动说明网卡能直接访问某款设备的显存。

如果原始 KV 在 GPU 或其他加速器显存里，而传输实际访问的是 Host 缓冲区，路径中就包含设备与 Host 之间的复制。上一课 Mooncake 案例已经展示过这样的可能路径。要判断是否直接访问设备内存，应查看参与传输的实际内存类型、注册方式和拷贝链，而不是只检查网络标签或提交者是谁。

网络承载：DOCA 3.5.0 archive · RoCE Modes；RFC 5040 §1.3给出建立在 TCP 上的 RDMAP 分层。软件实现边界见 rdma-core v65.0 的 RXE 说明。vLLM 固定源码中的默认 backend 配置本身不构成具体硬件路径的实测证据。

结论RDMA 是操作能力，IB／RoCE／iWARP 是相关网络或协议选择；CPU 是否参与控制、payload 在 Host 还是设备内存，是另外两项需要核验的事实。把它们分别问清，才能继续分析真实数据路径。

补充：NVSHMEM 的控制路径与数据路径

展开对照 Host staging、IBRC 与 IBGDA

NVSHMEM 是什么？它是 NVIDIA 面向多 GPU 的通信库，提供分区全局地址空间：程序对多个 GPU 上按约定对称分配的内存，用目标处理单元编号和相应地址表达远程访问。GPU 内核可以调用 put（远程写）、get（远程读）等操作；底层如何提交请求、如何搬运数据，由选用的传输实现决定。

先分清两种内容。payload 是实际要传输的张量字节；控制信息则说明“从哪里取、向哪里写、传多少”。Host staging 指把 payload 先复制到主机内存，再让网卡传输。GPUDirect RDMA 则让网卡直接访问已注册的 GPU 显存。这两种数据路径，不能仅凭控制代码运行在 CPU 还是 GPU 上来区分。

情形谁控制提交payload 如何到网卡
Host staging取决于通信实现GPU 显存 → Host 缓冲区 → NIC
IBRCCPU proxy 代理线程生成网卡请求并通知网卡可由 NIC 直接读取 GPU 显存
典型 IBGDAGPU 生成网卡请求并通知网卡NIC 直接读取 GPU 显存
CPU-assisted IBGDAGPU 生成请求，CPU 代为通知网卡仍可直接访问 GPU 显存

IBRC 是 InfiniBand Reliable Connection 传输。在官方示例中，GPU 把任务描述写入 Host 中的代理缓冲区，CPU 再构造网卡工作描述；经过 Host 的描述信息，不等于 payload 也经过 Host。IBGDA 是 InfiniBand GPUDirect Async 传输，典型模式把生成描述、敲 doorbell（写网卡通知寄存器）和完成查询交给 GPU。CPU-assisted 模式只把通知网卡这一步交回 CPU，不能因此归类为 Host staging。

为什么小消息更容易受益？每条消息都需要提交和处理控制信息；消息越小，这部分固定成本越突出。GPU 并行生成请求，可以缓解 CPU proxy 的串行处理瓶颈。大消息传输也可能已经受网卡带宽限制，因此不能把某次小消息收益外推到所有负载。这里比较的是传输分工，不保证任意硬件配置都支持这些路径。

上述 IBRC／典型 IBGDA 路径依据 NVIDIA 2022-11-22 技术博客；CPU-assisted 分工依据 NVSHMEM 3.0 技术说明及 3.0.6 发布说明。均为官方机制说明，不是本机实测。

检查 1路径判断

某个 PD 进程中，有 CPU 线程持续提交传输任务并检查完成结果；网络侧确认相关数据走以太网，报文带有 UDP/IP 封装。工程师据此说：“CPU 还在忙，而且走 UDP，所以这里没有使用 RDMA。”

  1. 这个判断是否成立？请分别解释 CPU 活动和 UDP/IP 封装能说明什么、不能说明什么。
  2. 如果还要判断这些数据是不是从 GPU 显存直接交给网卡，仅凭“使用了 RDMA”是否足够？你还需要确认哪一段数据路径？

用自己的话解释即可，不需要计算，也不要求给出尚未讲解的底层配置命令。

参考要点

CPU 可以在提交任务或轮询完成，而主体数据仍由 RNIC 搬运；UDP/IP 可能是 RoCEv2 的封装，两种现象都不足以排除 RDMA。要确认 GPU 显存直达网卡，应沿实际注册并被传输后端访问的内存区域，核查 GPU→Host 拷贝是否发生；业务张量最初位于 GPU 并不足以说明路径。

3从普通指针到网卡获准访问的内存区域

沿主线第 1 项进入内存注册；先看本节，再对照 rdma-core v65.0 的 ibv_reg_mr 手册与 rping_setup_buffers。

继续前面的例子：P 的 Host 缓冲区里已有 64 KiB 数据，D 有一个同样大小的接收区。C 程序拿到了两个指针，为什么还不能只把指针交给网卡就开始搬运？因为进程能够解引用一个地址，不代表网卡已经具有访问它的地址映射和权限；P 也不能因为知道 D 的一个地址，就任意写入 D 的内存。

因此，两端分别把一段地址范围注册给 RDMA 实现，得到 Memory Region（MR，内存区域）对象。对于这里使用的普通 Host 注册路径，系统需要准备设备可用的地址转换、访问权限，并保持内存页稳定可供 DMA 访问。MR 更像“这段缓冲区的设备访问登记”，而不是另一份数据容器：注册不会把 64 KiB 自动发送出去，也不要求把整段内容复制进网卡。

注册还需要一个本地 Protection Domain（保护域），用于约束哪些内存和通信资源可以一起使用。下面把两端已有的保护域分别记为 p_domain、d_domain。源码经常把保护域变量写成 pd，这里它与 prefill/decode 分离的“PD”是两个不同概念。

/* src、dst 已分别在 P、D 分配；nbytes = 65536。 */
/* P：网卡只需读取源数据，local read 默认允许。 */
struct ibv_mr *src_mr = ibv_reg_mr(p_domain, src, nbytes, 0);
/* D：允许网卡写入，也允许远端发起 WRITE。 */
struct ibv_mr *dst_mr = ibv_reg_mr(d_domain, dst, nbytes,
    IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_WRITE);

按 rdma-core v65.0 接口整理的两端示意，前提是注册成功；省略初始化、失败处理与清理。真实 rping 的 rdma_buf 同时设置 LOCAL_WRITE、REMOTE_READ 与 REMOTE_WRITE；此处按单向 WRITE 所需权限简化。

第二个调用里的 LOCAL_WRITE 是 RDMA 内存访问权限，不是 C 程序能否赋值的页面权限。手册要求：开启 REMOTE_WRITE 时也必须开启 LOCAL_WRITE。P 仅作为源、由网卡读取的区域不必因此加上这两个写权限。

成功注册后，本例接下来需要两类 key。它们用于校验设备访问，不是缓存内容的校验和，也不是业务请求 ID：

资料由谁使用在这次 WRITE 中负责什么
src_mr->lkey（local key）P 的本地网卡配合源地址与长度，标识本次本地访问所用的 MR。
dst_mr->rkey（remote key）随远端操作交给 D 端校验配合目标地址及访问权限，允许写入 D 已注册区域内的合法范围。
D 的目标地址、可用长度P 的提交逻辑确定写到哪里、最多能写多少；目标地址不是 P 可以直接解引用的本地指针。

D 要通过双方的控制协议把目标地址、rkey 和可用长度交给 P。本例的两端 QP 已经连好，建立连接与交换这些内存资料是准备阶段的不同工作。拿到正确 rkey 也不意味着可以越界，目标区域还必须保持注册且活着。

为什么把注册与每次提交分开地址映射和访问权限的准备有成本。长期使用的缓冲区可以先注册，再提交多次针对其中片段的搬运，避免把完整准备过程塞进每一次请求；相应地，软件要维持注册和缓冲区的生命周期，不能在网卡仍可能访问时注销或释放。注册一个大内存池，也不会替软件决定哪个槽此刻允许覆盖。

真实系统固定 rping 在 rping_setup_buffers 中先 malloc，再用 ibv_reg_mr 注册；它把收到的远端地址和 rkey 放进 WRITE 请求。这个分工也解释了 KV 交接为什么仍需要上层元数据：MR 只约束内存访问，不知道这段字节属于哪个请求、哪个 Token 或哪一层。两段 KV 即使都位于合法 MR 内，也可能在业务层被映射错。

接口依据：ibv_reg_mr；实现对应：rping 分配与注册。均固定 v65.0 / 58e40801bfed；保护域职责见 DOCA 3.5.0 RDMA 编程指南的对象说明。

本节限定普通 Host MR；按需分页注册等模式另有机制。设备显存还需要相应的驱动、映射与互操作支持，不能把 malloc 换成某个设备分配 API 后，就推定同一注册调用能够成功。rkey 也不替代应用认证或数据加密。

结论缓冲区保存数据，MR 声明设备访问的范围和权限。源地址／长度／lkey 与目标地址／rkey 共同描述搬运的两端；业务映射和安全复用仍由软件维护。

补充图谱：把缩写放进资源、请求和结果三层

这些名字并不是一组平级的数据结构。PD、MR、QP、CQ是准备阶段建立、通常多次复用的资源；WR、SGE是应用描述某一次操作所用的软件结构；WQE、CQE、WC分别是设备任务项、设备完成条目和应用取回的完成结果。实际 KV 字节始终存放在数据缓冲区里。

下面仍使用两端 Host 缓冲区的 64 KiB、非 inline、signaled、普通 RC WRITE。图中的 PD 指 Protection Domain（保护域），与 prefill/decode 分离的 PD 不是同一个概念；P、D 两台主机各有自己独立的保护域。先看资源关系，再切换阶段，最后接节点 4 的描述转换与回收图。

真实代码里，rping 把同一个 cb->cq 同时赋给 init_attr.send_cq 和 init_attr.recv_cq，再用 cb->pd 创建 QP。这样一来，SQ 和 RQ 可以向同一个 CQ 报告结果；但普通 WRITE 本身并不消耗对端 RQ，也不自动产生对端 RECV 完成。

固定 rdma-core v65.0 / 58e40801bfed：PD、MR、QP与CQ的接口关系；rping 的 CQ 关联。WR／SGE 的字段复制与 WC 恢复以节点 4 的固定 mlx5 实现为准。

先认清对象类别PD／MR／QP／CQ 搭好可复用的通信资源；WR／SGE 说明这次要做什么；WQE 是给设备执行的形式；CQE 经 provider 处理后，应用得到 WC。缓冲区里的 KV 数据是它们所描述和搬运的对象。

4工作请求怎样交给网卡，完成结果又怎样回来

继续同一条 WRITE，读到本节检查 2 为止；对应 rping 的请求准备、WRITE 提交与完成处理，以及固定 mlx5 provider 的 post_send 路径。

内存准备好后，P 还要描述“这次做什么”，并给网卡一个接收任务的地方。Queue Pair（QP，队列对）包含发送队列 SQ 和接收队列 RQ。本例使用 RC（Reliable Connection，可靠连接）类型的 QP，两端已建立相应连接。P 把自己发起的 WRITE 放到 SQ；这里“发送队列”可以承接 WRITE、READ、SEND 等操作，不只用于 SEND 消息。

P 用一个 C 结构体描述操作，这就是 Work Request（WR，工作请求）。其中的 Scatter/Gather Element（SGE，缓冲区片段描述）给出本地地址、长度和 lkey；一个 WR 可以引用多个 SGE，本例只有一段。下面的 remote_addr、remote_rkey 已从 D 获得，qp 是 P 的已连接 QP；任务标签 101 由软件任意选择，用于后续认领结果。

struct ibv_sge piece = {
    .addr = (uintptr_t)src,
    .length = nbytes,
    .lkey = src_mr->lkey
};
struct ibv_send_wr request = {0}, *bad = NULL;
request.wr_id = 101;
request.opcode = IBV_WR_RDMA_WRITE;
request.send_flags = IBV_SEND_SIGNALED;  /* 请求一条完成报告 */
request.sg_list = &piece;
request.num_sge = 1;
request.wr.rdma.remote_addr = remote_addr;
request.wr.rdma.rkey = remote_rkey;
int rc = ibv_post_send(qp, &request, &bad);

rdma-core v65.0 接口示意；注册与连接已成功，单个 WR，未开启 inline。真实字段对应 rping_setup_wr 及 rping 的 WRITE 分支；不是完整可运行程序。

IBV_SEND_SIGNALED 请求为这次操作产生完成报告，它不把异步提交变成同步等待。ibv_post_send 返回 0 表示提交成功；返回非零表示提交遇到错误。任务是否执行成功，要到完成路径去确认。

在本课核验的 mlx5 provider——对接这一类网卡的用户态实现——中，提交函数读取 WR／SGE 字段，把它们转换成网卡使用的 Work Queue Entry（WQE，工作队列项），并放入 SQ。然后按设备要求保证描述符写入的顺序，更新相关记录，再通过 doorbell（门铃）通知网卡有新工作。门铃是通知机制，不是装下 64 KiB KV 的容器。

这解释了两种对象为什么有不同生命周期：在这条固定 mlx5 路径中，提交函数已经复制所需的描述字段，成功返回后可以重用原 WR／SGE 结构；但本例没有使用 inline，主体数据仍在 src 指向的缓冲区中，网卡可能尚未读完。描述“从哪里读”的结构可以重写，不代表被读取的内容可以覆盖。软件还必须保留用于辨认在途请求的独立记录。

网卡通过 Completion Queue（CQ，完成队列）报告结果。硬件放入的条目叫 CQE；软件调用 ibv_poll_cq 后取得 Work Completion（WC，完成记录）。WC 中的 wr_id 用来辨认原请求，status 用来判断成功或失败。多个 QP 可以共享一个 CQ，因此“取到一条成功记录”还必须接着问“它属于哪一个请求”。共享 CQ 不会建立不同 QP 之间的全局执行顺序。

轮询可能暂时取不到记录，也可能取到失败记录。只有认领到本次请求的成功 WC，才具备本例源缓冲区不再被这次传输读取的依据；如果它还被其他任务引用，仍需保留。轮询消耗的是观察结果的 CPU 时间，不是 CPU 在代替 RNIC 逐字节搬运。

接着看 D：普通 RDMA WRITE 不消耗 D 的 RQ 接收请求，也不会自动在 D 的 CQ 生成一条对应的 receive completion。预先调用 ibv_post_recv 是为需要接收条目的操作准备缓冲区，例如 SEND；WRITE with immediate 也有额外接收语义，本节暂不展开。不能仅因它们都使用同一个 QP，就认为普通 WRITE 也要等一次 receive。

因此，D 的应用还需要传输后端或上层协议，把完成、内存可见性与“本批可以消费”接起来。固定 rping 的 WRITE 分支等到本地完成后，会另发一条 SEND 控制消息；这一条 SEND 才需要对端准备接收。P 的成功 WC、D 的软件收到通知、D 完成计算是三个不同事件，不能互相替代。MR 和 CQ 也不会验证 D 的 block table 是否指向了业务上正确的 KV。

实现依据：请求准备、WRITE 后另发控制消息。源码推断描述结构可重用的依据是 mlx5 同步构造 WQE、保存 wr_id 并返回；doorbell 细节见同文件 post_send_db。本节不将该实现细节推广为所有后端的内部流程。

图与正文限定正常成功、非 inline、signaled 的 RC WRITE。inline 会改变源 payload 何时可以重用，unsignaled 会改变完成追踪方式，错误与清理也需要额外规则；这里不把它们套入同一判据。RDMA 完成与 GPU kernel 的可见性衔接将在设备路径节点单独讨论。

结论MR 管内存访问，WR／SGE 描述本次操作，QP 提供队列，provider 构造 WQE 并通知网卡，CQ／WC 返回可认领的结果。软件必须分别管理提交、完成、数据消费和资源归还。

补充：SEND 接收什么，“数据可见”具体怎样保证

回到这次 P→D 搬运：主体数据是一段 64 KiB 缓存，P 还会在搬完后给 D 发一条小的控制消息。两者分别放在哪里？D 又依据什么开始读？把存储位置和读取时机分别追清，就能把“接收”和“可见”落实到具体代码。

SEND 的接收缓冲区，装的是消息内容

普通 WRITE 的请求中带有远端地址和 rkey，发送方按照事先获得的资料指定写入位置。SEND 使用另一种接口分工：发送方指定自己要发送的内容，接收方通过接收 WR 指定本地用于存放消息的内存。因此，D 要先分配并注册一块合适大小的内存，再调用 ibv_post_recv，把“消息可以放在这里”的描述提交给 RQ。

ibv_post_recv 本身既不是分配内存，也不是让 CPU 去逐字节收包。它预先提供接收描述。消息到达后，网卡／provider 按接收描述放置消息，应用在取得对应成功完成后读取接收缓冲区。接收区总容量必须足够容纳消息；如果没有可用的接收请求，普通 SEND 无法按这条正常路径完成接收。

在固定 rping 中，两类内容明确分开：rdma_buf 存 READ／WRITE 的主体数据；send_buf、recv_buf 存 SEND 控制消息。WRITE 已经把主体数据放进 rdma_buf，并不意味着稍后那条 SEND 消息也有了接收位置。如果 SEND 本身用来发送大块业务数据，接收缓冲区就要容纳那块业务数据；“SEND”并不限定消息一定很小。

/* rping_setup_wr：cb->recv_mr 已注册成功。 */
cb->recv_sgl.addr = (uint64_t)(unsigned long)&cb->recv_buf;
cb->recv_sgl.length = sizeof cb->recv_buf;
cb->recv_sgl.lkey = cb->recv_mr->lkey;
cb->rq_wr.sg_list = &cb->recv_sgl;
cb->rq_wr.num_sge = 1;
/* 准备阶段调用；bad_wr 接收提交失败的位置。 */
ret = ibv_post_recv(cb->qp, &cb->rq_wr, &bad_wr);

按 rdma-core v65.0 的 rping.c 两处代码合并展示，省略错误分支；不是一段连续源码。接收／发送／数据描述；预贴接收。

应用从 recv_buf 读取消息内容，从 WC 读取完成状态、长度等信息；预贴接收不是给 CQ 分配空间。rping 的控制结构含地址、rkey 和长度，但 WRITE 后的 go-ahead 通知主要利用消息到达与已有阶段状态推进流程，不存在独立的业务 request_id／ready 字段。真实 KV 交接协议可以另外设计请求、槽位与代际信息，避免把旧通知认成新请求。

“可见”是一项读取保证，具体动作取决于跨越的边界

当 D 开始消费本批数据时，读取应当观察到这一批已经写好的字节，不能读到旧内容、半份新数据，或不满足依赖顺序的数据。这就是这里说的可见性。“确认可见”不是统一调用某个函数，也不是每次把数据读回来校验一遍；它要求用接口规定的完成与同步机制，为后续读取建立保证。下面只改变消费者的位置，沿同一份数据看三种具体做法。

情况一：RNIC 写 Host，随后由 CPU 读取

先限定本节 Host 例子：使用 CPU 与设备保持 DMA 一致性的主机平台、普通注册内存及默认排序，并且没有其他写者竞争目标区域。固定 rping 的具体链路是：

  1. P 的完成线程取得本次 WRITE 的成功 WC；发送逻辑等到这个条件后，才提交后续 SEND 控制消息。
  2. D 的 CQ 线程取得这条 SEND 的成功接收完成。mlx5 provider 在观察到有效 CQE 后执行 udma_from_device_barrier()，约束后续 CPU 读与此前按序设备写的观察顺序；应用不需要自行在每次 poll 后再补一个这样的调用。
  3. D 的 CQ 线程根据消息和阶段更新状态，再 sem_post 唤醒消费线程；消费线程 sem_wait 成功返回、检查阶段后，才读取 rdma_buf。

这里同时跨过了两条边界：设备到 CPU 的观察顺序由平台与 provider 配合处理；CQ 线程到消费线程的交接由信号量处理。换成线程池，也可以使用有正确 release/acquire 语义的原子状态或锁，但单独加一个 CPU fence、把普通变量设成 ready=true，都不会等待尚未完成的 RDMA。

固定源码：WRITE 完成后发送通知；mlx5 的 from-device barrier及其定义；rping 的接收处理与 sem_post、sem_wait 后读取主体数据。依据仍为 58e40801bfed；这条通知链的保证不能替换成“收到任意通知即可读”。

情况二：RNIC 写 Host，随后复制到 GPU 再计算

现在 D 的消费者换成 GPU kernel。CPU 先按前面的协议确认 Host 缓冲区中的本批数据已经写完，再发起 H2D 拷贝。H2D 表示 Host→Device；下面假设 Host 缓冲区满足异步拷贝所需的固定页等条件、GPU 目标区有效，且所有 CUDA 调用返回成功。

/* CPU 已确认本批网络写入完成；s 是 D 的 CUDA stream。 */
cudaMemcpyAsync(gpu_dst, host_buf, nbytes, cudaMemcpyHostToDevice, s);
consumer<<<grid, block, 0, s>>>(gpu_dst);

同一 stream 的顺序保证 consumer 在这次拷贝之后执行。这里的具体“可见性动作”就是把拷贝与依赖它的计算放进同一条有序任务流；CPU 不必等拷贝完成才提交 kernel。但 host_buf 在 H2D 读完前仍不能覆盖或归还。

如果复制和计算使用不同 stream，CPU 上先后调用两个 API 并不足以建立两条 stream 的执行依赖。此时可以在复制流记录事件，让计算流等待这个事件：

cudaMemcpyAsync(gpu_dst, host_buf, nbytes, cudaMemcpyHostToDevice, copy_stream);
cudaEventRecord(copied, copy_stream);
cudaStreamWaitEvent(consume_stream, copied, 0);
consumer<<<grid, block, 0, consume_stream>>>(gpu_dst);

copied 是提前创建的 CUDA event；record 把此前拷贝的完成边界记在复制流中，wait 为计算流后续任务建立等待关系。它们不是新的数据缓冲区，也不负责等待刚才的 RDMA——网络完成必须先由网络那一层确认。

接口示意，省略 event／stream 创建与错误处理；语义依据 CUDA 12.8.1 Programming Guide · Streams及 cudaStreamWaitEvent。未在本机执行 GPU 实验。

情况三：RNIC 直接写 GPU 显存

这次没有 H2D 拷贝，外部网卡与 GPU 的任务流成为两条不同的执行路径。前提是显存已经按 GPUDirect RDMA 要求正确注册、映射，并满足 CUDA 一致性设置。CUDA 12.8.1 指南给出一条保守的安排：先让本批外部 DMA 写入相对于 CPU 完成，再由这条 CPU 控制路径提交依赖它的 GPU kernel。在这个方案中，网络完成确认加上后续 CUDA work submission，就是实际使用的排序机制。

这与“kernel 早已运行，等到一个普通 ready 变量变化就立即读”不同。一个与外部 RDMA 写并发运行的 kernel，可能观察到旧数据、部分写入或不符合预期顺序的数据；要在持续运行的 kernel 内交接，必须使用平台或通信库明确支持的同步协议。NVSHMEM 的 signal／wait 等原语有自己的合同，不能用随手写的 flag 替代。

CUDA 还提供更显式的可见性 API。以下示意限定：CPU 已确认本批网络写入完成，当前 CUDA context 是目标数据所属 context，设备支持 Host flush API，并且只要求该 owner context 消费：

cudaError_t st = cudaDeviceFlushGPUDirectRDMAWrites(
    cudaFlushGPUDirectRDMAWritesTargetCurrentDevice,
    cudaFlushGPUDirectRDMAWritesToOwner);
/* 检查 st == cudaSuccess 后，提交后续 consumer。 */

这个调用等待的是外部写对指定消费范围可见，不负责判断某个网络请求是否已经传完。是否需要、能否调用，要查询 cudaDevAttrGPUDirectRDMAWritesOrdering 与 cudaDevAttrGPUDirectRDMAFlushWritesOptions：原生排序已覆盖所需范围时，flush 是 no-op，可以省略；需要使用上述 Host API 时，还要具备对应的 Host 支持位。不能把它变成每次接收后无条件添加的一步。

GPUDirect 的注册与并发边界：CUDA 12.8.1 GPUDirect RDMA · Synchronization and Memory Ordering；显式 flush 的语义、scope 和能力条件：CUDA Runtime API 13.0.1 · cudaDeviceFlushGPUDirectRDMAWrites。两份文档的版本分别固定，不将 NVIDIA 接口假定为其他加速器的保证。

生产端同样要建立依赖：如果源数据由 GPU kernel 产生，CPU 可以在生产 stream 里 cudaEventRecord，再 cudaEventSynchronize 成功等到生产完成后，才提交会读取这块显存的网络操作；仅 record 而不等待不足以约束 CPU 的下一次提交。无论生产端还是消费端，cudaDeviceSynchronize() 都不能替代网卡的完成确认。

把抽象说法落到代码SEND 的接收 WR 交代消息内容存在哪里；完成事件交代哪批操作已结束；provider 的设备排序、线程交接、CUDA stream／event 或适用的 GPUDirect 同步接口，再把这一批数据交给特定消费者。代码 Review 时应指出具体接口和依赖对象，而不能只留一句“确保可见”。

补充：描述怎样变成任务，结果怎样约束回收

仍看 P Host→D Host 的 64 KiB 普通 RC WRITE，使用非 inline payload，并为本次请求开启 signaled。连接、MR 与队列已准备好。下面先追任务描述，再追资源何时可以重用；这些名字不是同一种对象在不断改名。

两个容易混淆的地方：SGE 描述缓冲区，不是缓冲区本身；WC 是软件输出，不是 CQE 的另一个指针名称。固定 mlx5 在提交时保存 wr_id，poll 时再从追踪信息恢复它，说明 WC 不只是把硬件 CQE 原样复制一遍。

固定依据：rdma-core v65.0／58e40801bfed。构造 WQE 与保存 wr_id；解析 CQE 并恢复 WC 字段；非 inline 源缓冲区生命周期。清理硬约束见 CQ 的 QP 关联和 PD 关联资源；本例内存清理顺序对应 rping_free_buffers。这些是接口与实现关系，不是本机运行轨迹。

连成一句话PD 约束资源关联，MR 登记可访问的数据区域；WR／SGE 由应用描述任务，provider 转成 SQ 中的 WQE；RNIC 执行后把 CQE 写入 CQ，provider 经 poll 给出 WC，应用再据对应结果管理消费和回收。

检查 2生命周期与完成判断

沿本页固定的 mlx5 路径，P 用两个 QP 分别把 Host 源缓冲区 A、B 写入 D 的两个目标区。两侧的区域均互不重叠，注册和权限正确；两次都是非 inline、signaled 的普通 RC WRITE，使用不同的 wr_id 且完成追踪记录仍有效，发送完成共用 P 的一个 CQ，且没有其他任务引用 A。

P 提交 A 返回 0 后，重用原来的 WR／SGE 结构描述并提交 B。随后只取得了属于 B 的成功 WC，尚未取得 A 的 WC。

  1. 重用 WR／SGE 描述结构，与覆盖 A 中的源数据，是否可以作出相同的安全判断？分别说明依据。
  2. D 没有为这些普通 WRITE 预先调用 ibv_post_recv，自己的 CQ 也没出现对应的接收完成。这是否足以判断 WRITE 失败？D 要开始消费数据，还需要哪一层安排？

解释依赖关系即可，不需要写代码或计算。

参考要点

本课固定 mlx5 路径在提交期间读取 WR／SGE 字段并构造设备 WQE，因此提交成功后可以重用原描述结构；但 A 的非 inline payload 仍需要本次传输不再读取它的完成依据。B 的成功 WC 不能证明 A 已完成，共享 CQ 不建立跨 QP 顺序。尚未取得 A 的 WC 意味着完成证据不足，不等于 A 必定仍在执行。

普通 WRITE 不消费 D 的接收 WR，也不自动产生对应 RECV 完成，因此没有预贴接收或没有这条接收完成都不足以判定失败。D 的消费要与本批数据完成、可见性和正确映射衔接。rping 在 WRITE 完成后另发 SEND 是一种具体通知方式；其他后端可以用不同的就绪协议。SEND 的接收区和各类可见性操作见本节点补充。

符号与名词

RDMA
Remote Direct Memory Access；在约定的地址范围与权限下进行远程内存访问和数据放置的一类能力／操作。
RNIC、Host DRAM、payload
本课 RNIC 指支持硬件 RDMA 的网卡；Host DRAM 是主机内存；payload 是本次实际搬运的数据内容。
内存注册
让通信实现知道哪些内存区域可以被设备访问，以及允许哪些操作；具体对象与权限在后续节点展开。
InfiniBand、RoCE、iWARP
与 RDMA 相关的网络／协议选择；RoCE 在以太网上承载 RDMA，iWARP 可基于 TCP。
opcode、ibv_post_send
opcode 标明操作类型；ibv_post_send 将工作请求提交给选定队列，其名字不限定工作请求必须是 SEND 操作。
NVSHMEM
NVIDIA 面向多 GPU 的通信库，以分区全局地址空间表达跨 GPU 数据访问。
Host staging、GPUDirect RDMA
前者经主机缓冲区中转 payload；后者允许网卡直接访问已注册的 GPU 显存。
IBRC、IBGDA
NVSHMEM 的传输实现；此处比较 CPU proxy 与 GPU 生成、提交网卡请求的分工。IBGDA 还存在由 CPU 代敲 doorbell 的模式。
MR、lkey、rkey
MR 是注册内存区域；lkey 用于本地 RDMA 内存访问，rkey 用于远端访问校验。它们不验证业务数据属于哪个请求。
Protection Domain
保护域，本地 RDMA 资源的访问关联范围；源码常缩写 pd，与 prefill/decode 分离无关。
QP、SQ、RQ、RC
QP 为队列对，包含发送队列 SQ 与接收队列 RQ；RC 是 Reliable Connection（可靠连接）传输类型。本课普通 WRITE 由发起方 SQ 提交。
WR、SGE、WQE
WR 是软件工作请求；SGE 描述一个本地缓冲区片段；WQE 是设备工作队列项。描述结构与其指向的 payload 有不同生命周期。
provider、doorbell
provider 是对接具体 RDMA 设备的实现；doorbell 用来通知设备有工作可处理。
CQ、CQE、WC、wr_id
CQ 是完成队列，CQE 是其中的完成条目；软件 poll 后取得 WC，用 wr_id 识别请求、status 判断结果。
signaled、inline
signaled 请求一条完成报告；inline 将 payload 随任务内联提交。本例只使用前者，主体数据保留在源缓冲区。
数据可见性、DMA 一致性
可见性指特定消费者后续读取能观察到应当读取的写入；Host DMA 一致性、完成处理、线程交接和 GPU 同步分别处理不同边界，不能互相替代。
CUDA stream、event、H2D
stream 是有序设备任务流；event 标记其中的完成边界，可供 Host 或其他 stream 等待；H2D 是 Host 到 Device 的数据拷贝。
RDMA 设备 context
软件打开本端 RDMA 设备后使用的句柄；PD 和 CQ 由它创建，QP 则关联指定 PD 及完成队列。
