5Continuous Batching：在执行步之间重组请求集合

对应固定源码：Scheduler.schedule 的 running／waiting 处理、结果更新与结束请求回收。前面的 trace 帮助定位时间，本节开始解释是谁安排下一批工作。

继续同一个单卡文本服务。请求的到达时刻和输出长度不相同：有的很快结束，有的还要生成很长一段。如果服务必须等一整组请求全部结束才接纳下一组，先完成的请求就无法让等待者尽早获得执行机会。Continuous Batching 把重组机会放到模型执行步之间，根据请求的新状态形成下一次执行计划。

这里的“一个 batch”指本轮交给模型执行的一组请求及其待处理 token 位置，不是一个固定不变的用户请求组。一次已经提交的执行使用确定的输入；新请求可以被接收并排队，再参与后续调度。异步调度能够把不同批次的准备与执行做成流水，也不等于把新请求临时插进正在执行的 kernel。

下面固定一个便于核对的教学模型：同步调度，执行及输出处理结束后再观察下一步；单卡 TP=PP=DP=1，普通自回归生成；不启用 speculative decoding、prefix cache 命中、多模态、KV 传输或抢占。模型中 KV 充足，其他准入限制不触发；这些是图的前提，不是实际部署的默认配置。本段的输出产生／交付均指服务端正式生成并记入请求状态，不表示客户端在同一步已经收到流式消息。

让一个早结束的请求，为等待者让出机会

为观察成员变化，先把主例重置到一个新的调度快照：R₁、R₂ 两条已完成 prefill 的请求正在 decode，分别还需生成并记入输出序列 1 个和 3 个 token 后停止。R₃ 已到达并等待，输入为 3 个 token，要求输出 2 个 token；本例不会提前遇到 EOS。活动请求名额为 2，每步待前向处理的位置预算为 4。每次普通 decode 处理一个已知输入位置并采样下一个 token；R₃ 的完整 prefill 处理三个输入位置后，可以交付首个输出。

设计上的收益机会来自两个变化：结束请求不再拖住等待者直到整组清空；每轮可以把不同请求当前需要的工作放在一起执行。但混入更多工作也可能拉长某一步，使既有 decode 请求等待下一输出更久。因此需要同时观察新请求的 TTFT、既有请求的 raw ITL／TPOT 与整体吞吐，不能只数“少了几轮”就宣称用户一定更快。

从模型对应到真实的 Scheduler 与 Worker

固定源码先为已有 running 请求分配工作，再考察 waiting 请求的准入。请求结束后，调度器根据返回结果和停止条件移除相应状态，记录 finished ID，并按生命周期条件处理 KV；worker 在消费后续调度输出时更新自己的持久 batch。新请求于是可以在原先长请求仍未结束时加入后续执行。

准入同时受到请求名额、每步工作预算、KV 分配和其他适用约束影响。当前源码的 max_num_seqs 还可配合更小的 max_num_active_seqs 控制活动请求上限。具体缓存或在途传输条件可能影响何时真正释放资源，不能把“生成了结束 token”“调度移除”和“所有物理存储立即可复用”当成同一个事件。

调度计划也不只是请求 ID 的名单：num_scheduled_tokens 保存每个请求本轮安排多少已知 token 位置。图中第二步给 R₂ 分配 1、给 R₃ 分配 3；worker 仍要保留请求、位置和 KV 的映射，混合执行不意味着把两条文本拼成一条能互相看到历史的序列。

实现依据均为 vLLM commit d7ada3aace051fecec553c185225db2259c2ac6a：running 处理、waiting 准入、结果更新与移除。图的同步、资源充足和停止时刻是教学条件，不覆盖完整版的所有分支。

结论：Continuous Batching 改变的是执行步之间的请求组合。它提供及时利用后续执行机会的机制，实际准入仍由资源与策略共同决定。

补充：动态组批、token 调度与 packed 输入是怎样配合的

阅读 vLLM 时，常会先看到“每轮按 token 位置安排工作”和一维的输入数组。这些实现细节与 Continuous Batching 描述的是不同层面：前者说明本轮工作怎样分配和表示，后者说明请求集合能够在执行步之间动态重组。

同一次调度需要同时决定：本轮有哪些请求参加，以及每个请求处理多少已知 token 位置。例如计划 {A: 1, B: 3} 的键确定请求集合，值确定本轮工作量。在普通生成场景里，A 可以进行一次 decode，B 可以处理一段 prefill。结束者退出、符合条件的等待者在后续批次加入，使这份计划的成员与数值都能随请求状态更新。

单独“按 token 分步执行”并不保证连续准入。固定的一组请求也能每轮各处理一个 token；如果新请求始终要等这一组全部结束才能参加，仍没有获得 Continuous Batching 的动态组批行为。因此，不需要在 vLLM 的 token 调度器之外再想象一个独立的“请求间微调层”；调度器本身就在实现这种运行组织方式。

输入布局让组合更方便，但没有消除请求边界

[Batch, Sequence] 与 [Tokens] 首先描述输入的表示方式，不能单凭形状决定调度策略。下面只画本轮需要前向的 token IDs：A 有一个 decode 输入 a，B 有三个 prefill 输入 b₀、b₁、b₂。A 的历史 KV 另外保存，不在这个本轮输入数组里。

矩形表示：[[a, PAD, PAD], [b0, b1, b2]]
打包表示：[a, b0, b1, b2]
请求分段：[0, 1, 4]

矩形表示可以通过新增或复用 batch 行来容纳新请求，不必把新请求接成旧请求的逻辑续写。packed 表示把本轮有效片段连续摆放，通常可减少按最长 query 长度逐行 padding 的浪费；为执行对齐或 CUDA graph 形状匹配，实际系统仍可能保留 padding。经过 embedding 后还会有 hidden 等维度，不能把这里的一维 token ID 数组理解为模型内部所有数据都是一维。

在 packed 数组中，a 与 b₀ 虽然物理相邻，仍属于两个独立请求。分段起点 [0,1,4] 表明 A 使用区间 [0,1)，B 使用 [1,4)。Batch／Sequence 的逻辑结构没有消失，而是更多地由元数据显式表达：

信息本轮执行中回答的问题
query_start_loc当前 query 输入中，哪些位置属于哪个请求？本例为 [0,1,4]。
positions、seq_lens这些位置在各自逻辑序列中处在哪里，当前可用上下文范围是什么？
block_table、slot_mappingattention 访问哪份逻辑上下文的 KV，当前 token 的新 KV 写入哪些槽位？

这些边界和映射使 B 的 attention 不会因为物理相邻就把 A 当作自己的历史。KV 页在合法条件下可以共享，但共享存储并不把两个请求合成同一条逻辑序列。packed 布局的便利来自布局、状态与元数据共同配合，而不是只做一次 flatten。

把两层关系按执行顺序连起来

Scheduler 先依据请求状态和约束生成本轮计划；ModelRunner 再从各请求取出选中的位置，构造 packed 输入及 attention 元数据，交给模型执行。固定源码的 Host 侧仍使用按请求组织的 token 表，再通过请求索引与位置提取本轮数据；二维管理结构与一维执行输入可以同时存在。vLLM 的 token 粒度调度已经在落实 Continuous Batching；packed 布局帮助它高效组织变长工作，Chunked Prefill 则让长输入也能分多个执行步参与这种安排。

固定实现依据：请求索引与位置提取、query 分段与长度、CommonAttentionMetadata。例子仅解释本轮 token IDs 的布局，不是实际性能测量。

6Chunked Prefill：把长输入的推进放进每步预算

对应固定源码：token 预算、已知位置与计算进度、waiting 请求的分块分支。继续单卡服务，观察加入的新请求怎样与已有 decode 共享一次执行。

Continuous Batching 允许在后续轮次接纳新请求，但一个长 prompt 的 prefill 可能一次带来很多待处理位置。如果整段都放进一次较长的执行，其他请求的下一次输出机会也会受这次执行时长影响。Chunked Prefill 将未处理的 prompt 切成可在后续步骤继续推进的片段，使长输入与其他请求的工作能够交错安排。

切分的是计算进度，不是把一段文本变成相互独立的请求。前面 chunk 产生的 KV 仍属于该请求，后面 chunk 的注意力需要此前上下文。正常自回归生成要在所需输入处理完成后，才向请求交付首个输出；中间 chunk 即使内部为实现方便做了临时采样，也不能把这些临时结果当成有效输出。

预算计的是输入工作位置，不是本轮产出 token 数

把主例重置到另一个给定快照：R₁、R₂ 都在 decode，在观察 R₃ 首输出的这些轮次内不会结束；R₃ 的 prompt 改为 10 个 token，最终需要 2 个输出。活动名额足够容纳三个请求，KV 充足。本例将两项源码 token 预算设为相等，先用 BtokB_{\mathrm{tok}}Btok​ 表示统一的每步预算，稍后再对应源码配置；没有额外长 prefill 上限、prefill 执行间隔限制或其他预算限制，本轮按给定顺序先安排 R₁、R₂ 各一个位置，再安排 R₃。

这是为了看清分配过程而固定的顺序。实际源码的 running 优先并不等于所有 decode 都无条件优先，因为未完成的 prefill chunk 也可以已在 running 中；具体顺序、节奏和分配还受版本与配置影响。

在 Btok=8B_{\mathrm{tok}}=8Btok​=8 时，两条 decode 用掉 2 个位置，给 R₃ 的本轮剩余额度为 6。第一轮处理 R₃ 的前 6 个输入位置，第二轮再处理剩余 4 个；R₃ 在第二轮结束后交付首个输出。第一轮总共处理 8 个位置，但本步生成、可供后续返回客户端的有效新输出只有 R₁、R₂ 各一个；8 不是“生成了 8 个新 token”。

用进度差理解 prefill 与 decode 的统一安排

对请求 r，记 prompt 长度为 pr，已正式记入该请求输出序列的生成 token 数为 gr，已前向处理的已知位置数为 cr。在本节普通自回归、同步执行且无重算的条件下，尚需处理的已知位置数为：

dr=(pr+gr)−crd_r=(p_r+g_r)-c_rdr​=(pr​+gr​)−cr​

调度器从这些已知但尚未处理的位置中分配本轮工作。真实源码同时有 max_num_scheduled_tokens 和 max_num_batched_tokens 两项预算；只有明确使它们相等，才可像本例一样合成一个预算。忽略本例不触发的其他约束后，核心关系可以写成：

remaining = num_tokens_with_spec - num_computed_tokens
num_new_tokens = min(remaining, token_budget, input_budget)

num_new_tokens 在这里是本轮分配的前向位置数，不是新增输出数。对刚到达的 R₃，已知的 10 个 prompt 还没有被计算；最后一段 prefill 完成并交付首个输出后，已知序列又多了一个刚采样的 token，下一次 decode 才以前向输入处理这个 token，再采样下一个。

从小模型看服务取舍

把相同关系放大：如果某份实验协议选择每步预算 2048，并给 64 条 ready decode 各安排一个位置，那么剩余额度至多为 1984 个输入位置。2048 与 64 是这里给定的说明规模，不表示实际机器的默认值或推荐最优值；实际准入还可能被其他约束进一步缩小。

较大的预算可能让长 prefill 用更少的决策步骤完成，也可能提高某些算子的执行效率；同一轮工作增多，又可能使已有 decode 的下一输出等待更久。较小的片段提供更多重新组合请求的机会，却可能增加调度和小批次执行开销。token 位置并不是等时工作单位，长上下文 decode 和 prefill 的每个位置成本也不同，因此步骤少不自动等于毫秒时间更短。

分块只限制本轮计算量，不会把已经累积的 KV 变成“只保留一个 chunk”。当前固定配置还可在准入时检查完整输入的 KV 容纳条件。每请求的 chunk 上限也只是一个上限，实际分配仍取决于总预算、请求进度和适用的准入条件。

后续参数对照会在同一服务案例中记录真实每步行为、TTFT、raw ITL／TPOT 与吞吐，再判断取舍。这里不根据教学控件选择“最优预算”；量化对照仍留给单元三，以同口径 BF16 基线复用。

完整输入 KV 的配置见 scheduler_reserve_full_isl。若对照关闭 chunked，还需满足该版本对 max_num_batched_tokens 与 max_model_len 的合法性要求；不能直接把本图“预算小于 prompt”的设置当作一个合法的关闭分块运行。

结论：Chunked Prefill 让长输入可以分步推进；Continuous Batching 决定不同请求怎样共同参与后续执行。两者连接到同一套请求进度、资源条件和每步预算，具体服务收益仍由真实测量决定。

检查 6空出请求名额之后

同一单卡服务处理完一轮结果后，R₁ 已结束且请求名额已释放，R₂ 还要继续 decode。R₃ 已排队；下一调度点的请求名额和本轮 token 预算足够，R₃ 的其他准入条件也均满足，但 KV 管理器明确报告无法为 R₃ 分配必需的 KV。本题不启用抢占、换出或其他释放方案。

R₃ 没有加入，是否说明服务退回了静态批处理？如果唯一改变是 KV 也足够，R₃ 是否必须等 R₂ 整条请求结束，加入应发生在哪个执行边界？

沿准入条件与执行边界解释即可，不用计算吞吐，也不用猜未给出的调度参数。

参考要点

R₃ 没有加入不能据此判为静态批处理。本题已经给定请求名额、token 预算及其他条件满足，阻止准入的是必需 KV 无法分配。Continuous Batching 允许在执行步之间动态改变成员，不保证任何到达请求都能立即执行。

当唯一不足的 KV 条件也满足时，R₃ 可以在后续调度决策形成的新执行批次中加入，不必等待 R₂ 整条请求结束。这是执行计划之间的重组，不是把新请求任意插入已经执行中的 kernel。

检查 7能分块，是否就会推进

沿用本节同步执行、无额外缓存命中或 KV 传入的模型。本题给定的调度策略不代表所有 vLLM 配置的默认行为。两类预算分别是：每步最多安排 2 个 token 位置，输入处理容量上限为 8 个位置；两者都计本轮待前向处理的位置数，不是请求数或新输出数。请求名额与 KV 均充足。长请求 P 已经准入并完成一部分 prefill，但输入尚未处理完。

在所考察的轮次中，另两条 decode 请求始终 ready，每轮各需要 1 个位置。策略先安排它们，再考虑 prefill，没有给 P 预留额度或轮转机会。P 必须完成全部输入处理，才能产生首个有效输出。

工程师只调小 P 的每次 prefill chunk 上限，就声称 P 会更快得到首个输出，而且 decode 的 ITL 不受影响。这个判断有何依据？P 开始推进首先需要什么条件？若从现有总调度额度中让出一部分给 prefill，decode 侧可能付出什么代价？

按实际分配的预算与首输出条件解释即可，不用猜具体配置命令或计算耗时。

参考要点

本轮可安排额度是 2，两个 ready decode 各占 1，P 没有得到实际分配；输入上限 8 不提供另一份独立额度。调小单请求的 chunk 上限不会创造剩余调度预算，所以在所给轮次和策略下，不能据此声称 P 更快产生首个输出。

P 推进的必要条件是实际获得前向处理额度，并最终补齐全部必需输入。若保持现有优先策略，需要 decode 需求不再占满额度；调整预留、轮转或额度分配也可以让 P 在 decode 尚未结束时推进。因此不应普遍表述为“必须等某条 decode 完成”。

若在当前总额度内给 prefill 让出一部分，就会减少本轮可安排给 decode 的工作机会，至少一条 decode 可能延后，进而可能拉长它的输出间隔。具体毫秒影响还取决于每轮执行时间和后续路径，不能保证所有请求都同幅变化，也不能保证 ITL 完全不受影响。

7把一次调度参数变化做成可复核的服务对照

对应资料：固定版本的 Scheduler 配置继承、实际分配限制，以及 vllm bench serve 的结果保存。建议先读本节讲解，再回看所引源码。这里把前六节的方法连成同一个服务案例的对照设计。

仍考虑单卡 BF16 文本服务：已有请求在 decode，新来的长输入需要 prefill。前一节说明了如何分配每步工作，现在的问题是：如果把预算调大，用户更快看到首段了吗？持续输出是否仍顺畅？服务整体处理得更多了吗？这些问题需要同口径的运行结果，不能只从配置数字或调度步骤数量推出。

因此要同时保存原始参数和最后生效的配置，并用相称的调度记录或短 trace 核对实际批次。这一步区分“改了一个数字”和“确实改变了想研究的执行条件”。如果所选负载始终用不到两档上限，当前观察可以形成该负载下的负结果，但不能推广为调度机制在所有场景都没有价值。

一个显式参数也可能影响多条内部路径。固定源码将它用于持久缓冲区容量，并纳入计算图配置 hash；实际 batch shape、预热覆盖和执行路径都可能随之改变。它们是需要记录和解释的派生变化，不能把“只改一个配置”直接写成“内部只有配额这一种机制变化”。与它无关却同时更换的模型、负载或 profiler 状态，则会破坏原本的比较。

固定实现：预算继承、实际分配限制、计算图 hash 的配置因素。这些源码说明潜在作用路径，不证明本次尚未采集的性能结果。

正确性、干净计时和短 trace 各自承担一项工作

两档配置先满足同一份事前确定的正确性判据。请求返回成功只是其中一项执行状态，不能替代模型输出核验；实际输出长度也必须保留，避免把输出变短误认为执行更快。具体校验样本、参考和容差由实验方法给出，不在看到结果以后临时降低标准。

随后按相同方法完成预热与重复运行，记录输入、运行顺序和所有结果。交替运行顺序有助于发现热状态或时间漂移，但本身不保证消除全部噪声。每个配置先保留各轮的绝对指标和波动，再计算同口径相对变化；不能只展示最有利的一轮，也不能把不同轮的分位数随意平均后改称全部样本的同一分位数。

性能报告来自关闭 profiler、采用一致记录方式的运行。另取对应配置与负载的短采集窗口，用来读实际安排、资源活动和依赖。trace 可以解释候选原因，但采集带来的开销、事件覆盖和窗口必须单独说明；它不代替干净 benchmark 的服务时间。

导师串讲：沿一个长请求，把七个节点连起来

现在把同一个场景从头走一遍：一个长请求 R₃ 到来时，单卡 BF16 服务里已有一些请求持续 decode。我们先固定请求内容、生成条件、到达方式与客户端测量边界。R₃ 何时被产生、何时真正发出、何时收到首个和后续输出，分别留下记录；TTFT、TPOT、raw ITL、E2EL 与整轮吞吐，才有了可以追溯的来源。

进入引擎后，请求名额、KV 和工作预算共同约束准入。Continuous Batching 允许后续执行计划根据新状态改变成员；Scheduler 为选中的请求分配本轮位置，ModelRunner 再准备 packed 输入及各请求的 attention 元数据。物理上相邻的 token 仍保持不同逻辑上下文，已结束请求与新请求的状态也按执行边界更新。

把前一节的教学模型放大：假设当前有 64 条 ready decode，每轮各处理一个位置；R₃ 有 4096 个尚未处理的 prompt token，请求名额上限为 128，KV 与其余条件满足。仍采用普通同步生成，给定这些 decode 在 R₃ 完成 prefill 前不结束、每轮先安排它们，没有其他限制。

若两项预算都为 2048，留给 R₃ 的额度为 1984，模型中分成 1984、1984、128 三段；若都为 4096，则分成 4032、64 两段。这些数量由给定条件计算，只说明首输出可能在更少的调度步骤后具备产生条件。更多工作集中在一轮，会怎样改变真实执行时长与其他请求的输出间隔，还需要测量，不能从三步变两步直接写出延迟提升比例。

因此，在真正比较前先验证两档正确性，并核对生效配置确实对应预期干预。性能运行关闭 profiler，按固定协议留出预热、重复与原始记录；另采对应窗口的 trace，从慢请求关联到相关批次，区分 Host 准备、设备工作、传输、分配和等待。判断某项工作是否限制目标时，沿必要依赖追到完成边界，不把所有条形长度相加。

最后回到报告。先陈述同口径观测，再说明它怎样支持或修正事前预测；把已有依据支持的机制与仍然未知的机制分开。配置是否值得采用，要结合业务重视的等待、平均输出节奏、停顿与容量，以及同一请求上的服务目标。这里得到的是一条从请求到证据的分析链，正式运行结果应由同一份服务 benchmark packet 承载。

上面的 64／4096 及分段数量属于教学构造，不是本课实测，也不代表已选定的 AMD 硬件或正式实验规模。

参考要点

请求级 TPOT P99 为 40 ms，表示对每个合格请求的平均每 token 耗时取第 99 百分位，得到阈值 40 ms；它不表示最慢 1% 请求的 TPOT 均值，也不表示这些请求都恰好为 40 ms。pooled raw ITL P99 为 120 ms 同样是间隔样本的高分位阈值，不是最大值，可以有间隔超过它。

kernel 代码和单次耗时不变，不妨碍调用减少降低总工作量；但总工作量减少不保证目标请求一定更早完成。应把减少的工作关联到目标请求的依赖、等待与资源活动，检查它是否改变必要路径的完成时刻，以及其他路径是否仍决定完成边界。只有累计时间或占比，还不足以建立端到端因果归因。

综合核验 2从调度过程解释服务取舍

单卡流式服务中，多个请求正在 decode，一条长 prompt 请求 P 到来。服务已启用 Continuous Batching 和 Chunked Prefill，采用本课的普通同步生成模型，不使用 speculative decoding 或额外缓存命中；请求名额与 KV 均充足。

比较同一长输入，只提高每步有效 token 预算，其他主要条件相同。题设给定：P 实际获得更多 prefill 份额，完成输入所需步数减少；原有 decode 请求在 P 产生首个输出前持续 ready。请串起 P 从加入后续执行批次、分段处理输入到产生首个输出的过程，并解释为什么步数减少仍不能保证 TTFT 和已有 decode 请求的 ITL 同时改善。

参考要点

P 到来后进入待处理集合；在资源和策略允许的调度边界，Scheduler 可把 P 的一部分待处理输入加入后续执行计划，无需等原有请求整条结束。每轮按已完成进度与可用预算继续分配 P 的工作，已计算输入对应的 KV 支撑后续片段。在本题普通同步、无额外缓存命中的模型中，全部必需输入处理完后，才具备生成并返回首个有效输出的条件。

decode 持续 ready 表示每个调度边界仍有工作可供安排，不表示这些请求一直未执行，也不保证每轮都被选中。实际批次可以混合 decode 与一段 prefill；每轮成员和份额仍由策略、预算及请求状态决定，不能把“每一批必定混合”当成通用条件。

提高预算使 P 获得更大份额并减少步数，这是题设给定的调度变化。TTFT 计算的是客户端等待时间，包含各次推进前的等待、实际执行以及首输出返回路径；每步工作变多可能使单步更长，因此步数更少不保证这些时间之和更短。在同步混合批次中，decode 的下一次输出也可能受到该步执行时间或后续调度机会影响，ITL 可能拉长，但是否变长及变化幅度仍需测量。

机制上存在更快推进长输入与维持 decode 输出节奏的取舍；更大的批次也可能改变设备执行效率。应在同口径服务测量中观察 TTFT、ITL 与吞吐，再用实际安排和时间线解释结果，不能只从步数或预算数字断言效果。

CPU FP32 参考：目的与边界

你的追问

为什么本次试验需要cpu fp32的参考？

需要的是独立数值正确性检查，CPU FP32 是本次选择的实现方式，不是所有性能实验的必需条件。请求成功和输出长度一致仍不足以证明模型计算正确，因此使用同一权重与输入，在 Transformers 的独立实现里计算参考概率，再与 vLLM 的输出核对。

FP32 减少参考计算自身的舍入误差；允许 BF16 服务结果在事前确定的容差内偏离。把已经以 BF16 保存的权重提升为 FP32，并不能恢复存储时已经损失的精度。CPU 则让参考不占用服务的 GPU 显存，它并不天然比 GPU 更正确。原则上也可以安排隔离执行的 GPU FP32 参考。

实际校验使用服务器生成的前缀做 teacher forcing：预测第 j 个生成 token 时，参考也看到此前实际生成的 token，避免早期近似平局造成整段序列分叉。检查每个位置的概率差与 greedy gap，而不是用 HTTP 200 或文本非空替代正确性。

这里的 logprob 是概率的自然对数，nats 是对应单位；greedy gap 是参考 top-1 的 logprob 与实际所选 token 的参考 logprob 之差，用来判断选择是否接近参考最优项。

报告显示：新配置的 TTFT 中位数、TPOT 中位数及请求级 TPOT P99 更低，输出 token/s 更高，但 pooled raw ITL P99 更高。另采的对应配置 trace 显示某个热点 kernel 的累计时间下降。报告没有提供跨轮重复证据，也未说明业务优先级或 SLO，却写道：“用户体验全面改善；每组有 2 万个间隔样本，两个 P99 都已稳定；收益由这个 kernel 变快造成。”

综合核验 2：原题、原答与 ready 的含义

原题

单卡流式服务中，多个请求正在 decode，一条长 prompt 请求 P 到来。服务已启用 Continuous Batching 和 Chunked Prefill，采用本课的普通同步生成模型，不使用 speculative decoding 或额外缓存命中；请求名额与 KV 均充足。

比较同一长输入，只提高每步有效 token 预算，其他主要条件相同。题设给定：P 实际获得更多 prefill 份额，完成输入所需步数减少；原有 decode 请求在 P 产生首个输出前持续 ready。请串起 P 从加入后续执行批次、分段处理输入到产生首个输出的过程，并解释为什么步数减少仍不能保证 TTFT 和已有 decode 请求的 ITL 同时改善。

像向面试官解释那样，用一段连贯文字回答即可；不需要计算、录音或列命令。

词义澄清

原有 decode 请求持续 ready的意思是decode请求在P 产生首个输出前都不加入执行批次吗？

ready 表示在调度边界仍有下一步 decode 工作可安排，不表示这些请求一直未执行，也不保证每轮都获配。它们在 P 处理输入时可以反复加入后续执行批次。

你的原答

明白。那么提高了每步有效 token 预算。从P请求到来，P请求需要进行prefill。调度器开始调度，根据更高的token预算进行调度，将原有decode请求和新来的P请求调度到后续执行批次中。其中，根据token预算对P请求的序列进行分段，每一批只处理一段序列。直到P请求的输入序列被全部处理完，最后一个处理批次会产生首个输出。其中每一批都是decode请求和分段的P请求一起进行执行计算。P获得更多prefill token份额，减少了完成首次输出的步数，不一定保证TTFT和decode的ITL同时改善。因为此时批次虽然尽早地处理了prefill需求，但由于需要同时处理prefill和decode，大计算量的prefill会对decode的输出时间产生影响，会使得ITL变长。

讨论后的补准

主链是后续批次准入、按预算分段推进、全部必需输入完成后具备首输出条件。每批并非必然混合 prefill 与 decode；步数更少还要结合单步时长判断 TTFT，ITL 则只能说可能变长。后来的实践用真实记录检验这些取舍，而不是把讲解中的方向当成保证。

符号与名词

s、uⱼ、J、L
s 为客户端请求函数的发送起点；uⱼ 为第 j 个被接受的输出消息的处理时刻；J 为输出消息数，L 为实际生成 token 数。时间使用同一客户端单调时钟，J 不一定等于 L。
TTFT、E2EL、TPOT、raw ITL
首个输出事件等待、到最后输出事件的请求时间、首输出之后按 token 数摊销的平均时间、相邻输出消息间隔列表；具体边界依赖所选工具与端点。
D、S、goodput、SLO
D 为完整正式测试窗口（秒），S 为成功请求集合；SLO 是明确的服务目标，goodput 为成功且同时满足所选目标的请求数除以 D，单位 req/s。
trace 与 benchmark packet
trace 是带时间关系的执行事件记录；benchmark packet 是使测量可回看、可复核的一组配置、命令、正确性与原始结果材料，不等同一张汇总表。
Host 范围、stream、correlation
Host 范围记录 CPU 代码或调用的经过时间；stream 表示设备工作的一条提交／执行序列；correlation 将相关的 Host 提交与设备活动联系起来，不自动提供全部数据依赖。
关键路径、total、self
关键路径是在给定依赖与持续时间下决定目标最早完成的约束链；total 包含某范围的经过时间，self 扣除记录到的子调用。跨层或重叠范围不能直接相加为端到端时间。
Continuous Batching、执行步、请求名额
在后续调度决策中根据请求状态重组执行集合；一个执行步是一次已确定输入的模型工作，步骤并不等长。请求名额是逻辑准入约束，不是固定 GPU 行或 KV 地址。
Chunked Prefill、Bₜₒₖ、pᵣ／gᵣ／cᵣ
长输入按每步可用工作预算分段推进。Bₜₒₖ 为本节合并后的每步 token 位置预算；pᵣ 为 prompt 长度，gᵣ 为已正式记入请求的生成输出数，cᵣ 为完成快照中的已前向位置数；不能将图中快照解释为真实异步字段任意时刻的设备完成量。
