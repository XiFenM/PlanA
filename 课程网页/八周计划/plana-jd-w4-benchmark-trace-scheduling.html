从一次算子计时，走到一份能解释服务取舍的报告

上一单元把一个 MatMul 的工作量、时间和 Roofline 放在了同一口径下。现在把视角移到使用模型的人：请求已经发出，多久才能看到开头？生成过程中会不会停顿？服务承接更多请求时，这些体验又会怎样变化？同一台 GPU 上的算子效率，只是这条服务路径中的一部分。客户端发起方式、服务器排队、prefill 与 decode 的交错、输出回传，都可能改变最后看到的指标。

本课沿一个单卡 vLLM V1 流式文本服务案例展开。先定义报告中的时间和吞吐，再固定 benchmark 的负载与比较条件；随后用一条 trace 观察执行与等待，回到 Continuous Batching 和 Chunked Prefill 的决策，最后只改变一项调度参数检查取舍。AMD 增强采用同一个小模型服务主题：环境与 BF16 基线可供单元三的量化对照复用，具体模型与版本将在实验准备时按实际支持范围固定。

学完这一课，应能判断两份服务报告是否真的可比，区分用户等待、输出节奏与服务容量；能读出 trace 中真正影响完成时间的依赖，并用独立的调度变式和受控数据解释取舍。已有的请求主链和算子计时知识直接作为前置，性能主张始终限定在明确的环境与负载中。

前置回看：单元一的 MatMul 实测案例。服务测量的主例从下面的客户端时间线开始。

1先知道时钟在哪里，再解释一个服务指标

对应资料：客户端 async_request_openai_completions 与服务 benchmark 的 calculate_metrics。本节先用时间线理解，再核对源码字段。

设两个请求 R₁、R₂ 发给同一个流式文本服务。客户端会逐段收到输出，而不是只在最后拿到完整回答。现在希望知道“首段等了多久”“后面输出是否平稳”和“整轮服务处理了多少工作”。这三个问题需要不同的时间边界和统计对象。

本课选定固定源码中的 openai backend、/v1/completions 流式路径。负载发生器产生请求后，客户端可能先等待并发名额；真正进入请求函数、即将调用 session.post 时才记起点 s。随后记录被适配器接受的输出消息时刻 u₁、u₂……uJ。这些时钟都在客户端，不是 GPU 生成 token 的时刻。

一条请求的四种时间

TTFT（Time to First Token）描述从所选发送起点到第一个输出事件的等待；其中可以包含网络、服务器排队、prefill 和回传。它不等于单独一次 prefill kernel 的时间。E2E latency 描述所选请求完成边界内的总时长；适配器把这个时长保存在 latency 字段，benchmark 再按 E2EL 汇总。终点是最后一个被接受的输出消息，因此本例为 250 ms，而不是含收尾的 270 ms。

TTFTr=ur,1−sr,E2ELr=ur,Jr−sr\mathrm{TTFT}_r=u_{r,1}-s_r,\qquad \mathrm{E2EL}_r=u_{r,J_r}-s_rTTFTr​=ur,1​−sr​,E2ELr​=ur,Jr​​−sr​

raw ITL 是未经“每请求平均”的相邻输出事件间隔列表。令 Jr 为客户端接受的消息数，Lr 为这条请求实际生成的 token 数；二者分别计数。TPOT（Time per Output Token）则把首个输出之后的整段时间按剩余 token 数摊开，每条合格请求只产生一个数：

ITLr,j=ur,j−ur,j−1,2≤j≤JrTPOTr=E2ELr−TTFTrLr−1,Lr>1\begin{aligned}\mathrm{ITL}_{r,j}&=u_{r,j}-u_{r,j-1},\quad 2\leq j\leq J_r\\\mathrm{TPOT}_r&=\frac{\mathrm{E2EL}_r-\mathrm{TTFT}_r}{L_r-1},\quad L_r>1\end{aligned}ITLr,j​TPOTr​​=ur,j​−ur,j−1​,2≤j≤Jr​=Lr​−1E2ELr​−TTFTr​​,Lr​>1​

R₁ 的 TTFT=100 ms、E2EL=250 ms；raw ITL 为 [40, 30, 80] ms，TPOT 为 (250−100)/(4−1)=50 ms。TPOT 把一条请求归纳成一个平均值，raw ITL 保留了这次输出中出现过的 80 ms 停顿；二者都值得保留，回答的问题不同。

真实网络先送来字节块，再由客户端拆出流式消息；一块字节可能含多条消息，一条消息也可能带多个 token。因此 raw ITL 在这个工具里首先是输出消息事件的间隔。输出 token 数优先取 usage；当该值缺失或为 0 时，有 tokenizer 就对完整输出重新分词估算。这个估算也未必与服务端原 token 序列完全一致，所以协议要记录长度来源，不能直接写成“ITL 个数加一”。所选 Completions 适配器接受非空 choices，其中的文本允许为空，所以字段 TTFT 也未必就是用户首次看到非空字符的时间；换端点时必须重新核对这些边界。

固定源码：时间戳与输出消息条件。client_queue_time 另记请求产生到发送计时起点的差值，包含名额等待及发送前的调度／准备，不是服务器排队时间。服务器内部的同名指标使用另一组事件，不能仅凭字段名混合比较。

汇总之前，先决定谁算一个样本

仍用同一个服务，再加入 R₂：它从 0 ms 开始，在 80 和 200 ms 各收到一个 token，220 ms 收尾；因此 TTFT=80 ms、E2EL=200 ms、TPOT=120 ms，raw ITL 只有 [120] ms。现在，按请求汇总 TPOT 时，样本是 [50, 120]，均值为 85 ms；混合 raw ITL 时，样本是 [40, 30, 80, 120]，均值为 67.5 ms。

差异来自权重：每条请求对 TPOT 分布贡献一个值，输出事件更多的请求对 raw ITL 分布贡献更多间隔。均值如此，p50／p95／p99 的样本集合也不同，不能把“每请求 TPOT 的 p50”和“混合 raw ITL 的 p50”当成同一个量。分位数本身也要附样本量；这两条教学请求只能说明定义，不能形成稳定的尾延迟结论。

固定实现怎样处理短输出和失败请求？

只有成功请求进入 TTFT、E2EL 和 raw ITL 分布；TPOT 分布还要求实际输出长度大于 1。L≤1 时没有“首 token 之后每 token”的分母，因此不应把界面显示的默认零当成真实零耗时；这个版本在 goodput 判定里将该类请求的 TPOT 按 0 处理，是需要写明的工具约定。若 usage 长度缺失且没有 tokenizer，源码还会用 1 占位；这样的占位不能充当精确的生成 token 数，正式报告应确保长度来源可靠。失败／超时必须另报数量和原因，不能只展示删去失败样本后的较低延迟。

整轮吞吐与 goodput 使用同一个测试窗口

把成功请求集合记为 S，整轮 benchmark 时长记为 D（秒）。这个 D 从正式请求发生循环之前开始，到全部请求任务收尾完成为止；它包括到达间隔和客户端等待，并不是各请求 E2EL 相加。设 Ir、Lr 为请求 r 的实际输入／输出 token 数：

Req/s=∣S∣D,Output tokens/s=∑r∈SLrDTotal tokens/s=∑r∈S(Ir+Lr)D\begin{aligned}\mathrm{Req/s}&=\frac{|S|}{D},\qquad \mathrm{Output\ tokens/s}=\frac{\sum_{r\in S}L_r}{D}\\\mathrm{Total\ tokens/s}&=\frac{\sum_{r\in S}(I_r+L_r)}{D}\end{aligned}Req/sTotal tokens/s​=D∣S∣​,Output tokens/s=D∑r∈S​Lr​​=D∑r∈S​(Ir​+Lr​)​​

再给定这两条请求的完整测试窗口：从图中发送起点之前的 −30 ms 开始，到 R₁ 在 270 ms 收尾，故 D=0.30 s；前 30 ms 表示窗口内的请求发生与发送前准备。只有 R₁、R₂ 两条请求且都成功，那么请求吞吐约为 6.67 req/s，输出吞吐为 6/0.30=20 token/s。不能因为名字都带 token/s，就混用输出吞吐与输入加输出的总 token 吞吐。

goodput 是满足服务目标的成功请求速率。服务目标 SLO 可以指定 TTFT≤150 ms、TPOT≤60 ms；所选条件必须在同一条请求上同时满足。本例 R₁ 达标，R₂ 的 TPOT 不达标，所以 goodput=1/0.30≈3.33 req/s。它不是 50% 的达标比例，也不是“几个汇总分位数看起来各自达标”。

本实现将失败请求的输出长度记为 0，它们不进入成功吞吐或 goodput 的分子；失败或超时收尾仍可能拉长 D。这里的成功仅表示通过该请求函数的成功判定，模型输出是否正确还需要独立判据。

聚合依据：样本选择与 SLO 联合条件、吞吐和分位数。本节两条请求及所有时间均为明确给定的教学构造，计算已复核，不作为本课实测。

结论：解释一个服务指标，至少要说明时钟在哪、边界在哪、谁算一个样本、分母是哪段时间。只有这些信息一致，数字的高低才有共同含义。

补充：把 TPOT 放回请求时间线

面对一份流式生成报告，TPOT 回答的是：首个输出之后，完成剩余输出平均每个 token 用了多久。它把一条请求的生成段压成一个数，适合比较平均节奏；首段等待和中途某一次停顿需要另外观察。沿用本节点的时间边界，对实际输出长度 Lr>1L_r>1Lr​>1 的请求，有：

E2ELr=TTFTr+(Lr−1)TPOTr\mathrm{E2EL}_r=\mathrm{TTFT}_r+(L_r-1)\mathrm{TPOT}_rE2ELr​=TTFTr​+(Lr​−1)TPOTr​

因此，输出长度相同时，TPOT 更小意味着这条请求首输出后的总时间更短；如果 TTFT 也相同，E2EL 也会更短。若 TTFT 或实际输出长度改变，只看 TPOT 就无法判断整体完成时间。这是请求级关系，不能把分别汇总的 TTFT p50、TPOT p50 直接代入，得到 E2EL p50。

相同平均值，可以有不同的停顿

仍假设每条请求输出 4 个 token，每条消息恰好带 1 个 token。首个输出之后有三个间隔。下面两组间隔的总时长都为 120 ms，所以 TPOT 都为 40 ms：

请求三个 raw ITL（ms）TPOT（ms/token）最大消息间隔（ms）
甲40、40、404040
乙10、10、10040100

乙在最后一次输出前停了更久，前面的短间隔却把平均值拉回相同水平。TPOT 相同并不保证消息输出同样平稳。真实消息与 token 未必一一对应，仍须沿用本节点已经说明的适配器边界，不能将 raw ITL 直接当成 GPU 逐 token 执行时间。

先在请求内平均，再在请求之间取分位数

每条合格请求先产生一个 TPOT；把这些请求级均值组成样本，再按约定算法计算 p50、P99。P99 是分布高端的一个分位阈值，不是截取最慢 1% 的请求再求平均，也不是所有输出消息中最长的间隔。分位数算法可能在相邻样本间插值，报告应保留方法与样本量。

如果本批 20 条请求的 TPOT 都为 40 ms，本批 TPOT P99 也是 40 ms。这只说明这批请求的平均节奏在该口径下相同，既不排除上面的 100 ms 局部停顿，也不证明总体或跨轮稳定。一般的 20 条样本中，P99 主要受最大端少数值影响，不能据此承诺未来请求的稳定尾部表现。

TPOT 在哪些判断中有用

  • 长文本平均生成速度：它帮助描述首输出之后的平均等待成本；阅读过程是否会卡顿，仍需结合 raw ITL。
  • 受控配置比较：固定模型、工作负载与统计口径后，用 TPOT 和整体延迟判断配置变化，保留绝对值与跨轮波动。
  • 并发与容量取舍：把 TPOT 与吞吐、TTFT 一起看，判断服务接收更多工作时是否牺牲了请求体验；单看吞吐无法回答这一点。
  • 服务目标与 goodput：在同一条请求上联合检查 TTFT、TPOT 是否达标，再统计达标成功请求速率；不能用两个汇总分位数各自达标代替联合判断。
两组间隔及“20 条 TPOT 均为 40”的数据由导师补充，用于解释平均、停顿与分位数；计算已核对，不是新的服务实测。

2让两次 benchmark 回答同一个问题

对应资料：固定源码中的请求发生、并发限制与整轮计时。这里先解释协议的设计理由，实际输入规模和运行脚本在正式实验前约定。

现在希望比较同一服务的两个调度配置。即使模型和 GPU 一样，改变“请求什么时候进入系统”也会改变队列、批次和用户等待。协议的作用，就是固定足以影响结论的条件，让最后的差异能够回答事前提出的问题。

固定到达方式与固定并发，描述不同的负载

一种方式是预先指定请求到达时刻，例如每隔一段时间产生一个请求；服务变慢时，后来的请求仍按这条到达序列出现，等待可能积累。另一种方式是保持固定数量的进行中请求，完成一个才补入下一个；服务变慢时，补入速度也会随之降低。这两种方式都可用于测量，但它们给服务施加的压力不同。

在真实 benchmark 客户端里，“按时产生请求”和“真正发出 HTTP 请求”还可能隔着并发限制。固定源码在取得并发名额后才进入请求函数，发送前的等待另存为 client_queue_time；因此同时报告到达规则、并发上限和客户端排队情况，才能知道某段等待落在哪里。不能只看服务器内部排队或客户端 TTFT 中的一项，就宣布全部等待消失。

本课后续只选择一项主要调度变量对照，两种调度机制的理解检查围绕同一服务场景完成。与单元三复用 BF16 基线时，还要核对负载和统计口径；调度变化与量化变化分别比较，才能说明各自带来的取舍。

性能测量与 trace 分别负责什么

干净 benchmark 用于回答“在这些条件下究竟多快”；profiler trace 用来观察 Host、设备工作和等待怎样排列，帮助解释原因。采集 trace 本身可能增加开销，因此协议要把带采集的运行和干净计时分开，并尽量保持其余配置一致。节点 3 会沿同一个案例具体读这些事件。

预热、重复次数、运行顺序和相称的样本规模由 Agent 在实验准备时给出并解释。样本不足时，尾分位数只能作为探索性观察；原计划中约 200 个请求用于 p95、约 1000 个用于 p99 的经验提醒，也不自动保证估计稳定。先用少量代表性负载回答问题，再根据观察决定是否需要扩大。

本节点依据 客户端并发与测试窗口及原冲刺计划的性能规范。AMD 单卡服务案例的型号、镜像与工具支持按原增强方案在实验准备时核对；本节教学构造不替代真实环境中的验证。

结论：公平对照既要固定计算与软件，也要固定施加给服务的负载和报告规则。不同负载下各自测得的数字可以是真实的，但比较结论必须保留这些条件差异。

检查 1服务报告是否可比

甲、乙在同一 GPU 上使用相同模型、精度、请求集合与生成参数，均为 100% 成功，实际输出 token 总数相同。甲按预先固定的到达时刻产生请求，报告“每请求 TPOT 的中位数为 40 ms”；乙维持固定并发、每完成一个请求就补入下一个，报告“所有 raw ITL 混合后的中位数为 30 ms”。两边都以各自完整测试时长计算吞吐，乙的输出 token/s 更高。

报告据此写道：“乙的调度更优，用户等待更短，输出也更顺畅。”哪些观察能够成立，哪些归因或体验结论仍缺依据？如果只做一次最小公平对照，你会统一哪些关键口径，并保留哪些请求级记录来判断取舍？

不用猜具体调度算法，也不用列完整命令；围绕观测对象、负载与证据范围解释即可。

三个报告数值可以各自在原测试条件下成立。实际输出 token 总数相同而乙的输出 token/s 更高，说明乙本轮完整测试时长更短；这不直接说明每条请求等待更短或输出更平稳。甲乙的到达方式不同，TPOT 与混合 raw ITL 的样本对象也不同，所以这些报告不足以比较调度配置本身。原题没有说明调度参数是否改变，不能自行补入该前提。

最小公平对照需要对齐到达规则、并发上限、请求与生成条件、端点和测量／聚合定义，并明确唯一主要变化。按请求 ID 保留发送前到达与发送起点、首个／后续／末个输出事件、实际输出长度、成功／失败状态；由此核对 TTFT、E2EL、每请求 TPOT 和 raw ITL 列表，以及适用的服务目标。更丰富的分位数不能替代这些口径。

检查 2把体验对应到请求级记录

现在已统一两边的模型、GPU、请求集合、生成条件、到达序列、并发上限与指标定义。两边各有 20 条成功请求，每条实际输出长度都大于 1，每请求 TPOT 的中位数均为 40 ms。本题被接受的输出消息均含可见文本，但用户仍觉得乙“开始输出前等得更久，中途偶尔长时间停住”。

如果只补一份按请求 ID 关联的原始记录，你会保留哪些数据，分别核对首段等待、输出停顿和整体完成时间？基于这 20 个请求级样本得到的 TPOT P99 应怎样表述？

不用计算分位数数值；说明记录与体验之间的对应关系即可。

参考要点

首段等待对应 TTFT，输出过程中的停顿对应 raw ITL 列表及其顺序，整体完成时间对应本课定义的 E2EL；按同一请求 ID 保存时间边界和输出长度，才能关联这些指标。只保留一个 TPOT 平均值或汇总中位数，会丢掉首输出之前的等待和请求内部的局部停顿。

TPOT P99 的输入是 20 个请求各自的 TPOT 平均值。P99 是按约定分位算法得到的高分位阈值，不是最慢 1% 请求的平均，也不是某个输出消息的最长间隔。样本很少时，高分位主要受最高的一两个观察影响；可以注明“基于本轮 20 条请求的探索性结果”，不能将其写成稳定的总体尾部性能。

检查 3请求平均值与一次停顿

设本轮有 20 条成功请求，每条实际生成 4 个 token，且每条输出消息恰好对应 1 个 token。观察到这 20 条请求的 TPOT 全部为 40 ms。

这与“某条请求在首个输出之后，相邻两条输出消息之间出现过 100 ms 的间隔”是否矛盾？请解释理由，并说明怎样限定本轮 TPOT P99 结论的适用范围。

不用计算 P99，也不用实际采集；解释平均值、单个间隔和样本范围之间的关系即可。

参考要点

不矛盾。每请求有 4 个 token 且每消息对应 1 个 token，首输出之后共有 3 个间隔。例如 [10, 10, 100] ms 的平均值是 40 ms，仍包含一次 100 ms 的停顿。请求内的平均值不能约束每个局部间隔都等于平均值。

题设给定本批 20 条请求的 TPOT 全部为 40 ms，因此从这批样本计算的 TPOT P99 也为 40 ms。这个结果描述的是本批请求级平均值，不能证明未来请求、不同轮次或服务总体表现稳定，也不能证明消息输出间隔平稳。整体分布一致的信息来自全部 20 个样本，不是仅凭一个 P99 就能推断。

3把一个长输出间隔放回执行时间线

对应资料：vLLM 固定版本的 profiling 文档、worker 批次注解与 ModelRunner 范围；PyTorch profiler 的时间定义和关联逻辑。先读下面的局部时间线，再对照真实字段。

前两节记录了客户端何时收到 R₁ 的输出。假如某个间隔比平时长，raw ITL 可以定位这个现象，却没有告诉我们服务端是在计算、准备输入还是等待依赖。profiler trace 保存事件名、起止时间、所在进程／线程或 stream，以及可用的关联信息，把“发生了什么、发生在何时”展开成一条条轨道。

沿用同一个单卡服务，现在放大一个参与 R₁ 生成的批次。下面是为讲解构造的时间线，不是实际采集结果，也不声称固定 vLLM 每轮都执行这些具体拷贝或等待。假设请求日志已把 R₁ 关联到这批工作；其计算可能同时服务其他请求，不能把所有 kernel 时间独占记给 R₁。

图内各轨道使用同一构造时间轴，单位 ms；零点为这段服务端局部工作的开始，并非前面客户端的发送起点。主例设 TP=PP=DP=1，且不启用额外跨 rank 路径。Host 等待的是目标数据的 D2H 完成事件，不是全设备同步。背景 kernel G 不产生该输出所需的数据；为单独研究依赖，这个模型固定各段时长，并暂不引入资源争用造成的间接影响。

读关联和依赖，不只看条形是否挨在一起

Correlation ID 或 flow 关联可以把一次 Host 提交对应到设备活动；数据依赖还需要结合 stream 顺序、事件等待和数据消费关系核对。图中目标 K 虽在 2.4 ms 已经提交，仍要等 H2D 于 3.2 ms 完成；输出 D2H 在 2.5 ms 已提交，也要等 K 在 6.2 ms 完成。这些依赖说明了为什么“排进队列”与“可以开始执行”是两个时点。

Host 等待区间 2.5–6.7 ms 与设备工作重叠。它长达 4.2 ms，并不表示又在设备计算之外额外花了 4.2 ms。读取输出需要 D2H 完成，等待的存在有正确性理由；解释延迟要继续追问前面的数据何时可用。

固定 vLLM 源码中的 gpu_model_runner: forward 包围 Host 侧的 _model_forward(...) 调用，范围结束本身不是设备完成事件。worker 的 execute_context_…_generation_… 注解汇总批次中的请求／token 数，也不自动给出 R₁ 对每个 kernel 的独占归属。细范围还受开关控制，找不到这个名字不能据此认定没有执行 forward。

实现依据：forward 范围、批次注解及可选范围开关。PyTorch 2.13.0 固定构建的关联与内存记录解析说明关联 ID、Host／设备事件和瞬时内存记录的区别。

结论：trace 的阅读单位是“事件、轨道、关联与依赖”。长条、空白和名字都要放回采集范围与目标输出中解释。

4从热点列表走到目标输出的关键路径

继续图 3.1 的同一个批次。先明确目标是“这批响应何时在 Host 上组装就绪”，再追溯所有必须先完成的工作；客户端收到输出的时间还需要另外关联。

汇总表可以告诉我们哪些事件累计花费较多，时间线则保留了重叠、嵌套与等待。在图 3.1 中，G 执行 7 ms，K 执行 3 ms，kernel 时长相加为 10 ms；本批响应却在 7.7 ms 组装就绪，因为两个 stream 存在重叠，且本批不必等待 G 结束。这个相加结果适合描述所汇总的设备活动总时长，不能直接称为端到端延迟。

Host 侧也存在重复计数：准备范围的 total 为 2 ms，其中已经包含 0.5 ms 的分配子范围。在只记录这一个子范围的假设下，准备的 self 时间为 1.5 ms。不能再将 2 与 0.5 相加当作经过时间；self 只是扣除了被记录的子调用，仍可能包含等待或未单独标注的工作，不等于纯 CPU 计算时间。

定义依据：PyTorch 2.13.0 固定构建中的 cpu_time_total、self_cpu_time_total 与 device_time_total。不同工具的列名和聚合规则需按其版本确认，不把这三个数字相加成请求耗时。

关键路径由必须等待的依赖决定

目标输出的关键路径，是在当前依赖和各段时长下，决定它最早何时就绪的那条约束链。如果一步同时依赖两个前置分支，必须等较晚的那个完成；因此要从目标输出向前追依赖，而不是从最长 kernel 名称向后猜瓶颈。

本例中，目标 K 的开始取决于 H2D 是否完成，以及 K 是否已经提交。令 dK 为 K 的持续时间；图中的其他模型参数固定，便有：

在基线 dK=3 ms 下，本批响应在 7.7 ms 组装就绪。下面只改 K 或 G 的时长，观察“累计 kernel 时间”和“本批响应组装就绪时间”会怎样响应。它是对给定依赖的推演，不是新测量；资源争用与其他时长也随优化变化的真实情况，需要另外验证。

因此，某项工作占时很长，只能把它列为调查候选。若它不在目标的直接依赖链上，缩短它是否能带来间接收益，还要检查共享资源、队列与重叠关系。相反，Host 同步等待很长时，应检查它正在等的生产者和完成条件；直接删掉等待可能让后续代码读取尚未就绪的数据，并不能构成有效优化。

把候选解释变成可检验的因果判断

  1. 固定目标和观测范围。先说清要改善 TTFT、请求级 TPOT、局部停顿还是整轮吞吐，并把慢请求的 ID、输出事件与相关批次窗口关联起来。本地响应组装就绪提前，并不自动等于客户端整个输出间隔缩短同样多。
  2. 沿依赖提出候选解释。区分 Host 准备慢、设备数据尚未就绪、计算持续时间长、队列等待和输出处理；检查该解释是否真的位于目标路径上。
  3. 选择能区分候选的最小证据。例如查看提交与设备活动的关联、事件等待关系、必要的采集类别与请求日志。观察某一条轨道没有事件时，先核对覆盖范围，不立即宣称 GPU 空闲。
  4. 用受控、无采集开销的运行确认性能。同口径核对正确性、请求集合、输出长度、到达方式与运行顺序，保留绝对值和跨轮波动。profile 为原因提供线索，干净 benchmark 为服务性能提供依据；未解决的偏差如实保留。

后续真实 AMD 单卡环境会按实际工具版本核对活动类型、关联字段和采集窗口。例如 ROCprofiler-SDK 的固定版本资料把 HIP API、kernel dispatch、memory copy 与 memory allocation 分成不同采集类别；不能因为采到了其中一种，就假定其他轨道也完整。这里还没有采集目标平台的服务 trace。

采集范围依据：vLLM activities 与注解及frontend／worker 窗口差异；AMD 分类依据为 ROCprofiler-SDK 0.6.0／ROCm 6.4.1 文档，仅用于本节概念映射，不代表未来机器安装了该版本。

结论：热点回答“哪里累计工作多”，关键路径回答“目标为何还不能完成”。性能归因要把两者与实际测量边界连接起来，再用受控证据检验解释。

检查 4kernel 变快，目标为什么没提前

某次服务端批次输出必须等待两个分支都完成。它们在同一时间轴的 0 ms 开始并行执行：分支 A 是 5 ms 的 GPU 工作，分支 B 是 7 ms 的 Host 侧输出信息准备；两者完成后，还需 1 ms 组装输出。假设没有相互资源争用，这个局部批次的所有依赖已经给全。

一个正确性通过的改动只把 A 从 5 ms 缩短到 3 ms，B、组装时长和依赖均不变。kernel 汇总时间减少了 2 ms，但这个批次的输出完成时间没有改变。

这两项观察是否矛盾？请沿依赖解释应该优先核对哪条路径。如果进一步要声称真实服务的 TTFT 或 TPOT 得到改善，除了这条带采集的时间线，还需要哪些口径匹配的证据？

不用计算加速比，也不用猜具体 kernel；区分局部工作、目标完成和服务性能即可。

参考要点

不矛盾。在题设固定的并行依赖、B=7 ms 与组装=1 ms 下，局部输出都要等较晚的 B 完成；A 从 5 ms 缩到 3 ms 没有改变这一约束。关注 B 路径是合理的，但不能把这个结论推广到存在资源争用、依赖改变或 B 也改变的情况。

分支结束、组装起止等服务端记录可用于局部原因诊断。要主张真实服务 TTFT／TPOT 改善，还需与请求 ID 关联的客户端测量，以及模型、负载、输出长度、正确性和运行条件匹配的无 profiler 对照；本地组装就绪到客户端输出之间仍可能有其他环节。重复运行与波动记录用于限定结论的稳定范围。

检查 5把服务性能主张测清楚

继续检验同一个改动。模型、GPU、请求集合、生成条件、到达方式、并发上限与指标定义都相同，正确性均已验证。基线开启 profiler 时，报告的 TTFT 中位数为 200 ms、TPOT 中位数为 50 ms/token；改动后关闭 profiler，得到的两项中位数分别为 180 ms 和 45 ms/token。

这组数字是否足以证明不带采集开销的真实服务 TTFT／TPOT 得到改善？你会补哪种最小对照，并保留哪些逐请求原始数据，来复核 TTFT 和 TPOT？

只说明验证方法，不用计算提升比例，也不需要现在执行实验。

参考要点

这组数字混合了改动和 profiler 采集状态两项差异，不能把下降归给改动，也不能断言全部由 profiler 造成。应取得改动前后都关闭 profiler 的同条件 benchmark；若已有改动后数据的方法、原始记录和条件完整匹配，可复用并补齐缺少的基线，否则完成一组匹配对照。保持原定预热、重复及运行顺序，报告绝对值与跨轮波动。

按请求 ID 保存客户端发送计时起点 s、首个被接受输出时刻 u₁、最后输出时刻 uⱼ、实际输出 token 数 L 及长度来源，并记录成功／失败。TTFT=u₁−s；本课 E2EL=uⱼ−s；L>1 时 TPOT=(E2EL−TTFT)/(L−1)。如果直接保存的是已计算的 TTFT 和 E2EL，也要保留清楚的计时边界；不能把未说明起点的绝对到达时间当作 TTFT。分析输出节奏时另外保留完整 raw ITL 列表。

符号与名词

s、uⱼ、J、L
s 为客户端请求函数的发送起点；uⱼ 为第 j 个被接受的输出消息的处理时刻；J 为输出消息数，L 为实际生成 token 数。时间使用同一客户端单调时钟，J 不一定等于 L。
TTFT、E2EL、TPOT、raw ITL
首个输出事件等待、到最后输出事件的请求时间、首输出之后按 token 数摊销的平均时间、相邻输出消息间隔列表；具体边界依赖所选工具与端点。
D、S、goodput、SLO
D 为完整正式测试窗口（秒），S 为成功请求集合；SLO 是明确的服务目标，goodput 为成功且同时满足所选目标的请求数除以 D，单位 req/s。
trace 与 benchmark packet
trace 是带时间关系的执行事件记录；benchmark packet 是使测量可回看、可复核的一组配置、命令、正确性与原始结果材料，不等同一张汇总表。
Host 范围、stream、correlation
Host 范围记录 CPU 代码或调用的经过时间；stream 表示设备工作的一条提交／执行序列；correlation 将相关的 Host 提交与设备活动联系起来，不自动提供全部数据依赖。
关键路径、total、self
关键路径是在给定依赖与持续时间下决定目标最早完成的约束链；total 包含某范围的经过时间，self 扣除记录到的子调用。跨层或重叠范围不能直接相加为端到端时间。
