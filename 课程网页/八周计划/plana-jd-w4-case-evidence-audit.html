2Conv3D 的显存到底涨在哪一步？

沿用上一单元的 patch 输入，读这次项目自己的 F2–F6。项目侧记录为 vLLM 0.9.3，内部提交号和原始快照仍待核实。

最先出问题的是 Qwen2.5-VL-32B 的视频请求。它在产生首个 token 之前耗尽了显存，调用栈停在 Conv3D。调用栈给了你排查入口。要判断是哪次分配变大，还得把算子里的动作拆开看。

你提取了一个视频形状的单例。输入原本是二维矩阵，每行放一个视觉块。设备上的 view 让算子把同一块存储读成通道、时间、高、宽几个轴。再往下，算子实际生成了一份通道在最内层的新存储。RGB 只有三个通道，每个时间和空间位置上的小段都要单独补齐，临时缓冲就变大了。

根据你的项目口述，为了定位这部分增量，你把重排从算子内部移到调用前，再按阶段看显存快照。显存跃升跟到了重排之后。这次对照把一部分膨胀定位到了重排与补齐。若要进一步给出它占整次峰值的精确字节数，还需要看到当时同时存活的其他分配，包括输出缓冲和工作区。项目卡 F2–F3

定位实验之后才是正式修改。你负责复现和布局分析，在模型侧保留二维输入，并在初始化时按相同顺序整理权重。算子同事修改内部读取和计算，让专用 Conv3D 直接接收这种布局。根因分析和方案设计由双方共同完成。这样说，听者能分清为了定位而移动重排的那个单例，以及上线方案里实际消除的那份通道末置临时存储。

参考要点

这个差值衡量的是假设对照中，在同一个兼容算子版本、同一组 32B 图片和同一计时口径下，切换输入与权重布局对平均 TTFT 的影响。原项目里，我负责 OOM 定位、模型侧调用重构和初始化时的权重预排布，算子同事同时修改了专用算子的实现。原项目前后的服务计时反映两项改动共同落地后的效果，另一个算子版本上的差值只能按那次测试的条件报告。

3ECG 从 30–40 秒降到 20 秒以内，这段时间量的是什么？

沿 ECG 卡 F2 和 F6 核对数字，再用 F3–F5 接上原因、改动和验证。ECG 核心案例 · 2026-11-16 的根因补充

上一张卡的秒表在客户端收到第一个 token 时停下。ECG 项目里，用户发来一张心电图和一句文本指令，还要等模型把整段分析生成完。项目采用客户基于 Transformers 编写的自定义模型。按你确认的测量口径，秒表从请求发出走到完整输出结束，图像预处理也算在里面。输出上限是 1024 个 token，各次生成的平均长度约为 700–800 个。

低批量的热点，为什么会追到权重布局？

第一轮优化后的 Profile 仍把热点指向 decode 阶段的小批量 MatMul。一次读入静态权重，能一起用这份权重做乘法的 token 较少。按已有的 Roofline 方法估算，权重搬运值得优先检查。再往下追，硬件同事确认了更具体的原因。按你在 2026-11-16 补充的项目记录，从 HBM 向片上内存搬权重时，原布局下同一次跨行读取的多个块会争用同一 bank 通道。

看一个缩小的地址例子。为演示只用四个通道 A 到 D，物理块号每前进一格就换到下一个通道。权重有四行，每行四个等长布局块。算子现在要读每行的第一个块。按行存时，相邻行的目标隔了四个块，刚好又回到同一通道。改为块内保持行优先、块之间按列排列后，这四个目标在存储中紧挨着。

布局块规定权重在存储里怎么放，计算块规定 MatMul 的一步要取多少元素。消费权重的算子必须按新映射找到同一个逻辑元素。通道分布可以由给定的地址规则复算，实际带宽和服务耗时还取决于运行时有没有充分利用这些通道。项目里已确认 bank 冲突的根因，实际带宽数值仍待测量记录支持。

自己做了什么，正确性又和谁比？

你负责端到端 Profile、热点形状分析，在 PyTorch 框架侧定义 Tensor 扩展，并在模型加载权重后完成预排布和模型回归。团队共同选定这个方向，算子与硬件同事处理底层访存实现并确认硬件访问模式。转换完成后只保留新布局的权重，带静态参数的线性层在 prefill 和 decode 都可复用。像 QK 的点积这样的动态矩阵乘，两端的数据要等请求到来才产生。

在项目已经跑过的用例里，普通布局和预排布都在同一自研芯片上运行。相同输入和参数下，MatMul 输出逐元素数值相等。再运行完整模型，新旧布局得到的 logits 也逐元素数值相等，生成的 token 一致。CPU 对照另用容差判据。要回答新设备或新模型也能否保持这些结果，还得核对它自己的实现与回归覆盖。项目卡 F4–F5

面试怎么讲约 45–60 秒

我负责的是客户 Transformers 模型的端到端适配。我们从发请求量到生成结束，包含图片预处理，单请求前后各测十次取平均。初始版本约三十到四十秒，先改 Host 准备、小形状计算和融合路径，已经降到约二十秒。继续看 decode 的热点时，我和算子同事把方向收窄到静态权重的跨行读取，硬件同事确认有 bank 通道争用。我在框架侧接入新的张量布局，加载时一次排好权重，和底层读取实现配合后，完整请求降到了二十秒以内。我还核对了同芯片上的 MatMul 输出、模型 logits 和生成 token。

本节归纳 三个阶段的完整请求时间说明服务改善了多少。硬件团队的定位说明为什么改布局有用，同芯片的新旧路径对照说明已经验证了哪些数值结果。回答追问时，每份材料都对应一个具体问题。

检查 2移植后的新记录能支持哪个时延结论？

权重预排布后来也移植到了 vLLM。假设在 vLLM 上用同一芯片、相同输入和服务配置，对照了普通布局与预排布。两条路径的 MatMul 输出逐元素相等，预排布的平均 TTFT 更短。客户端计时到收到首个 token 就结束。

面试时可以据此说“vLLM 上的 ECG 完整请求从 30–40 秒降到了 20 秒以内”吗？请用两三句话讲清这批新记录支持什么，以及要报告 vLLM 完整请求的前后时延，还缺什么对照。

参考要点

在假设的 vLLM 对照中，可以报告所测 MatMul 的输出逐元素相等，以及预排布后该组请求的平均 TTFT 更短。客户端收到首个 token 就停表，后续生成这段耗时还没有量到。原来的 30–40 秒和 20 秒以内属于客户 Transformers 栈的完整请求。

要报告 vLLM 的完整请求时延，需要在该栈自己的普通布局和预排布两条路径上，固定输入、并发、生成条件和计时范围，都从客户端发出请求计到完整输出结束，再按一致的重复次数和统计方法比较。

4异步 H2D 改成阻塞后恢复正常，这条观察支持什么？

读 Qwen3-32B／vLLM V1 项目卡 F2–F5，再对照奕行智能二面的 Host Padding 片段。前者记项目最终怎么修，后者核对面试当天实际说了什么。项目卡 · 回听位置

按你后来确认的项目记录，客户在自研后端开启高等级异步拷贝后，偶尔看到乱码、空回复或重复输出。现场同事收集了曾出错的请求，你用这些输入做离线重放。生成出的第一个不同 token 会进入后续生成，所以排查时，你先找最早的分叉，再比较那一步的 logits 和候选 token。

这个案例里，观察手段本身会改动时序。加上较多 Tensor Dump 后，原异常消失。单独把从主机到设备的异步拷贝（H2D）切到阻塞路径，当时的重放也恢复正常。这给了团队一个临时规避办法，并把排查范围缩小到异步准备与拷贝的衔接处。要说明究竟漏等了什么，还得沿一次数据消费追到生产端。

消费者等的是哪份数据，哪一步把它准备好？

从消费者往前看，它要读的是设备上写完的张量。设备拷贝要先收到提交的任务，而后台线程要先在 CPU 上把输入补齐到暂存张量，再提交这次 H2D。在旧路径里，等待设备流只覆盖已经提交的工作。如果后台还在准备输入，消费者对设备流的等待可能先返回，此时后台还未提交这次拷贝。项目卡 F3–F4

最终修复落在你负责的框架／后端层。你把补齐后的张量纳入异步任务的标记与等待，使下游能等到本次 CPU 准备、提交和设备拷贝全部完成。项目沿用了现有 Runtime 能力。验证时恢复原有异步配置，撤掉临时阻塞和额外诊断等待，然后把现场收集的 168 条请求连续重放 5 轮。840 次执行中未再观察到原异常。这个结果能回答“恢复异步后，这批输入怎么样”，要计算故障率下降幅度，还需要修复前同条件的统计。项目卡 F4–F5

检查 432B 视频的第一个分叉

假设固定 32B 模型的权重、视频抽帧和提示词，各条路径都用贪心解码。自研芯片的专用 Conv3D 路径和整模 CUDA 路径在同一段视频上，从第 8 个生成 token 开始不同。你会加哪条参照路径？如果它和专用路径生成的全部 token 都相同，这次对照能说明什么，哪件事还没查清？

参考要点

加一条参照路径，把同一段视频交给同一个 32B 模型，只把视觉入口的专用 Conv3D 换成 CPU Conv3D。其余模型仍在自研芯片上运行，权重、抽帧、提示词和解码设置也都保持一致。如果两次生成的 token 逐个相同，就能说对这条请求，换用专用 Conv3D 后，生成的序列保持了一致。

这时，两条路径与整模 CUDA 的输出都在第 8 个 token 处分叉，跨平台差异来自哪一步仍待定位。贪心解码每一步只选得分最高的 token，即使两组 logits 有细小差别，选中的 token 也可能相同。要检验这一次 Conv3D 本身的数值误差，可以取这段视频实际送入该层的同一份输入和权重，按相同位置和输出通道对齐两边的结果，再按约定容差比较。

如果让你写白板，你在初始化和 forward 里分别改了什么？画出输入、权重和输出各一行是什么，再补上算子还需要的四个维度。

输入的每一行是一个 patch，权重的每一行是一个输出通道的卷积核。我在初始化时把每个核按“通道、时间、高、宽”的顺序展平并保存。到了 forward，输入已经按相同顺序排好了，我沿用二维传输，把输入、二维权重和原来的四个维度一起交给专用算子。它返回的每一行就是这个 patch 的输出特征。模型调用和权重处理是我改的，算子内部怎样在片上排数据和计算由算子同事负责。

白板上可以这样写。N 是本次的 patch 数，O 是输出通道数。下面用 patch_conv 代称我们约定的算子接口。

O, C, T, H, W = weight.shape
weight_2d = weight.reshape(O, C * T * H * W)

# forward：设备上的 patches 已是 [N, C*T*H*W]

既然都展平了，直接换成矩阵乘会更快吗？先解释“一块对应一次投影”，再讲目标设备实际要搬哪些数据。

这版模型里，卷积核和步长都是 2×14×14，每次正好覆盖一块。把一个 patch 和一个核按相同顺序展开，对应元素乘起来再求和，就得到那个输出通道的值。所以数学上可以写成输入矩阵乘以展平权重的转置。我们实际接的是支持这个布局的专用 Conv3D。要选通用 MatMul，我会在同一设备、同一批形状上把额外的布局转换、搬运和计算一起计时，再比较结果。

改了元素顺序怎么验对？视频也比过整模型的输出吗？先说单算子的数值参考，再说图片的生成结果，最后交代视频还缺哪一项。

算子层我用同一份 BF16 输入和权重跑 CPU Conv3D。视频形状的单例里，CPU 输出末尾有三个长度为 1 的维度，我只去掉这三个维度，让 patch 和输出通道一一对应，再按相对容差 0.1、绝对容差 0.05 比较。新旧设备实现分别用 CPU 结果作参考。

模型层当时验的是 32B 的 10 个图片用例。温度设为 0、种子设为 1234，只切换专用 Conv3D 和 CPU Conv3D，生成的 token 序列逐例一致。视频当时做到算子层，32B 视频的模型级回归还可以补。我的做法是固定视频帧、提示词、权重和解码设置，只换这一层再比生成序列。这样发现差异时，才好继续追到这次改动。

首轮完整口述 约 60–90 秒

先降到约 20 秒的那轮，能举一个你真的改过的表达式吗？用 RoPE 准备系数时的外积举例，再解释为什么保留相同的数学结果。

比如准备 RoPE 系数时，每个位置都要跟每个频率相乘。原来用很小的批量矩阵乘做这个外积，在我们的低批量场景下，调度这次计算本身就有开销。拿一个样本来说，把位置编号排成一列、频率排成一行，做广播乘法，输出里第 i 行第 j 列仍然是位置 i 的值乘以频率 j 的值。同一轮我还把不依赖视觉编码结果的元数据提前准备，并复用了已有的融合算子。我们量到的是这几项一起改完后的请求时间。

矩阵乘很慢，怎么进一步判断要改权重的读取顺序？区分 Profile 找到的热点、Roofline 给出的方向和硬件同事确认的根因。

第二轮 Profile 里，decode 时的小批量矩阵乘占了很多时间。单请求生成一个新 token 也要用一整份线性层权重。我按实际形状估了乘加次数和至少要搬的字节数，发现同一份权重只被少数输入行复用，所以优先查供数。随后硬件同事确认，DMA 从 HBM 搬数据到片上时，同一块列、不同权重行的读取会挤到同一 bank 通道。把这些行用到的布局块挨着放，就能把这批读取分到不同通道。实际快多少还得回到算子和服务上量。

“加载时排好”在代码里是什么样？逻辑上把权重转置了吗？指给对方看一个权重元素搬去了哪里，以及谁按这个新位置把它读回来。

我在 PyTorch 侧定义了相应的 Tensor 扩展，在 Transformers 加载权重后处理一次。先把每个逻辑行切成等长的布局块，块内保留原来的元素顺序，把各行的第一块放在一起，接着放各行的第二块。比如原来逻辑第 r 行第 c 列的那个数，在新存储里仍然代表同一个权重。做矩阵乘时，底层算子按约定的新地址取它。加载结束后只保留预排布的权重，后面的 prefill 和 decode 都直接复用。框架侧的表示和加载逻辑由我负责，底层读取由算子、硬件同事配合实现。

白板上先取每行恰好能整分的例子。block_elems 表示一个布局块装下的元素数。下面三行演示加载时的物理重排，项目里由 Tensor 扩展把这种表示传给算子。

blocks = weight.reshape(rows, cols // block_elems, block_elems)
packed = blocks.permute(1, 0, 2).contiguous()
# packed[j, r, e] 保存 weight[r, j * block_elems + e]

为什么只排权重？重排之后怎么证明模型还能对齐？先说哪些数据能在加载时准备好，再分别讲算子和模型比了什么。

线性层的权重在加载时就知道，换一次布局可以被很多次推理复用。激活要等请求进来才产生，连它一起改就要协调前后算子的接口。像注意力里 Q 和 K 的乘法，两边都是运行时产生的张量，也用不上这份预排权重。我先给同一颗芯片上的普通布局 MatMul 和预排布 MatMul 喂相同输入、相同参数，所测输出逐元素相等。再比修改前后的整个模型，logits 也逐元素相等，生成的 token 一致。

20 秒是首 token 还是整段生成？这个数字能报到 vLLM 上吗？把秒表的起点、终点和运行栈交代清楚。

这组数来自客户的 Transformers 服务，从客户端发请求计到完整输出结束，包含图像预处理。输入是一张约 800×500 像素的心电图和一句指令，输出上限是 1024 个 token，平均生成约 700–800 个。单请求，优化前后各跑 10 次取平均，都包括第一次请求。发请求时模型已经初始化好了。预排布技术后来移植到了 vLLM。要给出那边的秒数，我会在 vLLM 上按同样的输入、并发和生成条件，重新计普通布局和预排布两条路径的完整请求。

vLLM V1 异步 H2D｜模型偶尔给出异常回答，你是怎么查的？

回答脉络 从客户能看到的异常讲起。先说哪一次对照缩小了范围，再解释设备流为什么会“等了个空”，最后用恢复异步后的重放结果收尾。

首轮完整口述 约 60–90 秒

Qwen3-32B 在自研芯片上跑 vLLM V1 时，客户启用较高等级的异步拷贝后，偶尔遇到空回复或文本重复。现场同事收集了出过问题的请求。我负责重放和定位，发现单独把主机到设备的拷贝，也就是 H2D，切成阻塞后，这批请求的异常就消失了。这先给了客户一个规避办法，也让我把精力集中到数据什么时候才准备好。

后台要先在 CPU 上把输入补齐，再向设备流提交拷贝。下游原来只等设备流里已经提交的工作，它来得早时，CPU 还在补数据，设备流里根本没有这笔拷贝可以等。我在框架和后端的衔接处把补齐后的中间张量也纳入异步跟踪，让下游能等到这笔拷贝真正完成。修好后我恢复了原来的异步配置，撤掉临时阻塞和额外的诊断等待，把 168 条现场请求连续重放 5 轮。840 次执行里都没再观察到原来的异常。

看见乱码，为什么会去查拷贝？加了 dump 反倒正常，又能说明什么？从第一个分叉的 token 讲起，再讲哪一步让调查转向了时序。

我先固定采样条件，重放相同的请求，找到第一次生成不同 token 的位置，再比那一步的 logits 和靠前的候选词。一旦选出了不同的 token，下一步读到的上下文也跟着变了。排查中我发现，多加几处张量 dump 后，异常反而不见了。这个现象提醒我，观察本身可能改变了时序。随后我保留同一批输入，只把异步 H2D 换成阻塞，异常也随之消失。这个对照把范围缩到了 H2D。究竟漏等哪一步，还得去看主机准备、拷贝提交和下游读取的先后关系。

设备流明明同步过了，为什么下游还能读早？把设备能看见拷贝的时刻，和下游开始等待的时刻放到一条时间线上。

关键是等的时候，设备流里有没有这笔任务。原始张量先在 CPU 上补齐，补好才会提交 H2D。如果下游在 CPU 还没准备完时就去等设备流，流里先前的工作都可能已经结束，那次等待就返回了。随后后台才提交这笔拷贝。下游需要的其实是“这次输入已经传好”，所以得让它从主机准备阶段就能看见这个尚未完成的依赖。

你的修复在代码的哪一层？什么时候登记，什么时候才能标记完成？说出生产方登记的对象、任务完成的条件，以及消费 kernel 放行的条件。

我改的是框架侧对异步任务的跟踪，复用了已有的 Runtime 能力。我记得是在 CPU 开始做 padding 前，就把源张量、补齐用的中间张量和设备目标张量关联到这笔未完成的任务。这样，即使拷贝还没进入设备流，下游也知道这份数据还在准备。等 CPU 补齐、H2D 已提交并且设备把数据拷完，这次任务才能标记完成。使用目标张量的 kernel 要等到这个条件满足才能开始读。

白板上画两边就够了。下游可能很早就到达等待点，消费开始的条件是两边约定的同一个“完成”。

框架登记   源张量、中间张量、目标张量关联本次未完成任务
后台准备   CPU 将源数据补齐到中间张量，再提交 H2D
设备完成   中间张量的数据拷贝到目标张量完毕，才能标记完成
下游消费   等本次任务完成，才允许消费 kernel 读取目标张量

一直用阻塞拷贝也能规避，为什么还要改跟踪？这是 Runtime 的修复吗？分别说明临时止住异常和最终恢复异步，各需要哪项改动。

阻塞路径给了客户一个先把服务跑稳的办法，但调用方要等拷贝完成才能继续。异步原本允许其他互不依赖的工作往前走，真正需要等的是马上要读这份数据的消费者。我负责把这条依赖补回框架和后端的张量跟踪，沿用设备已有的拷贝和同步能力。这样可以恢复原来的异步配置。项目里我能给出的是正确性回归结果，修复对吞吐的具体影响还需要同负载的性能对照。

840 次是 840 条不同请求吗？怎么判断回归的确覆盖了原问题？先数请求，再数轮次，把运行条件和仍缺的对照说完整。

现场同事收集的是 168 条请求，我把同一批请求重放了 5 轮，所以是 840 次执行。回归时把原先启用的异步配置恢复了，也撤掉了临时阻塞和额外诊断等待，这样才是在原问题关心的条件下看结果。我能报告的是这批执行里没有再观察到原异常。要量化故障率下降了多少，还需要修复前同条件下的执行次数和异常次数。
