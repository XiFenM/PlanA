GLM 简历上的 120 秒量了什么？

B 版简历写到，调整 GLM-5.3-Flash 的状态布局后，decode 单步的 Host 耗时从约 120 秒降到 2.6 秒。自我介绍里有一句“处理非连续状态访问带来的 Host 开销”。把两份材料和项目表对起来，这里的 Host 指主机侧，计时范围是模型生成过程中的一个 decode 步。B 版简历 · 对应自我介绍

项目记录保留了同一短提示词下、在模型里插桩得到的两行数。“计时单位”说清一行是按步还是按次调用计时。“每步调用数”用来把一次调用的耗时换算成每步的合计。

第一行换成秒是 119.962 和 2.579，简历上的约数能对上。在这条短提示词上，拆池前测得的 decode 单步 Host 耗时约为拆池后的 46.5 倍。要算客户端等完整回答的时间缩短了多少，得另拿同一负载的端到端计时作对照。GLM 项目记录 · 状态拆池与分阶段计时

为什么值得改布局？原来每个 block 里先存卷积状态，再存递推状态，读取相邻两个 block 的卷积状态时，中间隔着一整份递推状态。项目记录显示，这种不连续的访问在目标后端走了很慢的主机搬运路径。拆池后，同一种状态跨 block 连续存放。每个 block 里的数据合计仍是 542,720 字节，改变的是取这些数据要走的路径。

怎样用这一列？ 在同一条 Host 线程上，假设一个 decode 步依次执行 N 次 conv update，以拆池后的 0.19 毫秒估算每次调用耗时，这部分合计约为 0.19 × N 毫秒／步。计数时只取这个步、这条线程上的 conv update。如果 trace 还记下了每次调用的实际耗时，把它们相加就得到这一步内 conv update 的累计耗时。

用 AMD 单卡的六轮记录复算输出吞吐

这次换一把秒表，量整批请求完成得有多快。W4 单元二用一张 AMD gfx1100 卡跑 Qwen2.5-1.5B-Instruct，精度为 BF16。每轮使用同一批 48 条请求，长短提示词各占一半，最多 8 条同时在途。每条请求都生成 128 个 token，所以每轮的有效输出是 6,144 个 token。实验负载与计时方法

预算是一步最多可以调度的 token 数。单独采集的 2,048 档四请求短 trace 里，有一步调度了 2,047 个 prefill token 和 1 个 decode token，也有一步只调度了 4 个 decode token。长提示词在较大的预算下有机会分成更少的 prefill 块。要判断整轮是否真的少跑了几步、GPU 是否被用得更充分，需要对照两档同负载的实际步数、各步的 token 构成和 GPU 活动记录。单独采集的调度批记录

如果客户端等了很久才收到同一条请求的下一个 token，可能是相关执行步变长，也可能是请求等待下一次执行或输出送达花了更久。要分清原因，可以把长间隔对应的请求和调度、设备执行、客户端收包这几处时间点对齐。

书面小变式。 假设现在只剩 8 条请求一起解码，每步每条生成 1 个 token，期间没有新请求或抢占。把预算从 512 提到 2,048，会减少每条请求再生成 32 个 token 所需的调度步数吗？写一句理由就行。

两档预算都要 32 步。 8 条请求可以一起算，每步每条各生成 1 个 token，一共只用掉 8 个 token 的预算。对同一条请求，下一个 token 依赖刚生成的那个，所以这 32 个 token 要逐步生成。512 和 2,048 两个上限都够用，调高上限不会让这一批请求在同一步多生成一个 token。

本组接口与调度顺序采用 W1 的 vLLM v0.26.0 单卡 V1 路径。请求执行与输出契约

单卡 vLLM V1 服务怎样返回第一个生成 token？

回答要点 固定服务和计时口径。沿前端、调度器、执行端和前端返回这四处交接，讲清每一处传的是什么。

参考口述

我以一台已经加载好模型的单卡服务为例。用户发来纯文本聊天请求，要求流式输出。这次启用分块 prefill，关闭投机解码，提示词也没有命中前缀缓存。我在客户端从发出请求开始计时。

API Server 先用聊天模板整理消息，再分词得到提示词的 token ID。温度等采样设置会单独整理。前端把请求标识、token ID 和采样参数发给 EngineCore。调度器根据这一步的 token 预算和可用 KV 块，决定让哪些请求各推进多少个 token。执行端据此组批，ModelRunner 准备输入、位置和注意力所需的元数据，再调用模型。

长提示词可以分几步做 prefill。算到最后一个输入位置时，输出层把该位置的隐藏向量变成词表分数，采样器选出第一个生成 token。引擎把 token ID 和请求标识送回前端，前端解码并发出文本增量。客户端收到第一段带生成内容的消息时停表，这就是我用毫秒报告的首 token 延迟，也就是 TTFT。

改成非流式返回，客户端还能直接量到 TTFT 吗？

回答要点 先确定停表事件。流式看首次生成内容，非流式看完整响应。要观察引擎的中间结果，另用服务端同一只钟。

参考口述

流式请求会陆续收到消息，我在第一段生成内容到达时停表，只有角色标记或空内容的消息会跳过。非流式请求等整段回答准备好才交给客户端，所以同一只秒表量到的是端到端请求时延。只有请求发出和完整响应收到这两个时间点，无法从中还原首 token 出现的时刻。

如果可以在服务端打点，我会在同一前端进程打两次时间戳，一次在收到请求时，一次在收到引擎送来的首个生成 token 时。两者之差回答的是服务端前端等了多久。客户端实际看到文字，还要经过后续的解码、发送和传输。

最后一个位置的隐藏向量，怎样变成第一个 token？

回答要点 输出线性层得到词表分数 logits。贪心取最高分，top-k 随机采样在保留的候选中按概率选。

参考口述

我取最后一个输入位置的隐藏向量，把它送进模型的输出线性层，也叫 LM head。输出权重的每一行对应词表里的一个 token。用这一行和隐藏向量做点积，就得到这个 token 的分数。把所有行一起算，就是一次矩阵乘法。带偏置的输出层还会加上偏置。得到的这排原始分数叫 logits。贪心解码直接选最高分的 ID。如果用 top-k 随机采样，就保留分数最高的 k 个候选，用 softmax 得到它们的概率，再抽一个 ID。

首个 token 已经选出来，下一步怎样生成第二个？

回答要点 第一个生成 token 是下一步的输入。历史 K、V 从缓存读取，当前位置的 Q、K、V 新算，新的 K、V 写入缓存。

参考口述

prefill 结束后，提示词在各层的 K 和 V 已经存好了。我把刚选出的第一个 token 作为下一步模型输入。在每一层，当前位置会算出自己的 Q、K 和 V。Q 用来和可见位置的 K 算注意力权重，包括历史位置和自己，再用这些权重对相应的 V 加权。历史 K、V 可以直接读缓存，当前位置的新 K、V 则写回去供后续步使用。经过剩下的网络层、输出投影和采样，就得到第二个 token。

已有请求正在 decode，又来了一个长提示词，这一步怎么排？

回答要点 看 RUNNING 和 WAITING 两类请求，先安排运行中的工作，再看剩余 token 预算和可用 KV 块。运行中的请求也可能还在做 prefill。

参考口述

在这个配置下，调度器先看已经运行的请求。token 预算和 KV 块都够时，本步排进去的普通 decode 请求各推进一个 token。优先让这些请求继续出词，有助于缩短用户等下一次输出的时间。如果本步还有 token 预算，也能给新请求分配 KV 块，就可以把新提示词的一部分放进同一批做 prefill，剩下的留到后面的步。这里优先考虑的是请求的运行状态。一个上一步只处理了部分提示词的请求，也可能已经在 RUNNING 队列里。

同一批有多条请求，注意力怎样找到其中一条的历史 KV？

回答要点 先按请求选块表，再用逻辑块号查物理块号。序列长度限定有效上下文。

参考口述

调度侧给请求分配 KV 块，执行端根据调度结果维护每条请求的块表。注意力要读某条请求的历史时，先选这条请求在当前批次对应的那一行。行里按逻辑块的先后顺序存着物理块号。即使这些块在显存里不连续，内核也能沿块表找到它们，再结合序列长度读出这条请求的有效 KV。

历史 KV 用块表读，当前 token 的新 K、V 写到哪里？

回答要点 在单卡、等长块的例子里，用 token 的序列位置求逻辑块号和块内偏移，从请求的块表查出物理块号，得到写入槽位。

参考口述

ModelRunner 会为本步每个输入 token 准备 slot_mapping。拿单卡的等长块来说，位置从零开始，位置除以每块的 token 数，商是逻辑块号，余数是块内偏移。用逻辑块号查这条请求的块表得到物理块号。物理块号乘块大小，再加块内偏移，就是这个 token 的槽位。执行端按这个槽位写入当前层新算的 K 和 V。批次顺序变化时，token 和它的槽位也得一一对上。

本组的模型、修改分工与验证范围依据项目记录。Conv3D 项目卡 F1–F6

请讲一次你亲自定位的多模态推理显存问题。

回答要点 从 32B 的一条视频请求讲起。用快照说明哪一步分配了新存储，讲清模型侧和算子侧分工，最后用可运行性与精度对照收尾。

参考口述

我在自研芯片上用 vLLM 0.9.3 适配 Qwen2.5-VL。32B 模型处理一条视频请求时耗尽了显存，Python 调用栈指向视觉编码器入口的 Conv3D。我提取那次调用的形状做了单例，沿后端实现找到一次通道末置的重排。把重排移到算子调用前再看显存快照，显存占用就在它后面明显上升。原因是每个时空位置的三个颜色分量放在一起只占很短一段，每段都要按设备要求补齐。

我和算子同事一起改了接口。我在模型侧保留已有的二维 patch 输入，在初始化时把卷积核按相同顺序展平。专用算子由同事实现，按我们约定的布局和原始维度读取数据。改完后，原视频请求能够跑完。我先用 CPU 参考验证单算子，结果在设定的容差内。再用 32B 模型跑图片，只切换视觉入口的 Conv3D，两条路径生成的 token 逐例一致。

调用栈指向 Conv3D，怎样把显存上涨定位到重排这一步？

回答要点 五维 view 共用原存储，生成通道末置的连续布局时申请新存储。把重排单独拿出来看快照。

参考口述

最初一行就存着一个完整 patch。设备上的 view 只是把同一份存储解释成五维。后端接下来把通道移到末尾，实际写出一份连续的新存储，这时才要重新分配。原来只在每行 patch 的末尾补齐一次，新布局在每个时空位置都留下一个只有三个数的通道段，每段都要补齐。我的依据是把重排单独移出来后，显存跃升也跟着它走。要确定最终是哪次分配失败、当时申请了多少字节，还得查原始分配记录。

你在初始化和 forward 里具体改了什么？

回答要点 每行输入是一个 patch，每行权重是一个输出通道的卷积核。两边的元素顺序相同，算子接口另收原始维度。

参考口述

输入在主机侧已经按 patch 展平了。我在 forward 沿用这份二维输入和原有的二维传输路径。权重只在模型初始化时整理一次，把每个输出通道的卷积核按通道、时间、高和宽的顺序展成一行。调用专用算子时，我同时传入原来的四个维度，算子就能把每个输入元素和对应权重配起来，输出每个 patch 的特征。这样省去了通道末置时那份反复补齐的临时存储。二维行末本身仍按硬件要求对齐。我的改动在模型调用和权重初始化，算子内部的读取与计算由算子同事负责。

单算子数值怎样对齐？两种输出形状不同，按什么判据通过？

回答要点 同一份 BF16 输入与权重，对照 CPU Conv3D。CPU 输出从 (14040, 1280, 1, 1, 1) 去掉末尾三个单例维，与 (14040, 1280) 对齐。相对容差 rtol=0.1，绝对容差 atol=0.05。

参考口述

我在 CPU 上准备同一份 BF16 输入和权重，用 CPU Conv3D 算参考输出，再用展平后的输入和权重跑芯片上的专用算子。拿视频形状的那个单例来说，CPU 输出的前两维已经对应 patch 和输出通道，末尾还带着三个长度为一的维度。我只去掉这三个维度，再把同一个 patch、同一个输出通道的数逐项比较。测试套件设的相对容差是 0.1，绝对容差是 0.05，这个用例在这组容差内通过。实测最大误差要看当时的误差记录。

视频重新跑通后，模型生成结果的正确性验证到了哪里？

回答要点 原视频复跑验证显存问题。模型精度用 32B 的 10 个图片用例验证，只替换 Conv3D，逐例比生成的 token 序列。

参考口述

怎样报告优化前后的平均首 token 延迟？

回答要点 32B 图片组，单并发，10 个用例每例前后各一次。客户端计时，分别取算术平均。

参考口述

我们用 Qwen2.5-VL-32B，在相同服务配置下比较优化前后的 Conv3D 路径。服务就绪后，测试并发固定为 1。同一组十个图片用例，每个用例在两条路径上各发一次流式请求。从客户端发出请求开始计时，到收到第一个生成 token 时停表。优化前和优化后各有十个 TTFT，分别取算术平均。按这个口径，平均 TTFT 从分钟级降到了五秒以内。

这组首 token 计时能拆出模型侧改动单独省下的时间吗？

参考口述

我在 Qwen2.5-VL-32B 上用同一组十个图片用例，一次只发一个请求。优化前后每例各测一次，客户端的计时起止点相同。我负责保留二维输入、重构模型调用和调整初始化时的权重布局，算子同事同时改了专用 Conv3D 的实现。这组请求的平均首 token 延迟从分钟级降到五秒以内，是双方改动一起落地后的结果。

如果要单独估算布局改动省了多少时间，我会选一版能同时处理新旧布局的算子，固定输入、并发和计时口径，只切换布局再测。得到的差值只能按那次对照的算子版本和负载报告。

保持模型调用和布局不变，只换兼容的算子实现，这次差值能归给谁？

回答要点 看两条路径究竟改了哪个变量，再说明测量的是算子耗时还是服务指标。结果只按当次负载和版本报告。

两台机器分别做 prefill 和 decode，一条请求怎样交接过去？

回答要点 先定模型、两端并行配置和 KV 布局。decode 端预留目标块，prefill 端推送有效 KV，decode 端确认本地可读再继续生成。

参考口述

我先选一个简单配置。两台机器各用一张卡，模型、KV 精度、块大小和布局一致。我选 prefill 端主动推送，decode 端用主机内存中转。decode 端先给这条请求留好接收缓冲区和目标显存块，双方对齐请求身份、要传哪些逻辑块以及它们在目标端的位置。

prefill 端算完提示词，各层 KV 就绪后，把有效数据传到对端的接收缓冲区。我让 prefill 端同时负责选出第一个生成 token，把它和继续生成所需的请求状态一起交接。decode 端确认数据收齐后，按自己的块表把 KV 拷进显存。等计算流可以读取这些块，就用刚交接的 token 做下一步 decode。这样两端可以分别调度计算，代价是目标端要预留缓存，交接也要花时间。

收到“发送完成”的通知，attention 在什么条件下可以读 KV？

回答要点 先定义通知能证明哪一步。主机收齐、设备拷贝提交、目标显存可读是三个时刻。

参考口述

我会把请求和预期传输的块对应起来，看通知具体保证了什么。在主机中转的方案里，确认整份数据抵达 decode 端的主机内存之后，还有一次主机到显存的拷贝。如果拷贝和 attention 在不同的流上，我会让计算流等待这次拷贝的完成事件。这样 attention 读到的才是这条请求已经写好的 KV。换成设备直传，也要核实传输后端如何保证目标侧可见，并和计算流建立依赖。

每层 GQA 配置相同，一条请求要传多少有效 KV？

回答要点 单卡、全注意力、只传有效提示词位置。把提示词 token 数、层数、KV 头数、每头维度、K/V 两份和每元素字节数相乘。

参考口述

我先算一个 token 在一层的数据。它的 K 有“KV 头数乘每头维度”个元素，V 在这个配置下同样大，所以乘二。如果 KV 用 BF16，每个元素又占两个字节。最后乘层数，再乘要交接的有效提示词 token 数，就得到整条请求的有效 KV 字节数。GQA 里多个查询头共享 KV 头，所以这里用的是 KV 头数。按整块传输产生的尾部补齐和协议开销需要另外计。

有效 KV 字节数 = 有效 token 数 × 层数 × KV 头数 × 每头维度 × 2 × 每元素字节数

怎样估传输时间？主机中转时还要算哪一段？

回答要点 用有效载荷除以同单位的有效带宽。256 MiB ÷ 25 GiB/s = 10 ms，这里只估网络段。

参考口述

我先统一单位。256 MiB 是 0.25 GiB，按每秒 25 GiB 的有效带宽来算，网络搬运这份数据需要 0.01 秒，也就是 10 毫秒。这是给定带宽、忽略额外开销时的网络时间。按我们选的整份收齐再拷入显存的方案，decode 端还要等本地拷贝完成。要解释端到端的交接时延，我会沿实际时间线再看排队、通知和两端搬运，确认哪些阶段串行、哪些发生了重叠。

等 KV 超时了，预留的显存块什么时候能安全复用？

回答要点 业务可以先判失败。保留目标块及旧任务的关联，等所有相关访问结束，再交还内存池。

参考口述

超时意味着这条请求已经等得太久。这个方案里我会先让请求失败，把目标块放进待回收状态。若后端支持取消，我还要弄清它返回的是“收到取消请求”，还是“所有已提交的访问都已经结束”。

主机中转时要分别照看两段。接收缓冲区要等旧网络传输停止访问，而且本地拷贝也读完了才能复用。目标显存要等本地拷贝完成，或确认取消后它不会再写。已经提交的 attention 等任务也要结束对这些块的访问，相关引用都释放后，块才能归还。拿不到这些保证，就让相关缓冲区继续隔离，按后端的恢复流程处理。关掉网络通道以后，已经提交到本地设备的工作仍需单独确认。

复习要点 把请求、缓冲区和最后一次访问它的任务对应起来。网络传输、显存可读和块可回收，各有自己的完成条件。

回答到一半偶尔会卡一下。把 prefill 和 decode 拆开会有帮助吗？

回答要点 用客户端相邻输出 token 的时间间隔（ITL）衡量卡顿，比较两组的 ITL P99，单位是毫秒。同时看首 token 延迟（TTFT）和整套服务的输出吞吐（token/s）。

参考口述

我先假设模型单卡就能放下，两台机器各有一张同型号的卡。一组每台都跑完整实例，各自做 prefill 和 decode。另一组一台做 prefill，另一台做 decode，两端通过网络交接 KV。两组用相同的生成设置，把同一批请求按原来的到达间隔重放一遍。

我怀疑长提示词在做 prefill 时，让正在出词的请求多等了一会儿。两组都逐 token 流式返回。我会在客户端记录每条请求相邻两个 token 隔了多少毫秒，把这些间隔放在一起取 P99。只有拆开后长停顿明显缩短，用户等首字的时间和服务每秒输出的 token 数也都达标，我才会选拆分。

如果是等很久才看到第一个字，之后出字很顺，又怎么判断？

回答要点 主指标换成客户端 TTFT（毫秒）。服务端分别量请求等调度的时间和实际执行 prefill 的时间。拆分后还要看首 token 之后平均每个输出 token 的用时（TPOT）和相邻 token 的间隔（ITL）。

参考口述

我还是用两台各一张卡的机器，比较两个完整实例和一台 prefill 配一台 decode，按相同的到达时间回放同一批请求。这次我关心用户等首字等了多久，就从客户端发出请求计到收到第一个生成 token，用毫秒比较两组的 TTFT。

首字慢可能是请求在排队，也可能是提示词本身算得久。我会在服务端把这两段分开计时。如果原先是在等 decode 让出算力，拆开就有机会缩短排队。

我还会看首 token 什么时候返回。如果发给客户端之前要等 KV 交接，这段等待就计入 TTFT。如果 prefill 端先返回首 token，我会看第二个 token 有没有因为等 KV 而晚到。只有 TTFT 明显缩短，后面的 TPOT 和 ITL 也满足服务要求，我才会在这批请求上选拆分。
