1先把性能数字归到一个明确的任务

对应学习计划节点 1；承接 W2 的 MatMul 语义，重点看本节的工作量与计时边界。

设一次调用处理 128 行隐藏向量，每行 5120 个特征，投影后得到 25600 个特征。令 M=128、K=5120、N=25600：M 是本次调用实际处理的总行数，不直接等于请求数；K、N 取自 Qwen3-32B 的公开配置。本例只取一个扩展投影的数学形状，实际框架可能融合 gate／up 等操作，不能把这一次乘法当成整个 MLP。

A、B、C 都已分配在同一设备上，使用 BF16 存储；累加按 FP32 建模，结果再写成 BF16。我们分析密集乘法，直接写新 C，不读取旧 C，也不包含 bias、激活、残差或通信。这样的限定让两份实现先对齐“要交付什么结果”，之后才有可能比较代价；具体运行时仍需核对精度配置，不能把这些建模条件当作框架默认保证。

沿用一个 FMA 计两次浮点运算的口径，本次有效工作量为 Ftask=2MNK=33,554,432,000 FLOPF_{\mathrm{task}}=2MNK=33{,}554{,}432{,}000\ \mathrm{FLOP}Ftask​=2MNK=33,554,432,000 FLOP。这是按数学任务计算的工作量。若实现因 tile 补齐或额外归约执行了更多操作，硬件实际执行量 Fexec 可以不同；增加无效工作不会让用户的数学任务变大。后面用 Ftask／时间比较的是有效工作速度，不能直接把这个比率叫作执行单元忙碌百分比。

接着确定分母。下面是接口伪代码，只表达异步关系：

# A、B、C 已在设备上；输入依赖已满足
enqueue_gemm(A, B, C)   # 返回表示提交，不等于设备计算完成
wait_until_C_ready()    # 等到本次结果满足读取条件

CPU 从进入调用到返回的时间，可能只覆盖请求提交。要讨论设备执行，必须使用能覆盖相应设备工作的计时方式；具体测量协议在单元二展开。即使都测到了真实设备时间，也还要分清下面三种范围。

尺寸依据为固定 Qwen3-32B config；GEMM/FMA 口径见 NVIDIA 指南 §1–2。异步关系见 PyTorch 2.9 文档。本段数字是模型计算，不是本机 benchmark。

结论先对齐数学任务、精度和完成边界，再命名性能比率；同一个 FLOPs 分子配不同时间，会回答不同层次的问题。

这还不是显存分配器的全部占用，更不是一次调用真实经过 HBM 的流量。为了在运行前作估算，我们另建一个理想预算 Q0：A、B 需要从 HBM 读入，各元素只跨该边界一次；C 最终向 HBM 写出一次；不读旧 C，也没有外部中间结果。只有在这些假设下，Q0 才与上面的 Stensor 数值相等；“数据有多大”和“经过边界多少次”仍是两件事。

第三本账是 QHBM：按照明确的工具配置、计数定义和观测范围，得到实际 HBM 读写字节。缓存承接可以减少外部读取，重复读取、暂存结果和访问粒度可以增加流量；输出何时写回 HBM，也影响一个观察窗口内的计数。因此 Q0 是带前提的预算，不是任何一次 kernel 都必须达到的通用下界。权重 B 有 250 MiB，“执行过预热”本身不能证明它已经完整驻留某一级缓存。

参考要点

两者交付同一个正确的密集 GEMM，按相同口径计算的有效数学工作量都是 F_task=2MNK；GEMM 本体时间相同，因此有效数学吞吐 F_task/t_GEMM 相同。乙的实际 HBM 字节更多，说明本段平均搬运速率更高，同时实际计算强度 F_task/Q_HBM 更低；这些事实不能证明完成相同任务的速度提高，也不能仅据此认定增加流量的具体原因。

完整投影的比较必须包含每次调用所必需的阶段。题设中甲只需 GEMM，乙还需不可跨调用复用、与 GEMM 串行的 GPU 重排；只比较所述设备阶段时，乙增加了额外时间。至少需要补齐乙的重排耗时、完整操作从约定输入具备到结果满足读取条件的耗时，并分别保留对应范围的流量；不能把 GEMM 的局部流量配上整个方案时间后，仍称为 GEMM 本体带宽。

计时终点应是所需结果已就绪，而不是异步 API 提交返回。如果要比较整条请求，还需按两者一致的边界纳入其余必需阶段，并检查是否有重叠或其他不同开销；题设并未提供这类更广范围的运行证据。

3资源上界与微基准参考线，分别能说明什么

对应学习计划节点 3，承接 Roofline 技术报告 §3、附录 A.1。下面沿用同一个 MatMul，新增的是资源参数的含义与可比较条件。

主例的数学任务与流量口径已经明确，但还没有取得实际测试设备的信息。先定义同一种密集计算模式下的算力上界 Pcap，单位 FLOP/s；再定义所讨论 HBM 边界的带宽上界 βcap，单位 B/s。这里的上界都带着设备、频率、资源分区和精度条件。BF16 输入、FP32 累加如果走矩阵计算路径，应匹配这一路径的密集峰值，不能仅因累加是 FP32 就套普通 FP32 通路，也不能把稀疏峰值用于密集任务。

在本课常规密集乘加计算的口径下，令 F 表示有效数学工作，Q 表示与它对应的 HBM 流量。完成同一任务至少要满足计算和搬运两项约束，因此沿用你已推导过的关系：

tGEMM≥F/Pcap,tGEMM≥Q/βcap,tlower=max⁡(F/Pcap,Q/βcap).\begin{aligned}t_{\mathrm{GEMM}}&\ge F/P_{\mathrm{cap}},\\t_{\mathrm{GEMM}}&\ge Q/\beta_{\mathrm{cap}},\\t_{\mathrm{lower}}&=\max(F/P_{\mathrm{cap}},Q/\beta_{\mathrm{cap}}).\end{aligned}tGEMM​tGEMM​tlower​​≥F/Pcap​,≥Q/βcap​,=max(F/Pcap​,Q/βcap​).​

取 max 是为了得到两项都必须满足的乐观下界；它不承诺实际执行已把计算与搬运完美重叠。令 I=F/Q，就得到同一模型的有效吞吐上界：

Rcap(I)=min⁡(Pcap,βcapI)R_{\mathrm{cap}}(I)=\min(P_{\mathrm{cap}},\beta_{\mathrm{cap}}I)Rcap​(I)=min(Pcap​,βcap​I)

两条分支相交于 I∗=Pcap/βcapI_*=P_{\mathrm{cap}}/\beta_{\mathrm{cap}}I∗​=Pcap​/βcap​。位于斜线段，只表示这个两资源模型中的 HBM 约束更紧；实际运行仍可能受并行度、依赖、启动和片上层级限制，不能仅凭横轴位置宣布 HBM 已经饱和。

现在给模型代入一组明确的假设参数：Pcap=300 TFLOP/s，βcap=1 TB/s，TF 与 TB 均用十进制前缀。它们不对应某个已确认的 GPU，也不是测量结果；后续由你的环境采集和测量替换。保持前面的 Q0=270,008,320 B，本例的计算项约 0.1118 ms，搬运项约 0.2700 ms，因此模型下界约 0.2700 ms，对应上界约 124.27 TFLOP/s。

另一种常见画法使用独立微基准的结果。例如，一段专门的矩阵计算或访存程序提供 Pref、βref。它们受输入 shape、读写比例、访问模式和运行条件影响；用它们画出的线是经验参考。测得过的某个速率，不会仅因被放进 min 公式，就成为其他程序绝对无法超过的物理上界。即便两项各自都测得可信，也不保证某个 GEMM 能同时达到两项。

Roofline 技术报告允许用规格或微基准建立资源模型，§3、附录 A.1 说明流量与标定范围。本节区分“已观测参考值”与“有适用条件的上界”，是对证据来源的判读；GEMM 的密集精度与执行粒度边界同时参照 NVIDIA 矩阵乘指南。

结论同一个公式可以接入不同来源的参数；结论的强度取决于参数是否匹配，以及它是资源上界还是一次可比的经验参考。

这个等式说明：在这些前提下，相对当前位置 Roofline 较高，可以反映总线搬运速率接近所选上界，却不能说明搬运量已经接近最低需要。若实现有冗余读取，Q 会增加、I 会降低，当前位置的斜线高度也会下降；相对这条较低的线得到较高比率，也不意味着更快完成任务。比较实现优劣时，仍要回到同一个正确任务的绝对耗时、实际流量和完整工作范围。

反过来，离曲线较远也不能唯一定位原因。先核对 F、Q、计时范围、精度与峰值是否匹配；再把“重复搬运”“等待或并行度不足”“参考环境不匹配”等作为候选，寻找能够区分它们的观测与对照。只有曲线距离，没有 trace、计数口径和受控比较时，不能跳到某个 kernel 机制或具体优化结论。

沿同一个投影看全程：128 行隐藏向量从 5120 维映射到 25600 维。先明确它只是一项密集 GEMM，输入输出的 BF16 存储和 FP32 累加是已声明的分析条件。由此得到约 33.55 GFLOP 的有效工作；再给 A、B、C 的一次 HBM 读写建立约 257.5 MiB 的预算。后一个数字同时带着冷数据、复用和写回范围的假设，不能只因 shape 没变就当成实际流量。

接着选择与实际设备、计算模式和存储边界匹配的资源参数，把计算项与搬运项放进同一上下界模型。规格参数和独立微基准具有不同的证据来源；某个微基准得到的速率可以帮助比较，但不是目标程序无法超过的普遍上限。CPU 异步调用返回、GEMM 本体结束和完整投影结果就绪，也对应不同时间，分子与分母必须指向同一范围。

拿到运行结果以后，先看正确性与绝对时间，再解释相对比率。实际流量更多，可以把点在同一 Roofline 上的参考位置压低；接近这个较低位置不说明实现最好。共同的 Q0 则提供同一预算基准，使相同比较条件下的比率排序与耗时排序一致，但仍不能冒充硬件观测。只有时间而没有实际流量时，仍能报告有效吞吐和模型对照，流量与瓶颈机制则保持证据边界。

这条链最终服务于一个工程判断：在明确的工作负载与环境下，哪种实现更值得采用，为什么这样判断，还有哪些原因没有排除。真实模型的单次投影已经涉及数百 MiB 权重与数十 GFLOP 工作；把数学、数据路径和测量范围接好，比单独追求一个更高的百分比更有用。

符号与名词

M、K、N
M 是本次送入投影的输入行数，K 是每行输入特征数，N 是输出特征数；A[M,K]、B[K,N]、C[M,N]。
F_task 与 F_exec
F_task 是按约定计数的有效数学浮点工作量；F_exec 是实现实际执行的相应浮点工作，可能因执行粒度等原因不同。一个 FMA 按 2 FLOP 统计。
S_tensor、Q_0、Q_HBM
分别表示张量有效元素的总字节数、给定冷数据与复用前提的 HBM 流量预算、指定范围实际观测的 HBM 读写流量；字节单位均为 B。
t_GEMM、t_op、t_request
分别对应 GEMM 本体、约定的完整操作、完整请求的时间；使用吞吐或带宽比率时要写明分母覆盖的工作。
存储精度与累加精度
本例 A/B/C 按 BF16 存储，每元素 2 B；乘积累加按 FP32 建模。内部 FP32 累加不自动意味着存在一份写到 HBM 的 FP32 中间矩阵。
P_cap、β_cap、R_cap(I)
所选计算模式与 HBM 边界的资源能力上界，以及在给定计算强度 I 下两者较紧的有效吞吐上界。使用时必须核对型号、精度、频率与资源范围。
P_ref、β_ref
来自独立微基准的经验参考速率；适用性受工作负载和运行条件限制，不因代入 Roofline 公式就成为所有程序的物理上限。
η_peak 与 η_roof
有效数学吞吐分别除以计算通路上界、当前位置的资源 Roofline；两种分母回答不同问题，都不直接等同硬件忙碌百分比。
