A 在等下一个字，B 在等第一个字

在上一单元里，我们的“复习助手”已经通过 RadixCache 认出了两条请求共享同一份讲义。现在把镜头拉进线上推理最常遇到的真实冲突：老用户 A 正在流式看模型吐字（问的是“吞吐是什么？”），就在此时，新用户 B 带着同一份 2,048 token 的讲义外加一段 768 token 的新日志冲进系统（问“为什么首字慢？”）。虽然 B 能直接复用讲义的 KV 缓存，但剩下 768 个新 token 依然需要 GPU 算一遍。眼下只有一张单卡 GPU，A 想接着吐下一个字，B 想赶紧算出第一个字——下一轮前向计算，调度器到底把卡给谁？

LLM 推理调度器（Continuous Batching 的核心引擎）的本质，就是每一轮前向（iteration）重新做一次发牌决定。每轮开头，调度器先清点刚进门的新请求和上一轮没答完的老请求，再核对 请求名额、KV 显存和单步算力预算，决定本轮拼出怎样的批次送进 GPU。模型跑完后，结果处理器负责“按人头分账”：提示词还没读完的请求，先把刚算好的 KV 存起来，留到下一轮继续；只有真正读到提示词末尾的请求，才会弹出它的第一个回答 token，并在后续轮次加入大家一起做 Decode。

同一轮前向对两位用户的体感截然不同：B 盯着屏幕等第一个字蹦出来，这段耗时叫 TTFT；A 已经看到了一半回答，正在等下一个字紧跟着出来，相邻两字之间的停顿叫 ITL。直达直球概念题（拒绝背书） · 直达场景追问 · 直达预算对比模拟器

1这一轮模型到底拿到哪个批次？

从 Scheduler.event_loop_normal 调用 run_batch 处向上回溯。

先把实验环境控制干净，剥离干扰项：单卡、普通自回归文本生成、走同步主循环（关闭调度与执行重叠、抢占和推测解码）。同时开启 Chunked Prefill，但暂时关闭混合组批（不把 Prefill 和 Decode 混进同一批）。此时老请求 A 还没答完，新请求 B 是唯一刚到的请求，且系统还有空余 请求名额 和充足的 KV 显存。

一轮开始时，新到的 B 先落在 waiting_queue（候车室），正在吐字的 A 留在 running_batch（在跑名单）。选批结束后，调度器会产出两个非常容易混淆的字段：plan.running_batch 和 plan.batch_to_run。把鼠标移到下面代码旁的编号注释上，一眼看清它们的分工：

plan = self.get_next_batch_to_run()
if plan is not None:
    self.running_batch = plan.running_batch
    batch = plan.batch_to_run
    result = self.run_batch(batch)

scheduler.py · 真正传给 run_batch 的是 batch（即 plan.batch_to_run）

  1. 每轮开头重新做一次选批决策，决定是先算新来的 Prefill 还是老请求 Decode。
  2. 保存“记在账上还没答完的活跃请求”（A 仍稳稳留在这里，名额未释放）。
  3. 真正推上 GPU 前向计算的是 batch_to_run——本轮只装着 B 的 EXTEND 批次。

在关闭混合组批的路径里，我们常听到的 “Prefill 优先” 指的就是选批顺序：调度器会先去候车室捞新请求，只要能凑出一个合法的 Prefill 批次，本轮 GPU 就先算 Prefill；只有当候车室里捞不出任何可运行的 Prefill 批次时（比如没新请求，或者名额/显存满了），才会退一步让 running_batch 里的老请求做 Decode。而 FCFS 管的则是候车室内部的排队顺序，两者各司其职。

既然“Prefill 优先”，A 占着的名额会被 B 挤掉吗？

这是新手最容易误解的一点。把时间停在 B 刚入队、正准备选批的瞬间：A 虽然刚算完上一轮，但它的话还没说完，它的 KV 索引还挂在请求映射表（req_to_token_pool）里。只要 A 没结束且没开启抢占，它的请求名额就会跨轮一直攥在手里，哪怕它这一轮轮空没上 GPU。

把这两层彻底分清就不会再绕晕了：队列策略（FCFS / LPM）管的是“等待者内部谁先接受体检”；“Prefill 优先”管的是“体检通过组出新批后，本轮 GPU 先跑新批还是跑老批”。等获准的 B 读完最后一段提示词、且还要继续回答时，调度器才会把它并入 running_batch，和 A 一起进入 Decode 队列。本轮选批分支 · Prefill 完成后并入运行批次。

2B 已经进批算了一轮，为什么用户还没看到第一个字？

在 PrefillAdder.add_one_req 里追踪本轮输入区间，再到结果处理器看输出门控。

现在给 B 套上一组真实具体的数字，方便我们像查账一样逐个 token 核对：B 套完对话模板后总长 2,816 个 token，其中前 2,048 个（公共讲义）已经命中显存里的 KV 缓存，真正需要新算的是后面 768 个（新性能日志 + 提问）。设 KV 每页 16 个 token，单轮分块上限 chunked_prefill_size = 512，且本轮这 512 的额度全部留给 B，其余资源均充足。

试试直接拖动或点按句子里的数字：当 B 在 2,048 个命中前缀之后还有 768 个新 token，且每轮分块上限为 512 时（关闭混合组批），第一轮模型会实际计算 512 个新位置，还剩 256 个留在 chunked_req 里——因此 B 一共需要 2 轮才能读完提示词并吐出首字（第一轮交付输出：0 个）。

读准入代码时，把三道门槛拆开看最清楚：① 请求名额决定“能同时服务几个人”；② KV 空间确保显存装得下新增位置，并给后续生成留出安全余量；③ 分块额度则给单次前向的计算量封顶，防止一条超长输入把 GPU 霸占太久。因为前 2,048 位已有现成 KV，B 本轮直接从第 2,049 位起算，但受限于 512 的分块上限，这一轮最多只能推进到第 2,560 位。

源码用左闭右开区间来定位本轮切片，B 的 extend_range 记为 [2048, 2560)。把 B 的 2,816 个 token ID 排成一排看就非常直观：get_fill_ids() 先在右端截到第 2,560 位，组批代码再把左边已经命中缓存的 prefix_indices 切掉，精准留下中间那 512 个新 token 送进模型：

# 跳过已命中缓存的前缀，仅把本轮新增的分块 token 送进前向
input_ids = [r.get_fill_ids()[len(r.prefix_indices) :] for r in reqs]
extend_lens = [len(ids) for ids in input_ids]

模型算完这 512 个位置后，为什么用户屏幕上还是空白？因为模型必须读完提示词的最后一个位置（第 2,816 位），才能据此预测第一个回答 token。当前只读到第 2,560 位，结果处理器一眼认出这是个中间分块，直接跳过流式输出；而老请求 A 这一轮又没上卡。于是就出现了线上排查时最耐人寻味的一幕：GPU 满载跑了一整轮，但 A 和 B 两位用户在这段时间里都收到 0 个 新字。

随堂自检 1判断输出属于谁

把时间定格在 B 刚入队、本轮选批之前：老请求 A 还在 running_batch 里，并且占着系统唯一的请求名额，准备继续 Decode。新请求 B 排在 waiting_queue 里。

B 的讲义（2,048 位）全部命中缓存，后面只剩短短 16 个新 token，KV 空间和 token 预算也都绰绰有余。此刻没有未完成的分块，抢占和混合组批都关闭。结果这一轮 GPU 生成了 1 个 token——能算作 B 的首 token 吗？本轮真正上卡的是谁，B 又留在哪里？

展开参考要点

不能，这个 token 是 A 的下一个输出。 因为并发名额已经被 A 占满，且抢占关闭，B 哪怕只剩 16 个 token 也过不了准入这一关，只能老老实实留在 waiting_queue。调度器凑不出新的 Prefill 批次，于是把 A 的一步 Decode 送进了 GPU。

系统共有 2 个请求名额，原先被 A 和 C 占满，B 在候车室排队。上一轮 A 和 C 的模型前向都已经算完，A 还要继续生成。抢占和混合组批依然关闭，B 的其他条件都满足。下一轮选批前，你必须核对 C 的哪一项状态，才能判断 B 能不能进批？

展开参考要点

必须核对 C 是否已经彻底结束并释放了请求名额。 “前向算完”只代表 C 刚走完一步 Decode，不代表它答完了。只有当 C 触发了停止条件（如生成 EOS 或达到最大长度）、退出 running_batch 并归还名额后，B 才能获准进入本轮的 Prefill 批次。如果 C 还要继续生成，A 和 C 依然占满 2 个名额，B 只能继续等。

3等待队列已经空了，B 的最后 256 个位置从哪里接上？

沿着 chunked_req 追踪中间分块的轮间接力。

回到节点 2 结束时的现场：A 和 B 都有名额，混合组批仍关闭。B 已经借着讲义命中了前 2,048 位，第一轮又新算了 512 位，还差最后 256 位就能读到问题末尾。此时没有新请求进来，waiting_queue 已经空空如也——那调度器下一轮怎么记得去接着算 B，而不是直接跳过它去算 A？

秘密就在 chunked_req 这个专属指针上。第一轮把 B 截断时，调度器不仅把 B 放进了执行批次，还顺手把它的句柄挂在了 self.chunked_req 上。等第一轮前向跑完、进入下一轮选批前，系统会做两件关键的衔接工作：第一，把刚算出的 512 个位置的 KV 槽号登记回缓存，让 B 手里持有的前缀长度从 2,048 推进到 2,560；第二，在把上一轮完成的请求并入 running_batch 时，特意把还在读提示词的 B 过滤掉，不让它提前混进 Decode 队伍。

if self.chunked_req is not None:
    self.chunked_req.init_next_round_input()
    self.chunked_req = adder.add_chunked_req(self.chunked_req)

先接上正在分块的请求 · 为它设置区间并判断是否还要续算。

  1. 选批最先检查 chunked_req，优先级高于 waiting_queue。
  2. 刷新 B 的最新 prefix_indices（此时已推进到 2,560）。
  3. 把最后 256 个位置装进本轮批次；因已到末尾，返回值变为 None，解除续算挂起。

追分块续算必须双线核对： chunked_req 负责把没读完的请求“留在场上”，已有 KV 槽号负责把下一段的起点接严实。即便等待队列已经清空，这条续算链路依然能无缝推进。

4B 分块读提示词时，A 怎样在同一次前向里继续出词？

沿用相同的请求与缓存，从 PrefillAdder 预留额度一路追到 mix_with_running。

刚才关闭混合组批时，B 连占两轮 GPU，老用户 A 硬生生干等了两轮都没吐字——这就是线上常见的“长请求一来，老用户回答卡顿”。现在把时钟拨回 B 刚到达的那一轮，所有条件纹丝不动（每页 16 token、B 命中 2,048 剩 768、分块额度 512、普通 token 输入且不返回 logprobs），唯一的变化是打开开关：enable_mixed_chunk = True。

开启混合组批后，调度器允许 A 的一步 Decode “搭便车”拼进 B 的 Prefill 批次。具体怎么分额度？A 做一步 Decode 需要把上轮刚生成的 1 个 token 喂回模型，所以调度器先从 512 的总预算里扣掉 1 个给 A，留给 B 的可用额度变成 511。接下来是一个非常关键的源码细节：因为 B 是本轮首次获准且需要截断的长请求，SGLang 会把可用额度向下对齐到整页（16 的倍数）——511 除以 16 最多装下 31 个整页，即 496 个 token（余下 15 个零头本轮不用）。于是同一轮 GPU 前向里，模型同时吃进 B 的 496 个位置和 A 的 1 个位置，各自查各自的 KV，互不干扰！

在源码里追踪 A 的去向也很有意思：调度器为 A 做好 Decode 准备后，通过 mix_with_running 把它并进本轮的 MIXED 批次，并记入 decoding_reqs。第一轮批内请求顺序是 [B, A]，对应的输入长度数组 extend_lens = [496, 1]。紧接着，调度器会把原本独立的 running_batch 置空——注意别被“置空”吓到，A 并没有丢，它只是从单独的运行批次“坐进了”本轮发往 GPU 的混合大巴里，名额和 KV 都在。

混合组批的核心价值，是让老请求 A 在 B 做 Prefill 期间也能不断流地吐字。 不过请注意：每一轮混合前向本身可能比纯 Decode 慢，所以实际毫秒级延迟到底省了多少，必须同负载实测 B 的 TTFT 和 A 的 ITL 分布说了算。

展开参考要点

不能断定。 A 做一步普通 Decode 占了 1 个输出，剩下 1 个输出有两种可能：① 如果本轮 decoding_reqs 里同时包含 A 和 D，那 A、D 各吐 1 个字就凑齐了 2 个，B 只是在算中间分块，输出仍为 0；② 如果 D 在上一轮刚好结束了，本轮只有 A 在 Decode，那多出来的 1 个就一定是 B 读完提示词末尾后吐出的首 token。

换一轮来看：decoding_reqs 里明确有 A 和 D，两者都正常走完一步普通 Decode。B 的提示词总长 800 个位置，本轮从第 641 位一口气算到第 800 位（开始前输出为 0）。三条请求都正常写回，可日志却写着“全批共追加了 2 个回答 token”。这笔账对得上吗？

5同一条长提示词到了 vLLM，这一轮能算到哪里？

沿着 vLLM V1 v0.26.0 的 Scheduler.schedule()，看统一 token 预算如何切分。

把刚才完全相同的 A 和 B（B 总长 2,816、命中 2,048、剩 768 要算；KV 块大小 16；单卡全注意力文本模型）搬到 vLLM V1 v0.26.0 里跑一遍。为了公平对比，把 vLLM 的单步总预算 max_num_scheduled_tokens 同样设为 512，长提示词单独截断阈值设为 0。两边纸面上都是“512”，但底层扣账逻辑大不一样。

第一步：先照顾已经在跑的 self.running。 vLLM V1 并不区分“Prefill 批”和“Decode 批”，它直接拿出一张 512 的总预算支票，先遍历 self.running。正在 Decode 的 A 需要把上一步采出的 1 个 token 喂回模型，于是直接划走 1 个预算，账上还剩 511：

# 为每个 running 请求记账并从统一总预算池中扣减
num_scheduled_tokens[request_id] = num_new_tokens
token_budget -= num_new_tokens

遍历运行中的请求，计算本步所需位置 · 记录分配并扣减预算

  1. 直接按 request_id 登记本轮给它算几个 token（A 记为 1，随后 B 记为 511）。
  2. 统一从 token_budget 扣减，不分 Prefill 批还是 Decode 批，余量全部留给等待队列。

第二步：拿剩下的预算接纳等待中的 B。 调度器确认还有并发名额、且 B 可复用 2,048 个前缀后，直接取“待算长度 768”与“剩余预算 511”的较小值——第一轮干脆利落地分出 {A: 1, B: 511}！注意这里和 SGLang 的细微差别：在全注意力路径下，vLLM 按需向上分配整块物理 KV 显存，但本轮实际送进模型计算的 token 可以直接停在物理块中间（B 算到第 2,559 位，最后一块写到第 15 槽就停，不需要向下对齐到 496）。

第一轮结束时，B 已经被放进 self.running（哪怕它还没读完提示词、输出序列仍为空）。因此到了第二轮，“先调度 RUNNING 请求”会同时给 A 划 1 个、给 B 划走剩下的 257 个，B 算完第 2,816 位后产出首 token。新请求入运行列表 · 推进计算进度 · 判断未读完的请求

SGLang 新请求的整页额度检查与截断 · vLLM 给等待请求分配剩余 token 预算 · 按需向上取整分配物理块。

两套框架都能让 A、B 同轮并进，但出发点不同： SGLang 是“先组 Prefill 批，开混合后把 Decode 并进来”；vLLM V1 是“统一池子先分给 RUNNING，剩下余量再接纳 WAITING”。看清每条请求实际分到的 token 数，才能解释边界场景下首字为什么会差出一整轮。

导师串讲 · 一条线串起 A 的下一个字与 B 的第一个字

如果线上突然告警，有人抱怨“首字太慢”或“吐字一卡一卡”，按这条四步排查链路走一遍，所有现象都能对上号：先锁人——记下 A 和 B 的请求 ID，确认 B 到底有没有过准入关，以及前缀缓存把它的计算起点推到了哪里；再看车——检查真正送进 GPU 的批次，在 SGLang 里看 A 是留在 running_batch 轮空，还是坐上了 MIXED 拼车，在 vLLM 里直接查 num_scheduled_tokens 字典。

最后对账——前向返回后，再次核对两个 ID 的输出序列长度。A 每跑一步普通 Decode 就稳稳多 1 个字；B 只要还在中间分块，就只是在默默推进 KV，直到读完提示词最后一个 token 的那一轮才会弹出首字。批次级吞吐只能告诉你“卡没闲着”，只有把逐轮输入切片、逐请求输出变化、客户端时间戳三张表对齐，你才能真正向业务方解释清每一位用户的等待。

Part A · 面试官直球问概念，怎样回答才不像背书？

反背书核心心法：别一上来就念维基百科定义。用 4 步工程叙事——① 先说不用它之前线上有多痛 → ② 一句话讲清核心直觉 → ③ 落到单轮调度/硬件机制 → ④ 顺手带出它没解决的边界问题，面试官立刻就能听出你是真做过工程的人。

直球概念题 1 · 必考基石

“你先直接跟我讲讲，什么是 Continuous Batching（连续批处理）？”

面试官在考什么看你能不能从“静态组批的 GPU 空转痛点”讲起，说清调度粒度从 Request 级细化到 Iteration 级，并自然衔接到后续的显存与混批挑战。
像背书的踩坑答法“Continuous Batching 也叫 iteration-level scheduling，是 Orca 论文提出的，可以动态插入和移除请求，提升吞吐量。”——太干，没画面感，面试官会觉得你只背了概念。
① 痛点切入静态组批有木桶效应：短请求答完了还得陪长请求空转。
② 一句话直觉把“一锅炖完再开下一锅”改成“每算完一个字就检查空位、随时加菜”。
③ 落到机制每轮 iteration 重新选批：谁吐出 EOS 立刻退批释名额，候车室新请求立刻补位。
④ 引出延伸单靠它还会遇到 Prefill/Decode 抢卡和 KV 碎片，顺手引出 Chunked Prefill。
展开反背书高分口述（约 45 秒）

我一般从它解决的“木桶效应”来理解。早期的静态组批（Static Batching）就像凑满一桌人再开席：假设 4 条请求打包上卡，其中一条 10 个字就答完了，另一条要写 1,000 字，那答完的槽位就只能一直陪着空转，外面排队的请求也进不来，GPU 气泡特别严重。

Continuous Batching 干的事其实很直白：把调度粒度从“整批请求”切细到“每一轮模型前向（iteration）”。每算完一个 token，调度器就重新盘一次账——谁吐出结束符立刻退出批次、释放名额和 KV，外面候车室的新请求下一轮就能立刻顶上来。像 SGLang 里 event_loop_normal 每轮重新调 get_next_batch_to_run，本质上就是在跑这个循环。不过一旦允许新旧请求随时插进来，就会马上遇到新问题：新来的长 Prefill 和正在跑的 Decode 怎么共处？这就自然引出了后面的 Chunked Prefill 和混合组批。

面试官大概率顺着问：“你刚提到 Prefill 和 Decode 共处有冲突，那你顺便说说它俩到底有什么本质区别？”（无缝衔接下一题！）

直球概念题 2 · 硬件直觉

“请讲讲 Prefill 和 Decode 两个阶段有什么本质区别？为什么调度器要费这么大劲处理它俩的冲突？”

面试官在考什么看你能不能把“Compute-bound vs Memory-bound”讲出矩阵形状和显存带宽的物理直觉，并和用户侧的 TTFT / ITL 挂钩。
像背书的踩坑答法只扔一句“Prefill 是计算密集型，Decode 是访存密集型”就结束了，讲不出为什么以及对调度的影响。
① 看输入形状Prefill 一次喂几百上千 token（大矩阵 GEMM）；Decode 每次只喂 1 个 token（近乎 GEMV）。
② 看硬件瓶颈Prefill 算力吃得满（Compute-bound）；Decode 每次搬一遍全部权重和 KV 只算 1 个字，卡在显存带宽（Memory-bound）。
③ 看用户指标Prefill 决定新用户的 TTFT；Decode 决定老用户的 ITL。
④ 看调度冲突单卡混跑时，长 Prefill 会把老用户的 ITL 拉爆；只保 Decode 又会让新用户 TTFT 排队卡死。
展开反背书高分口述

如果从 GPU 干活的方式看，这两个阶段几乎是两种完全不同的负载。Prefill 是把用户整段提示词一次性并行送进模型，输入矩阵很大，算术强度高，能把 TensorCore 算力打满，瓶颈在算力，它直接决定新用户的首字延迟 TTFT。

到了 Decode 阶段，因为自回归生成必须一个字一个字蹦，每条请求每轮只送进去 1 个新 token。哪怕你只算这 1 个 token，GPU 也得把几十 GB 的模型权重和历史 KV Cache 完整从显存搬进片上缓存读一遍，算力根本吃不饱，瓶颈全卡在显存带宽上，它决定老用户的吐字流畅度 ITL。

正因为性格完全相反，把它们塞到同一张卡上就会打架：如果放任一条几千字的长 Prefill 一口气算完，老用户的 Decode 就得干等几百毫秒，体感就是“回答到一半卡住了”；反过来如果只顾着让 Decode 跑，新请求的 TTFT 就会飙升。调度器做分块 Prefill、混合组批，甚至集群层面做 PD 分离，归根结底都是在调和这两者的矛盾。

直球概念题 3 · 拆弹思想

“什么是 Chunked Prefill（分块预填充）？它解决了什么问题，又有什么代价？”

面试官在考什么不仅要懂“把长 Prompt 切块”，更要考你知不知道它和 Mixed Batching 的配合关系，以及“切太小有什么副作用”的工程权衡。
像背书的踩坑答法只说“切块能降低 ITL、让显存更平滑”，忘了提“中间分块不出首字”和“切太碎会降低计算密度、增加 KV 重读开销”。
① 痛点切入一条 8K/32K 长输入一口气算完，单步耗时会直接把同卡 Decode 用户的 ITL 打穿。
② 核心做法给单步前向设 token 预算上限（如 512），把长 Prompt 切成多块分轮算，中间块只写 KV 不吐字。
③ 黄金搭档配合混合组批（Mixed Batching），把老用户的 Decode 拼进每个 Prefill 小块里，借 Prefill 的算力“顺路”带 Decode 走。
④ 工程代价块切太小会损失 GEMM 计算密度，而且后面每一块做注意力时都要反复重读前面已算好的 KV，反而可能拉长 TTFT。
展开反背书高分口述

Chunked Prefill 其实就是给单次前向计算加了一道“熔断上限”。以前来一条几千 token 的长提示词，GPU 必须一口气把它全算完，这几百毫秒里同卡所有正在吐字的老用户全得干等，ITL 瞬间飙高。有了 Chunked Prefill 之后，调度器按固定预算（比如 512 token）把长输入切成几段，一轮只算一块、把这块 KV 存好就先交还控制权，直到最后一块读完才吐首字。

它真正的威力在于和混合组批（Mixed Batching）配合：因为每轮 Prefill 只切了 512，就可以把老用户的 Decode 拼进同一批里一起算——原本 Decode 搬运权重算力闲着也是闲着，顺路把一小块 Prefill 算了，既保住了老用户不断流，又提高了单步算力利用率。

当然它不是免费午餐：如果把分块切得太碎，一方面矩阵太小打不满 TensorCore，另一方面后续每一块算 Attention 时都要把前面已经写好的历史 KV 重复读一遍，访存开销变大，新请求的 TTFT 反而会变慢。所以线上一定要按业务 SLA 压测找平衡点。

直球概念题 4 · SGLang 招牌

“很多人说 SGLang 强在 RadixAttention / Prefix Caching，你能直接讲讲前缀缓存是怎么和调度器打配合的吗？”

面试官在考什么看你能不能把“缓存数据结构（RadixTree）”和“调度器决策（匹配跳过 + LPM 排序 + 驱逐保护）”串成闭环，而不是孤立地背前缀树。
像背书的踩坑答法只讲“用基数树存 KV Cache、LRU 淘汰”，完全没提调度器怎么利用命中结果去切片和排优先级。
① 痛点切入多轮对话、System Prompt、RAG 共享长文档时，每次请求从头重算 Prefill 太浪费算力。
② 数据配合前缀树把历史 KV 按 token 序列组织起来；新请求入队时先查树，直接拿到可复用的 prefix_indices。
③ 调度配合执行时只算未命中的增量部分（EXTEND）；排队时若开 LPM 策略，优先放行命中前缀更长的请求。
④ 边界注意开启 LPM 虽能大幅拉高缓存命中率和吞吐，但高负载下要防短前缀请求饿死；且正在用的节点需加锁防 LRU 误驱逐。
展开反背书高分口述

前缀缓存如果只当成一个被动缓存用，威力只发挥了一半；SGLang 的巧妙之处在于让缓存和调度器深度联动。场景上很好理解：线上很多请求都带着相同的几千字 System Prompt、多轮历史或者公共文档，每次从头算 Prefill 太亏了。SGLang 用 RadixTree 把算过的 KV 组织起来，新请求一来，先在树上匹配最长公共前缀，拿到现成的 KV 槽号（prefix_indices）。

接下来调度器在三个地方和它打配合：第一，组批计算时直接把命中前缀切掉，只把剩下的增量新 token 送进模型做 EXTEND，大幅压缩 TTFT；第二，如果把等待队列策略从默认的 FCFS 切成 LPM（最长前缀匹配），调度器会优先挑“和当前热缓存重合度最高”的请求先上卡，避免热缓存刚被踢掉又来命中它的抖动；第三，对正在跑和正在分块续算的请求锁定缓存引用计数，防止显存紧张时把它们依赖的前缀节点给 LRU 驱逐了。工程上用 LPM 时我也会顺手盯一下短前缀请求的排队尾延迟，防止饥饿。

Part B · 面试官抛具体场景深挖：源码状态机、跨框架对比与线上排障

概念答稳之后，面试官马上会切入具体数字和线上故障场景来验证你的深度。以下 8 题全部沿用本单元的单卡 A/B 场景（SGLang v0.5.17 & vLLM V1 v0.26.0）。

场景题 1 · 一分钟全局开场

“假设现在单卡上老请求 A 正在流式吐字，新请求 B 带着一段很长的提示词刚进来。你能用一分钟跟我讲清楚，SGLang 下一轮到底是怎么拍板决定算谁的吗？”

面试官在考什么看你能不能从“用户体感（TTFT/ITL）”切入，用一条清晰的闭环讲清“入队 → 准入 → 选批 → 执行 → 回写”。
容易踩的坑一上来就背“SGLang 是 Prefill 优先所以先算 B”，忘了提准入检查、混合组批开关以及“中间分块不出首字”。

回答骨架 ① A/B 各自在等什么（ITL vs TTFT）→ ② 队列与三道准入关 → ③ 关混合 / 开混合两条路径 → ④ 结果写回（读完末尾才吐首字）。

展开高分参考口述（约 1 分钟）

这个场景本质上是老用户 A 在等下一个字（ITL），新用户 B 在等第一个字（TTFT），两人抢同一张卡。在 SGLang 里，B 进来先落进 waiting_queue，A 留在 running_batch。每一轮选批，调度器先过三道准入关：并发名额够不够、KV 显存够不够、本轮分块额度能吃多少新 token。如果关闭了混合组批，只要能给 B 凑出合法的 Prefill 批次，本轮 GPU 就优先算 B，A 留守在 running_batch 等下一轮；凑不出才继续跑 A 的 Decode。如果打开了混合组批且满足条件，调度器会把 A 的一步 Decode 拼进 B 的分块批次一起上卡。前向跑完后按请求结算：A 跑完一步就能多吐一个字，而 B 必须等到最后一块提示词读完，才会吐出它的首个回答 token。

场景题 2 · 名额 vs 执行权

“你刚才提到 SGLang 默认是 Prefill 优先——那是不是意味着只要 B 一进队，就能立刻把正在生成的 A 挤下去，抢走 A 的位置？”

面试官在考什么测试你是否把“请求名额（跨轮保留）”和“单轮 GPU 执行权（逐轮分配）”混为一谈，以及是否清楚抢占的边界。
容易踩的坑顺着面试官诱导说“会挤掉 A”，或者含糊地说“A 算完这步就把名额让出来了”。

回答骨架 ① 直接纠偏：不会自动挤掉，名额跨轮保留 → ② 并发上限=1 vs 上限=2 对比 → ③ 点出 running_batch 与 batch_to_run 的区分。

展开高分参考口述

不会自动挤掉，这里要严格区分“请求名额”和“本轮 GPU 执行权”。在关闭抢占和混合组批的前提下，只要 A 还没答完，它的并发名额和 KV 槽位就会跨轮一直占着。如果系统并发上限只有 1，名额已经被 A 占满，哪怕 B 前缀全命中，准入检查也会直接返回空，B 只能继续排队，GPU 还是跑 A。只有当并发上限至少为 2、B 拿到空闲名额并凑出 Prefill 批次时，“Prefill 优先”才会生效——本轮 GPU 先算 B，但 A 依然稳稳占着自己的名额留在 running_batch 里等下一轮。真要为了 B 腾出 A 的名额，必须走专门的抢占路径。排查源码时，我看 running_batch 确认谁还活着，看 batch_to_run 确认本轮到底算了谁。

场景题 3 · 排队公平性 vs 缓存命中

“现在候车室里 B 先到（命中 256 个前缀），C 后到（命中 2,048 个前缀），系统刚好只剩 1 个空名额。SGLang 会先放谁进去？这跟 Prefill 优先是一回事吗？”

面试官在考什么考察你对等待队列排序策略（FCFS / 优先级 / LPM）的掌握，以及能否分清“队列内排序”和“批间优先级”。
容易踩的坑以为 SGLang 有 RadixAttention 就默认按 LPM 排序，忘了这版默认其实是 FCFS。

回答骨架 ① v0.5.17 默认 FCFS 先检 B → ② 补充显式优先级与 LPM 两种分支 → ③ 区分“等待者之间”与“新旧批次之间”。

展开高分参考口述

这取决于等待队列配了什么调度策略，它和“Prefill 优先”管的是两层事。在 SGLang v0.5.17 里，默认策略是 FCFS（先到先服务），所以只要 B 的其他资源条件都满足，就会先放先到的 B 进去。如果打开了显式请求优先级，就先比优先级、同级再按入队时间。而如果切成了 LPM（最长前缀匹配），调度器为了最大化 RadixCache 复用，就会把命中 2,048 位的 C 排到前面先放行。总结来说，FCFS 和 LPM 解决的是“候车室里谁先拿入场券”，而“Prefill 优先”解决的是“拿到入场券之后，本轮 GPU 先算新批还是先算正在 Decode 的老批”。

场景题 4 · 分块续算状态机

“我看日志里 waiting_queue 明明已经空了，B 的长提示词上一轮又只算了一半，那下一轮调度器怎么不会把 B 给忘掉？它又是怎么知道从第几个 token 接着算的？”

面试官在考什么验证你有没有真正看过 Chunked Prefill 的状态流转源码，知不知道中间分块既不在 waiting_queue，也不能提前混进 running_batch。
容易踩的坑随口编造“B 算完一块又重新塞回 waiting_queue”或者“B 已经放进 running_batch 跟着 Decode 一起算了”。

回答骨架 ① 核心指针 self.chunked_req → ② 轮间 KV 槽号登记推进前缀 → ③ 读到末尾前不追加输出、不并入 Decode。

展开高分参考口述

不会忘掉，因为调度器用了一个专门的字段 self.chunked_req 来挂住还没读完提示词的请求。B 第一次获准时确实已经移出等待队列了，如果因为分块额度不够被截断，调度器就会把它记在 chunked_req 里，并且在轮间整理时特意把它过滤掉，不让它提前混进 running_batch 做 Decode。同时，上一轮刚算出来的那段 KV 会被登记到缓存并更新到 B 持有的槽号上——比如总长 2,816、命中 2,048、第一轮算了 512 后，B 的已有前缀就推进到了 2,560。下一轮哪怕等待队列是空的，调度器一上来就会优先检查 chunked_req，直接从第 2,561 位接着切出最后 256 个位置。直到这最后一块算完，结果处理器才会给 B 追加首个回答 token。

场景题 5 · 源码硬核细节

“你看过 SGLang 混合组批的源码对吧？那我考你个细节：每页 16 token、预算 512、A 占了 1 个 Decode，留给 B 的余量明明是 511。为什么 B 第一块只能算 496 个，可如果它特别长，下一轮续算却能算满 511 个？”

面试官在考什么典型的“源码深度鉴别题”，用来区分“读过博客”和“真正跟过 PrefillAdder 分支代码”的候选人。
容易踩的坑笼统回答“SGLang 每轮都强制按 16 页对齐”，忽略了首次准入截断与续算 add_chunked_req 的代码路径差异。

回答骨架 ① 用 1,200 token 的例子带着算 → ② 首次准入（向上整页检查、向下整页截断得 496）→ ③ 续算路径（直接取 min(剩余, 可用额度) 得 511，仅记账扣减按整页算 512）。

展开高分参考口述

这个差别来自“首次准入”和“后续续算”走的是两个不同的代码分支。拿 B 还剩 1,200 个新 token 举例：预算 512 扣掉 A 的 1 个 Decode 后，每轮留给 B 的可用额度都是 511。第一轮是首次准入，源码会先把待算长度按 16 向上取整检查能不能整段装下；发现装不下需要截断时，就把 511 向下对齐到整页，31 页刚好是 496 个，所以第一块算 496。但从第二轮开始，B 已经是 chunked_req 走续算分支了，此时剩余 704 个，add_chunked_req 会直接取剩余长度和可用额度的较小值，把 511 个真实 token 全送进模型，第三轮再算完最后的 193 个。不过在预算记账层面，那 511 个仍会按整页记成扣掉 512。

场景题 6 · 线上排障实战

“假如线上跑着混合组批，一轮 MIXED 前向结束后，你发现只有 A 的回答变长了，B 还是没出字。你怎么快速确认 B 这一轮到底是‘已经算了一块只是没读完’，还是‘压根没排进去’？”

面试官在考什么考察你把源码数据结构转化为可观测排障手段的能力：能不能报出具体要抓哪些字段。
容易踩的坑只盯着 running_batch 或全批新增 token 总数看（混合组批后单独的 running_batch 会被置空，合计数也分不清归属）。

回答骨架 ① 查 batch_to_run 成员和 extend_lens → ② 核对 decoding_reqs → ③ 对照 B 的输入区间右端是否到末尾及 output_ids 长度差。

展开高分参考口述

我不会只看全批输出合计数，也不会被置空的 running_batch 误导，而是直接按请求 ID 查三个地方。第一，查本轮真正送进模型的 batch_to_run 里有没有 B，再看对应的 extend_lens——比如请求顺序是 [B, A] 且 extend_lens = [496, 1]，就能铁证如山地确认 B 确实算了 496 个新位置，同时 A 算了 1 个 Decode。第二，看 decoding_reqs 确认本轮到底有哪些请求在 Decode，排除其他并发请求的干扰。第三，对照 B 本轮的 extend_range 右端有没有触及提示词末尾，以及写回前后 len(B.output_ids) 的差值。只要 B 在批次里且右端还没到末尾，那“没出字”就是正常的中间分块推进。

场景题 7 · 跨框架横向对比

“SGLang 开混合组批和 vLLM V1 开分块 Prefill，看起来都能让 A 和 B 在同一轮里一起往前走。如果让你给团队讲讲它们底层的调度差异，你会怎么讲？”

面试官在考什么看你能不能从“设计哲学差异”落到一个具体的边界反例（500 token 临界点），证明你既懂架构又懂实现细节。
容易踩的坑只停留在“两者都支持 Chunked Prefill，差不多”或者背诵过时的 vLLM V0 架构，拿不出具体差异案例。

回答骨架 ① 架构思路对比（SGLang 拼车合并 vs vLLM V1 统一预算池先 RUNNING 后 WAITING）→ ② 抛 500 token 临界点反例（496 vs 500）→ ③ 客观补充：轮数少不等于实测延迟必然更低。

展开高分参考口述

两者虽然都能同轮推进 A 和 B，但底层调度思路正好相反。SGLang 的主干还是先尝试组 Prefill 批次，开启混合组批后，预留出 Decode 额度再把活跃的 Decode 请求并进来跑一个 MIXED 批。而 vLLM V1 取消了显式的 Prefill/Decode 批次划分，直接维护一个单步总 token 预算池：先遍历 self.running 给所有运行中请求（包括还在分块 Prefill 的请求）划预算，剩下的余量再拿去接纳 waiting 里的请求。

举个最能看出差别的边界例子：单卡全注意力模型，两边预算都设 512、页/块大小 16，A 用 1 个 Decode，刚来的 B 还剩 500 个新 token。SGLang 首次准入按 16 向上取整检查需要 512，超出了 511 的余量，于是向下截断只算 496 个，B 第一轮出不了首字；而 vLLM V1 允许计算停在物理块内部，能直接把 500 个全部吃进 511 的余量里，第一轮就让 B 吐出首字。当然，实际谁的 TTFT 更快还要结合单步执行耗时实测。

场景题 8 · 线上卡顿与压测设计

“线上业务一到高峰期，长提示词请求一多，老用户就投诉‘回答到一半突然卡住好几秒’。有人提议直接把 chunked_prefill_size 调小，你觉得一定管用吗？如果是你，你会怎么排查和验证？”

面试官在考什么考察工程方法论：能不能先定位根因（是没进批还是单步慢），再设计严格的控制变量压测，而不是盲目调参。
容易踩的坑直接拍胸脯说“调小分块肯定有用”，忽略了关闭混合组批时调小分块依然可能连续跑多轮 Prefill，以及分块过小会拖慢 TTFT。

回答骨架 ① 先对齐时间线定因 → ② 点出“关混合时只调小分块不一定救得了 A” → ③ 给单变量对照实验设计（固定负载重放 + 盯 TTFT 与 ITL P99）。

展开高分参考口述

不一定管用，得先对齐时间线搞清卡顿的真正原因：在 A 两次出字的漫长间隔里，到底是 GPU 一直在连轴转算 B 的 Prefill、A 压根没进批？还是 A 已经进了混合批次，但单步前向因为分块太大跑得太慢？如果没开混合组批，单纯把分块调小，调度器依然可能连续几轮把 B 的小分块排在前面，A 还是得干等；而且分块切得太碎，会损失 Prefill 的计算密度，反而拉长新请求的 TTFT。

如果由我来验证，我会做严格的单变量对照：先在同一套服务里固定硬件、模型、采样参数和流式返回方式，用相同到达时间表重放同一批请求（保证 A 从相同解码进度起步、B 命中相同长度的缓存前缀）。第一组只调分块大小，第二组再单独对比混合组批开关。客户端按毫秒同时采集新请求 B 的 TTFT，以及横跨 B 到达窗口内老请求 A 的 ITL 分布，重点盯住长尾指标（比如 ITL 的 P99）。只有看到 A 的长停顿明显收敛，同时 B 的 TTFT 仍在 SLA 范围内，这个改动才算真正立得住。

面试官可能会顺着追问：“如果既想保长上下文的 TTFT，又绝对不能影响在线 Decode 的 ITL，在多卡集群上还能怎么做？”（提示：PD 分离架构 Prefill-Decode Disaggregation。）

符号与名词（正文悬停可随时查看）

Continuous Batching
连续批处理（Iteration-level Scheduling）。把调度粒度细化到每一轮模型前向，谁完成立刻退批释放名额，新请求随时补位，消除静态组批的空转气泡。
TTFT
Time to First Token，首字延迟。从客户端发出请求到收到第一个生成 token 的耗时，主要受排队等待与 Prefill 轮数/耗时影响。
ITL
Inter-Token Latency，字间延迟。流式输出时相邻两个生成 token 到达客户端的时间间隔，决定了老用户体感是否“卡顿”。
Prefill
预填充阶段。并行处理用户输入的提示词、生成对应的 KV Cache 并预测第一个输出 token，属于计算密集型（Compute-bound）。
Decode
解码阶段。自回归逐字生成回答，每条请求每轮仅输入 1 个新 token，需反复搬运权重与历史 KV，属于访存带宽密集型（Memory-bound）。
Chunked Prefill
分块预填充。把超长提示词按固定 token 预算切分为多块分轮计算，中间分块仅写入 KV 不产生输出，用以限制单步前向耗时、保护在线 ITL。
EXTEND
SGLang 的前向模式之一。在已有前缀 KV 的基础上，继续计算一段新的提示词位置（空前缀也走该模式）。
MIXED
SGLang 开启混合组批（enable_mixed_chunk）后的前向模式，单次前向同时包含 Prefill 分块与 Decode 请求。
running_batch
SGLang 调度器维护的“当前活跃、尚未结束的请求集合”。只要请求未结束且未被抢占，就会留在这里并跨轮保留并发名额。
batch_to_run
本轮选批结束后，真正送进 run_batch() 上 GPU 执行的批次。核对某条请求本轮有没有真正算过，必须看它而不是只看 running_batch。
waiting_queue
等待准入的新请求队列（候车室）。调度器按 FCFS、显式优先级或 LPM 顺序逐一检查并发名额、KV 空间与分块额度。
请求名额
调度器还能同时容纳几条活跃请求的配额（由并发上限与请求映射表空闲行数共同约束），按“条请求”计数，跨轮保留直至请求结束或被抢占。
chunked_req
SGLang 调度器用于记住“当前正在分块、提示词尚未读完”的请求句柄，下一轮选批时会最先接手续算，优先级高于 waiting_queue。
RadixCache、prefix_indices
SGLang 基于基数树组织的前缀 KV 缓存；prefix_indices 记录当前请求命中的已有 KV 槽号，组批时会直接跳过这部分不再重算。
FCFS、LPM
等待队列的两种排序策略：FCFS 按入队先后服务（v0.5.17 默认）；LPM 按 RadixCache 命中的最长前缀长度排序，以最大化缓存复用。
