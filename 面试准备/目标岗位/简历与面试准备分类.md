## 1. 分类原则与使用方式

分类依据是岗位需要交付什么，以及招聘方会从哪些经历判断胜任力。同一个项目可以支持多类岗位，但简历中的主张、项目顺序、展开细节和面试追问会不同。

| 分类 | 招聘方主要希望看到的能力 | 简历与准备定位 |
| --- | --- | --- |
| A．框架、模型与硬件后端集成 | 让模型在目标硬件上正确、稳定地运行，并维护框架与后端之间的接口 | 主投；框架／Runtime 母版的基础版本 |
| B．端到端推理性能与模型优化 | 用实验找出瓶颈，在保持正确性的前提下改善性能 | 主投；独立的推理性能母版 |
| C．分布式推理与 Runtime | 解释并设计跨设备、跨进程的执行、调度、通信与资源回收 | 定向冲刺；框架母版的分布式专项变体 |
| D．ML／LLM 平台研发 | 让模型服务、计算作业或训练数据流程可维护、可观测、可扩展 | 平台方向；服务、计算、数据流程分别取材 |
| E．客户技术优化与开发者生态 | 把客户技术问题推进到交付，并把方法和边界讲清楚 | 接受客户协作和技术表达工作时重点考虑 |
| F．云资源效率与数据平台 | 用数据改进云资源利用率、容量与服务运行 | 相邻方向；围绕数据与资源效率单独组织 |
| G．HPC 工作负载与系统性能 | 分析并优化具体计算工作负载及 CPU／并行系统行为 | 相邻方向；由性能母版派生并单独准备 HPC |

使用时先定位岗位主分类，再确定一个必要的次方向。不要因为职位标题相似就把不同招聘编号合并，也不要因为某条 JD 罗列了多种技术，就把全部经历塞进同一份简历。

自 2026-11-09 起，现有 16 条岗位／渠道记录由用户指定为**核心重点目标**；企业范围扩大后新增岗位统一为**扩展候选**。目标层级、技术分类和招聘核验状态分别记录：后续新增岗位继续归入 A–G，D/E 子方向沿用，不自动改变核心重点目标。下面用原有核心岗位说明各类准备方式，扩展候选按其主分类复用，并补充具体 JD 的差异。

当前范围约定：

- 算子与编译器不再作为独立投递类别；Triton 等已有实践可作为框架和性能能力的辅助证据，压缩呈现。
- Zenlayer、Rakuten 不在当前考虑范围。
- 国内渠道的 AMD 资深 AI 框架工程师、AMD Agentic AI Inference Engineer、NVIDIA AI Computing Development Engineer 已纳入考虑，但完整 JD 尚未核验，分类为暂定。它们与官网岗位是否重复仍待确认。
- 本文的准备重点是投递建议，不代替原学习计划、进度或学习断点，也不把待补能力登记为已掌握。

## 3. A：框架、模型与硬件后端集成

对应岗位见 [清单 A 类](README.md#category-a)：Arm China 框架岗、NVIDIA TensorRT／TensorRT-LLM AIGV，以及暂定归入此类的 AMD 猎聘框架岗和 NVIDIA BOSS AI Computing 岗。

### 简历应证明什么

能够从模型进入框架到设备执行梳理完整链路，在模型接入、后端接口、状态与内存管理、精度排障和回归中承担明确职责。个人概述优先突出非 CUDA 加速器上的 PyTorch／vLLM 适配及生产问题闭环。

建议项目顺序：

1. **GLM 推理适配**：突出模型执行路径、权重映射、混合 KV cache／状态池、Graph 边界和交付。
2. **Qwen3 异步 H2D 修复**：突出确定性复现、根因缩小过程、同步覆盖范围与修复后回归。
3. **Conv3D 或 ECG 短案例**：补充跨模型、跨接口的布局与后端适配能力，按 JD 二选一。

性能结果用于证明实现有效，但应先交代本人修改了哪一层、为什么需要修改，以及如何证明没有破坏正确性。

### 面试准备重点

- 模型、框架、硬件插件、Runtime 和算子接口的职责边界。
- 权重、Tensor、状态池、KV block 与执行 metadata 的组织方式。
- CPU 准备、H2D 提交、设备完成、消费者执行之间的依赖。
- 动态 shape、Padding、Graph 与 eager 路径的兼容条件。
- 从输出异常追到首个数值分叉的方法，以及最小复现、边界输入和回归设计。

### 同组内的差异

- **Arm China**：重点讲定制硬件 backend 的完整集成与框架接口。
- **NVIDIA JR2018990**：在框架叙述之外，补准 TensorRT／TensorRT-LLM 的推理执行和性能设计。已有后端经验支持迁移能力，不直接写成 TensorRT 实战。
- **两条国内渠道记录**：先使用框架母版定位，取得完整 JD 后再决定是否增加性能或分布式侧重；不从相似名称推定官网 Req。

## 4. B：端到端推理性能与模型优化

对应岗位见 [清单 B 类](README.md#category-b)：AMD 96121、Qualcomm Performance & Modeling，以及暂定归入此类的 AMD Agentic AI Inference。

### 简历应证明什么

能够建立可比较的工作负载和基线，用 Profile、受控实验与成本模型定位瓶颈，再通过框架、内存、Host 或通信路径的改动改善结果。

每个主要案例按“**工作负载和基线 → 瓶颈证据 → 优化措施 → 正确性与性能结果**”展开。建议项目顺序：

1. **GLM 性能与容量优化**：KV 容量核算、非连续状态页引发的 Host 开销、metadata 搬运、持久 buffer、Graph 路径。
2. **Conv3D 布局优化**：临时存储膨胀、OOM 根因、完整联合方案的 TTFT 改善。
3. **ECG 权重预排布**：加载期转换与运行期重复开销的取舍、端到端时延及客户验收。

异步 H2D 案例可用简短条目支撑正确性与实验方法，不必在性能版中保留完整排障叙述。

### 面试准备重点

- TTFT、TPOT、吞吐、并发与尾延迟分别描述什么，优化目标如何选择。
- 计算、内存、Host、拷贝和通信瓶颈如何区分，Profile 与时间线怎样支持判断。
- Roofline、KV 字节量和带宽下界的假设、适用范围及与实测的差异。
- 受控实验、测量边界、预热、重复次数、统计方法和正确性验证。
- 换成长上下文、高并发、不同模型或不同硬件后，原结论是否仍然成立。

### 同组内的差异与风险

- **AMD 96121**：框架开发与性能工程交叉；以端到端性能母版为主，同时保留 vLLM／PyTorch 集成能力。Kernel 集成要求不等于主责是独立写 kernel，仍在当前考虑范围。
- **Qualcomm Performance & Modeling**：模型接入和精度验证围绕 Cloud AI 的延迟、吞吐、内存与扩展性展开；专项 5+ 年经验门槛仍是投递风险。
- **AMD Agentic AI Inference**：暂挂推理性能，并附加 C 类标签。仅凭“Agentic”不足以归入 Agent 应用开发；需要确认交付对象是推理引擎、serving／Runtime 还是业务 Agent。

## 5. C：分布式推理与 Runtime

对应岗位见 [清单 C 类](README.md#category-c)：AMD 94063、AMD 96120。

### 简历应证明什么

能够解释和处理框架与通信后端之间的契约、异步执行依赖及跨设备资源生命周期。以 A 类母版为基础，提前展示：

1. **通信适配与执行流调整**：本人修改的层次、可回退设计、单例和训练负载验证。
2. **异步 H2D 正确性**：完成依赖、缓冲区生命周期、复现和验证方法。
3. **GLM 多卡模型适配与 KV 管理**：只写真实部署配置和本人负责的部分。

PD/KV 源码分析和方案设计作为技能或技术研究的辅助证据，篇幅与已实施项目区分。当前不制作声称已交付生产级 RDMA／PD 系统的“资深分布式推理专家”履历。

### 面试准备重点

- TP／PP／EP 的张量切分、通信点、通信量和并行组合取舍。
- PD 对 TTFT／ITL 的潜在收益、传输代价与负收益场景。
- Scheduler、Worker、connector 和 transport 的职责边界，调度等待与背压。
- KV 创建、传输、ready、消费、引用归还和安全释放。
- 完成、失败、取消、超时、重复通知与进程重启的区别；结果失效不等于旧访问停止。
- 拓扑、带宽、消息量、通信计算重叠及正确性与性能验证。

### 两个岗位的深度差异

| 岗位 | 需要加强的讨论 |
| --- | --- |
| AMD 94063 | PD、Large-EP、RL 相关功能的接入点、接口约束与具体性能优化 |
| AMD 96120 | 完整 Runtime 的架构、调度、可靠性、扩展性、上游协作和长期维护责任 |

W3 可以增强上述问答和方案讨论，但真实网络、目标平台兼容性、设备停止访问及性能仍需实测证据。

Cadence 职位名中的“Leader”不直接代表人员管理；Optiver 的“Senior”也不替代对职责和证据的判断。Unity 本次对应的是 offline ML 平台，不能套用搜索缓存中的在线推理岗位描述。

## 7. E：客户技术优化与开发者生态

对应岗位见 [清单 E 类](README.md#category-e)：NVIDIA DevTech、Arm DevRel。

### 简历应证明什么

能够理解客户约束、复现并定位问题、协调接口与交付职责，最终给出可验证的结果，并把技术方案、限制与使用方法讲清楚。

建议项目顺序：

1. **ECG 客户交付**：客户时延目标、本人责任、Profile 与优化取舍、验收。
2. **多模态／Conv3D 适配**：从客户输入或模型行为提取单例，与算子和后端团队确定接口并验证。
3. **GLM 或异步 H2D 案例**：按岗位选择性能工程或复杂正确性排障，体现技术深度。

已有布局、压测及部署文档可支撑交付能力；只保留真实的文档形式和受众，不包装成未发生的公开传播成果。

### 两个子方向

| 子方向 | 简历应增加的侧重 | 面试准备重点 |
| --- | --- | --- |
| **NVIDIA DevTech** | 客户工作负载、代码与性能优化、最小复现、问题闭环 | GPU 加速思路、诊断过程、约束澄清、优化取舍、跨团队协作；不是只准备售前表达 |
| **Arm DevRel** | 端侧模型部署与优化、技术解释、指南、demo 和开发者合作 | 量化与部署、全栈 profiling、英语技术讲解、内容与示例设计；Arm 端侧实操和公开表达成果仍需证据 |

两者都应准备英文项目讲解、模糊需求澄清及个人责任说明。Arm 版本需要更明显的技术表达证据，一份只有性能数字的研发简历不足以覆盖其工作重心。

## 8. F：云资源效率与数据平台

对应岗位见 [清单 F 类](README.md#category-f)：Microsoft GPU COGS／Efficiency。

### 简历应证明什么

能够处理可靠的数据与指标，并通过分析改进资源利用和服务运行。提高国药数据质量平台、异常监控、指标血缘工具的篇幅，再用 GLM 的容量核算和性能诊断支撑数据驱动的效率分析。

本岗位中的 GPU 是被管理和分析的资源。仅展开 Attention、KV 与模型接入，会使简历的主要证据偏离平台职责。

### 面试准备重点与边界

- telemetry 的采集、质量、聚合、解释与可观测性。
- 利用率、容量、成本模型及性能／成本取舍。
- 数据管线、可靠云服务、异常诊断和工程维护。
- 当前未证实云账单、fleet 管理、FinOps 或容量规划经验；推理加速结果不能改写成云成本节省。

若正式投递这条岗位，应围绕数据平台与资源效率单独组织，不能只替换推理性能版的关键词。

## 9. G：HPC 工作负载与系统性能

对应岗位见 [清单 G 类](README.md#category-g)：Intel HPC and Financial Workload Optimization。

### 面试准备重点与边界

- CPU 缓存、内存访问、线程并行和 Linux 性能分析。

- 可复现 benchmark、性能归因和客户技术沟通。
- 数学统计背景可支持分析能力，但不等于金融计算项目经验；MPI／OpenMP 与 HPC 应用实践仍是单独缺口。
