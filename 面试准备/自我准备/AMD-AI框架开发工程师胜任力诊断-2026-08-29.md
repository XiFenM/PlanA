# AMD AI 框架开发工程师胜任力诊断

> - 诊断日期：2026-08-29
> - 目标方向：AMD AI 框架开发工程师
> - 能力重心：大模型推理优先，训练系统素养兼顾
> - 证据范围：PlanA 当前材料、截至 2026-08-29 的全部面试记录与复盘、官方在招岗位样本
> - 配套计划：[高级 AI 框架开发工程师八周证据冲刺计划](../../计划/高级AI框架开发工程师-八周证据冲刺计划.md)
> - 市场基线：[AI 框架岗位需求索引](<../../Job Description/AI框架方向/市场岗位需求/README.md>)

## 0. 执行结论

当前最准确的职业定位不是“从零准备 AI 框架”，也不是“已经稳定达到 AMD 高级推理框架岗”，而是：

> 已具备较扎实的非 CUDA 加速器推理框架适配、模型接入、跨层性能定位和疑难问题排查经验。真正稳定的优势是能够从端到端错误、OOM 或延迟异常出发，把问题逐步收敛到 tensor shape、layout、片外访存、通信边界或异步依赖，并与算子、runtime 和模型团队形成闭环。当前尚缺少 AMD 高级岗位最看重的端到端系统所有权证据，主要缺口是当前 vLLM/SGLang 核心架构、C++/HIP/Kernel、TP/EP/PD/RDMA、定量性能模型、公开 upstream 和可审计 benchmark。训练方向有工作接触，但没有形成系统化、可追问的证据。

岗位分层结论：

| 岗位层级 | 当前判断 | 行动建议 |
|---|---|---|
| AMD 上海 `87545`，早期职业阶段 AI Framework Eng. | **有条件可投；在本轮采样岗位中能力主题最相邻** | 不必等八周计划全部结束；先完成 claim 校准、vLLM 主链、可复算性能案例、C++ 基础，以及一个多 GPU/多节点瓶颈诊断案例 |
| AMD 上海 `78999`，3 年以上 AI Framework Eng. | **经历相邻，关键硬证据不足** | 完成 C++、Kernel/custom op、ROCm 映射、定量 benchmark 和公开工件后重点投递 |
| AMD 上海 `89398`，PD/Large-EP 方向 | **专项拉伸且存在资历风险** | 技术补强可缩小 EP/PD 差距，但官方 5 年以上经验要求无法由八周计划关闭 |
| AMD `88008`、`81040`、`80979` 及本地 MORI 复合 JD | **当前拉伸目标，尚未稳定胜任** | 是否达到以 ROCm/Kernel、分布式、benchmark 和 upstream 验收门槛为准，不按日历时间承诺 |
| AMD `76255` | **历史架构参照** | 原页面已失效，只保留框架/runtime 岗位画像，不进入当前投递队列 |
| AMD/NVIDIA 高级训练框架岗 | **不是当前主投方向** | 本轮补到 L2 系统素养；不按 Principal/Senior 训练岗位深度准备 |

这里的“有条件可投”不是录用概率，也不代表满足地域、职级和招聘流程的全部条件；它只说明现有生产经历与该岗位公开能力模型存在实质重合。

## 1. 诊断方法与证据边界

### 1.1 能力等级

| 等级 | 定义 | 合格证据示例 |
|---|---|---|
| L0 | 没有可用证据 | 只见名词，或材料完全未覆盖 |
| L1 | 能识别概念和基本用途 | 可说明术语，但无法独立推导、定位源码或设计验证 |
| L2 | 能独立解释和推导一个固定范围 | 能画数据流、手算 shape/bytes、映射固定版本源码、给出可执行 test design |
| L3 | 能在真实工程中独立实现、排障或测量 | 有代码/日志/trace/benchmark，能说明个人负责边界、根因和回归 |
| L4 | 能主导架构与跨团队/上游演进 | 有长期系统所有权、公开设计/PR/review、规模化验证和可迁移方法 |

等级是学习规划工具，不是招聘概率。`L2/L3` 表示生产实践接近 L3，但公开或面试证据尚不足以稳定支撑该等级。

置信度：

- **A**：多份较高质量材料相互印证，或有明确的固定源码/产物。
- **B**：有完整叙事，但主要来自单次面试、单模型音频理解或自述。
- **C**：只有简记、宽泛简历 claim 或缺少作答，暂不能定论。

### 1.2 面试证据等级

- **F1：较高置信的现场呈现**
  - 地平线：完整音频、双 ASR 校准；仍缺逐句声纹确认。
  - XG 一面：带时间戳文字记录，但只覆盖 `00:41:52–01:29:48`。
  - XG 二面：主体问答较完整，正式问答约为 `00:07:22–00:50:07`。
- **F2：中等置信的现场呈现**
  - 奕行二面、安霸：完整音频经单一 Gemini 模型理解，再由本地技术审计校准；时间点只作近似回听锚点。
- **Q：技术校准**
  - 复盘中关于 vLLM、AWQ、TP/EP、Roofline、RDMA 的正确解释是评估标准，不代表面试时已经掌握。
- **U：未知**
  - 只有问题简记而无作答、无代码、无 benchmark、无正式反馈时，必须保留未知，不能推断为会或不会。

本诊断评估的是“现有材料能够支持什么结论”，不是对真实能力的最终裁决。所有项目成果和性能数字均来自候选人自述，尚未由代码、日志、profile、benchmark 或第三方记录独立验证。“本场没有观察到”不等于不会。

### 1.3 证据优先顺序

1. 可公开、可复现的代码、测试、benchmark 和固定源码审计。
2. 真实生产经历中能够明确个人职责、条件、结果和回归的案例。
3. 地平线双 ASR 校准报告与 XG 两轮带时间戳记录。
4. 奕行二面、安霸的最终报告和证据审计。
5. 小红书、奕行一面的问题简记，只作为考题目录。
6. 简历中的技能清单不能单独证明能力。

早期地平线报告应以[双 ASR 校准版](../面试问题经验/分析成果/reports/interview-20260813-01-self-review-asr-calibrated.md)为准。`run-20260823-01.normalized.json` 中“12 个维度全部 positive”等模型外推已被[证据审计](../面试问题经验/分析成果/analysis/run-20260823-01.evidence-qa.md)否定，不纳入本诊断。

## 2. 目标岗位不是一条单线

[本地目标 JD](<../../Job Description/AI框架方向/高级AI框架开发工程师.md>)实际混合了两类画像：

1. **MORI/GPU Networking 专项**：MORI-EP、MORI-IO、MORI-SHMEM、UMBP、vLLM/SGLang、MoE EP、PD 分离、GPU Direct RDMA 和 8–64 GPU。
2. **通用高级推理框架**：scheduler、KV、Kernel、编译器/runtime、分布式推理、性能优化和开源领导力。

截至 2026-08-29，未在 AMD 官方招聘页确认到与第一段完全一致的单一岗位，因此不能把两段所有要求同时视为近期主投的硬门槛。官方岗位显示出更合理的梯度：

- [AMD `87545`](https://careers.amd.com/careers-home/jobs/87545?lang=en-us)重视 LLM/多模态、框架集成、生产代码，以及多 GPU/多节点上的计算、内存和通信瓶颈诊断；C++/Kernel/ROCm/开源是加分项。
- [AMD `78999`](https://careers.amd.com/careers-home/jobs/78999?lang=en-us)明确要求 3 年以上经验和 Linux C++，工作职责扩展到 GPU Kernel、训练与推理、多 GPU/多机和上游协作；HIP/ROCm 等具体技术位于优先经验部分。
- [AMD `88008`](https://careers.amd.com/careers-home/jobs/88008)、[AMD `81040`](https://careers.amd.com/careers-home/jobs/81040?lang=en-us)和[AMD `80979`](https://careers.amd.com/careers-home/jobs/80979?lang=en-us)分别代表 vLLM 性能、Kernel 和端到端推理性能的当前拉伸层。
- AMD `76255` 原页面截至诊断日已不再返回职位正文，只保留为框架/runtime 架构的历史样本。
- [AMD `78259`](https://careers.amd.com/careers-home/jobs/78259?lang=en-us)代表训练框架上限，要求 PyTorch internals、DDP/FSDP、混合精度、内存规划、通信计算重叠和上游影响力。

因此，本轮目标定义为：

> 先把现有非 CUDA 推理框架经历转换成 AMD `87545/78999` 可验证的通用证据，再补 ROCm/HIP、分布式和 upstream；MORI Senior 作为拉伸设计题；训练补到能解释、能推导、能做最小验证的系统素养。

| 技术表达与现场推导 | L2 | L3 | L3/L4 | A | 熟悉案例有深度，陌生题易先猜再修正；是能力转化瓶颈 |
| 英文技术沟通 | L1/L2 | L2 | L3 | C | 有 PlanA 训练材料，但没有英文系统设计或项目答辩证据 |

带“自述 / 可证”的行专门区分项目档案所描述的生产水平与当前材料能够审计到的水平；其余斜杠表示等级区间。多次重复讲述同一个案例只提高“能稳定讲述”的置信度，不提高项目结果真实性。

### 4.1 三类缺口不能混为一谈

- **知识缺口**：例如 BF16/FP8、Prefix Cache、EP/PD、C++ object model。
- **实践缺口**：例如 HIP Kernel、rocprof、RCCL、多机 RDMA、SGLang 实际修改。
- **证据缺口**：做过但没有固定版本、代码、benchmark、PR、测试或清晰 ownership。
- **表达缺口**：知道或做过，但不能在白板上先定义配置、单位和假设，再完成推导。

当前最高优先级不是把所有 L1 都读成 L2，而是让项目档案中接近 L3 的高价值经历获得可信证据，并关闭会在面试中直接导致失分的 P0 基础。

## 5. 现有材料稳定支持的优势

### 5.1 跨层排障是最稳定的核心竞争力

多场面试反复出现同一方法：

1. 从错误、OOM、TTFT 或吞吐异常建立稳定基线。
2. 用 profile、逐层对齐、开关和控制变量缩小范围。
3. 把问题落到 shape、layout、访存、copy、stream、通信或 runtime 可见性。
4. 抽取最小失败 case，与算子/runtime 团队完成修复或继续收敛。
5. 用 Replay、回读、CI 或端到端回归设计验证修复并降低复发风险。

支持材料：

- [XG 一面报告](../面试问题经验/分析成果/reports/interview-xg-20260818-01-analysis.md)：模型导入、精度对齐、profile 与最小失败 case。
- [地平线校准报告](../面试问题经验/分析成果/reports/interview-20260813-01-self-review-asr-calibrated.md)：Conv3D 小通道对齐、OOM/TTFT、KV 生命周期等。
- [奕行二面报告](../面试问题经验/分析成果/reports/interview-yixing-recording-02-analysis.md)：逐层/二分精度定位和并发异步 Padding race。
- [安霸报告](../面试问题经验/分析成果/reports/interview-ambarella-20260828-01-analysis.md)：Conv3D、Fused RoPE、AWQ 与 Host 聚合等案例。

奕行二面的 Host Padding 竞态与 `projects.md` 中 Qwen3-32B/vLLM V1 的低概率 H2D/D2D 异常暂按两条案例管理：前者是 F2 单模型理解，最终修复和数字待回听；后者来自项目档案，根因尚未闭环。它们不能互相补充证据。

面试中最适合稳定复用的表述是：

> 我负责从框架症状建立证据链并收敛问题，能够把模型级异常定位到算子、layout、通信或 runtime 边界；底层 Kernel 或 runtime 的最终实现如果由其他团队完成，我会明确说明自己负责复现、接口、验证和回归的部分。

不应扩张成“独立完成所有 Kernel 和底层 runtime 修复”。

### 5.2 非 CUDA 后端迁移经验具有真实市场价值

AWS Neuron 与 AMD 岗位都要求把 PyTorch/vLLM/SGLang 带到非 NVIDIA 后端。项目档案与面试材料目前能够支持的实际接触是：

- 模型定义、权重、输入和执行路径接入；
- layout、dtype、精度对齐、最小失败 case 和性能回归；
- 框架、Kernel、runtime、通信和客户之间的跨栈定位与协作闭环。

以下属于由现有经历抽取出的可迁移问题地图，但还不能当作本人已完整负责的实现证据：

- framework/platform 与设备后端注册，以及 DeviceGuard、allocator 和构建链；
- custom op 的完整注册与 device 调用链、stream/allocator 语义、缺失算子和 fallback 策略。

但迁移价值必须写成“方法和问题结构相似”，而不是“已经熟悉 ROCm/HIP”。

### 5.3 多模态经历与 AMD `87545` 直接相邻

Qwen-VL、ERNIE-VL、Qwen-Omni、Conv3D、M-RoPE、图像/视频/语音输入链路，与 `87545` 对多模态模型和模型感知实现的要求高度重合。当前最需要补的是：

- 具体模型版本与代码路径；
- 输入如何进入 processor/model runner；
- tensor shape/layout 的变化；
- 精度判据与性能 workload；
- 框架修改、算子修改和协作部分的边界。

这类多模态 LLM 经历不能自动证明经典视觉和端侧媒体 pipeline 能力。安霸材料显示，YOLO/CNN、NMS、视频编解码和 C++ 端侧串联仍是证据空白；它会影响边缘 SoC 岗位，但不是当前 AMD LLM 框架主线的 P0。

### 5.4 客户交付和跨团队闭环是高级潜力证据

外部测评、客户模型、云服务部署和多团队协作支持“在真实工程约束下参与交付”的判断。它能提供一部分工程可信度，但不能替代可审计的上游代码和独立 ownership 证据。

## 6. 推理框架诊断

### 6.1 vLLM：做过不等于能稳定讲清当前架构

已观察到：

- 接触 scheduler、worker、model runner、engine、KV block、Chunked Prefill 和设备插件。
- 能结合模型 bring-up、KV、异步 copy 和多模态链路讲项目档案中的问题。

面试暴露：

- XG 二面 `00:18:04–00:28:13` 没有先给出 `scheduler → KV manager → worker/model runner → backend` 全景。
- V0 到 V1 的核心边界主要由面试官提示。
- PagedAttention、Prefix Cache 和 block lifecycle 容易混在一起。

关闭条件：

1. 不看稿画出 `OpenAI request → processor → EngineCoreRequest → scheduler → KV manager → model runner → attention backend/custom op`。
2. 对每个边界说明输入、输出、ownership、同步和失败路径。
3. 用固定 commit 指出 8–12 个核心文件/类/函数。
4. 能解释 V0/V1、Chunked Prefill、Prefix Cache、PagedAttention 各自改变什么，不改变什么。
5. 完成当前 Pass C-1，而不是重新阅读已通过的 Pass A–B。

### 6.2 KV Cache：先统一单位，再谈机制

已有基础：请求结束释放、尾块追加、满块申请、逻辑 block 与硬件对齐冲突。

主要风险：

- `256` 有时像 token block，有时像 byte/element/address alignment。
- 对 Prefix Cache 缺 block hash、refcount、eviction、copy-on-write 和 partial block 的稳定解释。
- 不能把 PagedAttention 的动态地址索引只说成“避免碎片”。
- 地平线双 ASR 一致确认：Padding 先答右、后改左，没有先区分 dense prompt batch、生成向右追加和 Paged KV slot/block table，也没有把 mask、position id、logits 读取位置与 KV slot 写成同一组不变量。

关闭条件是完成一份单位严格的 KV 账本：模型、dtype、层数、head 数、head size、block tokens、TP、每请求 token 数、物理 bytes、分配/引用/释放和 prefix reuse 全部可复算；另完成一组 Padding/position/mask/logits/KV-slot 不变量推导，明确 dense prompt batch 与增量生成的差异。

### 6.3 SGLang：当前只应标为对照阅读

现有材料没有 SGLang 实际开发、RadixAttention 修改或公开源码证据。因此：

- 可在计划中用 SGLang 对照 scheduler、KV 和 backend 边界；
- 不需要与 vLLM 同等深挖；
- 在完成一个固定源码 map 前，不在简历中用“熟悉 SGLang”暗示实践深度。

## 7. 性能、Kernel 与数值诊断

### 7.1 强项是事后 profile，短板是事前定量推导

跨场最稳定的失分模式是：

- TP/EP 不先固定 shape 和切分轴；
- MatMul 不先算 FLOPs、Bytes、Arithmetic Intensity、可达性能上界及对应执行时间下界；
- KV 不先统一 token、element、byte 和 address alignment；
- 优化收益不先声明 workload、绝对值、分位数和正确性阈值；
- 陌生题先用相邻经验猜测，再由面试官收窄语境。

奕行二面的 MatMul Roofline 没有完成 `FLOPs → Bytes → AI → 可达性能上界（对应执行时间下界）→ 实测效率`。这不是一个孤立知识点，而是高级性能岗位的核心方法缺口。

### 7.2 优化案例必须升级为可审计 Case Card

每个案例至少记录：

```text
问题与用户影响
→ 模型/版本/shape/dtype/并发/硬件抽象
→ 基线绝对值和测量方法
→ 正确性契约
→ 初始假设与反证
→ profile/trace/counter
→ 根因与个人负责边界
→ 修改位置与协作边界
→ 优化后绝对值、相对变化和波动
→ 回归、限制与未完成项
```

首批只做 3 张：Conv3D、blocked/Col-major layout、`projects.md` 中 Qwen3-32B/vLLM V1 的低概率 H2D/D2D 异常。奕行二面的 Host Padding 竞态另作 F2 回听卡，不与第三张合并。RoPE、AWQ、KV 对齐暂作候选，不同时铺开。

### 7.3 Kernel 能力应拆成四层

| 层次 | 当前证据 | 下一步 |
|---|---|---|
| 判断是否需要融合/专用 Kernel | 较强，能从中间张量、launch、layout 和 HBM 解释价值 | 给出 shape、bytes 和证伪条件 |
| 选择/接入 Kernel | 有框架侧和算子团队协作经历 | 完成一个公开 custom op/Kernel dispatch trace |
| 独立实现和调优 | 证据不足 | 做一个小而真实的 HIP/Triton 切片，不追求完整 FlashAttention |
| 一阶硬件分析 | 证据不足 | 能读 occupancy、register、LDS/shared memory、cache、coalescing 与 wavefront/warp 指标 |

对 AMD `88008`，官方描述明确表示不一定每天从零写 Kernel，但必须能说明为什么慢、应该改变什么。因此优先级应是“性能诊断 + Kernel 集成 + 一个小实现”，而不是大量孤立算子题。

### 7.4 数值与量化

需要补齐的基础：

- FP16、BF16、FP8 E4M3/E5M2 的范围、精度和典型使用位置；
- 输入/输出 dtype、accumulation/opmath dtype、master weight 的区别；
- RMSNorm/Softmax/Reduction 为什么常用更高精度累积；
- AWQ 的 group、scale、zero-point、calibration、outlier/sensitive channel 与 Kernel layout；
- W4A16 在 Prefill 与 Decode 中为什么收益不同。

不要把“接入量化模型”写成“负责量化算法和精度优化”，除非有相应代码和数据。

## 8. C++、PyTorch、Runtime 与 ROCm 诊断

### 8.1 C++ 是近期最大的硬门槛风险

XG 一面 `01:12:05–01:17:17` 对可执行文件段、overload/override/name hiding 和动态库定位回答不稳。安霸材料也表明日常开发以 Python 为主。对 `78999` 和 Senior 系统岗，这类基础错误会覆盖掉前面的项目优势。

P0 范围：

- object lifetime、RAII、copy/move、virtual dispatch、overload/override/name hiding；
- stack/heap、ELF section/segment、storage duration、shared library 装载和符号定位；
- thread、mutex、condition variable、atomic、memory ordering 的最小正确模型；
- pointer/reference/span、ownership 和异步 buffer lifetime；
- CMake/编译/链接/ABI/pybind11 的可操作基础。

验收不是刷完一本书，而是：能现场实现一个 producer-consumer 或异步 buffer lifetime 练习，使用 sanitizer/日志验证，并分别说明它与两条 race 叙事可能相关和不能直接类推的部分。

### 8.2 PyTorch backend：经验需要一个公开混合栈锚点

项目档案对 backend/custom op 的自述接近 L2，当前可审计证据约为 L1；`schema → dispatcher → backend key → fake/meta → device guard` 仍主要是技术审计给出的校准标准，不是现场已经完整讲出的能力。PlanA 只完成 PyTorch Internals 概览，需要一个最小证据把以下链路连起来：

```text
Python API
→ Dispatcher/schema
→ fake/meta 或 shape inference
→ C++ extension/custom op
→ device/stream/allocator guard
→ HIP/Triton/CPU reference
→ correctness + benchmark + CI
```

无 AMD 硬件时，可以完成固定源码审计、CPU/CUDA 可运行 harness 和 HIP porting matrix，但必须把 AMD 运行标为待验证。

### 8.3 ROCm/HIP/RCCL：可迁移，不可冒充

当前没有 AMD GPU、hipcc、rocprof、RCCL、XGMI 或 wavefront 的直接面试证据。正确策略是：

1. 建立“现有自研后端 → CUDA 参考 → ROCm/HIP”语义映射。
2. 明确 device、stream/event、allocator、graph、custom op、collective、profiler 的等价项和不等价项。
3. 无 AMD 环境时只交 B 级源码/测试设计；有环境时再补 A 级 build、correctness 和 rocprof trace。
4. 不在没有硬件数据时写 AMD 性能提升。

## 9. 分布式推理诊断

### 9.1 TP/PP/SP/CP：从名词转为 shape 与 bytes

已有 Megatron TP、collective 测试和多卡部署接触，但面试中出现 collective 固定化、Prefill/Decode 与 TP/PP 过度绑定等问题。

最低验收：给定 `B、S、H、num_heads、num_kv_heads、TP、EP、dtype`，能够：

- 写出 Attention 和 MLP 各阶段局部 tensor shape；
- 说明在哪个轴切分；
- 判断 AllReduce、ReduceScatter、AllGather、All-to-All 或 P2P；
- 在给定有效带宽假设后，计算每 rank 通信 bytes 和通信时间下界；若给定 latency/SLO，再反推最低所需带宽；
- 说明 sequence/context parallel 的差异与适用边界。

推理 DP 另行验收：它不是 tensor 切分。需要说明 replica routing、queue/backpressure、DP attention 或 DPLB 的观测与决策边界，以及它与 TP/EP 组合时的负载和 KV 影响。

### 9.2 MoE/EP：当前是 MORI 类岗位红灯

XG 二面 `00:38:00–00:47:23` 的端侧 MoE 设计多次依赖面试官提示，并错误套用多卡冗余专家/EPLB。当前需要稳定掌握：

```text
router logits
→ top-k expert selection
→ token count / capacity / padding
→ permutation / dispatch
→ grouped GEMM
→ combine / restore order
→ load balance / EPLB
```

必须能分别解释单卡多专家、单机多卡和跨机 EP，不能把“EPLB”“专家冗余”和“通信优化”混成一个答案。

### 9.3 PD 分离与分布式 KV：当前只有相邻经验

现有 TCP/CPU 路径、Host staging/聚合和 KV 对齐经验可以迁移，但还不能证明 PD 系统设计能力。需要补齐：

- P/D 两侧 block ownership、metadata、ready/ack、cleanup 和 failure；
- TP 配置不同下的 KV 重分片；
- pull/push、CPU proxy/GPU direct、host staging 的权衡；
- transfer 与 compute overlap；
- TTFT、ITL、throughput、P95/P99 的目标冲突；
- 何时 PD 不值得做，以及用什么数据证伪。

### 9.4 RDMA 与网络：不要把 RDMA 和 IB 当成二选一

最低知识链：memory registration、MR、QP、CQ、WR、doorbell、progress、ordering、GPU Direct、IB/RoCE、NIC/NUMA/PCIe/XGMI 拓扑。没有真实设备时，交付数据路径图、失败矩阵、通信量模型和可执行测试方案即可，不能声称跑通过 MORI/RDMA。

## 10. 训练方向诊断

当前训练证据主要是 DeepSpeed ZeRO-3、Megatron-LM TP 与通信接口适配接触；奕行一面只记录“被问过 DeepSpeed”，没有现场回答。不能据此声称熟悉完整分布式训练。

本轮训练目标定为 L2：

1. 画清一次训练 step：dataloader → forward → activation → backward → gradient sync → optimizer update → checkpoint。
2. 计算参数、梯度、optimizer state、activation 的显存账目。
3. 比较 DDP、FSDP/ZeRO-3、TP、PP、SP/CP、EP 的切分对象、通信、内存和失败模式。
4. 解释 mixed precision、loss scaling、gradient accumulation、activation checkpointing 和通信计算重叠。
5. 用一个小模型或固定源码做最小策略验证；不要求多机训练性能纪录。

本轮不做：完整 TorchTitan/Megatron 深潜、训练编译器全栈、RLHF/PPO/GRPO 细节或训练 Principal 级架构领导力。

## 15. 优先级与补强顺序

### P0：近期面试生存线

前两个有效周先完成最小面试生存线；需要原始数据和完整审计的 Case Card/benchmark 最晚在 W4 关闭：

1. 从当前 Pass C-1 恢复，关闭 vLLM 请求到 EngineCore 的主链。
2. 完成 C++/Linux 基础诊断清单和一个并发生命周期练习。
3. 完成一张小型 MatMul/Conv3D Roofline；W4 再补完整 benchmark、profile 和回归。
4. 完成 5 个并行组合题，覆盖 TP/PP/DP/SP/CP/EP 的 tensor shape、通信字节或 routing；其中至少 1 题包含推理 DP、replica routing 与 backpressure。
5. 审计 CV、项目和自我介绍的 claim、数字、单位与 ownership。
6. 建立 Conv3D、layout、Qwen3-32B/vLLM V1 低概率 H2D/D2D 异常三张 Case Card 草稿，冻结待核数字、单位和 ownership；奕行 Host Padding 另作 F2 回听卡，W4 完成审计。

### P1：AMD 主目标证据线

在第 3–6 个有效周完成：

1. MoE `route → dispatch → grouped GEMM → combine` 和 EP 通信模型。
2. PD/KV ownership、metadata、failure、重分片和 overlap 状态机。
3. PyTorch custom op 的 Python/C++/device/stream/allocator 完整调用链。
4. ROCm/HIP/RCCL 与现有自研后端的迁移矩阵。
5. 一个 Kernel 集成或小型 HIP/Triton 实现与 profiler 分析。
6. 一个可公开评审的 issue/reproducer/test/doc/benchmark 工件。

### P2：训练兼顾与面试闭环

在第 7–8 个有效周完成：

1. 一次训练 step 与显存账本。
2. DDP/FSDP/ZeRO、TP/PP/SP/CP/EP 决策表。
3. 两场推理 mock、一场训练系统素养 mock。
4. 5 分钟中文和英文项目陈述。
5. 按 `87545`、`78999`、MORI/Senior 三层分别准备简历和提问。

## 16. 投递与面试门槛

### 16.1 不必等待全部计划结束的条件

面向 AMD `87545` 或相似早期/中级框架岗，满足以下五项即可主动投递并边投边补：

- 简历中没有已知的范围扩大和数字冲突；
- 能脱稿讲清 vLLM 主链和一个多模态模型接入案例；
- 能完整复算一个性能案例；
- C++ 基础诊断没有明显红灯。
- 能用一个具体配置解释多 GPU/多节点场景的计算、内存和通信瓶颈；缺少真实多节点数据时明确证据边界。

### 16.2 `78999` 进阶门槛

在上一层基础上增加：

- 一个 C++/custom op/Kernel 可运行或可审查工件；
- 一份 ROCm/HIP/RCCL 迁移矩阵；
- 一组多 GPU tensor/communication 推导；
- 一个公开可评审工件。

### 16.3 Senior/MORI 拉伸门槛

至少增加：

- vLLM EP/PD 固定源码与 Change Cards；
- Kernel profiler 一阶分析；
- RCCL/RDMA/拓扑与多机性能模型；
- 可审计 benchmark 和性能回归；
- 持续 upstream 或架构所有权证据。

若真实面试窗口少于 14 天，使用冲刺计划中的应急路径，优先保住 P0，不临时扩读完整 MORI、编译器或训练框架。

## 17. 八周后的合格状态

本轮成功不要求把所有能力提升到 L3，而要求建立以下可核验组合：

- **推理核心**：vLLM 主链、KV、MoE EP、PD/KV 能在固定源码和白板上讲清。
- **性能核心**：至少一个案例具备完整 Roofline、profile、绝对基线、正确性与回归。
- **系统核心**：一个 Python/C++/custom op/Kernel 混合栈工件，能解释 lifetime、stream 和 allocator。
- **AMD 迁移**：明确 ROCm/HIP/RCCL 的已知、映射和待验证，不冒充硬件实测。
- **训练素养**：一次训练 step、显存/通信账本和并行策略选择达到 L2。
- **工程证据**：一个公开可评审 upstream 工件，三个审计过的项目 Case Card。
- **表达闭环**：两场推理 mock 和一场训练 mock 经追问，不再依赖面试官收窄问题。

## 18. 当前明确不做

- 不同时深挖 vLLM 与 SGLang 全部源码；vLLM 为主，SGLang 窄对照。
- 不实现完整 FlashAttention、完整 MoE Mega Kernel 或完整 EP/PD toy serving。
- 不在没有 AMD/RDMA 硬件时制造虚假性能数据。
- 不把公司内部代码、未公开 API、硬件参数或日志迁入公开材料。
- 不以刷完课程或累计小时替代关卡验收。
- 不为训练相邻能力展开完整 TorchTitan、RLHF 或编译器课程。
- 不把所有 Senior/Principal JD 的并集当成近期岗位硬门槛。
