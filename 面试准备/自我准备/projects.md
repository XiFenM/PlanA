## 项目一：多模态大模型推理框架适配与性能优化

- **时间**：2025年04月 - 2026年03月
- **角色**：核心开发工程师
- **技术栈**：`PyTorch`、`vLLM V0/V1`、Python、C/C++、自研算子库、自研通信库
- **涉及模型**：Qwen2.5/3-VL、Ernie4.5-VL、Qwen3-Omni

### 项目背景

公司自研加速芯片的软件生态仍在建设期，主流推理框架、模型结构与算子实现主要面向 CUDA 平台。多模态模型还会引入图像、视频和语音预处理、高维 Tensor、3D 位置编码、Vision Attention 及卷积算子，使框架兼容、数值精度、内存排布和端到端性能问题相互耦合。

### 职责

- 负责多模态模型在自研芯片上的 `vLLM` 端到端适配、精度对齐和性能优化。
- 维护模型执行层与 `PyTorch`、算子库之间的接口，推动框架特性和缺失算子落地。
- 通过跨平台基线、Profile、算子单测和 Trace 定位模型级瓶颈，并协调算子、运行时和硬件团队完成定位、修复与回归验证。

### 关键行动

1. **打通模型执行链路**：梳理多模态输入从预处理、Embedding、Vision Encoder、位置编码到语言模型的执行路径，逐层补齐模型注册、配置解析、输入映射和设备算子支持，使图像、视频及语音链路能够在自研芯片上运行。
2. **统一多模态 RoPE 接口**：重构 Fused Rotary Embedding 调用方式，兼容文本 RoPE、视觉 M-RoPE 与音频一维 RoPE，减少模型间的重复适配逻辑，并为融合算子提供稳定接口。
3. **优化内存排布和矩阵计算**：在 `PyTorch` 与 `vLLM` 中接入多维 Col-major Matmul，处理高维 Tensor、前后置变形和临时 Tensor 生命周期问题，降低特殊硬件访存排布带来的额外开销。
4. **解决关键算子瓶颈**：围绕 Conv3d、Flash Paged Attention、Vision Attention、GELU、Scatter 和 Index 等算子建立模型形状单测；通过设备实现、CPU Fallback、精度对比和调度条件控制，在保证正确性的前提下逐步替换性能瓶颈。
5. **建立端到端诊断方法**：同时观察 Host 空洞、Kernel 时间、Tensor Layout、跨设备拷贝和通信行为，避免只根据单算子耗时判断瓶颈；对随机精度问题使用中间值 Dump、算子级复现与跨平台结果对齐。
6. **跨仓库交付**：在内部 `vLLM V0/V1`、`PyTorch` 和算子仓库间同步修改，补充 CI 用例、模型测试和技术文档，确保功能可持续维护。

### 量化结果

- 在 Qwen3-VL 链路完成 Conv3d 优化与模型侧验证，使首 Token 延迟下降 **40%**。
- 完成 Qwen2.5/3-VL、Ernie4.5-VL 与 Qwen3-Omni 的阶段性适配，覆盖图像、视频和语音等多模态输入。
- 形成可复用的多模态 RoPE、Col-major Matmul 和算子精度排查方法，降低后续同类模型的接入成本。

### 面试深挖点

- `vLLM` 的多模态输入如何从 Processor 进入 Model Runner，最终与文本 Token 合并？
- M-RoPE 与普通 RoPE 的位置索引和 Tensor Layout 有什么差异，为什么适合做融合？
- Col-major 布局为什么适合目标硬件？转换放在 Host 还是 Device，各自的收益和风险是什么？
- Conv3d 为什么会同时造成显存和性能问题？如何区分 Padding、访存、计算和调度开销？
- 多模态模型出现结果异常时，如何从最终输出逐步收敛到具体算子或数据路径？
- 为什么单并发优化有效，并不必然意味着高并发吞吐也同步改善？

### 2026-09-02 口述基线（待核验）

> 本节保存本次无稿口述中已经形成的项目逻辑，供后续 Case Card 和面试稿持续迭代，不替代上方已经审计的对外口径。存在冲突或缺少原始证据的内容统一列在“待核验字段”中；未经确认的硬件规格和性能数字不写入正文。

#### 当前叙述

这项工作最初来自交通业务客户对图像和视频分析的需求。道路摄像头会持续产生大量影像数据，客户希望从中自动筛选符合业务条件的片段。传统视觉模型通常需要针对不同任务分别训练或微调，多模态大模型则能够同时处理视觉信息和文本语义，通过调整 Prompt 支持更多业务场景。因此，我们需要在自研芯片上完成多模态大模型的推理适配。

我主要负责 Qwen2.5-VL、Qwen3-VL 和 ERNIE 4.5-VL 的框架层适配，包括模型执行链路打通、精度对齐和端到端性能优化。涉及底层算子实现时，我负责从模型和框架侧定位问题、整理真实 Shape、调整调用与数据布局，并与算子同事协同完成优化。

其中一个代表性问题发生在视觉 Encoder 的 Conv3D 路径。模型运行时首先出现了 OOM，调用栈将异常定位到了 Conv3D。根据当时的模型权重、KV Cache 和剩余显存估算，常规激活值原本应该能够容纳，因此我继续检查 Conv3D 调用过程中是否产生了预期之外的中间数据或临时空间。

沿着调用路径分析后，我发现该实现采用了 channels-last 输入布局。这样设计原本是为了提高通道数据的连续访存效率，但视觉输入的通道维度很小，而目标硬件要求末维按照较大的粒度进行内存对齐。小通道放在末维后会产生大量 Padding，不仅扩大物理存储量，还会让 DMA 搬运大量无效数据，使 Conv3D 同时出现显存占用和访存效率问题。

我在模型侧重新组织了 Conv3D 的物理数据布局，将卷积窗口相关维度组合为更适合硬件对齐的内维，并同步调整 Conv3D 输入处理逻辑和模型初始化阶段的权重布局。算子同事配合修改 Conv3D 内部计算实现，使 Kernel 能够按照新的布局读取和计算数据。

验证分为两个层级。第一层从模型中提取真实输入 Shape，构造 Conv3D 单例测试，与 CPU 参考实现进行正确性和性能对比，同时观察显存占用及更大输入下是否仍会出现 OOM。第二层回到完整模型，通过端到端 Profile 检查 Conv3D 热点占比和首 Token 延迟的变化，并完成模型输出的正确性回归。当前结果能够支持“该布局调整消除了已观察到的 OOM，并显著降低 Conv3D 开销和首 Token 延迟”；具体性能幅度仍需依据原始测试记录统一口径。

#### 个人职责边界

我负责问题复现、调用链和显存行为分析、根因假设验证、模型侧数据布局重构，以及模型初始化阶段的权重预排布。Conv3D Kernel 内部的计算和访存实现由算子同事负责。我参与了方案讨论、真实 Shape 提供和端到端验证，但不会将底层 Kernel 的实现工作表述为个人独立完成。

## 项目二：ECG 多模态模型部署与端到端性能优化

- **时间**：2025年11月 - 2025年12月
- **角色**：模型部署与性能优化负责人
- **技术栈**：`PyTorch`、`vLLM`、Python、自研算子库、模型服务环境

### 项目背景

客户 ECG 多模态模型需要在公司自研芯片上完成服务化部署。初始版本同时存在重复输出、环境兼容和端到端耗时过高的问题，模型性能受到矩阵计算、Tensor 扩展及框架调度等多处瓶颈影响。

### 职责

- 负责模型环境搭建、功能正确性验证、性能分析、优化方案推进和云服务交付。
- 协调框架与算子团队解决热点算子问题，并验证优化是否真正改善端到端延迟。

### 关键行动

1. **先解决正确性再优化性能**：复现并修复重复吐词问题，建立稳定输入与输出基线，避免在错误结果上进行无效调优。
2. **拆解端到端耗时**：通过 Profile 识别 Col-major Matmul、Tensor 扩展及其他热点路径，区分框架开销与算子耗时。
3. **实施针对性优化**：接入 Col-major Matmul，推动热点形状的算子优化，并调整模型和服务环境中的调用路径。
4. **持续回归与交付**：在每轮算子更新后复测精度和端到端耗时，完成部署环境整理并交由云服务团队上线。

### 量化结果

- 将单次推理耗时从 **40 秒以上降低至 10–15 秒**。
- 修复重复输出问题，完成模型服务化交付。

### 2026-09-02 口述基线（待核验）

> 本节记录一次无稿项目恢复结果，供后续核对代码、Profile 和 Benchmark 后持续修改，不替代上方已有的对外口径。客户对标平台、硬件型号、内部带宽、目标阈值和本次口述新增的性能数字，在披露范围与原始记录确认前不写入正式面试材料。

#### 当前叙述

这个项目来自医疗业务客户的模型部署需求。模型同时接收心电图图像和文本 Prompt，并生成供专业人员参考的分析结果。它由客户基于 Hugging Face `Transformers` 编写自定义 `forward`，并不是直接运行在标准 `vLLM` 模型执行链路中。项目复用了部分已经在其他推理链路中验证过的融合算子和权重处理能力，实际运行栈边界仍需结合代码进一步确认。

我负责模型的端到端适配，包括执行链路打通、精度对齐、性能分析和优化推进。项目的主要困难是，在目标硬件能力与客户参考平台存在差距的情况下，把端到端时延降低到验收范围内。

我首先使用 Profile 拆分端到端时间，并进行了三类优化：

1. **减少 Host 交互**：检查 Vision Encoder 结束后的 Host 侧 Metadata 准备，将不依赖中间计算结果的工作提前处理，缩短执行链路中的 Host 空洞。
2. **迁移融合算子**：模型主体仍包含常见语言模型结构，因此我将已经在其他推理链路中验证过的部分融合算子接入该模型，减少中间 Tensor 和额外调度开销。
3. **替换不适合小 Shape 的计算路径**：RoPE 系数准备阶段使用小 Shape `BMM` 计算外积。在该项目的低并发场景中，通用矩阵乘单元的调度成本较高。我将这一计算改写为广播逐元素乘法，并保持原有数学语义。

完成这些修改后，端到端时延已经明显下降，但仍有波动。第二轮 Profile 显示，Decode 阶段的 Attention 和 FFN 小批量矩阵乘仍占据主要耗时。我根据实际 Shape、数据类型和读写数据量进行 Roofline 估算。对 `[b, K] × [K, N]` 的矩阵乘，计算量为 `2bKN`，最低数据搬运量可以近似写成 `dtype_bytes × (bK + KN + bN)`；当 `b` 较小时，权重读取占主导，计算强度较低。该结果表明后续优化应该优先处理权重访存。

进一步分析表明，原有权重布局与 Kernel 的分块读取顺序不匹配。跨行读取相同列的数据时会降低有效带宽，但冲突所在的具体存储层级和地址映射仍需通过硬件资料或计数器确认。团队随后采用 blocked Col-major 权重布局：Tile 内部保持行优先，Tile 之间按照列优先顺序排列，使权重的物理排布更接近 Kernel 的实际读取顺序。

我在 `PyTorch` 框架侧定义了相应的 Tensor 扩展，并在模型加载权重时完成预排布，避免在每次推理期间重复转换。底层 Kernel 和硬件访存路径由算子与硬件同事协同调整。该方案只改变静态权重布局，没有扩展到激活输入和输出，因为激活布局由前后算子的接口共同决定，继续修改会扩大适配和回归范围。完成这些优化后，模型达到了客户的端到端时延目标；具体起止耗时和单项收益仍需根据原始记录统一。

#### 个人职责与协作边界

- **我负责**：端到端 Profile、热点 Shape 分析、Host 路径调整、小 Shape 计算重构、Roofline 初步推导、`PyTorch` Tensor 扩展、模型加载阶段的权重预排布，以及模型级精度和性能回归。

#### 当前叙述

`vLLM` 从 V0 演进到 V1 后，引入 Persistent Batch，并在输入准备中更系统地使用异步 H2D。以 Block Table 等输入元数据为例，框架可以提前发起 Host-to-Device 拷贝，使其与后续 CPU 输入准备或调度计算重叠。异步 H2D 并非 V1 首次引入，但 V1 的执行方式提高了 pinned Host Memory、异步 DMA、Stream Ordering 和 CPU/H2D Overlap 对后端完整性的要求。

在自研后端支持异步 H2D 后，客户现场低概率出现输出异常，包括 Think 标签不闭合、乱码、空回复和重复循环。现场同事收集了触发过异常的请求，我负责制定临时规避方案、重放请求、缩小问题范围，并继续推进框架侧根因分析和修复验证。

我按照精度问题的常规路径开展排查：

1. 固定采样随机性，将 Temperature 等参数调整为确定性配置。
2. 对同一输入重复执行，定位输出第一次发生分叉的 Token，避免被后续 KV Cache 传播的误差干扰。
3. 比较分叉位置的 Logits 和 Top-k 候选，判断是否只是边界接近造成的采样变化。
4. 沿模型执行路径 Dump 中间 Tensor，尝试定位最早出现数值差异的层或算子。

这次排查出现了明显的观察者效应：加入较多 Tensor Dump 后，异常不再出现。这个现象不能直接证明同步缺失，但说明执行时序可能影响复现。我随后将异步 H2D 单独切换为阻塞路径，并对现场请求重新执行，异常随之消失；调整其他执行配置没有形成同样稳定的控制效果。因此，现有实验能够把问题范围缩小到异步 H2D 相关路径，并支持关闭异步 H2D 作为客户侧临时规避方案，但尚不足以仅凭这一组实验确认具体竞态位置。

根据本轮口述，最终根因位于两阶段拷贝链路：后台任务先在 CPU 侧将原始 Tensor Padding 到 Staging Tensor，再向设备 Stream 提交异步 H2D。下游等待只覆盖了已经进入设备 Stream 的任务，没有覆盖 CPU Padding 完成和 H2D 提交这两个前置事件。等待发生得较早时，设备 Stream 可能因为队列中尚无任务而提前返回，随后下游便可能消费尚未完整写入的数据。完整依赖应当覆盖 `CPU Padding 完成 → H2D 提交 → 设备拷贝完成 → 下游消费`，不能只等待设备 Stream 当时已有的任务。

最终修复是在 CPU Padding 过程中，将 Padded Tensor 也纳入设备异步任务的统一标记与等待机制。这样，后续消费者执行同步时会同时考虑 CPU Padding、H2D 提交和设备拷贝，不会因为设备 Stream 中暂时没有任务而提前继续执行。

修复后，我使用现场收集的 168 条请求连续重放 5 轮，合计完成 840 次请求执行，未再观察到 Think 标签不闭合、乱码、空回复或重复循环。该结果支持问题已经在当前现场请求集和回归范围内解决。

其中一个代表性问题是多 Stream 通信没有产生预期收益，反而引入了较大的调度开销。原有实现将通信算子放到独立 Stream，希望通信能够与计算重叠。但在当时的目标后端和训练负载下，Profile 没有显示有效的计算与通信并行；与此同时，该运行时需要通过批量提交摊销算子启动成本。频繁切换 Stream 会拆分原本可以合并的提交批次，并增加 Event、Wait、跨流依赖和命令提交开销。

我通过端到端 Profile 检查执行时间线，观察到频繁的 Stream 切换。部分 Stream 只有 `Event Record`、`Stream Wait` 等同步操作，没有对应的有效计算或通信任务，时间线上还存在较多空白。这些现象说明多 Stream 调度可能是主要开销来源，后续的单 Stream 对照实验进一步支持了这一判断。

修复时，我增加了一个默认关闭多 Stream 通信的环境变量开关。开关关闭时，通信算子与对应计算依赖被放到同一执行 Stream，不再为通信创建额外的操作 Stream；需要保留原有行为时，可以显式开启多 Stream。修改同时涉及 `PyTorch` 通信适配层和自研通信库，因为通信库内部还会创建用于标记任务启动与完成的辅助 Stream，仅修改上层无法完整消除切换。

验证分为两个层级。第一层使用小范围测试检查算子提交情况：调整前，通信算子会打断计算 Stream 上正在积累的提交批次；调整后，计算与通信按照同一 Stream 顺序执行，提交批次不再被相同方式反复拆分。第二层回到端到端训练 Benchmark，比较相同负载下的训练耗时。当前口述能够支持“单 Stream 方案显著减少了该环境中的调度与启动开销”；具体起止耗时、正确性回归和适用边界仍需根据原始记录确认。
