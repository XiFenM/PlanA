# 代表项目档案

> 本文件用于沉淀面试项目故事。项目内容按“项目背景—职责—关键行动—量化结果—面试深挖点”组织；涉及性能数据时，仅保留已确认可以对外披露的口径。

## 项目一：多模态大模型推理框架适配与性能优化

- **时间**：2025年04月 - 2026年03月
- **角色**：核心开发工程师
- **技术栈**：`PyTorch`、`vLLM V0/V1`、Python、C/C++、自研算子库、自研通信库
- **涉及模型**：Qwen2.5/3-VL、Ernie4.5-VL、Qwen3-Omni

### 项目背景

公司自研加速芯片的软件生态仍在建设期，主流推理框架、模型结构与算子实现主要面向 CUDA 平台。多模态模型还会引入图像、视频和语音预处理、高维 Tensor、3D 位置编码、Vision Attention 及卷积算子，使框架兼容、数值精度、内存排布和端到端性能问题相互耦合。

### 职责

- 负责多模态模型在自研芯片上的 `vLLM` 端到端适配、精度对齐和性能优化。
- 维护模型执行层与 `PyTorch`、算子库之间的接口，推动框架特性和缺失算子落地。
- 通过跨平台基线、Profile、算子单测和 Trace 定位模型级瓶颈，并协调算子、运行时和硬件团队闭环。

### 关键行动

1. **打通模型执行链路**：梳理多模态输入从预处理、Embedding、Vision Encoder、位置编码到语言模型的执行路径，逐层补齐模型注册、配置解析、输入映射和设备算子支持，使图像、视频及语音链路能够在自研芯片上运行。
2. **统一多模态 RoPE 接口**：重构 Fused Rotary Embedding 调用方式，兼容文本 RoPE、视觉 M-RoPE 与音频一维 RoPE，减少模型间的重复适配逻辑，并为融合算子提供稳定接口。
3. **优化内存排布和矩阵计算**：在 `PyTorch` 与 `vLLM` 中接入多维 Col-major Matmul，处理高维 Tensor、前后置变形和临时 Tensor 生命周期问题，降低特殊硬件访存排布带来的额外开销。
4. **解决关键算子瓶颈**：围绕 Conv3d、Flash Paged Attention、Vision Attention、GELU、Scatter 和 Index 等算子建立模型形状单测；通过设备实现、CPU Fallback、精度对比和调度条件控制，在保证正确性的前提下逐步替换性能瓶颈。
5. **建立端到端诊断方法**：同时观察 Host 空洞、Kernel 时间、Tensor Layout、跨设备拷贝和通信行为，避免只根据单算子耗时判断瓶颈；对随机精度问题使用中间值 Dump、算子级复现与跨平台结果对齐。
6. **跨仓库交付**：在内部 `vLLM V0/V1`、`PyTorch` 和算子仓库间同步修改，补充 CI 用例、模型测试和技术文档，确保功能可持续维护。

### 量化结果

- 在 Qwen3-VL 链路完成 Conv3d 优化与模型侧验证，使首 Token 延迟下降 **40%**。
- 完成 Qwen2.5/3-VL、Ernie4.5-VL 与 Qwen3-Omni 的阶段性适配，覆盖图像、视频和语音等多模态输入。
- 形成可复用的多模态 RoPE、Col-major Matmul 和算子精度排查方法，降低后续同类模型的接入成本。

### 面试深挖点

- `vLLM` 的多模态输入如何从 Processor 进入 Model Runner，最终与文本 Token 合并？
- M-RoPE 与普通 RoPE 的位置索引和 Tensor Layout 有什么差异，为什么适合做融合？
- Col-major 布局为什么适合目标硬件？转换放在 Host 还是 Device，各自的收益和风险是什么？
- Conv3d 为什么会同时造成显存和性能问题？如何区分 Padding、访存、计算和调度开销？
- 多模态模型出现结果异常时，如何从最终输出逐步收敛到具体算子或数据路径？
- 为什么单并发优化有效，并不必然意味着高并发吞吐也同步改善？

## 项目二：ECG 多模态模型部署与端到端性能优化

- **时间**：2025年11月 - 2025年12月
- **角色**：模型部署与性能优化负责人
- **技术栈**：`PyTorch`、`vLLM`、Python、自研算子库、模型服务环境

### 项目背景

客户 ECG 多模态模型需要在公司自研芯片上完成服务化部署。初始版本同时存在重复输出、环境兼容和端到端耗时过高的问题，模型性能受到矩阵计算、Tensor 扩展及框架调度等多处瓶颈影响。

### 职责

- 负责模型环境搭建、功能正确性验证、性能分析、优化方案推进和云服务交付。
- 协调框架与算子团队解决热点算子问题，并验证优化是否真正改善端到端延迟。

### 关键行动

1. **先解决正确性再优化性能**：复现并修复重复吐词问题，建立稳定输入与输出基线，避免在错误结果上进行无效调优。
2. **拆解端到端耗时**：通过 Profile 识别 Col-major Matmul、Tensor 扩展及其他热点路径，区分框架开销与算子耗时。
3. **实施针对性优化**：接入 Col-major Matmul，推动热点形状的算子优化，并调整模型和服务环境中的调用路径。
4. **持续回归与交付**：在每轮算子更新后复测精度和端到端耗时，完成部署环境整理并交由云服务团队上线。

### 量化结果

- 将单次推理耗时从 **40 秒以上降低至 10–15 秒**。
- 修复重复输出问题，完成模型服务化交付。

### 面试深挖点

- 如何定义并稳定复现端到端延迟，怎样避免模型加载、预热和输入处理干扰结果？
- 为什么 Col-major Matmul 能改善该模型，如何判断布局转换成本没有抵消收益？
- Profile 中发现热点后，如何决定修改框架、调度算子还是开发专用 Kernel？
- 如何同时设计精度回归和性能回归，避免优化引入新的输出异常？
- 面对客户环境与研发环境不一致时，如何缩小问题范围并保证交付？

## 项目三：vLLM V1 异步拷贝低概率精度异常专项

- **时间**：2026年05月 - 至今
- **角色**：专项问题主要排查与框架侧开发
- **技术栈**：`vLLM V1`、`PyTorch`、C++ Runtime、H2D/D2D Copy、Stream、Replay 与 Trace 工具
- **当前状态**：已完成关键路径收敛，最终根因仍在闭环

### 项目背景

Qwen3-32B 在自研芯片上启用高等级异步拷贝后，会低概率出现标签不匹配、重复输出、异常截断及采样参数污染等问题；切换为阻塞拷贝后表现稳定。问题横跨 `vLLM` 输入准备、Sampling、Block Table、`PyTorch` 拷贝实现和底层 Runtime，具有随机、难复现且容易被同步操作掩盖的特点。

### 职责

- 负责推理链路异步拷贝点梳理、实验设计、诊断代码开发和结果归档。
- 在 `vLLM`、`PyTorch` 与 Runtime 之间建立证据链，排除无关假设并缩小高风险路径。
- 为最终修复设计端到端 Replay、微型测试和回归机制。

### 关键行动

1. **建立可信基线**：统一请求集、异常分类、终止原因和日志格式，区分固定 HTTP 错误、已知不稳定请求与真正由异步路径引入的异常。
2. **实现细粒度控制开关**：为输入、Sampling、Attention、KV Cache 和输出等路径增加分模块 Blocking/Async 控制，使单点隔离和组合实验可重复执行。
3. **分层拆解随机问题**：围绕 Sampling Metadata、Runner Inputs、Block Table 等高风险类别开展控制变量实验，并通过防御性检查提前捕获受污染 Tensor，避免非法采样参数进一步触发底层 Hang。
4. **追踪 Producer-Consumer 时序**：加入 Copy/Consumer Trace、Storage 与 Stream 关联、H2D/D2D 屏障、Hash 和双回读校验，验证 CPU Staging、设备写入可见性及下游消费时机。
5. **构造微型验证**：将正式链路中的 Copy、Reformat 和 Writer 行为抽取为压力测试与 Canary，区分专用 Kernel、目标 Storage 后续覆盖和 Runtime Completion 语义等假设。

### 阶段性结果

- 证明异常与异步数据路径显著相关，并将全链路随机问题收敛到少数高风险拷贝和运行时可见性路径。
- Sampling Metadata 改为阻塞拷贝后，采样参数越界及其引发的底层 Hang 消失；剩余输出异常仍需继续定位。
- 建立可复现、可逐点隔离的诊断体系，为后续底层修复和稳定回归提供基础。

### 面试深挖点

- 异步 H2D 为什么不仅涉及 Stream 同步，还涉及 Host Buffer 生命周期和 CPU Staging？
- 为什么增加回读或日志后问题可能消失？如何识别观察者效应？
- Event、Stream Sync、设备写入可见性和 Runtime Completion 之间是什么关系？
- 如何证明某个 Copy 点只是相关，而不是最终根因？
- 如何设计能长期进入 CI 的随机竞态回归测试？
- Workaround、最小修复和底层根因修复应如何划分验收标准？

## 备选项目：DeepSpeed、Megatron-LM 与通信后端适配

- **时间**：2024年06月 - 2024年08月
- **角色**：框架与通信适配开发
- **技术栈**：`PyTorch`、`DeepSpeed`、`Megatron-LM`、自研通信库、C++、Python

### 项目背景

自研加速芯片需要兼容主流分布式训练框架，但设备 Tensor 的 Padding、数据类型、流模型和集合通信接口与 CUDA/NCCL 存在差异，导致 ZeRO 与 Tensor Parallel 用例出现精度异常、卡死或接口缺失。

### 职责

- 推进 `DeepSpeed ZeRO-3` 与 `Megatron-LM Tensor Parallel` 测试适配。
- 定位框架调用、`PyTorch` 设备后端与通信库之间的语义差异。
- 将稳定用例和问题 Case 沉淀为单元测试与 CI。

### 关键行动

1. 将 ReduceScatter、AllGather、Broadcast 等真实框架调用抽取为独立测试，验证任意形状、数据类型和 Reduce Op。
2. 定位 Tensor Padding、切分规则、通信输入输出形状及多流同步导致的问题，并在框架或通信适配层修正。
3. 补齐 Pin Memory、AMP、Local Rank 和 Reduce Op 等框架能力，使 Tensor Parallel 主链路能够运行。
4. 将已验证的通信和分布式用例纳入 CI，降低后续代码演进造成的回归风险。

### 项目结果

- 打通 `Megatron-LM Tensor Parallel` 关键测试链路，并完成 `DeepSpeed ZeRO-3` 的阶段性兼容。
- 修复多类通信接口和数据类型问题，形成从分布式框架到通信 Kernel 的跨层调试方法。

### 面试深挖点

- ZeRO-3 在参数分片、Gather 和 ReduceScatter 阶段分别依赖哪些通信语义？
- Tensor Padding 为什么会影响集合通信的输入输出形状和正确性？
- Tensor Parallel 在 Attention 与 MLP 中如何切分，通信点分别在哪里？
- 自研通信库与 NCCL 的 Stream 语义不一致时，框架适配层应该如何处理？
- 如何把偶发 Hang 转化为稳定的最小复现和 CI 用例？
