## 备选项目：DeepSpeed、Megatron-LM 与通信后端适配

- **时间**：2024年06月 - 2024年08月
- **角色**：框架与通信适配开发
- **技术栈**：`PyTorch`、`DeepSpeed`、`Megatron-LM`、自研通信库、C++、Python

### 项目背景

自研加速芯片需要兼容主流分布式训练框架，但设备 Tensor 的 Padding、数据类型、流模型和集合通信接口与 CUDA/NCCL 存在差异，导致 ZeRO 与 Tensor Parallel 用例出现精度异常、卡死或接口缺失。

### 职责

- 推进 `DeepSpeed ZeRO-3` 与 `Megatron-LM Tensor Parallel` 测试适配。
- 定位框架调用、`PyTorch` 设备后端与通信库之间的语义差异。
- 将稳定用例和问题 Case 沉淀为单元测试与 CI。

### 关键行动

1. 将 ReduceScatter、AllGather、Broadcast 等真实框架调用抽取为独立测试，验证任意形状、数据类型和 Reduce Op。
2. 定位 Tensor Padding、切分规则、通信输入输出形状及多流同步导致的问题，并在框架或通信适配层修正。
3. 补齐 Pin Memory、AMP、Local Rank 和 Reduce Op 等框架能力，使 Tensor Parallel 主链路能够运行。
4. 将已验证的通信和分布式用例纳入 CI，降低后续代码演进造成的回归风险。

### 项目结果

- 打通 `Megatron-LM Tensor Parallel` 关键测试链路，并完成 `DeepSpeed ZeRO-3` 的阶段性兼容。
- 修复多类通信接口和数据类型问题，形成从分布式框架到通信 Kernel 的跨层调试方法。

### 面试深挖点

- ZeRO-3 在参数分片、Gather 和 ReduceScatter 阶段分别依赖哪些通信语义？
- Tensor Padding 为什么会影响集合通信的输入输出形状和正确性？
- Tensor Parallel 在 Attention 与 MLP 中如何切分，通信点分别在哪里？
- 自研通信库与 NCCL 的 Stream 语义不一致时，框架适配层应该如何处理？
- 如何把偶发 Hang 转化为稳定的最小复现和 CI 用例？

#### 当前叙述

这个项目处于公司训练框架适配的早期阶段，目标是在自研芯片上支持多卡并行训练，并完成 Llama 2 13B 的 SFT 训练，使训练损失与 CUDA 参考平台对齐。项目早期尝试使用 DeepSpeed，后续转向 Megatron-LM；两个阶段分别采用了哪些并行配置，以及最终交付以哪套框架为准，仍需结合项目记录确认。

我的工作主要集中在训练框架与自研通信后端之间的适配，可以分为三个阶段：

1. **并行策略与通信单元测试**：我先从并行相关测试入手，了解 DP、TP、PP、SP、CP 和 EP 的基本通信语义，并检查通信组创建、Rank 映射和集合通信调用。这个阶段修复过通信算子调用中的分组问题，但实际覆盖了哪些并行策略、哪些问题进入正式交付，还需要进一步核对。
2. **端到端训练精度排查**：通信基础能力稳定后，我开始调试完整训练链路。Python 前向过程会动态建立 Autograd 计算图，`.backward()` 再由 Autograd Engine 调度反向节点。反向计算、集合通信和参数更新形成的链路比显式前向过程更长，数值偏差也会继续传播。我当时主要使用算子调用日志和二分方法缩小范围，定位可能引入损失偏差的算子或通信阶段。
3. **训练性能优化**：端到端训练能够执行后，我根据 Profile 分析通信及其调度开销，并围绕 Stream 使用方式优化训练效率。

其中一个代表性问题是多 Stream 通信没有产生预期收益，反而引入了较大的调度开销。原有实现将通信算子放到独立 Stream，希望通信能够与计算重叠。但在当时的目标后端和训练负载下，Profile 没有显示有效的计算与通信并行；与此同时，该运行时需要通过批量提交摊销算子启动成本。频繁切换 Stream 会拆分原本可以合并的提交批次，并增加 Event、Wait、跨流依赖和命令提交开销。

我通过端到端 Profile 检查执行时间线，观察到频繁的 Stream 切换。部分 Stream 只有 `Event Record`、`Stream Wait` 等同步操作，没有对应的有效计算或通信任务，时间线上还存在较多空白。这些现象说明多 Stream 调度可能是主要开销来源，后续的单 Stream 对照实验进一步支持了这一判断。

修复时，我增加了一个默认关闭多 Stream 通信的环境变量开关。开关关闭时，通信算子与对应计算依赖被放到同一执行 Stream，不再为通信创建额外的操作 Stream；需要保留原有行为时，可以显式开启多 Stream。修改同时涉及 `PyTorch` 通信适配层和自研通信库，因为通信库内部还会创建用于标记任务启动与完成的辅助 Stream，仅修改上层无法完整消除切换。

验证分为两个层级。第一层使用小范围测试检查算子提交情况：调整前，通信算子会打断计算 Stream 上正在积累的提交批次；调整后，计算与通信按照同一 Stream 顺序执行，提交批次不再被相同方式反复拆分。第二层回到端到端训练 Benchmark，比较相同负载下的训练耗时。当前口述能够支持“单 Stream 方案显著减少了该环境中的调度与启动开销”；具体起止耗时、正确性回归和适用边界仍需根据原始记录确认。
