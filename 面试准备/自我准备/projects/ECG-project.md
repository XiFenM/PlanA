## 项目二：ECG 多模态模型部署与端到端性能优化

- **时间**：2025年11月 - 2025年12月
- **角色**：模型部署与性能优化负责人
- **技术栈**：`PyTorch`、`vLLM`、Python、自研算子库、模型服务环境

### 项目背景

客户 ECG 多模态模型需要在公司自研芯片上完成服务化部署。初始版本同时存在重复输出、环境兼容和端到端耗时过高的问题，模型性能受到矩阵计算、Tensor 扩展及框架调度等多处瓶颈影响。

### 职责

- 负责模型环境搭建、功能正确性验证、性能分析、优化方案推进和云服务交付。
- 协调框架与算子团队解决热点算子问题，并验证优化是否真正改善端到端延迟。

### 关键行动

1. **先解决正确性再优化性能**：复现并修复重复吐词问题，建立稳定输入与输出基线，避免在错误结果上进行无效调优。
2. **拆解端到端耗时**：通过 Profile 识别 Col-major Matmul、Tensor 扩展及其他热点路径，区分框架开销与算子耗时。
3. **实施针对性优化**：接入 Col-major Matmul，推动热点形状的算子优化，并调整模型和服务环境中的调用路径。
4. **持续回归与交付**：在每轮算子更新后复测精度和端到端耗时，完成部署环境整理并交由云服务团队上线。

### 量化结果

- 将单次推理耗时从 **40 秒以上降低至 10–15 秒**。
- 修复重复输出问题，完成模型服务化交付。

### 面试深挖点

- 如何定义并稳定复现端到端延迟，怎样避免模型加载、预热和输入处理干扰结果？
- 为什么 Col-major Matmul 能改善该模型，如何判断布局转换成本没有抵消收益？
- Profile 中发现热点后，如何决定修改框架、调度算子还是开发专用 Kernel？
- 如何同时设计精度回归和性能回归，避免优化引入新的输出异常？
- 面对客户环境与研发环境不一致时，如何缩小问题范围并保证交付？

#### 当前叙述

这个项目来自医疗业务客户的模型部署需求。模型同时接收心电图图像和文本 Prompt，并生成供专业人员参考的分析结果。它由客户基于 Hugging Face `Transformers` 编写自定义 `forward`，并不是直接运行在标准 `vLLM` 模型执行链路中。项目复用了部分已经在其他推理链路中验证过的融合算子和权重处理能力，实际运行栈边界仍需结合代码进一步确认。

我负责模型的端到端适配，包括执行链路打通、精度对齐、性能分析和优化推进。项目的主要困难是，在目标硬件能力与客户参考平台存在差距的情况下，把端到端时延降低到验收范围内。

我首先使用 Profile 拆分端到端时间，并进行了三类优化：

1. **减少 Host 交互**：检查 Vision Encoder 结束后的 Host 侧 Metadata 准备，将不依赖中间计算结果的工作提前处理，缩短执行链路中的 Host 空洞。
2. **迁移融合算子**：模型主体仍包含常见语言模型结构，因此我将已经在其他推理链路中验证过的部分融合算子接入该模型，减少中间 Tensor 和额外调度开销。
3. **替换不适合小 Shape 的计算路径**：RoPE 系数准备阶段使用小 Shape `BMM` 计算外积。在该项目的低并发场景中，通用矩阵乘单元的调度成本较高。我将这一计算改写为广播逐元素乘法，并保持原有数学语义。

完成这些修改后，端到端时延已经明显下降，但仍有波动。第二轮 Profile 显示，Decode 阶段的 Attention 和 FFN 小批量矩阵乘仍占据主要耗时。我根据实际 Shape、数据类型和读写数据量进行 Roofline 估算。对 `[b, K] × [K, N]` 的矩阵乘，计算量为 `2bKN`，最低数据搬运量可以近似写成 `dtype_bytes × (bK + KN + bN)`；当 `b` 较小时，权重读取占主导，计算强度较低。该结果表明后续优化应该优先处理权重访存。

进一步分析表明，原有权重布局与 Kernel 的分块读取顺序不匹配。跨行读取相同列的数据时会降低有效带宽，但冲突所在的具体存储层级和地址映射仍需通过硬件资料或计数器确认。团队随后采用 blocked Col-major 权重布局：Tile 内部保持行优先，Tile 之间按照列优先顺序排列，使权重的物理排布更接近 Kernel 的实际读取顺序。

我在 `PyTorch` 框架侧定义了相应的 Tensor 扩展，并在模型加载权重时完成预排布，避免在每次推理期间重复转换。底层 Kernel 和硬件访存路径由算子与硬件同事协同调整。该方案只改变静态权重布局，没有扩展到激活输入和输出，因为激活布局由前后算子的接口共同决定，继续修改会扩大适配和回归范围。ECG 模型中，预排布写在 `Transformers` 模型加载后的处理阶段；之后这项权重重排布技术也移植到了主推的 `vLLM` 中。完成这些优化后，端到端时延从最初的 30–40 秒，经前三项常规优化降到 20 秒左右，再经权重预排布降到 20 秒以内，达到客户的验收目标；三项常规优化的单项收益没有分别测量。

#### 测量条件（2026-09-29 确认）

- **运行栈**：客户基于 `Transformers` 的自定义模型；所报时延均在该运行栈上测得。
- **计时起止**：从请求发出到完整输出结束，包含图像预处理。
- **输入**：心电图图像约 800×500 像素；prompt 为一句要求模型分析的话，长度 16。
- **输出**：生成上限 1024 token，多次生成的平均长度约 700–800 token。
- **并发**：单请求（2026-09-02 口述：绝大多数场景只有一个请求）。
- **统计**：优化前后都测 10 次取平均，都包含首次运行；自研芯片上没有预热编译，算子库预先编译为 so 文件；初始化操作在发出请求、开始计时之前完成，因此首次运行既不含编译开销，也不含初始化开销。
