# 项目二：ECG 多模态模型部署与端到端性能优化

> 本文件为本项目的主要事实文档。2026-11-09 将原 ECG Layout Case Card 的有效内容合入[核心案例、验证证据与边界](#ecg-layout-case-card-v1)：运行栈与性能采用 2026-09-29 本人确认，布局调用范围与正确性采用 2026-11-01 补充；固定 512 bytes 布局块、DMA 通道映射与 bank conflict 根因采用 [2026-11-16 本人补充](#ecg-layout-bank-confirmed-20261116)。本人明确说明根因已由硬件同事确认；原始代码、Profile、硬件记录和 Benchmark 未在本次更新中独立复验。

## 项目概览

- **时间**：2025年11月 - 2025年12月
- **角色**：模型部署与性能优化负责人
- **技术栈**：客户基于 `Transformers` 的自定义模型、`PyTorch`、Python、自研算子库、模型服务环境；权重预排布技术后来移植到 `vLLM`，下述端到端秒数属于原 Transformers 栈。
- **当前状态**：已完成客户模型适配和云服务交付；具体版本、回归覆盖及部分排障细节仍待补录。

### 项目背景

客户 ECG 多模态模型需要在公司自研芯片上完成服务化部署。初始版本存在环境兼容和端到端耗时过高等问题，性能受到 Host 准备、小 Shape 计算及权重访存等多处影响。旧档案还记录了重复输出问题已修复，其具体根因、修复方法与对应版本尚未恢复。

### 职责

- 负责模型环境搭建、功能正确性验证、性能分析、优化方案推进和云服务交付。
- 协调框架与算子团队解决热点算子问题，并验证优化是否真正改善端到端延迟。

### 关键行动

从 Host 交互、小 Shape 计算和融合路径优化，推进到加载期静态权重预排布，再完成同芯片新旧布局及模型级回归。具体实现与个人分工见[核心案例 F3–F5](#ecg-layout-case-card-v1)。

### 量化结果

当前确认的端到端口径为 **30–40 秒 → 约 20 秒 → 20 秒以内**，分别对应初始版本、常规优化后和权重预排布后。完整工作负载与计时条件见下方 F2，阶段归因、旧数字冲突和限制见 F6。

### 面试深挖点

- 如何定义并稳定复现端到端延迟，怎样避免模型加载、预热和输入处理干扰结果？
- 为什么 Col-major Matmul 能改善该模型，如何判断布局转换成本没有抵消收益？
- Profile 中发现热点后，如何决定修改框架、调度算子还是开发专用 Kernel？
- 如何同时设计精度回归和性能回归，避免优化引入新的输出异常？
- 面对客户环境与研发环境不一致时，如何缩小问题范围并保证交付？

### F1：主张与适用范围

我负责一个 ECG 多模态模型在自研芯片上的端到端适配、精度对齐和性能优化。模型接收心电图图像与文本指令，基于客户使用 `Transformers` 编写的自定义 `forward` 执行。在完成 Host 路径、小 Shape 计算与融合算子等优化后，我继续根据 Profile 和低批量矩阵乘的 Roofline 估算，与算子同事共同调整静态权重布局。

我在框架侧定义了相应的 Tensor 扩展，在模型加载后的处理阶段完成 blocked Col-major 权重预排布，并负责模型级回归。底层 Kernel 访存实现由算子与硬件同事协同处理。项目端到端时延由最初约 30–40 秒，经常规优化降到约 20 秒，再经权重预排布降至 20 秒以内。以下按这些阶段说明依据，不将全部收益归给布局修改。

### F3：从热点判断到布局方案

第一轮优化后，第二轮 Profile 仍显示小批量矩阵乘占据主要耗时。我结合实际 Shape、数据类型与读写数据量进行 Roofline 初步估算，判断后续应优先检查权重访存。

对 `[b,K] × [K,N]` 的矩阵乘，计算量可按 `F=2bKN` 估算。若输入与权重各从所选存储层读取一次、输出写入一次，流量模型为 `Q_min=s_A·bK+s_B·KN+s_C·bN`，其中 `s_A、s_B、s_C` 是对应元素的存储字节数。低批量下，权重项可能占据大部分流量。这是用于复核判断的方法表达；本轮读取示例的权重类型已明确为 BF16，其他热点配置、实际读取次数、缓存复用与实测带宽仍待补齐，不用公开模型尺寸或假设带宽填充项目数据。

#### F3.1 固定布局块与算子计算块

2026-11-16 本人补充并明确：项目中的 bank conflict 根因已经由硬件同事确认。这里沿用硬件团队的 bank 通道术语，指 **HBM → 片上内存的 DMA 读取路径**。本轮给出的硬件规则与布局定义如下：

| 对象 | 已确认的规则或本轮示例 |
| --- | --- |
| Tensor 数据对齐 | 强制按 512 bytes 对齐 |
| DMA 最小读取粒度 | 从 HBM 读取 Tensor 的最小粒度为 512 bytes |
| 一条 DMA 的并行读取能力 | 最多同时读取八个 512 bytes 块，对应八个 bank 通道 |
| blocked Col-major 的布局块 | 固定为 512 bytes；块内保持行优先，块之间按列优先排列 |
| 本轮权重示例 | BF16 `[4096,4096]`；每个元素 2 bytes，每行 8192 bytes，包含 16 个 512 bytes 布局块 |
| 本轮算子计算块示例 | `[256,256]`；每行 256 个 BF16 元素恰好是一个 512 bytes 布局块，整个计算块为 128 KiB |

**固定的是 512 bytes 布局块，不是 MatMul 算子的计算 Tile。** 以前“Tile 内行优先、Tile 间列优先、Tile 大小不变”的写法混淆了这两个层次，改为上述定义。`[256,256]` 是本人本轮用于解释读取方式的计算块，不据此认定所有 Kernel 配置都使用同样大小。

#### F3.2 普通行优先为什么集中到同一 bank

只看示例权重左上角的 `[256,256]` 计算块。每条 DMA 计划读取八行，每行 256 个 BF16 元素，即八个 512 bytes 块。假设第一个块对应 bank 0，普通行优先下，相邻行的起始地址相差：

```text
行间隔 = stride(0) × 元素字节数 = 4096 × 2 = 8192 bytes
八个 bank 的块级映射周期 = 8 × 512 = 4096 bytes
8192 % 4096 = 0
```

按本人给出的通道映射，相邻行没有前进到下一个 bank，而是回到相同的 bank。这个计算块的 256 个行片都落到 bank 0，单条 DMA 的八个读取目标也争用同一通道，无法利用其八通道并行读取能力。这里描述的是该计算块的跨行读取；换到其他列块时，对应的 bank 编号可能改变，不能把它扩写成整个权重矩阵的所有访问都只经过 bank 0。

#### F3.3 512 bytes 块级列优先怎样改变访问

将每行划分成 16 个 512 bytes 布局块后，先依次存放所有行的第 0 个布局块，再存放所有行的第 1 个布局块，依此类推。每个 512 bytes 块内部的元素顺序不变。这样，同一个块列中相邻行的物理地址只相差 512 bytes，八行对应的八个块就依次分布到 bank 0–7。

以下表格给出左上角计算块首八行的读取目标。地址均相对于权重起始位置，单位为 bytes，并沿用首块对应 bank 0 的假设：

| 逻辑行 | 普通行优先偏移 | 普通布局 bank | blocked Col-major 偏移 | 预排布后 bank |
| --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 0 | 0 |
| 1 | 8192 | 0 | 512 | 1 |
| 2 | 16384 | 0 | 1024 | 2 |
| 3 | 24576 | 0 | 1536 | 3 |
| 4 | 32768 | 0 | 2048 | 4 |
| 5 | 40960 | 0 | 2560 | 5 |
| 6 | 49152 | 0 | 3072 | 6 |
| 7 | 57344 | 0 | 3584 | 7 |

按这个布局定义，可以把本例无尾部补齐的地址关系展开如下。令 `r、c` 是权重的逻辑行、列索引，`j=c//256` 是所在块列，`e=c%256` 是 512 bytes 块内的元素偏移：

```text
普通布局块号 = 16*r + j
预排布块号   = 4096*j + r

普通布局字节偏移 = 8192*r + 512*j + 2*e
预排布字节偏移   = 512*(4096*j + r) + 2*e

bank 编号 = 布局块号 % 8    # 本例首块从 bank 0 开始
```

这是根据本人提供的布局和通道规则展开的地址模型，不是对实际 Kernel 代码的反向还原。对左上角 `[256,256]` 计算块，预排布后 256 个布局块在八个通道上各分布 32 个；每组八行都可以使用不同通道，改善本次确认的同 bank 争用及供数效率。数据仍按原来的逻辑权重参与矩阵乘，消费 Kernel 必须遵守新的物理映射。

#### F3.4 根因确认与性能边界

当前可以明确表述：**原行优先布局的跨行 DMA 读取导致 bank 通道冲突，根因已由硬件同事确认；512 bytes 块级列优先预排布改善了这个读取模式。** 不再把固定粒度、冲突层级或 bank conflict 根因列为尚未确认。

本人未提供实际带宽数据。本轮仅复核了给定地址模型的算术与通道分布，没有新增实机测试。因此，不报告实测带宽或带宽利用率，不把八个通道可同时参与换算成固定八倍加速，也不声称所有访存限制都已消除。实际实现的布局标记、调度与缓存行为，以及完整 Kernel 配置和回归覆盖，仍按已有记录继续核对。

### F4：修改位置与个人职责

我在 `PyTorch` 框架侧定义相应的 Tensor 扩展，并在 `Transformers` 模型加载权重后的处理阶段完成预排布。转换完成后不再保留原布局权重，相关层的 prefill 和 decode 都使用预排布权重，后续调用复用这一表示。消费该权重的算子需要遵守相同的布局约定；实际布局标记与 Dispatch 细节仍待核。

这次方案只调整静态权重，没有同时改变激活输入和输出。激活的布局涉及前后算子的接口，继续调整会扩大适配与回归范围。权重预排布技术后来也移植到 `vLLM`，但本节的端到端秒数仍对应 ECG 的 `Transformers` 运行栈。

| 职责 | 已确认工作 |
|---|---|
| 我负责 | 端到端 Profile、热点 Shape 分析、Host 路径调整、小 Shape 计算重构、Roofline 初步估算、Tensor 扩展、加载期权重预排布，以及模型级精度和性能回归 |
| 我与同事共同完成 | 收敛访存瓶颈、选择 blocked Col-major 方向，评估只调整静态权重的工程边界 |

这项预排布覆盖模型中所有使用静态参数权重的矩阵乘，例如各线性层；QKᵀ、注意力概率乘 V 等动态矩阵乘不在该范围内。

### F5：正确性验证与回归

我同时进行了 MatMul 算子输出的数值级对照和模型端到端回归。在相同参数与输入条件下，我比较自研芯片上的预排布 MatMul 与普通布局 MatMul，输出逐元素数值相等。模型端到端比较中，logits 与修改前逐元素数值相等，输出 token 一致。这些是本次共建补充的项目口述结果。

| 验证层级 | 已确认的比较内容与结果 | 保留的边界 |
|---|---|---|
| MatMul 算子 | 预排布与普通布局两条路径均在自研芯片上运行；相同参数与输入下，输出逐元素数值相等 | 版本、比较函数与原始用例清单待核；F3 的 BF16 读取示例不替代数值回归覆盖记录 |
| 模型端到端 | logits 与修改前逐元素数值相等，输出 token 一致 | 输入样本、采样配置与回归范围待核 |

这组逐元素相等的对照没有使用 CPU 结果作为参考。跨 CPU 的结果比较采用容差标准；具体 CPU 验证记录与容差尚未列出，不能将两种比较口径混写。

本次明确的固定重排粒度是 512 bytes 布局块。逐元素相等记录的是同一自研芯片新旧布局的实际对照结果；该结论限定在已执行的测试范围内，具体实现与原始覆盖记录仍待核验，不外推到不同计算路径或所有输入。

### 当前叙述

这个项目来自医疗业务客户的模型部署需求。模型同时接收心电图图像和文本 Prompt，并生成供专业人员参考的分析结果。它由客户基于 Hugging Face `Transformers` 编写自定义 `forward`，并不是直接运行在标准 `vLLM` 模型执行链路中。项目复用了部分已经在其他推理链路中验证过的融合算子和权重处理能力，实际运行栈边界仍需结合代码进一步确认。

我负责模型的端到端适配，包括执行链路打通、精度对齐、性能分析和优化推进。项目的主要困难是，在目标硬件能力与客户参考平台存在差距的情况下，把端到端时延降低到验收范围内。

我首先使用 Profile 拆分端到端时间，并进行了三类优化：

1. **减少 Host 交互**：检查 Vision Encoder 结束后的 Host 侧 Metadata 准备，将不依赖中间计算结果的工作提前处理，缩短执行链路中的 Host 空洞。
2. **迁移融合算子**：模型主体仍包含常见语言模型结构，因此我将已经在其他推理链路中验证过的部分融合算子接入该模型，减少中间 Tensor 和额外调度开销。
3. **替换不适合小 Shape 的计算路径**：RoPE 系数准备阶段使用小 Shape `BMM` 计算外积。在该项目的低并发场景中，通用矩阵乘单元的调度成本较高。我将这一计算改写为广播逐元素乘法，并保持原有数学语义。

完成这些修改后，端到端时延已经明显下降，但仍有波动。第二轮 Profile 显示，Decode 阶段的 Attention 和 FFN 小批量矩阵乘仍占据主要耗时。我根据实际 Shape、数据类型和读写数据量进行 Roofline 估算。对 `[b, K] × [K, N]` 的矩阵乘，计算量为 `2bKN`，最低数据搬运量可以近似写成 `dtype_bytes × (bK + KN + bN)`；当 `b` 较小时，权重读取占主导，计算强度较低。该结果表明后续优化应该优先处理权重访存。

进一步分析将问题定位到原有权重布局与 Kernel 的跨行 DMA 读取不匹配。2026-11-16 本人补充明确：该路径的 bank conflict 已由硬件同事确认，冲突发生在 HBM 向片上内存供数时。团队采用的 blocked Col-major 以固定 512 bytes 为布局块，块内行优先、块间列优先，使同一块列中相邻行的读取分布到八个 bank 通道。这一固定布局粒度与算子的计算 Tile 分开描述；完整地址示例与性能边界见 [F3](#ecg-layout-bank-confirmed-20261116)。

我在 `PyTorch` 框架侧定义了相应的 Tensor 扩展，并在模型加载权重时完成预排布，避免在每次推理期间重复转换。底层 Kernel 和硬件访存路径由算子与硬件同事协同调整。该方案只改变静态权重布局，没有扩展到激活输入和输出，因为激活布局由前后算子的接口共同决定，继续修改会扩大适配和回归范围。ECG 模型中，预排布写在 `Transformers` 模型加载后的处理阶段；之后这项权重重排布技术也移植到了主推的 `vLLM` 中。完成这些优化后，端到端时延从最初的 30–40 秒，经前三项常规优化降到 20 秒左右，再经权重预排布降到 20 秒以内，达到客户的验收目标；三项常规优化的单项收益没有分别测量。

### 测量条件（2026-09-29 确认）

- **运行栈**：客户基于 `Transformers` 的自定义模型；所报时延均在该运行栈上测得。
- **计时起止**：从请求发出到完整输出结束，包含图像预处理。
- **输入**：心电图图像约 800×500 像素；prompt 为一句要求模型分析的话，长度 16。
- **输出**：生成上限 1024 token，多次生成的平均长度约 700–800 token。
- **并发**：单请求（2026-09-02 口述：绝大多数场景只有一个请求）。
- **统计**：优化前后都测 10 次取平均，都包含首次运行；自研芯片上没有预热编译，算子库预先编译为 so 文件；初始化操作在发出请求、开始计时之前完成，因此首次运行既不含编译开销，也不含初始化开销。
