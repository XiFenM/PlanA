- **技术栈**：
  - 推理框架：`vLLM` v0.28.1rc0，以及自研 AI 加速芯片的 vLLM 硬件插件（OOT platform + monkey-patch 体系）
  - 自研芯片版 `PyTorch`（aten 后端）；编程语言为 Python 和 C++

- **涉及模型**：GLM-5.3-Flash（公开配置）
  - 规模：总参数约 321B，激活参数约 18B，上下文长度 1M tokens
  - **注意力**：混合结构，共 45 层，排布为 `[KDA×3 + DSA]×11 + KDA`
    - 34 层 KDA（Kimi Delta Attention）：线性注意力，每个请求带 conv state 和 recurrent state
    - 11 层 KPool-DSA：池化索引器 + NoPE 稀疏 MLA，latent 512 维，`qk_rope_head_dim=0`，TopK 为 2048 个 token 外加尾池 token
  - **MoE**：后 42 层为 MoE，288 个路由专家中选 Top-8，另有 1 个共享专家；激活函数是带 clamp 的 SwiGLU（`swiglu_limit=10`）
  - **特殊层**：每层都有 4 路 mHC 残差（含 20 轮 Sinkhorn）；另有多模态视觉塔和 1 层 MTP
  - 部署权重：AWQ 4-bit 混合量化版（约 184 GB），BF16 激活，8 卡 TP=8

### 项目背景

- **为什么适配**：GLM-5.3-Flash 是新发布的开源 MoE 大模型，需要在自研 AI 加速芯片上提供推理服务。【待补充：业务或客户需求、时间节点（脱敏后）】
- **上游支持状况**：上游 vLLM 对该模型的支持还在 PR 阶段，实现依赖 NVIDIA 的 Triton、TileLang 和 `torch.compile`，这些在自研芯片上都不能用。
- **需要框架新增支持的结构**：
  1. **KDA 线性注意力**：短卷积和递推状态都要做状态缓存；prefill 和 decode 路径不同；需要复用 vLLM 的 Mamba 类状态管理。
  2. **KPool-DSA 稀疏注意力**：每 4 个 token 压缩成一个池化 key，在池级别打分取 TopK，再展开成 token 下标；还要维护尾池环形缓存。
  3. **NoPE 稀疏 MLA**：芯片已有的 MLA 算子按 576 维（512+64）实现，这个模型需要 512 维、不带 RoPE 的版本。
  4. **mHC 四路残差**：没有现成的芯片实现。
  5. **MoE**：需要支持 SwiGLU clamp，以及 AWQ 权重在芯片上的布局。
  6. **混合 KV cache**：MLA 页、KPool 池页、尾池页、KDA 状态页同时存在；平台固定 `block_size=256`，上游的共享页假设在这里不成立。

### 关键行动

1. **框架接入**
   - **做了什么**：
     - 在插件中新增 KDA、KPool indexer、mHC、512 维 NoPE 稀疏 MLA 的 PyTorch native 实现，用 monkey-patch 替换上游依赖 Triton 的路径。
     - 重新绑定 GLM5 的 MLA 模块，补齐权重打包映射：gate_up、fused_qkv_a、wk_weights、in_proj_qkvbfg_a。
     - 写静态审计脚本，只读 safetensors 头信息，确认 111,346 个权重 key 全部被映射覆盖。
   - **代表性改动 ①：混合 KV cache 分配（两次 OOM）**
     - **问题**：
       - 上游把 34 层 KDA 合成一个组，并假设 KDA 状态页能放进 MLA 页。TP=8 时 KDA 页约 0.518 MiB，MLA 页只有 0.25 MiB，假设不成立。
       - 插件实际是按层独立分配，于是 `num_blocks` 被高估约 6.5 倍，第一次 OOM。
     - **改动**：
       - 在 KV cache 分组入口把 KDA 拆成每层一个独立 spec，按真实页大小计费。
       - 解决第一次 OOM 后仍然 OOM：定位到平台层为共享页布局做的 Mamba 页 padding（542,720 B 被补到 786,432 B，约浪费 5.7 GiB），改为跳过这一步。
     - **验证**：
       - CPU 单测复现“分组 → 核算 → 分配”三者一致。
       - 真机上 KV cache 从 45,409 tokens 提升到 148,762 tokens，不再 OOM。
   - **代表性改动 ②：Mamba 状态拆池**
     - **问题**：conv 和 recurrent 两种状态打包在同一个字节页里，切出来的是非连续 view。芯片后端碰到这类张量会退化成 host 逐元素搬运，`index_select`、`index_copy_`、conv 算子都慢了 1000 到 8000 倍。
     - **改动**：
       - 新增状态池容器，给每种状态分配独立的连续池。
       - 总字节数和 block id 语义不变，保持 512B 对齐，保留开关可以回退。
       - 同步适配 KV 清零、runner 绑定和状态迁移。
     - **验证**：
       - 21 例单测。
       - 真机上用同一 prompt 对比，prefill 和 decode 的单步 host 耗时分别降低约 31 倍和约 46 倍。
   - **联调中修掉的其他阻断问题**（约 15 项），例如：
     - 视觉塔 RMSNorm 走到了 Triton 路径
     - AWQ MoE 的 qzeros 需要 colpack 布局
     - KV manager 返回契约不一致、缺参数
     - 芯片不支持 `searchsorted` 和 `uint64`
     - align 模式下跨块状态迁移依赖 Triton kernel，改为 eager 兜底
   - **融合算子**：
     - 需求梳理：按模板写了 18 份算子需求；以 aten 注册表为准，在真机上逐条核查已有算子能否覆盖，分成“新增 / 扩展 / 修复 / 复用”四类，最终提交 12 条。
     - 验收：实测交付的 KDA 算子，定位到几个缺陷：
       - 长序列（N≥3072）卡死设备
       - wrapper 每次都搬运整个状态池，比原实现慢约 110 倍
       - kernel 不读 stride
       - aten 侧 scalar 参数打包错误，导致输出恒为 0
     - 接入：修复后接入 KDA 短卷积 prefill/update、KDA recurrent decode、KDA gated RMSNorm、NoPE MLA cache 写入、mHC pre/post、KV 整页清零等 8 个算子，每个都保留开关，可回退到 native。
2. **精度对齐**
   - **已做（算子级）**：
     - 参考：以 HF Transformers 的 GLM5Next 实现作为公式 golden，用 CPU FP32 参考实现和插件 native 实现做对照。
     - 结果：
       - KDA conv 和 decode 的 state 逐位一致，decode 输出误差不超过 1 个 bf16 ULP
       - KV 清零、MLA cache 写入逐字节一致
       - mHC 融合算子与 native 对照，误差不超过 6.4e-5
     - 修正了两处语义问题：
       - KPool 打分必须是“逐 head 点积 → ReLU → 按 head 加权”，与现有 MQA 算子的“先加权再点积”不等价
       - 稀疏 MLA 的 scale 必须保持 `1/sqrt(256)`
     - 全量回归测试约 292 例通过。
   - **已知并接受的偏差**：第一阶段 MoE router 用 BF16 logits（原模型是 FP32），可能改变临界专家的 Top-8 选择。
   - **【待补充】端到端精度对齐**：需要确定参考平台（如 GPU vLLM 或 HF）、对比方法（greedy token 一致率、logits 误差或下游评测集）、误差指标和容差、覆盖的输入，以及定位到的偏差来源。
3. **性能优化**
   - **方法**：
     - 用 py-spy 采样、vLLM torch profiler 和芯片官方 profiler 做 step 级归因。
     - 发现 trace 里自定义算子的 `dur` 其实是异步队列的排空时间，不能用来归因；改为按 host↔device 往返事件计数来归因。
   - **瓶颈与对应动作**：
     - ① 非连续状态页导致 host 逐元素搬运 → 拆池（见上）。
     - ② mHC 的 torch 回退占 decode 主线程约 52% → 把 mHC pre/post 融合算子接入插件（kernel 由算子组提供）。
     - ③ 发现 mHC post 因为形状判断错误一直回退到 native，修掉判断；同时修掉测试的“假绿”（两边都回退时对比也能通过），改为计数断言 kernel 确实被调用。
     - ④ 删掉 indexer 里强制 D2H 的 `torch.equal` 校验，这部分约占 decode 时间的 12%。
     - ⑤ 稀疏 MLA 索引转换：把 `div(floor)` 加二维高级索引改为 `//` 加逐行 `gather`。
     - ⑥ KDA 的静态参数改在加载期预物化，decode 每步少 68 次拷贝。
   - **【待补充】后续工作**：
     - 接入其余融合算子：KDA 状态 gather/scatter、KPool 四件套、NoPE 稀疏 MLA、KDA chunk prefill
     - 解除 `--enforce-eager`，打开图捕获
     - 多并发和长序列场景的性能

### 面试深挖点

1. **混合 KV cache 为什么会 OOM？**
   - 上游的共享页假设为什么在固定 block 256、TP=8 下不成立？
   - 怎么保证分组、容量核算、实际分配三者一致？
2. **拆池是怎么定位出来的？**
   - 为什么页内 view 会让所有搬运都慢 3 到 4 个数量级，而且耗时跟整个 storage 大小有关，跟实际搬了几页无关？
   - 为什么选择在插件侧拆池，而不是等融合算子？
3. **性能归因方法**：
   - 为什么 profiler 里自定义算子的 `dur` 不可信？怎么改用往返事件计数？
   - decode 耗时几乎不随 batch 变化，说明了什么？（瓶颈在 host 派发，每步约 3.9 万次 op）
4. **算子接入时的契约适配**：
   - 芯片要求每条逻辑行是独立的 512B 物理行，所以 view 操作数必须物化
   - state 布局互为转置
   - PAD_SLOT_ID 要归一处理，否则会触发断言、导致设备不可用
   - aten 侧 scalar 打包错误导致输出恒为 0，是怎么定位的
5. **算子验收方法论**：
   - 怎么避免测试“假绿”？（用 monkeypatch 计数，断言确实走了 kernel）
   - 设备卡死时怎么隔离？（换卡，并记为该算子的缺陷）
   - 怎么把缺陷整理成算子组可以直接复现的文档？

> 最难的一个问题出现在第一次真机跑通之后：服务非常慢，prefill 一步要 179 秒，decode 一个 token 要 120 秒，芯片上几乎看不到计算。我做了插桩 profile，发现 96% 的时间花在 KDA 状态的 gather/scatter 和卷积上。再做隔离实验，定位到根因：两种状态打包在同一个页里，切出来的是非连续 view，芯片后端遇到这种张量会退化成 host 逐元素搬运，耗时跟整个池的大小成正比。
> 我在插件侧把状态池拆成两个独立的连续池，block 语义和总内存都不变，保留开关可以回退，并用单测和真机做了验证。同一个 prompt 下，prefill 单步从 179 秒降到 5.7 秒，decode 从 120 秒降到 2.6 秒。
> 之后我继续按 profile 归因做插件侧优化：接入 mHC 融合算子，修掉一个一直回退到 native 的形状判断，去掉强制 D2H 的校验，改写索引转换。目前的阶段性结果是单请求 TPOT 约 370 ms。
