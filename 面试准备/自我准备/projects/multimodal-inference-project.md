- **时间**：2025年04月 - 2026年03月

- **技术栈**：`PyTorch`、`vLLM V0/V1`、Python、C/C++、自研算子库、自研通信库
- **已明确个人职责的模型**：Qwen2.5-VL、Qwen3-VL、ERNIE 4.5-VL；旧材料中的 Qwen3-Omni 不并入当前已确认范围。

### 项目背景

公司自研加速芯片的软件生态仍在建设期，主流推理框架、模型结构与算子实现主要面向 CUDA 平台。已确认的图像／视频模型适配涉及预处理、高维 Tensor、位置编码、Vision Attention 及卷积算子，使框架兼容、数值精度、内存排布和端到端性能问题相互耦合。

### 职责

- 负责多模态模型在自研芯片上的 `vLLM` 端到端适配、精度对齐和性能优化。
- 维护模型执行层与 `PyTorch`、算子库之间的接口，推动框架特性和缺失算子落地。
- 通过跨平台基线、Profile、算子单测和 Trace 定位模型级瓶颈，并协调算子、运行时和硬件团队完成定位、修复与回归验证。

### 关键行动

1. **打通模型执行链路**：梳理多模态输入从预处理、Embedding、Vision Encoder、位置编码到语言模型的执行路径，逐层补齐模型注册、配置解析、输入映射和设备算子支持。按具体模型记录图像／视频适配，不由旧模型列表推定语音链路已完成。
2. **多模态 RoPE 接口工作**：旧概览记录了 Fused Rotary Embedding 调用方式重构及多种 RoPE 接口支持；保留为框架工程材料，具体模型覆盖、个人改动与回归范围需回到项目记录细化，不据此扩张未确认的 Omni／语音模型经历。
3. **优化内存排布和矩阵计算**：在 `PyTorch` 与 `vLLM` 中接入多维 Col-major Matmul，处理高维 Tensor、前后置变形和临时 Tensor 生命周期问题，降低特殊硬件访存排布带来的额外开销。
4. **解决关键算子瓶颈**：围绕 Conv3d、Flash Paged Attention、Vision Attention、GELU、Scatter 和 Index 等算子建立模型形状单测；通过设备实现、CPU Fallback、精度对比和调度条件控制，在保证正确性的前提下逐步替换性能瓶颈。
5. **建立端到端诊断方法**：同时观察 Host 空洞、Kernel 时间、Tensor Layout、跨设备拷贝和通信行为，避免只根据单算子耗时判断瓶颈；对随机精度问题使用中间值 Dump、算子级复现与跨平台结果对齐。
6. **跨仓库交付**：在内部 `vLLM V0/V1`、`PyTorch` 和算子仓库间同步修改，补充 CI 用例、模型测试和技术文档，确保功能可持续维护。

### F2：问题与基线

首次视频推理在 32B 模型上出现 OOM，Python 调用栈指向 PyTorch Conv3D，模型无法正常完成该输入的推理。我重新执行并打印输入 Shape，提取视频单例，继续检查调用内部的连续化与维度重排。（项目口述）

32B 视频没有可用的优化前 TTFT；3B 视频可以运行并计时，32B 图片也有可运行的性能基线。三组结果分别比较，不能跨模型替换基线。权重、KV Cache、激活和临时存储的完整峰值账本，以及当时失败分配的精确记录仍待核。（项目口述／待核）

### F3：布局机制与定位证据

令 `K=C×T×H×W`。原始 Host 输入已经按每个视觉块展平为 `(N,K)`。H2D 准备阶段先补齐二维末维，传入设备后，PyTorch 仍显示逻辑 Shape `(N,K)`。随后设备侧 view 将其解释成 `(N,C,T,H,W)`，复用原存储。Conv3D 内部再生成通道末置的 `(N,T,H,W,C)` 新存储，小通道维在大量空间位置上分别补齐，产生显著的物理存储膨胀。view 本身没有生成那块大缓冲区。（项目口述）

对于每个物理最内层数据段，记 `R(x)=ceil(x×s/A)×A`，其中 `s` 为元素字节数，BF16 的 `s=2`。按已描述的布局整理，二维输入容量为 `N×R(K)`，通道末置输入容量为 `N×T×H×W×R(C)`；权重的相应容量用 `out_channels` 替换 N。这是布局容量推导，不能直接作为分配器实测或模型峰值。（项目口述与推导）

我依据自研算子库的输入要求提出补齐膨胀假设，检查处理逻辑后发现通道末置操作。为验证分配位置，我构造单例，将重排从 Conv3D 内部移到调用前，使用 PyTorch 显存 snapshot 检查各阶段，观察到重排后显存跃升。它支持将这部分膨胀定位到重排与补齐阶段；原始快照、失败分配与同时存活对象尚未恢复。（项目口述／待核）

输出缓冲及算子工作区也可能贡献显存占用。进一步核对时，可以结合实际物理布局，在对应分配前后检查快照，区分它们与输入补齐的贡献。这是后续核验方法，不能写成该项目已经排除了所有其他分配来源。（待核）

### F4：修改与个人职责

优化后，模型侧保留输入 `(N,K)`，沿用二维 H2D 路径，向专用 Conv3D 传递原 `C、T、H、W` 的维度元数据。权重在初始化时整理为 `(out_channels,K)`。两侧均取消通道末置的新存储生成，让算子直接接收二维布局；原有二维末维补齐仍然存在。专用算子返回 `(N,out_channels)`，内部 SRAM 布局与计算实现由算子团队负责，具体细节我不掌握。（项目口述）

输入与权重采用相同的零起始展平索引 `k=c×T×H×W+t×H×W+h×W+w`。整除和取模可恢复原坐标，同一卷积窗口内的元素配对得以保留。该映射说明逻辑布局关系，实际数值正确性依靠 F5 的参考对照。（项目口述与推导）

### F5：正确性与模型回归

单算子验证在 CPU 上使用 `torch.randn` 准备同一份 BF16 输入和权重，先执行 CPU Conv3D 得到参考结果，再将输入与权重展平并 H2D，执行专用算子。当前具体恢复的是视频 Shape 单例。CPU 输出 `(14040,1280,1,1,1)`，专用算子输出 `(14040,1280)`；比较前仅 squeeze CPU 结果末尾三个单例维，保留分块数和输出通道轴。（项目口述）

CPU Conv3D 是共同参考；新旧设备算子分别对它验证，未进行新旧设备实现直接互比。测试套件使用 `rtol=0.1、atol=0.05`，结果在该容差内通过。内部累加精度、实际误差分布、单测随机种子与具体比较函数待核，不把容差通过写成逐位相等。（项目口述／待核）

没有进行视频输入的模型级精度回归。视频 Shape 的随机张量单测、单个视频的性能计时和图片模型级回归，分别保留各自的验证范围。（项目口述）

## 历史口述基线（2026-09-02）

> 本节保留 2026-09-02 的无稿口述及当时待核事项，不表示旧概览已经独立审计。后续 2026-09-29 的本人确认及案例补充已合入前文“核心案例、验证证据与边界”，其中已补准模型范围、布局关系、验证和性能口径。以下原口述内容和当时待核表保留追溯，不重新裁定已确认字段；当前仍待核内容以前文 F6 为准。

### 当时叙述

这项工作最初来自交通业务客户对图像和视频分析的需求。道路摄像头会持续产生大量影像数据，客户希望从中自动筛选符合业务条件的片段。传统视觉模型通常需要针对不同任务分别训练或微调，多模态大模型则能够同时处理视觉信息和文本语义，通过调整 Prompt 支持更多业务场景。因此，我们需要在自研芯片上完成多模态大模型的推理适配。

我主要负责 Qwen2.5-VL、Qwen3-VL 和 ERNIE 4.5-VL 的框架层适配，包括模型执行链路打通、精度对齐和端到端性能优化。涉及底层算子实现时，我负责从模型和框架侧定位问题、整理真实 Shape、调整调用与数据布局，并与算子同事协同完成优化。

其中一个代表性问题发生在视觉 Encoder 的 Conv3D 路径。模型运行时首先出现了 OOM，调用栈将异常定位到了 Conv3D。根据当时的模型权重、KV Cache 和剩余显存估算，常规激活值原本应该能够容纳，因此我继续检查 Conv3D 调用过程中是否产生了预期之外的中间数据或临时空间。

沿着调用路径分析后，我发现该实现采用了 channels-last 输入布局。这样设计原本是为了提高通道数据的连续访存效率，但视觉输入的通道维度很小，而目标硬件要求末维按照较大的粒度进行内存对齐。小通道放在末维后会产生大量 Padding，不仅扩大物理存储量，还会让 DMA 搬运大量无效数据，使 Conv3D 同时出现显存占用和访存效率问题。

我在模型侧重新组织了 Conv3D 的物理数据布局，将卷积窗口相关维度组合为更适合硬件对齐的内维，并同步调整 Conv3D 输入处理逻辑和模型初始化阶段的权重布局。算子同事配合修改 Conv3D 内部计算实现，使 Kernel 能够按照新的布局读取和计算数据。

验证分为两个层级。第一层从模型中提取真实输入 Shape，构造 Conv3D 单例测试，与 CPU 参考实现进行正确性和性能对比，同时观察显存占用及更大输入下是否仍会出现 OOM。第二层回到完整模型，通过端到端 Profile 检查 Conv3D 热点占比和首 Token 延迟的变化，并完成模型输出的正确性回归。当前结果能够支持“该布局调整消除了已观察到的 OOM，并显著降低 Conv3D 开销和首 Token 延迟”；具体性能幅度仍需依据原始测试记录统一口径。

### 口述中的个人职责边界

我负责问题复现、调用链和显存行为分析、根因假设验证、模型侧数据布局重构，以及模型初始化阶段的权重预排布。Conv3D Kernel 内部的计算和访存实现由算子同事负责。我参与了方案讨论、真实 Shape 提供和端到端验证，但不会将底层 Kernel 的实现工作表述为个人独立完成。
