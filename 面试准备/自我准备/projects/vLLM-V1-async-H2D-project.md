## 项目三：vLLM V1 异步拷贝低概率精度异常专项

- **时间**：2026年05月 - 至今
- **角色**：专项问题主要排查与框架侧开发
- **技术栈**：`vLLM V1`、`PyTorch`、C++ Runtime、H2D/D2D Copy、Stream、Replay 与 Trace 工具
- **当前状态**：根据 2026-09-02 口述，已完成根因定位、修复和现场请求集回归；具体对外口径仍待整理

### 项目背景

Qwen3-32B 在自研芯片上启用高等级异步拷贝后，会低概率出现标签不匹配、重复输出、异常截断及采样参数污染等问题；切换为阻塞拷贝后表现稳定。问题横跨 `vLLM` 输入准备、Sampling、Block Table、`PyTorch` 拷贝实现和底层 Runtime，具有随机、难复现且容易被同步操作掩盖的特点。

### 职责

- 负责推理链路异步拷贝点梳理、实验设计、诊断代码开发和结果归档。
- 在 `vLLM`、`PyTorch` 与 Runtime 之间建立证据链，排除无关假设并缩小高风险路径。
- 为最终修复设计端到端 Replay、微型测试和回归机制。

### 关键行动

1. **建立可信基线**：统一请求集、异常分类、终止原因和日志格式，区分固定 HTTP 错误、已知不稳定请求与真正由异步路径引入的异常。
2. **实现细粒度控制开关**：为输入、Sampling、Attention、KV Cache 和输出等路径增加分模块 Blocking/Async 控制，使单点隔离和组合实验可重复执行。
3. **分层拆解随机问题**：围绕 Sampling Metadata、Runner Inputs、Block Table 等高风险类别开展控制变量实验，并通过防御性检查提前捕获受污染 Tensor，避免非法采样参数进一步触发底层 Hang。
4. **追踪 Producer-Consumer 时序**：加入 Copy/Consumer Trace、Storage 与 Stream 关联、H2D/D2D 屏障、Hash 和双回读校验，验证 CPU Staging、设备写入可见性及下游消费时机。
5. **构造微型验证**：将正式链路中的 Copy、Reformat 和 Writer 行为抽取为压力测试与 Canary，区分专用 Kernel、目标 Storage 后续覆盖和 Runtime Completion 语义等假设。

### 阶段性结果

- 证明异常与异步数据路径显著相关，并将全链路随机问题收敛到少数高风险拷贝和运行时可见性路径。
- 阶段性地将 Sampling Metadata 改为阻塞拷贝后，采样参数越界及其引发的底层 Hang 消失；其余输出异常在当时仍需继续定位。
- 后续确认 CPU Padding、异步 H2D 提交和设备侧消费之间缺少完整依赖，并通过统一的异步等待标记修复该时序问题。
- 使用现场收集的请求完成多轮重放，未再出现原有输出异常。

### 面试深挖点

- 异步 H2D 为什么不仅涉及 Stream 同步，还涉及 Host Buffer 生命周期和 CPU Staging？
- 为什么增加回读或日志后问题可能消失？如何识别观察者效应？
- Event、Stream Sync、设备写入可见性和 Runtime Completion 之间是什么关系？
- 如何证明某个 Copy 点只是相关，而不是最终根因？
- 如何设计能长期进入 CI 的随机竞态回归测试？
- Workaround、最小修复和底层根因修复应如何划分验收标准？

### 2026-09-02 口述基线（待核验）

> 本节记录本次无稿口述中形成的问题链路，供后续持续润色和核对表达。项目事实以 2026-09-02 的用户口述为当前来源。

#### 当前叙述

`vLLM` 从 V0 演进到 V1 后，引入 Persistent Batch，并在输入准备中更系统地使用异步 H2D。以 Block Table 等输入元数据为例，框架可以提前发起 Host-to-Device 拷贝，使其与后续 CPU 输入准备或调度计算重叠。异步 H2D 并非 V1 首次引入，但 V1 的执行方式提高了 pinned Host Memory、异步 DMA、Stream Ordering 和 CPU/H2D Overlap 对后端完整性的要求。

在自研后端支持异步 H2D 后，客户现场低概率出现输出异常，包括 Think 标签不闭合、乱码、空回复和重复循环。现场同事收集了触发过异常的请求，我负责制定临时规避方案、重放请求、缩小问题范围，并继续推进框架侧根因分析和修复验证。

我按照精度问题的常规路径开展排查：

1. 固定采样随机性，将 Temperature 等参数调整为确定性配置。
2. 对同一输入重复执行，定位输出第一次发生分叉的 Token，避免被后续 KV Cache 传播的误差干扰。
3. 比较分叉位置的 Logits 和 Top-k 候选，判断是否只是边界接近造成的采样变化。
4. 沿模型执行路径 Dump 中间 Tensor，尝试定位最早出现数值差异的层或算子。

这次排查出现了明显的观察者效应：加入较多 Tensor Dump 后，异常不再出现。这个现象不能直接证明同步缺失，但说明执行时序可能影响复现。我随后将异步 H2D 单独切换为阻塞路径，并对现场请求重新执行，异常随之消失；调整其他执行配置没有形成同样稳定的控制效果。因此，现有实验能够把问题范围缩小到异步 H2D 相关路径，并支持关闭异步 H2D 作为客户侧临时规避方案，但尚不足以仅凭这一组实验确认具体竞态位置。

根据本轮口述，最终根因位于两阶段拷贝链路：后台任务先在 CPU 侧将原始 Tensor Padding 到 Staging Tensor，再向设备 Stream 提交异步 H2D。下游等待只覆盖了已经进入设备 Stream 的任务，没有覆盖 CPU Padding 完成和 H2D 提交这两个前置事件。等待发生得较早时，设备 Stream 可能因为队列中尚无任务而提前返回，随后下游便可能消费尚未完整写入的数据。完整依赖应当覆盖 `CPU Padding 完成 → H2D 提交 → 设备拷贝完成 → 下游消费`，不能只等待设备 Stream 当时已有的任务。

最终修复是在 CPU Padding 过程中，将 Padded Tensor 也纳入设备异步任务的统一标记与等待机制。这样，后续消费者执行同步时会同时考虑 CPU Padding、H2D 提交和设备拷贝，不会因为设备 Stream 中暂时没有任务而提前继续执行。

修复后，我使用现场收集的 168 条请求连续重放 5 轮，合计完成 840 次请求执行，未再观察到 Think 标签不闭合、乱码、空回复或重复循环。该结果支持问题已经在当前现场请求集和回归范围内解决。
