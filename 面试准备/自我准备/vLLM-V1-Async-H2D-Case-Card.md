## F1：主张与适用范围

我负责 Qwen3-32B 在自研后端使用 `vLLM V1` 时出现的低概率异步拷贝精度问题排查，包括现场请求重放、控制实验、临时规避方案、框架侧时序分析与修复验证。问题涉及 CPU 数据准备、异步 H2D 提交和设备侧消费之间的依赖关系。

项目最终确认，原有等待没有覆盖后台 CPU Padding 完成和 H2D 提交这两个前置阶段。我在框架／后端层补齐 Padded Tensor 的异步标记与等待，使消费者等待完整的数据准备与拷贝链条，Runtime 无需修改。修复后恢复原先触发异常的异步配置，撤掉临时阻塞与额外诊断等待，再将现场收集的 168 条请求连续重放 5 轮，共 840 次执行，未再观察到原有输出异常。该结果限定在所述请求集和配置范围内，不扩张到所有输入、并发和软件版本。

## F3：重放、控制实验与定位过程

我先统一请求集、异常分类与日志记录，区分固定 HTTP 错误、已知不稳定请求和异步路径相关异常，并为不同拷贝路径设置 Blocking／Async 控制开关。这样可以保留相同的输入，逐项改变执行条件，缩小问题范围。各组实验的精确配置和轮次仍待恢复。

在精度排查中，我将 Temperature 等采样参数调整为确定性配置，对同一输入重复执行，寻找第一次出现分叉的 Token，再比较该位置的 logits 与 Top-k 候选，并沿模型路径检查中间 Tensor。这个顺序用于避免把第一次分叉之后传播的差异当作最初原因；具体请求、分叉位置与数值记录尚未恢复。

加入较多 Tensor Dump 后，异常不再出现。这说明诊断操作可能改变复现条件，但仅凭这一现象还不能确定缺失的依赖在哪里。随后单独将异步 H2D 改为阻塞路径，异常也随之消失。这组对照支持将调查集中到异步 H2D 相关路径，并支持关闭异步 H2D 作为客户侧临时规避方案；具体竞态位置需要继续沿准备、提交和消费的时序分析。

项目档案还记录了 Copy／Consumer Trace、Storage 与 Stream 关联、回读校验及微型压力测试等诊断工作。本卡保留这些排查方法，不为尚未恢复的某条 Trace 补写观测值，也不把诊断操作加入后的稳定运行直接当成修复完成的依据。

## F4：依赖缺口、修复与个人职责

该路径由后台任务先在 CPU 上将原始 Tensor Padding 到 Staging Tensor，再向设备 Stream 提交异步 H2D。下游消费者需要等待的是下面这条完整关系：

```text
CPU Padding 完成 → H2D 提交 → 设备拷贝完成 → 下游消费
```

原等待只覆盖已经进入设备 Stream 的任务，没有覆盖 CPU Padding 和后续提交。当消费者较早开始等待时，设备队列可能暂时没有对应的拷贝任务，等待便提前返回；后台随后才完成准备并提交 H2D，下游却已经可能开始读取尚未完整写入的数据。

我在框架／后端层补齐 Padded Tensor 的异步标记与等待，将 CPU Padding 过程中产生的 Padded Tensor 纳入设备异步任务的统一管理。后续消费者的同步因此覆盖 CPU 准备、H2D 提交和设备拷贝，不再仅依赖等待时设备队列中已经存在的任务。该修复由我完成，Runtime 无需修改；对应提交、实现位置和标记的内部接口仍待核。

| 职责 | 已确认内容 |
|---|---|
| 我负责 | 确定性重放方案、首个分叉 Token 与中间 Tensor 排查、异步／阻塞控制实验、客户临时规避方案、框架侧时序分析、在框架／后端层补齐 Padded Tensor 的异步标记与等待，以及现场请求集的修复后回归 |
| 现场同事负责 | 收集客户环境中的异常请求和必要运行信息，为重放提供输入 |
| Runtime 范围 | 复用既有能力，本次修复无需修改 Runtime |

这次修复的实现归属限定在上述框架／后端改动，不扩张为开发或修改全部底层 Runtime。

## F5：修复后验证与回归范围

修复后，我恢复原先触发异常的异步配置，撤掉临时阻塞和额外诊断等待，使用现场收集的 168 条请求连续重放 5 轮，共完成 840 次请求执行，未再观察到 Think 标签不闭合、乱码、空回复或重复循环。这个结果来自项目回归及本次口述补充，不是整理本卡期间重新执行的测试。

| 验证内容 | 已确认结果 | 仍需核对的条件 |
|---|---|---|
| 现场请求集回归 | 恢复原异步配置、撤掉临时阻塞和额外诊断等待后，168 条请求 × 5 轮未再观察到原异常 | 精确开关值、采样与并发配置、版本及逐次执行记录 |
| 修复前对照 | 阻塞 H2D 可使当时重放中的异常消失 | 与修复后相同条件下的执行次数、异常次数和配置差异 |
| 依赖修复验证 | 已确认统一异步标记与等待补齐 CPU 准备、提交和设备完成之间的关系 | 对应版本的实现位置、原始时序证据与可独立复查的测试记录 |

840 次执行来自同一批请求的重复重放，不能当作 840 个独立场景，也不能据此推断所有工作负载的失败概率为零。已确认回归恢复了原先触发异常的异步配置；修复前在相同请求集和完整配置下的异常次数仍未恢复，因此不计算故障率下降幅度。
