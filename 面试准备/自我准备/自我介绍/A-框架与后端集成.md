## 技术二面

您好，我叫 xxx，目前主要负责自研 AI 芯片上的 PyTorch、vLLM 模型执行与后端接口。最近完成了 GLM-5.3-Flash 的插件接入和发布验证，文本版本由云服务团队上线。

我也负责过 PyTorch 后端的异步 D2H 实现。原路径即使指定非阻塞拷贝，仍因 Host 内存、传输对齐和布局还原而进入同步中转，Worker 会在提交过程中等待完成。我在框架侧分配满足条件的 pinned 输出，接入算子同事提供的布局转换实现，再提交异步传输；不符合条件的输入继续使用同步回退。

提交返回后，设备源数据和转换后的临时缓冲区仍可能被传输访问。因此我记录它们使用的 Stream，并为 Host 分配关联完成事件，避免提前复用；下游读取也必须等待真正完成。这部分既包含调用接口，也包含分配和消费之间的依赖。

我完成了目标构建的拷贝契约、回退与生命周期回归，并在 Qwen3-32B 的多卡配置下验证请求完成。不同负载的性能结果有差异，开销和等待发生的位置需要分别说明。

我希望继续负责这样的框架与后端接口工作，在功能实现之外持续维护验证和适用条件。

## 技术追问时再补充

| 面试官追问 | 可以补充的说法 | 使用边界 |
| --- | --- | --- |
| GLM 缓存具体调整了什么 | 按目标平台的实际分配处理混合缓存分组和页容量；另外将卷积状态与递推状态拆成连续池，并调整清零、绑定和迁移 | 容量修复与状态拆池是不同改动；拆池保持总字节数和块编号语义 |
| D2H 为何需要专用输出分配 | 输出需要满足 pinned 内存和传输对齐条件，逻辑 Shape 与物理存储分别处理；布局转换 Kernel 由算子团队提供 | 不披露内部对齐参数或接口名，不把布局 Kernel 归为本人独立实现 |
| D2H 是否总能提升性能 | 现有有限请求对照中，多并发有正向观察，单并发吞吐出现下降；提交更早返回和端到端更快分别判断 | 不宣称所有 D2H 已异步化、设备传输与计算必然重叠或生产收益已确认 |
| H2D 和 D2H 是同一项工作吗 | H2D 是低概率输出异常的依赖修复；D2H 是后端异步回传能力实现，两者分别维护测试与结论 | 不混用性能、回归次数和实现归属 |
| H2D 修复怎样验证 | 补齐 CPU Padding 完成、H2D 提交与设备完成的等待，恢复原异步配置并撤去临时阻塞后，现场请求回归未再观察到原异常 | Runtime 复用既有能力；具体回归范围按 H2D 档案，不外推所有负载 |
