## 技术追问时再补充

以下实现与验证细节只在相关追问中展开；开场先交代职责，再概述通信和 D2H 两个案例。

| 面试官追问 | 可以补充的说法 | 使用边界 |
| --- | --- | --- |
| 多 Stream 开销怎样定位 | 当时的 Profile 没有显示有效通算重叠，却有频繁切流、额外等待和提交批次拆分；结合执行时间线及单 Stream 对照确定调整方向 | 结论属于当时后端与负载，不等于所有硬件都不支持并行 |
| 单 Stream 方案修改了哪里 | 同时处理 PyTorch 通信适配层和通信库中的相关流管理，避免只取消上层流而保留内部额外切换 | 不表示独立实现完整通信库或通信 Kernel；具体正确性与性能范围按档案 |
| 单 Stream 方案怎样验证 | 先检查小范围单例的提交行为，再比较相同训练负载的耗时；保留恢复多 Stream 的配置路径 | 不补造训练 Loss 对齐、完整框架覆盖或未确认的性能数字 |
| 为什么保留多 Stream 路径 | 当前收益来自特定后端和训练负载，其他平台可能具备有效重叠能力，因此保留配置选择 | 不承诺单 Stream 普遍更快，不补造性能百分比 |
| D2H 如何避免内存提前复用 | 为设备源数据、临时缓冲区记录使用 Stream，为 Host 分配关联完成事件；下游读取等待传输完成 | 分配保护和消费等待是不同职责，不能只保留一个 Tensor 引用就推定全部依赖正确 |
| D2H 与下一批推理有什么关系 | 普通 Decode 的下一步 token 可以保留在设备侧，CPU 回传主要服务输出及部分状态处理，因此提交后返回为后续工作提供条件 | 不宣称所有路径都解除阻塞，现有有限实验也未证明所有设备传输与计算重叠 |
| D2H 性能结果怎样判断 | 现有有限请求对照中，多并发有正向观察，单并发吞吐出现下降；提交耗时、设备完成时间和端到端表现分别记录 | 不宣称所有负载加速，也不把请求成功等同 A/B 内容一致或生产验收通过 |
| 是否有多卡模型交付 | GLM-5.3-Flash 在既有 vLLM 插件中完成模型、混合缓存和执行适配，文本版本由云服务团队上线 | 本人负责插件实现、算子验收与发布验证；不扩张为集群平台或全部 Runtime 的开发 |
| RDMA、P/D 和 EP 做到什么程度 | 有固定源码对照和方案讨论，可解释数据布局、完成通知与回收依赖 | 这部分是理解与设计材料，没有真实 RDMA 设备验证，不改写成生产系统经验 |
