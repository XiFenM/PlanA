## 技术二面

您好，我叫 xxx，目前主要负责自研芯片上的框架适配与性能定位，关注内存核算、数据布局和异步执行之间的关系。

GLM-5.3-Flash 项目中，缓存分组采用的页容量假设与目标平台实际分配不一致，导致启动内存不足。我按不同缓存和状态的真实分配方式重新核算，并处理额外补齐，使预算与分配一致。随后定位到两类状态共用字节页形成非连续视图，引发较大的 Host 搬运开销；我将它们拆成连续池，保持总字节数和块编号语义，并验证清零、绑定和迁移。

另一个例子是 PyTorch 后端的异步 D2H。我负责输出分配、布局算子调用、拷贝提交和生命周期保护，布局 Kernel 由算子团队实现。满足 pinned 内存和对齐条件时提交异步拷贝，同时保护源、临时缓冲及 Host 输出分配；不适用的输入保留同步回退，调用方仍需在读取前等待完成。

验证时我分别检查提交行为、完成后的数据和缓冲复用，再比较实际请求负载。不同并发下的收益并不一致，因此我保留性能改善和退化的结果，不把异步提交本身当作端到端加速。

后续希望继续承担计算平台中执行与资源相关模块的实现、验证和维护。

## 技术追问时再补充

下表用于具体机制与结果的追问。先说明测量对象，再引用数字，不将 Host 耗时、设备搬运和完整请求的结果混用。

| 面试官追问 | 可以补充的说法 | 使用边界 |
| --- | --- | --- |
| GLM 容量怎样改善 | 修正混合缓存的分组、页容量与额外补齐；相同部署配置和显存预算下，记录的 KV cache 容量由 45,409 提升到 148,762 tokens | 容量核算和后续服务性能是不同指标，不推导为集群资源利用率提升 |
| 状态拆池为什么有效 | conv state 与 recurrent state 分别进入连续池，保持总字节数和块编号语义；该阶段通过 21 项单测与真机对照 | 改善目标后端的搬运路径，不代表同等比例减少状态总容量 |
| Host 开销的测量是什么 | 同一短 prompt、插桩条件下，decode 单步 Host 耗时约 120 秒降至 2.6 秒 | 不是正式服务的每 token 延迟，也不换算为整模吞吐倍数 |
| 训练通信改动由谁完成 | 本人基于框架测试定位问题，修改 PyTorch 通信适配层和通信库相关逻辑，保留多流恢复路径 | 不扩大为完整训练框架或通信 Kernel 的独立实现；收益限定当时后端与负载 |
| D2H 怎样保护内存 | 设备侧通过 Stream 记录保护源和临时分配，Host 分配关联完成事件；消费者在完成后读取 | 生命周期保护不等于调用方可以提前读，生产接入与验收属于其他团队 |
| 异步 D2H 是否总能加速 | 受测 Qwen3-32B、BF16、TP4 环境中，不同并发有性能改善与退化的观察；提交更早返回、数据完成和服务吞吐分别比较 | 只按有限请求对照说明；请求成功不等于生成内容一致，未证明持续负载收益或设备计算重叠。具体内部性能数字保留在项目档案，不新增到面试口述 |
