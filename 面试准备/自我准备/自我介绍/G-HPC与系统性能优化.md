## 技术一面

您好，我叫 xxx，硕士毕业于复旦大学大数据学院，专业是应用统计，本科是数学与应用数学。目前在自研 AI 芯片公司从事框架适配和性能优化，主要通过 Profile、成本估算和对照实验分析计算、访存与执行开销。

一个代表项目是 ECG 客户模型的端到端优化。我先处理 Host 准备和小 Shape 计算，再结合矩阵乘的计算量与读写量，检查静态权重的访问方式。我负责 PyTorch 侧的 Tensor 扩展和加载期权重预排布，使后续计算复用适合消费算子的布局；底层 Kernel 由算子同事实现，模型最终达到了客户的时延验收目标。

另一个案例是视觉模型的 Conv3D 内存问题。我从 OOM 追到通道末置带来的重复物理补齐，修改模型侧输入和权重布局，并与算子团队完成接口调整和回归。

我希望继续围绕具体工作负载开展系统性能研发，从数据移动、执行依赖和真实测量出发选择优化，并对正确性、结果口径和维护范围负责。

## 技术二面

您好，我叫 xxx，目前的工作主要是自研 AI 芯片上的框架适配和计算负载性能分析，关注 Host 调度、内存布局、数据搬运和通信执行对端到端时间的影响。

在 ECG 项目中，常规优化之后的小批量矩阵乘仍是热点。我结合实际 Shape 和最低读写量作 Roofline 初步估算，继续检查权重供数。方案保持 Tile 大小不变，块内行优先、块间列优先；我在 PyTorch 框架侧实现 Tensor 扩展，并在模型加载后完成权重预排布，后续计算复用这一表示。算子同事负责配套的访存实现。

我在同一自研芯片上对照了新旧布局的 MatMul 输出和模型 logits，已有测例中逐元素数值相等、输出 token 一致。完整请求时延在多项联合优化后达到客户目标，收益按整套方案报告，并保留 Transformers 运行栈和计时范围。

Conv3D 的案例则让我进一步区分逻辑元素量与物理分配：我定位小通道补齐产生的额外存储，负责模型侧布局和调用修改，再与专用 Kernel 进行接口和数值验证。

我希望继续负责工作负载优化，在测量假设、代码改动、正确性和性能结果之间建立清楚的对应关系，并维护可重复的回归条件。

| ECG 的具体结果 | Transformers 执行链下，单请求端到端由约 30–40 秒降至 20 秒以内；前后各 10 次平均，包含图像预处理和完整输出，平均约 700–800 token | 这是多阶段联合优化结果，不是布局独立收益，也不改写成 vLLM 测量 |
| 权重预排布的代价 | 转换在加载阶段完成，供相关静态权重矩阵乘复用；需要维护配套布局契约 | 不是所有 MatMul 都适用，QKᵀ 等动态矩阵乘不在范围内；不声称已证实某一级 bank conflict |
| 怎样使用 Roofline | 结合实际 Shape、dtype 和存储层级，估算 FLOPs、Bytes 和算术强度，再与 Profile 对照 | 个人项目支持初步估算，未恢复全部实测带宽、缓存复用和计数器，不将它描述为所有 Kernel 的完整建模 |
| Conv3D 怎样验证 | 有视频 Shape 的单算子 CPU 参考对照；Qwen2.5-VL-32B 的 10 个图片测例做了模型级回归与平均 TTFT 对照 | 图片组平均 TTFT 从分钟级降到 5 秒以内；原 OOM 视频没有优化前 TTFT，也没有视频模型级精度回归 |
| 通信执行流做过什么 | 基于 DeepSpeed／Megatron-LM 测试调试通信后端，定位多 Stream 切换开销并实现可回退的单 Stream 方案 | 结论限定当时后端与负载；不等同独立开发完整训练系统或通信 Kernel |
| C++／Linux 与 HPC 经验怎样区分 | 工作中有框架和后端修改；个人实践中有 CPU 单槽并发缓冲、ELF／动态库诊断 | 练习与工作分别说明；不把数学背景或 AI 性能项目扩张为已完成 MPI／OpenMP、金融计算或完整 HPC 应用项目 |
