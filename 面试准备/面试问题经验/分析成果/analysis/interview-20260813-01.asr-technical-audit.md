## 一、证据与 ASR 校准边界

- OpenAI 转写共 11,164 字，豆包转写共 12,630 字；两者对问答顺序和核心语义高度一致，因此下列双模型共识内容可信度较高。
- 两份 ASR **均无时间戳，也无说话人分离（diarization）**。说话人只能依据问答轮次推断，不能用 ASR 替换现有视频模型提供的时间点；现有时间点仍只能作为近似导航。
- 豆包转写看起来保留了更多口语成分和部分数字，OpenAI 转写断句略简洁，但没有逐句人工听校，不能据此断言谁整体更准确。
- 两者都大量错写领域词：`vLLM` 被写成 VLM、VM 或 VRM，PagedAttention、Conv3D、RMSNorm、Qwen-VL、Triton 等均有明显识别污染。
- 高风险分歧主要位于专有名词、模型名、具体 shape 和单位，例如视觉部分“3、8、12”的真实含义、矩阵分块中 1024 的单位、公司名和模型版本，不能当作候选人原话。
- 两模型共同确认的关键陈述包括：AWQ/W4A16、block size 256、Linear Attention 未深入、布局优化 10%–20%、TP 中 AllReduce/AllGather、`C=3` 补到 256、MTP、Prefill/Decode、先答右 Padding 后改左 Padding、KV 交错布局、Prefix Cache、Fused MoE、Chunked Prefill、RMSNorm 使用 FP32，以及 BF16/FP16/FP8 讨论。下面的技术审计主要基于这些双模型共识。
- 本文不把 ASR 文本当作逐字引语；涉及说话人、面试官提示幅度、数字、单位、版本或精确术语的结论，仍需回听原音频确认。

## 二、逐项技术问答审计

### 1. vLLM 部署流程与 AWQ 量化

**候选人观点**

先解析模型结构和硬件支持度；不支持 FP4/FP8 时用 AWQ 转成 W4A16/W8A16；切几层抽取算子 case，从单卡逐步适配。

**正确部分**

由小到大 bring-up、按算子拆 case、先解决格式与算子覆盖再全网验证，是扎实的工程流程；明确硬件激活计算主要使用 BF16，也符合异构部署语境。

**错误或不严谨部分**

- AWQ 通常是从 FP16/BF16 基准权重，经校准做 INT4 weight-only PTQ；“FP4 直接转 INT4”若按字面理解会形成二次量化。
- AWQ 不是“重新量化训练”；W8A16 也不能自然概括为 AWQ 的典型输出。
- 面试官问 KV Cache 是否 FP16 时，候选人先表示认可，后面又说硬件只能或主要使用 BF16，存储 dtype 与计算 dtype 出现矛盾。

**面试官追问意图**

确认候选人是真的掌握量化链路、输入权重来源、校准与 dtype，而非只会调用转换工具。

**更好回答骨架**

`原 checkpoint dtype → 是否能取得 BF16/FP16 原权重 → 量化算法及校准集 → group/scale/zero-point → 目标 W/A dtype → 敏感层豁免 → 逐层误差与端到端指标`。

若只能拿到 FP4 checkpoint，应明确：“可反量化后再量化，但信息不可恢复，优先避免，并单独评估二次量化误差。”

### 2. PagedAttention、动态长度与 Block Size

**候选人观点**

请求进入 ModelRunner 前由 Scheduler 计算逻辑 block 需求；Decode 超出尾块时分配新 block；block 固定为 256；每层 Attention 有自己的 KV Cache。

**正确部分**

按需分块、尾块继续追加、满块再申请、block table 做逻辑到物理映射、请求结束释放，基本生命周期是对的。

**错误或不严谨部分**

- vLLM 的 `block_size` 单位是 token，不是字节；256 必须说明版本和自研后端约束。
- 更准确的职责是 Scheduler 做预算和 admission，KV cache manager 分配 block/slot，ModelRunner/Attention backend 消费元数据。
- “每层都有 cache”对存储成立，但 block 映射通常按 cache group 协同管理，Hybrid/Linear Attention 还可能有不同 cache spec。
- “长度不到 256 就与 Prefix Cache 不兼容”过强；更准确是传统 full-block prefix caching 下没有完整可复用块，不能产生该段的 cache hit，但普通 KV 使用不受影响。

**面试官追问意图**

检查是否真正理解动态 Decode、每层 KV 存储和新型 Attention，而不是只会复述 PagedAttention。

**更好回答骨架**

`block 单位/版本 → 每块内存公式 → Scheduler/KV manager/ModelRunner 职责 → prefill 写入 → decode 追加 → 尾块碎片 → prefix 共享引用计数/回收 → hybrid attention cache group`。

### 3. 矩阵乘布局重排

**候选人观点**

矩阵分块后跨行 stride 访问引发 HBM bank conflict；加载期离线重排静态权重为分块列优先，提升 10%–20%，不改激活布局。

**正确部分**

只预打包静态权重、把 layout transform 前移到加载期、让 kernel 按硬件向量宽度连续取数，是非常可信且有区分度的案例。

**错误或不严谨部分**

- “HBM bank conflict”需要地址到 channel/bank 的映射和计数器证据；也可能是不合并访问、burst/cache-line 浪费或 partition 冲突。
- “没有运行时开销”应改为“稳态执行无额外 transform；存在启动时间、存储和多布局维护成本”。
- tile shape、stride、lane 映射及动态 shape 边界没有说清。

**面试官追问意图**

验证软硬件协同、根因定位和性能证明能力。

**更好回答骨架**

`原始 M/N/K 与 dtype → tile/stride 地址模式 → profiler counter → packed layout 地址公式 → kernel load 方式 → 启动/空间代价 → 数值回归 → 绝对值和相对收益`。

### 4. Tensor Parallel 通信

**候选人观点**

TP 中 Linear 后需要 AllReduce/AllGather，模型结束后 AllGather 各 rank 数据再做 Softmax。

**正确部分**

知道 TP 正确性依赖 collective，并提到做通信稳定性和数值验证。

**错误或不严谨部分**

这是本场应升级为重点缺口的内容：

- collective 不是“Linear 后固定插入”的规则。
- QKV、gate/up 常为 column parallel，可继续保持 shard；O、down 常为 row parallel，对 partial sum 做 AllReduce 或 ReduceScatter。
- 最终 vocab-parallel logits 是否 AllGather 取决于采样实现，也可以做分布式 max/sum/top-k，不是固定操作。

**面试官追问意图**

通过 shape 和 collective 放置判断候选人是否理解 TP 原理，还是只参与过联调。

**更好回答骨架**

画两条链并标 tensor shape：

`QKV column-parallel → local attention → O row-parallel → AllReduce/ReduceScatter`

`gate/up column-parallel → local activation → down row-parallel → AllReduce/ReduceScatter`

再说明 sequence parallel、vocab parallel、每次 collective bytes 和 dense reference 校验。

### 5. 多模态视觉 Encoder / Conv3D

**候选人观点**

视觉输入 `C=3` 被移到末维后按硬件补到 256，单个中间张量约膨胀 85 倍，造成 OOM/TTFT；合并相邻维度后传入 kernel，在片上缓冲恢复逻辑 shape。

**正确部分**

症状、profiling、根因、框架与 kernel 协同修改的链条完整，是本场最强案例之一；`256/3≈85.3` 在“元素数真实物化”语境下成立。

**错误或不严谨部分**

- 两份 ASR 都没有可靠保留真实 tensor shape，不能确认“3、8、12”是什么。
- 必须区分 logical shape、physical layout、字节对齐和 channel 元素对齐。
- 维度合并不能只靠 reshape 叙述，需要说明卷积索引语义、stride 和 kernel 如何恢复。
- “视觉 Encoder 只有第一部分看图片”不精确；更可能指 patch embedding/Conv3D 只在前端执行一次。

**面试官追问意图**

考察真实端到端 profiling、视觉算子和硬件对齐约束。

**更好回答骨架**

`原 shape/layout → 哪个 tensor 被物化 → 对齐单位 → 理论与实测内存 → 物理 layout 改造 → kernel 索引不变量 → 峰值内存/TTFT 前后值 → 分辨率和 batch 边界`。

### 6. FastV、投机解码与 MTP

**候选人观点**

MTP 使用草稿模型一次预测多个 token；接受率低时逐层 dump，与参考机器比较精度。

**正确部分**

知道 speculative decoding 的收益受接受率影响；若自研后端移植有数值错误，逐层 diff 是合理排障手段。

**错误或不严谨部分**

- 面试官明确提到的 FastV 更接近视觉 token 剪枝，不是 MTP；候选人没有回应这个算法。
- 通用独立 draft model 与模型内置 MTP heads/modules 需要区分。
- 接受率低不一定是精度问题，还可能来自 draft/target 能力差、采样参数、tokenizer、验证策略和 workload。

**面试官追问意图**

测试除硬件布局之外，对前沿推理算法优化是否有直接经验。

**更好回答骨架**

先区分 `visual token pruning / independent draft speculative decoding / MTP heads`，再分别讲适用模型、额外计算、接受长度、验证开销、正确性保证和端到端 break-even 条件。

### 7. Prefill 与 Decode 优化

**候选人观点**

Prefill 计算密集，使用 TP；Decode 带宽密集，使用 PP；MTP 提高计算利用率；Prefill 的 batch-token 预算开大，Decode 开小。

**正确部分**

Prefill 常偏 compute-bound、Decode 常偏 memory-bound 是合理起点；MTP 可提高 Decode 的算术强度；意识到吞吐和单 token 延迟的权衡。

**错误或不严谨部分**

- “Decode 一般用 PP”不是通用结论。PP 更偏模型容量和多 microbatch 吞吐，单请求 Decode 会引入 stage bubble 与通信延迟。
- `max_num_batched_tokens` 通常是调度器全局 token budget，不是分别为 Prefill/Decode 配两个值；Decode 每请求通常贡献 1 个 token，主要还受并发序列数影响。
- compute/memory 分类会随 batch、context、模型和硬件改变，应以 roofline 或硬件计数器确认。

**面试官追问意图**

检查是否能从瓶颈模型推导优化，而非背诵“Prefill 计算、Decode 访存”。

**更好回答骨架**

`先给 batch/context/硬件 → 算 FLOPs 与 bytes/token → profiler 证实瓶颈 → Prefill 优化 GEMM/TP/chunk → Decode 优化 batching/KV 访问/fusion/spec decode → 说明 TP/PP/EP/DP 的通信和延迟代价`。

### 8. 左右 Padding 与 Decode

**候选人观点**

先答右 Padding，因为生成向后追加；随后在追问下改为左 Padding。

**正确部分**

意识到生成 token 沿时间轴向右追加。

**核心问题**

把稠密 prompt batch 的 Padding、生成追加方向、Paged KV 的 slot/block 管理混成一个问题。这不是单纯口误，而是现场抽象与限定语境不足；是否存在实现错误仍不能据此断定。

**面试官追问意图**

看候选人能否把 batch 对齐、logits 位置、position id、mask 和 KV 写入位置统一推演。

**更好回答骨架**

“我先区分三种语境：decoder-only 的稠密 prompt batch 通常左 pad；生成 token 追加在右侧；vLLM continuous batching/PagedAttention 主要由 `seq_lens`、slot mapping、block table 表示有效位置，物理 KV 未必存在传统左右 pad。若问具体后端 padding，还需看 CUDA Graph、请求行或 block-table 约束。最终核对 mask、position、logits 读取位置和 KV slot 五个不变量。”

### 9. KV Cache 交错布局

**候选人观点**

一个硬件寄存或访存单元能装一个 FP32 或两个 BF16，因此交错两个 BF16，并把 K/V 组织成更大的连续区域。

**正确部分**

按 vector width 打包低精度数据、针对 DMA/vector load 改布局，是可信的硬件适配思路。

**错误或不严谨部分**

- ASR 的“四位”逻辑上很可能是“4 字节/32 bit”，不能照录成 4 bit。
- K 与 V 在 QK 和 PV 阶段的消费方式不同，简单拼接不天然更优；需要地址公式、load 指令和 kernel 改造证据。
- 未说明 head、head-dim、token、block 中究竟哪一维交错，以及相应的对齐和边界处理。

**面试官追问意图**

验证候选人是否真正做过 cache layout，而不只是概念描述。

**更好回答骨架**

`原 layout → vector/transaction 宽度 → 新地址公式 → QK/PV 各自 load pattern → 是否需要转置/解交错 → 额外指令和空间 → reference attention 数值回归 → 带宽与 latency 计数器`。

### 10. Prefix Cache 与 block 生命周期

**候选人观点**

Prefill 和 Decode 使用同一 KV block；尾块未满就继续写，满后申请新块；block 不搬移，请求结束释放。

**正确部分**

主生命周期和避免搬运的思想正确。

**错误或不完整部分**

没有覆盖共享前缀的 refcount、copy-on-write、哈希命中、eviction、preemption，以及 partial block 是否可共享的版本约束。

**面试官追问意图**

深挖 allocator/GC，而不仅是 Attention 计算。

**更好回答骨架**

`prefill 分配与写入 → decode 追加 → full/partial block → prefix hash/refcount → 共享块不可原地改写 → request end/eviction/preemption → free list 复用`。

### 11. Fused MoE

**候选人观点**

把打分、Top-K、路由和专家计算融合为 Fused MoE，减少纯计算硬件上的调度开销；同时坦言参与不深。

**正确部分**

operator fusion 能减少 launch 和中间 tensor 流量；对经验边界表达诚实。

**错误或不严谨部分**

“融合成一个算子”不等于“一个 kernel”。实际常拆为 router、token sort/permute、grouped GEMM、activation、combine；Expert Parallel 还包含 All-to-All。回答没有涉及负载均衡、capacity、动态 token 数和两次 GEMM。

**面试官追问意图**

区分模型适配经验和真正的 MoE kernel/runtime 深度。

**更好回答骨架**

`router logits/softmax/top-k → expert counts/prefix sum → permute/dispatch → grouped GEMM1+activation+GEMM2 → weighted combine → local expert 与 EP → 可融合边界、buffer、负载均衡和通信`。

### 12. Chunked Prefill

**候选人观点**

把长 Prefill 切成小 chunk，让 Decode 请求插入，避免 Decode 延迟过长。

**正确部分**

核心动机和调度作用回答正确。

**错误或不完整部分**

没有讲 token budget、Decode 优先策略、chunk size，以及 TTFT、ITL、吞吐之间的代价。

**面试官追问意图**

确认候选人理解调度器，而非只知道开关名。

**更好回答骨架**

`调度 token budget → 先服务 running decode → 剩余预算分给 prefill chunk → chunk size 对 TTFT/ITL/throughput 的影响 → KV 分配与抢占 → 用 p95 ITL 和吞吐选择参数`。

### 13. RMSNorm、FP16、BF16 与 FP8

**候选人观点**

RMSNorm 使用 16 位会有精度或溢出问题，所以改为 FP32；BF16 动态范围接近 FP32、尾数较少；FP16 尾数精度更高；FP8 有两种格式但未能说出。

**正确部分**

知道 BF16 与 FP32 指数范围接近、FP16 尾数精度高于 BF16，也有用 FP32 提升归约稳定性的真实实践。

**明确缺口**

- 没有区分输入/输出 dtype 与内部 opmath dtype。合理做法常是 BF16 输入输出，平方、mean、`rsqrt` 等内部使用 FP32。
- RMSNorm 是 mean-square，不是去均值后的 variance。
- FP16 的主要溢出风险来自较窄指数范围；BF16 仍会因 7-bit fraction 和长归约累积误差而需要 FP32。
- “FP4/FP8 模型都能跑，所以小数精度不重要”是错误类比；权重/激活量化依靠 scaling 和敏感算子保高精度，不能推导 RMSNorm 可低精度归约。
- 没答出 FP8 `E4M3` 与 `E5M2`，说明格式基础不扎实。

**面试官追问意图**

测试数值格式和敏感算子，而非只问是否调用 FP32 kernel。

**更好回答骨架**

先写公式：

`y = x * rsqrt(mean(x²) + eps) * w`

说明 BF16 输入转 FP32，平方、归约和 `rsqrt` 使用 FP32，再转回 BF16。随后给出位宽：FP16 为 `1/5/10`，BF16 为 `1/8/7`，FP32 为 `1/8/23`；FP8 E4M3 精度较高、范围较窄，E5M2 范围较大、精度较低，并说明 scale/amax 粒度和关键算子保高精度。

### 14. C++、Triton 与 JIT（反问段）

**候选人观点**

PyTorch 底层主要是 C++；Triton 使用 Python DSL 编译为 PTX 或二进制；端侧算子不会直接用普通 Python 执行。

**正确部分**

总体分层认知正确，并在听清 JIT 后完成修正。

**错误或不严谨部分**

“算子不可能用 Python 写”过于绝对；Python DSL、代码生成和 JIT 完全可以作为开发前端，最终执行的是编译产物。Triton 的 PTX 表述也只适用于相应 GPU 后端。

**面试官追问意图**

了解候选人是否能迁移到 C++ Runtime 和编译工具链。

**更好回答骨架**

区分 `Python 模型/DSL 前端 → IR/pass/codegen → C++ Runtime → 设备 kernel`，再说明自研后端在哪一层接入。

## 三、对现有自我复盘报告的修订建议

1. 将 **TP collective 推导** 从“术语可能不精确”升级为优先复测项；两份 ASR 都支持候选人的固定化表述。
2. 将 **Prefill 使用 TP、Decode 使用 PP** 单独列为不严谨甚至可能错误的通用化结论。
3. 增加 **MTP 内置 heads 与独立 draft model 的区别**，并注明候选人没有回答 FastV。
4. 增加 **KV Cache dtype 矛盾**：前段同意 FP16，后段说硬件主要或只能 BF16。
5. 增加 **Prefix Cache 不到 256 并非“不兼容”**，而是 full-block 命中受限。
6. RMSNorm 实践可保留为正面信号，但“数值理论扎实”应降为中等：FP32 fallback 有经验，BF16/FP16/FP8 理论解释明显不稳。
7. 视觉和矩阵布局仍是最强案例，但精确 shape、单位、计数器和绝对指标需要回查，不能让 ASR 猜词补全。
8. 当前报告把 Padding 作为唯一最明确问题略显偏轻。更适合的 P0 组是：
   - Padding、position 与 KV slot 的语境；
   - TP shape 与 collective；
   - BF16/FP16/FP8 与 RMSNorm opmath。
9. AWQ、MTP、PagedAttention 和 MoE 放在 P1：有工程经历，但算法或抽象边界不够精确。
10. 所有 ASR 校准后的结论仍不得写成逐字引语；由于没有时间戳和 diarization，不能据此独立认定面试官提示幅度或精确说话人归属。

## 四、总体判断

候选人的硬件适配和真实问题定位信号很强，尤其体现在权重布局重排、视觉中间张量对齐问题和 KV 数据布局三个案例。这些内容显示出从模型和框架一直下沉到数据排布及硬件访存约束的实际工作经验。

本场暴露的核心短板不是“没有做过”，而是从具体项目经验上升到通用原理时，shape、dtype、算法边界和 collective 推导不够稳定。Padding、TP 通信以及 BF16/FP16/FP8 与 RMSNorm 应成为下一阶段最高优先级；AWQ、MTP、PagedAttention、Prefix Cache 和 MoE 则需要把已有实践整理成术语精确、边界明确、可用数据验证的答案。

这份审计不能判断候选人是否具备未被提问的能力，也不能代替原音频人工听校。尤其由于两份 ASR 均无时间戳和说话人分离，任何涉及“谁在何时说了哪句话”的结论都必须回到原始录音复核。
