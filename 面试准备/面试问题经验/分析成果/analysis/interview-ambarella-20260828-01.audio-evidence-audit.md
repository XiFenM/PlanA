## 2. 低音量处理审计

原始视频的音频确实很轻。源文件为 AAC 单声道、48 kHz，测得综合响度约 `-35.37 LUFS`、真峰值约 `-1.94 dBTP`、平均音量约 `-36.1 dBFS`，低层背景声约在 `-55.43 dBFS`。因为源音频存在接近峰值的瞬态，直接统一增加约 17 dB 会有削波风险。

实际处理采用双遍动态响度归一化，目标为 `I=-18 LUFS`、`TP=-2 dBTP`、`LRA=11 LU`，并转为 16 kHz 单声道 MP3 供模型分析。处理后实测综合响度约 `-18.64 LUFS`、真峰值约 `-1.52 dBTP`、响度范围约 `9.1 LU`，完整解码校验通过。

| 项目 | 处理前 | 处理后 | 审计判断 |
| --- | ---: | ---: | --- |
| 综合响度 | `-35.37 LUFS` | `-18.64 LUFS` | 可辨识度显著改善 |
| 真峰值 | `-1.94 dBTP` | `-1.52 dBTP` | 动态处理避免了简单增益造成的明显削波 |
| 响度范围 | `13.4 LU` | `9.1 LU` | 对话动态收敛，便于模型处理 |
| 降噪 | 无 | 无激进降噪 | 避免把专业词、辅音和弱语音一并损伤 |

归一化会同时抬高底噪，因而不能把处理后听起来更清楚等同于源语音信息被恢复。此次没有使用激进降噪，优先保留专业术语和弱语音的原始形态。原始视频未被覆盖或改写；所有处理均发生在派生音频副本上。

## 4. 逐题技术核验

### 4.1 离职原因与当前工作内容

**现场主旨**：当前岗位除 AI 框架工作外还承担客户接洽、评测支持，希望下一份工作更聚焦研发。

**核验**：这属于职业动机，不是技术事实。风险在表达方式：如果只强调“不想做客户与评测”，容易被理解为不愿承担产品交付。更好的口径是承认这些经历带来了真实场景和问题闭环，同时说明希望提高核心研发工作的占比。

**证据等级**：B；原句需回听。

### 4.2 自我介绍与个人职责

**现场主旨**：工作覆盖模型接入、精度对齐、部署交付、热点算子分析、硬件特性适配和外部评测。

**核验**：分类合理，也和后续案例相互印证。欠缺的是个人 ownership：哪些模块由候选人设计与实现，哪些由算子、编译器或硬件团队完成；指标、代码边界与长期维护责任都未在开场建立。

**表达审计**：面试官明确要求放慢语速，这是一条直接可执行的现场反馈。后续应使用“结论一句—三项职责—一个最强案例—岗位连接”的 60 秒结构。

**证据等级**：B。

### 4.3 KV Cache 强对齐与 Prefix Cache

**现场主旨**：通用 vLLM 的块粒度与自研 TPU 的“256 强对齐”要求冲突，影响非整齐长度的前缀复用；候选人在框架层做二次切分或取模。

**技术核验**：

- 专用加速器的向量宽度、内存事务或 kernel shape 要求确实可能与通用框架的逻辑 block 不一致；问题方向成立。
- 必须区分 vLLM 的 `block_size`（通常表示每个 KV block 容纳的 token 数）与底层的字节、元素、地址或 tensor 维度对齐。“16/32/64 对 256”若混用两种单位，结论会失真。
- Prefix caching 是否下降，取决于 hash/逻辑块、物理分配、slot 映射和复用粒度。仅说“取模/二次切分”不足以验证正确性。
- 应补出 logical block → physical allocation → block table → attention backend 的映射，以及碎片、命中率和 kernel 接口变化。

**审计结论**：这是强经历信号，但当前说法尚不能独立证明方案设计的完整性。

**证据等级**：B（问题与主旨）/ C（单位、实现、收益）。

### 4.4 变长输入与 Attention kernel 分档

**现场主旨**：无需为每个输入长度导出一套完整模型，上层根据长度区间调度底层不同长度的 Attention kernel。

**技术核验**：按 shape bucket 或 kernel specialization 分发是静态/半静态后端常见做法，回答方向合理。但“直接支持变长”需要拆成：请求层是否动态、执行图是否动态、kernel 是否分桶、超出 bucket 是否 padding 或重新编译。还需要说明：

- bucket 边界和选择策略；
- padding 比例与计算浪费；
- 首次编译/缓存代价；
- prefill 与 decode 是否使用不同路径；
- 最大上下文和异常长度如何处理。

**证据等级**：B；实现与性能为 C。

### 4.5 Fused RoPE 与片外访存

**现场主旨**：多模态模型的旋转位置编码存在特殊交错/索引操作；独立 Index/Slice 在 TPU 上造成多次 HBM 往返，因此做融合。

**技术核验**：减少中间张量物化和片外访存是算子融合的典型收益，Memory-bound 判断成立。需要收紧三点：

1. 明确模型和 RoPE 变体，可能涉及多维/分段旋转，但不能仅以“视觉模型特殊”代替张量定义；
2. 明确融合边界，是 index + reshape + RoPE，还是进一步融合进 Q/K 投影或 attention；
3. “全部在 SRAM/寄存器完成”必须由 kernel 实现和 profile 支持，现有音频只证明候选人这样解释过，不能当作实测事实。

此外，候选人后续说明自己主要处在框架层，因此必须区分方案提出、接口改造、kernel 实现和性能验收分别由谁完成。

**证据等级**：B（瓶颈与方案主旨）/ C（kernel 细节与收益）。

### 4.6 ERNIE / Qwen 模型适配

**现场主旨**：在当时的 vLLM 缺少现成 ERNIE 模型定义时，候选人完成首版框架层模型接入，并改造 Mask 逻辑。

**技术核验**：从零编写模型定义通常涉及权重映射、forward、并行切分、attention backend、采样和精度对齐，能够形成较强的框架层证据。但本次只听到“模型定义”和“按元素 Mask 改按列 Mask”，没有建立完整范围。Mask 改写必须给出张量 shape、广播规则和数学等价性，不能仅凭优化方向判断正确。

**证据等级**：B（参与接入）/ C（从零范围、Mask 等价性、模型版本）。

### 4.7 架构分层与 Conv3D 内存优化

**现场主旨**：候选人主要负责 PyTorch/vLLM 框架层；Qwen-VL 的 3 通道输入在某种 Channel-last 与 128 对齐约束下产生严重 padding，通过 transpose/reshape 或维度合并规避。

**技术核验**：若某一物理布局要求通道维向 128 补齐，`C=3` 的单维存储放大上限可接近 `128/3≈42.7` 倍，因此问题机制合理。但总显存是否增长“数十倍”还取决于完整张量布局、kernel 临时空间和生命周期。

更重要的是，空间维、batch 维和 channel 维不能在不改变 kernel 契约的前提下随意合并。需要说明原始 shape、目标 shape、卷积参数、数据布局、前后变换以及为何保持数学等价。若只是为了让底层 Conv3D kernel 使用另一种合法 layout，应明确这是布局变换，不要说成任意 reshape。

**证据等级**：B（问题主旨与框架层角色）/ C（shape、等价性、实际显存收益）。

### 4.8 C/C++ 与经典视觉

**现场主旨**：日常以 Python 为主，在 PyTorch 扩展、算子分发和显存管理接口中修改部分 C++；没有经典 YOLO/CNN 项目经验。

**技术核验**：这是清晰的能力边界，不应从“改过 C++ 扩展”外推到现代 C++ 系统工程、嵌入式 runtime、驱动或 kernel 开发。Qwen-VL 视觉编码器适配也不等于具备目标检测、后处理和视频 pipeline 经验。

**岗位含义**：面试官反复确认语言和视觉经历，说明这些很可能是岗位的实质考察项。它是当前最大的匹配风险，不是表达问题可以完全遮蔽的缺口。

**证据等级**：B。

### 4.9 AIME 与硬件算力

**现场主旨**：AIME 2024 用于数学推理评测；A100 BF16 约 312 TFLOPS，自研 TPU 约 200–210 TFLOPS，并口头概括为 A100 的约 60%。

**技术核验**：

- 把 AIME 2024 说明为美国高中数学竞赛题组成的数学推理基准，方向正确。
- 必须注明精度、稠密/稀疏口径和是否为理论峰值。TOPS 和 TFLOPS 也不能混用。
- 按候选人自己的数字，`200–210 / 312` 约为 `64%–67%`，不是严格的 60%；可说“约三分之二”或给出真实官方规格。
- 自研 TPU 的 200–210 TFLOPS 属候选人口述，未由本次材料独立验证。

**证据等级**：B（回答内容）/ C（自研芯片规格）。

### 4.10 AWQ 与 W4A16 性能收益

**现场主旨**：权重以 INT4 存储，激活保持 16 位；计算时反量化，读取权重的数据量下降，Decode 的访存收益超过反量化成本，端到端提升约 `20%–30%`。

**技术核验**：核心性能解释正确。权重量化从 FP16/BF16 到 INT4，权重存储与读取量理论上可降至约四分之一；在小 batch Decode 的 memory-bound 区间，融合反量化的额外计算可能小于带宽收益。

但 AWQ 不只是“W4A16”：它强调 activation-aware 的权重重要性评估与缩放/量化策略。实际 kernel 通常边读边解码并与 GEMM 融合，不应给人“先把全部权重展开为 BF16 再计算”的印象。`20%–30%` 是候选人自述结果，需补模型、batch、上下文、输入输出长度、硬件、基线和统计口径。

**证据等级**：B（机制）/ C（实测提升）。

### 4.11 DeepSeek 671B、32 卡与 Host 聚合通信

**现场主旨**：4 台机器、每台 8 张 64 GB TPU，共 32 卡部署 DeepSeek-V3 671B；TP 小包通信在 TPU 路径较慢，改由 Host/CPU 聚合后跨机通信再分发。

**技术核验**：4×8 的拓扑和 32×64 GB 的聚合容量在数量级上可容纳 671B 模型，但是否可运行取决于权重精度、激活参数量、KV Cache、临时 buffer、并行策略和运行时开销，不能只看总容量。

Host staging/aggregation 在专用互联对小消息支持不佳时可能有效，但它增加了 device↔host、主机内存和跨机网络路径。要证明方案成立，需要说明 collective 类型、消息大小、PCIe/互联拓扑、CPU 间协议、同步策略以及分层 benchmark。当前材料不支持把它概括为通用的“异构计算调度”。

音频理解结果显示，候选人现场主动收窄了简历中该表述的含义。这是边界修正，也说明简历标题与实际方案需要重新对齐。推荐改为：“针对 4 节点 32 卡 TPU 张量并行中的小消息通信瓶颈，参与实现 Host 侧聚合与分发路径，并以端到端吞吐/时延验证。”其中“参与/主导”和指标必须按事实填写。

**证据等级**：B（拓扑与方案主旨）/ C（精度、协议、收益和个人贡献）。

### 4.12 Attention、卷积与 FFN 的边界

**现场主旨**：标准 Transformer 的 Attention 由 Q/K/V 投影、`QKᵀ`、Softmax 和对 V 的加权组成；FFN 是后续独立子层，Attention 内没有卷积。

**技术核验**：对标准 Transformer block 而言回答正确。需要保留架构边界：某些混合模型可能在 block 或 token mixer 中引入卷积，但不能据此反推标准 self-attention 内部包含卷积。候选人面对问题中的不准确前提仍保持概念边界，是本轮清晰的正面信号。

**证据等级**：B，技术结论高置信。

### 4.13 个人项目、历史经历与业务反问

**现场主旨**：Agent/Skill 是个人探索；早期国药控股经历偏 SQL/ETL；候选人反问安霸的产品与部署形态。面试官介绍了嵌入式 AI SoC、AI Box、PCIe 加速卡以及大模型框架对接。

**核验**：这些产品形态只作为面试官现场口述记录，不替代公司官方资料。对岗位而言，它们解释了前面对 C/C++、经典视觉、SoC/插卡形态和 vLLM 的组合追问：团队可能希望同时覆盖边缘视觉基本盘和正在扩展的大模型推理能力。

**证据等级**：B；具体产品与岗位范围需 JD 或面试官后续确认。

## 8. 审计结论

本轮相对可靠的正面证据是：候选人的现场回答能够从框架层连接专用硬件的布局、对齐、片外访存和小消息通信问题，并给出具体工程改造方向；AWQ 的性能解释和标准 Attention 的概念边界尤其清楚。

最重要的风险不是“完全不懂底层”，而是证据深度与岗位重心可能错位：候选人的强项在 Python/vLLM 框架适配与跨层定位，安霸面试官则明显持续核查 C/C++、嵌入式、经典视觉和实际 kernel/通信实现。简历中过宽的“异构调度”措辞进一步放大了这种核查。

后续准备应同时做两件事：一是把现有强案例补成可审计的 shape、数据路径、实现边界和 benchmark；二是用最小可运行项目补足 C++、YOLO 前后处理和边缘端推理链路。由于没有逐字稿和正式反馈，本审计只能用于能力复盘，不能生成录用结论。
