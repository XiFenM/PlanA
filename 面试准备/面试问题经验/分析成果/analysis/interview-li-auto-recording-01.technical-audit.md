# 理想汽车面试技术核查

记录 ID `interview-li-auto-recording-01`，分析日期 2026-11-19。定位使用两套本地 ASR 的同一音频窗口。文中的计算和例子由复盘补做，现场原文可在[逐段转写](../transcripts/interview-li-auto-recording-01.local-indexed.md)中核对。

## 推理性能要给分母

L028、L040 两次出现单请求 16–17 tokens/s，第二次有明确的 decode 确认。如果这是稳定生成阶段的速率，倒数约为 **59–63 ms/输出 token**。服务同时处理多少请求、首 token 等了多久，需要各自测量。

L041–L043 的提问换成了输入吞吐。你给出不同输入长度的 prefill 耗时，随后说自己主要关注时延。若这几组时延确实覆盖单请求完整 prefill，按 K=1024 计算，64K / 70 s ≈ **936 输入 tokens/s**；128K / (150–160 s) ≈ **819–874 输入 tokens/s**。这是条件换算，现场没有给出这些计算结果。32K 的读数有口吃与识别歧义，保留空格比较可靠。若计时还包括排队、分词、网络或首个 decode 步骤，报告须注明计时边界，再给该数字准确命名。

L032–L039 中，64 GB 是单卡显存容量，约 200 TFLOP/s 是你报出的峰值算力，120–130 是你描述的实际场景量级；数据精度、稀疏性计数和测试负载没有给全。带宽一开始说 800–1000 G，追问后说明这是实测范围，标称峰值为 1.6 T，方向是单卡片上计算单元与显存之间。只有按同类测试、相同单位、十进制 GB/s 与 TB/s 理解，800–1000 对 1600 才对应约 50%–62.5%。不从这个百分比推断整个模型的执行效率，也不根据口述数值推测芯片型号。

## 线性注意力为什么要两份状态

L055–L067 支持区分两个时间尺度。核宽 4 的一维因果卷积在位置 t 使用当前输入和之前 3 个位置；解码推进一格时可以保留 3 个历史位置。递推分支维护矩阵状态，前一状态和当前输入一起决定下一状态，读取输出还涉及查询。面试中你说到了两个状态的用途。把这段讲成一轮 decode 的输入和输出，比直接列张量尺寸更容易听懂。[Kimi Linear 论文](https://arxiv.org/abs/2510.26692)

固定版本的 GLM-5.3-Flash 公开配置有 45 层，其中 34 层在 `kda_layers` 内，线性分支给出 `num_heads=64`、`head_dim=128`、`short_conv_kernel_size=4`。因此“末尾三位置”与该配置相容。若自研后端另采用 TP8 且均分 heads，则单 rank 可以有 8 个 heads；**TP8 是这里的推导前提**。本场音频对具体分片配置、槽位外轴和两个数值轴的重述不够清楚。将 `8×128×128` 写成待核的可能形状，优先用实际运行时 shape/stride 核实。[GLM-5.3-Flash 固定 revision 配置](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/46a050bec13002ad29ee795c16e61cf4fa3c4a9c/config.json)

L066–L067 两模型均把卷积尾部识别为 FP32、把递推矩阵识别为 BF16；L080/L102 又出现两种精度，但后两处的文字只支持并列列举。本场音频给出了**候选人的描述**；插件里的实际 dtype、模型配置和累加精度分别用代码、运行时 dump 核查。不能引用其他场次的听辨结果替本场定案。

L069–L091 中描述的是从统一字节池得到算子所需的有类型视图，或预先分为两类状态池。原始 buffer 用 int8/byte 表示、张量的计算 dtype、内存连续性和后端对齐是四件事。满足 stride/对齐条件时 view 可以共享存储；真正有性能开销的可能是后续 materialization/copy 或内核不支持某种布局。要验证个人改动，最短的一条证据链是相同输入下的分配规格、实际 stride、拷贝事件计数及耗时、输出一致性、端到端对照。[PyTorch Tensor.view 文档](https://docs.pytorch.org/docs/stable/generated/torch.Tensor.view.html)

## 4096 个 token 对应多少页

面试官给出 4096-token 请求，让你从连续预分配讲到分块；256 是你举例用的 block size。[L122–L138](../transcripts/interview-li-auto-recording-01.local-indexed.md#l122)

在没有共享块、预留块或推测解码额外槽位的例子中，每块存 256 个 token，则块数为 `ceil(T/256)`。4096 个 token 恰好填满 16 块。以零基位置计，最后一个 token 的位置 4095 对应逻辑块 15、块内偏移 255。下一个真正需要写入 KV 的位置 4096 对应逻辑块 16、偏移 0，这时新增第 17 块。可以举一行块表 `[31, 8, …, 52]`：逻辑块 0 访问物理块 31；逻辑块 15 访问物理块 52。块表把逻辑顺序与物理位置联系起来。[PagedAttention 原论文](https://arxiv.org/abs/2309.06180)

你已经提到按需增长、尾块满了继续分配、按请求查物理块号，也提到不同请求可以复用已有前缀块。前两项说明了如何避免按最大生成长度预留连续 KV。跨请求共享还取决于内容与上下文匹配、共享块查找和生命周期管理；分页本身不会让任意历史块都能命中。L129 出现数字连读，不能据 ASR 写成“回答了 116 块”或判定算错。

## Conv3D 的“四十几倍”该乘在哪个对象上

L141–L154 的叙述连接了视觉输入、通道移到末维、设备对齐、OOM、展平部分维度，以及算子根据元信息恢复逻辑维度。你将修改主要定位在 PyTorch 侧。公开的 PyTorch `Conv3d` 文档给出的批输入逻辑维度是 `(N,C,D,H,W)`。录音中先听到类似 `NCHW`，后续又明确提到“五维”，没有源码就不能据其中一个短语重建自研后端的真实物理布局。[PyTorch Conv3d 文档](https://docs.pytorch.org/docs/stable/generated/torch.nn.Conv3d.html)

两份识别在 L149 给出类似“122”，在追问后的 L151 都给出更完整的 **3→128**。若其他维度和元素宽度一致，且每行 3 个通道确实被物化为 128 个元素，则该输入张量的旧物理大小 / 理想紧凑大小 = `128/3 ≈ 42.67`。它度量的是一次布局膨胀。新布局仍可能有尾部 padding。例如只作演算，每行空间组取 14×14 个位置，则旧布局占 `196×128=25,088` 元素；若把一组的 588 个有效元素展平后按 128 向上对齐，新布局占 **640** 元素，比值变为 **39.2**。实际要看哪几轴被合并、每组各自如何对齐；这里的例子没有替代实测。

整模型的峰值还包括常驻权重、其他活跃张量、算子 workspace 和分配器保留内存。补证时分别给出该 tensor 的逻辑元素数、旧/新物理字节数，以及同负载的端到端峰值。要声称解决 OOM，还需一条原来能稳定复现、改后能稳定完成的测试记录。
