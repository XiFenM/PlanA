## 三、关键技术核验

### 1. 专用芯片存储层次与 GPU 类比

**候选人现场主张（经 Gemini 概述，待回听）：** 目标芯片更接近少量大核的 NPU/TPU，具有片外 HBM、片上显式管理的 Buffer 和 1024 字节对齐要求；候选人将片上 Buffer 类比为 GPU Shared Memory，并疑似表示该芯片没有 L1/L2 Cache。

**通用技术校准：** 将软件显式管理的片上 SRAM/Buffer 类比为 GPU Shared Memory，可以帮助说明“开发者负责搬运和复用”的特征，但不能视为严格等价。还需分别说明：可见范围、容量、bank 组织、DMA/向量搬运方式、是否有硬件 cache、寄存器层次，以及哪个软件层负责调度。

“没有 L1/L2 Cache”只能是对某个具体自研架构或软件可见模型的陈述，不能泛化为 NPU 的共同特征。片上单元的 `Vector Memory / Scalar Memory / Matrix Buffer` 命名存在识别歧义，应在 `09:00–11:50` 回听后再写入对外版本。

### 2. pybind11 不等于完整的 PyTorch 算子注册链路

**候选人现场主张（经 Gemini 概述）：** Python 与 C++ 都在使用，C++ 涉及 PyTorch 插件、设备/算子调用，Python 侧通过 pybind11 调用 C++ 能力。

**通用技术校准：** pybind11 能解释 C++ 函数或模块如何暴露到 Python，但 PyTorch 自定义算子还可能涉及 operator schema、dispatcher、backend key、meta/fake 实现、autograd 和设备 guard。现场回答抓到了语言绑定层，但如果岗位在问 PyTorch 插件架构，只答 pybind11 会显得层次不足。

更好的回答应先问清“绑定普通 C++ API，还是注册 PyTorch operator”，再画出：

`Python 调用 → operator schema/dispatcher → 自研 backend implementation → runtime/stream/device API → device kernel`

并明确自己实际改到哪一层。

### 3. DeepSeek/MoE 的 TP 与 EP 通信不能按两种互斥模式背诵

**候选人现场主张（经 Gemini 概述，数字待回听）：** 候选人疑似称接触的是 DeepSeek-V3、32 卡、单卡 64 GB；先前配置为 TP32，后续尝试 EP；profile 中观察到 AllReduce、All-to-All 和 AllGather。该概述没有提供完整、稳定的理论推导。

**外部标准事实与通用校准：** DeepSeek-V3 官方技术报告给出的模型规模是 671B 总参数、每个 token 激活 37B 参数；这只能核对模型公开规格，不能证明候选人当时的卡数、显存或并行配置。[DeepSeek-V3 Technical Report](https://arxiv.org/abs/2412.19437)

需要校准的不是某个 collective 名，而是表达框架：

- TP 描述单个张量/线性层如何分片；不同投影和实现可能触发 AllReduce、ReduceScatter 或 AllGather，不能说“TP 下全走 AllReduce”。
- EP 描述专家如何分布。Router 后的 token dispatch 和 expert 输出 combine 常对应两次 All-to-All/All-to-All-v，但是否还存在 TP collective，取决于 expert 内部是否再做 TP、并行组怎样配置。
- Dense Attention、shared expert、routed expert、最终 vocab/logits 可能属于不同并行域，不能用一条通信规律覆盖整网。
- “Profile 中同时看到 AllReduce 与 All-to-All”只能证明执行图包含两类 collective，不能单独证明它们属于同一个 MoE 子层或同一套并行配置。

本场的风险点是先用 profile 现象回答架构题，直到面试官继续追问才补出“早期 TP32、后来 EP”的时间/配置区分。下一次应先固定配置，再按层画 tensor shape、分片轴、parallel group 和 collective。

### 4. 机内/机间通信：RDMA 与 IB 不是同一层面的二选一

**候选人现场主张（经 Gemini 概述，术语待回听）：** 候选人使用片内/板内直连、RDMA、IB 网卡等词解释机内与机间差异，并把性能差距归因到物理链路和协议路径。

**通用技术校准：** InfiniBand 是网络互联/传输体系，RDMA 是远程直接内存访问语义和能力，可以基于 InfiniBand 或 RoCE；它不能简单与“机内通信”绑定。机内可能走 PCIe、NVLink、CXL 或厂商私有 fabric，机间可能走 IB/RoCE；collective 库再根据拓扑组织 ring/tree 等算法。

因此更稳妥的回答顺序是：

1. collective 语义是否相同；
2. rank 是否跨节点、拓扑和 parallel group；
3. 物理链路、NIC、交换网络及 GPUDirect/RDMA 能力；
4. 带宽、启动延迟、拥塞和跨 NUMA 路径；
5. 用 message-size sweep 与 topology-aware profile 验证差距。

### 5. Block-level Column-Major 案例：方案可信，根因和收益仍需证据

**候选人现场主张（经 Gemini 概述，单位与归因待回听）：** 候选人称 MatMul 的原访问方式存在跨步访问或 Bank Conflict，并与算子团队协作，把静态权重按 1024 字节 block 重排为 block-level column-major，使运行期更适合目标矩阵单元取数。

**通用技术校准：** 把静态权重预打包成硬件友好的 blocked layout，并把运行时 layout conversion 前移到加载期，是合理且有价值的优化。它不自动证明瓶颈位于 HBM bank，也不自动证明达到了满带宽。真正需要补齐的是：

- 原始与目标 layout 的地址公式、tile shape、dtype 和对齐单位；
- 1024 字节是 transaction、block、bank 宽度还是某级存储分配粒度；
- 低效究竟来自不合并访问、burst/cache-line 浪费、片上 bank conflict，还是其他 partition conflict；
- profiler counter 或带宽利用率怎样支持根因；
- kernel、单层和端到端的绝对/相对收益；
- 预打包增加的加载时间、额外存储、多 shape/多版本维护和精度回归成本。

在这些信息补齐前，不应把“完全消除 Bank Conflict”“全带宽读取”或“无额外开销”写成确定结果。稳妥说法是“改善矩阵单元供数的连续性和对齐，并减少稳态执行中的 layout 转换”。

### 6. Roofline 回答缺的是定量推导闭环

**候选人现场主张（经 Gemini 概述）：** 候选人先讲 profiler、算子占比、Host/Device 气泡、H2D/D2H 和异常小算子；面试官缩小到单个 MatMul 后，回答仍主要是与硬件标称算力比较，未完整给出计算强度推导。

**通用技术校准：** 对 `A[M,K] × B[K,N] → C[M,N]`，常用计算量约为 `2MNK FLOPs`。访存字节数不能机械背一个固定公式，而要基于 dtype、缓存/片上复用、C 是否读改写、权重是否常驻和实际 tile 计算最小数据移动量。随后计算：

`Arithmetic Intensity = FLOPs / Bytes`

`可达性能上界 = min(峰值算力, Arithmetic Intensity × 有效带宽)`

`理论耗时下界 = max(FLOPs / 峰值算力, Bytes / 有效带宽)`

最后再用 profiler 检查 achieved FLOPs、有效带宽、occupancy/矩阵单元利用率、同步和 launch gap。候选人现场主要答出了最后一步，缺前两步，因此给人的印象是“会找热点，但不一定能先验判断这个 shape 应该跑到哪里”。

### 7. 精度与并发排障：方法正确，需把定位手段和最终修复分开

**候选人现场主张（经 Gemini 概述）：** 面对乱码或特殊字符输出，候选人会检查 logits/采样、做逐层或二分 dump、对照 reference，并检查 collective 边界；并发案例中，候选人称把异步阶段改为同步后问题消失，继而定位到 Host Padding 与 H2D/设备消费之间缺少依赖。Gemini 还记录了 `125 次/约 30 次异常`，该数字未人工确认。本文不把“感叹号”直接等同于通用的 Token 0。

**通用技术校准：** 上述精度排查顺序合理，下一次应补充固定 seed、dtype、误差指标/容差、首个分歧层和自动化回归。

在并发 Bug 案例中，“改成同步后问题消失”是很好的定位证据，但不是最终修复本身。更完整的闭环应说明：

- Host Padding 的生产者和 H2D 消费者分别在哪个线程/队列；
- 原依赖为何没有被 stream/event/future 表达；
- 最终如何建立 happens-before，而不是永久串行化；
- 是否增加高并发、多 batch、不同 shape、长时间压力和 sanitizer/日志回归；
- 修复后的错误率、吞吐与延迟是否恢复。
