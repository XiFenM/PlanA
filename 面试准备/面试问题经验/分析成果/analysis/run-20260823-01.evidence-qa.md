## 技术一致性核验

### 1. Padding：需要先限定语境

Decoder-only 的普通稠密 batch 通常使用左 Padding，使每一行的最后位置是真实 token；自回归生成的新 token 则沿序列轴追加在右侧。vLLM 的 PagedAttention／continuous batching 主要依赖有效长度、slot mapping 与 block table 管理各请求 token，不应与稠密张量的左右 Padding 混为一谈。部分执行后端还会为请求行或 block table 做另一层 Padding。

因此，22:55–24:30 最合理的复盘结论是：**回答前没有先区分 prompt batch、生成追加和 KV block-table 三种语境，导致表述不稳；不能仅凭摘要判定实现逻辑错误。**

官方参考：

- [Hugging Face：LLM generation 的 Padding 说明](https://huggingface.co/docs/transformers/v4.57.0/llm_tutorial)
- [PyTorch：`pad_sequence` 的左右 Padding 参数](https://docs.pytorch.org/docs/stable/generated/torch.nn.utils.rnn.pad_sequence)
- [vLLM Spyre scheduler：后端请求 Padding 示例](https://docs.vllm.ai/projects/spyre/en/latest/contributing/scheduler.html)

### 2. PagedAttention 与 Block Size

vLLM 的 `block_size` 单位是 **每个 KV block 的 token 数**，不是字节。某些官方版本（如 v0.17）在参数枚举中允许到 256，同时说明 CUDA 后端限制不超过 32；这些限制是版本和后端相关事实，不应当作永久规则。因此摘要中的 256 若准确，应明确实际 vLLM 版本和自研后端。调度器会请求 KV cache manager 分配 block／slot，并由 block table 建立序列逻辑块到物理块的映射。“Scheduler 分配逻辑 block”是可理解的简写，但不够精确。

官方参考：

- [vLLM Engine Arguments：block size](https://docs.vllm.ai/en/v0.17.0/configuration/engine_args/)
- [vLLM Engine Arguments：最新版](https://docs.vllm.ai/en/latest/configuration/engine_args/)
- [vLLM PagedAttention 设计](https://docs.vllm.ai/en/stable/design/paged_attention/)
- [vLLM Scheduler 源码](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/sched/scheduler.py)

### 3. Prefill、Decode、Chunked Prefill 与 MTP

“Prefill 常偏计算密集、Decode 常偏访存密集”是合理的工程启发式，不是跨 batch、context、模型和硬件都不变的定律。Chunked Prefill 是调度策略；vLLM 会在 token budget 内协调 decode 与 prefill chunk。MTP 属于带验证的 speculative decoding，要求模型存在相应的 MTP head／草稿路径，收益取决于接受长度和验证开销，不能泛化为所有模型的通用提速手段。

官方参考：

- [vLLM Optimization and Tuning](https://docs.vllm.ai/en/latest/configuration/optimization/)
- [vLLM MTP](https://docs.vllm.ai/projects/speculators/en/latest/user_guide/algorithms/mtp/)
- [vLLM speculative decoding acceptance metrics](https://docs.vllm.ai/en/latest/features/speculative_decoding/acceptance_metrics/)

### 4. RMSNorm 与 BF16／FP16

使用 FP32 完成平方、均方归约和 `rsqrt`，再转回低精度，是常见且稳健的实现。摘要中的“求方差”和“BF16 易溢出”不够准确：RMSNorm 计算 mean-square，不做去均值；FP16 的范围较小，平方和归约更容易溢出，而 BF16 与 FP32 具有相同指数位宽，主要风险通常是尾数较短造成的舍入和归约精度，而非动态范围不足。

官方参考：

- [PyTorch RMSNorm](https://docs.pytorch.org/docs/stable/generated/torch.nn.RMSNorm.html)
- [Hugging Face Llama RMSNorm 的 float32 计算](https://github.com/huggingface/transformers/blob/main/src/transformers/models/llama/modeling_llama.py)
- [Google Cloud：bfloat16 format](https://docs.cloud.google.com/tpu/docs/bfloat16)

### 5. Tensor Parallel 通信

“Attention 与 MLP 的 Linear 后插入 AllReduce 与 AllGather”若按字面理解会过度泛化。标准张量并行中，column-parallel 与 row-parallel 的切分方式、输出是否保持分片、是否开启 sequence parallel，会决定使用 AllGather、AllReduce 或 ReduceScatter。正确复盘应要求画出 QKV→Attention→O 和 up/gate→down 的 tensor shape、分片轴与 collective，而不是背固定规则。

官方参考：

- [Megatron Core：ColumnParallelLinear / RowParallelLinear](https://docs.nvidia.com/megatron-core/developer-guide/0.15.0/apidocs/core/core.tensor_parallel.layers.html)
- [NCCL collective semantics](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)

### 6. AWQ、W4A16 与 W8A16

摘要中的“FP4／FP8 权重经 AWQ 转为 W4A16／W8A16”必须回片澄清。公开 AWQ 主路径是 activation-aware 的 weight-only PTQ，通常利用校准激活从 FP16／BF16 基准权重生成 INT4 W4A16。W8A16 是通用 INT8 weight-only 格式，不应自然等同于 “AWQ 的 W8A16”。若真实流程是遇到目标芯片不支持的 FP4／FP8 发布模型后回到高精度原始权重重新量化，这是合理语境；若直接对已量化 checkpoint 再量化，则存在二次量化误差。

官方参考：

- [MIT Han Lab：AWQ](https://github.com/mit-han-lab/llm-awq)
- [TensorRT-LLM：precision / quantization modes](https://nvidia.github.io/TensorRT-LLM/_modules/tensorrt_llm/quantization/mode.html)
- [ONNX Runtime：量化与逐层调试](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)

### 7. Fused MoE 的抽象层级

把 Top-K／dispatch／GEMM／reduce 表示成一个 Fused MoE operator，以减少框架调度与中间存储，是合理方案；这不等于全部工作已融合成一个设备 kernel。公开实现往往分别融合 router、permute／dispatch、grouped GEMM 和 combine，expert parallel 还包含跨设备通信。应追问是 operator 还是 kernel、local expert 还是 EP、是否包含 gate matmul／softmax、两次 GEMM+activation 与 AllToAll。

官方参考：

- [Megatron Core：MoE](https://docs.nvidia.com/megatron-core/developer-guide/nightly/user-guide/features/moe.html)
- [vLLM：fused top-k router](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/layers/fused_moe/router/fused_topk_router.py)

### 8. Layout／Bank Conflict 与 `C=3 → 256`

离线预打包权重、把运行时 layout transform 前移，是合理且有价值的优化。摘要把 stride 访问低效进一步归因到 “HBM Bank Conflict”，但公开 GPU 资料中的 bank conflict 通常首先指片上 shared memory／LDS；global/HBM 的 stride 也可能表现为不合并访问、cache-line 浪费或 channel／partition 冲突。自研 ASIC 可能有自己的 bank 映射，但需要 memory level、bank 数／宽度、地址映射、lane／stride 和硬件计数器才能完成归因。

`C=3` 补到 256 若指 channel 元素数，单个受影响 tensor 的理论存储倍率约为 `256 / 3 ≈ 85.3`；若指 256-byte 对齐则不是该倍率。必须明确单位、tensor layout 与是否真实物化，不能写成“整体模型显存增长 85 倍”。

官方参考：

- [CUDA Best Practices：shared-memory banks 与 strided access](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#shared-memory-and-memory-banks)
- [NVIDIA Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)
