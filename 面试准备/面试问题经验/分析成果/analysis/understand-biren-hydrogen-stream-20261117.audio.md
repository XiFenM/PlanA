### Q2：核心模型结构（5.3 Flash）与缓存池改造
- **近似位置**：约 `06:20–09:30`
- **问题/追问**：面试官针对自述项目提问，询问对 `JM/GM/GLM 5.3 Flash` `[待回听]` 模型是否熟悉，并请简单介绍及说明适配难点。
- **候选人实际回答**：
  - 模型两大特点：其一引入了线性注意力机制（音近 `KTA/KDA` `[待回听]`），自述其借鉴了“Kimi K3” `[待回听]` 架构；其二采用了 `Sparse MLA`，并称这也是 `DeepSeek` 之前的代表性创新。
  - 缓存机制差异：与传统全序列保存 `KV Cache` 不同，线性注意力的缓存保存的是“递推矩阵”以及卷积最后几个 token 的状态。
  - 遇到的框架痛点：当时线性注意力模型结构尚未固化，框架（`vLLM`）原生采取“为每层申请一块完整平铺开来的 `int8` 内存块”的方式分配缓存。而该模型的两类状态实际上拥有不同的数据类型（一部分为 `FP32` `[待回听]`，一部分为 `BF16`）与不同的张量形状（递推矩阵约 `8×128×128`，卷积尾部为最后 3 个 token 即 `3×hidden_dim`）。
  - 性能问题与解法：若将原生单一平铺的 `int8` 块直接传入后端算子，会因 dtype 不匹配、shape 不匹配及内存不连续，触发硬件后端内部隐式的重排/拷贝动作（在后端执行很慢），造成较大性能瓶颈。候选人的方案是将原生统一内存池拆分为“递推矩阵池”与“卷积尾部池”两个独立连续池，使算子能直接从连续池中按对齐格式读取，从而显著提升性能。
- **提示或自我修正**：候选人在提及 `8×128×128` 形状时加上了“我记得”作为不确定限定。
- **短证据**：“直接申请一个 int8 类型的……完全平铺开来的一个内存块”、“把这个池进行一个拆开……拆成两部分，就是递推矩阵池和一个卷积尾部池”。
- **可信度及待确认项**：工程问题定义与解法因果链较完整；模型具体名称、线性注意力缩写 `KDA/KTA`、`Kimi K3` 说法以及算子侧实际加速比均为口述，`[待回听]` 核实原词。

### Q4：DSA 中的 MLA 计算过程推导
- **近似位置**：约 `10:15–15:40`（定位待核实，主体在 `10:00–15:00` 并延至 `15:40` 前后）
- **问题/追问**：面试官指出模型另一部分注意力结构是 `DSA`（自述其中本质为 `MLA` 加 `Sparse`），请候选人结合平台 Markdown 编辑器推导一遍 `MLA`（重点 QK 部分）的计算过程。
- **候选人实际回答**：
  - 候选人表示对 `Sparse` 部分有些遗忘，但可以推导 `MLA`。
  - 输入与投影：先在 Markdown 写出输入 `x`（口述假设激活值形状含 `token`、`head`、`hidden_dim` 等维度；传统注意力会直接对 `Q, K, V` 做投影）。
  - `MLA` 核心思路：认为 `K` 和 `V` 并非所有维度都包含有效信息，可通过线性层（`linear`）将其联合压缩至低维隐向量（`latent`，记为 `L`，口述“具体的算子方面我可能看得不是很多”），该向量维度远小于直接投影后的 `K, V`。
  - 缓存与还原：推理时仅将体积较小的 `latent` 向量存入 `Cache`，计算前再从隐向量还原（上投影）出高维的 `K` 和 `V`（口述还原后形状“应该就没有 head 了，整个就是 `d_k`”）。
  - `Q` 路径与后续计算：认为 `Q` 不占 `Cache`，直接通过投影从 `x` 得到；随后执行正常的 `Q·K^T` 与 `Softmax` 等计算。
- **提示或自我修正**：
  - **面试官提示 1**：在候选人表达忘记 `Sparse` 时，面试官表示“不用 Sparse，就 MLA 就可以，Sparse 比较独立”。

- **短证据**：“通过一个线性层然后压缩到一个低维的隐藏向量里面”、“我没有提旋转位置，因为我默认旋转位置编码在前面就已经做好了”。
- **可信度及待确认项**：候选人掌握了 `MLA` 低秩压缩缓存 `latent`、减小 KV Cache 占用的核心思想；但推导中出现多处细节偏差或未展开项（如输入 `x` 带有 `head` 维的表述、上投影张量维度的含糊、未体现标准 MLA 中为兼容矩阵吸收而采用的解耦 RoPE 设计），且 Markdown 实际书写内容不可见。

### Q5：8 卡 `TP8` + `AWQ W4A16` 量化部署决策
- **近似位置**：约 `15:40–19:00`
- **问题/追问**：面试官引用候选人材料中的“8 卡 `TP8`、`AWQ` 4 比特量化（`W4A16`）”方案，提问单卡显存多大、为何 8 卡全部采用 `TP8` 而非其他并行切分方案。
- **候选人实际回答**：
  - 显存核算：模型经 `W4A16` 量化后权重体积约“100 到 200G 左右，200G 不到一点”；单卡显存 `64GB`，8 卡总计 `512GB`（`8×64`），`TP8` 可直接将权重均摊到 8 张卡上。
  - 曾评估过 `TP4 + DP2` 方案，最终放弃并选用 `TP8` 的两大原因：
    1. **算子优化与整机商用习惯**：其他模型也用 `TP8`，商业交付通常为单机 8 卡且希望用满 8 卡；`TP8` 核心集合通信为 `AllReduce`，团队对其做过多次深度优化。若采用 `TP4 + DP2`，则 MoE 部分会引入 `EP`（专家并行）的 `dispatch` 与 `combine` 通信，底层对应 `All-to-All` 通信，而团队在该通信算子上优化不足、效率偏低。
    2. **缓存空间与长上下文诉求**：`TP4 + DP2` 会在非 MoE 层复制权重，挤压可用缓存显存；而该模型最大支持“一兆（1M）”上下文，虽当前硬件仍放不下 1M，但实测在 `TP8` 下可支撑“170 几 K 左右”的上下文长度。
- **提示或自我修正**：无。
- **短证据**：“我们一张卡是有 64GB”、“大概是在能够放个 170 几 K 左右”、“主要还是……通信算子上面优化的不是特别好”。
- **可信度及待确认项**：显存数字（单卡 64GB、总计 512GB、量化后近 200GB、实测 170+K）与业务约束逻辑自洽；相关硬件型号与实测上下文长度属现场自述。

### Q7：追问 MoE 在 `TP8` 与 `EP8` 下的显存差异
- **近似位置**：约 `19:40–21:10`（跨 `20:00` 边界）
- **问题/追问**：面试官设定前提“先不考虑 Attention 的 KV Cache”，追问在 MoE 自身层面，采用 `TP8` 与 `EP8` 对显存占用有什么区别。
- **候选人实际回答**：候选人未从权重分片大小直接对比，而是从**运行时（尤其 Decode 开启 Graph 模式）的通信缓冲区开销**切入：在 `DP + EP` 模式下，每次前向无法预先确定各专家会接收多少个 token；为保证低延迟模式下能够开启计算图（Graph），必须按最坏情况预留显存缓冲区，大小估算为“专家数 × 最大调度的 token 数 × hidden 维度”。候选人回忆此前估算过，这块预留缓冲区大概在“几百兆到 1 个 G 之间”，会额外挤占 KV Cache 空间。

### Q11：PyTorch 后端异步 `D2H` 的实现机制
- **近似位置**：约 `26:10–31:00`（跨 `30:00` 边界）
- **问题/追问**：面试官请候选人展开说明“PyTorch 后端异步 `D2H` 能力”是在哪一层、具体如何实现的。
- **候选人实际回答**：
  - 业务背景：源于 `vLLM v1` 之后在调度器（`scheduler`）与执行器（`worker`）之间引入了异步调度能力，上一轮采样（`sample`）出的 token 需要在结果未完全回传 host 前就开始准备下一批调度，因此需要异步 `D2H`。
  - 硬件限制：自研芯片显存数据强制要求内存对齐（`padding`）。例如逻辑上为 `5×1` 的 `int32` 张量，在 device 上实际按 `5×128` 存放。
  - 原有痛点：旧路径是将整个 `5×128` 数据回传给 CPU，再由 CPU 剥离 padding 还原为连续内存；CPU 参与重排导致 `D2H` 无法真正异步化。
  - 改进方案（主要在 `PyTorch` 后端改造）：
    1. 请算子同事编写了一个在 device 侧转成 CPU 布局的算子，将 `5×128` 中的 5 个有效数压缩写到第一行的前 5 个位置，异步 `D2H` 时只需拷贝第一行的 `128` 个元素。
    2. 在 `PyTorch` 后端提前在 host 侧申请满足对齐尺寸（例如大小为 `128` 而非 `5`）的内存接收区，使异步 `D2H` 能合法写入。
    3. 传输完成后无需 CPU 搬运，直接利用 `PyTorch` 的 `view` 机制将较大缓冲逻辑映射为符合上游期望的小张量（如逻辑上匹配 `5×1` 形状）。
    4. 同步保护：由于异步 `D2H` 时下游消费方不能直接读取未就绪数据，在下游消费处加入了等待事件（`wait event`）或 `stream` 同步机制，确保数据确实到达后再吐出 token。
- **提示或自我修正**：无。
- **短证据**：“原本上它其实是一个 5 乘一个 128 这样子一个大小的形状”、“在 PyTorch 后端申请一块……128 大小的内存”、“通过 view 机制……逻辑上形状是跟之前匹配的”、“wait event 或者说是 stream 同步”。
- **可信度及待确认项**：完整涵盖了背景、硬件约束、后端与算子协同、主机侧零拷贝 `view` 映射以及异步同步保护，工程细节丰富，可信度高；具体同步原语 API 与性能收益数值未提及。

### Q13：业余学习的 `Triton` 与 `FlashAttention-2` 设计思路
- **近似位置**：约 `31:35–34:50`
- **问题/追问**：面试官提及候选人曾业余学习过一些 `Triton` `[待回听]` 算子，请简单介绍 `FlashAttention-2` 的设计思路。
- **候选人实际回答**：
  - 核心目的：避免将注意力中间结果矩阵反复读写到高带宽显存（`HBM`）中，从而节省显存带宽搬运（同时指出计算复杂度上并无减少，“我觉得也是 `O(N^2)` 吧，还是要整个都计算出来”）。
  - 关键机制 `Online Softmax`：由于 `Softmax` 需要全局最大值与指数求和分母，分块计算时每次只算一小块，利用前一块与当前块的最大值差值计算校准系数，对之前的中间累加结果进行重缩放（rescale），再累加当前块的结果，最终得出正确的 `Q·K^T` Softmax 与 `V` 的乘积块。
  - `FlashAttention-2` 的切分循环结构：外部固定一个 `Q` 的 tile，内层循环遍历 `K` 的 tile（口述中也提及按顺序遍历 `V` 并计算输出 `O` 的对应结果）。
- **提示或自我修正**：候选人中途卡顿了一秒（“从哪里开始讲？”），面试官缓和提示称只需讲简单思路即可（“因为这也不是你主要工作嘛，没关系”）。
- **短证据**：“避免去 HBM 上面之间的拷贝”、“我觉得是在 Online Softmax 里面”、“固定一个 Q 的 tile，然后去遍历那个 K 的 tile”。
- **可信度及待确认项**：准确抓住了 IO 感知（减少 HBM 读写）、Online Softmax 重校准及 FA2 以 Q-tile 为外层循环等关键点；口述中对 K 与 V 在内层同循环步内的累加过程描述略显简略，未展开 FA2 相比 FA1 减少非矩阵乘法 FLOPs 及序列并行等优化细节。

## 6. 后续准备

以下建议为面向候选人的后续复盘练习方案，**非本场音频发生内容**，均不虚构额外项目或数据：

1. **规范 `MLA` 与 `DSA` 全链路数学与张量推导（关联 `Q4`）**
   - **练习方式**：脱离参考资料，在白板上完整写出标准 `MLA` 从输入 `x: [B, S, D]` 出发的下投影、上投影、`RoPE` 解耦分支（`q_pe`, `k_pe`）与 `nope` 分支合并的过程，并补充推导推理阶段“矩阵吸收”如何消去 `K` 的上投影还原步骤；另外单独梳理 `DSA` 中 `Sparse` 索引/选取机制。
   - **完成标准**：能在 5 分钟内无提示完成全部张量维度标注，并准确指出 `RoPE` 为何不能直接置于常规低秩矩阵吸收之前。

2. **固化核心项目模型的结构参数与显存/Cache 公式（关联 `Q2`, `Q3`, `Q9`）**
   - **练习方式**：对简历中的核心代表模型，整理一张一页纸速查表，明确写清全局与单卡切分后的 `num_heads`、`d_k`、`d_v`、卷积核窗口大小、不同池的 `dtype` 以及页/块容量核算公式。
   - **完成标准**：被追问任一硬编码张量形状（如 `8×128×128`）和容量指标（如 `148,762 tokens`）时，可在 10 秒内拆解出每个数字的物理来源，并清晰区分“Bug 纠错前后”与“真实优化收益”。

3. **系统对比 `TP`、`DP+EP` 在权重、激活与运行时缓冲上的显存账（关联 `Q5`, `Q6`, `Q7`）**
   - **练习方式**：分别列出 Dense 层与 MoE 层在 `TP8` 与 `TP4+DP2+EP8` 两种方案下的“静态权重显存 + 激活峰值显存 + Graph 静态缓冲 + KV Cache 剩余空间”四栏对比表。
   - **完成标准**：被问及 MoE 显存差异时，能按“静态权重 -> 动态缓冲 -> 激活与通信代价”三层结构作答，不遗漏主干维度。

4. **补齐多机分布式推理与 `All-to-All` 通信认知短板（关联 `Q8`, `Q12`, `Q17`）**
   - **练习方式**：针对 GPU 集群常见的机内全互联 + 机间高速互联架构，学习并梳理多机大 `EP` 场景下 `dispatch/combine` 的通信掩盖（计算-通信重叠、双微批次流水线）与负载均衡常见做法。
   - **完成标准**：能够口头画出单机与多机 `EP` 的通信链路差异图，并准确说明至少两种降低 `All-to-All` 尾延迟的工程手段。

5. **精炼 `FlashAttention-2` 算子切分与复杂度表述（关联 `Q13`）**
   - **练习方式**：对照 `FlashAttention-1` 与 `2` 的核心差异，用伪代码写出外层 `Q` tile、内层 `K, V` tile 单循环内的 `Online Softmax` 更新与 `O` 缩放累加步骤，并区分 IO 复杂度（HBM 访问量）与计算 FLOPs 复杂度。
   - **完成标准**：无需停顿思考即可在 2 分钟内讲清 Online Softmax 公式与 FA2 相比 FA1 改动的三处关键点。

6. **重构项目成果的量化表述，杜绝模糊包装（关联 `Q9`, `Q10`）**
   - **练习方式**：逐条审查过往准备的项目亮点（如“3 倍容量提升”、“Graph 抓图策略”），将“修复误算”客观重写为真实改进动作（如“重构混合池容量核算逻辑，消除错配导致的内存浪费/崩溃”），并统一口述口径（如明确抓图分桶规则）。
   - **完成标准**：所有宣称的性能/容量数字均能当场给出“优化前基线测试条件、优化后复测条件及真实对比口径”三要素。
