### Q3：KDA 线性注意力原理与 vLLM 缓存池定制优化（约 12:35）
- **问题与追问**：
  1. 针对上述“尚未开启的优化”或近期在 `5.3 Flash` 上做过的优化，请展开具体说明。
  2. （约 14:40）追问卷积：询问 Flash 模型中是否真的有卷积、哪里会用到卷积、是否确定该操作叫卷积，并要求简述大概实现。
  3. （约 16:25）追问原理：要求用一句话简要概括整个 `KDA` 的原理。
  4. （约 19:00）追问精度与配置：确认 vLLM 中 `int8` 的设定是仅针对该模型还是其缓存池原本就是固定精度；能否通过配置修改类型。
  5. （约 21:20）追问实现与版本：询问候选人具体在框架里改了哪些内容来实现自定义类，并追问 `5.3 Flash` 发布已有一段时间，为何 vLLM 原生未提供良好支持；追问团队所使用的 vLLM 版本号。
  6. （约 24:05）追问性能收益与未支持特性：指出“新增一个类型只是跑通，不代表性能好”，询问是否达成预期、还有哪些后续优化空间；追问为何 `MTP`、`FP8` 这些相对成熟的功能当前未支持，并确认候选人与算子团队的职责边界。
- **候选人实际回答**：
  - **核心背景与问题诊断**：`5.3 Flash` 的最大特点是引入了线性注意力 `KDA`（后解释为 `Kimi Delta Attention`）。在当时使用的 vLLM 中，由于社区线性注意力模块尚未收敛，上游采用了一个通用、连续化的 `int8` cache 池，把所有层（听似“34 层”，`[待回听]`）统一为长达几十万的一维大池。在自研芯片上执行算子前，需要先对大池做切分/view 并重新连续化拷贝成算子所需张量，这一步耗时极大。
  - **定制拆分方案**：分析该模型 KDA 实际只需要两类缓存：
    1. 卷积尾部缓存：保留末尾 `3` 个 token 的卷积状态，形状为 `3 * hidden_dim`（连读`[待回听]`），类型 `fp32`；
    2. 递推矩阵缓存：每个位置需保留 `heads * dk * dv`（连读`[待回听]`）的递推状态矩阵，类型 `bf16`。
    候选人借鉴常规 KV cache 的槽位与分块模式（如 `8 * 128 * 128`），将单一通用池直接拆分为两个贴合本模型目标形状与数据类型的专用缓存池，省去计算前的切分和连续化拷贝。
  - **关于卷积与 KDA 原理的解释**：说明 KDA 内部包含一个一维“因果卷积”，每次从前向后看 `4` 个 token 并汇聚到一端（此处现场表述为“从前向后看四个 token 汇聚到最前面”，与因果卷积常规语义存在表述偏差，见技术核查）。被要求概括 KDA 原理时，表示卷积后得到类似 `QKV` 的特征，再经线性与 norm 等操作得到状态 `S`，随后与前一位置的递推矩阵做递推更新并不断向后叠加，因此必须缓存卷积尾部与递推矩阵。
  - **改动细节与版本限制**：说明 vLLM 上游使用 `int8` 只是为了先让各类尚未统一的线性注意力模型都能跑起来，无法通过配置改类型，必须改代码。团队（“我们做了一个自己的 `MambaCache` group”）实例化了自定义 cache 类；本人主要负责形状和数据类型调整、复用原有 `MambaCache` 大部分功能，并重写后段按目标形状与槽位大小整除分配的逻辑。之所以未用上游新版本，是因为芯片插件接入后公司无法反复跟随大版本升级（否则引发大量代码冲突）。现场报出当前使用版本为 `v0.30.1`，面试官核对称“现在已经 `0.34`”（两者版本号均存在公开版本体系存疑，`[待回听]`）。
  - **收益、后续空间与分工**：强调拆池就是为了性能；后续两项主要优化方向为支持 `MTP`（多 token 预测）和尝试 `FP8` KV cache。解释此前未支持是因为自研芯片需要算子团队编译与实现算子、需要研发周期；补充说明简历所写项目阶段尚未支持，但截至目前团队已接近支持完成。确认本人主要负责框架侧改动，算子由其他团队负责。
- **面试官提示与引导**：多次在技术细节过密时提醒“先用几句话概括现有问题、思路和收益”，并明确区分“功能跑通”与“性能达标”。

### Q5：PagedAttention 原理与 `page_table` / `block_table`（约 28:00）
- **问题与追问**：
  1. 询问是否了解 vLLM 经典的 `PagedAttention` 算法。
  2. 要求具体举例：假设一条 `4096 tokens` 的请求，在没有 `PagedAttention` 之前和有了之后分别是怎么做的、逻辑与物理映射如何建立、为什么能省显存。
  3. 追问核心数据结构 `page_table`（或 `block_table`）长什么样、起到什么作用。
- **候选人实际回答**：
  - **基本思路**：将原本连续分配的 KV cache 池进行分块（block），不再为单条 sequence 预分配完整连续大空间，而是通过 `block_table` 建立从逻辑块到物理块的映射，方便前缀复用并减少显存碎片。
  - **4096-token 对比说明**：
    - 无 PagedAttention 时：必须估算该请求未来可能生成的最大最坏长度，一次性分配连续 KV cache，导致大量预留浪费；且存在前缀复用需求时，连续方案难以细粒度部分复用。
    - 有 PagedAttention 时：假设 `block_size = 256`，输入 4096 个 token 占用 `16` 个块（候选人连读中提及“16 块……17 块然后再加上一个末尾的”，或指满块后的尾块预留，`[待回听]`）。后续 decode 阶段不按最坏长度预分配，而是等最后一个块填满后再按需新增一个块，使占用显存随生成渐进增长。此外，当新请求前段与历史请求相同、仅在中间某处分叉时，可以以 block 为单位复用分叉前的所有块。
  - **`page_table` / `block_table` 结构与作用**：先反问确认“你是说 `block_table` 是吗”，随后说明其本质是记录每条请求具体映射到了哪几个物理 block 编号；算子计算 attention 时，通过该索引表查询并读取对应物理 block 中的 KV cache。
- **面试官提示**：在候选人给出概念定义后，引导其结合 `4096 tokens` 举例对比优化前后的差异。

### Q6：其他项目补充——多模态 `Conv3D` 显存 OOM 优化（约 33:45）
- **问题与追问**：
  1. 询问日常工作中是否还有其他未提及、值得探讨的优化工作。
  2. 听完后追问：只是最后一个维度发生 padding，为什么会让整体显存变成 `40` 几倍？
  3. 确认该项目对应的模型、以及具体在什么框架和库中做的修改。
- **候选人实际回答**：
  - **问题背景与现象**：主动补充简历中的多模态 `Conv3D` 优化工作，发生在一个多模态模型适配中（听似“千问3 32B VL”，`[待回听]`），现象是直接报 `OOM`（显存不足）。
  - **根因定位**：输入数据原形状按候选人口述涉及 `NCHW` 与五维形状（口述示例说 `5, 14, 14, 3` 仅四维，但后又提到恢复成五维，`[待回听]`）。原实现将 channel（`C=3`）移到最后一维；由于自研芯片存在强制对齐/padding 机制，导致最后一维 `3` 被直接 pad 到 `128`，造成海量显存浪费。
  - **解决思路与收益**：因为把任何较小的维度放在末尾都会触发 padding，最终把除前面 `N`（或前两维）之外的维度全部展平为二维张量（口述类似 `NH` 形态），再在算子内部根据输入原始形状元数据重构恢复成五维并完成计算。估算因 `3` 被 pad 成 `128`，节省了将近 `40` 几倍显存。
  - **解释倍数质疑与所在框架**：确认由于最后一维从 `3` 扩充至 `128`，整个多维张量的总体体积也相应被放大约 `128/3` 倍，产生溢出效应。确认项目为“千问3 32B VL”多模态推理，使用 `PyTorch` 和 `vLLM`，但该项修改主要在 `PyTorch` 层完成以适配算子调用。

## 四、针对性准备练习与验收标准（4 项）

### 练习 1：KDA 线性注意力公式与 Cache 拆分量化复盘
- **练习内容**：手写一页纸梳理 KDA（Kimi Delta Attention）单步递推结构（1D Causal Conv 状态更新 + Delta Rule 状态矩阵递推），并补充自研芯片上“通用 `int8` 池 vs 拆分双池”的端到端对比数据与内存布局图。
- **验收标准**：能用不超过 90 秒讲清因果卷积的方向（过去 3 个 + 当前 1 个）、状态衰减与递推更新公式；能当场报出拆分前拷贝算子占比、优化前后的 prefill/decode 耗时及显存占用变化（不含模糊定性词）。

### 练习 2：算力、带宽与 Roofline 指标快速换算训练
- **练习内容**：针对自己简历项目的硬件参数（`200 TFLOPS` 峰值 / `120–130` 实测、显存带宽 `800–1000 GB/s` 实测 / `1.6 TB/s` 峰值、`64 GB` 显存），计算当前模型在 decode（`bs=1`）和 prefill（`32K`/`64K`/`128K`）下的理论带宽受限/算力受限上限，对照实测 `16–17 tokens/s` 与 `70s`/`150–160s` 找出差距根源。
- **验收标准**：面对面试官追问“prefill 吞吐多少 tokens/s”、“性能瓶颈在算力还是访存”，能在 5 秒内完成心算给出 `tokens/s` 量级并给出硬件利用率百分比估算。

### 练习 3：`Conv3D` 五维张量布局与硬件对齐案例结构化表达
- **练习内容**：对照原项目代码，精确写下 `Conv3D` 改造前后的 tensor shape 变化（五维原貌 → 展平二维 → 算子内部片上重构方式），并说明为何二维传入不触发 `128` padding 而只改变末尾维就会整体膨胀 42.6 倍。
- **验收标准**：口头复述时维度数量前后完全一致（5 维就是 5 个字母/数字），能顺畅解释“硬件最后维 stride 对齐要求”与“片上/算子内部重构不落地 HBM 冗余 padding”的原理。

### 练习 4：SGLang / vLLM 调度与无侵入插件机制对比准备
- **练习内容**：结合理想汽车面试官提及的 `SGLang` 主力架构与多客户 `vLLM` 兼容需求，整理 SGLang（RadixAttention 前缀树缓存、Zero-Overhead 调度）与 vLLM（PagedAttention、`block_table`、平台插件 `Platform`/`Worker`/`CustomOp` 注册机制）的设计异同。
- **验收标准**：能够明确区分“必须改主体模型文件的场景”与“可通过注册自定义 Op/Backend 无侵入替换执行路径的场景”，并清晰画出 `block_table` 形状与物理寻址过程。
