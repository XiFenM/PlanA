## 1. 结论先行

这场面试最可靠的正向信号，是你确实做过自研 AI 加速器上的框架适配，并能把硬件约束落到权重布局、视觉算子中间张量、KV Cache 分块和运行时调度上。离线权重重排、多模态输入通道对齐导致 OOM、Paged KV 的块生命周期，是本场最有区分度的三个案例。

双 ASR 也改变了旧报告的优先级判断。Padding 题的迟疑是真实存在的，但它不是本场唯一的 P0。更值得优先修复的是以下三组问题：

1. **低精度与量化基础不够扎实，且主导范围没有在回答开头讲清。** 你先以较强口吻描述了 FP4／FP8 到 W4A16／W8A16 的 AWQ 流程，后面才明确量化精度调优并非自己主导。RMSNorm、BF16／FP16、FP8 格式的讨论中，工程处理有实践，但理论解释出现了明显松动。
2. **运行时与并行知识还没有形成稳定的不变量模型。** Padding／position／KV slot 没有先分语境，TP collective 被说成固定插入规则，Prefill／Decode 又被过快映射到 TP／PP；这些不是三个孤立口误，而是同一种 shape 与数据流推导能力不足。
3. **项目案例有真实内容，却缺少可复现的证据契约。** 10%–20% 的布局收益、接近百倍的局部张量膨胀、TTFT 降低，都没有伴随基线、绝对值、shape、dtype、统计口径、正确性阈值和不适用边界；MTP 等技术也容易停留在用过功能而未说明机制与适用条件。

一句话画像：**你已经具备较强的异构推理适配与跨层问题定位经验；当前面试竞争力的主要瓶颈，是基础概念的精确性、系统方案的条件化推导，以及把真实项目经验压缩成可验证的工程证据。**

## 3. 逐题表现重新校准

### 3.1 自我介绍：内容真实丰富，但岗位主线不够聚焦

你把经历分成了三类：推理框架与模型适配、性能优化与定位、客户测评和问题复现。[E1]

优点是覆盖面完整，也能让面试官知道你并非只做单个算子。问题是模型名、项目名和工作项较多，最强案例出现得较晚；框架、算子、运行时、客户协作之间的主次不够鲜明。面试官听完后仍需要重新选择一个方向深挖。

下一次应把自我介绍压成四个信息块：

1. 当前定位：自研加速器上的推理框架与性能工程；
2. 主导边界：自己主导的模块、协作完成的模块、仅参与的模块；
3. 两个最强结果：离线布局重排、多模态 OOM／TTFT 定位；
4. 岗位连接：希望把云端／数据中心 ASIC 经验迁移到端侧确定性、内存和时延约束。

### 3.2 模型部署、量化与 Paged KV：运行时实践强于量化算法

这一部分展示了真实的部署链路：检查模型结构和硬件支持度、抽取小规模算子 case、做单卡适配，再接入框架执行链。你对 Paged KV 的块分配也不是只会背概念；在多轮追问后，能够说明 Prefill 和 Decode 使用同一逻辑 KV 空间，末块未满时继续写，超过块边界后分配新块，请求结束后释放，不需要在块之间搬运。[E3]

需要校准的地方有三项：

- **量化 ownership 出现前后落差。** 你先描述了用 AWQ 处理 FP4／FP8 权重，后面才说明量化精度调优由其他同事主导，自己主要参与导出后的跑通和适配。[E2] 这不等于能力造假，但会让面试官担心边界表达。以后第一句就应区分主导、参与和调用工具。
- **量化路径表述存在技术风险。** AWQ 的典型语境是从较高精度基准权重做 activation-aware 的 weight-only 量化；若真实流程是从原始高精度权重重新量化，应明确说出。若是对已量化 FP4／FP8 checkpoint 再转 INT4，则要解释二次量化误差。当前回答没有把输入权重来源、scale 粒度、校准集和精度验证讲清。
- **KV Cache dtype 前后矛盾。** 在量化追问中，你顺着面试官确认过 KV Cache 使用 FP16；后半段又说明硬件主要使用 BF16、激活为 BF16。两份 ASR 都保留了这处矛盾，但无法判断是口误、把 A16 泛称为 16 位，还是不同路径确实使用不同 dtype。下一次必须明确区分权重 dtype、激活 dtype、KV Cache dtype 和 opmath dtype。
- **新型注意力机制是已确认的知识边界。** 对 Linear／Hybrid Attention 的状态管理，你明确表示尚未深入。[E4] 这是诚实且正确的应对，但对于推理框架岗位，它应进入后续补课清单。

此外，你把不足 256 token 的前缀描述成与 Prefix Cache 不兼容，这个说法不够准确。更精确的表述应是：若缓存系统按完整 block 计算可复用前缀，未满尾块通常不能作为完整可共享块复用，会形成粒度和碎片代价；这不等于 Prefix Cache 功能整体不兼容。[E3]

本题校准结论：**Paged KV 与常规 vLLM 执行链是较强实践项；量化是推理接入级经验，不应包装成算法主导经验。**

### 3.3 权重布局与 TP：一个强案例，一个薄弱回答

离线权重重排是全场最成熟的案例之一。你交代了跨 stride 取数的访存问题、只重排静态权重而不强迫激活保持同一布局、在模型加载期完成转换，以及自述的 10%–20% 收益。[E5]

它仍缺少两类证明：

- 根因证明：到底是自研 HBM 的 bank/channel 映射冲突、不连续访问、transaction 浪费还是其他机制；
- 基准证明：代表性 M/N/K、dtype、batch、硬件频率、warm-up、重复次数、p50／p95 和正确性容差。

TP 回答则明显弱一些。你把 AllReduce／AllGather 说成较通用的插入方式，并把最终聚合与 Softmax 联系起来，但没有根据 column-parallel／row-parallel、分片轴、sequence parallel 和下游张量需求推导 collective。[E6] 这会给面试官一种做过通信算子接入、但对标准并行分解掌握不够系统的印象。

本题校准结论：**硬件布局优化强；分布式推理目前只能判为有接入和验证经验，不能据本场判为架构级掌握。**

### 3.4 多模态视觉前端：最能代表你能力的案例

两份 ASR 都支持以下因果链：视觉输入通道数较小，将通道移到受硬件 256 对齐约束的末维后，局部激活／中间结果产生巨大填充，导致 OOM 或明显的首 token 延迟；在算子同事提示异常 memory-bound 后，你们检查 shape，通过合并相邻维度、推迟恢复原形状来减少物化的 Padding。[E7]

这个案例的优点不仅是解决了问题，还体现了：

- 能从端到端症状回到算子 shape；
- 能承认最初遗漏了 Padding 因素，并利用协作信息修正定位方向；
- 能在框架表示和底层算子之间调整张量语义。

旧报告把它写得略显确定。双 ASR 只能确认局部张量接近百倍膨胀和 TTFT 得到降低，不能确认整体模型显存提升了同样倍数，也不能给出绝对改善量。精确算子名和被合并的维度也有识别噪声。

本题校准结论：**这是最适合做 STAR 案例的项目，但必须补上单位、具体 tensor、前后绝对值、正确性回归和动态 shape 边界。**

### 3.5 Prefill、Decode、MTP、Padding 与 KV 生命周期：知识点多，条件化不足

你能正确抓住常见启发式：Prefill 往往更偏计算密集，Decode 往往更偏访存；也能解释 Chunked Prefill 把长请求切片，使 Decode 请求能穿插调度，从而控制在线请求时延。[E8] 后续关于块追加、跨块分配和释放的说明也较完整。[E3]

问题集中在从启发式到方案的推导：

- 把 TP 主要对应 Prefill、PP 主要对应 Decode，过于绝对。是否采用 TP／PP 要同时看模型能否装下、单 token 批量、通信拓扑、流水气泡、首 token 和 inter-token latency；PP 并不会因为 Decode 偏访存就天然更合适。
- 对 MTP 的解释偏功能使用层，并把它说成使用一个草稿模型。若讨论的是模型内置 MTP heads，它与独立 draft model 的 speculative decoding 不是同一实现；需要先说清具体算法，再补前向代价、验证开销、接受率或平均接受长度，以及错误分布对收益的影响。
- 面试官还追问了 FastV，你在没有听清后转而回答投机采样／MTP，没有回到 FastV 本身。FastV 属于多模态视觉 token 处理方向，与 speculative decoding 不是一个问题；这是一次明确的漏答。更好的处理是请对方解释缩写，确认问题后再答，不要用相邻熟悉概念替代。
- `max_num_batched_tokens` 一类预算参数不能只按 Prefill 大、Decode 小来背结论，应结合调度目标、并发量和 P99 延时测量。
- Padding 题中，你先从生成 token 向右追加推出右 Padding，之后改成左 Padding，又进入 KV Cache 优化话题，没有先区分稠密 prompt batch、生成方向和 Paged KV 的 slot／block 表示。[E9]

Padding 不是简单的记忆错误，而是一个答题方法问题：**在语境含混时，你倾向于先给结论，再补定义。** 对框架岗位，更稳的做法是先声明张量表示、有效长度和不变量，再讨论左右 Padding 是否存在。

K／V 连续或交错布局可以保留为硬件适配信号，但 ASR 无法恢复寄存器宽度、lane 数和精确地址公式，因此不能像旧报告那样把它写成已经验证的具体 SIMD 布局。[E10]

### 3.6 MoE、RMSNorm 与低精度：工程处理存在，理论解释需优先补强

MoE 部分你主动说明参与不多，主要讲到路由、Top-K 和后续计算的融合方向。[E11] 这说明你了解问题形态，但本场没有证明你负责过 token permutation、grouped GEMM、combine、expert parallel 通信或单 kernel 设计。旧报告把 Operator／Fusion 评为强，依据不足；更合适的是中等偏上，强项主要来自布局和视觉算子案例，而不是 MoE。

RMSNorm 部分有一个实际正确的工程选择：低精度实现出现差异后，最终使用 FP32 计算以保证稳定。[E12] 你也能说明 BF16 的指数范围接近 FP32、尾数更短。然而后续把 LLM 能使用 FP4／FP8 类比为 BF16 小数精度下降通常问题不大，这个推理不成立。权重量化、激活量化、累加精度和归一化敏感算子有不同的误差传播机制；FP8 的格式选择和 scaling 也不能只按总位数比较。面试官追问 FP8 常用格式时，你没能稳定说出 E4M3／E5M2，这进一步说明当前知识还没有形成可随时调用的结构。

本题暴露的是两层差距：

1. 你知道某些敏感算子需要 FP32，但还不能稳定解释 mean-square、累加误差、溢出／下溢、舍入误差和 scaling 的区别；
2. 遇到不确定的位宽细节时仍继续推断，而不是明确边界并回到可验证的实验。

这比单独背熟 FP8 格式名称更重要，也是未来两周的首要补强项。

### 3.7 反问环节：有技术兴趣，但岗位研究和提问设计不足

从对话顺序看，你关注了车端模型规模、C++、自动编译和 JIT 等问题。[E13] 这些方向与岗位相关，但反问中多次先给出自己的假设，例如车端模型较小、通信要求不高、主要是一两块芯片，再由面试官纠正或补充。

反问更适合用来获取决策信息，而不是验证未经调研的猜测。下一次优先问：团队当前优化目标的排序、框架与编译器／Runtime／算子的职责边界、板端 profiling 和回归手段、入职三个月的典型交付。这样既能显示岗位理解，也能帮助你判断匹配度。

| P0 | Prefill／Decode 到 TP／PP／MTP 的推导过度概括，并漏答 FastV | 高：[E8] | 每个方案都给 workload、瓶颈证据、通信／验证开销、收益条件和反例；区分内置 MTP heads、独立 draft model 与视觉 token 优化 |
| P1 | 工程案例缺 benchmark 与正确性契约 | 高：[E5、E7] | 六张案例卡全部补齐绝对值、相对值、shape、dtype、统计口径、容差和边界 |
| P1 | 反问中假设较多、获取的信息价值不高 | 中：[E13] | 提前调研产品与岗位，以指标、职责、工具链和前三个月交付为主线 |
| P2 | Linear／Hybrid Attention 未深入 | 高：[E4] | 能解释状态结构、复杂度、KV／recurrent state 管理和混合层调度 |
| P2 | C++／编译器缺可展示证据 | 证据空白 | 做一个可运行的小项目补展示；不能从本场反推为不会 |

## 6. 下一次回答应采用的结构

以下是建议模板，不是对本场原话的复述。

### 6.1 项目案例

`场景与目标 → 基线 workload → 定位证据 → 根因 → 自己主导的修改 → 正确性验证 → 性能结果 → 代价与边界`

每个案例至少准备：

- 一个绝对指标，例如毫秒、GB、GB/s 或 tokens/s；
- 一个相对指标；
- 一个正确性指标；
- 一个失败条件或不适用场景；
- 一句 ownership 说明。

### 6.2 歧义题

1. 先确认问题指的是稠密张量、continuous batching 还是物理 KV；
2. 画出最小 shape；
3. 标明有效长度、position、mask、logits 读取位置和 KV 写入位置；
4. 推导结论；
5. 说明不同后端可能有不同表示。

### 6.3 不完全熟悉的问题

先说清已经掌握的边界，再用不变量推演，最后指出需要查实现的部分。Linear Attention 那一题中明确说未深入是对的；下一步只是把后续推演补得更系统，而不是勉强给出确定答案。

### 6.4 量化 ownership

把工作拆成四层：算法选择与校准、权重导出、Runtime 加载与格式适配、精度／性能回归。逐层说明自己主导、协作或仅使用工具，避免面试官在后半段才发现角色边界。

## 7. 学习路线

路线按每周 10–12 小时设计。重点是产出下一次面试能展示的证据，不以阅读量为目标。

### 未来 2 周：修复最容易失分的基础与表达

#### 任务 A：低精度与 RMSNorm 数值实验（6 小时）

- 实现 FP16、BF16 输入下的低精度累加与 FP32 opmath 两版 RMSNorm；
- 扫描 hidden size、输入幅值和异常值，记录 max-abs、relative error、Inf／NaN；
- 整理 FP16、BF16、FP8 E4M3／E5M2 的指数、尾数、动态范围与典型用途；
- 明确 RMSNorm 使用 mean-square，而非去均值 variance。

验收：能在 5 分钟内解释溢出、下溢、舍入和累加误差的差别，并用实验图支持结论。

#### 任务 B：量化流程边界图（4 小时）

- 画出高精度权重到 W8A16／W4A16 的完整流程；
- 标注校准集、scale 粒度、zero-point、敏感层例外和精度回归；
- 把自己过往项目按主导／协作／使用工具重新标注。

验收：能够回答输入 checkpoint 是什么精度、为什么不是二次量化、如何找首个发散层，以及哪些工作并非自己主导。

#### 任务 C：TP／PP 与 Paged KV 手算（6 小时）

- 为一个两层 Transformer、TP=2／4 手推 QKV、O、gate/up、down 的每卡 shape；
- 记录每个 AllReduce、ReduceScatter、AllGather 的触发条件和通信字节数；
- 用三个不等长请求画 Prefill、两步 Decode、末块追加、跨块分配和释放；
- 分别说明 dense left padding、生成向右追加和 slot／block table，不混用三种语境。

验收：面对变体题时先画 shape，再决定 collective 或 Padding，而不是先背结论。

#### 任务 D：重写六张工程案例卡并录两次模拟面试（6–8 小时）

六张卡建议覆盖：布局重排、多模态 OOM／TTFT、Paged KV、TP 通信验证、MTP 精度定位、RMSNorm。每张按第 6.1 节补齐指标与边界。两次录音复盘只统计三件事：是否先限定语境、是否讲清 ownership、是否给出验证指标。

两周交付物：一份数值实验报告、一张量化流程图、两张运行时／并行推导图、六张案例卡、两次模拟面试复盘。

### 未来 1 个月：把薄弱点变成可运行证据

#### 项目 1：可调试的 weight-only 量化实验（10–12 小时）

- 从 FP16／BF16 基准权重分别做 INT8 weight-only 和 AWQ INT4；
- 比较 per-channel／per-group scale 和不同校准集；
- 做逐层输出对比，记录首个显著发散层和 mixed-precision exemption；
- 汇总模型大小、精度、latency 和吞吐变化。

验收：不只会调用工具，还能解释每个配置影响了什么误差来源。

#### 项目 2：Prefill／Decode 性能与调度实验（8–10 小时）

- 固定模型、硬件、输入／输出长度、并发度、warm-up 和重复次数；
- 记录 TTFT、TPOT／ITL、tokens/s、p50／p95／p99 和峰值内存；
- 改变批 token 预算、Chunked Prefill 和并行配置；
- 若模型支持 MTP，记录接受率、平均接受长度和验证开销。

验收：能说明 TP、PP、MTP 分别在什么条件下收益、无收益或退化。

#### 项目 3：C++ Paged-KV 最小实现（12–16 小时）

- 实现 block allocator、末块追加、引用计数、prefix 共享和回收；
- 用 RAII 表达所有权，加入并发测试、边界测试和 sanitizer；
- 输出碎片率、分配耗时和不同 block size 的权衡。

验收：用代码证据补上本场没有直接考察的 C++ 系统工程能力。

一个月交付物：三份可运行项目、一份统一 benchmark 模板、一次针对推理框架岗位的 45 分钟模拟面试。

### 未来 3 个月：形成编译器—Runtime—算子—测量闭环

建议只做一个主项目，避免再次形成知道很多名词但证据分散的状态。

#### 主项目：小型异构推理执行器

阶段一：从 ONNX、`torch.export` 或自定义 IR 导入一个小 Transformer，实现 shape／type inference、常量折叠、DCE、简单 fusion 和 layout propagation。

阶段二：加入静态权重预打包、Paged KV allocator、Prefill／Decode 调度和一个可替换的 attention backend。

阶段三：加入 INT8／INT4 weight-only 路径、RMSNorm FP32 opmath 和逐层正确性对比。

阶段四：建立 benchmark dashboard，统一记录 TTFT、TPOT、吞吐、尾延时、内存和每项优化的 IR／布局变化。

验收标准：

- 每个 pass 有前后 IR diff 和测试；
- 每项优化都有基线、正确性容差和性能数据；
- 能解释布局变化如何影响算子和 Runtime；
- 能在 20 分钟内完成系统设计讲解，并指出端侧 deadline、静态内存和失败降级如何进入设计。

每两周做一次固定复测，题目轮换覆盖低精度、量化、TP／PP、Padding／KV、Linear／Hybrid Attention、C++ 所有权、图编译 pass 和车端时延预算。

## 10. 最终边界

本报告不评价人格、职级或录用概率。所有性能数据均来自面试自述，没有代码、日志、设备计数器或独立 benchmark 支撑。双 ASR 能显著改善对话主旨和角色边界的理解，但不能替代人工听录音；尤其是专有名词、英文缩写、寄存器单位和精确算子名，仍需本人按原音频复核。

最值得你保留的不是某个框架名，而是已经形成的工程习惯：从硬件限制、张量 shape 和运行时数据流定位问题。最值得你改变的是回答方式：**先限定条件，再画出不变量；先讲自己做了什么，再讲系统做了什么；先给验证证据，再给性能结论。**
