## 重点案例复盘

### 1. Conv3D：把有记忆点的问题补成可验证的张量变换

这段最有价值的地方，是把 OOM 和首 token 慢联系到一个具体的物理布局约束，而不是笼统归因于模型大。（Q2）

需要收紧的首先是单位。“512 字节对齐”和“3 补到 256”可能在某种 dtype 下对应同一约束，也可能是不同层面的说法，当前材料不足以选择。不要直接复述底稿中的“整体显存扩大数百倍”。其次，合并几个维度必须保持卷积语义，并满足下游 kernel 的布局约定，不能只说 reshape 后就等价。

建议把案例固定为下面一条可复查的链：

`原模型/版本与 shape → 物理布局及对齐单位 → 实际 allocation/padding → 为什么导致 OOM 或读写浪费 → 修改后的索引映射 → 精度、峰值内存、首 token 耗时对比`

至少补一张原始与变换后张量表：每一维含义、dtype、stride、逻辑元素数、物理字节数，以及变换是否触发拷贝。再用一个很小的输入验证变换前后卷积结果一致。算子内部由谁实现、你负责什么接口和验收，放在案例开头就能让后续贡献更明确。

### 2. 权重预排布：把格式知识和性能证据分开

Q3 中“小 batch 下权重读取压力大，所以考虑加载时预排布”的分析路径有工程意义。NZ 的块间列优先、块内行优先类比也有官方格式依据。[Ascend 数据格式说明](https://www.hiascend.com/document/detail/en/canncommercial/850/opdevg/Ascendcopdevg/atlas_ascendc_10_0099.html)

但换成 NZ 类布局不会自动证明减少了 bank conflict。必须确认瓶颈是 HBM 访问、DMA 传输、片上存储冲突，还是格式转换与计算单元接口不匹配。一个格式在不同芯片上的作用也可能不同。

下一次把 `M/N/K、dtype、batch、原布局、目标布局、实际搬运字节、带宽、kernel 时间、端到端时间` 放在同一张对比表。把加载时 pack 的一次性开销列出，再说明为什么能在重复推理中摊销。缺少原始数字时明确说需要回查记录，不补写加速比。

### 3. 偶发乱码：保留排障过程，明确同步契约

Q4 比单纯介绍一个性能优化更能展示排障思路：先定位数值偏离，再观察调试手段如何改变复现，最后缩小到异步执行边界。增加打印或同步后故障消失，是有价值的线索。

不过，这个现象也可能改变调度、缓冲区生命周期或执行重叠，不能单独证明某个 Host padding 任务没有完成。下一次需要准确回答四个问题：谁生产数据、谁读取数据、哪个完成信号覆盖哪一步、何时允许复用内存。

以下是**建议核查的通用依赖顺序**，不是已经还原的现场实现：

`Host 数据准备完成 → H2D 拷贝入队/完成 → 消费这些数据的 kernel 执行 → 缓冲区安全复用`

分别画出故障路径和修复路径，标出线程、流、Event 与缓冲区拥有者。补修复前后的同负载复现统计，以及取消 debug 同步后仍能通过的压力回归。设备流等待只覆盖其定义的工作范围；Host 侧任务必须有相应的完成关系，具体接口以自研 Runtime 为准。[CUDA 异步执行中的流与同步语义](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)

底稿加入的“锁页内存双缓冲彻底消除竞争”没有现场证据，本报告不采用。简历也应等回查原文与实际修复后再改写为准确的对象、机制、职责和结果。

### 4. 后端插件化：从“替换接口”走到“能解释对象和调用路径”

Q7–Q9 和 Q15 构成这场材料中最值得优先处理的一组问题。参考 torch_npu 和使用 AI 本身都不能说明方案好坏；关键在于你是否明确保留了哪些语义、替换了哪些机制，又验证了什么。

建议先把常见稠密 Tensor 的关系讲清楚：TensorImpl 包含 shape/stride 等元信息并关联 Storage；StorageImpl 管理 DataPtr 和容量；Allocator 负责分配与释放相关语义。设备对象、内存指针、算子 descriptor 和流状态不是同一个东西。本地固定源码可从 [TensorImpl](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/c10/core/TensorImpl.h)、[StorageImpl](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/c10/core/StorageImpl.h) 和 [Allocator](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/c10/core/Allocator.h) 开始。

再围绕一次 `empty → copy → add → copy back` 画实际调用路径：分发如何命中 PrivateUse1，内存从哪里分配，设备与流如何选择，不支持的算子如何处理，异常怎样返回。设备改名只是使用入口，不等于完成这些接入。[PyTorch PrivateUse1 官方教程](https://docs.pytorch.org/tutorials/advanced/privateuseone.html)

这个练习应区分真实设备、教学 mock 和 CPU fallback。仅让 `add` 返回正确结果不足以证明真正走了新后端；还要有分发路径、设备信息和数据搬运的验证。若只实现 mock，就明确标注模拟范围。

### 5. AI 编码验证：测试通过后，继续说明测试为什么可信

底稿的总览把你的回答概括成“只依赖端到端”，但逐题记录实际包含计划、测试与一定程度的代码检查。因此，不能抹去这些已经提及的做法。（Q15）

下一步要补的是测试设计背后的依据。例如，针对一次后端接口改造，可以先列出旧接口的 shape、dtype、alias、同步与错误处理约定，然后设计独立的参考输出和反例。让同一个生成过程同时写实现和一组只会通过的测试，无法形成充分的独立验证。

面试时可以用一个真实变更说明：你亲自审查了哪段关键代码；哪一个测试曾经失败；失败揭示了什么语义问题；修复后如何验证；哪些配置仍未覆盖。比罗列测试工具名称更能回答“你为什么相信它正确”。数值误差阈值也应按 dtype 和运算定义，不要求所有平台逐比特一致。[PyTorch 数值精度说明](https://docs.pytorch.org/docs/main/notes/numerical_accuracy.html)

## 基础题：保留正确主旨，补齐适用边界

| 主题             | 本次底稿呈现的主旨                                   | 下一步补充                                                                     |
| ---------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------ |
| Chunked Prefill  | 把长 prefill 分片，减少对 decode 的长时间占用        | 解释 token budget、ITL/TTFT 和吞吐权衡；用长短请求混合负载观察尾延迟           |

vLLM 官方文档明确讨论较小 token budget 对 ITL、较大 budget 对 TTFT 的权衡，不能把 chunked prefill 表达为所有指标必然同时改善。[vLLM 调优文档](https://docs.vllm.ai/en/stable/configuration/optimization/#performance-tuning-with-chunked-prefill)

FlashAttention 仍计算 dense attention；原论文的 I/O 复杂度依赖 SRAM 容量等条件，并非简单地把所有复杂度从二次降为线性。本次底稿的简化说法已经在审查中纠正，不能据此认定你在录音中讲错。[FlashAttention 原论文](https://arxiv.org/html/2205.14135v2)
