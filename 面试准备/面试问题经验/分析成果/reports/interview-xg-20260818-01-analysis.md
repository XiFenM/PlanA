## 主要亮点

### 1. 模型导入方法论完整

`00:51:33–00:55:44` 是整段最强的能力证据。你把新模型导入拆成跑通、精度对齐和性能优化，并能说明用公开数据集或官方结果校准、用 profile 找到异常 token/算子、再抽取最小失败用例交给算子团队。它同时体现了交付顺序、问题缩小能力和跨团队协作。

下一次应把这个方法论绑定到一个真实模型：模型与版本、首次失败现象、定位路径、你改了哪一层、算子团队改了什么、精度标准、修复前后时延或吞吐。这样才能从“流程讲得清楚”升级为“个人能力证据”。

### 2. 融合判断具有硬件约束意识

`00:55:47–01:04:31` 中，你没有只说“减少 kernel launch”，而是提到了自研芯片无法并发多 stream 时的 matmul+all-reduce 通算重叠、RoPE 奇偶切片和 shape 操作，以及 H2D/D2H 对流水线的打断。这说明你会从执行图、硬件能力和数据搬运三个层面看融合。

不足是案例没有闭环。面试官要的是一个你亲自完成的融合，而不是融合原则清单。

### 3. 能说明框架侧与算子侧的责任边界

你能够说明框架工程师负责定位、复现和最小化问题，算子团队负责底层修复。这种边界意识对异构硬件适配很重要。需要补强的是个人 ownership：哪些问题由你首次定位、你提交了什么最小用例、最终如何确认修复有效。

### 4. 对未参与内容相对诚实

传统 CV 框架、投机解码和部分量化问题上，你没有把团队经验全部包装成个人经历。诚实边界本身是优点。更好的表达方式是“我没有直接做过；我理解的机制是……；如果由我接手，我会用……验证”，这样既不夸大，也能展示迁移能力。

## 重点问题与更佳答法

### 1. 个人贡献和量化结果不足

问题：多个回答以“我们框架”“团队做过”“上游支持”为主，面试官难以判断你的级别和独立贡献。

更佳结构：

1. 背景与目标：模型、硬件、版本、基线和失败现象。
2. 个人责任：你负责的模块、决策和代码边界。
3. 定位过程：看了哪些 trace、shape、kernel 或通信指标，排除了什么。
4. 修改与协作：你改了什么，其他团队改了什么。
5. 验证：正确性数据集、误差阈值、性能 workload、回归范围。
6. 结果：绝对数值、相对提升、适用 shape 和仍然存在的限制。

### 2. KV Cache 相关概念混在一起

问题：在 KV Cache 命中问题上，你更接近在解释一次对话请求的生命周期和分块显存管理，没有清晰区分 PagedAttention、prefix caching、请求间前缀复用和命中率指标。

更佳答法：先明确“我没有做过命中率优化”，再分层回答：PagedAttention 解决 KV block 的管理和碎片问题；prefix caching 关注请求间可复用前缀；命中率需要定义统计单位并结合前缀长度分布、hash/block 粒度、淘汰策略和工作负载评估。最后说明你会观察命中 token/block、节省的 prefill 计算、额外管理开销以及端到端 TTFT。

### 3. 融合案例缺少实现闭环

问题：原则是对的，但缺少具体图和数据。

更佳答法：固定一个你最熟悉的案例，给出融合前后的算子序列、输入输出 shape、产生的中间张量、H2D/D2H 或 collective 位置、融合实现层、数值误差阈值、kernel 时间和端到端收益。还要说明什么 shape 下退化，以及 register/shared memory 或编译缓存带来的代价。

### 4. 框架路线显得被动

问题：你把路线概括为“上游支持什么就适配什么”，容易让人认为只承担机械跟随。

更佳答法：说明如何从客户 workload、硬件瓶颈和上游成熟度形成优先级，例如兼容性、收入/交付影响、性能潜力、维护成本和依赖风险。即使最终仍跟随上游，也应展示你参与过版本选择、特性取舍或回归门槛设计。

### 5. 投机解码和量化停留在概念层

问题：投机解码能讲基本原理，但没有本人经验；量化回答没有清楚说明方案、精度、kernel 或归属。

更佳答法：投机解码至少要能解释草稿 token、目标模型并行验证、接受/拒绝，以及接受长度、草稿开销、batch/序列分布对时延和吞吐的影响。量化则按权重/激活/KV 精度、校准方法、硬件 kernel 支持、精度回退、显存/带宽收益和端到端性能展开。没有做过时要明确标注为理解和验证计划。

### 6. C++ 基础需要立即补齐

材料中这是最明确、最容易被再次验证的短板。

- 可执行文件和进程内存：能够区分 `.text`、`.rodata`、`.data`、`.bss`，并解释 stack、heap 和静态存储期对象；已初始化与零初始化静态变量的落点不同。
- overload：同一作用域同名函数通过参数列表区分，不能只靠返回类型。
- override：派生类对基类虚函数使用匹配签名进行重写，代码中应使用 `override` 让编译器校验。
- name hiding：派生类声明同名函数可能隐藏基类的同名重载集，与 override 不是一回事。

不要只背定义。写一段含基类重载、派生类 override 和 `using Base::foo` 的最小代码，再用编译器观察不同调用。

### 7. Linux 进程诊断需要从“会用”升级到“会定位”

如果问题是“如何看某个可执行文件依赖哪些动态库”，可以用 `ldd <executable>` 做快速查看，再用 `readelf -d <executable>` 检查动态段。若进程已经运行，`/proc/<pid>/maps` 能直接看到实际映射的共享库，必要时结合 `lsof -p <pid>`；环境变量可从 `/proc/<pid>/environ` 核查。回答时要区分静态依赖、加载时解析和运行时 `dlopen`。

### 8. 转端侧意愿表达不够具体

“愿意继续了解”不会被理解为强烈拒绝，但也不足以消除岗位动机风险。更好的表达不是泛泛说有兴趣，而是说明：为什么端侧问题吸引你、云端经验能迁移什么、最缺哪三项知识、计划怎样在前 30/60/90 天补齐，以及你接受端侧路线不会持续追逐所有上游热点这一特点。
