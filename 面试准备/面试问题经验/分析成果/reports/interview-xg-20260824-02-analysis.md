## 重点问答复盘

### 1. 框架工作量与个人 ownership

面试官在 `00:10:27–00:13:45` 连续追问“具体做了什么”“工作量是否不大”“有没有比较大工作量的投入”，说明他不满足于“参与 vLLM/PyTorch 适配”这一层描述，而是在确认你是否主导过足够复杂的模块。

你的多流转单流案例逻辑成立，但你也承认它属于适配初期工作。问题不在于工作小，而在于回答没有立即补上更完整的 ownership 证据。更好的顺序应是：先用一句话说明模块规模和个人职责，再用多流案例作为其中一个决策点，最后给出代码面、测试矩阵和上线结果。

建议准备成下面这组字段：

1. 上游版本与目标硬件限制；
2. 你负责的目录、模块和接口边界；
3. 修改前后的执行时间线；
4. 正确性、性能和回归测试；
5. 代码量不是重点，但要说明设计、实现、联调和维护中哪些是你完成的；
6. 最终支持了哪些模型、shape 和部署场景。

### 2. 权重排布优化：最强案例，但还可更扎实

`00:14:04–00:17:40` 的回答是本轮表现最好的一段。你没有停留在“做了 MatMul 优化”，而是将问题连接到小 batch、访存瓶颈、block 级权重排布和加载期转换，并给出约 `20%–30%` 的收益。

报告仍不把“完全消除 bank conflict”或“已量产”写成无条件事实：前者是 AI 图的过度归纳，后者在主记录中的回答被转写成“是吗”，语境大概率是肯定，但字面不够干净。

下一次应补齐四类数字：

- 典型 `M/N/K`、batch、dtype 和权重 shape；
- 原布局与新布局的精确定义，以及 padding/对齐如何处理；
- kernel、算子和端到端分别提升多少，基线是什么；
- 精度回归、额外加载时间和显存开销。

这样才能把“有性能直觉”升级为“可以复现和审计的工程成果”。

### 3. vLLM 全链路与 PagedAttention

面试官在 `00:18:04` 明确给出了 scheduler、worker、model runner、backend 四个层次。你要求缩小问题范围是合理的，但随后只讲 KV block 对齐案例，没有先给出系统骨架，因此听感上更像“熟悉若干适配点”，而不是“掌握全链路”。

当被问到非连续 KV block 如何参与 attention 时，你说“按 block table 的索引读 slot”抓住了高层核心，并非完全错误；真正缺失的是继续解释：

- scheduler/KV cache manager 如何分配逻辑块并生成物理 block ID；
- model runner 如何把 block table、sequence metadata 和 query 交给 backend；
- paged attention kernel 如何按 block ID 与 block offset 定位 K/V、做 mask 和分块计算；
- 不连续访问带来的合并访存、tile、动态 shape 和 kernel specialization 问题如何处理；
- 你本人只负责到哪一层，和算子团队的接口契约是什么。

这段案例还需要先统一单位和数据结构。常见 vLLM 语境中的 `block_size` 指每个 KV block 容纳的 token 数，硬件的 `128/256 Bytes` 对齐则是另一层约束；主记录把 `32/64/256`、字节对齐和物理 block 混在一起，无法确认真实设计。如果确实用更大的物理分配承载较小逻辑 block，需要进一步说明 slot 粒度、内部切分、碎片开销、block table 是否增加一级映射，以及 attention kernel 接口怎样保持兼容。否则“物理分配变大但逻辑—物理映射完全不变”的说法是不完整的。

你在 `00:24:06` 明确说不清楚算子内部实现，边界表达是可信的；需要改进的是在承认边界之前，先把自己确实掌握的跨层数据流讲完整。

### 4. Prefix caching 与 vLLM V0→V1

你对 prefix caching 的回答只有“完全匹配后复用以前的 KV 块”，这遗漏了 block 粒度的 hash、引用计数、空闲/驱逐和部分前缀命中。面试官后续提到的另一个框架大概率是 SGLang 及其 RadixAttention，但原转写不干净，报告不把具体比较题写成百分之百确定。

V0→V1 方面，你能主动关联到自己适配过的异步准备/拷贝，这是有效局部证据；但核心调度变化由面试官先说，你随后才关联到 batched-token 预算。面试官所说“从 batch 调度到 token 调度”更适合作为口头概括；更精确的表述是：V1 用统一 scheduler 在每轮为请求分配 token 预算，不再严格拆分 prefill 和 decode 路径，从而更自然地组合 chunked prefill、prefix caching 和 speculative decoding。

建议用“架构—数据结构—一次调度—缓存生命周期—硬件适配点”五层准备，而不是背版本差异清单。

### 5. 端侧低时延设计与投机解码

`00:29:44–00:31:35` 中提出的 graph、CPU 开销、Tile 级调度和融合方向是合理的，而且与你已有的小 batch 与硬件适配经验相连。这段不足主要是没有先建立完整性能模型。

更好的开场应先澄清：模型与量化精度、prefill/decode 占比、上下文长度、batch、静态 shape 的粒度、内存层级、目标 TTFT/TPOT、功耗和精度边界。随后再按以下顺序设计：

1. shape bucket、padding 和内存/workspace 静态规划；
2. 权重、KV Cache 和中间张量的布局与常驻策略；
3. graph capture/预编译，减少 CPU 与 launch 开销；
4. kernel fusion、Tile 流水和访存复用；
5. 量化与精度回归；
6. prefill/decode 分路径优化；
7. 以 trace 和分层 benchmark 验证每项收益。

你对投机解码的担心并非毫无道理：最终收益确实取决于草稿成本、接受率和验证成本。但“小模型已经很小”不能直接推出“投机解码价值有限”，还需要比较 EAGLE/MTP/self-spec 等轻量草稿路线，并建立 `草稿开销 + target verify 开销 < 节省的逐 token 解码开销` 的 workload 模型。

### 6. MoE：云端经验与端侧设计之间存在明显断层

你能说明 MoE 的 top-k、dispatch、expert FFN、combine 和 EP，也接触过 Qwen、ERNIE 等 MoE 模型。这支持“做过模型适配”，但不能支持智能纪要中的“熟悉 fused MoE、DPEP 和 dispatch/combine 优化”：这些术语主要由面试官列出，你明确回答自己只是了解流程。

P/D 分离与 KV 传输的回答也需要更精确。你说当前小场景直接走 TCP/CPU 路径，这可能是合理的实测取舍，但没有给出上下文长度、层数、KV head、dtype、传输字节数和链路时延，不能只用 batch 小证明传输成本低。P/D 分离和 TP/DP/PP 也是不同维度；更好的回答应说明 P、D 两侧怎样分配 KV block，metadata 与 KV 如何交接，TP 度不同是否需要重分片，以及 CPU staging、P2P/RDMA、传输—计算重叠各自的适用边界。面试官所说“小 batch 没必要 P/D 分离”也不是普遍定律，隔离 prefill 对 decode 的干扰和控制尾部延迟仍可能有价值，最终要以 TTFT、TPOT/P99 和链路占用验证。

在单端问题中，你先使用了多卡冗余专家/EPLB 的思路。面试官两次提醒“单卡”和内存受限后，你仍没有主动形成静态执行方案，最终关键的 token 维度 padding/分桶也是面试官讲解的。这里应当形成下面这张设计图：

`router/softmax/top-k → token count/prefix sum → permutation/dispatch → 按专家分桶和 padding → grouped GEMM 或 fused expert kernel → unpermute/combine`

回答时要同时覆盖：

- 动态 token 数如何映射到有限的静态 shape bucket；
- padding 浪费、最大 workspace 和尾部小 GEMM 的取舍；
- expert weight 是否常驻、怎样减少碎片和搬运；
- 热点 expert 导致的串行尾延迟，而不仅是多卡负载均衡；
- 单端内存紧张时为何不能直接复制大量冗余专家；
- prefill 与 decode 的 token 分布不同，是否需要两套 kernel/bucket；
- 正确性、延迟 P50/P99、内存峰值和功耗如何验收。

### 7. 编程、C++ 与现场沟通

编程测试因为共享权限失败而取消，不能把“未完成测试”解释为“不会编程”。本轮只能确认你日常以 Python 为主，并自述在扩展 PyTorch 时使用 C++；C++ 基础、工程质量和调试能力仍与一面一样属于待验证项。

沟通上有两个可改进点：

- 面对不熟悉的问题，你有时先用“这很复杂吗”“跟一般优化差不多吧”回应，再等待面试官说明难点。这容易被理解为尚未识别问题却先下结论。更好的方式是复述约束、列出已知与未知，再提出一个验证假设。
- 结束时没有反问。考虑到一面已经出现端侧动机待确认，这会错失表达兴趣和校准岗位要求的机会。

## 对面试官技术提示的校准

面试官的提示能反映岗位关注点，但也不能自动当作唯一标准答案：

- “V0 从 batch 调度变成 V1 token 调度”是方向性简写，更准确的是统一 token-budget scheduler。
- “softmax + top-k 融合后不是瓶颈”通常成立，但 expert 数、token 数和硬件 backend 不同，仍应以 profile 判断。
- “端侧投机解码非常重要”是岗位经验判断，实际收益依赖接受率、草稿/验证成本、额外内存和功耗。
- “小 batch 没必要 P/D 分离”忽略了隔离 prefill 干扰和尾延迟控制等目标。
- “冗余专家在单端没有意义”对常见内存受限单卡通常是合理警告，但在多 cluster、独立 memory bank 等特殊硬件上仍需测量后判断。
- token padding 不必机械取 2 的幂，应该对齐到编译器支持的 shape bucket 或 kernel tile。

因此，复盘重点不是把面试官的每句话背成答案，而是学会在明确约束和指标后给出可验证的工程取舍。

## 优先准备清单

### P0：先补成能完整回答的四道题

1. **vLLM 一次请求全链路**：API server → engine/core → scheduler/KV cache manager → worker/model runner → attention backend → sampler/output；准备一张你们硬件适配点的叠加图。
2. **PagedAttention 与 prefix caching**：从 block table、逻辑/物理块、kernel 读取、block hash、引用计数、驱逐和部分前缀命中完整讲一遍，再比较 vLLM block-hash 路线与 SGLang RadixAttention 的数据结构差异。
3. **V0→V1**：不要只背异步拷贝；用统一 token 预算 scheduler 串起 chunked prefill、prefix caching、spec decode、KV cache manager 和 worker/model runner 的变化。
4. **端侧单卡 MoE**：手画 `route → dispatch → bucket/pad → grouped/fused expert compute → combine`，给出静态 shape、workspace、内存峰值和 P99 latency 的取舍。

### P1：把最强案例写成可验证工程故事

1. 为权重排布案例补全 `M/N/K`、dtype、布局示意、对齐、padding、加载成本、精度、算子/端到端收益和回归范围。
2. 为多流转单流案例画执行 timeline，说明修改模块、事件同步、正确性门禁和性能数据；不要把它单独包装成主要项目。
3. 准备一个你主导的最大模块，用“目标—约束—设计—代码边界—协作—指标—遗留问题”回答 ownership。

### P1：端侧性能知识闭环

1. 用 `TTFT / TPOT / P50 / P99 / 峰值内存 / 功耗` 描述目标，区分 prefill 与 decode。
2. 为 graph、融合、Tile 调度、量化、KV Cache、shape bucket 分别写出收益来源、适用条件和失败条件。
3. 为投机解码建立成本公式，比较 draft model、EAGLE/MTP 和 self-spec，不再只用模型大小作判断。

### P2：现场策略

1. 遇到陌生设计题先复述约束，再列“已知、假设、验证指标”，避免先说“应该和普通优化差不多”。
2. 如果问题很大，可以请求缩小范围，但先给 30 秒全景图，证明你知道各层如何连接。
3. 提前检查共享屏幕和本地编译环境；准备无法共享时用口述伪代码、复杂度和测试用例继续作答。
4. 至少准备三个反问：入职 90 天要主导的模块、端侧静态 shape/runtime 的当前最大难点、框架与算子/编译器团队的接口边界。
