## 对融合记录的技术整理

- “减少 tensor 形状变换”要区分只修改 metadata 的 reshape，与会真实搬运数据的 transpose、layout conversion 或 contiguous copy。
- H2D/D2H 是主机与设备之间的传输，设备端 kernel 融合不会自动消除它。回答时需要说明传输为何出现在两段计算之间，以及融合、异步化或流水化怎样改变数据依赖。
- “是否溢出到显存”还不够，应进一步检查峰值中间张量、register/shared memory 压力、occupancy、重计算、数值稳定性、动态 shape 和消费者 fan-out。
- 融合粒度不是越大越好；最终应以正确性回归、不同 shape 的稳定性和端到端 benchmark 决定。

以上是对简记内容的补全，不是对现场回答的纠错。

## 后续准备

### 1. 准备一个完整的 vLLM 适配案例

用固定结构讲述：上游特性与目标 → 自有硬件/runtime 缺口 → 修改的抽象层和执行路径 → 自己负责的代码与协作边界 → 正确性验证 → 性能结果 → 版本兼容和回归。至少准备一个具体 shape、一个绝对指标、一个相对提升和一个失败边界。

若涉及自研硬件插件，可对照官方的 [vLLM Plugin System](https://docs.vllm.ai/en/latest/design/plugin_system/) 检查自己实际改动的是 platform、worker、attention backend、device communicator、custom ops 还是其他层。该文档只用于统一术语，不代表本场使用的是当前官方插件方案。

### 2. 明确“v0-v1-v2”的语境

先回忆“v2”是面试官的内部称谓、你所在项目的代际，还是其他框架版本。无法确认时保留为待核实术语。版本比较要绑定具体 tag 或 commit，并按架构和代码路径说明，不要只按版本号罗列功能。

### 3. DeepSpeed 训练

准备一个实际训练配置，说明 ZeRO 不同阶段切分了哪些模型状态、对应的通信和显存代价，以及 offload、activation checkpoint 和吞吐之间的权衡。最好使用一个亲自处理过的 OOM、吞吐或稳定性案例。官方 [DeepSpeed ZeRO 文档](https://deepspeed.readthedocs.io/en/stable/zero3.html) 可用于核对当前配置项，但回答仍应以你实际使用的版本和数据为准。

### 4. Attention 融合粒度

分开讨论 prefill 与 decode。逐段检查 QKV、RoPE、attention core、KV Cache 读写和 output projection 的生产者—消费者关系；同时说明大粒度融合对中间张量、寄存器压力、动态 shape、KV layout 和可维护性的影响。

### 5. 前沿模型研究

准备一个从研究到工程决策的闭环：读论文和代码 → 提炼架构变化 → 判断对算子、显存和调度的影响 → 做最小 PoC/benchmark → 决定是否适配。只说“关注前沿模型”无法形成可验证的能力证据。
