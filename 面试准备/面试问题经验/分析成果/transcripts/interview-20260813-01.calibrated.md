## 3. 动态长度、Paged KV Cache 与 Linear Attention

**面试官（推定）：** VLM 输入是定长还是动态长度？如果 Decode 不断增长，KV Cache 怎么管理？

**候选人（推定，整理）：** 支持动态长度。vLLM 有基于 block 的 Paged KV Cache 管理机制，把 KV Cache 分成小 block。每个请求计算时分配若干 block，避免一次占用一整块很大的显存。

请求进入 ModelRunner 计算前，Worker 中的 Scheduler 会根据每个请求的需求计算逻辑 block 数，再把元数据交给下面的 ModelRunner。Decode 增长到需要更多 KV 空间时，就分配一个新的 block。

**面试官（推定）：** Block 多大？

**候选人（推定）：** 我们的 Block Size 固定为 256，这是硬件要求。CUDA GPU 上一般可以更小，比如 32。

> 校准备注：这里的 256 按上下文应是每个 KV block 的 token 数，但原答没有说出单位、vLLM 版本或自研后端配置。

**面试官（推定）：** 每一层的 KV Cache 怎么管理？Linear Attention 呢？

**候选人（推定）：** 每一层、每个 Attention 都有自己的 KV Cache。Linear Attention 这部分我没有仔细看过；我简单看过它和 Hybrid Attention 相关，但具体机制还没有深入研究。

## 4. 分块 GEMM 的权重布局优化

**面试官（推定）：** 讲一个你做过的算子优化。

**候选人（推定，整理）：** 以列优先的矩阵乘优化为例。矩阵乘会把 A、B 分块；取一个小块时，每一行可能取 256 个元素，然后跨到下一行继续取，中间有 stride。在我们的硬件上，这种访问会出现类似 CUDA bank conflict 的问题，但候选人称冲突发生在 HBM 侧，而不是 shared memory。

解决思路是对每 `[1024 的单位与含义待回听]` 的权重数据做搬移/重排，使分块后的数据更接近列优先访问。权重在模型加载阶段预排布，运行时不再承担转换成本，最终性能提升约 10%–20%。

只调整 Linear 层和 MoE 层的权重，不调整激活：激活还要被下一算子消费，下一算子未必接受同样的列优先布局。硬件强制每次按 256 个元素一组访问，所以分块预排布更匹配硬件。

> 校准备注：“HBM bank conflict”是候选人的现场归因。两份转写都没有给出 memory level、地址到 bank 的映射、硬件计数器、M/N/K、dtype 或 benchmark 口径，无法从文本独立验证。

## 6. Qwen3-VL Conv3D 的 OOM/TTFT 优化

**面试官（推定）：** 讲一下 Qwen3-VL 链路里 Conv3D 的端到端性能优化。

**候选人（推定，整理）：** 这个问题也与硬件有关。视频图像输入的 channel 是 3。为方便计算，适配 Conv3D 时把 channel 移到了最后一维；但硬件要求最后一维按 256 对齐，C=3 被 Pad 到 256 后，中间激活的存储接近膨胀百倍，容易 OOM。即使其他维度较小、数据能放下，从 HBM 读取大量填充数据也会使算子严重 memory-bound。

一开始只观察到算子异常慢，没有注意到 Padding。与算子同事一起检查参数 shape 后，发现了明显的对齐膨胀。最后把若干维度合并；现场举的数字是 3、8、12，合并后末维成为几百，不再把 3 单独 Pad 到 256。传入算子内部的缓冲区后，再恢复成原始 shape 进行计算。

这样未必消除了所有冗余计算，但显著降低了中间张量的显存压力，基本解决 OOM，并降低了首 Token 延迟（TTFT）。视觉 Encoder 主要在最初处理图像，后面已经变为 embedding，因此这一问题对 TTFT 特别明显。

**录音状态：** 此处双方“喂、你好”确认连接，语音似乎短暂中断；无法判断是否漏掉少量内容。

**面试官（推定）：** 听起来是依据硬件特性修改 shape、减少 Padding？你们是强制按 256 对齐？

**候选人（推定）：** 对，硬件只支持这种格式，所以必须按 256 对齐。我们做自研芯片，优化通常会先从硬件特性考虑。

> 校准备注：两稿都近似说出 `NCHW`，但视频 Conv3D 可能涉及 `NCTHW` 等五维布局；确切维序需要回听或查项目记录。3→256 对单个被物化维度的理论倍率约为 85.3，不等于整个模型显存都增长同样倍数。

## 8. Prefill 与 Decode 的优化重点

**面试官（推定）：** LLM 的 Prefill 和 Decode 在性能优化上，重点分别是什么？

**候选人（推定，整理）：** 一般来说，Prefill 更偏计算瓶颈，Decode 更偏带宽瓶颈。Prefill 要减少计算压力，可以用 TP 并行；Decode 阶段候选人提出可以采用 PP，并用 MTP 提高一次生成的 Token 数，充分利用计算能力。

vLLM 里还有一个类似 `max_num_batched_tokens` 的参数，用于控制每次迭代计算多少 Token。候选人认为 Prefill 阶段可以设得更大，Decode 阶段因关注单 Token 延迟，应该相对小一些。

> 校准备注：参数全名、是否按阶段动态设置，以及“Prefill 用 TP、Decode 用 PP”的适用条件都没有说清；这段应作为复盘对象保留，而不是整理成通用结论。

## 10. K/V 交错布局与 Block 生命周期

**候选人（推定，整理）：** 我们硬件的某个访问/寄存单元是 `[疑似 4 字节或 32 bit，专有术语待回听]`，可以放一个 FP32，或者两个 BF16。针对两个 BF16，会做交叉排布，把前后两组数据组合在一个 32-bit 单元中。

原先 vLLM 把 K Cache 和 V Cache 分开，我们把它们做成交错或合并布局，使访问更连续，便于在一整块 KV Cache 中存取。

**面试官（推定）：** 新 Cache 是按需申请？Block 固定为 256 会有什么问题？Prefix 和 Decode 两部分如何衔接？

**候选人（推定，整理）：** 对，按 block 分配。Block Size=256 的缺点是短请求也会占用一个较大的 block；Prefix Cache 如果只缓存完整 block，那么长度不到 256 的前缀缓存不上。

Prefill 和 Decode 操作的是同一套 KV Cache 数据。Prefill 把数据写到已经分配的 block；Decode 根据 block table 找到对应 block，继续往最后一个未满 block 的后面写。超过 256 的边界时，再申请一个新 block。Block 之间不重新搬运；请求结束后释放这些 block，供新请求复用。

> 校准备注：这段没有说明 K/V 的确切 layout/address formula、Prefix Cache 的哈希和引用计数，也没有讨论 block 共享或抢占。
