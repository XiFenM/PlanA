# 面试复盘回答

本目录保存逐场面试的复盘与参考回答。每场面试一份文档，沿现场顺序整理问题、追问、原回答的优点与不足，以及下一次可以怎样回答。

本流程根据 2026-11-08 已确认的复盘方式整理，[地平线复盘](地平线-2026-08-13.md)是首份完整示例。原始材料和历史分析仍由[上级目录](../README.md)导航；本目录用于形成面试准备材料，不替代原始记录或项目事实档案。

## 1. 复盘要产出什么

每道题回答以下问题：

1. **面试官问了什么，还追问了哪些细节？** 区分主问题、同题子问题和后续新话题。
2. **之前的回答哪里好、哪里不够好？** 保留已经答对的部分，指出概念、推导、表达、职责或证据上的具体缺项。
3. **怎样组织会更好？** 给出贴合题目的回答顺序、关键机制和适用条件。
4. **参考回答具体怎么说？** 提供可以直接用于面试准备的连贯回答，而不只列术语、资料链接或待办项。

涉及做过的项目时，引用现有[自我准备材料](../../自我准备/)。各场面试的自我介绍暂且搁置，全部面试复盘完成后再统一处理。

## 2. 工作方式与范围

- **本流程不使用 `guide-learning`。** 复盘直接围绕面试问题与答法展开，不转入开课、测验、验收或练习流程，也不更新课程账本、学习断点和实际学习时长。
- **不以重新回忆项目为前置。** 不要求用户再次讲述已有项目的全过程；已有事实先从项目档案、Case Card 和已确认的修订中读取。
- **发现具体缺项时才补项目描述。** 先指出现有描述缺什么、为什么影响这道题，再针对缺项补充。没有依据的参数、实现和数字保持未知，不为了使回答完整而杜撰。
- **实机待核细节集中追加。** 按用户 2026-11-14 的要求，后续复盘中需要回到项目代码、环境或测试记录确认的细节，统一加入[实机核查清单](实机核查清单.md)，写明关联题目、检查方法和所需证据；同一缺项沿用编号并补充关联场次。
- **按用户要求的节奏推进。** 用户指定一道题时，完成该题及其现场子问题；用户授权复盘整场时，连续补完整场实际问题，最后准备扩展问答，不要求逐题重复确认。
- **一场一份文档持续追加。** 已认可的内容保留在同一文档中；后续补题、修正技术表述或更新引用，不拆成多份重复稿。
- **反问按公司和岗位独立准备。** 按用户 2026-11-15 的要求，不在复盘中编写统一反问话术；准备具体面试时，结合该公司的岗位职责与团队情况单独整理。现场交流事实仍可从原始材料与历史分析追溯。
- **本目录的写入不附带其他动作。** 不自动制卡、生成学习记录、改写简历、提交或推送，也不自动启动下一场面试。

## 3. 材料怎么使用

不同材料承担不同职责，不将一份报告中的所有判断直接当成事实。

| 材料 | 用途与边界 |
| --- | --- |
| 原始文字记录、录音转写、校准稿 | 确认现场问题、回答主旨、追问顺序与职责表述；标明缺失段落、识别噪声及说话人不确定性 |
| 已有分析报告与技术审查 | 提供待复核的判断与线索；优先查看明确标注的修订版或校准版，并核对它修正了什么 |
| 简记、智能纪要、自动总结图 | 辅助发现主题；只有题目而没有现场作答时，不能评价原回答好坏 |
| [项目档案](../../自我准备/projects/README.md)、Case Card、[Claim-evidence 矩阵](../../自我准备/Claim-evidence矩阵.md) | 支持个人职责、真实改动、测试范围和结果；同一事实有冲突时，采用对应字段已确认的修订口径，不机械地以整个文件的更新时间裁决 |
| 官方文档、原始论文、固定版本源码 | 核验标准参考回答中的技术事实、条件和实现；注明关键版本，不将通用实现套成自研平台事实 |

具体处理规则：

- 校准转写是整理稿时，不把它加引号冒充逐字原话；题干只能恢复主旨时就说明这一点。
- 初答不完整，但后续追问已经补齐的，应评价为“初答不完整，后续补齐”，不能写成完全不会。
- 报告中的负面判断也要核验。技术配置不明确、概念没有展开、实际实现错误是不同结论，不能互相替代。
- 缺少现场证据不等于不会，缺少后续验收也不等于当前仍未掌握；后来的学习或项目可以支持当前参考回答，但不能倒填为当时已经展示的能力。
- 只有问题简记时，写“考察主题与参考答法”，原回答评价标明无材料可判断，不补写现场表现。

## 4. 问题与追问怎样归类

| 类型 | 放在哪里 | 怎样处理 |
| --- | --- | --- |
| 主问题 | 按现场顺序新建编号章节 | 保留题意与来源，整理原答分析及完整参考回答 |
| 同题现场追问 | 所属主问题章节中的子问题 | 补充该追问的原回答、不足、关键细节和参考回答；多个紧密相关追问可以一起回答，但要能找到各自答案 |
| 随后进入的新话题 | 下一个编号章节 | 不因紧跟前题出现就全部归为前题子问题；以话题和考察对象是否变化为依据 |
| 扩展问题 | 全文最后的“扩展问题与参考回答” | 标注关联题目；整场实际问题复盘完后统一准备，不写成现场已问，不评价不存在的原回答 |
| 候选人反问与双向交流 | 现场事实保留在原始材料与历史分析；反问按目标公司和岗位独立准备 | 明确交流性质，不作为面试官考题，也不编写统一反问话术 |
| 自我介绍 | 暂不展开 | 全部面试复盘完成后统一处理 |

例如，地平线第一题中的 AWQ 和 W4A16 是部署流程的现场子问题；动态输入与 KV Cache 管理成为第二题；“模型已被 vLLM 支持，为什么还要适配”等补充问题放在文末。

原回答主动展开的细节，可以作为该题分析和参考回答的内容，但不能改写成面试官已经提出的独立追问。

后续实际问题始终插入扩展章节之前。逐题复盘期间，文末可以先保留扩展题目和准备要点；完成整场时，应补成实际参考回答，不留下只有题目的空提纲。

## 5. 单题的分析与参考回答

### 5.1 评价原回答

先还原回答覆盖的内容，再说明不足。按题目需要检查以下方面，不要求每题机械套满：

- **概念是否准确**：是否混淆相邻概念、不同精度、逻辑表示与物理实现。
- **机制是否连贯**：能否从输入、Shape、状态与依赖解释结果，而不只报框架或算子名称。
- **条件是否明确**：是否把某个配置、版本或负载下的做法说成通用规则。
- **表达是否回应题意**：有没有漏答，或用熟悉的相邻话题替代未听清的问题。
- **个人职责是否清楚**：自己负责、协作完成、其他团队实现的部分有没有分开。
- **验证是否支撑结论**：正确性、性能与覆盖范围是否对应，是否把相关现象说成已证明的根因。

原回答已经正确时，可以直接肯定，并补充必要条件；不为了生成“缺点”而强行挑错，也不根据技术回答推测面试官心理或录用结果。

### 5.2 写出更好的答法

回答结构按题目选择。例如：

- 流程题：阶段与目标 → 关键接口 → 完成判据 → 项目例子。
- 机制题：对象与状态 → 数据流或控制流 → 设计理由 → 条件与边界。
- 优化题：负载与基线 → 定位证据 → 修改与职责 → 正确性 → 性能及代价。
- 对比题：固定比较条件 → 两种方案的机制 → 收益与成本 → 适用场景。

必要时给出 Shape、公式、小例子或映射表，让推导可检查。变量先说明含义、维度与单位；例子明确标为解释性示例，不将示例数字写成项目数据。

### 5.3 形成完整参考回答

- 使用连贯、可直接表达的中文，保留必要技术名词。先回答问题，再展开关键机制和边界，不用一串名词代替回答。
- 根据题目复杂度决定长度；主回答交代主线，现场子追问继续展开细节，不强制所有题采用相同篇幅。
- 第一人称经历只使用现有材料支持的事实；通用方法用“我会”或条件分支表达，不能自动升级为“我已经做过”。
- 区分源码或论文解释、项目事实与推断。涉及实现差异时绑定版本，不把某个平台的默认行为说成所有平台都成立。
- 项目数字同时保留模型、运行栈、负载、计时范围与测试组。不同测试组不能拼接成一次优化结果，联合改动的收益不能随意归给其中一项。
- 后续材料已明确修订旧数字或职责时，采用已确认的新口径，并链接到依据；历史原始记录保持原样。
- 技术依据就近链接到官方资料、论文或固定源码；项目依据链接到仓库现有材料，不重复复制完整项目档案。

## 6. 每场文档的组织

文件名以公司、已确认的面试日期和必要轮次区分，例如 `地平线-2026-08-13.md`；同公司同日多轮时加轮次。日期未知就使用“日期未确认”等明确表述，不拿报告生成日期或文件元数据冒充已确认的面试日期。

同一场面试的初版报告、校准版和技术审查是不同证据版本，归入同一份复盘文档，不重复算成多场面试。

文档头部记录面试信息、整理日期、来源与材料完整度，并提供问题导航。以下骨架可按题目复杂度调整；没有现场子追问时，不必创建空的子问题节。

```markdown
# 公司／场次面试复盘回答

- 面试日期、轮次：按已确认信息填写。
- 整理日期：YYYY-MM-DD。
- 分析依据：链接原记录、校准稿及报告，说明材料限制。
- 覆盖范围：已完成哪些内容，自我介绍暂缓。

## 问题导航

按现场顺序链接各题，并标出对应来源位置。

## 1. 第一题

### 1.1 问题与现场细节
### 1.2 原回答的优点与不足
### 1.3 更好的回答方式
### 1.4 参考回答
### 1.5 现场子问题

每个子问题包含：现场题意、原回答评价、关键细节、参考回答。

## 2. 下一道实际问题

沿用上述方式；与前题重复的机制可以引用已有章节。

## 扩展问题与参考回答

### E1. 扩展问题

标注关联题目，给出参考回答及必要依据；不进行现场表现评分。
```

章节号服务于单场文档的阅读顺序，不等同于报告或转写的章节号；通过导航保留两者对应关系。参考[地平线文档](地平线-2026-08-13.md)中的现场问题导航、同题子问和文末扩展组织。

## 7. 实际执行顺序

1. **确认本轮范围并读取现有材料。** 按用户指定的场次或题目工作，优先读校准稿和已修订分析，必要时回到文字记录；不默认重做音频处理。
2. **整理现场问题顺序。** 分清主问题、同题追问和新话题，自我介绍跳过；扩展候选先放在文末，反问按目标公司和岗位另行准备。
3. **核对原答与技术判断。** 同时保留答对的内容、明确缺项和不确定处；需要核验的事实查一手资料或固定源码。
4. **引用项目事实并写参考回答。** 读取相关项目和已确认修订，按真实职责与证据范围组织，发现具体缺项再处理。
5. **写入同一场文档。** 逐题模式完成本题及其子问；整场模式覆盖全部实际话题后，再补齐扩展回答和导航。
6. **检查覆盖、技术与引用。** 确认每个实际问题和子追问都有去处，标准答法可直接使用，项目边界与引用一致。

开始后按已授权范围自然推进，不为每个步骤重复请求确认。用户改变题目或范围时，沿用已经完成的内容继续调整。

## 8. 完成检查

- 实际问题按现场顺序覆盖，同题追问没有遗漏；含混题干没有被补成确定原话。
- 每题都有原回答分析和完整参考回答；只有简记的材料明确说明无法评价原答。
- 扩展题位于全文最后；整场完成时已经有答案，不混入现场评分。
- 原答正确部分、后来补充、当前技术参考与真实项目事实分别标明。
- 公式和技术结论有必要的假设、单位、版本与适用范围，项目数字没有跨模型、负载或测试组混用。
- 自我介绍仍然暂缓；没有顺带开始下一场或修改学习状态。
- 仓库内链接使用相对路径，文件与锚点可定位；检查 Markdown 格式并运行 `git diff --check`。新增未跟踪文件也要单独检查空白和链接，不能只依赖 Git diff。
