## 1. 工作分配、交付模型与规模

**现场题意与定位。** `00:41:52–00:43:33`。记录从工作分配的回答中途开始，随后问交付哪些模型、“小模型”有多小。原答说第一年以框架和模型适配为主，第二年约 30%–40% 用于客户测评及问题定位；提到 Qwen、Llama、GLM 家族，以 100B 以下为当时参照，并称更大模型的多卡通信尚不完善。

**原答复盘。** 工作结构和接触范围讲清了，但“小”是相对概念，100B 不能作为统一分界；团队遇到通信问题也不能直接归为个人未解决。具体 GLM 型号不可靠，不能用后来 GLM-5.3-Flash 的交付补写这次经历。

**更好的回答方式。** 先给阶段性职责，再说明模型范围和实际交付边界；用参数量、精度、上下文、并行配置描述负载，不用“大／小”代替配置。

**参考回答。**

> 当时第一年主要做框架和模型适配；客户增加后，第二年约三到四成时间用于测评和问题定位，其余仍围绕推理链路。两部分有交叉，例如客户问题会转成框架修复和回归用例，因此这是工作投入的粗略描述。
>
> 我主要负责过 Qwen2.5-VL、Qwen3-VL 和 ERNIE 4.5-VL 的框架接入、精度对齐与性能定位。我会逐项说明本人改动和算子协作，不能仅列模型家族就表示所有型号或机制都由我实现。
>
> 当时说 100B 以下较小，是相对于团队云端部署范围，不适合直接套到端侧。部署难度还要看权重格式、KV 容量、上下文和并行方案；更大模型的通信问题是团队当时的现状，具体到我负责的内容，应再落到明确的调用与验证范围。

个人职责采用[已确认的 CL03 修订](../../自我准备/Claim-evidence矩阵.md#claim-wording-decisions-20260929)和[多模态项目档案](../../自我准备/projects/multimodal-inference-project.md)；历史工作比例只在本场语境内使用。

## 2. 云端与端侧差异、方向意愿

**现场题意与定位。** `00:43:33–00:47:08`。面试官解释岗位偏单芯片端侧，并询问是否愿意继续往这个方向。你反问技术栈，随后表示继续了解。对方说仅借鉴 vLLM 部分设计，不直接照搬其完整服务能力。

**原答复盘。** 主动确认岗位方向是合理的；但把端侧先概括为“小模型、单卡”，没有展开资源和服务目标。表示继续了解不等于已经决定转向，也不是明确拒绝；参考回答应说明判断标准，不能替用户虚构职业决定。

**更好的回答方式。** 区分共同技术与具体约束，再提出能帮助决策的岗位问题。

**参考回答。**

> 我理解云端与端侧都需要正确执行模型、管理状态并定位性能问题，但典型约束不同。云端经常要处理多请求调度和多卡通信；端侧更可能面对固定内存、带宽、功耗和小 batch 的时延要求。两边都可能同时关心吞吐和延迟，不能绝对划分。
>
> 我已有的硬件适配、Shape／Layout 分析、数值对齐和跨团队定位可以迁移。需要补的是目标平台的执行与内存模型，以及在单设备资源约束下把一个特性做深的经验。
>
> 我愿意继续了解这个机会，但想先确认：框架岗位主要负责核心 runtime 与模型执行，还是产品集成也占较大比例？前三个月最希望解决哪一个性能或兼容性问题？这些信息能帮助我判断技术方向是否符合下一阶段目标。

端侧设计是根据题设给出的判断，不把对方当时的单芯片路线泛化为所有端侧产品。

## 3. vLLM 插件如何接入自研芯片

**现场题意与定位。** `00:47:08–00:49:05`。问所用版本，插件是为了多机多卡还是其他特性。原答说明设备适配，涉及 Platform、ModelRunner、Engine 和 KV 对齐；版本被识别为多个互相冲突的值。

**原答复盘。** “插件用于接入自研设备”回答正确，也有具体缓存约束。不足是层次没有组织好，block 的 token 数和硬件字节对齐混在一起；不能因插件需要设备执行支持，就推定必须重写 Engine 或全部 Scheduler。

**更好的回答方式。** 按“注册设备 → 配置能力 → 执行与算子 → 内存／缓存接口 → 验证”说明，历史版本保持未知。

**参考回答。**

> 这里的插件主要是让 vLLM 能在自研设备上执行，不等于专门增加多卡功能。以当前参考接口说明，Platform 负责声明设备能力、检查配置并选择 Worker 和 Attention backend；Worker 初始化设备和权重，ModelRunner 准备执行输入，底层通过后端算子和运行时完成计算。通信支持是其中一部分。
>
> 我会尽量复用上游调度语义，在设备不兼容的接口上做适配。例如缓存要分别明确每个 block 容纳多少 token、每层张量的物理布局，以及按字节计算的对齐要求。不能把 256-token block 和 256-byte 对齐当成同一件事，也不能从一个约束直接推导另一个。
>
> 适配完成要检查模型加载、Prefill／Decode、缓存写入和读取、异常回收及数值回归。历史具体版本在本次记录里不可靠，我不会报一个猜测版本；接口名称和职责也应以对应代码版本为准。

技术依据：[固定版本 Plugin System](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/plugin_system.md)、[架构说明](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/arch_overview.md)。

## 4. KV 命中、PagedAttention 与连续批处理

**现场题意与定位。** `00:49:16–00:51:33`。先问是否做过 KV 命中率优化，再问 PagedAttention 和批处理。批处理术语在转写中出现多个变体，结合上下文按连续批处理准备，不能声称恢复了确切原词。

**原答复盘。** 明确说未做命中优化，并正确描述按块分配、Decode 增长后加块。不足是把一次请求沿用 KV 与跨请求前缀复用混在一起；“不再碎片化”过于绝对；对连续批处理仅说复用上游，没有解释机制。

**更好的回答方式。** 分开分配、复用和调度三件事，再回答做过什么。

**参考回答。**

> 我当时主要适配块大小和分配接口，没有做过命中率专项优化。Paged KV 将请求的逻辑位置映射到池中的物理块，按需求追加，避免为每个请求一次预留连续的最大上下文空间。它减少外部碎片和过度预留，但仍可能有尾块未用空间、物理对齐及元数据开销。
>
> 同一请求从 Prefill 到 Decode 继续使用自己的 KV，是请求状态延续；Prefix Cache 则让新请求复用兼容的相同前缀。命中需要前面的上下文和模型条件一致，不是某一段 token 文本相同就一定能复用。请求结束可以解除引用，缓存内容仍可能保留，直到再次使用或被淘汰。
>
> 连续批处理关注每轮哪些请求一起执行。完成或退出的请求可以移出，新请求在调度轮次加入，不必等待整个初始 batch 全部结束。它和分页缓存互相配合，但不是同一个机制。如果只是复用了上游，我会说清使用与验证范围，不把它说成自己实现了调度算法。

依据：[原始 PagedAttention 论文](https://arxiv.org/abs/2309.06180)、[固定版本前缀缓存设计](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/prefix_caching.md)。尾块复用规则还需按具体版本与缓存粒度判断。

## 5. 新模型导入、精度定位与算子交接

**现场题意与定位。** `00:51:33–00:55:44`。问不同模型怎样适配，并追问算子问题由谁定位和修复、“切片”具体指什么。原答给出跑通、跑对、优化三阶段，说明提取失败单例交给算子团队，也承认可能是框架调用错误。

**原答复盘。** 主线完整，协作边界明确。缺项是参考基线、采样配置、首个差异点、单例内容和回归判据；公开榜单分数受评测设置影响，不能单凭不同分数认定某个算子错误。

**更好的回答方式。** 每阶段给完成判据，再用现有案例说明“我定位什么、同事修改什么、怎样回归”。

**参考回答。**

> 我先固定模型与权重版本、输入处理、生成配置和目标后端。功能阶段检查算子和 dtype 支持，把真实 Shape 提成小用例，先让最小链路执行。正确性阶段优先对照同版本参考路径，固定输入和采样条件，检查中间张量、logits 和模型任务结果；公开分数只能在评测口径一致时比较。
>
> 有差异时，我会从最早出现偏差的位置缩小范围，检查输入、布局、位置和缓存是否已经错误，再决定是框架调用还是设备算子问题。交给算子团队的单例应包含输入或构造方式、Shape、dtype、stride、参数、参考输出、误差判据和复现步骤；修复后既跑单例，也回到整模回归。
>
> 例如现有 Conv3D 案例中，我负责复现、调用链与显存分析、模型侧布局和权重预处理；专用 Kernel 由算子同事实现。已有单算子 CPU 对照和 10 个图片的模型级回归，但没有视频模型级精度回归。我会保留这种测试范围，不把单例通过说成所有输入都正确。

项目依据：[Conv3D 案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)。本题不用旧稿的 TTFT 40% 表述。

## 6. 传统模型与框架软件栈

**现场题意与定位。** `00:55:47–00:57:56`。问传统图像模型能否运行、是否另有 runtime，以及 vLLM、PyTorch 和底层实现怎样衔接。原答说传统 CV 由其他同事负责，同样以 PyTorch 为枢纽，随后把底层概括为 C++、上层概括为 Python。

**原答复盘。** 没有冒领传统 CV 工作。需要收窄“全部底层都是 C++”“每个算子必经基础 PyTorch 算子”：语言不等于软件层次，融合自定义算子、编译路径和设备 Kernel 都可能不同。

**更好的回答方式。** 以职责与调用接口划层，再指出自己确认和未确认的部分。

**参考回答。**

> 传统 CV 模型由其他同事负责，我没有足够材料描述那套具体 runtime。共同点可能是使用同一个 PyTorch 设备后端，但它的模型执行和服务调度不一定经过 vLLM。
>
> 对我熟悉的大模型路径，vLLM 管请求、调度、KV 和模型执行；模型层会使用 PyTorch 运算或自定义融合算子。PyTorch 的算子分发按设备和实现找到后端入口，再进入 runtime 和设备代码。一个融合算子可以直接覆盖多个数学操作，并不要求先把每一步拆成独立的基础算子调用。
>
> Python 主要承担组织和控制，C++ 常用于框架与运行时接口，设备计算还可能由其他语言或编译器生成。判断性能应看真实调用图、同步和数据搬运，不能只根据代码语言判断快慢。

依据：[PyTorch 自定义算子官方说明](https://docs.pytorch.org/tutorials/advanced/custom_ops_landing_page.html)与[固定版本 vLLM 架构](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/arch_overview.md)。

## 7. 怎样判断算子融合及个人参与

**现场题意与定位。** `00:57:56–01:03:55`。先问是否考虑层融合，再追问本人参与、实际模型例子、如何判断适合目标芯片。原答谈到 MatMul＋AllReduce、RoPE 奇偶切片，以及动态输出长度引起的 D2H／分配。

**原答复盘。** 能从依赖、布局和 Host 往返思考，但没有给出完整实施与验证链。“多 stream 没有并行”不自动证明合成一个算子就能通算重叠；reshape 也不一定搬数据。第三个算子名称无法可靠恢复，不能直接认定就是 `repeat_interleave`。

**更好的回答方式。** 先判断成本和依赖，再说明融合层次；将设计方向与本人已完成项目分开。

**参考回答。**

> 我会从 Profile 找到可以减少的实际成本：中间张量落内存、重复读写、Kernel 下发或 Host 同步，再检查依赖和硬件资源。融合不是越大越好，还要看片上空间、并行度、编译成本、数值行为和不同 Shape 是否退化。
>
> MatMul 和 AllReduce 的情况，先确认这是 TP 的部分和归约，而不是所有线性层都需要通信。如果分块结果完成后就能开始传输，且后端允许计算单元与通信通路同时工作，才可能做 Tile 流水；如果硬件资源根本不允许重叠，换成一个接口也不会凭空产生并行。普通多流无收益与专用算子内部是否能重叠，需要分别验证。
>
> RoPE 的切片与重排，要区分只改视图和真实物化。若后端为奇偶索引反复搬数据，可以让消费算子直接按所需索引读取，减少中间缓冲，但必须保留配对和旋转语义。动态输出长度则要查清为何必须读回 CPU：若长度能由已知 metadata 得到，可以提前提供；否则要设计设备端分配或有界缓冲等支持，不能笼统说融合就消除 D2H。
>
> 我的实际边界是模型与框架侧定位、组织输入、接入与验证，底层融合 Kernel 由算子同事负责。可明确引用 ECG 项目中已有融合算子迁移及小 Shape 外积改写，但当前档案没有恢复每个融合算子的独立收益，我不会用理论例子代替已落地证据。

项目依据：[ECG 布局案例卡](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)。视图与拷贝依据：[PyTorch 固定源码文档](https://github.com/pytorch/pytorch/blob/0bd89deb431509d893177a84cfa4768aa0399809/docs/source/tensor_view.md#L9)。

## 8. 框架路线与团队分工

**现场题意与定位。** `01:03:55–01:05:34`。问是否借鉴其他框架、谁选择技术路线、团队人数和分工。原答称主要跟随 vLLM 上游，团队约 5–7 人，按模型或特性划分，同时支撑客户。

**原答复盘。** 团队事实表达直接，但“上游支持什么就做什么”没有说明交付优先级和个人能影响的选择。5–7 人属于原团队，不是 XG；不能照搬智能纪要错误归属。

**更好的回答方式。** 事实保持原样，补充作为执行者如何评估需求；不虚构自己拥有架构或路线决定权。

**参考回答。**

## 12. C++ 使用与 ELF 文件布局

**现场题意与定位。** `01:12:05–01:13:25`。确认开发语言后，问编译后可执行程序有哪些段、代码在哪、静态变量在哪。原答说日常 C++／Python，但明确答不出这些布局问题。

**原答复盘。** 这几问有明确的知识缺口；不能用写过 PyTorch 扩展代替回答。题目中的“段”需先区分 ELF section、加载 segment 和进程内存区域。

**更好的回答方式。** 限定 Linux ELF 的常见实现，说明典型落点与检查工具，不把编译器实现惯例当成 C++ 语言保证。

**参考回答。**

> 以 Linux ELF 为例，链接视角常见 `.text` 放机器指令，`.rodata` 放只读数据，`.data` 放需要文件提供初始内容的可写数据，`.bss` 描述运行时需要零填充的空间，它通常不在文件里存一整段零。加载器主要按照 program header 中的 segment 建立映射，一个 segment 可以覆盖多个 section。
>
> 静态存储期变量不是都放在一个固定区。普通非零初始化的可写对象常在 `.data`，零初始化对象常在 `.bss`；常量、线程局部对象、动态初始化和被优化掉的对象要分别看。函数内 `static` 也不是普通自动局部变量。栈和堆属于运行时内存组织，不能直接当作 ELF 的 `.stack`、`.heap` 两个固定 section。
>
> 我会用 `readelf -S` 看 section，`readelf -l` 看加载 segment，结合符号表判断某个对象的实际落点。这样既能回答典型结构，也能验证特定编译选项下的结果。

依据：[ELF Sections 规范](https://gabi.xinuos.com/elf/03-sheader.html)、[GNU readelf](https://sourceware.org/binutils/docs/binutils/readelf.html)。

## 13. overload、override 与名字隐藏

**现场题意与定位。** `01:13:35–01:15:55`。问重载、重写、覆盖等术语，并追问如何确认派生类没有错误覆盖基类方法。原答先谈 Tensor 实现继承，后来只说检查参数类型、数量和返回值，承认区分不清。

**原答复盘。** 继承使用经历不能替代概念解释。返回类型不能单独构成普通函数重载；虚函数覆盖还需关注 `const`、引用限定等条件；同名隐藏与虚函数覆盖不同。“重写／覆盖”的中文译名易混，直接使用 overload、override、name hiding 对齐。

**参考回答。**

> overload 是同一查找范围里同名的不同函数，通过参数等条件做重载决议，不能只改返回类型。override 是派生类覆盖基类虚函数，需要对应的函数签名，返回类型相同或满足协变规则。我会显式写 `override`，签名写错时让编译器报错。
>
> name hiding 是名字查找问题：派生类声明了同名函数，可能把基类整组同名函数隐藏，即使它并没有覆盖那些函数。需要保留基类重载时，可以用 `using Base::f` 引入，再通过参数选择。虚调用最终执行哪一个覆盖，和先找到哪些候选函数，是两个步骤。

下面是参考例子，不是现场写过的代码：

```cpp
struct Base {
    virtual ~Base() = default;
    virtual int f(int) const { return 1; }
    int f(double) const { return 2; }
};
struct Derived : Base {
    using Base::f;
    int f(int) const override { return 3; }
};
// Derived d; Base& b = d;
// d.f(1.5) == 2；b.f(1) == 3。
// 去掉 using 后，d.f(1.5) 会匹配 Derived::f(int)，发生转换。
// 把派生 f 的 const 去掉但保留 override，编译器会报错。
```

**怎样避免调用错。** 除了 `override` 和必要的 `using`，还应打开相关编译告警，测试通过基类引用和派生对象的调用；不靠肉眼只比较返回值。依据：[C++ 工作草案虚函数规则](https://eel.is/c++draft/class.virtual)、[成员名字查找](https://eel.is/c++draft/class.member.lookup)。

## 14. Linux 进程、动态库与环境

**现场题意与定位。** `01:15:55–01:17:17`。问如何找 PID、运行进程依赖的库及环境变量。原答会用 `ps -ef | grep`，但用 `env` 回答目标进程环境，并认为难以从进程查看依赖库。

**原答复盘。** PID 查找方向正确。`env` 展示调用它的环境，不是任意目标进程的环境；文件声明的依赖、启动时解析的库和当前实际映射需要区分。

**参考回答。**

> 我会先用 `pgrep -af` 找候选，再用 `ps -p` 核对完整命令和父进程，避免仅凭名字认错进程。`/proc/PID/exe` 可以定位实际可执行文件，`cmdline` 可以核对启动参数。
>
> 文件层面用 `readelf -d` 看 `DT_NEEDED`；对可信自有二进制可以用 `ldd` 检查加载解析。运行中的进程则看 `/proc/PID/maps`，那里能看到当前映射的共享库，包括已经由 `dlopen` 加载的库。文件依赖列表不等于实际已加载列表，也看不到静态链接代码对应的独立共享库映射。
>
> 环境要看目标进程的 `/proc/PID/environ`，它以空字符分隔，通常表示 `execve` 时的初始环境，不保证反映进程后来通过 `setenv` 等作出的全部变化；需要确认当前值时还要结合进程自身的诊断信息。读取也受进程访问权限限制。

命令结构示例，不表示本次需要读取用户进程或凭据：

```bash
pgrep -af '目标程序'
ps -p "$target_pid" -o pid,ppid,args
readlink -f "/proc/$target_pid/exe"
readelf -d /path/to/program
cat "/proc/$target_pid/maps"
tr '\0' '\n' < "/proc/$target_pid/environ"
```

依据：[Linux proc 文档](https://docs.kernel.org/filesystems/proc.html)、[environ 的初始环境边界](https://man7.org/linux/man-pages/man5/proc_pid_environ.5.html)、[GNU readelf](https://sourceware.org/binutils/docs/binutils/readelf.html)。

## 扩展问题与参考回答

以下是为补强本场主题准备的问题，不写成现场已问。

### E1. 前缀缓存命中率应该怎样定义，怎样提高？

关联第 4 题。

> 先明确统计单位。请求命中率可以定义为命中过至少一段前缀的请求数占比；token 命中比例更接近省掉的 Prefill 工作量，还需要记录命中长度分布。高请求命中率可能每次只省几个 token，不能直接代表效果好。
>
> 我会固定真实请求分布，检查模板和 tokenization 是否稳定、可复用前缀长度、池容量及淘汰行为，再测缓存开关前后的 Prefill 计算量与 TTFT。提高复用不能改变输入语义；模型、LoRA、多模态内容等不兼容时必须隔离。缓存带来的收益要覆盖查找与管理成本。

依据：[固定版本前缀缓存键与生命周期](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/prefix_caching.md)。

### E2. 动态输出 Shape 引起同步，是否只能靠融合？

关联第 7 题；以下 `repeat_interleave` 是解释性例子，不认定为现场含混的算子名。

> 不一定。先判断输出长度是否能从已有 metadata 得知；能得知就可提前传入，避免为求长度而读回设备。若长度只能由设备结果决定，还要评估有界缓冲、分阶段执行或后端动态分配能力，不能伪造一个长度。
>
> PyTorch 的 `repeat_interleave` 提供 `output_size`：当调用方已知正确总长度时，可以避免计算输出 Shape 所需的同步。但它不保证消除所有拷贝或所有同步，也不等价于已经融合了前后算子。

依据：[PyTorch 固定源码中的参数说明](https://github.com/pytorch/pytorch/blob/0bd89deb431509d893177a84cfa4768aa0399809/torch/_torch_docs.py#L13708)。

### E3. 为什么单流有时更快，融合有时又能重叠？

关联第 7、9 题。

> Stream 是提交和依赖组织方式，实际并行还受执行资源与运行时约束。多流若没有形成有效重叠，反而拆散提交批次、增加 event 和切换，单流可能更快。另一方面，专用融合算子可能使用不同的内部执行路径，让已经就绪的 Tile 传输与后续计算重叠，但这需要硬件和后端真实支持。
>
> 我会把两条路径的 Host 提交、设备时间线、依赖与资源占用放在一起比较，再做正确性和端到端对照。不能从“使用了两条流”证明并行，也不能从“融合成一个名字”证明重叠。

项目参考：[通信单流适配的职责与边界](../../自我准备/projects/DeepSpeed-Megatron-project.md#project4-oral-baseline-20260903)。

### E4. 如何用小程序验证 override 与名字隐藏？

关联第 13 题。

> 保留本题的 Base／Derived 例子，分别测试派生对象调用、基类引用调用，再去掉 `using Base::f`。前两者可以验证重载查找与虚分派不是同一件事；去掉 using 后，double 参数可能转换为 int，调用派生版本。接着把派生函数的 const 改掉而保留 override，应该编译失败。
>
> 这个例子只能说明语言规则，不证明大型后端接口都正确。实际修改还要核对基类声明、调用位置和测试覆盖；尤其不能仅凭名字相同就认为已经覆盖了预期虚函数。

依据：[C++ 虚函数与 override 校验](https://eel.is/c++draft/class.virtual)。

### E5. 为什么 `ldd` 正常，运行时仍可能加载错库？

关联第 14 题。

> `ldd` 反映它所使用的加载环境，实际服务可能处于不同容器、路径和环境；程序也可能稍后用 `dlopen` 加载更多库。排查时先核对进程实际可执行文件和启动环境，再查看 maps 中实际映射的路径，必要时检查动态段中的 NEEDED、RPATH／RUNPATH 和符号版本。
>
> “文件声明需要什么”“加载器在哪里找到它”“运行时已经映射什么”是三层证据。即使名字相同，也应核对实际构建和 ABI；不能只看到一个 `.so` 文件名就认定版本匹配。

依据：[Linux 动态加载器说明](https://man7.org/linux/man-pages/man8/ld.so.8.html)、[proc 映射信息](https://docs.kernel.org/filesystems/proc.html)。

### E6. 一个优化案例怎样避免只讲流程？

关联第 5、7、9 题。

> 我会先说可复现的症状和固定负载，再说哪条证据把问题缩小到了什么位置，接着列本人改动与协作改动，最后给对应的正确性和性能对照。算子耗时、整模 TTFT、完整请求时延不能混成一个收益指标。
>
> 例如 ECG 案例的 30–40 秒到 20 秒以内属于 Transformers 项目的完整请求时延，且包含多阶段优化；Conv3D 的当前口径属于特定图片测试组的 TTFT。它们不能互换，也不能把联合修改的收益全部算作某一个 Kernel 或框架补丁。

依据：[ECG 案例卡](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)、[Conv3D 案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)。
