## 2. 通信多流转单流及个人工作量

**现场题意与定位。** `00:10:27–00:13:40`。问框架具体工作，追问原多流如何组织、怎样改成单流、是否损失性能、其他芯片是否验证，以及工作量是否不大。原答说明目标后端不能实现预期重叠，改为单流减少切换；承认未测其他芯片，属于早期适配工作。

**原答复盘。** 动机与经验边界合理。不足是把“芯片不支持并行”说得太笼统，没有区分设备能力、运行时提交和当前负载；“很大提升”无可靠数字。工作范围不能只靠修改行数评价，也不能包装为独立设计整个通信系统。

**更好的回答方式。** 原执行时间线、无效重叠的证据、改动层、依赖保持、验证与回退。

**参考回答。**

> 原路径把通信放到独立 stream，希望和计算重叠。但在当时目标后端和负载上，Profile 没有看到有效重叠，反而有频繁切流、event／wait 和提交批次拆分。我的判断针对这条实际路径，不等于所有芯片或所有多流都无效。
>
> 我增加开关，让相关计算与通信按同一执行 stream 的依赖顺序提交，并处理上层 PyTorch 通信适配与通信库内部的辅助流，保留恢复原行为的方式。实际工作包含定位、接口修改、单例与端到端验证；它确实是早期适配中的一个较小决策点，不作为全部框架工作量的证明。
>
> 正确性上需要保持数据就绪、通信完成和消费顺序，不能因为少了 event 就破坏异步 Work 的契约。性能上比较同负载的提交次数、Host 空洞和整步耗时。现有材料只支持该环境中开销降低，没有可信的通用加速百分比，也没有其他芯片的对照，因此不能推断换平台同样有收益。

项目依据：[DeepSpeed／Megatron 项目口述基线](../../自我准备/projects/DeepSpeed-Megatron-project.md#project4-oral-baseline-20260903)。其中对异步 Work 及跨流语义仍有待核项，以上完整检查要求不自动变成历史已全部通过的测试。

## 3. 权重布局优化、收益与交付

**现场题意与定位。** `00:13:45–00:17:54`。要求较大投入的框架案例，追问布局细节、收益和是否量产。原答讲 block 级列优先、加载期预排布、小 batch 访存收益，并报 20%–30%；量产应答转写为“是吗”，不能据此确认。

**原答复盘。** 已经连起了负载、硬件和转换时机，是本场具体的工程案例。缺项是 block 内外顺序、真实 Shape／dtype、有效区域与 Padding 的约定、数值验证和计时范围；bank conflict 及“完全消除”未有独立证据。当前已确认 Case Card 收窄了旧收益，优先采用新口径。

**更好的回答方式。** 以布局契约和本人职责为主，收益按对应项目与测试组说，量产状态只陈述可确认范围。

**参考回答。**

> 我做的是静态权重的 blocked Col-major 预排布：Tile 大小不变，块内行优先，块间列优先，让权重物理顺序更贴近配套 Kernel 的分块读取。框架侧在加载后完成转换，后续 Prefill 和 Decode 都复用；动态的 QKᵀ 等矩阵乘不属于这次预排布范围。
>
> 我负责 Tensor 扩展、权重预处理、框架接入和模型回归，底层访存实现由算子与硬件同事负责。改变布局后还要约定哪些地址有效、如何索引和清理 Padding，不能继续沿用旧布局的有效区域假设。现有材料不足以恢复现场提到的全部掩码细节，我不会补造私有地址公式。
>
> 既有测试中，同一设备的新旧布局 MatMul 输出逐元素数值相等，模型 logits 和输出 token 也一致。ECG 项目从约 30–40 秒，经常规优化到约 20 秒，再经权重布局到 20 秒以内，前后各 10 次平均，计完整请求且包含图像预处理。这是 Transformers 项目的阶段结果，不能转换成布局独立百分比或 vLLM 的收益。技术后来移植到 vLLM；本场“已量产”的状态仍不能只靠含混转写确认。

依据：[更新后的 ECG 布局案例卡](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)。不沿用现场 20%–30% 或旧档案其他区间拼接新结论。

## 4. vLLM 全链路及硬件适配

**现场题意与定位。** `00:18:04–00:21:46`。面试官明确点出 Scheduler、Worker、ModelRunner、backend。原答要求缩小范围后转向 KV block 对齐，描述“大物理块承载小逻辑块”，并说尽量复用上游映射。

**原答复盘。** 用实例说明约束有价值，但没有先回答全链路。token block 大小与字节对齐混用，无法确认 32／64／256 的真实接口；如果真的引入子块，光改 block table 的 Shape 不足以证明寻址不变。

**参考回答。**

> 以 V1 参考架构说，一次请求先经输入处理进入 EngineCore。Scheduler 依据请求状态和 token 预算决定本步工作，KV 管理器负责命中和分配；Executor 将执行计划交给 Worker，Worker 管设备与模型，ModelRunner 准备 token、位置、块表和 slot 等元数据，调用模型及 Attention backend。结果再经过采样和请求状态更新，返回下一轮或输出。
>
> 自研设备适配时，我会分别确认 Platform 的能力声明、Worker 初始化、ModelRunner 输入组织、缓存布局、算子与通信接口，尽量保持上层语义一致。具体改哪层由不兼容点决定，不是所有层都必须重写。
>
> KV 例子先区分 B 个 token 的块与 A 字节对齐。若 Kernel 只接受某个块粒度，最直接是整个链路统一这个粒度；若希望更大物理分配承载更小逻辑子块，就必须定义子块偏移、有效长度、分配与回收，并保证写入和读取都理解映射。当前转写不足以证明历史方案具体怎样实现，我会把这些说成需要核对的契约，不声称只改 Shape 就完成适配。

依据：[固定版本架构](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/arch_overview.md)、[Platform 插件接口](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/plugin_system.md)。

## 5. 离散 KV 块的 Attention 计算

**现场题意与定位。** `00:20:46–00:24:06`。追问逻辑／物理块映射、块 ID 为 `0、10、11` 时怎样计算 Attention，是否自写 Kernel，以及动态 Shape／index 的实现。原答说按 block table 读 slot，随后承认不了解 Kernel 内部。

**原答复盘。** 按索引读取抓住了核心，不应评价为完全错误。缺项是地址、有效长度、分块计算及全上下文归一化；“这很复杂吗”没有回应难点。非连续的是块指向的 KV 存储，block table 自身可以是连续的索引数组。

**更好的回答方式。** 给出一个逻辑位置到物理槽的例子，再解释块间如何合成正确结果。以下限定普通 full attention，地址布局由具体 backend 定义。

**参考回答。**

> 设每块 B 个 token，逻辑位置 j 属于块 `j // B`，块内偏移是 `j % B`。块表为 `[0,10,11]` 时，第二个逻辑块从物理块 10 读取；最终地址还要加 layer、KV head、feature 和对应 stride。不能直接把整个历史 KV 当连续数组读，但也不必先复制成一个大连续缓冲。
>
> ModelRunner 把块表、实际序列长度、query 位置等交给 Kernel。Kernel 根据块 ID 分块加载 K/V，计算缩放后的 `qkᵀ/√d`（d 为 head dimension），屏蔽尾块无效槽和不合法因果位置，再完成 Softmax 和对 V 的加权。页内可以组织连续或向量化读取；页间由索引决定，具体 gather、Tile 和预取要按目标设备支持选择。
>
> 分块不能改变 Softmax 的归一化范围。可以维护全局最大值、指数和及加权输出，或先算各块的局部统计再合并；不能每块单独归一化后把结果直接平均。我没有独立实现过现场那套 Attention Kernel，但框架侧需要把这些元数据和有效区域约定清楚，并与算子同事共同验证跨块、尾块和不同长度。

一个可检查的合并关系：每块对有效 score 算 `m_b=max(s)`、`l_b=Σexp(s−m_b)`、`o_b=Σexp(s−m_b)v`，再令 `m=max_b(m_b)`，结果为 `Σ_b exp(m_b−m)o_b / Σ_b exp(m_b−m)l_b`。这是说明性公式，不是历史 Kernel 的代码还原。

依据：[固定版本 Triton Attention 的块表寻址](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/attention/ops/triton_unified_attention.py#L424)、[Softmax 辅助实现](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/attention/ops/triton_attention_helpers.py)。这说明通用机制，不要求自研后端使用 Triton。

## 6. Prefix Cache 与 RadixAttention

**现场题意与定位。** `00:24:12–00:26:02`。问前缀命中和块复用，再比较 vLLM 与另一个框架的机制。转写不干净，结合“树状查询”按 SGLang RadixAttention 准备；不能将具体原词视为人工核验结果。原答只讲完全匹配，随后记起树结构。

**原答复盘。** 复用原则正确，但缺缓存键、最长前缀、引用与淘汰。“树状查询”不是 Redis；也不能把不同数据结构说成数学 Attention 算法不同。

**参考回答。**

> Prefix Cache 复用的是兼容执行条件下已经算过的前缀 KV。一个块的内容不仅由块内 token 决定，还依赖此前上下文；LoRA、多模态输入和缓存格式等也可能影响复用。命中后增加使用引用，未命中的后缀继续计算；请求结束解除引用，空闲缓存可保留或在压力下淘汰。
>
> vLLM 的典型路线是块哈希，把父前缀哈希、本块 token 及必要的额外标识组成键，维护哈希到物理块的映射。SGLang RadixAttention 则以压缩前缀树组织 token 前缀与 KV 索引，通过路径匹配找最长可复用部分，必要时拆分节点，并对活跃节点锁定、对可淘汰节点回收。
>
> 两者都要处理复用条件、生命周期和内存预算。区别主要在索引组织、匹配和管理方式，不是一个能复用、另一个不能。尾部粒度和具体淘汰策略要绑定版本；不能简单说所有 vLLM 只支持某种完整块规则，或 SGLang 可以无条件任意粒度复用。

依据：[vLLM 前缀缓存设计](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/prefix_caching.md)、[SGLang 固定提交的前缀匹配与节点拆分](https://github.com/sgl-project/sglang/blob/43a3f956cb0c9fe9b7b7a042af8d8743176b9dba/python/sglang/srt/mem_cache/radix_cache.py#L651)。vLLM 同版代码还有细粒度命中分支，见[FullAttentionManager](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/single_type_kv_cache_manager.py#L654)。

## 7. vLLM V0 到 V1 的变化

**现场题意与定位。** `00:26:02–00:28:13`。问架构升级。原答主动说输入准备与异步拷贝；统一 token 调度由面试官先提示，你随后联想到 token 预算。

**原答复盘。** 具体适配过的局部路径是有效证据，但没讲出架构目标。“V0 按 batch，V1 按 token”过于粗略，不能理解为 V0 没有连续批处理或 token 预算；V1 也不是仅为追赶某个前缀缓存结构。

**参考回答。**

> 我会把 V1 的重点概括为降低 CPU 开销，并把调度、KV 管理和执行组织统一起来。它保留模型和 Kernel 等成熟部分，同时重构 Scheduler、KV manager、Worker、采样和 API 层，使多种优化更容易组合。
>
> 调度上，可以按每个请求本轮要计算多少新 token 来分配统一预算，自然组合 Prefill 分块、Decode、前缀命中和投机候选；这不表示每轮只运行一个 token，也不表示 V0 完全没有 token 预算。输入准备还通过持久 batch、增量更新和更少的 Python 操作减少重复开销。
>
> 架构上分离前端处理、EngineCore 调度和设备执行，各部分的状态与通信接口更明确。异步拷贝只是其中一个执行优化，是否与计算重叠还要看依赖和后端支持。我的现场经历主要证明看过并适配过局部输入路径，当前这份全景解释不能倒填为当时已经完整回答。

依据：[V1 官方发布说明](https://blog.vllm.ai/2025/01/27/v1-alpha-release.html)、[固定版本 V1 Guide](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/usage/v1_guide.md)。版本比较应以具体提交和行为为准。

## 8. 静态 Shape 下的端侧低时延框架

**现场题意与定位。** `00:28:17–00:31:35`。题设为端侧、小 batch、静态执行形状和低 latency。原答提出 Graph、减少 CPU 下发、Tile 调度和融合；引用的框架名称有噪声，不据此恢复某篇文章。

**原答复盘。** 优化方向合理，缺少输入范围、状态、内存与验收目标。静态 Shape 是题设对编译／执行路径的限制，不是“HBM 本身只有静态 Shape”；云端也可能有严格时延目标。

**更好的回答方式。** 先定义有效动态长度怎样落到静态执行，再按关键路径处理成本。

**参考回答。**

> 我先固定模型、量化、上下文范围和并发，区分 TTFT、后续 token 间隔及尾延迟。静态执行不意味着用户输入必须同长，可以把有效长度映射到有限的 Shape bucket，准备对应编译产物和固定 workspace，同时通过长度、mask 和索引隔离补齐部分。
>
> 内存上先预算权重、KV、激活、工作区和 Graph 缓冲，明确哪些常驻、哪些复用。执行上分别观察 Prefill 的大块计算与 Decode 的权重／KV 读取、Host 下发和同步；据此选择预编译或图重放、减少往返、布局和融合。Tile 流水只有在依赖、片上空间和执行资源允许时才有效，切得更细也可能增加调度开销。
>
> 我会用代表性的短长输入、冷启动与热运行、连续生成和突发请求比较时延、内存、功耗及正确性。Graph、融合或量化都是候选手段，不能在没有成本模型时承诺越多越快。遇到不支持的 Shape，要有正确的分桶或回退路径，不能让填充影响有效 token 的语义。

这里是按题设提出的参考设计。vLLM 的可比较实现见[固定版本 CUDA Graph dispatcher](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/cudagraph_dispatcher.py)，不认定 NPU 必须采用 CUDA Graph。

## 10. MoE、融合与云端 EP

**现场题意与定位。** `00:33:13–00:36:20`。问是否了解 MoE、fused MoE／Softmax＋Top-K／dispatch-combine／DP-EP 中熟哪一部分，以及部署是否分布式。原答提到模型接入、Top-K、分发和 EP，明确说主要了解流程，具体算子交由算子团队。

**原答复盘。** 接入经历和职责诚实。应补清 router 作用于 hidden states，选择专家而不是“Top-K token”；EP 是专家放置与通信，融合并非天然消除路由和所有搬运。

**参考回答。**

> 典型稀疏 MoE 中，router 根据 token 的 hidden state 按模型规则计算专家分数，选出 Top-K 专家和权重；运行时把 token 按专家整理，执行专家 FFN，再按原 token 位置和路由权重合并。它不是拿 Attention 的概率直接当专家路由，评分和归一化要遵守具体模型。
>
> EP 把专家分布到不同 rank，目标专家在远端时需要 dispatch／combine 通信。DP 的独立请求副本、TP 的张量分片和 EP 的专家分布是不同维度，实际进程组和通信要按配置解释。“DP-EP”不是一条足以说明实现的算法名称。
>
> 我当时主要做模型和框架接入、提取算子需求及验证，没有材料支持把整个 fused MoE 或通信后端说成自己实现。一个 Fused MoE 接口可以包含重排、多个 GEMM、激活和合并等多段 Kernel，甚至通信。性能评估要明确计入哪些步骤，并对照路由、专家结果和最终输出，不能只说融合成一个算子就完成优化。

依据：[固定版本 Fused MoE 组件设计](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/fused_moe_modular_kernel.md)。后来的 GLM MoE 适配不倒填为 2026-08-24 已展示的经验。

## 11. P/D 分离与 KV 传输

**现场题意与定位。** `00:36:20–00:37:58`。问是否做 P/D、两侧部署模式、是否优化 KV 传输。原答说还在适配，P、D 都用类似 TP／DP 配置，传输走 CPU／TCP，参与不深。面试官认为小 batch 无需分离，你附和。

**原答复盘。** 保留了未深入的边界，但“小场景”不能证明 KV 数据量小；上下文和层数同样重要。“小 batch 不需要 P/D”也不是通用定律，隔离干扰和尾延迟可能仍有价值。

**参考回答。**

> P/D 分离描述 Prefill 与 Decode 使用不同服务资源；TP、DP、PP 描述每侧如何部署模型，两者正交。两侧采用相同 TP／DP 并不妨碍分离，也不自动证明它值得做。历史材料只支持在适配、使用过 CPU／TCP 路径，没有可靠的传输性能对照。
>
> 设计时先确认权重与缓存格式兼容，在 D 侧分配目标槽，传输 KV 和块映射、有效长度等元数据，完成并确认就绪后才能消费；源侧要到传输依赖完成后才能释放。TP 度或布局不同还可能需要重分片，不能直接照搬 block ID。
>
> 在各层 KV 规格一致、K/V head dimension 相同的普通 full attention 下，一个请求的有效 KV 数据量可先按 `2×L×S×Hkv×d×s` 估算：L 是相关层数，S 是传输长度，Hkv 是相应副本／rank 实际 KV head 数，d 是 head dimension，s 是元素字节数，再补块补齐、复制和其他状态。batch 小但上下文很长，传输仍可能很大。
>
> TCP／CPU staging 的简单性要与复制和链路开销比较；设备直传或 RDMA 需要对应硬件和生命周期支持。最终看分离带来的干扰隔离、资源匹配收益能否覆盖传输与协调成本，并同时满足 TTFT、TPOT、尾延迟和吞吐，不能单靠 batch 决定。

依据：[DistServe](https://arxiv.org/abs/2401.09670)。[P/D 方案卡](../../自我准备/学习设计/ChangeCard-03-PD-KV-transport.md)属于设计素材，不作已上线证据。

## 12. 单端 MoE 的完整执行设计

**现场题意与定位。** `00:38:00–00:44:46`。给出单设备、静态执行、128 专家选 Top-8 等说明性条件，要求设计 dispatch、专家 FFN 和 combine。原答先套多卡冗余专家，经纠正后认为普通优化即可，随后猜 Top-K 是瓶颈。连续内存、动态 token 数与静态 Shape 的矛盾主要由面试官提示。

**原答复盘。** 原答没有先锁定单设备约束，也没有区分专家权重布局与动态 token 聚集。这里需要补的是完整方案，不应只背面试官“Top-K 不是瓶颈”：不同后端仍要测。现场数字是设计例子，不是已实现项目配置。

**更好的回答方式。** 路由 → 计数与前缀和 → token 重排 → 分桶与有效标记 → 专家计算 → 加权还原；同时定义 workspace 和溢出处理。

**参考回答。**

> 我先限定所有专家在一个设备内，暂不引入 EP 通信。输入 hidden states 为 `[T,H]`，每个 token 选 K 个专家，产生 T×K 个 token-expert 对。统计各专家数量 n_e，用前缀和确定输出偏移，把同一专家的输入聚到连续区域，同时保留原 token ID、专家 ID 和路由权重。
>
> 静态执行下，为每个 n_e 选择后端支持的 bucket，补齐并记录有效行数；不能为了凑桶随意丢 token 或改变专家选择。若超过最大桶，可以切成多次合法调用或使用正确回退，容量和临时空间需提前规划。专家权重布局是另一条稳定接口，不要把 token 重排误说成每轮都重排权重。
>
> 专家 FFN 可使用分组 GEMM或匹配 bucket 的专用路径。输出按保存的映射还原，遵守模型规定施加路由权重并求和，确保同一 token 的多个专家贡献不互相覆盖；若并行归约，就要有明确的输出区、同步和合并方式。
>
> 我会分段测路由、重排、FFN、合并，观察补齐比例、带宽、workspace 和尾部等待。Prefill 的 token 多、Decode 的 token 少，适合的桶和 Kernel 可能不同；Top-K 是否瓶颈由 Profile 确定。单端先追求正确且可控的执行，不预设所有专家同时并行，也不把一整个接口误认成一个设备 Kernel。

参考设计依据：[Fused MoE 组件与 workspace](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/fused_moe_modular_kernel.md)、[token 按专家对齐的固定实现](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/model_executor/layers/fused_moe/moe_align_block_size.py)。这是当前标准答法，不声称现场已经独立给出。

## 13. 为什么 Padding token 维度

**现场题意与定位。** `00:44:46–00:46:33`。你问是否补专家权重，面试官澄清是 token，并以 15 个 token 进入 16 行编译形状举例。原答说明此前只考虑 hidden 维补齐，最后在提示后理解。

**原答复盘。** 这是提示后补齐，不应写成主动方案。两类 Padding 分属不同约束；bucket 不必都是 2 的幂，“CUDA Graph 只接受 2 的幂”也不是正确解释。

**参考回答。**

> 专家输入是 `[n_e,H]`，n_e 是这轮路由到专家的 token 数，H 是隐藏维。hidden 维补齐通常服务于向量化或布局对齐；token 维补齐则让动态 n_e 落到编译或 Kernel 支持的执行形状，两者可以同时存在。
>
> 比如合法 bucket 包含 16，n_e=15 时执行 16 行，但只把前 15 行作为有效输入，最后一行的输出不能参与 combine。补零本身不够：带 bias 或其他运算可能使补齐行输出非零，因此要用有效长度或映射明确排除。bucket 按编译器和 Kernel 的支持选，不必机械取 2 的幂。
>
> 我会同时控制浪费和覆盖范围：桶太粗会多算，桶太细会增加编译产物与管理成本。遇到 n_e 超过最大桶要切分或正确回退，不能静默截断；也不能把一次静态输入形状支持当成整个路由已静态化。

依据：[固定实现中的 token 数对齐和无效索引](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/model_executor/layers/fused_moe/moe_align_block_size.py#L12)。

## 扩展问题与参考回答

### E1. 分页 Attention 为什么不能每页 Softmax 后直接相加？

关联第 5 题。

> 每页独立 Softmax 都把本页概率归一成 1，但整段 Attention 的分母应包含所有合法历史位置。直接把各页输出相加或平均，等于改变了各页的总权重。应保存每页最大值、指数和及未归一化加权输出，再按共同最大值重标定并合并，或在遍历中做等价的在线更新。
>
> 尾块无效 token 和未来位置不进入统计；分块方式可以改变执行顺序，却不能改变模型定义的归一化范围。数值归约顺序仍可能导致低精度差异，所以需要在容差内对照参考路径。

依据：[固定版本 Attention Softmax 实现](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/attention/ops/triton_attention_helpers.py)。

### E2. 相同 token 文本为什么不一定命中同一 KV？

关联第 6 题。

> KV 取决于模型实际看到的输入和此前上下文。相同局部文本放在不同前缀后，隐藏状态一般不同；相同视觉占位 token 也可能代表不同图像。模型或 LoRA、位置语义、缓存格式等条件不同，同样不能直接复用。
>
> 缓存键需要覆盖影响计算结果的上下文与标识，复用还要满足存储兼容性和生命周期。数据结构选择哈希或树不能替代这些约束；提高命中率应减少无意义的输入不稳定，而不是忽略差异。

依据：[vLLM 缓存键的父哈希及额外信息](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/prefix_caching.md)。

### E3. 静态 MoE 的最大 workspace 怎样估算？

关联第 12、13 题。

> 先定义最大本轮 token 数 T_max、每 token 专家数 K、隐藏维 H 和中间维 F。有效 token-expert 对最多是 T_max×K；按专家对齐后，总行数会增加，若每个活跃专家按 B 行对齐，额外行数每个最多 B−1。这个上界还需按实际实现是否给空专家留空间调整。
>
> 再分别核算重排输入、FFN 中间结果、输出、路由索引与权重，结合生命周期看哪些缓冲能复用。不能简单给每个专家都分配 T_max×K 行，也不能假定所有临时张量同时消失。容量不足时减少单次执行规模并保持语义，不能静默丢弃路由项。

依据：[固定版本 token 对齐分配上界](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/model_executor/layers/fused_moe/moe_align_block_size.py#L72)、[workspace 契约](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/fused_moe_modular_kernel.md)。公式用于规划，不是目标芯片实测容量。

### E4. P/D 两侧 TP 度不同，KV 能直接搬过去吗？

关联第 11 题。

> 不能仅复制字节就认为完成。两侧可能对 KV heads、层或 token 使用不同分片，物理块大小和布局也可能不同。需要定义全局 token／layer／head 到源位置和目标位置的映射，再决定重分片、拼接或复制；GQA 中某些 KV head 可能在多个 rank 上复制，不能机械按 TP 数均分。
>
> 传输完成还要交接有效长度和状态，防止 D 侧读到未就绪数据。验证应与不分离的参考运行比较相同请求的后续输出，并分别计量重排、复制、网络与同步开销。不同 TP 的灵活性不等于可以忽略这些成本。

依据：[DistServe 的资源与并行方案讨论](https://arxiv.org/abs/2401.09670)。

### E5. 投机解码怎样比较收益，又怎样保持正确性？

关联第 9 题。

> 性能比较使用相同目标模型、采样规则和负载。记一轮起草、验证及状态处理的成本为 C，实际提交 token 数为 N，先看 C/N 与普通 Decode 每 token 成本，再测服务端排队与并发后的端到端指标。接受率高可能伴随昂贵草稿，不能单独判定加速。
>
> 对标准随机投机采样，候选从草稿分布 q 采样，在当前已接受前缀下以 min(1,p(x)/q(x)) 接受；首次拒绝从归一化的 max(p−q,0) 残差中采样并作后续状态处理。这里 p、q 必须对应实际采样规则。保证的是目标分布，不是固定种子下每次字串都完全相同。

依据：[投机解码原论文](https://proceedings.mlr.press/v202/leviathan23a.html)。这些规则不能直接套到未说明概率或验证契约的任意草稿方法上。

### E6. 怎样证明升级框架或使用 Graph 没有改变模型语义？

关联第 4、7、8 题。

> 固定模型与权重版本、输入处理、生成配置和精度路径，分层比较升级前后或 eager／Graph 路径。除算子与 logits，还要覆盖请求开始和结束、不同有效长度、bucket 边界、缓存复用、拒绝候选和并发回收等状态行为。
>
> Graph 重放需要稳定的地址和执行契约，但 buffer 里的有效内容及 metadata 必须每轮正确更新。一次热运行通过，不能证明切换 batch 或复用请求槽后仍正确。性能对照还需区分编译／捕获、预热与稳态，不把首次成本排除后又宣称冷启动也加速。

依据：[固定版本 Graph 调度与匹配](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/cudagraph_dispatcher.py)。
