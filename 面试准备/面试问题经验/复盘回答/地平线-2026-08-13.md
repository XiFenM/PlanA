## 1. 使用 vLLM 部署模型的流程

### 1.1 问题与回答主线

本题按“讲一下在 vLLM 上的部署流程”复盘。校准转写将现场题意整理为 VLM 部署，结合本场上下文，具体场景是“在自研芯片上，用 vLLM 部署多模态模型”。

回答应该先给面试官一条完整主线：

**兼容性评估 → 最小链路跑通 → 正确性验证 → 性能优化 → 服务与回归验证。**

### 1.2 原回答的不足

当时的回答有合理的起点，但过早进入了量化细节。根据[校准转写第 2 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#2-vlm-部署流程与量化)，原回答主要覆盖：

`分析模型结构和格式 → 硬件不支持某些低精度格式 → 使用 AWQ → 提取几层和算子小 case → 协同算子适配`

其中，“先检查硬件支持，再提取小 case”值得保留。需要改进的是：

- **整体流程没有先交代完整。** 面试官还没听到怎样判断部署完成，讨论就进入 FP4／FP8 转换。
- **vLLM 中具体适配什么没有展开。** 模型实现、权重加载、多模态输入、设备算子、Attention／KV Cache 等层次没有区分。
- **正确性和性能验证在这一段没有讲出来。** 单算子能运行之后，怎样确认完整模型正确、怎样确认优化有效，需要成为部署流程的一部分。
- **团队流程与个人职责没有及时区分。** 介绍量化工具容易引出算法追问，应当在相关环节直接交代自己负责加载适配还是量化校准。

这些是这段回答的缺项，不代表实际工作中没有做过。

以下两项属于部署流程题的现场子问题，具体复盘与参考回答见本题第 1.6 节。动态长度和 KV Cache 管理另列为第二题；其余扩展问题移至文末。

### 1.4 更好的回答方式

先讲每个阶段要解决什么、怎样判断完成，再用一个项目例子落地。量化放在兼容性评估中的一个分支即可，不需要在开头展开全部算法细节。

下面的参考回答中，项目职责来自现有材料，部署步骤使用“我会”的表达，作为通用方法，不把所有步骤都声称为已经完成的项目事实。

### 1.5 参考回答

> 我的工作场景主要是在自研芯片上做 vLLM 模型接入，负责过 Qwen2.5-VL、Qwen3-VL 和 ERNIE 4.5-VL 的框架适配、精度对齐和性能优化。我会把部署分成兼容性评估、功能跑通、正确性验证和性能优化几个阶段。
>
> 首先明确模型版本和目标负载，包括输入输出长度、多模态输入规模、并发以及时延要求。然后检查模型结构、权重格式和目标设备能力，估算权重、KV Cache、激活与临时空间的内存需求。需要分别确认模型在 vLLM 中是否已有实现，以及这份实现依赖的算子和数据类型能否在目标芯片上执行。
>
> 接着跑通最小链路。我会优先复用已有模型实现，检查配置解析、权重加载和模型执行接口；对于不支持的算子，从模型里提取真实 Shape 和数据类型，做成小 case，与算子同事协作。多模态模型还需要检查预处理、视觉编码、特征合并和位置编码是否保持原模型语义。权重格式不兼容时，再单独处理量化或格式适配。
>
> 功能跑通后，要建立正确性对照。固定输入、预处理和生成配置，先检查算子与局部模块，再比较完整模型的输出；出现偏差时，通过中间结果定位最早发生明显差异的位置。验证要同时覆盖 Prefill 和后续 Decode，并根据目标场景逐步加入长输入、不同多模态规模和并发请求。
>
> 正确性通过后，再用 Profile 判断瓶颈是在 Host 处理、设备计算、访存、数据拷贝还是通信，针对性调整布局、算子和调度配置。优化前后使用同一负载，比较 TTFT、输出 token 时延、吞吐和峰值内存，同时重新做正确性回归。如果交付范围包括在线服务，还需要补充并发压测、长时间运行和异常请求验证。
>
> 比如已有的 Conv3D 案例，我从 OOM 和调用链追到小通道物理补齐造成的显存膨胀，负责模型侧输入布局和权重预排布调整，专用 Kernel 由算子同事修改。验证先做单算子的 CPU 参考对照，再回到完整模型检查输出和首 token 延迟。这是上述适配、定位、修改和回归流程中的一个具体例子。

项目部分对应[多模态推理项目档案](../../自我准备/projects/multimodal-inference-project.md)与[Conv3D 案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)。正确性对照也符合 vLLM 官方提供的模型输出、logprobs 和多模态处理测试方向；实际比较应按测试条件选择判据，不能要求所有生成结果都逐字一致，见[官方测试说明](https://docs.vllm.ai/en/stable/contributing/model/tests/)。

这版回答给面试官留下了清楚的追问入口：**哪里需要适配、怎样验证、出现问题如何定位，以及自己具体负责哪部分。** 首轮讲到这个层次即可，AWQ、KV 管理和性能案例再随追问展开。

### 1.6 现场子问题的复盘与参考回答

本节技术资料核验于 2026-11-08，用于准备更准确的回答，不代表历史项目使用了相同版本的工具或接口。项目经历仍按现有材料表述，不补写未确认的权重来源、量化参数或硬件能力。

#### 1.6.1 FP4／FP8 怎么转换成硬件支持的格式？AWQ 在其中做什么？

**现场问题与原回答。** 面试官追问 FP4 是否转换为 INT4、具体怎样转换，并确认是否用 AWQ 形成 W4A16。原回答主要提到开源工具、重新量化和 AWQ，见[校准转写第 2 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#2-vlm-部署流程与量化)。

**原回答的不足。**

- 没有说明输入是原始 FP16／BF16 权重，还是已经量化过的 FP4／FP8 checkpoint。这两种起点对应不同的误差来源。
- 量化算法、数值格式和文件打包方式混在了一起。回答工具名不能替代对“输入什么、怎样变换、输出什么”的说明。
- 没有讲清校准数据、量化分组、scale、适用时的 zero-point，以及导出后怎样验证。现有记录只能支持“这些细节未展开”，不能据此认定项目实际转换错误。

**更好的回答方式。** 先交代源权重与目标后端约束，再说明量化与导出路径：

`源 checkpoint 及其量化元数据 → 可用的浮点权重表示 → AWQ 校准与缩放 → 目标 INT4 量化及打包 → 后端加载 → 数值与任务效果验证`

需要准备的细节如下：

| 环节 | 应说明的内容 |
| --- | --- |
| 区分数值格式 | FP4 和 INT4 的数值编码不同，即使同为 4 位，也不能把原始位模式直接当作另一种格式使用。FP8 也需结合具体格式和 scale 解释数值 |
| 有同版本高精度原权重 | 优先从原始 FP16／BF16 权重进行目标量化，减少对已经量化结果再次压缩带来的额外误差 |
| 只有低精度 checkpoint | 按源格式及其 scale 解码为近似浮点权重，再执行目标量化；反量化不能恢复先前丢失的信息。是否可接受，需要通过验证判断 |
| AWQ 的作用 | AWQ 是训练后、激活感知的权重量化方法：用校准输入观察激活分布，选择通道缩放，以减小重要通道的量化影响；缩放需有等价补偿，保持量化前变换的计算语义。标准 AWQ 流程不依赖反向传播训练 |
| 导出与加载 | 说明 group size、scale、是否使用 zero-point、哪些层保留较高精度，以及权重打包布局与目标 Kernel 的约定。相同数值表示的重打包与重新量化应分开讲 |
| 验证 | 对照可用的源模型参考，检查层输出、logits 和任务指标，再检查实际加载、内存与时延；只有低精度源权重时，不宣称对照到了不存在的原始高精度基线 |

AWQ 的激活统计与缩放机制依据[原论文](https://arxiv.org/abs/2306.00978)。当前 LLM Compressor 的 [AWQ 示例](https://docs.vllm.ai/projects/llm-compressor/en/latest/examples/awq/)也将通道缩放与后续量化分开。其 [checkpoint 转换文档](https://docs.vllm.ai/projects/llm-compressor/en/stable/guides/entrypoints/convert/)区分了 AutoAWQ 权重重打包，以及 FP8 反量化后再量化的路径；这些例子用于说明概念，不代表本项目实际调用了这些接口。

**参考回答。**

> 我会先确认源权重和目标后端支持的数值格式。FP4、FP8 和 INT4 的编码不同，转换时需要按数值及其量化参数处理，不能直接把位模式换一种解释。
>
> 如果能拿到同版本的 FP16 或 BF16 原始权重，我会优先从原始权重做目标 INT4 量化。AWQ 使用校准数据观察激活分布，通过带有等价补偿的通道缩放，减小重要通道受到的量化影响，再按目标方案量化和打包权重。这里属于训练后量化，不等同于重新训练模型。
>
> 如果只有已经量化过的 FP4 或 FP8 checkpoint，就要先按原格式和 scale 得到近似浮点权重，再做目标量化。这会引入新的误差，原来丢失的信息也不能通过反量化恢复，所以要对照可用的源模型检查数值和任务效果。
>
> 导出时还需要确认 group size、scale、是否有 zero-point，以及打包布局能被目标 Kernel 正确解释。我的项目职责主要在框架接入、适配和验证，量化精度调优不是我主导。

最后一句职责边界依据[现场职责说明](../分析成果/transcripts/interview-20260813-01.calibrated.md#7-量化精度职责与投机解码)及[现有项目档案](../../自我准备/projects/multimodal-inference-project.md#职责)。当前材料未确认具体源权重与量化参数，参考回答因此保留条件分支，不指定一条虚构的项目路径。

#### 1.6.2 为什么采用 W4A16？KV Cache 又是什么类型？

**现场问题与原回答。** 面试官确认 W4A16 后，原回答将 A16 解释为硬件计算路径支持 BF16；随后对 KV Cache 的类型追问作了肯定回应。校准稿将这处 FP16／BF16 标为待确认，见[校准转写第 2 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#2-vlm-部署流程与量化)。

**原回答的不足。**

- 说明了激活计算的硬件约束，但没有同时说明为什么压缩权重、为什么保留 16 位激活，以及采用这种方案的成本。
- 没有明确 W4A16 是位宽概括，具体还要说明权重和激活的数值格式。它也不规定 KV Cache、累加或归约的类型。
- KV Cache 的实际格式没有讲清。这里应记为精度配置表述不充分；不能仅凭“激活是 BF16、KV 可能是 FP16”就认定实现矛盾，存储与计算之间可以有后端支持的转换路径。

**更好的回答方式。** 先说明选择理由，再分开列出各对象的格式。

在本题讨论的 INT4 weight-only 方案中，压缩权重可以减少权重存储和读取量；保留 16 位激活可以继续使用适配的浮点计算路径，并避免额外引入低位激活量化误差。是否更快取决于实际负载、权重读取是否是瓶颈，以及解包、反量化与 Kernel 的开销；不能从权重位宽直接推出端到端加速比。[TensorRT-LLM 精度说明](https://nvidia.github.io/TensorRT-LLM/1.0.0/reference/precision.html)给出了 INT4／INT8 weight-only、FP16／BF16 激活及 MatMul 内即时反量化的具体实现例子。

| 对象 | 需要说清楚的类型与边界 |
| --- | --- |
| 权重存储 | 本题的目标方案是 INT4 权重，加上 scale、适用时的 zero-point 等元数据；W4 本身仅表达位宽，完整方案应注明格式 |
| 激活 | A16 可以对应 FP16 或 BF16，具体受 Kernel 和硬件路径约束；本场原回答强调的是 BF16 |
| KV Cache | 由缓存配置与 Attention backend 支持决定；weight-only 不表示 KV 也被量化。vLLM 有独立的 `kv_cache_dtype` 配置，但每种格式能否运行还要检查具体后端 |
| 内部计算 | 分别说明解包／反量化后的格式、乘法输入、累加和归约精度。A16 不代表所有内部计算也是 16 位，不能据此推定项目采用 FP32 累加 |

例如，vLLM 官方将 [KV Cache 量化](https://docs.vllm.ai/en/stable/features/quantization/quantized_kvcache/)作为独立功能配置。更低精度的 KV 存储还需要对应的 scale、读取或计算支持和效果验证，不能从“模型权重为 INT4”推导出来。

**参考回答。**

> 这里讨论的是 INT4 weight-only 的 W4A16：权重以 4 位整数和配套量化参数存储，激活保留 16 位浮点。这样做主要希望减少权重占用和读取流量，同时保留目标硬件支持的激活计算路径。A16 还需要进一步说明是 FP16 还是 BF16，具体按目标后端的支持来选择。
>
> W4A16 只概括权重与激活的位宽。以常见的 weight-only Kernel 为例，计算时会解包并反量化权重，再与 16 位激活参与运算；具体反量化、乘法和累加类型需要按后端实现分别说明。它的性能收益也取决于读取量减少能否覆盖反量化等额外开销。
>
> KV Cache 是单独的配置，不能从 W4A16 推出它的类型。需要单独说明实际缓存格式、Attention backend 是否支持，以及格式转换发生在哪里；如果启用更低精度的 KV，还要考虑 scale 和效果验证。因此，描述部署精度时，我会分别列出权重存储、激活、KV Cache 和内部计算类型。

本场 KV Cache 的精确 dtype 未被现有材料可靠确认，以上参考回答只给出正确的判断和表达方式，不擅自填入 FP16 或 BF16，也不要求通过重新回忆来补齐。

## 2. 动态输入与 KV Cache 管理

### 2.1 问题与回答主线

现场主问题是：**VLM 输入是定长还是动态长度？Decode 不断增长时，KV Cache 怎样管理？** 同段随后追问 block 大小、每层缓存，以及 Linear Attention，见[校准转写第 3 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#3-动态长度paged-kv-cache-与-linear-attention)。

本题应该讲清一条连续关系：

**有效输入长度 → 本步计算哪些 token → 需要哪些 KV 槽 → 逻辑块到物理块的映射 → Prefill 写入与 Decode 追加 → 请求结束后的回收。**

技术核验日期为 2026-11-08。涉及实现职责时，以 `vLLM v0.26.0@568afb3` 的 V1／MRV1 为参考，不将该版本倒填为历史项目版本。主回答先限定为 decoder-only 模型的普通 full-attention 路径；无跨层 KV 共享、无 CP、无投机预留的情况用于解释基本映射，Linear／Hybrid 的差异在现场子问题中单独说明。

### 2.2 原回答的优点与不足

原回答抓住了分页分块、按需求分配，以及 Decode 增长后增加 block 的基本方向。在后面的[Block 生命周期讨论](../分析成果/transcripts/interview-20260813-01.calibrated.md#10-kv-交错布局与-block-生命周期)中，还明确补充了：Prefill 与 Decode 使用同一套 KV，优先写入未满尾块，跨块边界后再分配，请求结束后释放。因此，本题应评价为**初答不够完整，后续已补齐基本生命周期**，不能归纳成不理解 KV Cache。

需要改进的地方如下：

| 原回答的情况 | 不够清楚的地方 | 更好的表达 |
| --- | --- | --- |
| 直接回答支持动态长度 | 没有展开“动态”的对象及限制 | 说明文本和多模态处理后的有效序列长度可以变化，但仍受模型、预处理、服务配置及内存容量限制 |

### 2.4 更好的回答方式

先限定动态输入与普通全注意力的场景，再沿一个请求的生命周期回答。注意区分以下三个层次：

| 层次 | 管理或使用的对象 | 本题中的职责 |
| --- | --- | --- |
| Scheduler／KV 管理器 | 本步 token 预算、请求块表、可用块与引用 | 决定本步处理哪些 token，为它们取得可用 KV 槽，并维护请求与块的关联 |
| Worker／ModelRunner | 设备 KV 缓冲、输入张量和 Attention metadata | 按配置建立设备缓存，准备本步的序列长度、块表、slot mapping 等执行输入 |
| Attention backend／Kernel | 当前 Q/K/V、本层缓存及执行元数据 | 将新 K/V 写到相应位置，并按请求的有效长度和映射读取历史缓存 |

这对应 V1 中的调度与执行分工，见[架构说明](https://docs.vllm.ai/en/v0.26.0/design/arch_overview/)、固定源码的 [EngineCore](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/engine/core.py#L243)与 [ModelRunner 缓存分配](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/worker/gpu_model_runner.py#L7238)。请求的“按需分配”通常是在已经建立的设备缓存池内分配块编号，不表示每增加一个 token 都重新申请显存或搬移旧缓存。

为了把映射解释具体，可以使用以下小例子；它只是参考答法中的示例，不是项目配置：

- 每块容纳 `B=16` 个 token 位置，一个请求需要为 18 个位置保留 KV，因此需要 2 个逻辑块。
- 逻辑块 0、1 分别映射到物理块 7、42。这里“物理块”指池内编号对应的存储区域，不要求连续。
- 逻辑位置 15 写入块 7 的偏移 15；逻辑位置 16 写入块 42 的偏移 0。序列的逻辑位置仍为 15、16，不因物理地址不连续而改变。

在无 CP、管理块与 Kernel 块大小相同的简单路径中，令 `p` 为从 0 开始的 token 逻辑位置，可写成：

```text
logical_block = p // B
physical_block = block_table[logical_block]
slot_id = physical_block * B + p % B
```

`slot_id` 是槽编号，不是字节地址；实际地址还取决于本层缓存布局、head 维度和 stride。该关系可对照固定版本的 [slot mapping 实现](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/worker/block_table.py#L347)。

长度还要与执行时刻对应：本步为即将参与前向计算的 token 准备 K/V 写入槽；刚采样得到的输出 token，通常到下一次前向才产生自己的 K/V。因此，“已输出多少 token”与“已经写入多少 KV 位置”不应在没有时刻说明时直接等同。

### 2.5 主问题参考回答

> 支持动态长度。以常见的 decoder-only 多模态模型为例，不同请求的文本长度、经过预处理后的视觉 token 数，以及最终生成长度可以不同。但动态长度仍受模型上下文、预处理规则、服务配置和可用内存限制。
>
> 对普通全注意力层，vLLM 使用分页方式管理 KV。设备侧会按配置建立缓存池，每个请求维护自己的逻辑块到物理块的映射。请求不需要预占一段能容纳最大生成长度的连续 KV 空间，而是根据实际计算需求取得块。
>
> Prefill 为本次处理的输入位置计算并写入 K/V。进入 Decode 后，继续使用这个请求已有的缓存，先写最后一个未满块；跨过块边界时再取得新块并更新映射。常规追加不需要为了保持连续地址而搬移已有 K/V，Attention 根据块表和有效序列长度读取历史缓存。
>
> 如果按 V1 的实现分工来说，Scheduler 在 EngineCore 一侧决定本步执行哪些请求和 token，再调用 KV 管理器安排块。Worker 侧的 ModelRunner 准备设备输入和缓存元数据，Attention backend 按 slot mapping 写入新 K/V，并使用块表读取本层历史数据。
>
> 请求结束后，在相关执行和资源依赖满足回收条件时，解除请求对块的引用，使可回收的块重新供其他请求使用。这通常是池内回收，不是把整份设备 KV 缓冲释放给系统；启用 Prefix Cache 时，部分内容还可能保留用于之后的复用。
>
> 这些描述针对普通全注意力。各层的 K/V 数据不同，但兼容的层可以协同管理块映射；如果模型还含滑窗或递推线性注意力层，则需要按各类状态的语义分别配置，不能把所有层都视为同一种随序列增长的 KV。

追加与回收可对照固定版本的 [SingleTypeKVCacheManager](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/single_type_kv_cache_manager.py#L321)与 [BlockPool](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/block_pool.py#L647)。这里的 Prefix Cache 只用于限定回收表述，命中、共享和淘汰细节留待对应现场题或文末扩展准备。

### 2.6 现场子问题的复盘与参考回答

#### 2.6.1 Block 多大？

**原回答与不足。** 原答说固定为 256，是硬件要求，并举了 CUDA 上较小块的例子。应补上单位及适用范围；不能将某个后端数值作为所有 vLLM 配置的答案。这里的 256 在校准稿中按上下文解释为 token 数，具体历史配置仍不通过猜测补全。

**应准备的细节。** `block_size=B` 是每块覆盖的 token 位置数，物理字节数还取决于层数、KV head 数、head dimension、dtype 和后端布局。以普通 MHA／GQA 的一层、一个 rank 为例，假设 K/V 的 head dimension 和 dtype 相同，定义：

- `H_kv,local`：该 rank 实际存储的 KV head 数；不能在发生复制时机械地用总 head 数除以 TP。
- `D`：每个 KV head 的维度。
- `s`：每个缓存元素的字节数。

不计布局 Padding、量化元数据等额外开销时，一层一块的 K/V 数据载荷是：

`2 × B × H_kv,local × D × s` 字节。

同规格的多层再按实际本地层数累计；Hybrid、MLA 或额外状态不能直接套用这一式。管理中的一个块编号也可能同时对应多层各自的存储片段，因此谈字节数时必须说明是一层还是一组。vLLM 的[块与页定义](https://docs.vllm.ai/en/v0.26.0/design/hybrid_kv_cache_manager/#definitions)区分了 token 粒度与物理内存大小。

在无额外预留、无共享、无滑窗回收的普通路径中，`T` 个需要保留 KV 的位置对应 `ceil(T/B)` 个逻辑块。大块通常减少块表项，但可能增加短请求和尾块的内部浪费；小块分配更细，管理与寻址开销可能更高。具体选择要服从 Kernel 支持并由实际负载验证，不能只追求最小块。

**参考回答。**

> 我会先说明 block size 的单位是 token 数，不是字节。具体值由后端支持和配置决定，不能给所有 vLLM 环境报同一个数。
>
> 它的字节大小需要结合本层实际 KV head 数、head dimension 和缓存 dtype 计算；同样是一个 token block，不同模型或不同层组占用的物理空间可能不同。
>
> 选择时要权衡管理粒度与浪费。大块可以减少块表项，但短请求或最后一个未满块会留下更多未使用空间；小块能细化分配，也可能增加元数据和访问开销。我会在目标 Kernel 支持的范围内，结合请求长度和并发分布选择并测量。

如果需要引用个人项目配置，可使用现有 GLM 项目档案中已记录的 `block_size=256`，并同时说明它属于后来完成的特定模型和后端部署；不能把该配置或原因倒填为这场面试的全部历史事实。

#### 2.6.2 每一层的 KV Cache 怎么管理？

**原回答与不足。** “每层 Attention 有自己的 KV”是普通模型下合理的起点，但还没有解释每层数据与统一管理之间的关系。需要补清：**数据按层区分，兼容的层可以共用块表与分配结果。**

普通 Transformer 中，不同层的输入和 K/V 投影通常不同，因此同一请求、同一 token 在不同层的 K/V 数值不同。vLLM 可以将具有兼容缓存规格和分配需求的层组成 cache group，组内使用相同的 block table；同一个块编号在各层指向本层的存储区域，不意味着跨层读取同一份 K/V 数值。模型显式设计的跨层 KV sharing 属于另一个条件，不能混入普通情况。

分组与块表关系见固定版本的 [KVCacheGroupSpec](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/kv_cache_interface.py#L938)。物理后端可以采用不同缓冲组织方式，面试回答应优先说明数据归属和寻址关系，而不是断言每层必须单独调用一次设备内存分配。

**参考回答。**

> 对普通全注意力模型，每层保存自己的 K/V，因为各层的输入和投影结果不同。请求计算到某一层时，会把这一层的新 K/V 写入本层缓存，再读取本层历史缓存进行 Attention。
>
> 管理上不一定每层各自分配一套完全独立的块表。规格和分配需求兼容的层可以组成一个 cache group，共用请求的逻辑到物理块映射。相同 block ID 对应的是不同层各自的数据位置，因此共享的是管理关系，不是 K/V 数值。
>
> 如果层的缓存类型或容量需求不同，就需要按对应规格分组和核算。最后由执行端将各层的缓存与块表、有效长度等元数据正确绑定。

#### 2.6.3 Linear／Hybrid Attention 呢？

**原回答与不足。** 原答明确说明尚未深入 Linear／Hybrid Attention。这是当时的知识边界，不能把诚实说明边界本身当作表达错误；准备更好的回答，需要补上与 full attention 不同的状态模型。

**应准备的细节。** 先说每类层需要保留什么，再谈池和分组：

| 类型 | 需要保留的状态 | 随序列长度的变化 |
| --- | --- | --- |
| 普通 full attention | 各层历史 token 的 K/V | 在不截断等条件下，随保留的历史长度增长 |
| Sliding-window attention | 后续计算仍需要的窗口内 K/V | 可按窗口回收更早的数据；实际分配还受块粒度和实现约束影响 |
| 可递推的因果 Linear Attention | 按具体算法定义的递推矩阵、向量等状态 | 当模型维度固定且只保留当前在线状态时，其状态尺寸可不随历史长度增长 |
| 带短因果卷积的递推结构 | 除递推状态外，还需保存下一步卷积依赖的尾部输入 | 分别按卷积窗口和递推状态规格核算，不能漏掉其中一类 |
| Hybrid 模型 | 上述多类状态的组合，必要时还有索引、尾部或辅助缓存 | 分类型求和，并加入实际页大小、对齐、工作空间和保留状态的开销 |

“Linear Attention 的状态固定”必须限定到具体递推实现，且只描述持久在线状态；不包含 Prefill 的临时 workspace、训练激活，以及为回退或前缀复用保留的多个状态检查点，也不能推出模型所有内存都与长度无关。可递推形式的一手依据见 [Linear Transformers 论文](https://proceedings.mlr.press/v119/katharopoulos20a.html)，不同层缓存需求的管理原则见 [vLLM Hybrid KV Cache Manager](https://docs.vllm.ai/en/v0.26.0/design/hybrid_kv_cache_manager/)。

**参考回答。**

> 这里需要先区分 Attention 类型。普通全注意力保留历史 K/V，历史越长，缓存通常越大。对于能够写成递推形式的因果线性注意力，可以将历史信息汇总到固定维度的状态里，Decode 时更新状态并计算当前输出，不需要像普通全注意力那样保存每个历史 token 的完整 K/V。
>
> 不过，固定的是特定实现的在线状态维度。如果模型还包含短卷积，就要另外保留卷积需要的尾部输入；如果运行时保留状态检查点或使用 Prefill workspace，也要分别计算这些开销。
>
> Hybrid 模型会把多类层放在一起。因此我会先列出每类层的状态形状、dtype、生命周期和增长方式，再结合后端页大小与对齐规则进行分组、容量核算和分配，保证计算出的容量与真实存储一致。不能给所有层统一套用普通 Attention 的每 token KV 公式。

### 2.7 现有项目材料怎样引用

本题的通用机制不需要通过重新回忆项目来补齐。若在今后的面试中需要一个 Hybrid 管理实例，可引用已经更新的 [GLM-5.3-Flash 项目档案](../../自我准备/projects/GLM5-3-flash-project.md)：

> 后来在 GLM 模型适配中，我处理过混合缓存的分组和容量核算。模型同时有 MLA 相关缓存，以及 KDA 的 conv state 和 recurrent state。我按目标平台的真实分配方式分别核算状态页，使容量估算与实际分配一致；又将两类 KDA 状态拆成独立连续池，减少非连续访问带来的搬运开销。

## 3. 分块 GEMM 的权重布局优化

### 3.1 问题与现场细节

现场主问题是：**讲一个你做过的算子优化。** 原回答选择了分块矩阵乘的权重重排，说明跨行取 Tile、加载期预排布、只改权重而不改激活，以及自述的性能收益，见[校准转写第 4 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#4-分块-gemm-的权重布局优化)。这些是回答中主动展开的细节，现有记录未辨认出需要另外列题的现场子追问。

### 3.2 原回答的优点与不足

优点是把硬件访问方式、数据布局和转换时机联系起来，也交代了激活布局受下游接口约束。需要修正的是：

- “HBM bank conflict”缺少存储层级、地址映射和计数器支持，只能保留为当时的根因猜测；当前可靠口径是布局与 Kernel 分块访问不匹配。
- “列优先”没有讲清块内、块间的顺序；1024 的单位未确认，不能补成硬件规格。
- 10%–20% 缺少指标和对照组，不能当作当前已核实的布局独立收益。
- 需要同时说清个人负责的预排布、同事负责的 Kernel，以及正确性和收益的验证范围。

### 3.3 更好的回答方式

采用 **负载与热点 → 布局不匹配 → 加载期预排布 → 算子消费约定 → 验证与代价** 的顺序。项目事实使用更新后的 [ECG 布局案例卡](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)，其中已经确认：Tile 内行优先、Tile 间列优先，Tile 大小不变；预排布覆盖静态参数权重的矩阵乘，Prefill 和 Decode 都使用，不包含 QKᵀ 等动态矩阵乘。

布局优化改变的是物理排列，不能仅靠修改逻辑 Shape 让原有 Kernel 自动理解新布局。仅创建 view 不复制数据、真正连续化可能产生拷贝的区别，可对照固定提交的 [PyTorch Tensor Views](https://github.com/pytorch/pytorch/blob/0bd89deb431509d893177a84cfa4768aa0399809/docs/source/tensor_view.md#L9)。这里的具体 blocked 布局仍以项目案例卡为依据。

### 3.4 参考回答

> 我做过静态权重的 blocked Col-major 预排布。一个具体应用是 ECG 多模态模型，它使用客户基于 Transformers 编写的执行链路。在处理 Host 开销、融合和小 Shape 计算之后，Profile 仍显示 Decode 的小批量矩阵乘较重。结合 Shape 和读写量估算，我们继续检查权重供数，发现原布局与 Kernel 的分块读取顺序不匹配。
>
> 方案保持 Tile 大小不变，Tile 内仍按行排列，Tile 之间按列排列。我负责框架侧 Tensor 扩展和模型加载后的权重预排布；算子同事负责配套的 Kernel 访存实现。转换后不再保留原布局权重，后续 Prefill 和 Decode 都复用新权重，避免每次推理重新转换。
>
> 这次只改静态权重，因为激活的布局涉及上下游算子接口；QKᵀ、Attention 概率乘 V 这种动态矩阵乘不在范围内。代价包括加载期处理和对专用布局接口的依赖，需要一起考虑。
>
> 在已做的对照中，同一自研芯片上新旧布局的 MatMul 输出逐元素数值相等，模型 logits 和输出 token 也一致。这是既有测试范围内的结果，不外推到所有输入。ECG 请求级平均时延从初始约 30–40 秒，经常规优化降到约 20 秒，再经权重预排布降至 20 秒以内；前后各测 10 次并包含首次运行，从请求发出计到完整输出结束，包含图像预处理，生成上限为 1024、平均约 700–800 token。全部收益不能归给布局。技术后来移植到 vLLM，但这组秒数属于 Transformers 项目。

上述数字与正确性结果均采用现有项目口述口径，原始记录尚未独立审计；不把它们替换成当年现场已完整展示的证据，也不宣称已经证实 bank conflict。

## 4. 分布式适配与 TP 通信

### 4.1 问题与现场细节

现场主问题是：**简历中的分布式／生态适配主要做什么？** 题干中的框架名有识别噪声；原回答说明功能适配和通信稳定性验证，并举 AllReduce、AllGather 为例，见[校准转写第 5 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#5-分布式适配与-tp-通信)。现有记录没有清晰独立的 Shape 子追问；下面的推导用于把本人主动举出的 TP 例子讲准确。

### 4.2 原回答的优点与不足

原回答明确了偏接入与验证的职责，没有直接声称主导并行架构。不足是先报 collective 名称，没有交代分片轴；“计算完聚合、最后 AllGather 再 Softmax”容易被听成固定规则。现有材料只能确认这次没有展示完整推导，不能据此判断所有实际调用都错误。

### 4.3 更好的回答方式与必要推导

先讲自己适配了哪一层，再用一个完整 MLP 解释通信。限定普通前向、输入复制、无 Sequence Parallel，忽略 bias，设 TP 数为 `p`，中间宽度 `F` 可被 `p` 整除；`X[T,H]` 中 `T` 是本步参与计算的 token 行数，`H` 是隐藏宽度。以下权重采用数学上的 `XW` 方向，不等同于 PyTorch 参数的存储维序。

| 步骤 | rank i 的 Shape 与结果 | 为什么这样通信 |
| --- | --- | --- |
| Gate／Up 按输出维分片 | `Wg_i、Wu_i: [H,F/p]`；得到两个 `[T,F/p]` | 每个输出通道的内积已完整，仅输出通道分散在各 rank；不是待求和的部分和 |
| 本地门控激活 | `A_i=SiLU(XWg_i) ⊙ XWu_i: [T,F/p]` | 对应通道可以本地计算；后续 Down 能直接消费分片，无需先 AllGather |
| Down 按输入维分片 | `Wd_i: [F/p,H]`；`Z_i=A_i Wd_i: [T,H]` | `Z_i` 只累加本 rank 的中间通道，是完整输出的部分和 |
| 恢复复制输出 | `Y=Σ_i Z_i: [T,H]` | 需要每个 rank 都得到完整和时使用 AllReduce；AllGather 拼接部分和不能替代求和 |

因此，**AllReduce 合并的是同一输出上的贡献，AllGather 拼接的是不同坐标上的分片**。是否通信由当前分片与下游所需布局决定。固定版本的 [LlamaMLP](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/model_executor/models/llama.py#L79)采用 Column-parallel Gate／Up 和 Row-parallel Down；[ColumnParallelLinear](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/model_executor/layers/linear.py#L569)按 `gather_output` 决定是否聚合，[RowParallelLinear](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/model_executor/layers/linear.py#L1694)按 `reduce_results` 决定是否归约。核验版本为 `vLLM v0.26.0@568afb3`，不倒填为历史项目版本。

### 4.4 参考回答

> 我的分布式工作主要是在自研芯片训练适配中，基于 DeepSpeed、Megatron-LM 的测试调试通信后端基础功能。我从真实框架调用提取通信测试，检查分组、Shape、dtype、设备 Padding 与流同步，把稳定用例放入回归。我的职责是把这些执行语义在自研后端上接通并定位差异，不把它说成自己设计了整套并行算法，也不将基础测试扩张为全部训练能力已经兼容。
>
> 以普通 TP 的门控 MLP 为例，我先假定输入 X 的形状是 T×H，并复制在 p 个 rank 上。Gate 和 Up 权重按中间维 F 分片，各 rank 得到 T×F/p 的输出，本地做 SiLU 和逐元素乘。随后 Down 权重按输入维切成 F/p×H，每个 rank 算出 T×H 的部分和。要让各 rank 得到完整输出，就对这些部分和做 AllReduce。
>
> 前一阶段没有必然的 AllGather，因为下一层能直接消费分片。只有消费者需要完整特征时，才需要把不同坐标的分片拼起来。输出词表如果分片，也要根据采样所在 rank 和后端执行方式选择 Gather、AllGather 或相应的分布式处理，不能说模型末尾必定 AllGather。换了并行配置，我会重新从张量分片和消费者需求推导通信。

个人经历的具体素材来自[分布式框架适配档案](../../自我准备/projects/DeepSpeed-Megatron-project.md)，范围采用 [Claim-evidence 矩阵 CL09 的已确认修订](../../自我准备/Claim-evidence矩阵.md#claim-wording-decisions-20260929)，不沿用旧概述中范围更大的兼容性说法。理论推导是当前参考答法，不声称现场已回答。词表聚合的条件分支可直接核对固定版本的 [LogitsProcessor](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/model_executor/layers/logits_processor.py#L85)。

## 5. Conv3D 的 OOM 与 TTFT 优化

### 5.1 问题与现场细节

主问题是：**讲一下多模态模型 Conv3D 的端到端优化。** 现场还确认“是否依据硬件特性修改 Shape、减少 Padding，以及是否强制对齐”，见[校准转写第 6 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#6-qwen3-vl-conv3d-的-oomttft-优化)。

现场以 Qwen3-VL 讨论；后续共建确认首次 OOM 是 Qwen2.5-VL-32B 视频，两代模型都涉及同类小通道补齐问题，但权重形状不同。以下参考回答采用更新后的 [Conv3D 案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)，不把两代模型及不同测量组混成一组数据。

### 5.2 原回答的优点与不足

原回答已经形成“通道末置 → 小通道补齐 → 显存和搬运膨胀 → 调整布局”的因果链，也说明了与算子同事协作。需要补强：

- 分开逻辑 Shape、物理新存储与补齐。view 本身不产生所述大缓冲，问题出在后面的实际重排和分配。
- 现场 3→256 只描述局部物化维度，不能推成整模型显存膨胀同样倍数；对齐单位和具体值不能靠 ASR 补齐。
- 用实际新旧接口说明怎样保持数学语义，避免“合并几个维度”过于笼统。
- 正确性、OOM 和 TTFT 的测试组分别交代；不能用可运行小模型的 TTFT 给 OOM 的大模型补造基线。

### 5.3 更好的回答方式

采用 **症状 → 分配位置 → 物理布局 → 框架与 Kernel 修改边界 → 分层验证 → 同组性能对照**。本例输入已经按视觉块整理为 `[N,K]`，`K=C×T×H×W`；旧实现生成通道末置存储时，在大量位置分别补齐小通道。新接口保留 `[N,K]`，传递原维度元数据，权重初始化为 `[out_channels,K]`，由专用 Kernel 按约定计算。

输入与权重使用一致的 `k=c×T×H×W+t×H×W+h×W+w` 索引，保留窗口内对应元素关系；实际正确性仍由数值对照验证。这里是已知 Patch Embedding 调用的布局契约，不是把任意 Conv3D 都改成简单 reshape。逻辑维序可核对 [PyTorch Conv3d](https://github.com/pytorch/pytorch/blob/0bd89deb431509d893177a84cfa4768aa0399809/torch/nn/modules/conv.py#L637)，view 与拷贝区别见[固定版本文档](https://github.com/pytorch/pytorch/blob/0bd89deb431509d893177a84cfa4768aa0399809/docs/source/tensor_view.md#L29)。

### 5.4 参考回答

> 我在多模态视觉 Encoder 的 Conv3D 路径处理过小通道布局问题。首次故障是 Qwen2.5-VL-32B 视频输入 OOM，调用栈指向 Conv3D。我提取真实 Shape 构造单例，检查内部重排，并将重排移到调用前观察显存 snapshot，看到重排后显存跃升。
>
> 原输入已经按视觉块展平为 N×K，后面的 view 复用存储；真正放大占用的是 Conv3D 内部生成通道末置的新存储。通道只有 3，却要在大量空间位置上分别按目标硬件粒度补齐，既占用显存，也增加无效搬运。这里是物理对齐，不是卷积语义上的边界 Padding。
>
> 我负责模型侧调用重构，保留二维输入，传递 C、T、H、W 元数据，并在初始化时按相同展平次序处理权重。算子同事修改专用 Conv3D 的读取和计算实现。二维末维补齐仍然存在，我们取消的是通道末置造成的大量重复补齐；内部 SRAM 细节不属于我已经确认的实现范围。
>
> 验证分成单算子和模型两层。已有视频 Shape 单例用 BF16 输入与权重，对照 CPU Conv3D，在 rtol=0.1、atol=0.05 下通过；模型级则对 Qwen2.5-VL-32B 的 10 个图片测例设 temperature=0、seed=1234，与 CPU Conv3D 路径比较，输出 token 一致。没有视频输入的模型级精度回归。
>
> 性能也按测试组报告：32B 图片组的平均 TTFT 从分钟级降到 5 秒以内，每个测例一次请求，统计 10 例平均；计时从请求发送到第一个 token，不含模型加载。最初 OOM 的 32B 视频没有优化前 TTFT，不能拿另一组耗时替代。布局和 Kernel 同时改动，当前结果属于协作方案，不能拆成我个人改动的独立收益。

这些是现有项目口述结果；回归条件、容差及待核字段见[案例卡 F5、F6](../../自我准备/projects/multimodal-inference-project.md#f5正确性与模型回归)。不沿用旧项目稿的 40%，也不把个别样本的通过扩展成所有模型、所有输入均已验证。

### 5.5 现场子追问：是改 Shape 减少 Padding？对齐是强制的吗？

**原回答与不足。** 当时肯定了硬件强制对齐，但没有区分改变解释方式与减少实际分配。256 保留为现场自述，不作为当前对外接口规格。

**参考回答。**

> 这条设备路径确实有物理对齐约束，我没有取消它。改动也不只是换一个 Shape 名称，而是避免生成通道末置的新存储，让输入和权重以双方约定的二维布局进入专用算子。这样仍保留二维末维对齐，但不再对每个小通道段分别补齐。正确性由一致的元素映射和参考对照保证，节省的是相关物理缓冲与搬运，不代表模型所有内存都按同一倍率减少。

## 6. 量化职责与投机解码：MTP／FastV

### 6.1 问题与现场追问

面试官先问是否调优 AWQ 量化精度，随后问还做过哪些优化，并举出投机采样和 FastV。原回答说明量化精度不是主责，参与过已有 MTP／草稿路径的接入，遇到问题会逐层 Dump 并与参考机器对比；FastV 没有听清或不熟悉，没有展开回答。来源：[校准转写第 7 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#7-量化精度职责与投机解码)。

### 6.2 原回答的优点与不足

职责边界和逐层数值对照方法值得保留。缺项主要有三个：MTP 与独立草稿模型混在一起，没有说明验证过程；低接受率没有区分草稿预测能力与实现异常；FastV 被相邻的投机解码话题替代，形成漏答。现有材料不能确认当时使用的具体模型、采样器和收益。

### 6.3 更好的回答方式

先交代个人职责，再分别解释三种机制。MTP 的多步预测训练目标或附加模块，可以被用于推理时起草候选，但不自动等于完整的投机算法；例如 DeepSeek-V3 可在推理时移除 MTP 模块，也可用其加速生成，见[技术报告 §2.2](https://arxiv.org/html/2412.19437v2#S2.SS2)。投机解码需要目标模型验证；FastV 则在视觉语言模型内部裁剪视觉 token，见[作者实现](https://github.com/pkunlp-icler/FastV)。

### 6.4 参考回答

> AWQ 方面，我主要参与框架接入和验证，没有主导量化精度算法调优。对于已有投机方案，我参与过使用和问题定位，会固定输入及配置，与参考实现比较中间结果。
>
> MTP 要区分训练与推理。训练时让模型学习预测多个后续 token；推理时可以利用对应模块生成候选，也可以使用独立草稿模型。随后由目标模型在正确的因果上下文中验证候选，只提交通过验证的前缀，并处理拒绝位置及后续候选的失效状态。随机采样要采用正确的接受与校正规则，才能保持目标采样分布；不能仅凭启用了 MTP 就宣称无损。贪心验证则要与目标模型自己的贪心决策一致。
>
> 收益要看每轮实际提交多少 token，以及起草、验证、调度和缓存处理花了多少时间。接受率低可能只是草稿与目标预测不同，也可能来自权重、位置、缓存或采样配置不一致，不能直接归因于数值精度。定位时先对齐配置与上下文，再比较目标和草稿各自的参考路径。
>
> FastV 是另一类优化：根据注意力等信息筛选视觉 token，减少后续层处理的视觉序列长度。它需要单独验证图像和视频任务效果，不具有投机解码那样的目标分布保持保证；我没有足够的现场经历可以将它作为自己做过的项目。

随机采样的分布保证依据[投机解码原论文](https://proceedings.mlr.press/v202/leviathan23a.html)，前提是验证和校正算法正确；分布相同也不等于固定随机种子下逐字输出必然相同。后来的 [GLM 项目](../../自我准备/projects/GLM5-3-flash-project.md)未启用 MTP，不能补写为本题的 MTP 落地证明。

## 7. Prefill 与 Decode 的优化重点

### 7.1 问题与回答主线

面试官问两个阶段的性能优化重点。原回答提出 Prefill 偏计算、Decode 偏带宽，随后将 TP 与 Prefill、PP 与 Decode 对应，并提到 MTP 和 `max_num_batched_tokens`。这一段没有恢复出独立的新追问，作为同一道题复盘。来源：[校准转写第 8 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#8-prefill-与-decode-的优化重点)。

### 7.2 原回答的优点与不足

原回答抓住了常见负载的差异，也注意到了调度预算。问题在于把经验倾向直接变成方案：瓶颈还受 batch、上下文和硬件影响；TP／PP 不能按阶段固定配对；统一调度的 token 预算也不是天然分别给 Prefill 和 Decode 设置两个值。

### 7.3 更好的回答方式

按“计算形态 → 实际瓶颈 → 候选优化 → 代价与指标”回答。Prefill 与 Decode 可以采用不同资源配置，但需要联合考虑 TTFT、TPOT、吞吐和通信；[DistServe](https://arxiv.org/abs/2401.09670)讨论的也是这些约束下的分阶段资源及并行方案，不是简单指定某一阶段使用 TP 或 PP。

### 7.4 参考回答

> Prefill 一次处理一段新输入，线性层通常能形成较大的矩阵乘，权重被多个 token 复用，因此较容易发挥计算吞吐。普通 Decode 在没有投机的情况下，每个活跃请求通常推进一个新 token，小 batch 时更容易受权重读取、KV 访问和下发开销限制。但这些都是常见倾向：长上下文、大并发、MoE 路由或通信也可能改变瓶颈，我会先看实际 Profile。
>
> Prefill 侧，我关注输入处理、GEMM 与 Attention 效率、临时内存和长请求对其他请求的干扰，再选择布局、融合、合适的分块和调度预算。Decode 侧，我重点看权重与 KV 读取、CPU 下发、拷贝、同步和小 Kernel，考虑减少 Host／Device 往返、图执行、融合和适合负载的量化；投机解码则需要额外比较起草与验证成本。
>
> TP 是层内切分，会在分片结果需要合并或重新分布的位置引入集合通信；PP 是按层切分，会有阶段间传输和流水气泡。两者都可能用于 Prefill 和 Decode，应根据模型容量、互连、并发和时延目标选择。特别是低并发自回归生成，单个请求仍要依次经过各流水阶段，PP 不会自动降低单 token 延迟。
>
> `max_num_batched_tokens` 控制一轮可调度的新 token 总预算，混合批次内要一起考虑 Prefill 和 Decode。预算偏小可能减少长 Prefill 对 Decode 的干扰，但会增加长请求完成 Prefill 所需的轮数；偏大也可能增加单轮时间。我会在固定输入输出长度分布、并发和正确性条件下，比较 TTFT、TPOT／ITL、尾延迟、吞吐与峰值内存，而不是只按阶段背一个大小方向。

预算与并行概念可核对 [vLLM v0.26.0 调优说明](https://docs.vllm.ai/en/v0.26.0/configuration/optimization/)。这里使用的是参考版本，不认定为历史项目版本，也不补写未经测量的加速数字。

## 8. 左右 Padding 与位置语义

### 8.1 问题与现场追问

面试官问输入使用左 Padding 还是右 Padding。原答先说右侧，理由是生成向后追加，随后改成左侧。之后追问涉及 Padding 空缺及 Prefix／Decode 的 KV 衔接，但题干部分不清，不能补成一道确定的优化设计题，见[校准转写第 9 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#9-左右-padding现场反复)。随后明确展开的硬件布局与块生命周期归入第 9 题。

### 8.2 原回答的优点与不足

原答尝试确认问题，也意识到存在缓存优化，但把三个问题混在一起：稠密 batch 怎样补齐、自回归怎样生成、KV 在哪里存储。修改“左／右”结论后，没有说明 mask、position 和 logits 选择的条件，因此不能让面试官判断修正依据。

这里不应背成“decoder-only 必须左 Padding”。关键是：**有效 token 的注意力关系、逻辑位置、预测所用的输出行和缓存位置必须一致。**

### 8.3 更好的回答方式

先声明执行方式，再给结论：

| 场景 | 回答重点 |
| --- | --- |
| 稠密 decoder-only batch，生成循环统一取最后一列 logits | 通常左 Padding，使各请求最后一个有效 token 对齐；右侧补齐后，短请求最后一列会是 PAD |
| 自定义支持右 Padding 的生成流程 | 必须正确选择最后有效 token 的 logits，并同步处理 mask、位置与后续缓存；右 Padding 不是数学上不可能 |
| vLLM 的打包 token 执行路径 | 根据请求边界和逻辑位置准备 metadata，不用一个“左／右”概括物理 KV；Graph 的额外补齐也不代表有效文本 token |

例如 `[PAD, PAD, a, b]` 与 `[c, d, e, f]` 的最后有效 token 都在最后一列。mask 排除 PAD 的注意力贡献，位置编号按模型约定生成；普通文本场景中 `a、b` 的逻辑位置不因前面补齐就自动变为 2、3。mask 也不会自动把取错的 PAD 行 logits 改成 `b` 的 logits。这个条件可对照 [Transformers 左 Padding 说明](https://huggingface.co/docs/transformers/llm_tutorial#default-generate)及 [v4.57.1 生成代码](https://github.com/huggingface/transformers/blob/v4.57.1/src/transformers/generation/utils.py)中的 `outputs.logits[:, -1, :]`。

### 8.4 参考回答

> 我会先区分稠密 batch 和 vLLM 的打包执行。如果是常见的 decoder-only 稠密批量生成，而且循环统一取最后一列 logits，我会用左 Padding，让最后一列都是各请求的最后一个有效 token。生成向右追加，并不能决定 Padding 放在哪边。
>
> 左 Padding 仍需要正确的 attention mask 和 position。mask 排除补齐位置，position 保持模型要求的有效序列语义，logits 则从负责预测下一 token 的有效位置取得。只设置 mask，不能修正从 PAD 位置取 logits 的问题。右 Padding 也可以由专门的执行逻辑支持，但这几项必须一起处理。
>
> 在 vLLM 中，我会进一步说明本步有效 token 怎样打包、请求边界在哪里、逻辑位置怎样计算，以及 slot mapping 将新 K/V 写到哪里。逻辑 token 连续不要求物理 KV 连续，也不能把物理缓存空槽当作文本 Padding。Graph 可能另外补齐执行规模，这些无效位置必须按后端契约隔离。

固定 `vLLM v0.26.0@568afb3` 的 MRV1 用 `query_start_loc` 描述本步请求边界，用已计算长度与本步偏移构造位置；普通非投机路径按各请求末行选择采样输出。见 [ModelRunner 输入与采样索引](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/worker/gpu_model_runner.py#L2050)。这说明参考实现，不倒填为现场分支事实。

## 9. K/V 交错布局、Prefix Cache 与块生命周期

### 9.1 问题与现场追问

原答由 Padding 转向 K/V 交错布局；面试官继续问缓存是否按需申请、256-token block 有什么代价，以及 Prefill 与 Decode 如何衔接，见[校准转写第 10 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#10-kv-交错布局与-block-生命周期)。硬件访问单元的名称和位宽识别不可靠，不据此补写寄存器、lane 或私有地址公式。

### 9.2 原回答的优点与不足

原答已讲清同一请求沿用 KV、尾块追加、越界分新块和结束释放，也指出大块的内部浪费。这些应保留。需要补准的是：布局重排不等于降低精度；同一请求的 Prefill／Decode 复用与跨请求 Prefix Cache 不是同一概念；“不足 256 无法缓存”必须限定具体缓存粒度与实现。原记录没有给出可核验的布局和基准，不能把访问更连续直接升级为已证明的带宽或端到端收益。

### 9.3 更好的回答方式

按“数值与布局 → 写入和读取 → 生命周期 → 前缀复用条件”回答。布局方案要同时约定写入端和读取 Kernel 的索引、stride 与对齐，不能只改一侧；数值格式不变时，它改变存放方式，不会自动减少每个元素的位数。

固定 `vLLM v0.26.0@568afb3` 的[单组协调器](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/kv_cache_coordinator.py#L435)要求该路径的 hash 粒度与 block size 一致；但[同版 FullAttentionManager](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/single_type_kv_cache_manager.py#L654)还含细粒度命中及部分尾块处理。因此不能将“完整块才复用”推广到所有版本和配置。

### 9.4 参考回答

> 如果讨论 K/V 交错，我会把它解释为物理布局优化：根据目标 Kernel 的读取方式，调整 K/V 或其中元素的组织，并让写入和读取遵守同一索引约定。它与把 BF16 改为 FP8 的缓存量化不同，也不自动减少 Attention 的算术量。是否值得采用，要比较访存、重排和写入成本，并验证数值及端到端指标；当前材料不足以还原本项目的具体地址公式。
>
> 生命周期方面，普通 full attention 的 Prefill 和 Decode 使用同一请求的逻辑缓存。Prefill 写入已计算输入的 K/V；Decode 为本步前向计算的位置追加 K/V，尾块未满就继续用，跨界后领取新块。刚采样出来的 token 通常到下一步前向才有自己的 K/V，不能把输出计数直接当缓存长度。
>
> 如果每块是 256 个位置，短请求也可能占用一个整块，产生尾部未使用空间。对按完整块复用前缀的实现，不满一块的部分不能直接命中完整共享块，但请求仍能正常运行；这只是复用粒度的限制。支持细粒度尾块的路径要按其具体契约另说。
>
> Prefix Cache 是在兼容的模型与执行条件下复用相同前缀已经算出的缓存；它不同于单个请求从 Prefill 进入 Decode 时继续使用自己的 KV。请求结束后，满足执行依赖的块解除引用，归零后可回收。启用前缀缓存时，内容可以暂留到后续命中或淘汰，而不是一结束就清空整份设备缓冲。

回收依据见固定版本的 [BlockPool 引用与空闲队列](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/block_pool.py#L702)。新布局或更低 dtype 都不能仅凭 token 文本相同就跨不兼容缓存直接复用。

## 10. MoE 与 Fused MoE

### 10.1 问题与回答主线

面试官问是否支持 MoE。原回答提到接入过 DeepSeek 等模型，说明自己做得不多，并描述路由、Top-K、token 分配及后续计算的融合。没有证据表明现场继续问了具体 EP 通信或单 Kernel 实现。来源：[校准转写第 11 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#11-moe-与-fused-moe)。

### 10.2 原回答的优点与不足

原回答识别了动态路由对硬件的挑战，也保留了个人参与边界。缺点是“融合”覆盖什么不明确：没有交代 token 重排、专家计算、加权还原，也没有区分框架算子封装、多个融合 Kernel 与单设备 Kernel。因此不能从“参与 Fused MoE”推导出独立实现了整条链路或通信后端。

### 10.3 更好的回答方式

先讲典型稀疏 MoE 的数据流，再说明实现和个人职责。路由的评分、归一化、Top-K 与共享专家规则依模型而定。路由权重施加位置也必须遵守模型契约：包含非线性的专家一般不能将输出加权随意移到输入端，更不能重复加权。vLLM 将准备／分发、专家执行和结束／合并分开组织，证明一个 Fused MoE 接口可以包含多个执行步骤，见[v0.26.0 设计说明](https://docs.vllm.ai/en/v0.26.0/design/fused_moe_modular_kernel/)。

### 10.4 参考回答

> 我参与过 MoE 模型接入和相关融合适配，但不会把整套底层实现都算作自己的工作。对典型稀疏 MoE，router 先按模型规则生成专家分数，选出每个 token 的目标专家和权重；运行时按专家整理 token，使专家计算能批量执行，再把结果还原到原 token 顺序并按路由权重合并。使用 EP 时，还要把需要远端专家处理的数据分发出去，再收回结果；单设备执行不需要这部分跨设备通信。
>
> 难点不仅是专家矩阵乘。不同专家收到的 token 数动态变化，会带来重排、容量、padding、负载不均和 workspace 问题，小批量下还可能产生很多小计算。优化需要把整理与计算放在同一条数据路径里考虑，减少重复搬运和临时张量，同时保证路由权重、专家编号和输出位置都对应正确。
>
> Fused MoE 可以指框架中的一个融合算子接口，也可以由多段 Kernel 和通信组成，不能仅从名字判断是单 Kernel。对于具体实现，我会说明融合了哪些步骤、保留哪些中间结果、采用什么专家计算布局，以及通信是否包含在测量范围内。验收会对照未融合路径，检查路由、专家输出和最终合并结果，再测完整 MoE 及整模性能。

可用于以后面试的补充实例是：在 **2026-09-01 之后开展、现已完成的 [GLM 项目](../../自我准备/projects/GLM5-3-flash-project.md)**中，负责 AWQ MoE 权重映射、打包与 `qzeros` 布局适配、算子接口和验收接入；融合 Kernel 由算子团队实现。该例晚于本场面试，不倒填为当时经历；已有 [EP 接入方案卡](../../自我准备/学习设计/ChangeCard-02-MoE-EP-dispatch-combine.md)则属于设计材料，不能当作通信后端已落地的证据。

## 11. Chunked Prefill

### 11.1 问题与回答主线

面试官问是否支持 Chunk 模式，并举例说请求很长、一次放不下。原回答说明可以切分 Prefill，在多轮调度中穿插 Decode，避免长 Prefill 持续阻塞其他请求。来源：[校准转写第 12 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#12-chunked-prefill)。

### 11.2 原回答的优点与不足

基本机制和在线调度动机正确。需要补充的是“一次放不下”指哪种限制：单轮 token 预算、临时激活／workspace，以及完整历史 KV 容量不是同一个问题。原答也没有说明后续 chunk 怎样接续已有状态，以及 chunk 大小的收益与代价。

### 11.3 更好的回答方式

先解释切分的对象是**一次请求的 Prefill 计算**，不是把请求拆成彼此独立的短上下文。已完成部分的 KV／递推状态保留，后续 chunk 按原始位置继续。vLLM 参考实现根据剩余 token 预算限制本轮新计算量，见[v0.26.0 固定源码](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/sched/scheduler.py#L869-L875)；chunk 并不要求每次严格等长。

### 11.4 参考回答

> 支持 Chunked Prefill。对于较长 prompt，可以分多轮计算，每轮只处理当前 token 预算允许的部分，给其他请求的 Decode 留出调度机会。这样能避免一个长 Prefill 把整轮执行时间拉得很长，通常有利于控制在线生成的等待，但具体效果还要看负载。
>
> 它保持原请求的连续语义。以前面已经算过一段输入为例，后续 chunk 从原序列的下一位置开始，使用此前保存的 KV，再写入本段产生的 KV；因果 mask 允许它看到合法历史，但不能看到未来。只有完成所需的 Prefill，才能正常开始该请求的后续生成。Hybrid 模型还需按对应层类型延续递推状态，不能每个 chunk 都清零重新开始。
>
> 如果“一次放不下”是单轮预算或临时激活峰值过大，切块可能缓解；如果是 full attention 的全部历史 KV 已超过可用容量，仅靠切块不能解决。随着完整输入被处理，仍然需要保存那些历史 K/V，除非另有量化、卸载、窗口或其他改变缓存需求的机制；模型上下文上限也不会因此自动扩大。
>
> chunk 较小会增加调度次数和部分执行开销，也可能让长请求更晚拿到首 token；chunk 较大可能提高单次计算效率，却使同批 Decode 等待更久。我会在代表性的长短请求混合负载下，比较 TTFT、ITL／TPOT、尾延迟、吞吐和内存，选择满足目标的预算，不承诺所有指标同时改善。

混合 Prefill／Decode 调度及计算形态的依据见 [SARATHI 原论文](https://arxiv.org/abs/2308.16369)。以上扩展了原答的实现条件与容量边界，不据此声称历史项目已完成所有配置下的验证。

## 12. RMSNorm、BF16 与 FP8

### 12.1 问题与现场追问

面试官问 RMSNorm 是否支持 FP16，随后追问 BF16 位数、它与 FP16 的范围和精度差别，以及 FP8 的格式，见[校准转写第 13 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#13-rmsnormbf16-与-fp8)。原答提到低精度曾有差异、最终采用 FP32；但记录不能确认 FP32 指内部计算还是完整输入输出。FP8 名称也没有可靠恢复，下面的标准名称不能补写成现场原话。

### 12.2 原回答的优点与不足

知道敏感算子可能需要较高精度、BF16 指数范围接近 FP32，是可保留的部分。主要问题是没有分开存储类型、内部计算和输出类型；混用了动态范围与分辨率；又用“模型能量化到 FP4／FP8”推断 RMSNorm 的低精度误差通常不重要。不同运算和张量的误差机制不同，这个类比不能成立。

### 12.3 更好的回答方式

普通 RMSNorm 对一个归一化向量计算：

`y_i = γ_i × x_i / sqrt((Σ_j x_j²)/n + ε)`

这里是均方，不先减均值；`ε` 的位置和数值按模型契约固定。参考 [PyTorch RMSNorm 定义](https://docs.pytorch.org/docs/2.15/generated/torch.nn.RMSNorm.html)。然后分别交代输入、平方与归约、缩放和输出的类型。

| 格式 | 符号／指数／显式尾数位 | 主要取舍 |
| --- | --- | --- |
| FP16 | 1／5／10 | 范围小于 BF16；在两者共同的正规数区间内，相邻可表示数更密 |
| BF16 | 1／8／7 | 指数范围接近 FP32，但有效数字少于 FP16；不能笼统说更精确 |
| FP8 E4M3 | 1／4／3 | 相比 E5M2 保留更多尾数位；须继续注明具体变体 |
| FP8 E5M2 | 1／5／2 | 用更少尾数位换更大范围；仍需说明缩放与计算路径 |

BF16 设计见 [Google 格式说明](https://cloud.google.com/blog/products/ai-machine-learning/bfloat16-the-secret-to-high-performance-on-cloud-tpus)。FP8 还存在 `E4M3FN`、`E4M3FNUZ` 等变体，NaN、Inf、零与指数偏置规则可能不同，不能只凭 E4M3 名称互换位模式，见 [ONNX FP8 定义](https://onnx.ai/onnx/technical/float8.html)。

### 12.4 参考回答

> RMSNorm 可以接收 FP16 或 BF16 输入，同时使用更高精度做内部计算。关键不是只报一个 dtype，而是说明平方、均方归约、加 epsilon、倒平方根和输出转换各用什么精度。常见做法是先将输入提升到 FP32，再计算平方和归约，最后按算子契约返回目标类型；这不要求整个模型改成 FP32，也不能事后补救输入在此前已经发生的溢出或舍入。
>
> RMSNorm 不减均值。平方可能放大数值范围，归约会累积舍入误差，因此需要对照参考实现检查误差与 Inf／NaN。BF16 的指数位多，范围比 FP16 大；FP16 尾数位多，在共同的正规数范围内分辨率更高。所以不能说 BF16 在所有输入上都更好，也不能把 FP32 归约理解为不会再有任何数值问题。
>
> 常见 FP8 包括 E4M3 和 E5M2，分别是 1 个符号位加 4／3、5／2 个指数／尾数位。选择时还要看具体变体、张量分布、scale 粒度和乘加路径。权重量化可用，不代表归一化也适合全程低精度。对于本项目，现有记录只能确认曾转向 FP32 处理，无法进一步确定当时的输入输出配置，我不会把参考实现的做法当成项目事实。

缩放用于将待表示数值映射到 FP8 的可用范围，不能恢复已经丢失的信息；权重、激活、KV 与归约可以采用不同精度策略。具体示例见 [Transformer Engine FP8 与缩放说明](https://docs.nvidia.com/deeplearning/transformer-engine/features/low_precision_training/fp8_current_scaling/fp8_current_scaling.html)。

## 14. 反问与技术交流：C++、Python、Triton 与 JIT

### 14.1 现场问题与追问

候选人反问车端是否主要使用 C++、不用 Python、框架是否较小；面试官随后问是否接触自动编译或运行时编译。原回答提到 Triton，从未听清的缩写转到 JIT 后完成确认，见[校准转写第 15 节](../分析成果/transcripts/interview-20260813-01.calibrated.md#15-候选人反问ctriton-与-jit)。

本场没有直接安排 C++ 编码或编译器实现题，因此不把这一段记成 C++ 编码失败或编译器能力已被完整考察。

### 14.2 原回答的优点与不足

- **保留已有分层认识。** 原答知道框架与算子的底层包含编译代码，也能把 Triton 与编译产物联系起来；听清 JIT 后及时修正。
- **“算子不可能用 Python 写”过于绝对。** 普通 Python 解释执行、Python 语法的设备编程 DSL，以及编译后运行的 Kernel 是不同层次。
- **“Triton 编译成 PTX”需要限定后端。** PTX 是 NVIDIA 路径中的表示，不能代指所有目标芯片的编译结果。
- **反问包含了尚未确认的结论。** 与其先说车端不用 Python，不如询问开发前端、交付产物与运行时分别是什么。

### 14.3 应准备的技术细节

| 区分 | 更准确的表述 |
| --- | --- |
| 开发语言与执行位置 | 模型组织或 Kernel 前端可以使用 Python／DSL，最终热点可能运行在编译后的 CPU 或设备代码上 |
| JIT 与 AOT | JIT 在运行期间根据需要进行编译或特化；AOT 在部署运行前生成产物。两者都需要说明支持的输入条件与不满足条件时的行为 |
| 首次执行与稳态执行 | JIT 可能包含编译、自动调优和缓存建立成本；测量时应分别报告冷启动和预热后的执行，而不是只报其中一个 |
| 使用编译器与实现编译器 | 编写 Triton Kernel、使用编译接口或做平台接入，不自动等于设计 IR、实现优化 pass 或开发完整 codegen |

Triton 的 [`triton.jit` 文档](https://triton-lang.org/main/python-api/generated/triton.jit.html)明确说明被装饰的函数会编译后在 GPU 上运行。PyTorch 的 [AOTInductor 文档](https://docs.pytorch.org/docs/main/user_guide/torch_compiler/torch.compiler_aot_inductor.html)则展示了从导出模型生成可在 C++ 环境加载的产物；它们用于说明分层，不代表目标自研平台具备同样的后端支持。

### 14.4 参考回答

> 我会把模型或算子的开发前端、编译阶段和部署执行阶段分开。普通 Python 通常承担模型表达和运行组织，但也可以用 Python 语法的 DSL 描述设备计算，例如 Triton；最终执行的是编译产物，不能因为源代码使用 Python 语法，就认为计算由 Python 解释器逐元素完成。
>
> JIT 是在运行期间按需要编译或特化，能够利用当时已知的输入类型、形状或配置；代价是首次执行成本，以及条件变化时可能产生的新编译。AOT 会把编译工作前移，部署时加载产物，但同样要说明产物支持哪些输入和目标设备。PTX 只适用于对应 NVIDIA 编译路径，其他后端应按它自己的产物说明。
>
> 我的相关经验应按具体工作描述，例如 Kernel 编写与调优、框架接口适配和执行验证。使用过 Triton 或编译接口，不等于独立实现过完整编译器后端。

这里的当前经验口径依据 [Claim-evidence 矩阵中的 CL11 修订](../../自我准备/Claim-evidence矩阵.md#claim-wording-decisions-20260929)，支持 Triton Kernel 实践；不把后来的练习成果写成 2026-08-13 已经向面试官展示的内容。

### 14.5 反问的参考表达

> 想了解一下团队的部署链路：模型和算子的开发前端主要是什么，最终交付的是编译产物、运行时插件还是其他形式？在线或板端运行时是否允许 JIT，动态 Shape 如何处理？这个岗位与编译器、Runtime、算子团队的接口主要在哪里？
>
> 另外，入职后的前几个交付通常是什么，团队会通过哪些正确性与性能指标验收？

这组反问把语言、编译与职责边界放在具体交付链路中，保留现场关注点，同时减少未经确认的假设。

## 扩展问题与参考回答

以下问题用于本场技术主题的补充准备，**不标记为现场已问，也不据此评价原回答**。回答中的通用验证方法不自动成为已完成的项目事实。与正文重复的机制只引用相应章节，重点补足条件变化后的判断。

### E1. vLLM 已经支持一个模型，为什么目标芯片上仍可能需要适配？

关联第 1 题。要区分模型结构支持与目标执行后端支持。

> vLLM 已经有模型实现，说明存在对应的配置、权重加载和前向组织方式，但目标芯片是否能运行，还要检查算子、dtype、Attention backend、缓存布局、通信与编译路径。如果模型结构相同，我会优先复用已有实现，定位依赖了目标设备不支持的环节，再补齐这些接口和执行路径。最后仍要做正确性与负载验证，模型能被注册或成功加载不足以证明部署完成。

依据：[模型接入](https://docs.vllm.ai/en/stable/contributing/model/basic/)与[硬件插件机制](https://docs.vllm.ai/en/stable/design/plugin_system/)。实际插件接口应按项目固定版本核对。

### E2. 具体改了 vLLM 哪些部分？怎样说明个人贡献？

关联第 1 题。应选一个已有项目说明“修改位置—原因—接口—验证”，避免列出全部框架模块并暗示都由自己实现。

> 我主要负责模型执行与框架侧接入。以多模态 Conv3D 为例，我提取真实 Shape，分析调用内部的重排与分配，再修改模型侧输入处理和初始化阶段的权重布局，向专用算子传递明确的维度与布局约定。Kernel 内部计算由算子同事实现，我负责接口协作以及算子、模型两级验证。这样可以明确区分框架修改、底层实现和最终验证的职责。

项目依据：[Conv3D 案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)。如果讨论后来的 GLM 插件，再单独引用其模型注册、权重、混合缓存与 Runner 修改，不将不同项目合成一次改动。

### E3. 多模态部署比纯文本多了什么？

关联第 1 题。重点是输入到模型序列的对应关系。

> 多模态链路多出媒体读取与预处理、编码器、特征投影，以及视觉或其他模态特征与文本序列的合并。我要保证预处理输出与模型版本匹配，特征数量和文本占位位置对应，并正确构造模型需要的位置与 mask。分辨率、帧数和媒体数量变化会改变 token 数及中间张量规模，因此还要检查容量和边界输入。具体模型的 RoPE 或 M-RoPE 规则需要分别实现，不能把所有多模态模型当成同一种位置编码。

依据：[vLLM 多模态接入](https://docs.vllm.ai/en/stable/contributing/model/multimodal/)。

### E4. 怎样证明部署正确，性能也达到要求？

关联第 1、3、5 题。把正确性标准、负载和计时范围放在性能结论前面。

> 我会固定模型与权重、输入处理、运行配置和参考实现，先比较关键算子或层输出，再比较模型 logits 和任务结果。数值判据按 dtype 与运算选择；生成结果不一致时先检查输入、采样与首个分叉，不把随机采样差异直接判为实现错误。
>
> 性能对照保持输入输出长度、并发和配置一致，分别报告冷启动与稳态，明确是否包含预处理、排队与网络。在线服务至少观察 TTFT、输出间隔、吞吐和峰值内存；需要尾延迟时，采集足够请求再报告分位数。每项优化都重新验证正确性，多个改动一起发生时，不能把全部收益归给其中一个。

这里是通用方法。已有项目实际覆盖范围仍以案例卡为准。模型对照可参考[vLLM 测试说明](https://docs.vllm.ai/en/stable/contributing/model/tests/)，指标定义可参考[Benchmark CLI](https://docs.vllm.ai/en/latest/benchmarking/cli/)。

### E5. KV 池不足时，应该排队、抢占还是报错？

关联第 2、7、11 题。先区分请求本身超限与其他请求暂时占用容量。

> 如果请求超过模型或服务配置允许的长度，应当在准入阶段处理，而不是让调度器无限等待。如果请求合法，只是当前可用 KV 块不足，可以延后调度，或者按策略抢占其他请求来释放可回收块。参考的 V1 常规路径会将被抢占请求放回等待队列，之后重新计算所需状态；代价是额外计算与时延。是否启用 offload 或其他恢复方式取决于具体后端和配置，不能说 vLLM 总会自动把 KV 搬到 CPU。

固定版本依据：[Scheduler 的抢占处理](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/sched/scheduler.py#L1216)。若抢占持续频繁，还应调整并发、请求长度、缓存预算或并行配置，而不是只看一次请求能否恢复。

### E6. 分页之后还有哪些内存浪费？

关联第 2、5、9 题。

> 分页让请求不必占用最大长度的连续 KV 区域，但没有消除所有浪费。最后一个未满块仍有内部碎片，后端可能有维度和页对齐，另外还有权重、激活、Workspace、通信缓冲及图执行缓冲。分析显存时要分别记账：逻辑有效 KV、按块保留的容量和整个进程分配量不是同一个数。即使缓存池已提前分配到设备上，请求真正占用或可复用的块数仍然会动态变化。

分页机制依据 [PagedAttention 论文](https://arxiv.org/abs/2309.06180)；本场物理 Padding 案例见第 5 题。

### E7. 相同前缀如何共享？一个请求结束会不会影响另一个？

关联第 2、9 题。

> 首先确认复用的是同一模型执行语义下的相同前缀，包括 token 序列及影响计算的附加条件；不能跨不同权重、LoRA 或不同多模态内容，仅凭文本相同就复用。命中时，请求引用已算好的缓存块。一个请求结束只解除自己的引用，仍被其他请求使用的块不能提前覆盖。写入后续 token 时，需要满足该实现的共享与隔离规则；缓存内容可保留待复用，也可以在满足条件后淘汰。
>
> 哈希粒度、完整块与部分尾块的规则要按版本解释。管理块较大不等于输入不足一块就不能推理，也不等于所有实现都无法复用任何部分前缀。

具体条件见正文第 9 题，以及固定版本的 [KVCacheManager](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/kv_cache_manager.py)和 [BlockPool](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/block_pool.py)。

### E8. 支持动态输入，是否意味着每次 Kernel／Graph 都接受任意 Shape？

关联第 2、8 题。

> 不一定。逻辑有效长度可以动态变化，执行时仍可以把输入放进固定大小的 bucket，或者按 Kernel 要求补齐。关键是区分真实 token 和物理补齐位置，并保证位置、mask、序列边界及 KV 或递推状态的写入槽一致。Graph 还可能要求地址和缓冲生命周期稳定；对不支持的形状，应有明确的新特化、重新捕获或 eager 路径。不能只把输入 Tensor 补齐，却仍使用旧长度的 metadata。

后来的[GLM 项目档案](../../自我准备/projects/GLM5-3-flash-project.md)记录了相应 metadata 与状态槽修复，可作实例；这不改变本场左右 Padding 题的历史回答。

### E9. 多卡时，每个 rank 的 KV 容量怎样估算？

关联第 2、4 题。以下先计算单个请求的普通 full attention，K/V 同 head dimension、同 dtype，暂不计跨请求前缀共享、跨层共享、CP、lookahead 预留、量化附加元数据和布局补齐。`T` 是该请求需要保留 KV 的位置数，`B` 是每块容纳的位置数。

> 我会按 rank 实际保存的层和 KV heads 计算。若本地有 L 层、每层实际保存 H 个 KV heads、head dimension 为 D、每元素 s 字节，T 个有效位置的 KV 载荷是 2×L×T×H×D×s。按块保留时，将 T 换成 B×ceil(T/B)。这里的 H 必须是实际本地值，KV heads 少于 TP 数时可能发生复制，不能始终用总量除以 TP。
>
> PP 要按各 stage 实际持有的层数计算；启用 CP 后还要明确哪些序列位置被分片。MLA、递推状态或其他 Hybrid 层需要使用自己的存储表示另算，最后再加上对齐、临时缓冲和其他内存。

多个互不共享缓存的请求，需要先分别按块取整，再求和：块数为 `Σ_r ceil(T_r/B)`，不能先把各请求长度相加再取一次整。启用前缀共享时，物理容量还需按实际唯一物理块计数，避免把同一共享块重复计算；`T_r` 同样指执行时刻对应的 KV 位置数，而不简单等于已输出 token 数。

变量与槽映射见第 2 题；KV heads 的分片或复制可核对固定版本的 [QKVParallelLinear](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/model_executor/layers/linear.py)。

### E10. 为什么只预排布静态权重？激活也换布局会怎样？

关联第 3 题。

> 静态权重可以在加载时转换一次，之后多次推理复用；激活每次输入都会变化，转换成本会反复发生，还要检查所有上下游消费者是否接受新布局。如果整段融合算子能共用一种布局并消除中间转换，改变激活布局也可能有收益，但必须比较整个子图的计算、拷贝和临时存储，不能只看其中一个 MatMul。当前 ECG 案例只调整静态权重，不能把这种选择说成激活布局永远不值得改。

项目依据：[ECG 布局案例卡](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)。

### E11. 怎样证明布局优化解决的是供数瓶颈？

关联第 3 题。

> 先固定 M、N、K、dtype 和计时范围，明确分析哪一级存储的数据流量，再结合 FLOPs、读写量和缓存复用假设估算算术强度。然后用 Profile 检查设备执行、搬运和 Host 间隙，做保持数学运算及其他配置不变的布局对照。如果要进一步认定 bank conflict，还需要对应存储层级、地址映射或计数器证据；仅凭改布局后变快，只能说明这条访问路径有改善，不能唯一确定底层原因。

本场项目的真实 Shape、流量和计数器未齐全，参考方法不补写为已经完成的测量；个人已确认事实见[ECG 案例 F3、F6](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)。

### E12. 启用 Sequence Parallel 后，MLP 通信怎样变化？

关联第 4 题。这里指与 TP 组配合、沿 token 轴保存激活分片的一类 Megatron 风格 SP，不泛指所有同名并行策略。

> 我会先确认算子入口和出口的张量布局。在一种常见安排中，进入 Column-parallel MLP 前，各 rank 持有不同 token 行但完整隐藏维，需要 AllGather 得到各 rank 的计算输入；本地 Gate／Up、激活和 Row-parallel Down 后，各 rank 得到完整 token 集上的输出部分和。若下一步只需要各自负责的 token 行，可以用 ReduceScatter 同时完成求和与 token 分片，而不是先 AllReduce 后再切片。
>
> 这个通信顺序来自消费者需要的表示。如果实际算子接口或分片方式不同，就要重新推导，不能把“SP 等于固定替换一个 collective”当作通用规则。

并行与激活分片的一手依据：[Reducing Activation Recomputation in Large Transformer Models](https://arxiv.org/abs/2205.05198)。

### E13. Attention 的 QKV／O 怎样做 TP？GQA 的 KV heads 较少怎么办？

关联第 4 题。

> 常规做法是把 QKV 投影的输出按对应 heads 分给各 rank，本地完成这些 heads 的 Attention；各 rank 的结果再进入按输入维分片的输出投影，得到同一隐藏输出的部分和，按下游布局做归约。这里 Q heads 与 KV heads 的数量可以不同。
>
> GQA 或 MQA 的 KV heads 较少时，要检查后端采用怎样的切分或复制。不能仅因为 TP 增大，就认定每个 rank 的 KV 总会等比例减小。应按真实的 head 映射核对权重加载、缓存容量和 Attention 输入。

固定实现依据：[QKVParallelLinear](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/model_executor/layers/linear.py)。并行度、head 数的可整除条件和复制规则按所选模型与后端核对。

### E14. Conv3D 布局变换怎样确认等价？还应补哪些输入覆盖？

关联第 5 题。

> 先写完整的卷积配置和窗口内索引，确认输入与权重使用同一元素配对，输出轴含义不变，再对照可信参考实现。展平只是表示变化，不能跳过 stride、padding、dilation、groups 等卷积语义的检查。验证应覆盖目标 Shape、边界输入和实际 dtype，再回到模型检查输出与性能。
>
> 当前案例已经有视频 Shape 的随机张量单算子对照，以及图片输入的模型级回归，但没有视频模型级精度回归。这三种证据不能互相替代。未来若要扩大支持范围，应增加相应真实输入和模型级对照后再更新结论。

项目依据：[Conv3D 案例卡 F4、F5](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)。

### E15. 随机投机采样怎样保持目标分布？

关联第 6 题。以下是标准随机投机采样规则，不代表历史项目已实现了该算法。

> 在当前已接受前缀下，令目标分布为 p、草稿分布为 q。候选 x 由 q 采样，以 min(1,p(x)/q(x)) 的概率接受；第一次拒绝时，从与 max(p−q,0) 成比例的归一化残差分布采样，并丢弃该位置之后的草稿。如果候选全部接受，还可从目标模型相应位置的分布采样一个额外 token。
>
> 验证必须使用正确的因果上下文，以及实际采样规则对应的分布，并处理拒绝后失效的缓存状态。不能用任意概率阈值替代这套接受和校正规则。保证的是目标采样分布，而不是两次运行使用同一随机种子后一定逐字相同。

依据：[Fast Inference from Transformers via Speculative Decoding](https://proceedings.mlr.press/v202/leviathan23a.html)。

### E16. 草稿接受率越高，投机解码就一定越快吗？

关联第 6、7 题。

> 不一定。我会用一轮起草、目标验证、调度与缓存处理的总时间，除以本轮实际提交的 token 数，再与相同条件下普通 Decode 的每 token 时间比较。更强的草稿可能成本更高，更长的候选会增加验证和状态处理，大并发时也可能挤占已经充分利用的计算资源。接受率、平均接受长度、每轮实际提交数应分别记录，最终仍看端到端时延与吞吐。

这一比较是平均成本模型；流水重叠、排队和批处理会影响真实结果，不能把某一次高接受率直接换算成服务加速比。

### E17. Prefill／Decode 分离与 TP／PP 有什么关系？

关联第 7 题。

> P/D 分离描述把两个阶段安排到不同的服务资源；TP 和 PP 描述模型内部怎样切分。Prefill 端与 Decode 端都可以采用自己的 TP、PP 或组合，然后解决 KV 交接、布局兼容、请求路由和资源配比。是否值得分离，要比较干扰隔离和资源匹配的收益，能否覆盖 KV 传输及协调成本，并同时满足 TTFT、输出间隔和吞吐目标。它不等于 Prefill 用 TP、Decode 用 PP。

依据：[DistServe](https://arxiv.org/abs/2401.09670)。个人已有的 [P/D 方案卡](../../自我准备/学习设计/ChangeCard-03-PD-KV-transport.md)可作为设计表达素材，不自动成为生产系统落地或性能测量证据。

### E18. MoE 只激活部分专家，为什么显存和延迟仍可能很高？

关联第 10 题。

> 每个 token 使用的专家少，减少的是这次专家计算量，不等于其他专家权重可以不存。如果全部专家常驻，权重仍占容量；如果卸载，会增加搬运和调度。运行时还要承担路由、重排、workspace、专家负载不均，以及使用 EP 时的分发、合并和等待。因此应分别分析权重容量、激活计算、数据搬运与负载分布，不能用“激活参数少”直接推出低时延。

实现中的步骤边界可对照 [vLLM Fused MoE 设计](https://docs.vllm.ai/en/v0.26.0/design/fused_moe_modular_kernel/)。

### E19. 输入已经是 BF16，RMSNorm 再转 FP32 有什么意义？

关联第 12 题，同时准备“先用低精度平方、再转 FP32 求和是否一样”的追问。

> 提升到 FP32 不能恢复输入在转成 BF16 时已经丢失的信息，但可以减少后续平方和归约继续使用低精度带来的误差。比较两条路径时，应使用同一份已经表示为 BF16 的输入，把输入表示误差和算子内部计算误差分开。
>
> 转换发生的位置也重要。如果平方已经在低精度中溢出或被严重舍入，之后转成 FP32 求和无法恢复；需要检查是否先提升再平方，以及乘法、累加、epsilon 和输出转换的实际实现。融合 Kernel 可能使用不同的内部指令，不能只根据 Python 输入 Tensor 的 dtype 推定整个计算过程。

公式及格式依据见第 12 题；这里不把通用做法补写成历史 RMSNorm Kernel 的实现。

### E20. 怎样确认 K/V 交错布局在端到端上有收益？

关联第 9 题。

> 我会固定模型、Shape、dtype、有效上下文和计算路径，分别比较新旧布局的写入或转换成本、Attention 读取成本，以及完整请求的时延和吞吐。再结合可获得的传输量、访问模式和计数器检查归因。仅有读取 Kernel 更快还不够，如果额外转换抵消收益、短上下文没有收益，或者并发时产生新的瓶颈，结论就需要收窄。正确性同时覆盖缓存写入、跨块读取和新旧布局的索引一致性。

这是参考验证方法。现有地平线材料没有对应的完整新旧布局基准，因此不填写假设的性能数字或硬件地址映射。
