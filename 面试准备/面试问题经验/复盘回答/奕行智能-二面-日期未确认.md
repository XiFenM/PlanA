## 1. 芯片计算与存储结构

### 1.1 现场题意与原答

约 08:05，面试官问芯片更像 GPGPU 还是 NPU，以及计算、存储单元怎样组织，并提示只需介绍大致结构。底稿概述原答提到了少量大核、矩阵和向量单元、片外 HBM、片上显式管理 Buffer 与对齐约束。核数、1024 的具体单位及片上单元名称未获独立确认。

### 1.2 优点、不足与更好结构

有效之处是从硬件约束解释适配工作。需要避免用“像 TPU”代替结构说明，也不能由核数少推导没有并行调度。更清楚的顺序是 **计算单元 → 数据存放位置 → 搬运与同步 → 框架受到的约束**，只使用可确认的公开抽象。

### 1.3 参考回答

> 我接触的是自研 AI 加速芯片，执行模型更接近专用矩阵与向量计算单元配合的软件栈，不能直接套用 GPU 的 thread／warp 层次。我会从软件可见的接口说明：矩阵类计算由相应加速单元执行，向量或布局处理走对应算子路径，数据在片外存储和软件管理的片上缓冲之间搬运。
>
> 对框架适配更直接的影响是支持哪些 dtype、输入布局与对齐、哪些计算能并行，以及提交和完成怎样同步。即使逻辑 Tensor 的 Shape 相同，实际物理补齐和搬运量也可能不同，因此要把布局与执行依赖一起检查。我负责模型和框架侧接口、问题定位与验收；具体硬件内部组织和微码实现按硬件、算子团队的正式接口说明。

GPU 对照只用于说明执行抽象差异，可参见 [CUDA 编程模型](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html)，不把其参数移植成自研芯片事实。

## 2. 片上存储与 GPU 的类比

### 2.1 现场题意与原答

约 11:30，面试官追问片上存储对应 NVIDIA GPU 的什么单元。原答把 Buffer 类比为 Shared Memory，并强调显式搬运；底稿还记录了没有 L1／L2 的说法，但审计要求限定为具体架构或软件可见模型。

### 2.2 优点、不足与更好结构

“由软件管理复用”是有效类比。问题在于把功能相似说成硬件完全相同。回答应先讲共同属性，再列可见范围、生命周期、搬运方式与同步的差异；“没有自动 cache”不能成为所有 NPU 的共同结论。

### 2.3 参考回答

> 如果只比较软件职责，显式管理的片上缓冲可以类比 GPU Shared Memory：程序需要决定搬入哪些数据、怎样复用，并保证生产者与消费者的顺序。硬件管理的 cache 则主要根据访问自动保留和替换数据，两者管理方式不同。
>
> 但这个类比不代表容量、bank 组织、可见范围和同步机制一致。GPU Shared Memory 通常有明确的线程协作范围；目标芯片可能按计算核、任务或专用搬运单元管理，必须看实际接口。回答某个 Buffer 的用途时，我会说明谁分配、谁写入、谁读取、何时可复用，再讨论它是否类似 Shared Memory。对于没有确认的 cache 层级，不凭“TPU 类架构”作判断。

这里保留的是存储管理方式的对照，而不是经过硬件手册验证的逐单元映射。GPU 侧的层次与线程协作范围见 [CUDA 编程模型](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html)。

## 3. Layout 转换在哪里发生

### 3.1 现场题意与原答

约 12:30，面试官用 Strided 访问、Transpose、Permute 等例子追问转换位置。底稿概述原答为在向量单元执行相关算子。回答给出了一个执行位置，但没有区分改元数据和真正搬运数据。

### 3.2 优点、不足与更好结构

应按 **逻辑视图 → 下游能否消费 stride → 是否需要物化 → 物化的位置与成本** 说明。不能把每个 `permute` 都当作设备拷贝，也不能认为所有 `reshape` 都不分配。一般 Tensor 语义与目标插件的实际路径要分别核对。

### 3.3 参考回答

> 先看操作是否真的改变物理存储。在 PyTorch 的常见 strided Tensor 语义下，transpose 或 permute 可以只改变维度和 stride；如果下游算子能按这个 stride 读，就不必先复制。若下游要求特定连续布局，则可能在 contiguous、后端重排或算子内部产生真实搬运；reshape 也可能返回视图或触发复制，不能只凭 API 名称判断。
>
> 在自研后端，真实重排可以由相应设备算子完成，也可能与消费算子融合。我要沿调用链检查实际分配、stride 和 trace，确认在哪一步搬运、是否重复物化。静态权重可以考虑加载期预排布，动态激活则要把每次转换及下游收益一起计算。我的工作是定义框架与算子的布局契约、定位多余转换并验收，不把向量 Kernel 的实现归给自己。

视图与复制语义依据固定提交的 [PyTorch Tensor Views](https://github.com/pytorch/pytorch/blob/0bd89deb431509d893177a84cfa4768aa0399809/docs/source/tensor_view.md)。项目例子见 [ECG 布局案例卡](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)。

## 4. C++、Python 与 PyTorch 注册

### 4.1 现场题意与原答

约 13:10，面试官问语言分工以及 C++ 能力如何暴露给 Python／PyTorch。原答提到插件、设备与算子接口、pybind11；审计认为绑定层回答有效，但没有完整说明 PyTorch 算子注册和后端分发。

### 4.2 优点、不足与更好结构

先区分普通 C++ API 绑定和 PyTorch operator，再讲 schema、backend 实现及执行路径。注册并不自动带来 Autograd、FakeTensor 或编译兼容；需要什么能力，就补相应实现和验证。不把通用完整链路说成自己全部做过。

### 4.3 参考回答

> 如果目标只是把普通 C++ 函数暴露给 Python，可以用 pybind11 定义模块和函数绑定。若希望它成为 PyTorch 算子，还要定义算子 schema，并把实现注册到相应分发键；Python 调用进入 dispatcher 后，由 Tensor 的设备等信息选择实现，再调用后端 runtime 和设备 Kernel。绑定与 dispatcher 是不同职责，不能只用 pybind11 概括全部过程。
>
> 接口层需要检查 Shape、dtype、布局、设备和当前执行流；异步算子还要保证输入存活和完成顺序。若算子要支持训练或图编译，还需按需求提供 Autograd、Fake／Meta 等能力，并测试这些组合。我的经验主要是框架接口、Tensor／Storage／Layout 和拷贝问题的适配与调试，底层 runtime、Kernel 和完整编译器实现有各自团队负责。

机制可对照 [pybind11 官方教程](https://pybind11.readthedocs.io/en/stable/basics.html)与 [PyTorch C++ 自定义算子教程](https://docs.pytorch.org/tutorials/advanced/cpp_custom_ops.html)。个人边界采用现有 [Claim 矩阵](../../自我准备/Claim-evidence矩阵.md)，不以教程覆盖范围代替项目证据。

## 5. DeepSeek、TP 与 EP 的通信

### 5.1 现场题意与原答

约 14:45–20:20，问题包括模型版本、部署卡数、DeepSeek 模型架构与通信，以及同一个 MoE／FFN 是否同时有 All-to-All 和 AllReduce。底稿概述原答先从 Profile 讲 collective，后来区分早期 TP 与后续 EP 配置。32 卡、单卡容量和具体并行组合未独立核实。

### 5.2 优点、不足与更好结构

实际观测有价值，但要先固定配置，再解释张量分片和通信组。TP 与 EP 并不互斥；Profile 同时出现两种 collective，也不能证明属于同一子层。历史部署细节没有足够确认材料，参考回答不补造配置。

### 5.3 参考回答

> 先以公开的 DeepSeek-V3 结构为例：Attention 使用 MLA，以压缩的 latent 等表示保存所需历史状态，减少 KV 存储；FFN 路径采用 DeepSeekMoE，包含共享专家和按 token 选择的路由专家。因此总参数量主要影响权重容量，每个 token 实际激活的参数与计算量则小得多，但路由、重排与通信仍有成本。训练中的 MTP 目标和推理时是否启用投机路径也要分开。这些是公开架构特征，不能据此确认本场实际部署了哪一份权重、量化或并行配置。
>
> 我会先明确讨论哪一套部署配置，避免把早期 TP 和后续 EP 的观测混在一起。TP 描述一个张量怎样切分，EP 描述专家怎样分布，两者可以组合。以普通 TP MLP 为例，Gate／Up 按输出通道分片，各 rank 本地完成对应激活；Down 按输入通道分片后得到同一输出的部分和，需要按下游布局做 AllReduce 或 ReduceScatter。
>
> MoE 启用 EP 时，token 需要送到持有目标专家的 rank，专家结果再回到对应请求，常见实现分别有 dispatch 与 combine 通信。如果专家内部还使用 TP，或模型其他部分使用 TP，执行图里还可能出现归约。因此要把 Attention、共享专家、路由专家和 logits 分开看。最后是否 Gather 或 AllGather 词表输出，也取决于采样位置和实现。
>
> 我的框架适配工作重心是检查分组、Shape、dtype、同步和执行结果，再把 Profile 中的通信对应到这些步骤；不将它表述为独立设计了整套并行框架。

结构背景见 [DeepSeek-V3 报告](https://arxiv.org/html/2412.19437v2#S2)；实现边界见 [vLLM Fused MoE 设计](https://docs.vllm.ai/en/v0.26.0/design/fused_moe_modular_kernel/)。训练框架经历遵循 [CL09 修订](../../自我准备/Claim-evidence矩阵.md#claim-wording-decisions-20260929)的基础通信后端测试调试口径。

## 6. 机内与机间通信

### 6.1 现场题意与原答

约 20:25，面试官问机内、机间的通信行为是否相同，差距来自哪里。原答从片间直连、网卡和交换网络解释；底稿中的 RDMA／IB 关系存在术语不确定性，不能直接判定原音频中的某一句说错。

### 6.2 优点、不足与更好结构

链路差异方向合理，应再分开 **collective 语义、rank 拓扑、传输能力和性能**。RDMA 是访问能力，InfiniBand 是互联体系，RoCE 可在以太网上提供 RDMA；不是“机内 RDMA、机间 IB”的二选一关系。

### 6.3 参考回答

> 相同的 AllReduce 在机内或跨机都需要完成规定的归约语义，但实现算法和传输路径可以不同。机内可能使用设备直连、PCIe 或厂商互联，跨机通常还要经过网卡和交换网络；具体应看拓扑以及设备内存能否被网络路径直接访问。
>
> RDMA 可以通过 InfiniBand、RoCE 等技术提供，不能把它当作机内链路的同义词。性能上，小消息常受启动、同步和协议开销影响，大消息更需要关注有效带宽、拥塞和 NUMA 路径。通信库也可能在节点内、节点间采取不同层级的归约方式。
>
> 我会固定 rank 数、消息大小和 dtype，分别测节点内与跨节点路径，再看完整 collective 和模型关键路径。不能只凭网卡标称带宽预测端到端时延，也不能把某次机间较慢的结果推广到所有配置。

RDMA 与各互联技术的关系见 [NVIDIA RDMA 编程指南](https://networking-docs.nvidia.com/doca/archive/3-5-0/rdma-aware-networks-programming-guide)。这里不替历史项目填写未确认的协议和物理拓扑。

## 7. 静态权重预排布

### 7.1 现场题意与原答

约 23:05，面试官问其他模型优化，随后确认是否修改了底层算子。原答介绍 blocked Col-major、加载期预处理及算子团队协作。底稿的“全带宽”“消除 bank conflict”已被审计收窄，不能当作测量结论。

### 7.2 优点、不足与更好结构

保留“硬件读取方式—布局—转换时机”的因果链；补清块内／块间顺序、个人分工、验证与代价。项目事实采用 [ECG 布局案例卡](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)，不沿用未确认的 1024 粒度或独立百分比收益。

### 7.3 参考回答

> 我做过静态参数权重的 blocked Col-major 预排布。ECG 项目中，常规 Host 和小 Shape 优化后，Decode 矩阵乘仍较重，我们结合 Shape、读写量和 Profile 继续检查供数路径。最终保持 Tile 大小不变，Tile 内按行排列，Tile 之间按列排列，让权重布局更匹配消费 Kernel 的分块读取。
>
> 我负责框架侧 Tensor 扩展和加载后预排布，算子同事实现对应 Kernel 访存。转换后不保留原布局权重，Prefill 和 Decode 复用新表示；动态的 QKᵀ 和 Attention 概率乘 V 不在范围内。代价是加载期处理和专用布局接口维护。
>
> 已有同芯片新旧布局对照中，MatMul 输出逐元素数值相等，模型 logits 和输出 token 一致；结论只覆盖既有测例。ECG 请求平均时延经多项优化从约 30–40 秒到 20 秒以内，不能把全部收益归给布局。这组数来自 Transformers 执行链，技术后来移植到 vLLM，不把两者混成一次测量。

具体计时条件见案例卡 F2／F6：前后各 10 次并含首次运行，计入图像预处理；当前没有布局独立加速比，也没有足够计数器证据认定冲突的硬件层级。

## 8. MatMul 的 Roofline 推导

### 8.1 现场题意与原答

约 26:15，面试官问怎样理论评估优化空间；约 29:15 又收窄为单个 MatMul。原答讲清了 Profile、Host 气泡和小算子检查，但没有完整推导计算量、数据移动量和理论界限。

### 8.2 优点、不足与更好结构

工程观测方法可保留，顺序改为 **定义问题和存储层级 → 算 FLOPs／Bytes → 上界或下界 → 实测解释差距**。Bytes 公式必须带假设，不能对所有 dtype、缓存和 `C=αAB+βC` 机械使用同一个系数。

### 8.3 参考回答

> 对 A[M,K] 与 B[K,N] 相乘得到 C[M,N]，常用约定下计算量约为 2MNK FLOPs。先以 HBM 为计量边界，假设 A、B 各读一次、C 只写一次、每元素 s 字节，则理想流量是 s(MK+KN+MN)。如果还需要读旧 C、存在量化参数、额外重排或重复载入，就要加上相应流量；缓存常驻也会改变这个边界。
>
> 计算强度 I 等于 FLOPs 除以 Bytes。使用匹配 dtype 和稠密性口径的算力 P、带宽 B，简化 Roofline 给出性能上界 min(P, I×B)，对应时间下界 max(FLOPs/P, Bytes/B)。它是模型中的界限，不是该 Shape 必然达到的速度；小矩阵、对齐浪费、流水填充和启动时间还会降低实际效率。
>
> 然后用实测耗时计算有效 FLOP/s，结合内存流量与执行时间线判断差距。如果理论已偏访存，就优先检查数据复用和布局；若预测偏计算而实测很低，则继续看矩阵单元利用、Kernel 选择及等待。端到端还要单列 Host、通信和排队，不能把单算子 Roofline 当成整个服务的加速预测。

模型依据 [Roofline 原始技术报告](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2008/EECS-2008-134.html)。当前项目只支持初步估算经历，不将上述完整测量流程写成已经全部完成。

## 9. Coding Agent 与验证

### 9.1 现场题意与原答

约 30:20，问题是是否使用 Coding Agent、怎样避免误导。底稿概述了辅助排障和实验脚本、误生成其他芯片平台接口，以及人工 review 和自动测试。工具名、模型代际与具体误用接口未独立核实。

### 9.2 优点、不足与更好结构

具体失败例子比泛泛强调效率更有说服力。补充 **来源约束 → 小范围修改 → 针对性验证 → 人工裁决**，不宣称 review 或 CI 能保证所有代码正确，也不虚构节省了多少工时。

### 9.3 参考回答

> 我会用 Agent 辅助检索调用链、整理排障假设和生成对比脚本，但对目标平台接口不能只信生成结果。遇到过它根据相似后端代码生成不属于当前平台的接口，因此我会让建议落到当前仓库、具体版本和已有函数，再检查它究竟是在引用真实实现，还是根据名称推测。
>
> 修改先限制在可以审查的范围，说明输入输出、预期行为和失败条件。验证也要对应修改目的：接口存在和能编译只是第一步，数值路径要做参考对照，异步路径要检查执行依赖，性能修改要比较相同负载下的完整时间。生成的测试同样需要审查，避免它只验证自己的实现假设。
>
> 最终由我判断代码和证据能否支持结论。测试通过只说明覆盖的条件下通过；没有实际运行的测试、没有可比较的数据，就不报告成已经验证的正确性或收益。

这里整理的是本场已有工具使用方式和通用工程判断，不新增特定产品功能、模型版本或生产自动化成果。

## 10. 模型精度异常排查

### 10.1 现场题意与原答

约 34:35，面试官问模型接入中的精度问题。原答从乱码、重复特殊字符入手，检查 logits／采样、逐层或二分 Dump、参考实现以及 collective 前后。方法较完整，但具体容差和复现条件没有展开；感叹号不能跨 tokenizer 等同为固定 token ID。

### 10.2 优点、不足与更好结构

先固定输入与执行条件，再找首个分歧；区分数值差异、采样放大、错误元数据与内存／同步问题。二分适合稳定可复现的偏差，随机故障要同时关注调试操作对时序的影响。

### 10.3 参考回答

> 我先固定模型权重、输入预处理、tokenizer 和采样配置，确认异常是每次稳定出现还是概率性出现。对于生成结果，先找第一次分叉的 token，再比较该位置 logits、候选概率和采样输入；不能只看最终文本，因为一个早期差异会影响后续全部上下文。
>
> 如果分歧来自模型计算，就沿网络比较中间结果，在可稳定复现时用二分缩小到首个异常层，再提取真实 Shape 的算子用例。比较时同时看 NaN／Inf、绝对与相对误差及任务影响；余弦相似度高也不能单独证明每个关键元素正确。多卡路径还要固定 rank 分组和分片含义，检查 collective 前后的预期数学结果、缓冲写入与完成顺序。
>
> 如果增加 Dump 后异常反而消失，我会保留这个线索，减少侵入性日志并做异步／阻塞控制实验，不直接断言某个算子数值有问题。修复后既重跑最小用例，也回到原请求集验证，结果只报告实际覆盖范围。

跨平台不保证逐位一致、批量形态与归约次序影响误差等边界见 [PyTorch 数值精度说明](https://docs.pytorch.org/docs/2.15/notes/numerical_accuracy.html)。个人方法与现场回归依据[异步 H2D 案例卡](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)。

## 11. Host Padding 与异步 H2D 竞态

### 11.1 现场题意与原答

约 37:35，面试官问单例正常、整网或并发下随机出错的经历。原答呈现了概率性乱码、强制同步后消失和 Host Padding 依赖缺失。底稿中的“125 次约 30 次异常”未独立确认；当前答法采用[异步 H2D 案例卡](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)已确认的修复链、2026-11-01 补充的修改层级与回归配置，不能当成现场已报出的新细节。

### 11.2 优点、不足与更好结构

这是较完整的排障案例。关键补强是区分定位实验与最终修复：同步后不出错支持时序相关，但不能单独锁定根因，也不意味着应永久串行化全部链路。应完整交代生产、提交、完成、消费四个时刻。

### 11.3 参考回答

> 我处理过异步 H2D 开启后低概率出现乱码、空回复和重复循环的问题。先固定请求与采样配置找首个分叉，再比较中间结果；大量 Dump 会让问题消失，提示调试改变了时序。将异步 H2D 单独改为阻塞后，异常随之消失，这支持临时规避方案，也把范围缩小到相关路径，但还不能凭这一步认定具体竞态。
>
> 后续确认链路有两个阶段：后台先完成 CPU Padding，再向设备 Stream 提交 H2D。原等待只覆盖已经进入设备 Stream 的任务，没有覆盖 Padding 完成与 H2D 提交。等待过早时，设备队列可能暂时为空，消费者却继续执行。完整顺序必须是 CPU Padding 完成、H2D 提交、设备拷贝完成，最后下游消费。
>
> 我在框架／后端层将 Padded Tensor 纳入统一的异步任务标记与等待机制，使消费者等到前置阶段全部满足，Runtime 无需修改。修复后恢复原先触发异常的异步配置，撤掉临时阻塞和额外诊断等待，再用现场 168 条请求重放 5 轮，共 840 次，未再观察到原有异常。这证明该请求集和配置内的修复效果，不代表所有并发和 Shape 都已排除竞态。

## 扩展问题与参考回答

以下是补充准备，不据此评价原回答，也不自动形成新的项目成果。

### E1. 对齐、stride 和 bank conflict 是一件事吗？

> 不是。对齐描述地址或维度是否满足某个粒度；stride 描述相邻逻辑元素在存储中的步长；bank conflict 则需要说明在哪一级分 bank 的存储、哪些访问同时争用同一 bank。它们可能互相影响，但不能由“不连续”直接推出 bank conflict。先给地址与访问模型，再用对应计数器或控制实验支持归因；没有这些证据时，只说布局改善了访问路径。

### E2. TP 的 AllReduce 与 EP 的 combine 能否互相替代？

> 不能只凭两者最后都有求和就替换。TP 归约合并同一输出坐标的分片贡献；EP combine 要按 dispatch 元数据把不同专家的输出送回对应 token，并处理路由权重和专家结果合并。若专家内部还做 TP，还可能需要额外归约。首先核对数据归属、输出形状、通信组和权重处理位置，再选择接口。[vLLM MoE 设计](https://docs.vllm.ai/en/v0.26.0/design/fused_moe_modular_kernel/)

### E3. 看见 AllReduce 耗时长，就说明网络慢吗？

> 不一定。某个 rank 先进入 collective，计时可能包含等待其他 rank 到达；还有 Host 提交、同步和拷贝等因素。先对齐各 rank 时间线，区分到达偏斜与实际传输，再用相同消息量的独立测试检查链路。如果优化上游计算后等待减少，不能把变化全部算成网络带宽提升。

### E4. 如何验证 pybind11 绑定后的自定义算子？

> 分开验证绑定、dispatcher 和计算。先检查符号可调用及参数错误处理，再检查不同设备、dtype、Shape 和布局是否选到正确实现；数值与可信参考比较。若需要 Autograd 或编译，另测对应注册。异步路径还要检查输入生命周期和执行顺序。`opcheck` 可以检查部分注册契约，但不能代替算子的数值正确性验证。[PyTorch 自定义算子教程](https://docs.pytorch.org/tutorials/advanced/cpp_custom_ops.html)

### E5. 为什么打印 Tensor 可能让竞态消失？

> 打印和 Dump 可能引入设备同步、回读、额外拷贝或调度延迟，改变生产者与消费者的相对顺序。现象消失只说明观察操作影响了执行条件。应保留最少的顺序日志，做单点异步／阻塞对照，再检查真正的完成事件；不能把加日志本身当成修复。

### E6. Stream 同步能等到未来才提交的 H2D 吗？

> 不能仅靠等待当时已经入队的任务保证这一点。若 Host 生产者尚在准备数据，必须先有机制等待准备完成并确认拷贝已提交，再等待相应设备完成，最后允许消费者读。具体用 future、任务句柄或其他机制取决于平台；不要把 CUDA API 名称直接套成自研 Runtime 实现。[案例卡中的依赖链](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)

### E7. 840 次没有复现，可以说异常率变成零了吗？

> 可以准确报告“恢复原异步配置、撤掉临时阻塞与诊断等待后，168 条现场请求重放 5 轮、共 840 次未观察到原异常”，不能据此证明所有负载上的真实异常率为零。请求之间可能不独立，覆盖也有限。若以后扩展不同并发、Shape 或运行时条件，应单独记录新增范围，不回写为这次已经覆盖。

### E8. 做过 Roofline 初步估算，怎样表达而不夸大？

> 我做过结合 GEMM Shape、FLOPs 和最低读写量的初步估算，用来判断权重读取可能是主要限制，再以 Profile 和布局对照收敛优化方向。尚未完整恢复存储层级的实测流量、缓存复用和有效带宽，所以不把它称为每个 Kernel 都有完整可复算的 Roofline 验证。[ECG 案例卡](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)
