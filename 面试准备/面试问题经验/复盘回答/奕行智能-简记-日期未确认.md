## 1. 怎样判断是否融合算子

### 1.1 已有记录与无法判断之处

简记提到“是否会溢出到显存、减少 Tensor 形状变换、减少 H2D／D2H 打断流水线”。无法确认这是本人回答、面试官提示还是事后总结，也不能确定“溢出到显存”指片上数据 spill、是否物化中间结果，还是总显存容量问题。

### 1.2 更好的准备方式

把判断分成语义、数据移动、资源和端到端收益四层。特别注意：transpose 本身也可能只生成 view；只有需要物化的 contiguous、布局转换等路径才产生相应搬运，reshape 是否复制也要看原布局。设备 Kernel 融合不会凭空消除主机与设备之间的依赖。

### 1.3 参考回答

> 我会先确认融合是否合法，包括数值行为、状态修改和消费者是否一致，再看能否减少真实中间张量的写回、重复读取、转换和下发。如果所谓形状变化只是 view，未必有值得消除的拷贝；如果确实发生了物化和布局转换，就要把读写成本算进去。
>
> 融合后还要检查资源。中间值留在寄存器或片上存储可能减少 HBM 往返，但过大的融合也可能造成 spill、降低并行度，或者失去原有专用 Kernel 的效率。如果是整卡峰值内存不足，还需分析同时存活的 Tensor 与 Workspace，而不能只数算子个数。
>
> 对 H2D／D2H，我会先说明为什么该数据要跨主机和设备。如果是 Host 读取中间值造成同步，需要改变执行位置或依赖路径才可能消除；单纯把两个设备算子合并不保证减少传输。最后固定负载，比较完整子图和端到端时延，并重新检查正确性。

机制依据：[PyTorch Tensor Views](https://docs.pytorch.org/docs/stable/tensor_view.html)、[FlashAttention 的 I/O 分析](https://arxiv.org/abs/2205.14135)。个人实例可引用[ECG 布局案例](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)，但不能认定它就是本简记第一行所指的案例。

## 2. DeepSpeed 训练与后端适配

### 2.1 已记录主题与准备边界

只有“DeepSpeed 训练”四字，不知道现场是否问过 ZeRO、offload 或具体故障。下面作为该主题的完整答题入口，所有细节不标为现场追问。

### 2.2 更好的回答方式

先交代个人参与层次，再解释训练状态和通信。典型 ZeRO 数据并行组中的划分如下：

| 阶段 | 分片内容 | 需要解释的代价 |
| --- | --- | --- |
| ZeRO-1 | 优化器状态 | 更新各自负责的参数状态，并协调参数副本 |
| ZeRO-2 | 再分片梯度 | 梯度归并与分片，仍需维护前后向使用的参数 |
| ZeRO-3 | 再分片模型参数 | 前向／反向在需要时取得参数分片，带来收集、缓存与生命周期管理 |

offload 将相应状态或计算移到 CPU／存储等位置，activation checkpointing 通过重算减少保存激活，两者解决的对象和开销不同。依据：[DeepSpeed ZeRO 文档](https://deepspeed.readthedocs.io/en/stable/zero3.html)。具体 collective、bucket 和预取策略依实现配置，不能只背一个固定序列。

### 2.3 参考回答

> 我在训练框架方面主要做自研芯片的通信后端基础测试和调试，使用过 DeepSpeed、Megatron-LM 的相关测试定位分组、Shape、Padding 和同步语义问题，不将这部分经历扩大为独立设计完整训练系统。
>
> 从机制上看，ZeRO 逐步在数据并行组内分片优化器状态、梯度和参数，减少副本冗余。Stage 3 还需要在计算前拿到相关参数，因此要同时考虑分片节省的容量，以及参数收集和释放带来的通信与调度成本。Offload 还会引入主机或存储路径，不能只看设备显存下降。
>
> 适配时我会先验证单个通信操作的输入输出、dtype、rank group 和完成语义，再运行真实框架调用，并检查训练数值和时间线。已有项目中，我定位过多 Stream 没有形成有效重叠，反而拆散提交批次的问题，并实现可回退的单 Stream 方案；这个结论只适用于相应后端和负载，不意味着所有平台都应关闭通信重叠。

个人范围采用 [CL09 的已确认修订](../../自我准备/Claim-evidence矩阵.md#claim-wording-decisions-20260929)，具体素材见[分布式适配档案](../../自我准备/projects/DeepSpeed-Megatron-project.md)。本节不补写缺失的并行配置、Loss 数字或完整交付范围。

## 3. 框架上的特性怎样适配

### 3.1 已记录主题与准备重点

原简记没有特性名称。参考回答应展示一个可迁移的方法，并用有依据的案例说明改动层次；不能把列出的所有层都写成每次适配都必须重写。

### 3.2 更好的回答方式

**特性语义 → 对后端的能力要求 → 已有接口与缺口 → 最小执行路径 → 正确性 → 性能与回归。**

需要分别检查数据类型、内存／流语义、算子和状态管理。支持一个 API 名称与实现其完整契约不同；CPU fallback 的正确结果也不能直接证明设备路径可用。

### 3.3 参考回答

> 我会先理解特性对外承诺的行为，再沿调用路径确认它依赖哪些后端能力。例如异步拷贝不仅是提供一个 Copy 接口，还涉及 Host 数据何时准备完成、何时提交、设备何时完成，以及消费者何时允许访问。
>
> 然后确定最小改动边界：已有能力能够复用的部分保持一致，缺失的接口或语义单独补齐。先做能验证契约的小 case，再放回框架和模型执行链，确认没有静默走到 fallback。
>
> 对性能特性，我还会检查它是否改变同步和缓冲生命周期。原有结果正确并不代表新并发路径正确，因此要在恢复真实执行配置后做回归。最终说明哪些由我修改、哪些依赖 Runtime 或算子团队，以及还有哪些配置没有验证。

已有[异步 H2D 案例](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)支持一条明确实例：补齐 CPU Padding 完成、H2D 提交、设备完成和消费之间的依赖，修复在框架／后端层完成，Runtime 无需修改；撤掉临时阻塞后，在 168 条请求×5 轮中未复现。它用于当前项目回答，不证明本场简记所指的特性就是这一次修复。

## 4. vLLM V0／V1／V2 的语境与比较方式

### 4.1 已记录内容与未知项

原简记只有“vllm v0-v1-v2”。“V2”可能指某个内部代际、执行组件或其他版本称呼，现有材料无法确定。不能把当前某个带 V2 名称的实现自动填入历史题意，也不要求重新回忆后才能继续准备。

### 4.2 更好的回答方式

首先区分引擎代际、软件包版本与某个 Runner 的版本；对未明确的名称说明条件，再比较能够绑定实现的差异。V0 与 V1 的公开演进可从核心循环、调度表示、缓存管理、Persistent Batch 和编译／多模态执行的组合来说明。

### 4.3 参考回答

> 我会先确认这里的版本指整个引擎，还是某个执行组件或内部分支。V0 与 V1 可以按公开引擎演进比较：V1 更系统地分离核心执行循环和其他 CPU 工作，按 token 进度统一调度，并通过复用输入状态和增量更新降低每轮准备开销。它继承和重组了不少已有能力，不能把分页、前缀缓存或异步拷贝都说成第一次出现。
>
> 对 V2 这个名字，我不会只凭编号给出差异，需要先把它对应到具体代码和版本。比较时看接口、状态所有权、调度与执行路径、后端支持和迁移验证，而不是断言版本号越大就必然更快。实际项目迁移还要检查模型、采样、KV metadata、异步和编译路径有没有变化。

公开比较依据：[vLLM V1 发布说明](https://vllm.ai/blog/2025-01-27-v1-alpha-release)。更详细的当前标准答法可交叉阅读[小红书第 1 题](小红书-简记-日期未确认.md#1-vllm-v0-与-v1-的区别)，两份简记的现场证据仍彼此独立。

## 6. 如何研究新模型并形成工程判断

### 6.1 已记录主题与准备重点

原简记没有具体模型。应准备从资料到部署决策的过程，区分已经适配的模型与只是读过资料的模型，避免用模型名称列表代替理解。

### 6.2 更好的回答方式与参考回答

> 我会先读官方模型说明、config 和实际实现，核对注意力类型、heads、位置编码、MoE、量化与多模态结构，而不是只看参数规模。接着把差异映射到部署问题：缓存保存什么、怎样随长度增长、需要哪些算子和数据类型，以及调度、通信和编译有什么新增要求。
>
> 对影响最大的差异，我会用最小可验证路径检查语义，再用代表性负载估算或测量计算、内存与数据搬运。适配决策应该说明预计收益、依赖、风险和验证范围；公开论文的结果不能直接作为目标硬件的性能结论。
>
> 介绍个人经验时，我会把资料核验、最小验证、框架接入和生产交付分开。没有实际做过的型号只说研究过哪些结构，不将相似模型的经验全部迁移成已完成适配。

当前可以引用[GLM 项目档案](../../自我准备/projects/GLM5-3-flash-project.md)中的混合状态分类、容量核算和状态拆池，说明结构变化怎样影响工程。该项目有自己的时间、版本和交付范围，不用于补写本简记的现场经历。

## 7. Attention 的融合粒度怎样选择

### 7.1 已记录主题与准备边界

简记没有指明 Prefill、Decode 或某个 Kernel。以下先讨论普通 decoder-only full attention 的典型路径，再给条件化答法；原回答无法评价。

### 7.2 更好的回答方式

沿 QKV 投影、位置变换、KV 写入与 Attention、输出投影检查可复用的数据和必须保持的状态。融合的单位可以是图级接口、多个 Kernel 或单个 Kernel，三者不能混称。

Prefill 的 Attention core 可以通过分块与在线 softmax 避免完整注意力矩阵写回；Decode 更需要考虑历史 KV 读取、小 batch、下发开销和分页布局。把 QKV、RoPE、KV 写入、Attention、输出投影全部合成一个 Kernel，并非普遍可行或最优。

### 7.3 参考回答

> 我会先看阶段和负载。Prefill 的 QK、softmax、PV 之间有很大的中间结果，采用分块与在线归一化可以减少 HBM 物化；Decode 的 query 较少，更关注历史 KV 读取、分页寻址和下发成本，两者不应只用同一套大矩阵思路。
>
> 具体融合时，先看数据能否在兼容的 Tile 和布局里被连续消费，例如位置变换与 KV 写入是否能减少一次中间读写。再评估寄存器、片上存储、并行度和其他消费者，不能为了减少 Kernel 数量而把工作集扩大到资源不合适。
>
> KV 写入属于有状态操作，融合后仍要保证逻辑位置、物理槽、dtype 和读写顺序正确。我会把数值、状态和不同 Shape 回归放在性能比较前，分别测子图和端到端结果，再决定融合边界。

依据：[FlashAttention](https://arxiv.org/abs/2205.14135)及[vLLM Paged Attention](https://docs.vllm.ai/en/v0.26.0/design/paged_attention/)。前者保留 dense Attention 的数学计算，不能仅因减少中间矩阵就称计算复杂度变为线性。

## 扩展问题与参考回答

以下问题为补充准备，不据此推断现场曾经追问。

### E1. ZeRO、TP 与 activation checkpointing 能否互相替代？

> 不能直接互换。ZeRO 主要减少数据并行副本之间的模型状态冗余，TP 分配层内计算与参数，checkpointing 用重算换激活存储。它们可以组合，但分别引入通信、调度或额外计算，应根据权重、优化器状态、梯度和激活哪个占主导来选择。

### E2. 为什么不能只用 Loss 能下降判断训练适配正确？

> 错误实现也可能在某些输入上产生下降趋势。需要固定配置，对照可信路径检查关键输出、梯度、更新和通信语义，并观察足够范围内的训练行为。还要区分数值误差容忍、随机性和实际接口错误；没有对照记录时，不把“跑了几步”写成精度已对齐。

### E3. 多 Stream 为什么可能更慢？

> 只有依赖允许且硬件能够并发执行时，独立 Stream 才可能带来重叠。额外 Event、Wait、提交批次拆分和资源竞争都可能抵消收益。已有项目的单 Stream 改动针对特定后端的批量提交与等待开销，不能据此推导其他平台也应串行执行。

依据：[训练通信项目](../../自我准备/projects/DeepSpeed-Megatron-project.md)。

### E4. 框架测试通过，却没走到目标 Kernel，如何发现？

> 除输出对照外，还要检查调用轨迹、设备信息或计数，确认目标分发路径真正命中。可以设置受控反例或禁用 fallback，验证缺失实现时测试会失败。性能测试也应确认没有在两条名义不同的路径上执行同一参考实现。

当前[GLM 项目](../../自我准备/projects/GLM5-3-flash-project.md)记录了通过调用计数发现 native／fused 两侧回退的问题，引用时保持该项目的独立时间和范围。

### E5. 提高融合粒度是否总能减少峰值内存？

> 不一定。融合可能减少全局中间张量，也可能延长其他数据的生命周期、增大 Workspace 或发生寄存器 spill。必须沿实际分配和存活关系计算峰值，而不是只比较输出 Tensor 的个数。

### E6. 新模型的理论显存够用，为什么仍会 OOM？

> 逻辑元素量只是起点，还可能有物理补齐、缓存页粒度、不同状态组、临时 Workspace 和并发存活的缓冲。应按后端实际分配单位核算，并通过分阶段观测确认增长位置；不能把一个逻辑 Shape 的估算当成完整峰值。

项目例子见[Conv3D 案例](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)与[GLM 混合缓存项目](../../自我准备/projects/GLM5-3-flash-project.md)，两者的原因和测试数据分别保留。

### E7. 怎么区分图级融合与单 Kernel 融合？

> 图级接口可以对外呈现为一个操作，但内部仍可能执行多个 Kernel、拷贝或通信。单 Kernel 融合则把更多计算放入一次设备执行中。应说明实际执行步骤和中间数据在哪里，以及测量是否包括准备、重排和通信，不能凭算子名称判断实现粒度。
