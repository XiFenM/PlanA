> 因此，某个模型可以被加载并不代表部署完成，还要检查输出、缓存与多请求执行是否正确，性能是否达到约定目标，并让这些条件进入后续回归。

## 3. KV 对齐与 Prefix Cache

### 3.1 现场题意与原答

约 04:05–08:00，面试官追问自研后端适配难点。原答讨论硬件强对齐与 Prefix Cache 复用，并提到二次切分或取模。审计认为问题方向成立，但“256”的单位、逻辑块与物理分配的具体映射不清，不能据概述证明方案已完整验证。

### 3.2 优点、不足与更好结构

按 **token 粒度 → 物理字节与对齐 → 索引 → 复用条件 → 代价** 说明。不能用硬件字节对齐直接替代每块 token 数，也不能仅凭“二次切分”推导命中率或正确性。

### 3.3 参考回答

> 这类问题的核心是框架逻辑粒度与设备存储接口的约束可能不一致。我会先定义 vLLM 的 block_size 表示每块容纳多少 token，再说明后端要求哪些维度、地址或字节数对齐。两者通过实际 layout 和索引关联，不能因为数字相似就当成同一个单位。
>
> 在普通分页缓存中，block table 表示请求的逻辑块对应哪些物理块，本步写入位置再映射到具体槽位。Prefix Cache 复用则还要满足模型、token 前缀和相关输入条件一致。若物理分配较大，希望以更细粒度复用，就必须明确小逻辑段怎样放入物理空间、索引怎样计算、哪些内容允许共享以及何时可回收，Attention backend 也要接受相同契约。
>
> 验证会覆盖非整块长度、跨块追加、部分前缀和并发复用，再分别统计有效 KV、物理占用、命中 token 和 TTFT。现有历史描述没有恢复完整映射，我不会仅用“取模切分”声称已证明所有边界正确。

通用管理机制参考 [vLLM v0.26.0 KVCacheManager](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/kv_cache_manager.py)与 [BlockPool](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/block_pool.py)；该参考版本不倒填为历史项目版本。

## 4. 变长输入与 Kernel 分档

### 4.1 现场题意与原答

约 08:05–11:05，面试官问不同 prompt 长度是否需要导出多个模型，并追问长度分档发生在硬件算子还是上层。原答说明上层根据区间选择底层 Attention 实现，不需要为每个长度导出完整模型。

### 4.2 优点、不足与更好结构

方向合理，但应区分请求可变、执行图可变与 Kernel 可支持的形状。还需说明 bucket 边界、Padding、超限路径和首次编译代价，不能由“支持动态输入”推出所有 Kernel 接受任意 Shape。

### 4.3 参考回答

> 请求层可以接受不同有效长度，但执行层不一定每次都使用完全动态的 Kernel。上层可以根据长度、dtype 和模式选择已有实现，或者把输入放入支持的 Shape bucket，再用有效长度和 mask 保持语义。这样通常不需要为每个 prompt 长度导出一份完整模型。
>
> 要检查的是每个 bucket 实际做多少无效计算，边界附近如何选档，以及超出支持范围时采用新特化、重新编译还是明确回退。Prefill 一次处理多 token，Decode 的形状和缓存访问不同，可能使用不同实现；Graph 路径还需要满足地址、metadata 和生命周期约束。
>
> 我会比较冷启动与稳态性能，覆盖档位边界、最大长度及混合请求，并检查补齐位置不会被当成有效 token，也不会污染 KV 或递推状态。选择更大档位可以减少编译种类，但不一定降低总时延，需要把计算浪费与调度开销一起测量。

形状、Padding 与图执行机制可对照 [vLLM CUDA Graphs 设计](https://docs.vllm.ai/en/v0.26.0/design/cuda_graphs/)。目标芯片能否使用相同机制，仍以自身后端实现为准。

## 5. Fused RoPE

### 5.1 现场题意与原答

约 11:10–13:10，面试官问 Fused RoPE 是什么、为什么做。原答指出特殊索引与中间张量引发片外搬运。底稿还扩写到 MatMul／Attention 融合和全程片上完成；技术审计明确这些边界缺少实现证据，本稿不沿用为事实。

### 5.2 优点、不足与更好结构

保留访存动机，补充具体 RoPE 变体、输入输出与融合边界。接口统一、图上融合与单 Kernel 实现不是同一层工作；不能把减少中间写回说成完全没有 HBM 访问。

### 5.3 参考回答

> RoPE 通常按位置对 Q、K 的成对维度做旋转，使注意力计算包含位置信息。融合要先明确当前模型的维度配对、旋转范围和位置索引；多模态的位置规则可能不同，不能只因为都叫 RoPE 就套用同一种索引。
>
> 我关注的优化动机是：如果切片、重排和旋转分别物化中间结果，就会增加 Kernel 下发和片外读写。将有直接数据依赖的步骤按明确接口组合，可以减少其中一部分中间张量与重复搬运。需要从实际实现确认融合了哪些操作，不能自动扩大为连同 QKV 投影或整个 Attention 都融合了。
>
> 我的相关职责在框架调用和接口适配、真实 Shape 整理及验证，底层融合算子由算子团队实现。验收会对照同一模型位置规则下的参考结果，再看 Kernel 与端到端时间；若没有 trace 和代码支持，就不宣称所有中间量都在片上、也不补写独立收益。

RoPE 机制见 [RoFormer 原论文](https://arxiv.org/abs/2104.09864)，项目接口工作见[多模态项目档案](../../自我准备/projects/multimodal-inference-project.md)。原答中未确认的具体融合边界保持未知。

## 6. ERNIE／Qwen 接入与 Mask

### 6.1 现场题意与原答

约 13:15–15:05，面试官问模型适配过程。底稿概述原答提到在缺少现成实现时编写 ERNIE 模型定义，以及按元素 Mask 改为按列 Mask。模型版本和具体 Mask 规则没有完整证据，不能把模型类接入扩张为从零实现整个 ModelRunner。

### 6.2 优点、不足与更好结构

应分别讲配置与权重、前向语义、后端接口和正确性；优化 Mask 时给出可见位置集合，而不是只讲表示变小。只有在对应条件成立时，逐元素表示才能等价压缩或广播。

### 6.3 参考回答

> 我负责过 Qwen2.5-VL、Qwen3-VL 和 ERNIE 4.5-VL 的框架层接入。对于没有现成模型实现的情况，先按参考模型建立配置和权重映射，再组织前向调用，接入 Attention、并行线性层和多模态处理接口。能执行之后，还要对齐预处理、中间结果和完整输出，不能只以权重加载成功判断适配完成。
>
> Mask 的优化必须保持每个 query 可以访问的 key 集合不变。例如原二维 Mask 如果在所有 query 行上都只由列索引决定，可以用一维列条件再广播；如果每一行的合法范围不同，像一般因果关系，就不能直接丢掉行维信息。还要检查布尔 Mask 与加性 Mask 的约定，以及目标接口中布尔值的含义。
>
> 本场提到的具体改写没有恢复出完整张量与公式，因此我会把可确认的模型接入职责和通用等价性判断分别说明，不补造某条 Mask 规则，也不把模型定义等同于独立重写推理引擎。

参考 [vLLM 模型接入文档](https://docs.vllm.ai/en/stable/contributing/model/basic/)与 [PyTorch SDPA 的 Mask 契约](https://docs.pytorch.org/docs/2.15/generated/torch.nn.functional.scaled_dot_product_attention.html)；后者的具体布尔约定不能泛化到所有 API。

## 7. 架构分工与 Conv3D

### 7.1 现场题意与原答

约 15:05–19:10，面试官先问架构分层与个人位置，再追问 Conv3D，确认是否通过前置 Transpose／Reshape 处理。原答抓住小通道补齐导致显存膨胀，但底稿中的对齐值和“合并维度”不足以证明等价。当前答法采用最新 [Conv3D 案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)。

### 7.2 优点、不足与更好结构

把分层职责放入实际数据路径：个人负责调用与布局，算子同事负责专用实现；逻辑 view、真实分配和数值验证分别说明。不能拿局部通道补齐倍率当整模显存倍率，也不能跨模型拼接性能基线。

### 7.3 参考回答

> 我主要在模型与框架层工作，向下与 PyTorch 后端、算子和 Runtime 协作。Conv3D 案例中，首次故障是 Qwen2.5-VL-32B 视频输入 OOM。我提取真实 Shape，沿调用检查发现：原输入已按视觉块展平，view 本身复用存储；后续生成通道末置的新存储时，小通道在很多位置分别补齐，才造成大量物理空间和搬运。
>
> 我保留二维输入 N×K，其中 K 是窗口内 C、T、H、W 的乘积，传递维度元数据，并按相同展平次序处理权重。算子同事修改专用 Conv3D 的读取和计算。二维末维对齐仍在，取消的是通道末置带来的重复补齐；这是一条明确的布局契约，不是任意 reshape 都能替代卷积。
>
> 单算子已有视频 Shape 的 BF16 CPU 参考对照；模型级是 32B 的 10 个图片测例，确定性配置下输出 token 与 CPU Conv3D 路径一致，没有视频模型级精度回归。性能也分组报告：32B 图片组平均 TTFT 从分钟级降到 5 秒以内，原先 OOM 的 32B 视频没有优化前 TTFT。结果属于布局与 Kernel 协作方案，不拆成个人独立收益。

本节使用后续确认的项目口述，不宣称现场已经给出这些测试条件。具体容差、每例一次请求和计时范围见案例卡 F5／F6；不沿用旧档案的 40%。

### 10.3 参考回答

## 11. AWQ 与反量化性能

### 11.1 现场题意与原答

约 23:45–25:30，面试官问 AWQ 怎样做，并追问多了反量化为何还能更快。原答抓住权重读取量下降，但把 AWQ 的算法和 W4A16 格式合在一起；底稿中的 20%–30% 未给出完整测量条件，不能直接采用。

### 11.2 优点、不足与更好结构

先说明激活感知的权重量化，再讲存储、解码与计算路径，最后给性能成立条件。权重裸数据从 16 位到 4 位接近四分之一，不等于物理带宽提高四倍，更不等于整模四倍加速。

### 11.3 参考回答

> AWQ 是训练后的激活感知权重量化方法，通过校准输入观察激活分布，选择有等价补偿的通道缩放，减小重要通道的量化影响，再按目标方案量化权重。常见部署是 INT4 权重、FP16 或 BF16 激活，但 W4A16 只概括位宽，具体还要交代 scale、分组和 Kernel 格式。
>
> 运行时可以边读取压缩权重边解包、反量化，并与矩阵乘配合，不必先把整份权重在 HBM 中展开为高精度副本。如果负载主要受权重读取限制，减少的搬运时间可能超过反量化开销，因此总体更快；如果计算已经很饱和、反量化不高效或负载转向 KV 访问，收益就可能变小甚至变差。
>
> 我会在相同模型、输入输出长度和并发下比较未量化基线与量化路径，检查精度、权重与 KV 占用、Kernel 和端到端时间。我的已确认职责主要在接入、接口和验证，不能把框架适配说成自己主导了 AWQ 算法调优，也不采用没有基线定义的百分比。

算法见 [AWQ 原论文](https://arxiv.org/abs/2306.00978)，即时反量化与格式示例见 [TensorRT-LLM 精度说明](https://nvidia.github.io/TensorRT-LLM/1.0.0/reference/precision.html)。

## 12. Host 聚合与多机通信

### 12.1 现场题意与原答

约 25:35–30:00，面试官追问简历中的异构调度、卡与主机连接及多机拓扑。底稿概述原答将其收窄为多机 TPU 小消息通信问题，使用 Host 聚合与分发；4×8 卡等数字、协议、实际收益和个人实现范围没有独立确认。

### 12.2 优点、不足与更好结构

应具体称为通信路径适配或优化，不用“异构调度”掩盖数据流。Host 路径可能适合某些小消息，但会增加 D2H／H2D、内存与同步成本。仅总显存足够，也不能证明模型在每个 rank 的权重、KV 和工作区都能装下。

### 12.3 参考回答

> 这段讨论的重点是多机推理中的小消息通信路径。专用设备的直连路径不一定在每种消息大小下都最优；一种候选方案是先把需要通信的数据交到 Host，完成节点内或跨节点的聚合，再把结果送回设备。是否值得采用，需要比较完整路径，不能只看 Host 网络这一段更快。
>
> 我会先固定 collective 的数学语义、rank 分组、消息大小与拓扑，再画出数据从设备产生、D2H、Host 聚合、跨机传输、H2D 到消费者的顺序。要检查数据格式、归约结果、缓冲生命周期和同步是否正确，然后比较端到端时间、Host 开销及显存占用；不能假设所有阶段都能自动重叠。
>
> 对个人贡献，应明确实际负责的是问题定位、框架调用、通信接口还是具体算法实现。现有材料没有给出可确认的代码边界和收益，我会保留方案主旨，不声称独立重写通信库，也不把这种路径推广成专用芯片通信的通用最佳方案。

collective 的接口语义可参照 [NCCL 操作说明](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)，仅用作通用对照，不认定历史项目使用 NCCL。已确认的训练通信经历仍采用 [CL09](../../自我准备/Claim-evidence矩阵.md#claim-wording-decisions-20260929)基础后端测试调试口径。

## 13. Attention、卷积与 FFN

### 13.1 现场题意与原答

约 30:05–32:15，面试官问 Attention 中是否包含卷积或 FFN。原答区分 QKV、注意力计算与后面的 FFN，方向正确。底稿将其描述为诱导题，但无法由单模型概述确认对方故意设陷阱，本稿只核对概念。

### 13.2 优点、不足与更好结构

保留清楚的架构边界，同时限定标准 Transformer。线性投影不是完整 FFN，某些混合模型加入卷积也不改变标准结构的定义；回答要允许对方所指的“模块”包含更大范围。

### 13.3 参考回答

> 如果讨论标准 Transformer，Self-Attention 先得到 Q、K、V，计算带缩放和 mask 的 QKᵀ，再经 Softmax 得到权重并对 V 加权，多个头的结果还会经过输出投影。这里存在可学习的线性变换，但它们不是通常所说的那段非线性 FFN 子层。
>
> FFN 是 block 中另一条主要计算路径，在每个 token 的隐藏向量上做升维、非线性和降维；具体模型可以使用门控形式。残差和归一化怎样排列，也要按模型的 pre-norm 或其他结构说明。标准 Self-Attention 本身不要求卷积。
>
> 如果所指的是某个带短卷积或其他 token mixer 的混合模型，则需要按该模型的 block 图重新定义边界。先说明正在讨论的结构，就能避免把“某个实现的 Attention 模块包含额外处理”和“标准注意力公式需要卷积”混在一起。

标准结构依据 [Attention Is All You Need](https://arxiv.org/abs/1706.03762)。本场这题主要是有效回答，补充限定条件即可，不虚构新的失误。

## 扩展问题与参考回答

以下均是补充准备，不计入本场已问问题或原回答缺陷。

### E1. Prefix Cache 命中率提高，TTFT 就一定变好吗？

> 不一定。要区分请求、block 和 token 命中率，并计算省下多少 Prefill；还要考虑哈希查找、元数据、缓存竞争和实际排队。命中很多短前缀可能只节省少量计算，低价值缓存还可能挤占更有用的空间。因此固定工作负载，报告命中长度分布、节省计算和 TTFT，不能只给一个命中百分比。[vLLM Prefix Caching](https://docs.vllm.ai/en/v0.26.0/design/prefix_caching/)

### E2. 大物理块能否同时服务多个细粒度逻辑块？

> 可以作为一种设计，但需要独立定义逻辑子块到物理页及偏移的映射，并处理引用计数、写入隔离、释放和后端索引。只说“大页里再取模”不足以证明正确。还要评估元数据、碎片、共享和 Kernel 访存代价；这是一种通用可能性，不作为历史项目已经采用的实现。

### E3. Fused RoPE 怎样证明保持模型语义？

> 固定 Q/K Shape、位置索引、旋转维度、配对方式与 cos／sin 约定，比较融合前后的结果，并覆盖边界位置、不同有效长度和多模态位置组合。若融合改变读写布局，还要验证缓存中的 K 与后续 Attention 读取一致。局部误差合格之后再跑完整模型；减少算子数并不自动证明结果等价。[RoFormer](https://arxiv.org/abs/2104.09864)

### E4. Mask 从矩阵改成列向量，什么时候不成立？

> 当合法位置还依赖 query 行时，单个列向量通常不够。例如标准因果 Mask 每一行可见的前缀不同，不能直接用一个相同列条件替代；如果另外保留了因果规则，则可以再叠加列级 Padding 条件。应比较组合之后每个 query 的最终合法 key 集合，并核对 API 的布尔和加性 Mask 约定。[PyTorch SDPA](https://docs.pytorch.org/docs/2.15/generated/torch.nn.functional.scaled_dot_product_attention.html)

### E5. Conv3D 局部占用缩小很多，整模显存也会等比例下降吗？

> 不会直接等比例下降。整模还包括权重、KV、其他激活、通信缓冲和临时空间，峰值取决于哪些分配同时存活。先用实际物理分配和生命周期比较，再报告总峰值；不能把小通道补齐比例乘到整模型上。当前案例保留已观察到的 OOM 消失和明确测试组的时延结果，未补造完整显存账本。[Conv3D 案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)

### E6. W4A16 能否决定 KV Cache 与累加精度？

> 不能。它概括权重与激活的位宽，完整方案还要说明数值格式；KV Cache 有自己的配置与后端限制。Kernel 内还要区分解包后的值、反量化、乘法输入、累加和归约，A16 不代表内部所有步骤均为 16 位。采用不同存储与计算格式时，要说明转换位置与数值影响。[TensorRT-LLM 精度说明](https://nvidia.github.io/TensorRT-LLM/1.0.0/reference/precision.html)

### E7. 端侧低时延优化可以直接复用云端方案吗？

> 可复用问题拆分和测量方法，具体方案需要重新看模型、输入到达模式、内存、功耗和资源竞争。大 batch 带来的吞吐收益可能增加等待；Host 聚合也可能不适用于单设备。先定义完整链路的时延范围与尾部目标，再逐层定位，不用设备数量或峰值算力代替系统分析。

### E8. Host 聚合为什么在小消息下可能有利？

> 小消息可能主要受每次提交、同步和协议启动开销限制。若 Host 路径能减少昂贵阶段或更高效地完成分层聚合，收益可能覆盖额外搬运；消息变大或设备直连更成熟时，D2H／H2D 与主机内存开销又可能主导。必须在相同 collective、消息分布和最终完成边界下比较，不能从一个小包结果推导所有消息都更快。

### E9. AIME 准确率一致是否意味着两个后端逐 token 一致？

> 不意味着。准确率只概括题目判分，两种推理过程和输出文本仍可能不同。逐 token、logits、层输出与最终任务指标是不同层级的证据，需要分别验证。后来 GLM 的 AIME26 结果只能按其模型、题集和生成配置报告，不能替代本场的 AIME 2024 结果，也不证明所有任务无差异。[GLM 项目评测边界](../../自我准备/projects/GLM5-3-flash-project.md)

### E10. 不熟悉的岗位技术被追问时怎样回答？

> 先明确已做过的范围，再说明能够解释的机制和仍缺直接经验的部分。例如可以介绍视觉 Encoder 的布局、数值与接口经验，同时承认没有完整 YOLO 视频链路交付。随后确认岗位需要哪类具体任务，用可以验证的接手思路继续交流；不把面试官提示或准备中的方案当成个人已完成成果。
