## 3. 适配自研后端有哪些难点

### 3.1 现场题意与原答

约 04:05–08:00，音频理解稿将现场追问概述为：在适配自研 TPU API 与 vLLM 的过程中，遇到了哪些较难的问题？该问题承接第 2 题的职责范围确认。底稿概述原答选择了硬件强对齐与 Prefix Cache 复用的案例，并提到二次切分或取模；这不是面试官独立提出的细粒度前缀缓存设计题，也没有逐字稿可以确认完整原句。

本人于 2026-11-15 明确放弃该问题的细粒度前缀缓存答法。当前改用已确认的 GLM-5.3-Flash 项目经历；“硬件对齐要求和前缀缓存粒度不一致，怎样处理”另存为[扩展题 E11](#amb-extra-e11)，只作通用设计准备。

### 3.2 优点、不足与更好结构

原答试图用具体案例说明通用框架与目标后端的差异，这个组织方式可以保留；但既然该项目经历已被本人撤回，就不再补写其实现或收益。

本题选择 GLM 混合缓存的两次 OOM。第二题介绍整体职责，并简述状态拆池；本题深入容量规划与实际分配的关系，按“启动故障 → 沿缓存分组和分配定位 → 修正核算与多余补齐 → 验证”展开。难点在于框架的容量核算、Worker 的物理分配和后端的访问约定需要一致，不能只调整一个配置或局部函数。

### 3.3 参考回答

> 我可以用 GLM-5.3-Flash 适配中的混合缓存 OOM 举例。这个模型除了 Attention 的 KV cache，还有线性注意力的卷积状态和递推状态，各类缓存的大小和存储方式不同。适配时，需要让框架规划出的缓存容量，与后端实际申请的内存保持一致。
>
> 当时服务在启动分配状态缓存时出现了 OOM。我沿着缓存规格、分组、每个 block 的字节数、可用 block 数量，一直检查到 Worker 的实际分配。发现移植时沿用了原实现的共享页核算方式，但目标后端的 Worker 会为 34 层线性注意力分别申请状态缓存。这两处假设不一致，导致规划出的 block 数量超过了实际可容纳的数量。
>
> 我在插件里增加了与实际分配方式对应的模型专用分组，把这些状态缓存按层分别核算，并使用真实的状态字节数计算容量。
>
> 修正后，启动仍然出现 OOM。继续检查发现，平台层还保留着为共享页统一大小的补齐逻辑，把每个状态页补到了更大的 Attention 页大小。但这条后端路径已经按层独立分配，状态读写也不使用补齐的尾部，所以这部分空间没有实际用途。我保留了后端要求的 block size 选择，取消了这条独立分配路径中多余的共享页补齐，并同步修改页大小的核算接口。
>
> 验证时，我先用离线测试核对缓存分组、block 数量和逐层分配的总字节数，再检查设备端的分配结果，确认 34 层状态缓存全部分配成功。这部分修改由我在框架和插件侧完成，解决的是容量规划与物理分配之间的不一致；模型整体后来完成了 TP8 文本版本交付。

依据：[GLM 项目档案“修复混合 KV cache 的两次 OOM”](../../自我准备/projects/GLM5-3-flash-project.md#2-修复混合-kv-cache-的两次-oom)。上述经历用于当前面试准备，不倒填为安霸现场已经完成或讲出的内容。共享页核算与按层独立分配的差异限定于该项目当时的实现，不泛化为所有 vLLM 或自研后端。

追问时分别说明：降低显存利用率不能修正核算与分配方式的不一致；取消的补齐是独立分配路径中不再需要的共享页尾部，不能由此推导硬件对齐都可以取消；分组修正、去掉多余补齐和第 2 题的状态拆池分别解决核算、容量和访问开销问题。具体实现分支与同一配置下的分配证据，关联[实机核查清单 C003](实机核查清单.md#c003)。

## 4. 变长输入与 Kernel 分档

### 4.1 现场题意与原答

约 08:05–11:05，面试官问不同 prompt 长度是否需要导出多个模型，并追问长度分档发生在硬件算子还是上层。原答说明上层根据区间选择底层 Attention 实现，不需要为每个长度导出完整模型。

### 4.2 优点、不足与更好结构

原答的主线正确：不需要逐长度导出完整模型，上层根据输入情况选择底层支持的 Attention 实现。口述先回答是否需要导出多个模型、分档由哪一层完成，再补充 Padding 的正确性与分档代价。不能由请求层支持变长，推导同一个 Kernel 支持任意 Shape；Kernel 分档与 Graph 分档也应分别说明。

### 4.3 参考回答

> 在我们当时使用的这条推理路径里，不需要为每一种 prompt 长度重新导出模型。同一份模型和权重可以处理不同长度的输入，底层算子库提供适合不同长度范围的 Attention 实现，上层在调用时选择对应的实现。
>
> 具体来说，长度分档的选择发生在上层的 PyTorch 调用路径中。底层算子决定自己支持哪些形状、需要哪些参数，上层根据实际输入选择能够支持它的实现。所以从模型使用者的角度看，输入长度可以变化，但底层不一定只靠一个完全动态的 Kernel 处理所有情况。
>
> 如果选中的实现要求把输入补齐到某个形状，就需要同时传递真实的有效长度，或者使用对应的 Mask 和元数据，让补齐部分不影响有效 token 的计算。涉及 KV cache 写入时，也要保证补齐位置不会覆盖有效请求的缓存。是否需要实际补齐，要看具体算子接口。
>
> 分档也有代价。档位较粗，可能增加无效计算和数据搬运；档位较细，又会增加需要准备和维护的实现数量。因此我会结合实际输入分布和性能测试选择档位，重点检查档位边界附近的正确性与性能。对于超出已有范围的输入，还要确认是否存在能够支持它的其他执行路径；没有的话，就需要扩展支持范围或明确报出限制。

追问时可以继续区分：

- **Prefill 与 Decode 的分档依据**：Prefill 需要考虑本次处理的 query 长度；普通 Decode 每个请求通常只增加一个 token，但已有 KV 长度仍在增长，不能只按最初的 prompt 长度理解整个执行过程。
- **Kernel 与 Graph 的分档层次**：前者选择算子实现，后者选择可以捕获或重放的执行图。vLLM 的 Graph 分发使用批次形态及补齐后的 token 数等信息，不能直接当作历史项目的 Kernel 分档规则。参考 [vLLM Graph 设计](https://docs.vllm.ai/en/v0.26.0/design/cuda_graphs/)。

具体档位、分发函数、Padding 要求和超限处理尚未从现有材料中恢复，已列入[实机核查清单 C021](实机核查清单.md#c021)。上述性能选择与超限处理是准备回答时的判断方法，不补造当时已经实现的自动回退或重新编译行为。

## 5. Fused RoPE

### 5.1 现场题意与原答

约 11:10–13:10，面试官问 Fused RoPE 是什么、为什么做。原答指出特殊索引与中间张量引发片外搬运。底稿还扩写到 MatMul／Attention 融合和全程片上完成；技术审计明确这些边界缺少实现证据，本稿不沿用为事实。

### 5.2 优点、不足与更好结构

原答提到索引操作和中间张量带来的访存开销，这条主线可以保留。口述按“RoPE 做什么 → 为什么融合 → 减少了哪些开销 → 自己负责什么”展开。具体融合范围以实际实现为准，不从 Fused RoPE 的名称推导它包含 QKV 投影或整个 Attention，也不将减少中间写回表述为完全没有 HBM 访问。

### 5.3 参考回答

> RoPE 是旋转位置编码，通常根据 token 的位置，对 Q、K 中指定的成对维度做旋转，让 Attention 的计算包含位置信息。Fused RoPE 是对这段计算的实现进行融合，在保持原来数学含义的前提下，减少执行开销。
>
> 如果用多个基础操作实现，通常需要先取得当前位置对应的 cos、sin，再按模型的维度配对方式取值，完成乘加计算并组织输出。如果这些步骤在后端分别执行，而且产生了需要实际存储的中间张量，就会增加算子下发，以及中间结果的写回和再次读取。
>
> 融合的思路是，让 Kernel 按正确的索引直接读取需要配对的数据，并完成旋转计算，减少为了中间步骤而单独生成张量的过程。这样主要节省的是算子调用和中间数据搬运的开销，输入读取和最终输出写回仍然存在。具体收益还要通过 Profile 确认，不能只看算子数量减少了多少。
>
> 我参与的主要是框架侧 Fused Rotary Embedding 的调用方式和接口适配，底层融合 Kernel 由算子团队实现。接入时需要特别注意不同模型的位置索引、旋转维度和 Tensor 布局。验收时，我会先对照原实现检查数值结果，再检查实际执行路径、算子耗时和端到端表现。

RoPE 机制见 [RoFormer 原论文](https://arxiv.org/abs/2104.09864)；“取位置对应的 cos、sin，再完成旋转”的通用路径可对照固定源码 `d7ada3aace051fecec553c185225db2259c2ac6a` 的 [vLLM RotaryEmbedding](../../../推理框架/references/vllm/vllm/model_executor/layers/rotary_embedding/base.py)。项目接口工作依据[多模态项目档案](../../自我准备/projects/multimodal-inference-project.md)，不把通用实现当作历史项目的融合边界。

两处表达需要收紧：

- 切片、reshape 不一定产生数据搬运。应当说“当后端实际物化中间结果时会增加开销”，再用调用链和 Profile 证明。PyTorch 的基础索引通常返回 view，reshape 则可能返回 view 或产生复制，见 [Tensor Views 文档](https://docs.pytorch.org/docs/2.15/tensor_view.html)。
- Fused RoPE 的名称不能证明融合了整个 Attention。目前材料不足以确认是否包含 QKV 投影、Attention 或 KV 写入，也不能声称所有计算全程留在片上。具体模型、融合范围、个人改动与回归结果继续按[实机核查清单 C012](实机核查清单.md#c012)核对。

### 6.3 参考回答

> 我以 GLM-5.3-Flash 的适配为例。当时的目标是在 8 卡自研 AI 加速芯片上，基于团队已有的 vLLM 硬件插件，完成 TP8 文本推理的接入和交付。我负责模型、权重、缓存和执行路径的适配，融合 Kernel 由算子团队实现。
>
> 开始时，我先明确这次发布的范围，包括 AWQ 权重、BF16 激活和文本推理，再检查模型结构与参考实现。这个模型包含线性注意力、稀疏 MLA、MoE 等结构，原来的部分执行路径依赖 Triton、TileLang 和 `torch.compile`，在目标平台上不能直接使用。因此需要先梳理各模块的输入输出、计算规则和状态，再通过 CPU FP32 参考与 native 实现检查局部计算的语义。
>
> 接下来是模型注册、权重加载和前向路径接入。权重这部分要处理模型命名空间、打包映射和量化布局，确认每个权重加载到了正确的位置。我还编写了权重索引审计脚本，检查是否存在漏加载、意外权重或重复映射，并明确跳过本次不启用的 MTP 权重。
>
> 与模型计算一起接入的还有缓存。这个模型既有 Attention 缓存，也有线性注意力的卷积状态和递推状态。我需要把缓存规格、分组、容量核算、实际分配，以及执行时的状态访问和迁移衔接起来。前面提到的混合缓存 OOM 和状态拆池，就是在这个过程中解决的问题。
>
> 在语义和接口逐步确认后，再接入芯片上的融合算子。我会把实际形状、dtype、布局和计算要求整理给算子团队，拿到实现后先做数值对照，再接入模型。这里还要确认测试确实执行了融合路径。我曾经遇到过 native 和 fused 两侧都回退、数值比较仍然通过的情况，后来增加了调用计数断言，避免测试没有覆盖到目标实现。
>
> 随后结合 Profile 继续优化整条执行路径，包括减少非连续状态搬运、合并 metadata 拷贝、减少阻塞读回，以及完成 Decode Graph 的适配。每次修改都需要同时检查结果和实际执行行为，尤其是缓存状态、Padding 和异步访问这些容易影响正确性的地方。
>
> 最后按层次完成验证：算子数值对照、请求与并发功能、Graph 和 eager 对照，以及端到端任务评测。发布前再清理诊断路径、完成定向回归，整理版本和部署文档，交给云服务团队正式上线。这次最终交付的是 TP8 文本版本，Decode 使用 Graph，Prefill 和 chunked prefill 保留 eager。

依据：[GLM-5.3-Flash 项目档案](../../自我准备/projects/GLM5-3-flash-project.md)。这版采用后补项目经历准备当前口述，不倒填为安霸现场已经完成或讲出的内容。各层验证分别采用档案记录的范围，不由任务准确率一致推导所有输入逐 token／logits 一致；本人负责适配与发布验证，正式生产部署由云服务团队完成。

### 7.3 架构分工的口述回答

> 从一次推理的执行过程看，上层应用把请求交给推理框架，框架负责调度和组织模型执行，再通过 PyTorch 设备后端和自研算子完成计算。更底层的设备内存、执行提交和硬件交互，由 Runtime、驱动等组件负责。
>
> 我主要负责模型和推理框架层的适配，包括模型接入、调用与数据布局调整、精度和性能问题定位，也会处理与 PyTorch 后端之间的接口问题。底层 Kernel、Runtime、驱动和编译器有对应团队负责。遇到跨层问题时，我会提取复现案例，与相关同事确定接口和修改方案，再完成框架侧接入与验证。

### 7.4 Conv3D 的口述回答

> 一个典型例子是 Qwen2.5-VL-32B 在处理视频时出现 OOM，调用栈指向视觉编码器里的 Conv3D。我提取了实际输入形状，构造独立单例，并把重排操作从 Conv3D 内部移到调用前，通过显存快照观察到重排后显存明显增长。
>
> 这个 Conv3D 用来完成视觉块的 patch embedding。原始输入已经按视觉块展平成二维，每一行包含三个通道、两个时间位置，以及十四乘十四的空间元素，共一千一百七十六个元素。原来的路径先用 view 将它解释成五维，再生成通道末置的新存储。
>
> view 本身没有复制那块大数据。问题出在后面的重排与补齐：目标后端对物理最内层有对齐要求，而通道只有三个，导致每个时间、空间位置上的小通道段都要分别补齐，产生大量额外存储和搬运。
>
> 我的修改是保留原来的二维输入，并在模型初始化时，把卷积权重按相同顺序展平，再将原来的维度信息传给专用 Conv3D。算子同事配合修改 Kernel 的读取和计算。这样仍然保留二维末维的补齐，但避免了对大量只有三个元素的小段重复补齐。输入和权重采用相同的展平顺序，保证元素之间的对应关系不变。
>
> 我负责问题复现、布局分析、模型调用和权重布局调整，算子同事负责 Kernel 内部实现。验证时，先用同一份 BF16 输入和权重对照 CPU Conv3D，再进行模型回归。Qwen2.5-VL-32B 的十个图片测例中，两条路径生成的 token 序列一致；单并发下，这组图片请求的平均首 token 延迟从分钟级降到了五秒以内，这是布局和专用算子共同修改后的结果。
>
> 视频方面，完成了视频形状的算子单测，但没有覆盖完整的视频模型精度回归。最初出现 OOM 的 32B 视频输入，也没有可比较的优化前 TTFT。

### 7.5 现场追问：是在 Conv3D 前加了 Transpose／Reshape 吗？

> 原始输入本来就是二维展平的。我保留了这个表示，去掉后续生成通道末置存储的路径，同时调整了权重布局和专用算子接口。这需要模型侧与算子侧共同修改，不能只概括成在 Conv3D 前加一次 reshape。

本节使用后续确认的项目口述，不宣称现场已经给出这些测试条件。依据[Conv3D 案例卡 F1–F6](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)：单算子对照在容差内通过；图片回归每例一次请求，使用 `temperature=0`、随机种子 `1234`；TTFT 为客户端发送请求到收到首个生成 token 的时间，模型加载和预热不计入。布局与 Kernel 为联合优化，不拆分个人独立收益，不沿用旧档案的 40%。

具体接口、展平映射和适用条件按[实机核查清单 C011](实机核查清单.md#c011)核对，显存快照与实验配置沿用 C009、C010。当前方案不泛化为任意 Conv3D，也不推断专用算子的内部 SRAM 布局。

## 10. AIME 与算力口径

### 10.1 现场题意与原答

约 21:40–23:45，问题包括 AIME 2024 是什么，以及芯片算力多少、如何与 A100 比较。原答对数学推理基准的方向正确；底稿中的自研峰值、比例和单位未独立核实，审计也指出其口头比例与所列数值不完全一致。

本人于 2026-11-15 确认 200–210 TFLOPS 无误，并同意按此前讨论的单卡 BF16 稠密理论峰值口径更新当前回答。以 A100 同口径的 312 TFLOPS 比较，约为 64%–67%，口述统一为“约三分之二”；历史底稿中的“约 60%”保留为原答，不继续用于当前口述。

### 10.2 优点、不足与更好结构

两项独立问题分别回答。介绍 AIME 时先说来源与用途，再按追问展开题集、生成与判分条件；介绍算力时直接给出单卡、数据类型、稠密／稀疏和理论峰值，再作同条件比较。题目准确率不能代替算子数值对照，峰值比例也不能直接代表某个模型负载的速度比例。

### 10.3 AIME 的口述回答

> AIME 是美国数学邀请赛。大模型评测会使用对应年份的竞赛题，考察模型解决数学问题的能力。AIME 2024 就是使用 2024 年的题目，题目有确定的整数答案，可以据此统计答对的比例。
>
> 在模型适配中，它可以作为任务级精度验证的一项指标，例如比较同一模型在自研后端和参考平台上的答题表现。比较时需要保持题集、每题生成次数、采样参数、输出长度限制和判分方式一致。不过，题目准确率相同，并不代表两个后端的每个 token 或中间计算结果都相同，算子级数值验证仍然需要单独进行。

AIME 的名称及整数答案形式见 [MAA 官方介绍](https://maa.org/maa-invitational-competitions/)。具体历史 AIME 2024 的评测配置继续按[核查项 C022](实机核查清单.md#c022)恢复，后来的 GLM AIME26 结果不用于证明本场所谈 AIME 2024 的成绩。

### 10.4 算力的口述回答

> 我们当时的模型计算主要使用 BF16。单卡 BF16 稠密矩阵计算的理论峰值大约是 200–210 TFLOPS。对比 A100 同口径的 BF16 Tensor Core 稠密峰值 312 TFLOPS，大约是它的三分之二。
>
> A100 还有一个 624 TFLOPS 的数字，那是带结构化稀疏条件的有效峰值，不能和这里的稠密峰值直接相比。
>
> 理论峰值只能说明硬件在相应条件下的计算能力。实际模型性能还受算子形状、内存带宽、数据搬运和通信等因素影响，所以我还会比较相同模型、输入输出长度和并发下的首 token 延迟、输出 token 间隔及吞吐。

自研数值依据本人于 2026-11-15 的确认；A100 的数值及稀疏条件见 [NVIDIA 官方架构说明](https://developer.nvidia.com/blog/nvidia-ampere-architecture-in-depth/)。`200÷312≈64.1%`，`210÷312≈67.3%`，仅用于理论峰值的同口径比较。BF16 浮点吞吐通常用 TFLOPS；如果对方问 TOPS，需要确认对应的数据类型与计算条件，不能直接拿 INT8 TOPS 与 BF16 TFLOPS 比数字。确认记录与规格来源的后续定位见[核查项 C023](实机核查清单.md#c023)。

## 11. AWQ 与反量化性能

### 11.1 现场题意与原答

约 23:45–25:30，面试官问 AWQ 怎样做，并追问多了反量化为何还能更快。原答抓住权重读取量下降，但把 AWQ 的算法和 W4A16 格式合在一起；底稿中的 20%–30% 未给出完整测量条件，不能直接采用。

### 11.2 优点、不足与更好结构

原回答的性能解释方向正确。口述先区分 AWQ 的量化方法和 W4A16 的执行方式，再说明为什么反量化不一定让推理变慢：权重读取需要是主要瓶颈，解包与反量化的实现也需要足够高效。对被量化的权重，16 位降到 4 位意味着裸数据量变成四分之一，不意味着硬件带宽提高四倍或整模自动加速四倍。

### 11.3 AWQ 怎样做

> AWQ 是一种训练后的权重量化方法。它会用少量校准数据观察激活分布，判断哪些权重通道的量化误差更容易影响输出，再搜索合适的通道缩放。缩放时做对应的等价补偿，使原来的浮点计算保持等价，然后再量化权重，尽量降低量化后的输出误差。
>
> 常见的部署形式是 W4A16，也就是权重用 4 位整数存储，激活保持 FP16 或 BF16。权重还需要配套保存 scale、零点等量化参数。AWQ 描述的是怎样得到这些量化权重，W4A16 描述的是权重和激活采用什么位宽。

激活统计与通道缩放机制见 [AWQ 官方说明](https://hanlab.mit.edu/projects/awq)。

### 11.4 多了反量化，为什么还能更快

> 因为增加计算步骤，不一定意味着总耗时增加。如果原来的执行主要受权重读取限制，例如一些小 batch 的 Decode 场景，那么减少从显存读取的权重数据，就可能节省很多时间。
>
> 对被量化的权重来说，从 16 位降到 4 位，裸数据量变成原来的四分之一，实际还要加上量化参数等开销。计算时虽然需要解包和反量化，但只要这些额外开销小于节省的访存时间，总体就能更快。
>
> 实现方式也很重要。高效的路径可以把反量化和矩阵计算融合：读取一块压缩权重，在 Kernel 内还原成计算所需的格式，随后直接参与计算，避免先把完整的高精度权重写回显存、再重新读取。
>
> 这个收益有条件。如果负载主要受计算限制，或者时间更多花在 KV cache、通信等部分，权重量化带来的加速就可能有限。最终需要固定模型、输入输出长度和并发，分别比较精度、Prefill 和 Decode 性能。

即时反量化与矩阵计算融合的实现见 [AWQ 论文的 TinyChat 部分](https://arxiv.org/html/2306.00978v6#S4.SS2)，这是通用机制的参考，不直接证明自研后端采用了相同执行路径。

### 11.5 进一步追问：你实际负责了什么？

> 我的工作主要是量化模型的框架接入。例如 GLM 项目使用 AWQ 4-bit 权重和 BF16 激活，我处理了权重映射、打包和 `qzeros` 布局等适配问题，并参与接口与结果验证。量化算法本身的设计、校准搜索，以及底层量化 Kernel 的实现，需要和我的接入职责分开说明。

个人范围依据[GLM 项目档案](../../自我准备/projects/GLM5-3-flash-project.md)。原稿中的“带宽提升近四倍”改为“被量化权重的裸数据量降到四分之一”；硬件带宽没有因此改变，整模加速也不会自动达到四倍。旧稿的 20%–30% 尚缺完整基线，暂不用于当前口述；实际反量化路径与性能条件按[核查项 C024](实机核查清单.md#c024)核对。

## 12. 框架中的通信排查与优化

### 12.1 准备的问题

按本人 2026-11-15 的要求，本节改为两个通用问题，不作为本场现场问答的逐句恢复：

1. 在框架中，一般如何定位排查通信相关问题？
2. 框架侧一般有哪些手段可以优化通信？

### 12.2 怎样组织回答

排查先区分卡死／超时、结果错误和性能慢，再沿“各 rank 的调用 → 数据与执行依赖 → 通信后端 → 设备及网络路径”缩小范围。性能分析要区分提交、等待其他 rank、实际传输和后续同步，不能把 Profile 中一段较长的通信事件全部归因于链路带宽。

优化围绕通信次数、传输量、可重叠的时间、数据路径和 rank 间的负载分布展开。下面是通用分析与设计方法，不能全部写成个人已完成的项目；实际经历可用第 12.6 节的单流配置案例支撑，DDP 的分桶设计另见[第 12.7 节](#amb-q12-ddp)。

### 12.3 通信问题怎样排查

> 我会先区分问题是卡死或超时、结果错误，还是性能慢，并固定模型、并行配置、进程分组、消息大小和软件版本，保留能够复现问题的最小输入。
>
> 如果是卡死，我会先收集所有 rank 的日志和调用栈，找到最早出现异常或没有继续推进的 rank。然后按同一个 step 和通信序号，核对通信组、参与 rank、collective 类型和调用顺序，再按这个操作的接口要求检查 dtype、元素数和分片大小是否匹配。某个 rank 提前报错退出，其他 rank 也可能表现成通信超时，所以不能只看最后报错的进程。
>
> 如果是结果错误，我会比较通信前后的数据，把问题缩小到具体一次 collective，并用小规模输入核对预期结果。还要检查逻辑形状与物理 Padding、数据类型和切分方式，以及生产数据、执行通信、消费结果之间的依赖。接口返回不一定代表设备已经完成通信，输入或输出缓冲也不能在异步访问结束前被覆盖或回收。
>
> 如果主要是性能慢，我会对齐同一轮各 rank 的 CPU 和设备时间线，检查通信何时提交、数据何时就绪、哪些 rank 到得晚，以及通信结果何时被后续计算使用。通信事件很长，可能是传输本身慢，也可能是在等某个 rank 完成前面的计算或输入准备。
>
> 最后把同样的通信类型、消息大小和拓扑抽成独立用例，对比模型内和模型外的行为。如果独立用例也慢，再检查后端配置、设备与网卡的连接、跨机链路和带宽基线；如果独立用例正常，就继续检查框架中的调用频率、布局转换、同步和负载不均衡。

调用一致性和异步完成规则参考 [PyTorch 分布式文档](https://docs.pytorch.org/docs/2.15/distributed.html#synchronous-and-asynchronous-collective-operations)；设备、拓扑、网络和后端基线的分层排查参考 [NCCL 故障排查](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting.html)。浮点归约对照应使用符合数据类型和运算顺序的误差标准，不要求任意归约顺序逐位相等。

### 12.4 框架侧怎样优化通信

> 我会根据排查结果选择优化方向。小消息很多、每次提交开销较大时，可以合并通信或调整 bucket，让多个合适的小 Tensor 一起传输。但 bucket 过大又会推迟发送，影响与计算的重叠，因此要根据数据就绪时间和实际负载调整。
>
> 如果主要问题是传输量，我会先检查有没有重复通信，以及后续计算是否真的需要完整结果。例如后续只需要各自的分片时，可以评估保留分片并使用 ReduceScatter，避免不必要的完整结果聚合；如果后面仍需要完整数据，就要把必要的 AllGather 成本一起算进去。调整并行策略或通信精度时，也必须保持计算语义并验证结果。
>
> 对能够与计算重叠的通信，可以在数据准备好后尽早提交，让不依赖通信结果的计算继续推进，到真正消费结果时再建立等待。这里需要保证各 rank 的调用顺序、设备流依赖和缓冲生命周期正确，并用时间线确认是否真的发生了重叠；异步接口或多开通信流本身不能保证更快。
>
> 数据路径和进程放置也很重要。我会减少非必要的布局转换、临时拷贝和 Host 中转，复用合适的通信缓冲，并让通信频繁的 rank 尽量使用较快的互联。若主要时间花在等待较慢的 rank，就要继续优化对应的计算、输入准备或任务分配，单独调整通信算法可能作用不大。
>
> 每次优化都要回到同一个模型负载验证结果和端到端时间。训练看 step time，推理看首 token 延迟、输出 token 间隔与吞吐，同时检查额外内存占用，不能只用某个通信接口返回得更快来判断优化成功。

梯度分桶、按数据就绪触发通信以及重叠的实例见 [PyTorch DDP 设计](https://docs.pytorch.org/docs/2.15/notes/ddp.html#internal-design)。算子、消息规模与传输路径的调优需结合实际后端，参考 [NCCL 性能排查](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/performance_and_tuning.html)，不预设某个算法或更多通信流对所有负载都更优。

### 12.7 扩展：PyTorch DDP 怎样通过分桶重叠计算与通信？

以下是通用设计示例，不作为本场已问问题或本人独立实现 DDP 的经历。以普通稠密 DDP、两个 rank 各使用一张 GPU、默认梯度归约和每轮一次优化器更新为例；不展开自定义通信 hook、join 或手动结束反向等特殊模式。

#### 一个三层网络的例子

每个 rank 保存完整模型副本，由调用方为它提供不同的小批量数据。默认初始化同步使副本从相同参数开始；DDP 不负责自动切分输入，数据划分通常由采样器等调用方逻辑完成。各 rank 在本地计算梯度，默认归约得到跨 rank 平均的梯度，再由各自的优化器更新参数。

假设前向顺序为 `L1 → L2 → L3`，反向中梯度大致按 `L3 → L2 → L1` 就绪。为便于说明，假设当前迭代使用两个 bucket：`B0` 包含 L3 的参数梯度，`B1` 包含 L2、L1 的参数梯度。这里的按层划分只是示例；真实分桶要考虑参数大小、设备、dtype 和就绪顺序，不能理解成 DDP 固定一层一个桶。

| 当前阶段 | 梯度与 Reducer 的动作 | 通信和计算的关系 |
| --- | --- | --- |
| 各 rank 执行前向并开始反向 | 本地计算梯度；参数梯度就绪时，Autograd hook 通知 Reducer | 不必等所有层的梯度都产生后才开始同步 |
| L3 的梯度全部就绪 | B0 在本地就绪，且轮到它的编号；通过 ProcessGroup 异步发起 B0 的 AllReduce | 另一 rank 也需发起对应操作，通信才能完成 |
| 继续计算 L2、L1 的梯度 | B0 的归约可以推进，B1 的梯度继续产生 | L2、L1 的反向计算不依赖跨 rank 归约后的 L3 参数梯度，因此存在重叠机会 |
| B1 的梯度全部就绪 | 按桶顺序发起 B1 的 AllReduce | 这一轮后续反向计算较少，末尾通信更容易留在等待路径上 |
| 反向收尾、准备更新参数 | 完成归约结果处理与必要等待，让优化器在消费梯度的执行流上安全使用结果 | 本例随后才执行 `optimizer.step()`，不在 B0 通信完成时提前更新 L3 |

这里，Autograd hook 报告本地梯度就绪，Reducer 管理桶与提交顺序，ProcessGroup 把通信交给 NCCL 等后端。计算和通信能否真正重叠，还取决于设备执行能力、资源竞争和其他 rank 的就绪时间；异步发起不保证已经完成或一定加速。

#### 为什么所有 rank 必须保持同一通信顺序

假设某个 rank 的 B1 意外先就绪，它也不能绕过 B0 先发 B1。两个 rank 都需要按一致的桶顺序调用：

```text
rank 0：AllReduce(B0) → AllReduce(B1)
rank 1：AllReduce(B0) → AllReduce(B1)
```

各 rank 的墙钟时间可以不同，操作的对应关系不能不同。否则可能把不对应的梯度放入同一次归约，或因参数不匹配而报错、卡死。固定源码的 `Reducer::mark_bucket_ready()` 使用 `next_bucket_` 控制顺序；后面的桶先就绪时，先保留就绪状态，等前面的桶就绪后再依次提交。这里等待的是前序桶达到可提交条件，不要求前序 AllReduce 已经在设备上完成后才提交下一桶。

#### 分桶解决什么，怎样调整

| 分桶方式或参数 | 可以减少什么开销 | 需要检查的代价或条件 |
| --- | --- | --- |
| 每个小梯度单独通信 | 较早发起部分通信 | 小消息多，调用与协议启动开销可能很高 |
| 所有梯度合成一个大桶 | 通信调用次数少 | 要等最后一部分梯度就绪，通常减少了与反向计算重叠的机会 |
| 用 `bucket_cap_mb` 调整桶大小 | 在小消息开销与就绪时间之间选择折中 | 观察第一个桶何时发起、末尾还要等待多久，以及各 rank 是否同时具备可提交的数据 |
| `gradient_as_bucket_view=True` | 在梯度与桶共享存储的条件下减少额外存储和拷贝 | 不直接减少网络上传输的梯度字节；梯度清理方式、视图约束与目标版本会影响收益 |
| 梯度累积配合 `no_sync()` | 跳过若干微批次的梯度同步，在同步轮次集中处理累积梯度 | 前向和反向都要放进该上下文，各 rank 的同步节奏保持一致，并正确处理 loss 缩放与优化器更新；不代表取消程序中的所有通信 |

普通分桶主要减少通信调用开销，并把一部分通信时间与反向计算重叠，本身不会把需要同步的梯度数据量降成原来的几分之一。`no_sync()` 是在既定梯度累积方案中减少同步轮次，应保持比较双方的有效批量和更新语义一致。

#### 可以怎样口述

> PyTorch DDP 是框架侧优化通信的一个例子。每个 rank 保存完整模型，在不同的数据上计算本地梯度，再同步梯度。DDP 用 Reducer 把多个参数梯度组成 bucket，并通过 Autograd hook 知道哪些梯度已经准备好。
>
> 比如一个三层网络，反向先产生最后一层的梯度。如果这部分已经组成一个就绪的桶，就可以按顺序发起 AllReduce，同时继续计算前面两层的梯度。这样有机会把通信和反向计算重叠；如果把所有梯度都放进一个大桶，就要等到较晚才能开始通信。
>
> 但也不能把桶切得无限小，因为小通信太多会增加启动开销。桶大小需要结合梯度就绪顺序和实际时间线调整。还有一个正确性条件：所有 rank 必须按相同的桶顺序发起归约，不能哪个桶在本地先准备好就先发哪个。
>
> 排查 DDP 通信性能时，我会看第一个桶发起得是否太晚、有没有 rank 一直晚到，以及反向末尾还剩多少通信等待，再决定调整桶大小、减少额外拷贝，还是处理负载不均衡。优化器更新前仍要保证同步后的梯度可以安全使用。

机制依据：[PyTorch DDP 设计](https://docs.pytorch.org/docs/2.15/notes/ddp.html#internal-design)及[DDP API](https://docs.pytorch.org/docs/2.15/generated/torch.nn.parallel.DistributedDataParallel.html)。设计笔记保留了早期实现的说明，本节的顺序与结束处理同时核对本地固定源码 `0bd89deb431509d893177a84cfa4768aa0399809` 的 [Reducer](../../../PyTorch/references/pytorch/torch/csrc/distributed/c10d/reducer.cpp)（`mark_bucket_ready`、`finalize_backward`），`no_sync()` 的范围核对 [DDP Python 实现](../../../PyTorch/references/pytorch/torch/nn/parallel/distributed.py)。分桶策略和新参数会随版本演进，示例不声称还原了任意模型的实际桶划分。

## 13. Attention、卷积与 FFN

### 13.1 现场题意与原答

约 30:05–32:15，面试官问 Attention 中是否包含卷积或 FFN。原答区分 QKV、注意力计算与后面的 FFN，方向正确。底稿将其描述为诱导题，但无法由单模型概述确认对方故意设陷阱，本稿只核对概念。

### 13.2 优点、不足与更好结构

原来的判断正确。口述先限定“标准 Transformer 的多头注意力子层”，再说明它与整个 block 的区别。区分 QKV／输出投影和独立 FFN 子层；对具体视觉或混合模型，按实际前向过程确认模块范围，不把某一种实现推广到所有 Attention。

### 13.3 参考回答

> 如果指的是标准 Transformer 的多头注意力子层，它不包含通常所说的那段 FFN，标准注意力计算本身也不要求卷积。如果指整个 Transformer block，通常会同时包含 Attention 和 FFN 这两个子层。
>
> Attention 先通过线性投影得到 Q、K、V，再计算 Q 和 K 的相关性，经过缩放、Mask 和 Softmax 后，对 V 做加权汇聚，最后经过输出投影。它主要负责让每个 token 从可见位置中获取信息。
>
> FFN 则在每个 token 的位置上，分别对特征做非线性变换，不在这一子层里直接混合不同 token。经典结构是两层线性变换，中间加激活函数；也可以采用 SwiGLU 这样的门控形式。QKV 投影虽然也是线性层，但属于 Attention 的组成部分，不等于这个独立的 FFN 子层。
>
> 如果讨论的是某个具体的视觉模型或混合架构，其中可能加入卷积，代码里的 Attention 模块也可能封装额外处理。这时需要沿实际前向过程确认范围，不能把某个模型的实现直接推广到所有 Attention。

标准子层划分见 [Transformer 原论文](https://arxiv.org/html/1706.03762v7)，门控 FFN 见 [GLU Variants Improve Transformer](https://arxiv.org/abs/2002.05202)。本场原答有效，当前主要补充限定条件，不虚构新的失误。

### 13.4 扩展追问：FFN 不是也可以用卷积实现吗？

以下是补充准备，不作为本场已问的独立问题。

> 可以。在布局和参数对应的条件下，逐位置的线性变换可以用 kernel size 为 1 的卷积表达，原始 Transformer 论文也这样描述过 FFN。这里卷积核只覆盖一个位置，完成的是通道之间的变换，并没有因此增加相邻 token 之间的信息交互。所以要区分子层的功能和它采用的具体实现形式。

依据：[原论文 §3.3](https://arxiv.org/html/1706.03762v7#S3.SS3)。这种实现等价不意味着标准 Attention 必须包含空间或时间上的局部卷积。

## 扩展问题与参考回答

以下 11 项均按可直接口述的方式准备，不计入本场已问问题或原回答缺陷。通用机制和设计回答不作为个人已完成经历；项目例子沿用正文已确认的职责与验证范围，说明性数字不作为项目参数。

<a id="amb-extra-e1"></a>

### E1. Prefix Cache 命中率提高，TTFT 就一定变好吗？

> 不一定。我会先确认命中率按什么统计，是请求数、block 数，还是 token 数。如果一个指标把“请求中有少量前缀命中”也算作一次命中，那么命中很多短前缀，与复用一大段长前缀，省下的 Prefill 计算可能差很多。
>
> TTFT 还包括排队、输入处理和剩余的 Prefill 等时间，缓存查找与管理也有开销。如果主要时间花在排队上，或者虽然命中了更多请求，但每次只省下一点计算，首 token 延迟就未必明显改善。
>
> 我会在相同的请求、到达模式和并发配置下，对比开启和关闭缓存的结果，并分开报告冷缓存和预热后的情况。除了命中率，还会看复用了多少 token、剩余 Prefill 耗时、排队时间，以及 TTFT 的中位数和尾部延迟，确认缓存到底改善了哪一段。

Prefix Cache 主要避免重复前缀的 Prefill 计算，参考 [vLLM 功能说明](https://docs.vllm.ai/en/v0.26.0/features/automatic_prefix_caching/)及[缓存设计](https://docs.vllm.ai/en/v0.26.0/design/prefix_caching/)。本题解释指标关系，不引用个人细粒度前缀缓存项目或未经确认的收益。

<a id="amb-extra-e2"></a>

### E2. 大物理块能否同时服务多个细粒度逻辑块？

> 可以评估这种设计，但框架和 Attention 后端需要一起支持。举一个容量上的例子：假设一块物理空间能容纳 256 个 token 的 KV，逻辑上希望按 32 个 token 管理，就可以考虑在里面安排八个逻辑子块。每个子块都要能映射到物理块编号和块内偏移。
>
> 这个映射还要传递到真正读写 KV 的算子。后端需要知道有效长度、读取范围和写入位置；如果它仍然只接受原来的整块接口，上层只改编号或增加一次取模，并不能让细粒度复用自动成立。
>
> 生命周期也要按这个设计重新核对。逻辑子块仍被请求使用时，对应的物理空间就必须保留；只有其中所有子块都允许释放，而且相关异步访问已经结束，整个物理块才能回收，相关缓存索引也要同步清理。共享的内容还要避免被另一个请求追加的数据覆盖，必要时分离可写空间或复制已匹配的部分。
>
> 最后再检查子块的实际字节偏移是否满足对齐要求，以及新增索引、引用管理和碎片带来多少成本。只有管理粒度变细后省下的容量或计算，超过这些额外开销，才值得采用。

256／32 仅用于说明逻辑容量划分，真实字节布局还取决于 dtype、KV 形状和后端对齐。该回答是通用设计，不代表本人完成过这项项目，也不宣称 vLLM 的任意版本默认支持；遇到硬件约束时的选择顺序见 [E11](#amb-extra-e11)。

<a id="amb-extra-e3"></a>

### E3. Fused RoPE 怎样证明保持模型语义？

> 我会先把原来的 RoPE 规则明确下来，包括 Q、K 的形状、哪些维度参与旋转、通道怎样配对，以及位置索引怎样取得对应的 cos、sin。多模态模型还要检查不同位置轴的处理，不能只因为接口都叫 RoPE，就认为它们的规则相同。
>
> 然后用同一份输入和位置参数，分别执行参考实现与融合实现，检查旋转后的 Q、K。测试要覆盖不同有效长度、边界位置和实际使用的位置组合；如果接口支持非连续输入，也要覆盖对应布局。浮点运算顺序可能变化，所以误差标准要与 dtype 和计算方式相符，不能一概要求逐位相等。
>
> 如果融合还包含 KV 写入，就要继续检查缓存里的 K 是否写到了正确位置，以及后续 Attention 是否按同一布局读取。我也会确认测试实际进入了融合路径，再回到完整模型做回归。数值和路径确认后，才比较 Kernel 与端到端性能。

数学规则参考 [RoFormer](https://arxiv.org/abs/2104.09864)；具体项目的融合范围、本人改动与验证记录仍按[第 5 题](#q5)和[核查项 C012](实机核查清单.md#c012)核对，不补写已经完成过的测试覆盖。

<a id="amb-extra-e4"></a>

### E4. Mask 从矩阵改成列向量，什么时候不成立？

> 要看这个 Mask 的限制是否只取决于 key 的列位置。如果所有 query 都需要屏蔽同样的列，比如同一条序列里哪些 key 是 Padding，那么这部分信息可以用一个长度等于 key 数量的一维 Mask 表示，再沿 query 维广播。
>
> 如果可见范围还取决于 query 所在的行，就不能直接这样替换。比如因果 Attention 中，第一个 token 只能看第一个位置，第二个 token 可以看前两个位置。一个对所有行都相同的按列条件，无法同时表示这两种限制。
>
> 如果后端另外处理因果约束，而显式 Mask 只负责屏蔽 Padding 列，那么仍然可以用较小的表示，但必须保证组合之后每一行的可见位置没有变化。若浮点 Mask 还带有不同位置的加性偏置，也要保留这些数值，不能只比较哪些位置被屏蔽。最后还要核对接口的广播规则、布尔值含义，以及是否允许同时设置这几类约束。

接口例子见 [PyTorch SDPA](https://docs.pytorch.org/docs/2.15/generated/torch.nn.functional.scaled_dot_product_attention.html)：其布尔 Mask 的 `True` 表示参与 Attention，与 `MultiheadAttention.key_padding_mask` 的含义相反；该版本文档也限制同时设置 `attn_mask` 与 `is_causal`。语义上可以组合约束，不代表任意 API 都允许同时传入相应参数。本题是通用判断，不恢复旧 ERNIE 案例中尚未确认的 Mask 规则。

<a id="amb-extra-e5"></a>

### E5. Conv3D 局部占用缩小很多，整模显存也会等比例下降吗？

> 不会直接等比例下降。Conv3D 的输入重排或临时缓冲只是整模显存的一部分，模型还有权重、KV cache、其他激活、通信缓冲和算子工作区。局部存储缩小多少，不能直接乘到整个模型上。
>
> 还要看这些分配什么时候同时存在。一个临时缓冲虽然只存活很短时间，但如果恰好在其他大块内存都还没释放时申请，就可能触发 OOM。减少它可能解决 OOM，却不一定让模型稳态占用出现同样幅度的下降。
>
> 我会固定模型、输入形状、dtype 和并发，在对应阶段检查实际物理分配与显存峰值，区分局部缓冲减少了多少、整模峰值减少了多少，以及性能有什么变化。逻辑 Tensor 的元素数、局部对齐倍率和分配器实测值，也要分别说明。

个人案例沿用[第 7 题](#q7)及[Conv3D 案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)：已有 OOM 现象和明确测试组的 TTFT 结果，不据此补造整模显存下降比例。完整峰值记录与测试配置沿用[核查项 C009、C010](实机核查清单.md#qwen25-vl)。

<a id="amb-extra-e6"></a>

### E6. W4A16 能否决定 KV Cache 与累加精度？

> 不能。W4A16 只概括权重和激活的位宽，连激活具体是 FP16 还是 BF16，都需要另外说明。KV cache 是另一类存储，有独立的配置和后端支持范围，不会因为权重是 4 位，就自动变成 4 位缓存。
>
> 累加精度也不能直接从 A16 推出来。Kernel 中，权重可能先解包和反量化，再以某种格式参与乘法，累加或归约又可能使用更高精度，最后再转换成输出类型。这些阶段需要逐一看实现。
>
> 所以介绍一个量化方案时，我会分别说明权重存储、激活格式、反量化与乘法输入、累加精度，以及 KV cache 的格式。只有这些条件明确，才能判断显存、性能和数值误差，不能把 W4A16 当成整条计算链所有 Tensor 的精度声明。

W4A16 的权重／激活含义见 [TensorRT-LLM 精度说明](https://nvidia.github.io/TensorRT-LLM/1.0.0/reference/precision.html)。内部计算与输入 dtype 不必相同的一个例子是 [PyTorch SDPA](https://docs.pytorch.org/docs/2.15/generated/torch.nn.functional.scaled_dot_product_attention.html) 的 math backend：对 FP16／BF16 输入保留 FP32 中间结果；该例不代表所有后端或矩阵 Kernel 的实现。项目实际数据路径继续沿用[核查项 C024](实机核查清单.md#c024)。

### E8. 多开通信流或使用异步接口，就能隐藏通信开销吗？

> 不一定。使用异步接口通常是为了让主机尽早返回，但这不能直接证明设备上的通信已经和计算并行。通信发起后，还要有不依赖它的计算可以继续执行，后端和硬件也要有条件让两者有效推进。
>
> 我会先检查数据依赖：数据准备好后再提交通信，把等待放到真正消费结果之前，并保护好异步期间的缓冲区。如果调用后立即等待，或者下一步计算马上就需要通信结果，能够重叠的空间通常就很小。多 rank 的通信顺序也要保持一致。
>
> 多个流还可能竞争计算、访存或链路资源，并增加 Event、Wait 和提交开销。所以我会比较单流与多流的时间线，看通信究竟覆盖了哪段计算、是否让计算本身变慢，最后再看同一负载下的 step time 或推理延迟，而不是只看接口更早返回。

一般排查与优化方法见[第 12 题](#q12)，已确认的单流配置经历只用于说明特定平台下的取舍，不作为普遍结论。

<a id="amb-extra-e9"></a>

### E9. AIME 准确率一致是否意味着两个后端逐 token 一致？

> 不意味着。准确率只反映最终有多少题被判为正确。两个后端的总分相同，答对的题目都未必完全相同；即使每道题最后都答对，推理过程、措辞和输出 token 也仍然可能不同。
>
> 如果要验证后端适配的数值正确性，我会另外对齐模型、输入和运行配置，检查局部算子或层输出，需要时继续比较 logits 和生成 token。即使 token 相同，也不能反过来证明 logits 完全相同；每一层验证只能支持对应范围的结论。
>
> 以 GLM 项目的已有评测为例，AIME26 使用 OpenCompass，每题生成一次、整个数据集运行一轮，temperature 为零，结果是三十题全部答对，与团队在八卡 H100 上运行同一模型的该项准确率一致。我能据此说明这组任务评测结果一致，但不能扩大成两个后端在所有输入上逐 token 或逐位一致。

完整评测与职责范围见[GLM 项目档案](../../自我准备/projects/GLM5-3-flash-project.md)。该 AIME26 结果不替代本场历史 AIME 2024 的成绩；生成参数、判分方式及后端对照按原项目记录保留。

### E11. 硬件对齐要求和前缀缓存粒度不一致，怎样处理？

关联[第 3 题](#q3)。这是面试官直接询问该技术问题时的通用设计回答，不作为本场独立提问或本人已经完成的项目。

> 我会先分清对齐要求作用在哪一层。框架的 block size 表示一块容纳多少个 token，后端的要求可能是地址、字节数或者某个维度对齐。只有先确认单位和限制对象，才能判断它是否真的要求增大 token 分块。
>
> 如果只是存储对齐，我会先检查能否通过布局和必要的 Padding 满足要求，同时保留合适的 token 分块粒度。如果后端接口确实要求较大的 token 块，那么在按完整块复用的路径里，共享前缀末尾不足一块的部分就需要重新计算。
>
> 如果这部分重复计算比较多，可以评估更细的前缀索引。但只修改哈希粒度或增加取模还不够，还要让缓存管理和 Attention 后端共同支持：命中的 KV 存在哪里、有效长度是多少，以及请求从哪个位置继续计算。
>
> 特别是多个请求共享同一物理块之后，如果它们要在块内追加不同的内容，就必须避免相互覆盖。可以评估把已匹配的部分复制到请求自己的块里，再继续写入，同时处理引用计数和回收。
>
> 最后我会比较省下的 Prefill 计算，是否足以抵消复制、索引和管理开销，并重点验证块边界附近的长度、共享前缀后分叉的并发请求，以及回收后重新分配的情况。正确性确认后，再比较首 token 延迟和显存占用。

复用还要求模型与前缀对应的计算条件一致；缓存键需反映前序 token、块内 token，以及相关 LoRA、多模态输入等差异。完整块缓存、前缀哈希和引用计数的参考基线见 [vLLM v0.26.0 Prefix Caching](https://docs.vllm.ai/en/v0.26.0/design/prefix_caching/)；更细前缀索引及部分复制是本题讨论的设计选择，不宣称该版本默认支持。命中收益与细粒度映射可继续结合 [E1](#amb-extra-e1)、[E2](#amb-extra-e2)回答。
