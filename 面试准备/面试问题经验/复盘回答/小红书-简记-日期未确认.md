## 1. vLLM V0 与 V1 的区别

### 1.1 已记录题意与准备重点

简记明确问两代引擎的区别、改进与优化点。没有原答，不能判断曾经遗漏哪些点。准备时应说明重构要解决的问题、改变的位置及收益条件；V0／V1 是引擎代际，不能直接等同于安装包版本号。

### 1.2 更好的回答方式

以官方 V1 初版设计为起点，再按实际比较的 tag／commit 核对：

| 比较维度 | 应讲清的变化 | 避免过度概括 |
| --- | --- | --- |
| 执行组织 | EngineCore 聚焦调度与模型执行，其他 CPU 工作与核心循环分开 | V0 已有多进程 API Server 等机制，不能说 V1 才第一次有多进程 |
| 调度表示 | 用每请求本步计算的 token 数统一描述进度，便于组合 chunked prefill、prefix cache 等 | 统一调度不表示 Prefill 和 Decode 的计算形态相同 |
| 输入与状态 | Persistent Batch 复用输入缓冲和状态，更多传增量更新 | 并非不用更新 metadata，也不是异步 H2D 从 V1 才出现 |
| KV 管理 | 优化数据结构与对象开销，改善前缀复用的执行成本 | V0 也有 PagedAttention／Prefix Cache，不能把已有能力都归为 V1 新增 |
| 编译与多模态 | 更系统地组合编译、图执行和多模态处理优化 | 可用性与收益依版本、模型和后端，不能照搬到自研平台 |

上述演进依据[vLLM 官方 V1 发布说明](https://vllm.ai/blog/2025-01-27-v1-alpha-release)；当前实现可对照 [v0.26.0 架构说明](https://docs.vllm.ai/en/v0.26.0/design/arch_overview/)，不把这个参考版本当成本场项目版本。

### 1.3 参考回答

> 我会先固定要比较的两个版本。V1 的重要变化是重新组织核心循环和状态管理，让调度、输入准备和已有优化更容易组合，同时减少 CPU 开销。
>
> 例如，调度可以统一表示每个请求本步要计算多少 token；执行端保留请求状态和输入缓冲，按增量更新，减少每轮重复构造。前缀缓存也着重优化管理成本，而不是从无到有地新增分页或前缀复用。
>
> 对平台适配来说，我关心这些变化是否改变了输入生命周期、metadata、异步拷贝、编译和图执行的要求。迁移时需要重新验证这些接口及正确性，并在相同负载下比较时延和吞吐。不能仅凭“V1”这个名字承诺所有模型都更快，也不能说 V0 不支持任何相关优化。

现有[异步 H2D 案例卡](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)可作为状态生命周期与后端适配的个人例子；其已确认结论是框架／后端依赖修复，不是独立开发了 V1 引擎。

## 2. MFU 的定义、计算与优化

### 2.1 已记录问题与子问

简记包含 MFU 的定义、计算、低 MFU 的可能原因和优化方法。原作答缺失，下面给标准准备，不标记为个人已暴露的短板。

### 2.2 定义与计算范围

MFU 通常指 Model FLOPs Utilization。设一次观测区间内，模型按明确算法口径完成的必要计算量为 `F_model`，耗时为 `Δt`，参与设备在对应计算精度下的峰值合计为 `ΣP_i`，则：

`MFU = F_model / (Δt × ΣP_i)`。

`F_model` 的单位是 FLOP，`P_i` 是 FLOP/s，时间和峰值覆盖的设备范围要一致。不能用设备忙碌时间比例代替该比值，也不能把低精度、稀疏模式的宣传峰值用于不符合条件的计算。

对忽略 Attention 等附加项的稠密模型训练，若 `N` 是相应参数量，每 token 的前向与反向可粗估为 `6N` FLOP；推理只有前向，不能直接使用 `6N`。长上下文 Attention、MoE 激活路径、Padding 和重计算需要分清：模型必要算量与实现额外执行的算量不是同一口径。MFU 不把激活重计算当作额外完成了模型工作；HFU 则关注硬件实际执行的计算。定义依据 [PaLM §4.1 与附录 B](https://arxiv.org/pdf/2204.02311)。

### 2.3 低 MFU 的原因与更好的定位方式

| 可能原因 | 应检查的证据 | 可评估的优化 |
| --- | --- | --- |
| 小矩阵或低批量 | 实际 Shape、Kernel 时间、计算单元利用情况 | 合批、合适的 Kernel／Tile、融合；同时检查时延约束 |
| 访存限制 | 选定层级的读写量、有效带宽和算术强度 | 布局、复用、融合、适用的量化 |
| 通信与同步 | 各 rank 时间线、通信量、等待和负载偏斜 | 并行组合、分组、依赖与重叠优化 |
| Host 下发与数据准备 | 设备空洞、CPU 热点、拷贝及同步位置 | 增量输入准备、减少往返、图执行等 |
| 无效或冗余工作 | Padding、重计算、负载不均、重复布局转换 | 改善分桶、工作分配和数据路径 |

这里是诊断候选，不是看到低 MFU 就直接选择某项优化。低并发 Decode 本来可能受访存而非算力限制，应同时看内存带宽、每 token 时延和业务目标。

### 2.4 参考回答

> MFU 是模型必要 FLOPs 的完成速率与参与设备理论峰值的比值。我会先说明模型、负载、计算精度和计时范围，再给分子分母。训练常用的 6N 每 token 只是忽略部分项的近似，推理、长上下文或 MoE 需要按对应执行量重新计算。
>
> MFU 低并不能直接说明算子写得差。可能是矩阵太小、访存受限，也可能是通信等待、Host 下发、Padding 或负载不均。我会从端到端时间线定位，再结合实际 Shape 和 Roofline 判断资源瓶颈，最后选择对应的优化。
>
> 验证时保持负载和正确性条件一致，同时报告吞吐、时延和内存。单纯通过更大 batch 提高 MFU，可能让请求等待变长；增加无用计算也不应被算作有效提升。因此 MFU 是诊断与比较的一项指标，最终仍要满足交付目标。

个人项目可以引用 [ECG 案例中的 Roofline 初步估算](../../自我准备/projects/ECG-project.md#f3从热点判断到布局方案)。现有材料未提供真实芯片的完整 MFU 测量，不补写具体百分比。

## 4. 何时融合算子，向前还是向后融合

### 4.1 已记录问题与子问

原简记明确询问融合的适用场景与方向。没有对应作答，不能评价当时是否理解资源约束。准备重点是生产者—消费者之间的真实数据移动，而不是“算子越少越好”。

### 4.2 更好的回答方式

先确认语义允许，再检查中间 Tensor 是否物化、是否被多处使用，以及融合后计算资源是否合适。以 `MatMul → bias → activation` 为例，把后两步纳入 MatMul epilogue 可能减少中间写回；但若 MatMul 输出还被另一个分支消费，就要计算保留中间值或重复计算的成本。纯 metadata view 的消除与消除一次真实 copy，收益不能混为一谈。

### 4.3 参考回答

> 我会从数据流判断。若相邻算子之间有较大的中间结果写回、重复读取、频繁下发或布局转换，并且数学和状态依赖允许，就值得评估融合。向前或向后只是相对于当前算子的说法，关键是哪个生产者和消费者能在同一执行单元里复用数据。
>
> 例如 MatMul 后的 bias 和激活可以考虑作为 epilogue，避免中间结果多次写回；反过来，前置转换能否融合进加载路径，要看访问方式和其他消费者。不能只看图上相邻，还要看 Tile、布局和生命周期。
>
> 融合也有代价：寄存器或片上存储压力增大可能引起 spill 或降低并行度，不同 Shape 可能失去专用 Kernel 的效率。最终比较完整子图和端到端性能，并做数值与边界回归。H2D／D2H 是否减少则要解释数据依赖和执行位置，设备 Kernel 融合不会自动消除主机传输。

减少 HBM 中间物化的具体例子可参考 [FlashAttention 原论文](https://arxiv.org/abs/2205.14135)；其分块与在线归一化并不将 dense Attention 的算术复杂度自动变成线性。个人适配例子可引用[多模态项目](../../自我准备/projects/multimodal-inference-project.md)，保留框架与算子团队分工。

## 5. TP、CP、SP 及 TP+CP 的通信与 Shape

### 5.1 已记录问题与明确子问

简记同时要求解释 TP、CP、SP，以及 TP 与 CP 并用时的通信算子和输入 Shape。具体模型、并行度和实现没有记录，不能从题干恢复唯一的通信序列；应先给出有条件的完整例子。

### 5.2 名称与范围

| 策略 | 本节使用的含义 | 要解决的依赖 |
| --- | --- | --- |
| TP | 按层内特征、heads 或中间维切分权重和计算 | 合并部分和，或在消费者需要时收集特征分片 |
| CP | 将长序列位置分给不同 rank | 本地 Q 仍需要其他序列片段的合法 K/V |
| SP | 与 TP 组配合的 Megatron 风格 sequence parallel，切分部分非 TP 算子的 token 轴激活 | 在 LayerNorm 等可逐 token 计算的位置节省激活，按相邻算子布局执行 AllGather／ReduceScatter |

这里的 SP 不泛指所有被称为序列并行的方案。CP 与 TP 的通信组分别对应序列轴和特征轴，不能把二者并成一个未经说明的全局 collective。

### 5.3 TP+CP 的前向示例

设输入为 `X[B,S,H]`，批大小 `B`、序列长度 `S`、隐藏宽度 `H=n_q×d`，Q heads 为 `n_q`、KV heads 为 `n_kv`、每 head 维度为 `d`。TP 度为 `p`、CP 度为 `c`，假设序列和 heads 均可按相应维度整除；先不启用 SP、PP、跨层共享和 KV head 复制。

rank 用 `(i,j)` 表示 TP 坐标与 CP 坐标。相同 `j` 的 rank 组成 TP 组，相同 `i` 的 rank 组成 CP 组。CP 之间复制相应权重分片，处理不同 token 位置；本例采用简单均分说明，真实因果实现还可能使用交错分块来平衡工作量。

| 步骤 | rank `(i,j)` 的主要张量 | 通信与原因 |
| --- | --- | --- |
| 进入层 | `[B,S/c,H]` | 同一 CP 片段的完整隐藏输入在该 TP 组内复制 |
| 本地 QKV 投影 | Q：`[B,S/c,n_q/p,d]`；K/V：`[B,S/c,n_kv/p,d]` | Column-parallel 投影得到本地 head 分片 |
| Attention | 本地 Q 处理全部合法历史 K/V；输出 `[B,S/c,n_q/p,d]` | 沿 CP 组获得其他序列块的 K/V，可用整体收集或 ring P2P 流式交换；不是无条件要求物化完整 K/V |
| 输出投影 | 本地部分和 `[B,S/c,H]` | 沿 TP 组 AllReduce 得到当前序列片段的完整隐藏输出 |
| MLP | Gate／Up 分片后本地激活；Down 生成部分和 | 沿 TP 组按消费者需要归约，与普通 TP 推导相同 |

流式分块 Attention 必须正确合并不同 K/V 块对应的归一化统计，不能把各块独立 softmax 后的输出直接相加。以上是前向示例；训练还涉及 K/V 梯度合并和 CP 权重副本的梯度同步，不能把该表当成完整训练通信表。

依据：[Megatron Core CP 说明](https://docs.nvidia.com/megatron-core/developer-guide/0.16.0/user-guide/features/context_parallel.html)与 [SP 原论文](https://arxiv.org/abs/2205.05198)。实际 CP 还存在 AllToAll 等实现；推理 DCP／PCP 的数据布局和步骤不能直接照抄本例。

### 5.4 参考回答

> TP 切分层内计算，CP 切分序列，SP 要先明确这里指哪种实现。我会用 Megatron 风格 SP 说明，它在 TP 的部分非矩阵并行区间切分 token 轴激活，并在算子边界转换布局。
>
> 以 TP=p、CP=c 为例，暂不启用 SP，输入 B×S×H 先按 CP 分为 B×S/c×H，同一 CP 片段在 TP 组内保留完整隐藏输入。QKV 投影再按 heads 切开，各 rank 得到本地序列片段和本地 heads 的 Q/K/V。
>
> Attention 的本地 Q 需要其他 CP 片段的合法 K/V，因此沿 CP 组交换缓存或状态；可以用 ring P2P 流式处理，也可以使用其他收集方式。每个序列块的 softmax 统计要合并正确。Attention 后的输出投影产生完整隐藏维的部分和，再沿 TP 组归约。这里 CP 通信解决历史位置依赖，TP 通信解决特征分片的贡献合并，两者不同。
>
> 如果启用 SP，部分入口可能先保存 B×S/(c×p)×H，进入需要完整 CP 片段的 TP 矩阵计算前 AllGather；Row-parallel 输出可以 ReduceScatter 回 token 分片。最终通信序列要由入口、出口布局决定。KV heads 少于 TP 数或不可整除时，也需要按后端的复制规则重算 Shape，不能机械除以 p。

本节是通用前向推导，不表示这场面试采用了上述配置，也不将个人基础通信适配经历扩张为独立设计全部并行策略。个人范围见 [CL09 已确认口径](../../自我准备/Claim-evidence矩阵.md#claim-wording-decisions-20260929)。

## 扩展问题与参考回答

以下为补充准备，没有对应现场作答评价。

### E1. 迁移 V1 后输出偶发错误，应如何排查？

> 先固定请求、生成配置与版本，定位最早分叉的 token 和层，检查输入、位置、缓存映射及异步依赖。分别关闭可疑优化做对照，但单次关闭后稳定只能缩小范围；修复后还要恢复原配置、撤掉诊断同步再回归。可以引用已有 H2D 案例的完整依赖与 168 条请求×5 轮范围，不把它扩张成所有 V1 问题都来自拷贝。

依据：[异步 H2D 案例卡](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)。

### E2. MFU 提高就一定代表服务更好吗？

> 不一定。提高 batch 可能让计算更饱满，却增加排队和尾延迟；不同精度或工作负载的 MFU 口径也可能不同。服务应同时检查 TTFT、输出间隔、吞吐、正确性和成本，MFU 只能在口径一致时辅助比较。

### E3. GPU 忙碌时间很高，但 MFU 低，是否矛盾？

> 不矛盾。设备可能持续执行访存、小 Kernel、同步或冗余工作，忙碌并不等于接近峰值完成模型有效 FLOPs。需要看计算指令、内存流量和时间线，而不是把利用率面板上的一个百分比直接替换为 MFU。

### E4. AI 写的实现和测试同时通过，为什么还要独立参考？

> 实现与测试可能共享同一个错误假设。应从接口契约、可信实现或手工可判定的边界例子取得独立依据，并让测试能够在已知错误时失败。对于异步、别名和设备路径，还要验证确实走到目标实现，而不是静默 fallback 后碰巧输出正确。

### E5. 算子融合后更慢，优先检查什么？

> 检查寄存器与片上存储压力、spill、并行度、实际中间拷贝是否消失，以及是否失去了原先高效的库 Kernel。再看是否有多个消费者导致重算、是否引入额外格式转换。固定 Shape 和精度做完整子图对照，不能只用 Kernel 数量判断性能。

### E6. CP 为什么不能只对各分片的 Attention 输出求平均？

> 每个 K/V 分片包含不同分数，其局部 softmax 分母不同。全局结果需要按一致的指数基准合并归一化统计和加权输出，简单平均局部结果通常不等于全局 softmax。因果 mask 和有效长度也必须对应到原序列位置。

分块归一化依据：[FlashAttention](https://arxiv.org/abs/2205.14135)。

### E7. TP 增大，KV 内存是否始终等比例减少？

> 不一定。实际本地 KV heads 可能因 GQA／MQA 的 head 数与 TP 度关系而复制；PP、CP、缓存布局和对齐也会改变每 rank 占用。应按后端真实映射计算，而不是总 KV 字节数统一除以 TP。

### E8. 为什么不把所有并行都改成 AllToAll？

> collective 表达不同的数据语义。求同一输出的部分和需要归约；拼接不同坐标需要 Gather 类通信；按目标 rank 重新分发数据才可能使用 AllToAll。应先确定数据在谁手里、谁要消费、需要拼接还是求和，再选算法和拓扑，不能把某一种通信当成通用优化。
