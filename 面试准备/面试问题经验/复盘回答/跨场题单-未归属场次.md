## 一、算子与 Kernel 优化

<a id="q1"></a>
### 1. 算子优化有哪些常用手段？

**考察点与条件。** 从瓶颈选择手段，说明收益、依赖和资源代价，而不是报优化名称。

**对已有笔记的技术校准。** 融合、双缓冲、流水线、特化和展开都是候选手段。双缓冲不自动形成重叠，需异步能力与正确依赖；流水线通常还需要排空阶段。Mask 不会让无效工作全部免费，CPU 侧特化也不只是利用分支预测，还涉及变体数量和编译成本。

**参考回答。**

> 我先区分计算、访存、同步和下发瓶颈。访存方面可用分块复用、连续或向量化访问、布局调整，减少中间张量；计算方面选择合适的矩阵单元、Tile 和数据类型；下发开销较大时考虑融合、图执行或批量提交。
>
> 双缓冲和软件流水线可以把下一块传输与当前块计算重叠，但要保证写入完成后才能读、消费结束后才能复用缓冲。融合、循环展开和模板特化也会增加寄存器、片上空间或代码体积，因此我会同时验证数值正确性、不同 Shape、资源占用和端到端收益，不把单个 Kernel 更快当成整模必然更快。

依据：[CUDA 异步流水线](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/pipelines.html)、[CUDA Kernel 资源与访存说明](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)。

<a id="q2"></a>
### 2. 如何判断算子或模型是否存在优化空间，以及应该朝什么方向优化？

**考察点与条件。** 固定负载、建立上下界、用证据区分瓶颈；算子和端到端分别测量。

**参考回答。**

> 我先固定 Shape、dtype、输入输出长度、并发和计时范围，得到可重复基线，再从整条执行时间线找到热点、空洞、拷贝和同步。对热点算子估算计算量 F 和所选存储层的必要流量 Q，比较计算下界 F/峰值算力与访存下界 Q/带宽；这个简化模型还要说明缓存复用和读写次数假设。
>
> 如果主要受供数限制，优先减少流量、改善布局和复用；算力利用差则看 Tile、并行度和指令路径；大量空洞则检查 Host、依赖、launch 和通信。最后做控制变量对照，确认瓶颈真的被改变，并检查是否只是把耗时转移到别处。理论上界与实测差距是线索，不是单凭一个低利用率就判定实现有错。

方法与假设可对照[ECG 案例卡中的 Roofline 表达](../../自我准备/projects/ECG-project.md#f3从热点判断到布局方案)，此处不使用该项目数字作为通用基准。

<a id="q3"></a>
### 3. 如何针对不同 Shape 设计特定的 Kernel？

**考察点与条件。** 形状分区、资源约束、调度与回退；不能仅按元素总数选同一配置。

**参考回答。**

> 先按决定计算形态的维度分类，例如 MatMul 的 M、N、K、批量、stride 和对齐，而不是为每个 Shape 都手写一份代码。小 M 可能更受权重读取和 launch 限制，大矩阵更强调 Tile 复用和矩阵单元吞吐，极长归约还要考虑拆分后的额外归约成本。
>
> 每类选择候选 Tile、线程／warp 数、流水级数和向量宽度，检查寄存器与 shared memory 是否限制并行驻留。整齐尺寸可以特化，尾部用正确 mask 或专门路径，非连续输入要处理 stride。分派条件、编译缓存和回退一并设计，再以代表性 Shape 和边界输入验证，避免某个最佳点换来大面积退化。

依据：[CUDA Kernel 线程、寄存器和访存约束](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)。

<a id="q4"></a>
### 4. 编写 Kernel 算子时有哪些难点？

**考察点与条件。** 数学、索引、并发和框架契约同时正确，性能取舍可验证。

**参考回答。**

> 首先是把数学定义落实到物理索引：Shape、stride、对齐、广播、尾块、别名和越界都要明确。其次是并发依赖，尤其异步拷贝、共享缓冲复用和归约，不能假设同一 warp 或不同 block 会按想象的顺序执行。
>
> 数值上要说明输入、乘法、累加和输出精度，以及不同归约顺序允许的误差。性能上则在复用、寄存器压力、并行度和调度开销之间取舍。接入框架时还要满足 stream、设备、workspace、动态输入和错误传播的约定。我会先用清晰参考实现和边界测试保正确，再分段测量优化，保留可比较的普通路径。

同步边界依据：[CUDA 线程块与内存模型入口](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html#thread-block-synchronization)。

<a id="q5"></a>
### 5. 什么是 Bank Conflict？如何发现和避免？

**考察点与条件。** 先说明存储层级、bank 映射和单次访问粒度；不把所有非连续访存都叫 bank conflict。

**参考回答。**

> 以常见 NVIDIA shared memory 为例，一个 warp 的同次访问若让多个线程访问同一 bank 的不同地址，可能需要拆成多次服务。对常见 32 位访问，可用地址除以 4 再模 32 理解 bank 映射；同一地址的读取广播通常不属于这种冲突，多线程写同一地址另有竞争问题。
>
> 我会结合实际索引和指令访问宽度推导，再用 profiler 的 shared-memory 冲突或事务指标验证。常见处理是调整布局、增加 Padding、swizzle 或改变线程分工，例如特定转置中的 32×32 改为 32×33；但不能对所有 dtype 和向量访问机械套用。HBM 侧若怀疑 bank／channel 冲突，需要另外的地址映射与计数器证据，不能仅凭 stride 大就下结论。

依据：[CUDA Shared Memory Bank Conflicts](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html#shared-memory-bank-conflicts)。

## 二、注意力机制与推理框架

<a id="q6"></a>
### 6. FlashAttention 系列有哪些关键优化？

**考察点与条件。** 区分数学复杂度、IO、并行划分和硬件流水；下列 FA4 是截至整理日期的补充资料，不推定历史问题已经要求它。

**参考回答。**

> 共同主线是在不物化完整 N×N 注意力矩阵的情况下分块计算，并用在线 Softmax 保持全上下文归一化。标准稠密 Attention 的主要计算仍是 O(N²d)，不是变成线性注意力；改善主要来自 IO、存储和执行效率。
>
> FA1 强调 IO-aware tiling 与重计算；FA2 减少非 MatMul 工作，调整跨 block 和 warp 的划分，减少 shared-memory 通信；FA3 面向 Hopper，用异步矩阵计算、TMA 和 warp specialization 组织重叠，也研究 FP8 路径。FA4 进一步面向 Blackwell 的不对称硬件增长，重构异步流水，减少指数／重标定开销，并利用 tensor memory 等能力。
>
> 选择实现要看设备、head dimension、长度、mask 和精度。算法保持稠密注意力语义，不表示所有低精度路径与参考逐位相等，也不代表同一版本在所有负载最快。

一手依据：[FA1](https://arxiv.org/abs/2205.14135)、[FA2](https://arxiv.org/abs/2307.08691)、[FA3](https://arxiv.org/abs/2407.08608)、[FA4](https://arxiv.org/abs/2603.05451)。

<a id="q7"></a>
### 7. vLLM 的调度机制是怎样的？

**考察点与条件。** 用固定版本解释请求状态、token 预算、KV 与执行回传；不把所有历史版本混成一个实现。

**参考回答。**

> 以 V1 为例，Scheduler 根据等待／运行请求、本轮 token 预算、序列和缓存约束，决定每个请求推进多少新 token。它结合前缀命中减少待计算量，再请求 KV 管理器分配本轮需要的块；容量不足时按策略等待或抢占，而不是无限接入。
>
> 长 Prefill 可以分轮，普通 Decode 每个活跃请求通常推进一个 token，投机解码则可能包含多个候选。执行计划送到 Worker／ModelRunner，后者准备位置、块表和 slot 等元数据，完成模型与采样后回传结果，调度器更新状态、结束或继续请求。完成的请求可以退出、新请求按轮次加入。统一 token 预算不是每轮只算一个 token，也不表示 Prefill 和 Decode 的计算成本相同。

依据：[固定 `vLLM v0.26.0@568afb3` 的 V1 Guide](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/usage/v1_guide.md)。

<a id="q8"></a>
### 8. 如何处理模型运行时的连续内存碎片问题？

**考察点与条件。** 原题措辞可能指需要大块连续空间时的外部碎片；先区分真实容量不足、存活对象和分配器碎片。

**参考回答。**

> 我先看活跃 Tensor、缓存池预留、空闲块大小和峰值生命周期，确认是总容量不够，还是有空闲容量却无法满足当前分配。长短生命周期混用和动态 Shape 反复改变分配大小，都会使问题复杂化。
>
> KV 可以用分页块池和间接寻址，避免每个请求要求一整段连续缓存；一般 workspace 可以预分配、按桶复用，减少临时物化并缩短存活期。但分页仍有内部浪费，对要求连续输入的 Kernel 也不能直接换成分散块。
>
> 连续虚拟地址与连续物理页是不同概念，具体能力取决于后端。`empty_cache()` 只释放分配器中未使用的缓存，不移动或压缩仍被 Tensor 引用的存储；若是活跃内存本来就超限，应减少负载、改精度或算法，不能靠清缓存解决。

依据：[PyTorch 固定版本内存管理说明](https://github.com/pytorch/pytorch/blob/0bd89deb431509d893177a84cfa4768aa0399809/docs/source/notes/cuda.md#memory-management)、[PagedAttention 论文](https://arxiv.org/abs/2309.06180)。

<a id="q9"></a>
### 9. 推理框架未来发展面临哪些痛点？

**考察点与条件。** 将趋势判断落到具体系统矛盾和指标；下面是当前判断，不是确定预测。

**参考回答。**

> 我会重点看三类矛盾。第一，长上下文、多模态和混合注意力让缓存类型、生命周期和内存预算更复杂，不能只围绕普通 KV 做统一假设。第二，MoE、投机和动态请求让执行形状与负载不断变化，需要兼顾图执行、低延迟、吞吐和尾部公平性。
>
> 第三，硬件和低精度格式变化很快，抽象层既要允许后端特化，也要保持数值与生命周期契约。单 Kernel 加速可能被 Host、跨设备传输或编译开销抵消，因此观测、基准和回归会越来越重要。
>
> 我不会只按特性数量评价框架，而会看它能否在目标负载和服务约束下稳定交付、解释退化，并控制适配与升级成本。P/D 分离、缓存共享和新 Kernel 都是解决具体矛盾的手段，不是所有系统必须采用的方向。

判断依据：[V1 的统一架构目标](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/usage/v1_guide.md)、[DistServe 的时延与资源约束](https://arxiv.org/abs/2401.09670)、[FA4 的硬件瓶颈变化](https://arxiv.org/abs/2603.05451)。

## 三、量化与数值精度

<a id="q10"></a>
### 10. Weight-only INT4、Weight-only FP8，以及同时量化权重和激活的 FP8，三者在应用上有什么区别？

**考察点与条件。** 区分存储格式、计算输入、scale、累加和输出；位宽不能直接推导速度或精度排名。

**参考回答。**

> INT4 weight-only 主要把权重压到 4 位，激活保留较高精度；FP8 weight-only 则用 8 位浮点存权重，两者都还需要量化参数和相应解码／计算路径。前者名义权重体积更小，但误差、打包和解量化成本也要评估；FP8 不必然在任何配置下都更准确。
>
> 权重和激活都使用 FP8 的方案，还需处理激活 scale 与格式转换，在支持相应矩阵指令的硬件上可获得低精度计算吞吐收益。仅把权重存成 FP8，不能据此声称执行的是 FP8×FP8 MatMul。
>
> 小 batch 权重读取占主导时，weight-only 常是候选；更大计算量下，权重与激活共同低精度可能更有价值，但要实测转换和 Kernel 开销。KV、累加和输出精度是另外的配置，不能从 W8A8 自动推出。

依据：[Torch-TensorRT 对 weight-only 与静态 FP8 的区分](https://docs.pytorch.org/TensorRT/user_guide/shapes_precision/quantization.html)、[TensorRT 数值格式和 scale](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/quantized-types-schemes.html)。

<a id="q11"></a>
### 11. 在 Weight-only 量化中，为什么只量化权重，不量化激活值？

**考察点与条件。** 从负载瓶颈和误差成本说明取舍，而不是声称激活无法量化。

**参考回答。**

> 小 batch 的生成过程中，大量静态权重需要反复读取，权重压缩可以降低容量和带宽压力。权重还可以提前分析、量化和打包，把部分成本放到加载或离线阶段。
>
> 激活随输入变化，分布和异常值更难处理；保留 FP16／BF16 可以减少额外校准或动态 scale 开销，也降低激活量化误差和后端改造范围。这是工程取舍，不是说激活不能量化。若算力或激活流量成为瓶颈，且硬件有高效 W8A8 等路径，就应比较共同量化。
>
> Weight-only 同样不是免费压缩：读取到的权重如何解包、反量化或以混合类型计算，会影响收益；因此需要同时看任务效果、Kernel 与端到端性能。

依据：[AWQ 的 weight-only 方法](https://arxiv.org/abs/2306.00978)、[Torch-TensorRT 的 weight-only 执行边界](https://docs.pytorch.org/TensorRT/user_guide/shapes_precision/quantization.html)。

<a id="q12"></a>
### 12. 动态量化和静态量化有什么区别？各自适用于什么场景？

**考察点与条件。** 本题主要按激活量化参数何时确定解释；这与动态 Shape、PTQ／QAT 或权重是否更新是不同维度。

**参考回答。**

> 静态激活量化通常在离线用代表性数据校准范围和 scale，部署时复用这些参数，运行开销较容易控制，但校准分布不匹配时可能裁剪过多或精度下降。
>
> 动态量化在运行时根据当前输入计算相应 scale，可以按 token、tensor 或 block 等粒度组织，适应输入范围变化，但增加统计、量化和元数据成本；具体支持粒度由实现决定。两者的静态权重都可以提前量化，因此不能把“动态”理解成每次重新训练权重。
>
> 输入分布稳定、校准样本充分且运行开销敏感时可优先评估静态方案；分布变化大、异常值差异明显或后端支持高效动态块量化时可评估动态方案。动态不等于完全不用离线工作，仍要验证权重、其他 scale 和整体任务效果。

依据：[TensorRT Quantization Workflows](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/quantized-types-workflows.html#dynamic-quantization)。该实现的动态块量化限制不泛化为所有框架。

<a id="q13"></a>
### 13. 模型出现精度异常时，如何定位异常点？

**考察点与条件。** 先建立可比基线，再区分数值误差、状态错误和并发错误。

**参考回答。**

> 先固定模型与权重、tokenizer／预处理、输入、生成配置、随机种子和参考实现，确认差异不是采样或版本导致。生成结果不同不能直接定位算子，应比较 logits 和中间结果，逐层或二分找到最早明显偏离的位置。
>
> 在该位置固定输入，检查 Shape、stride、mask、position、KV 写入及并行分组，再检查 dtype、scale、累加和归约误差。同时看绝对／相对误差、Inf／NaN 和分布，而不是只用一个统一容差判断所有层。
>
> 若只在并发或异步路径出错，可以用受控同步缩小范围，但同步让问题消失只是定位证据，不是最终修复。最后提取最小复现，修正真实依赖或数值路径，再做算子、模型和原触发负载回归。

数值边界依据：[TensorRT Accuracy Considerations](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/accuracy-considerations.html)；方法可对应现有[项目资料](../../自我准备/projects/multimodal-inference-project.md)，本题不新增个人项目结论。

<a id="q14"></a>
### 14. 为什么低精度数据类型仍能让模型产生有效结果？

**考察点与条件。** 同时回答 INT8／INT4／FP8／FP4 为什么可用，以及大量乘加为什么不必然导致结果失效。

**参考回答。**

> 模型需要的是足够准确的函数近似，并非所有中间数都必须保留 FP32 的每一位。量化通过合适的 scale、粒度和校准，把有限编码用在重要的数值范围；某些模型和任务能容忍一定扰动，但这种容忍必须通过验证确定。
>
> 低精度存储也不代表所有乘加、归约都在同样位宽完成。硬件可以用更高精度累加，敏感的归一化或 Softmax 可以保留更高精度。误差不一定每次同号累积，但也不能依赖相互抵消来保证正确；输入量化造成的信息丢失不会由 FP32 累加恢复。
>
> BF16 的范围接近 FP32，精细分辨率却低于 FP16；FP8／FP4 还更依赖格式与缩放。遇到异常值、长归约或敏感层，误差仍可能放大。因此“能有效运行”是格式、算法、混合精度和任务验证共同成立的结果，不是低位宽天然无损。

依据：[AWQ](https://arxiv.org/abs/2306.00978)、[数值精度风险与混合精度](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/accuracy-considerations.html)。

## 四、性能评估与分布式并行

<a id="q15"></a>
### 15. MFU 如何计算？

**考察点与条件。** 模型有效计算、计时范围、设备峰值和精度口径一致；MFU 不等于 `nvidia-smi` 的忙碌比例。

**参考回答。**

> MFU 可以写成 `F_model / (t × P_peak_total)`：F_model 是该批有效模型计算量，t 是对应墙钟耗时，P_peak_total 是参与设备在约定精度和稀疏口径下的峰值算力之和。也可用每 token 模型 FLOPs 乘全局 tokens/s，再除总峰值，不能把 TP 各 rank 的同一批 token 重复累计。
>
> 对典型稠密 Transformer 训练，参数相关主项每 token 约 6P，P 为参数量，还要考虑 Attention 等计算；前向推理不能照用训练的 6P。MoE 也不能把全部专家参数都当每 token 激活。MFU 不把为了省内存额外做的重计算当成更多有效模型工作，这与计入实现额外计算的 HFU 不同。
>
> 比较时说明 batch、长度、计时范围及峰值来源。Decode 本来可能受带宽限制，MFU 低并不单独证明优化失败。

依据：[PaLM §4.1 与附录 B](https://arxiv.org/pdf/2204.02311)。

<a id="q16"></a>
### 16. Megatron 中的 TP 并行是如何实现的？

**考察点与条件。** 按分片轴推导通信。下面用无 Sequence Parallel、输入复制、忽略 bias 的前向 MLP 作说明，维度可被 TP 数 p 整除。

**参考回答。**

> 令输入 X 为 `[T,H]`，中间宽度 F。第一层权重按输出维切成 `[H,F/p]`，每个 rank 得到自己的 `[T,F/p]`，可以本地做激活；门控 MLP 则让 gate 和 up 的对应分片本地相乘。第二层权重按输入维切成 `[F/p,H]`，本地结果虽是 `[T,H]`，却只是对部分中间通道的求和，需要在 TP 组内 AllReduce 得到完整输出。
>
> 因而两层之间不必先 AllGather。Attention 的 QKV 常按 head 相关维度分片，本地计算后由输出投影合并贡献；GQA 的 KV 切分或复制需另外说明。训练反向还要按梯度的复制／分片状态做相应归约，不能只看前向。
>
> 启用 Sequence Parallel 等配置后，消费者需要的布局变化，通信可能组合为 AllGather／ReduceScatter。TP 的关键是保持每个数学结果的贡献完整，不能按层名固定背一种 collective。

依据：[Megatron-LM 原论文](https://arxiv.org/abs/1909.08053)；可对照[固定版本 Column／Row Parallel 实现](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/model_executor/layers/linear.py#L406)，后者仅作共同机制的代码参照。

## 五、编程题与并发

<a id="q17"></a>
### 17. 如何使用 CUDA 编写 Top-K 堆排序？

**考察点与条件。** 先确认取最大还是最小、N 与 K、是否要求排序、重复值／NaN 规则。Top-K 选择不等于把全部数据堆排序。

**参考回答。**

> 若取最大的 K 个，可维护容量 K 的最小堆：先建堆，之后每个元素与堆顶比较，更大才替换并向下调整。单个顺序扫描最坏 O(N log K)，额外空间 O(K)；需要有序输出时，再对选出的 K 项排序，不能把堆本身当成已排序结果。
>
> CUDA 上我会分区独立选局部 Top-K，再合并候选得到全局 Top-K；每个分区保留 K 个足够覆盖全局候选，但要统一并列值和索引规则。避免所有线程争用一个全局堆，它会把并行变成锁和原子争用。
>
> 堆有依赖和不规则访问，大 K 的线程私有数组还可能溢出到 local memory。因此堆只是候选：很小 K 可比较 warp／寄存器选择，较大批量可比较 radix selection 或排序。最终按 N、K、batch 和是否有序测量，不能因为 CPU 上常用堆就认定 GPU 也最快。

GPU 实现参照：[PyTorch 固定版本 CUDA Top-K 的 radix 与排序路径](https://github.com/pytorch/pytorch/blob/0bd89deb431509d893177a84cfa4768aa0399809/aten/src/ATen/native/cuda/TensorTopK.cu)。这是算法说明，不冒充已完成的现场代码。

<a id="q18"></a>
### 18. 如何实现 LeetCode 线段树？

**考察点与条件。** 原记录没有题号；先明确区间聚合、点更新还是区间更新，不推定具体题目。

**参考回答。**

> 我先定义节点保存什么以及怎样合并，例如区间和用加法，空区间单位元为 0。把区间递归二分，叶子存原值，父节点合并左右结果。查询时分为不相交、完全覆盖和部分相交，统一使用 `[l,r)` 等边界约定；点更新改叶子，再沿路径重算父节点。
>
> 合并为 O(1) 时，建树 O(N)，点更新和连续区间查询 O(log N)，空间 O(N)。合并操作要满足结合律，不一定交换，左右结果顺序不能随便改。
>
> 若题目是区间加、区间求和，再加 lazy 标记：整段加 Δ 时更新 `sum += Δ×区间长度`，暂存未下传增量；需要访问子区间时下传，返回时重新合并。其他更新必须重新定义标记的作用与组合，不能把区间赋值和区间加的标记混用。

依据：[AtCoder 官方 Segtree](https://atcoder.github.io/ac-library/production/document_en/segtree.html)、[Lazy Segtree 的映射与组合要求](https://atcoder.github.io/ac-library/production/document_en/lazysegtree.html)。

<a id="q19"></a>
### 19. 如何在 CUDA 多线程环境中实现线程安全的生产者—消费者队列？

**考察点与条件。** 明确单／多生产者消费者、有界容量、FIFO 语义及参与者范围；正确性包括槽位所有权、发布、回收和执行进度。以下是有界 MPMC 环形队列的设计要点，不是未经验证的完整实现。

**参考回答。**

> 我会把“预留位置”和“数据已经就绪”分开。head／tail 配合 CAS 和每槽序号管理唯一所有者与代次；生产者先确认槽位可复用、取得所有权，再写 payload，最后对该槽就绪序号做 release 发布。消费者必须 acquire 读到对应代次的就绪状态，才能读 payload；读完后再 release 标记空闲，下一轮生产者 acquire 确认后才覆盖。只 atomicAdd 尾指针就允许消费，会读到尚未写完的数据。
>
> 协议还要处理满／空、环绕和滞后的预留者。不能先取号，遇到队满就随意放弃，留下永远不会发布的洞；序号位宽与复用规则要防止旧状态被误当成新一轮。原子操作本身只保护对应对象，`volatile` 或单独一个 fence 不能代替完整发布协议。
>
> 同一 block 内可用 block scope；不同 block 在同一 GPU 上通信至少要 device scope；CPU／GPU 或跨 GPU 还需要 system scope，以及双方可访问、支持相应系统级原子的内存和平台条件。双方的 scope 都必须覆盖对方；`__syncthreads()` 不能同步整个 grid。
>
> 内存顺序正确仍可能死锁。普通 grid 不保证所有 block 同时驻留，若消费者占满资源自旋等待尚未运行的生产者，就可能永远不前进。我会优先使用非阻塞 try 操作、分阶段 Kernel／事件依赖，或明确资源与进度契约的 persistent／cooperative 方案。persistent 本身不是保证；cooperative launch 也要满足支持条件和资源限制。CPU 只忙等标志同样不能替代保证设备进度的 CUDA 交互协议。
>
> 最后分别验证线性化／FIFO、每项恰好消费一次、容量边界和压力下的进度；线程安全不能直接等同于 lock-free 或高性能。

发布和 scope 依据：[libcu++ Memory Model 的消息传递示例](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/memory_model.html#example-message-passing)、[`cuda::atomic` 范围与 CPU／GPU 条件](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/synchronization_primitives/atomic.html)。调度进度依据：[CUDA C++ Execution Model](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cuda-cpp-execution-model.html)。上述官方文档核验于 2026-11-08；未运行队列实验，不声称已验证某份实现。
