## 1. 框架组职责与分工

### 1.1 问题与现场细节

面试官问组内定位、主要职责，以及与算子、Runtime、编译器团队的分工。原答说明自己负责 PyTorch／vLLM 接入、精度与性能、客户交付，底层由其他团队承担。这里是职责题，不重写自我介绍。

### 1.2 原回答的优点与不足

分层较清楚，也没有把所有底层工作归为己有。可以进一步把“适配”落到本人修改的对象、交给其他团队的输入和验收责任，而不只按组织名称划线。底稿没有代码证据，不能据此判断独立完成了整个后端。

### 1.3 更好的回答方式与参考回答

按“组内定位 → 本人代码范围 → 团队协作 → 结果验证”组织，与已确认的安霸职责口径保持一致。Conv3D 在这里简短举例，具体定位与优化留到第 2 题展开。

> 我所在的是框架组，主要负责自研芯片上的 PyTorch 和上层推理框架适配。我个人的工作以模型接入、精度对齐和性能优化为主，也会处理执行过程中涉及的 PyTorch 后端接口和数据拷贝问题。
>
> 具体到代码，我会修改模型执行逻辑、权重映射、缓存组织和 Tensor 布局，以及框架与设备算子之间的调用接口。遇到问题时，我会先从模型的输出、显存或性能表现入手，提取实际输入，缩小到可以独立复现的模块，再确定需要修改哪一层。
>
> 算子团队主要负责 Kernel 内部的计算和访存实现，Runtime、驱动和编译器也有对应团队。我会提供实际 Shape、dtype、数据布局、复现输入和参考结果，与他们共同确定接口和修改方案；框架侧的调用适配和接入由我负责。
>
> 修改完成后，我会先做局部数值或功能对照，再回到模型验证精度、显存和性能。客户现场的问题也会整理成复现案例和回归用例，并与交付团队协作处理。

需要用一句话举例时，可以接：

> 比如 Conv3D 优化中，我负责问题复现、输入布局分析、模型调用调整和初始化时的权重展平，算子同事负责专用 Kernel 的读取与计算，之后再一起验证算子结果和模型表现。

职责依据：[多模态项目口述](../../自我准备/projects/multimodal-inference-project.md#project1-oral-baseline-20260902)、[Conv3D 案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)、[GLM 项目档案](../../自我准备/projects/GLM5-3-flash-project.md)及[异步 D2H 项目](../../自我准备/projects/async-d2h-project.md)。使用当前已确认的经历准备新回答，不把后补项目倒填为现场已经讲出的内容。

## 2. Conv3D 的 OOM 与首 token 优化

### 2.1 问题与现场子追问

面试官要求解释多模态模型 OOM、首 token 慢的定位与优化，并追问具体算子逻辑及协作。原答联系小通道、末维对齐和布局，明确底层算子由同事实现。底稿中的卡数、显存和 `512 bytes／256／1280` 未统一，不用它们还原精确配置。

### 2.2 原回答的优点与不足

因果方向和职责边界值得保留。不足是没有把逻辑 Shape、实际分配、元素数与字节数分开，也没有完整说明变换等价性及测量口径。底稿“整体显存扩大数百倍”属于过度概括，不能作为本人已经说错的确定事实。

### 2.3 更好的回答方式

采用同一个已确认的 Conv3D 案例，与[寒武纪第 3、4 题](寒武纪-日期未确认.md#cb-q3)及[安霸第 7 题](安霸半导体-日期未确认.md#q7)保持事实一致。寒武纪版本提供完整的定位与布局解释，安霸版本补清个人分工；本题突出重复补齐怎样同时增加物理存储和数据搬运，再分别报告 OOM、算子精度、图片模型回归与 TTFT 结果。后补项目事实用于当前答法，不倒填成现场已全部展示。

### 2.4 参考回答

> 我用 Qwen2.5-VL 的 Conv3D 优化举例。最初是 32B 模型处理视频时出现 OOM，调用栈指向视觉编码器里的 Conv3D。我提取了实际输入形状，构造独立单例，再把重排操作从 Conv3D 内部移到调用前，通过显存快照观察到重排后显存明显增长。
>
> 这个 Conv3D 用来完成视觉块的 patch embedding。原始输入已经按视觉块展平成二维，每个块包含三个通道、两个时间位置，以及十四乘十四的空间元素，共一千一百七十六个元素。原来的路径先用 view 将它解释成五维，再生成通道末置的新存储。view 本身没有复制那块大数据，显存增长发生在后面的重排和补齐。
>
> 因为通道只有三个，而后端对物理最内层有对齐要求，所以每个时间、空间位置上的小通道段都要分别补齐。这既增加了实际存储，也让后续处理搬运大量无效数据，因此会同时带来容量和访存方面的开销。
>
> 我的修改是保留原来的二维输入，沿用二维的 Host 到设备拷贝路径，并在模型初始化时，把卷积权重按相同顺序展平，再把原来的维度信息传给专用 Conv3D。算子同事配合修改读取和计算。二维末维仍然需要补齐，但避免了对大量只有三个元素的小段重复补齐。
>
> 我负责问题复现、布局分析、模型调用和权重布局调整，Kernel 内部实现由算子同事负责。正确性上，输入和权重必须按相同顺序展开，保持窗口内元素的对应关系。之后用同一份 BF16 输入和权重对照 CPU Conv3D，再回到模型验证。
>
> 修改之后：在已验证的输入范围内，观察到原来的大规模临时张量和 OOM 现象消失；在 Qwen2.5-VL-32B 的十个图片测例中，专用算子路径与 CPU Conv3D 参考路径生成的 token 序列一致。性能方面，单并发下，这组图片请求优化前后的平均首 token 延迟从分钟级降到了五秒以内，这是模型布局与专用算子共同修改后的结果。
>
> 视频方面，完成了视频形状的算子单测，并使得32B模型能够处理视频输入。

### 2.5 现场追问：算子内部怎样计算，你与算子同事怎样分工？

> 我能具体展开的是输入、权重和输出之间的接口约定。输入的每一行对应一个视觉块，权重的每一行对应一个输出通道，两边按相同的通道、时间、行、列顺序展平，保持元素配对。Kernel 内部怎样分块、怎样安排 SRAM 和计算，由算子同事实现；我负责模型侧修改、接口接入和数值与模型验证。

事实依据：[Conv3D 案例卡 F1–F6](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)。单算子结果在约定容差内通过；十个图片测例每例一次请求，生成配置为 `temperature=0`、随机种子 `1234`。TTFT 取算术平均，计时从客户端发送请求到收到首个生成 token，不包含模型加载和预热。CPU Conv3D 是正确性参考，不自动视为性能比较的基线；布局与 Kernel 按联合结果报告，不把局部补齐倍率当作整模显存倍率。具体分配证据、测试配置和接口范围继续使用[核查项 C009–C011](实机核查清单.md#qwen25-vl)。

## 3. 小 batch MatMul 与权重预排布

### 3.1 问题与现场细节

面试官问另一客户模型的优化是否与 Conv3D 类似。原答讨论小 batch MatMul、加载期权重重排与 NZ 类比；模型专名和 bank conflict 的原话仍不确定。

### 3.2 原回答的优点与不足

识别权重读取压力、将转换放到加载阶段，是合理的工程思路。格式名称不能证明瓶颈：NZ 类比不代表自研平台使用完全相同的地址映射，也不能据此确定 HBM、DMA 或片上 bank 哪一层受限。

### 3.3 更好的回答方式与参考回答

按“发现热点 → 判断权重读取压力 → 调整物理布局 → 加载期预处理 → 验证结果”组织。与 Conv3D 案例相比，本题更强调静态权重怎样被反复使用。当前事实采用[ECG 布局案例卡](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)。

> 这个项目也涉及布局调整，不过重点是静态权重的读取。客户的 ECG 多模态模型基于 Transformers 运行。在完成 Host 路径、小 Shape 计算和部分融合优化后，第二轮 Profile 仍然显示，Decode 阶段的小 batch 矩阵乘占据了主要耗时。
>
> 小 batch 时，同一块权重能被这一轮计算复用的次数比较少，权重读取相对于计算的开销就比较突出。我结合实际 Shape、数据类型和读写量做了初步估算，再结合 Profile，把后续排查重点放到权重访问上。进一步分析发现，原来的权重布局与 Kernel 的分块读取顺序不匹配。
>
> 我们采用了 blocked Col-major 的布局：Tile 内部保持行优先，Tile 之间按列优先排列，Tile 大小没有改变。这样让权重的物理存放顺序更适合对应的分块读取。数学上仍然计算同样的矩阵乘，调整的是数据表示和消费它的访问方式。
>
> 我在 PyTorch 框架侧定义了相应的 Tensor 布局变换操作并注册成算子，并在模型加载权重后的处理阶段完成预排布。转换后不再保留原布局权重，后续相关线性层的 Prefill 和 Decode 都复用新表示，避免每次推理重新转换。这里处理的是静态参数权重，不包括 QKᵀ 等两个动态输入之间的矩阵乘。底层 Kernel 的访存实现由算子与硬件同事配合完成。
>
> 验证时，我先在同一自研芯片上，对比普通布局和预排布两条 MatMul 路径，再比较模型输出。在已执行的测试范围内，MatMul 输出和模型 logits 逐元素数值相等，生成的 token 也一致。
>
> 性能结果按阶段报告：项目初始的完整请求耗时约为三十到四十秒，经过常规优化降到二十秒左右，再经过权重预排布与算子协作，降到二十秒以内。前面几项优化和后面的布局修改都有贡献，所以不能把整个过程的收益都归给权重预排布。

小 batch 下权重复用与算术强度的关系可对照 [NVIDIA 矩阵乘性能指南](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html)。它支持分析方法，不替代自研后端的实际 Profile、缓存复用和带宽证据。

这组“20 秒以内”是原 Transformers 栈的完整请求耗时，不是 TTFT：单请求，优化前后各测 10 次取平均，包含首次运行和图像预处理，不包含请求前完成的编译与初始化。预排布需要与 Kernel 的读取约定配套，不能概括成单独调用一次 `transpose` 即可加速。当前保留“布局与分块读取顺序不匹配”的结论，具体存储层级的 bank conflict、有效带宽或布局独立收益不补报。

这段采用已确认的项目资料准备当前口述，不把底稿待确认的“ECG”专名升级为本场已准确听辨的词。预排布后来移植到 vLLM，不将原 Transformers 的秒数作为 vLLM 测量结果；具体实现与记录沿用[核查项 C027](实机核查清单.md#c027)、[C028](实机核查清单.md#c028)。

## 4. 异步拷贝导致的偶发输出异常

### 4.1 问题与现场细节

面试官追问乱码、EOS 异常怎样定位到同步问题。底稿记载候选人将“内存屏障”改述为异步拷贝／流同步；没有原简历，不能进一步评价整份简历。增加 Dump 后异常改变是定位线索，不是独立的竞态证明。

### 4.2 原回答的优点与不足

保留输出比对、控制异步等级和检查 Host 准备的路径。需要补充哪种完成事件保护哪块缓冲、拷贝何时入队，以及最终修复是否撤掉诊断同步后仍成立。底稿补出的锁页双缓冲和“无未知项”不采用。

### 4.3 更好的回答方式与参考回答

以[寒武纪第 5 题](寒武纪-日期未确认.md#cb-q5)为主版本，突出本场“怎样定位到同步问题”的提问。Dump 与阻塞对照帮助缩小范围，CPU 准备、H2D 提交与消费之间的依赖缺口解释根因，恢复异步后的回归验证修复。项目事实沿用[异步 H2D 案例卡](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)。

> 这个问题发生在 Qwen3-32B 使用 vLLM V1 的时候。自研后端启用异步调度与执行后，客户现场低概率出现乱码、空回复和重复输出。我主要负责请求重放、问题定位、框架和后端层的修复，以及修复后的验证。
>
> 我先固定输入和生成参数，对同一请求重复执行，寻找第一个发生分叉的 token，再比较对应的 logits 和中间 Tensor。这样可以尽量找到最早出现差异的位置，避免被后面不断传播的差异干扰。
>
> 排查时发现，加入较多 Tensor Dump 后，异常反而不容易复现。我怀疑诊断操作改变了执行时序，就进一步通过开关分别控制拷贝路径。单独把异步 H2D 改为阻塞后，重放中的异常也消失了。这可以作为临时规避方案，也让我把排查范围收窄到输入准备、拷贝提交和消费之间的依赖。
>
> 后来确认，这条 H2D 路径分成两段：后台任务先在 CPU 上把原始 Tensor 补齐成符合后端布局要求的临时 Tensor，然后才提交到设备的异步拷贝。原来的消费者只等待设备拷贝流，没有覆盖前面的 CPU 准备和 H2D 提交。
>
> 这样就存在一个时间窗口：CPU 还在做 Padding，目标 H2D 尚未提交，消费者已经开始等待设备流。此前已提交的任务完成后，等待就可能结束，但真正需要的那次拷贝还没入队。下游随后开始读取设备数据，就可能读到尚未完整写入的内容。
>
> 修复是在框架和后端层补齐 Padded Tensor 的异步标记与等待。依赖上分成两步：消费 Kernel 入队前，先确认 CPU 准备已经完成，H2D 和对应的完成事件已经提交；再让消费流等待拷贝完成，之后才能使用这份数据。同时还要保证原始输入、Padding 临时缓冲和设备目标，在各自的异步访问结束前保持有效。这次复用了已有 Runtime 能力，没有修改 Runtime。
>
> 验证时，我恢复了原先触发异常的异步配置，撤掉临时阻塞和额外诊断等待，再把现场收集的一百六十八条请求连续重放五轮，共八百四十次执行，没有再观察到原来的异常。这个结果说明修复在这批请求和配置下有效，不能直接扩大成所有负载都不会再出现问题。

两场统一采用的依赖顺序是：`CPU Padding 完成 → H2D 已提交 → 设备拷贝完成 → 下游消费`。修复段沿用寒武纪已选定的两步依赖表述；具体任务通知、事件记录和等待入口与历史代码的对应关系，继续按[核查项 C013–C015](实机核查清单.md#async-h2d)核对，不把原项目回归结果当作某套新增接口实现已验证的证据。

### 4.4 扩展追问：已经有设备 Event，为什么还需要前面的等待？

> 因为消费者开始等待时，后台可能还没有完成 Padding，拷贝和事件也就还没提交。先确认准备与提交完成，才能保证等待对象已经建立；之后的设备事件才负责保证拷贝完成后再消费。

该追问是补充准备，不作为现场已问的独立问题。需要比较 CPU 通知、设备流等待与 CPU 等设备完成时，可继续使用[寒武纪第 5.5 节的同步方式说明](寒武纪-日期未确认.md#cb-q5-sync)。CUDA 的[异步执行说明](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)仅作通用对照，不认定自研后端使用同名 API。168 条请求的 5 轮重放不是 840 个独立场景；没有同条件修复前异常统计或性能对照时，不补报失败率降幅或零开销结论。

## 5. Chunked Prefill

### 5.1 问题与原回答

面试官问为什么需要 Chunked Prefill。原答说明长 prompt 分块、在调度中穿插 Decode，避免生成请求等待过长。这一主旨正确，不需要为了复盘强行增加错误。

### 5.2 需要补清的条件

口述先用长 Prefill 影响正在生成的请求这一场景说明动机，再解释每轮预算、历史 KV 的具体读取方式，以及 TTFT、ITL 和吞吐之间的取舍。按本人 2026-11-16 确认的说明，明确后续 chunk 在每个 Attention 层读取该层历史 token 的 K、V，而不是只概括为“继续访问上下文”。

### 5.3 更好的回答方式与参考回答

> Chunked Prefill 主要解决长输入影响其他请求生成的问题。比如服务里已经有一批请求在逐 token 输出，这时来了一个很长的 prompt。如果一次把它的 Prefill 全部执行完，单轮计算可能持续很久，正在生成的请求就要等待，表现为输出 token 之间出现较长停顿。
>
> Chunked Prefill 会把这条长输入的 Prefill 分到多轮调度中，每轮只处理其中一部分。以 vLLM 的这类策略为例，可以先安排 Decode 请求，再用本轮剩余的 token 预算处理 Prefill；Prefill 的 chunk 也可以与 Decode 请求组成同一个 batch。这样能够限制单轮 Prefill 的工作量，让生成请求持续获得执行机会。
>
> 处理后面的 chunk 时，每个 Attention 层会读取前面 chunk 已经缓存的 K 和 V。当前 token 用自己的 Q，对历史 token，以及当前块中不晚于自己的 token 做注意力计算，再汇聚它们的 V。这样就能利用前面的上下文，同时避免重新计算历史 token 的 K、V；位置编号也继续沿用整条输入中的原始位置。
>
> 块大小需要取舍。块较小，通常有利于缩短单轮执行时间、改善 Decode 的 token 间延迟，但会增加调度和执行开销，也可能让长请求更晚完成 Prefill、拿到首 token。块较大，可能提高 Prefill 效率，但又会增加对 Decode 的影响。因此我会用实际的长短请求混合负载，比较 TTFT、token 间延迟和吞吐，再选择预算。

### 5.4 后面的 chunk 具体读取什么？

以普通因果 Self-Attention 为例，输入 `A B C D E F` 分成 `ABC` 和 `DEF` 两个 chunk。处理第二块时，每个 Attention 层的读取关系如下：

| 当前 token | 用哪些 K 计算注意力权重 | 用哪些 V 做加权汇聚 |
| --- | --- | --- |
| D | A～D 对应的 K | A～D 对应的 V |
| E | A～E 对应的 K | A～E 对应的 V |
| F | A～F 对应的 K | A～F 对应的 V |

`ABC` 的 K、V 来自该层历史缓存，`DEF` 的 K、V 在当前块的计算中产生。因果 Mask 保证 D 看不到 E、F；每一层读取的是自己这一层的历史 KV，不复用其他层的 KV。

### 5.5 分块是否也能解决长上下文显存不足？

> 分块可能降低一次执行所需的临时激活和工作区，但普通 full attention 仍然需要保留历史 KV。因此，如果最后要保存的 KV 本身就超过容量，单靠 Chunked Prefill 解决不了，还需要调整准入、缓存配置或并行方案。

`max_num_batched_tokens` 是一轮调度的总 token 预算，包含 Decode 和 Prefill 的工作量，不等于每条请求固定的 chunk 长度，也不是请求的最大上下文长度。

调度方式与预算取舍见 [vLLM v0.26.0 Chunked Prefill 说明](https://docs.vllm.ai/en/v0.26.0/configuration/optimization/#chunked-prefill)，分块 Prefill 与生成请求共同调度的思路见 [Sarathi-Serve](https://arxiv.org/abs/2403.02310)。参考版本用于核验机制，不作为历史项目版本；KV 示例限定普通因果 Self-Attention，不将所有递推或混合模型的状态都当作逐 token K/V。

## 6. 多轮图文与 embedding 对应

### 6.1 问题与现场子追问

面试官问多张图片怎样进入多轮上下文，并再次确认插入关系。原答介绍视觉编码、投影及文本占位位置；patch size、视觉 token 数和具体模型版本未可靠确认。

### 6.2 原回答的优点与不足

总体流程合理，但不能将一个模型的占位与投影方式推广到所有 VLM。需要说明占位符扩展、图像顺序和特征数量的对应，而不只是说“把 embedding 拼起来”。

### 6.3 更好的回答方式与参考回答

> 我以 Qwen2.5-VL 这类把视觉特征并入语言模型输入序列的模型为例。首先按照模型的对话模板组织多轮消息，保留用户、助手，以及文本和图片的出现顺序。处理器负责文本分词、图片预处理，并生成需要的图像尺寸或网格信息。
>
> 图片经过视觉编码器，以及模型规定的特征合并或投影模块，得到一组与语言模型输入维度匹配的视觉向量。一张图片通常对应多个视觉位置，数量取决于图片预处理和模型结构，不能固定理解成一张图只有一个 token。
>
> 构造语言模型输入时，文本位置使用文本 embedding，图片对应的占位区间填入这张图的视觉 embedding。多张图片要分别匹配各自的区间：图 A 的特征填到图 A 的位置，图 B 的特征填到图 B 的位置，不能只检查所有图片的特征总数是否相等。
>
> 多轮对话也是沿用这个对应关系。保留在上下文中的历史图片、问题和助手回答，仍然按照对话顺序排列，再接上新一轮的图片和问题。同时按模型要求构造位置编码和 Attention Mask。我在适配时会逐图核对特征数量、顺序、占位范围和位置映射，再检查完整模型的输出。

依据：[vLLM 多模态接入说明](https://docs.vllm.ai/en/stable/contributing/model/multimodal/)。已有个人范围见[多模态项目口述](../../自我准备/projects/multimodal-inference-project.md#project1-oral-baseline-20260902)，本题不新增具体适配版本。

主回答中的“处理器”概述前端的分词与多模态预处理流程；具体组件分工、执行阶段及向量填入方式见[第 6.4 节](#jd-q6-mm-input)，缓存复用条件见[第 6.5–6.7 节](#jd-q6-mm-cache)。

### 6.4 口述补充：processor 在哪里，图片怎样变成输入向量？

这些是通用机制准备，不作为现场已问的独立题目或本人已经完成的全部实现。以下以 Qwen2.5-VL 这类将视觉特征并入语言模型输入序列的模型为例，源码依据为本地固定 vLLM V1 快照 `d7ada3aace051fecec553c185225db2259c2ac6a`。

> 在常规 vLLM V1 服务里，API 收到图文消息后，先经过前端输入处理。对话模板、tokenizer 和多模态 processor 共同完成消息组织、文本分词和图片预处理。这一阶段通常在 Host 侧完成，产生 token ID、图片张量、网格信息，以及每张图在输入序列里的占位区间，然后再将请求交给调度引擎。
>
> 图片真正变成视觉向量，是 Worker 执行模型时完成的。以 Qwen2.5-VL 为例，Patch Embedding 先把视觉块映射成初始特征，其中使用了 Conv3D；Vision Transformer 再提取图像特征，Patch Merger 合并相邻位置，并通过投影得到与语言模型隐藏维度匹配的一组向量。
>
> 视觉位置的数量，可以由前端根据预处理后的网格和模型的合并规则预先计算。举一个单张静态图的例子：假设预处理后是二百二十四乘二百二十四，空间 patch 是十四乘十四，再按二乘二合并，那么二百五十六个视觉块会得到六十四个视觉向量。前端相应安排六十四个图像占位位置，Worker 随后算出要填入的向量。
>
> Worker 构造语言模型输入时，文本位置使用词嵌入，图像占位位置则填入对应的视觉向量。替换的是 inputs_embeds 中对应位置的向量，不是把图片转换成文字 token ID。多图时，每张图的特征数量和顺序都必须与各自的区间对应；两张图的数量相同，也不能交换填入位置。

数字示例假设单张静态图对应一个时间网格，仅用于解释数量关系，不作为个人项目的实际输入。服务前端的处理见 [Renderer](../../../推理框架/references/vllm/vllm/renderers/base.py)和[多模态处理设计](https://docs.vllm.ai/en/v0.26.0/design/mm_processing/)；视觉编码及 merger 见 [Qwen2.5-VL 实现](../../../推理框架/references/vllm/vllm/model_executor/models/qwen2_5_vl.py)，向量填入见 [embed_input_ids](../../../推理框架/references/vllm/vllm/model_executor/models/interfaces.py)与[特征合并实现](../../../推理框架/references/vllm/vllm/model_executor/models/utils.py)。

### 6.5 口述补充：视觉特征缓存有什么复用条件，怎样复用？

> 当前核对的 vLLM V1 实现支持这种复用，不过要先区分三层缓存。Processor 输出缓存保存图片预处理结果和网格等数据；视觉特征缓存保存视觉编码器及 merger 的输出；语言模型前缀 KV 缓存保存语言模型各层已经计算好的 K、V。它们命中后省掉的计算不同。
>
> 对前面这类 Qwen2.5-VL 路径，视觉编码本身不依赖问题文本，所以同一张图换一个问题，仍然可能复用视觉向量。前提是图像输入、影响结果的预处理条件，以及视觉编码器和 merger 的权重与配置一致。如果使用影响视觉分支的 LoRA，也需要区分；对应缓存条目还要存在，输出规格也要匹配。
>
> 实现上，框架通过多模态 identifier 查找缓存。默认会根据输入内容和相关处理参数生成标识；如果使用客户端提供的 UUID，调用方就要保证这个标识确实代表相同的有效输入。命中后，调度器不再安排对应的视觉编码，Worker 直接取出缓存向量，把本轮需要的部分填入输入位置；未命中时才执行视觉模型，并保存结果。
>
> 这个实现可以在不同请求之间共享同一个图像条目。请求结束后，没有引用的条目可以暂时保留，空间不足时再淘汰。因此，后续请求能否命中还取决于它是否能访问这份缓存，以及条目是否仍然有效；不能把它当作跨实例、跨重启自动保留的会话状态。

多模态标识的输入因素见 [ProcessorInputs.get_mm_hashes](../../../推理框架/references/vllm/vllm/multimodal/processing/inputs.py)，视觉 LoRA 的标识处理见 [InputProcessor](../../../推理框架/references/vllm/vllm/v1/engine/input_processor.py)。跨请求引用与淘汰由 [EncoderCacheManager](../../../推理框架/references/vllm/vllm/v1/core/encoder_cache_manager.py)管理，结果 Tensor 及读取位于 [GPUModelRunner](../../../推理框架/references/vllm/vllm/v1/worker/gpu_model_runner.py)。`mm_processor_cache_gb` 控制的是 processor 输出缓存，不是上述各层缓存的统一开关，见[配置定义](../../../推理框架/references/vllm/vllm/config/multimodal.py)。

### 6.6 口述补充：图片位置的语言模型前缀 KV 怎样复用？

> 图片位置和文本位置一起进入语言模型，因此它们的 KV 属于同一条输入序列的前缀缓存，并不是另建一份只按图片查找的 KV。复用时，要保证到命中边界为止的前缀计算相同，包括文本 token、图片内容、图像位置，以及相关模型和 LoRA 条件。
>
> 同一张图片并不足以保证它的语言模型 KV 相同。图像向量经过语言模型各层处理后，会受到前面上下文的影响。因此，图像位置之前的文本或其他图片已经不同，就不能只凭图片相同，把旧的那段 KV 直接接过来。
>
> vLLM 用块哈希识别这些前缀，哈希包含前序块、本块 token，以及多模态标识等额外信息。图片占位 token 的 ID 本身不能代表图片内容，因为不同图片可能使用相同的占位 ID。请求还要允许读取前缀缓存，相关缓存块仍然可用；设置了 cache salt 时，也需要在同一个缓存隔离范围内。实际命中长度仍受缓存块粒度和覆盖范围限制。
>
> 命中后，框架把已有 KV 块接入新请求的块映射，推进已计算 token 的边界，只对剩余部分执行 Prefill。后续 Attention 读取的是复用的历史 KV，加上当前请求新计算出来的 KV，不需要重新计算已经命中的那段前缀。

块哈希中的多模态标识及位置关系见 [KV 缓存哈希实现](../../../推理框架/references/vllm/vllm/v1/core/kv_cache_utils.py)，前缀查找见 [KVCacheManager](../../../推理框架/references/vllm/vllm/v1/core/kv_cache_manager.py)；图片占位符与图片哈希的区别可对照 [vLLM 前缀缓存设计](https://docs.vllm.ai/en/v0.26.0/design/prefix_caching/)。模型权重或相关计算条件改变后不能沿用旧缓存；缓存命中也不等于服务自动保存了完整对话，请求仍需提供或引用所需上下文和媒体信息。

### 6.7 口述补充：两类缓存怎样配合？

> 如果只有视觉特征命中，Worker 可以直接拿到图像向量，但当前上下文在语言模型里的 Prefill 仍然需要执行。视觉编码结果相同，并不代表它进入不同文本上下文后产生的各层 KV 也相同。
>
> 如果语言模型的前缀 KV 已经覆盖整个图像区间，这一段就不需要重新做 Prefill，本轮也不需要为这些位置重新取得输入向量。因此，调度器可以跳过对应的视觉编码，即使那张图的视觉特征条目已经被淘汰，也未必需要重算。
>
> 例如，两条请求都是同一个前缀、同一张图，只修改图像后面的问题，那么已有的共同前缀块可能被复用。如果修改的是图像之前的文本，视觉特征仍然可能命中，但图像位置的语言模型 KV 就不能按原前缀直接复用。哪一段能跳过，要看实际缓存命中边界。

在 Chunked Prefill 中，若本轮仍需要计算一部分图像位置，Worker 会从视觉缓存取对应的向量切片；没有可用结果时，再按模型规定执行该图片的视觉编码。不能据语言模型的分块方式，直接假定视觉 Transformer 也能独立编码任意切出的图像片段。相关窗口判断与编码安排见 [Scheduler](../../../推理框架/references/vllm/vllm/v1/core/sched/scheduler.py)，向量切片见 [GPUModelRunner](../../../推理框架/references/vllm/vllm/v1/worker/gpu_model_runner.py)。这些是固定源码的通用实现说明，历史项目的实际版本、缓存配置和本人改动继续按[核查项 C029](实机核查清单.md#c029)核对。

## 7. PrivateUse1 机制

### 7.1 问题与原回答

面试官问 PyTorch 的 PrivateUse1 如何抽象第三方后端。底稿记载尚在研究，没有展开。合理结论是这段未展示机制解释，不能扩大为没有框架工程能力，也不能照搬底稿“PyTorch 2.0 才引入”的说法。

### 7.2 更好的回答方式

复用[寒武纪第 6 题](寒武纪-日期未确认.md#cb-q6)的机制说明，但调整开头：寒武纪先问为什么做插件化，本题直接问 PrivateUse1 怎样接入第三方设备。因此先解释设备类型与分发入口，再用“创建张量、拷贝数据、执行加法”展开。机制保持一致，个人工程进度在第 8 题按实际实现另行说明。

### 7.3 参考回答

> PrivateUse1 是 PyTorch 为第三方设备预留的设备类型和算子分发入口。后端可以通过扩展库，把自己的设备能力和算子实现注册进来，让上层继续使用 PyTorch 的 Tensor 和算子接口。
>
> 我们可以从“创建张量、拷贝数据、执行加法”这条链来考虑如何接入第三方设备。创建设备 Tensor 时，后端需要接好设备内存分配，以及 Tensor 的形状、布局和存储管理；把 CPU 数据拷过去时，还需要实现数据传输，并保证异步拷贝与后续消费的依赖正确。PrivateUse1 提供接入位置，这些具体能力仍然由后端实现。
>
> 算子这边，例如两个 Tensor 都在这个设备上，调用 `torch.add(a, b)`。PyTorch 已经定义了加法的接口，插件可以通过 `TORCH_LIBRARY_IMPL`，把自己的实现注册到 `aten::add.Tensor` 的 PrivateUse1 分发项上。调用时，Dispatcher 根据输入 Tensor 的 dispatch key，以及当前线程的运行状态和 key 优先级，找到相应实现。必要时还会经过 Autograd 等包装层，再继续分发到设备实现。
>
> 设备实现负责处理参数、Tensor 布局和输出分配，再调用芯片算子库与 Runtime 提交计算。设备选择、Stream、Event 和资源生命周期等接口，也需要与 PyTorch 的使用方式衔接起来。
>
> 给 PrivateUse1 改成设备自己的名称、注册 Python 设备模块，主要是让用户更方便地访问后端。是否真正支持模型运行，还要看 Tensor、算子和目标功能是否接通。训练、自动混合精度、分布式和图编译，都需要分别检查相应支持，不能只凭设备名称已经可用，就认为后端适配完成了。

设备接入与注册入口见 [PrivateUse1 官方教程](https://docs.pytorch.org/tutorials/advanced/privateuseone.html)，分发和包装层的关系见 [Dispatcher 教程](https://docs.pytorch.org/tutorials/advanced/dispatcher.html)。设备名称、设备标识和具体实现分别说明；Dispatcher 根据有效 key 集合选路，不概括成固定的“设备 → dtype → shape”分发层级。上述是机制回答，不声明本人已经独立实现全部模块；具体项目范围与调用链沿用[核查项 C016、C017](实机核查清单.md#pytorch-plugin-dispatch)。

## 9. Tensor 的 Host／Device 描述

### 9.1 问题与原回答

面试官问 Tensor 的 Host／Device“描述符”。底稿只记录不太了解，且没有澄清这里指 PyTorch 对象还是设备 Kernel descriptor。因此参考回答先说明层级，不补成一个确定的原题。

### 9.2 更好的回答方式

先区分框架管理 Tensor 的对象与后端算子的 descriptor。以通常的稠密设备 Tensor 为例，说明 Host 侧元数据对象、Storage 及底层缓冲的关系，再用转置解释为什么多个 Tensor 能共享数据、为什么设备算子仅有数据指针还不够，最后补充异步执行时的生命周期。

### 9.3 参考回答

> 我会从两个层面理解：一层是 PyTorch 怎样管理 Tensor，另一层是后端怎样把 Tensor 转换成设备算子需要的参数。先以普通的稠密设备 Tensor 为例。
>
> 在 PyTorch 的 C++ 层，Tensor 可以理解为一个句柄，内部引用 TensorImpl。TensorImpl 保存这个张量的形状、stride、storage offset、数据类型和分发相关信息，并关联它的 Storage。其中，stride 表示沿某个维度移动一个位置，需要跨过多少个元素；storage offset 表示这个张量从底层存储的哪个位置开始。
>
> Storage 的底层实现 StorageImpl 管理数据缓冲，通过 DataPtr 保存数据地址、设备信息，以及释放数据所需的上下文和方法。通常由对应设备的 allocator 提供分配能力。这些管理对象位于 Host 侧，实际元素可以放在设备内存里。因此，CPU 可以读取张量的形状和布局，但持有设备地址，并不意味着 CPU 能直接读取那个地址里的数据。
>
> 把描述信息与数据存储分开，可以让多个 Tensor 共享同一份数据，同时采用不同的形状和访问方式。例如，对一个普通二维张量执行转置，可以创建新的视图，只调整形状和 stride，不需要马上搬动设备上的元素。
>
> 真正调用设备算子时，后端再根据 Tensor 的数据地址、形状、stride 和数据类型，组织 Kernel 参数或算子库要求的 descriptor。具体结构由后端决定，不需要把完整的 TensorImpl 复制到设备。这里必须正确处理布局和偏移，否则即使数据地址正确，算子也可能读到错误的元素。
>
> 如果设备执行是异步的，还需要管理数据缓冲的生命周期。Host 侧函数返回或 Python 引用消失，都不能作为设备已经完成访问的依据。后端需要结合流依赖和 allocator 的管理，避免内存被其他操作提前覆盖。

对象关系依据本地固定 PyTorch `0bd89deb431509d893177a84cfa4768aa0399809` 的 [TensorImpl](../../../PyTorch/references/pytorch/c10/core/TensorImpl.h)、[StorageImpl](../../../PyTorch/references/pytorch/c10/core/StorageImpl.h)和 [Allocator／DataPtr](../../../PyTorch/references/pytorch/c10/core/Allocator.h)。以上限定普通稠密设备 Tensor，不将这套物理表示直接外推到 meta、稀疏等全部 Tensor。

<a id="jd-q9-transpose"></a>

### 9.4 转置例子：为什么只有数据指针还不够？

下面是解释性示例，不是个人项目测量数据。先在 CUDA 设备上创建包含 0–5 的连续二维张量，再交换它的两个维度：

```python
x = torch.arange(6, device="cuda").reshape(2, 3)
y = x.transpose(0, 1)
```

| 对比项 | `x` | `y` |
| --- | --- | --- |
| shape | `(2, 3)` | `(3, 2)` |
| stride | `(3, 1)` | `(1, 3)` |
| storage offset | `0` | `0` |
| 底层 Storage | 两者共享 | 两者共享 |
| 逻辑上的内容 | `[[0,1,2], [3,4,5]]` | `[[0,3], [1,4], [2,5]]` |

转置后，设备内存中的元素仍按原来的顺序存放。变化的是怎样沿着这块内存访问元素。因此，后端如果把 `y` 当成普通连续的 `3×2` 张量读取，就会错误地理解为 `[[0,1], [2,3], [4,5]]`。后端必须使用正确的 stride，或者在算子要求连续输入时进行相应转换。转置视图共享数据与 `contiguous()` 的行为见 [PyTorch 2.15 Tensor Views 文档](https://docs.pytorch.org/docs/2.15/tensor_view.html)。

### 9.5 从框架对象到 Kernel 参数，以及异步生命周期

固定源码中的 [getTensorInfo](../../../PyTorch/references/pytorch/aten/src/ATen/cuda/detail/IndexUtils.cuh)会从 Tensor 提取数据指针、维数、各维大小和 stride，构造供部分 CUDA Kernel 使用的 [TensorInfo](../../../PyTorch/references/pytorch/aten/src/ATen/cuda/detail/TensorInfo.cuh)。这说明了框架管理对象怎样变成 Kernel 的输入参数，但不是所有后端共用的唯一描述符。

Host 对象释放与设备内存安全复用是两件事。CUDA allocator 可以利用流的执行顺序管理复用；跨流使用时，则需要正确记录使用关系或建立同步依赖，并不要求每次操作后都让 CPU 等待 GPU。具体语义见 [PyTorch 2.15 record_stream 文档](https://docs.pytorch.org/docs/2.15/generated/torch.Tensor.record_stream.html)。

### 10.3 更好的回答方式与参考回答

## 11. KV Cache 为什么成立

### 11.1 问题与原回答

面试官问 Attention 使用 KV Cache 加速的逻辑。原答抓住因果解码、历史 K/V 不随新 token 改变的主旨，值得保留；底稿中的复杂度扩写不能反推为本人现场说过。

### 11.2 更好的回答方式

保留原答的因果性主线，补清历史表示为什么在每一层都不受后来位置影响，再说明各层怎样复用 K/V、为什么不长期缓存 Q，以及每步仍需完成的计算。用生成过程区分本轮输入 token 与本轮预测的下一个 token，复杂度明确限定到单步 Attention。

### 11.3 参考回答

> 以普通的因果 Transformer 推理为例，在模型参数、输入前缀和位置等计算条件保持一致时，后来追加的 token 不会改变历史位置已经计算出的表示，因此历史 K、V 可以保存下来复用。
>
> 这个性质在每一层都成立。第一层中，历史位置只能关注自己和之前的位置，新追加的 token 被因果 Mask 排除，所以不会影响它的 Attention 结果。后面的归一化和前馈网络按位置处理，也不会引入未来位置的信息。因此，传给下一层的历史表示保持不变，逐层推下去，各层历史 K、V 都可以复用。
>
> 实现时，每一层分别保存自己的 KV Cache。以一次处理一个新 token 的 Decode 为例，当前层只计算这个新位置的 Q、K、V，再让当前 Q 与本层缓存的历史 K，以及当前位置的新 K 计算注意力权重，用这些权重对对应的 V 加权求和。新产生的 K、V 也加入本层缓存，供后续位置使用。
>
> 相对于每一步重新执行整个前缀，这样省掉了历史位置的重复前向计算，包括它们在各层的投影、Attention 和前馈计算。当前位置仍然需要经过所有层，也仍然需要访问历史 K、V。
>
> 通常只缓存 K、V，是因为后续位置需要历史 K 来计算注意力分数，需要历史 V 来汇总信息。历史 Q 用来计算历史位置自己的输出，处理新位置时已经不再需要，所以没有必要长期保留。
>
> 代价是缓存占用内存，而且普通全注意力每一步仍然要处理不断增长的历史 KV。因此，KV Cache 减少了重复计算，但上下文越长，缓存容量和每步的历史访问开销仍然会增加。

历史表示逐层不依赖未来位置，可以从因果 Mask 与逐位置前馈网络的结构推导出来，见 [Transformer 原论文 §3.1–3.3](https://arxiv.org/html/1706.03762v7)。这里说明计算依赖，不将不同执行路径中的浮点结果承诺为逐位一致。

<a id="jd-q11-generation"></a>

### 11.4 生成过程：什么时候产生新 token 的 KV？

假设输入是三个 token：`A、B、C`，模型接下来依次生成 `D、E、F`。以下为普通逐 token Decode 的解释性示例：

| 阶段 | 本轮送入模型的 token | 本轮新计算的 KV | 本轮结束后的 KV Cache | 本轮预测并选出的下一个 token |
| --- | --- | --- | --- | --- |
| Prefill | `A、B、C` | `A、B、C` 的各层 KV | `A、B、C` | `D` |
| 第一次 Decode | `D` | `D` 的各层 KV | `A、B、C、D` | `E` |
| 第二次 Decode | `E` | `E` 的各层 KV | `A、B、C、D、E` | `F` |

刚生成一个 token，不等于已经生成了它的 KV。Prefill 结束时，模型选出了 `D`，但缓存只包含 `A、B、C`；下一轮把 `D` 送入模型，才计算它在各层的 K、V，并预测 `E`。缓存按层维护，每层使用自己的历史结果，见 [Transformers KV Cache 说明](https://huggingface.co/docs/transformers/cache_explanation)。

### 11.5 复杂度说明

> 对单层单个注意力头，设历史长度为 n，Q、K、V 的维度都为 d，那么一次普通 Decode 的注意力打分和 V 加权求和仍然约为 O(nd)。这是单步 Attention 的成本，不能直接说整个生成过程已经变成线性复杂度。

这里计入的是当前 query 与历史及当前位置 K 的打分，以及对相应 V 的加权求和；不将它当作包含所有投影、前馈、层数和生成步数的整模成本。普通 causal Transformer 的解释不自动适用于双向编码器、不同位置语义或任意跨请求复用。若前缀、模型权重、位置规则或其他影响表示的条件改变，旧缓存不能直接沿用；跨请求共享还需要额外的身份、兼容性与生命周期检查。

概念上的追加不要求物理 Tensor 每步重新拼接，分页或预分配实现可以避免搬移旧数据。

## 12. FlashAttention

### 12.1 问题与原回答

面试官问 FlashAttention 为什么快。原答已涉及 tiling、online softmax 和避免完整矩阵物化，中途表示细节记忆不全。底稿“HBM 复杂度从二次降到线性”是技术扩写错误，不据此给现场回答扣分。

### 12.2 更好的回答方式

保留分块和在线 Softmax 主线，先说明完整中间矩阵造成的存储和 HBM 往返，再解释怎样用每行的累计量保持全行归一化。最后区分算术复杂度、中间存储和访存开销，不把减少中间矩阵物化等同于线性注意力。

### 12.3 参考回答

> FlashAttention 的主要收益，来自减少 Attention 中间数据在 HBM 和片上存储之间的反复搬运。以一次处理长度为 N 的序列为例，直接实现通常先计算 QK 转置，得到 N×N 的分数矩阵，再计算 Softmax 概率，最后与 V 相乘。如果把这些中间矩阵写入 HBM，再由后续计算读取，就会产生很大的存储和访存开销。
>
> FlashAttention 根据片上容量对 Q、K、V 分块，在片上完成局部分数计算、Softmax 状态更新和 V 的加权累积。分数块使用之后就可以丢弃，不需要保存完整的 N×N 分数矩阵或概率矩阵。
>
> 分块的难点在于，Softmax 的分母需要覆盖这一行的全部有效 Key。我们不能让每个块分别归一化，再直接把结果相加。因此，在线 Softmax 会为每个 Query 维护已经处理部分的最大分数、指数和，以及未归一化的 V 加权和。
>
> 处理新块时，如果发现了更大的最大分数，就把之前的指数和与加权和一起重新缩放，再加入新块的贡献。处理完全部有效位置后，用累计的加权和除以累计的指数和，得到最终输出。这样在数学上与整行 Softmax 等价，但浮点计算顺序不同，可能存在正常的舍入差异。
>
> 所以，FlashAttention 保持标准稠密 Attention 的计算语义，主要改善中间存储、访存和执行效率。对长度为 N、每个头维度为 d 的完整序列 Attention，主要算术量仍然是 O(N²d)。实际加速幅度还取决于序列长度、head dimension、片上容量和并行组织。

减少完整中间矩阵的物化、通过分块降低 HBM 访问，是[原论文](https://arxiv.org/html/2205.14135v2)的主线。HBM 访问量还与片上容量有关，不能笼统地说成从二次复杂度降到了线性。以上讨论普通稠密 Attention 的核心机制，不将其作为所有代际、硬件与 Kernel 的完整执行细节。

<a id="jd-q12-online-softmax"></a>

### 12.4 在线 Softmax 的更新公式

只看一个 Query，设它与 Key 的缩放后分数为 $s_j=qk_j^\top/\sqrt d$，对应的 Value 向量为 $v_j$。$d$ 是 Query 与 Key 的维度；$i$ 表示已经处理的位置，$j$ 表示新块的位置。已经处理的部分保存：

| 状态 | 含义 |
| --- | --- |
| $m$ | 已处理有效位置的最大分数 |
| $\ell$ | 指数和：$\sum_i e^{s_i-m}$ |
| $u$ | 未归一化的加权和：$\sum_i e^{s_i-m}v_i$，是一个向量 |

新块的有效位置集合记为 $B$，更新方式是：

$$
\begin{aligned}
m' &= \max\left(m,\max_{j\in B}s_j\right)\\
\alpha &= e^{m-m'}\\
\ell' &= \alpha\ell+\sum_{j\in B}e^{s_j-m'}\\
u' &= \alpha u+\sum_{j\in B}e^{s_j-m'}v_j
\end{aligned}
$$

全部有效块处理完后，输出为 $u/\ell$。公式假定这一行至少存在一个有效 Key；Mask 后的无效项不贡献求和，实际 Kernel 还需处理全 Mask 等边界。

### 12.5 重新缩放的例子

假设旧最大值是 **2**，新块出现了最大值 **4**。旧累计量使用的是 $e^{s-2}$，现在需要统一成 $e^{s-4}$，因此：

$$
e^{s-4}=e^{-2}e^{s-2}
$$

把旧的 $\ell$ 和 $u$ 都乘以 $e^{-2}$，就完成了统一，不用重新读取旧分数或逐项重算旧贡献。这也是为什么只调整分母、不调整加权和会得到错误结果。同样的累积与重标定逻辑可以对照 [Triton 的 Fused Attention 实现](https://triton-lang.org/main/getting-started/tutorials/06-fused-attention.html)；本例数字只用于解释指数换算，不是项目测量数据。

>
> 第三类是执行下发和异步协作。如果设备计算之间存在较多空闲，而 Host 在持续准备参数、提交小任务或等待同步，我会检查队列提交、批量执行、DMA 和事件依赖的支持，评估怎样减少 Host 往返和提交开销。这里需要与 Runtime 团队一起判断，哪些可以通过软件组织改善，哪些需要硬件接口或执行机制配合。
>
> 提交建议时，我会附上真实的输入形状、调用频率、有效数据量、实际搬运量，以及它在请求时间线上的影响，同时给出已经尝试的软件优化和剩余限制。这样硬件团队可以拿这些负载验证方案，而不是只根据算子名称决定增加哪种单元。
>
> 最后还要估算整模收益，并比较面积、功耗、带宽和实现复杂度。某个局部操作快很多，并不一定能明显改善请求延迟。我的重点是从框架侧提供可复现的负载和定位依据，与硬件团队一起确定值得投入的方向。

### 14.4 Amdahl 定律与收益估算

设某部分占原总时间的比例为 $f$，优化后该部分加速 $s$ 倍。在各部分不重叠、其他耗时不变的假设下：

$$
\text{总加速比}=\frac{1}{(1-f)+f/s}
$$

例如，一次执行耗时 **100 ms**，其中索引与重排占 **40 ms**。即使把这部分加速到两倍，总耗时也只是降到 **80 ms**：

$$
T_{\text{new}}=60+40/2=80\ \text{ms},\qquad
S=100/80=1.25
$$

该简化模型估计整体加速约为 **1.25 倍**。这是解释性示例，不是项目测量数据；存在计算与通信重叠时，还需要根据实际关键路径重新判断。依据：[Amdahl 定律说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#strong-scaling-and-amdahls-law)。

>
> 测试范围会根据修改风险选择。比如布局修改要覆盖非连续输入、切片和边界尺寸；异步修改要分别验证提交返回、完成后的数据正确性、跨流依赖，以及缓冲区释放和复用。对于关键的等待或边界判断，我还会在隔离测试中构造反例，检查测试能否识别缺少这些保证时的错误。

>
> 最后再进行模型级正确性和性能回归，检查局部修改是否影响完整执行链。交付时说明已经验证的版本、输入范围和执行模式，以及仍未覆盖的情况。如果某个关键机制还不能解释或验证，我会继续补充证据，不能只用端到端运行成功来替代这一步。

### E1. 只有总显存够，为什么模型仍可能 OOM？

关联[第 2 题](#jd-q2)、[第 7 题](#jd-q7)、[第 9 题](#jd-q9)。

> 总容量只是第一步，还要确认数据实际分配在哪张卡，以及执行到哪一步时达到峰值。多卡容量加起来足够，不代表每个 rank 都能容纳自己的权重、缓存和临时缓冲；并行切分方式也可能让各卡承担不同的存储。
>
> 估算时，我会把权重、实际分配的缓存块、布局补齐、激活、算子工作区、通信和 Graph 缓冲分开核算，再检查它们在时间上是否同时存活。比如布局转换需要一份新存储，而旧输入还不能释放，这个时刻的占用就可能明显高于只计算逻辑 Tensor 大小的结果。
>
> 真正定位时，我会先确认失败的是哪一次分配、申请多大、发生在哪个阶段，再查看当时存活的对象和分配器状态。以 PyTorch CUDA 为例，Tensor 已用内存和分配器保留内存是包含关系，不能直接相加；还要结合设备总占用检查其他分配。若总量看起来足够，也需要进一步判断内存池中的可用块能否满足这次请求。
>
> 我处理过的 Conv3D OOM 就与物理布局有关。原来的通道末置路径对大量小通道段重复补齐，增加了临时存储。定位之后，通过保留二维输入、调整权重布局，并与算子同事配合修改，减少了这部分开销。因此，解决 OOM 要对应具体分配原因，再决定调整布局、缓存预算还是并行配置。

项目事实见[Conv3D 案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)。分配快照与失败分配的历史细节继续按[核查项 C009](实机核查清单.md#c009)核对。已用与保留内存的口径参考 [PyTorch 2.15 CUDA 内存管理](https://docs.pytorch.org/docs/2.15/notes/cuda.html#memory-management)，其他后端按其分配器实现解释。

### E2. 有 view，为什么还要检查 stride 和真实搬运？

关联[第 2 题](#jd-q2)、[第 3 题](#jd-q3)、[第 9 题](#jd-q9)。

> view 可以让多个 Tensor 用不同的形状、stride 和偏移描述同一份存储，但这只说明建立视图时共享了数据。后续算子怎样读取这份数据，还要看它支持哪些布局。
>
> 比如一个连续的二乘三张量转置成三乘二，底层数据没有重排，但两个维度的 stride 交换了。后续算子如果能够按新的 stride 访问，就可以直接使用；如果只接受连续布局，就可能先生成连续副本，或者进入其他回退路径。搬运成本可能出现在消费这个视图的算子内部。
>
> 我会沿着生产者和消费者一起检查：生产者生成了什么布局，消费者要求什么布局，中间是否发生分配、补齐、重排或跨设备拷贝。同时也要区分 view 和 reshape；reshape 在布局无法直接兼容时可能复制数据，不能仅凭函数名称判断是否共享存储。
>
> 共享存储还意味着修改会相互影响。通过一个视图修改了底层元素，其他指向这些元素的视图也会看到变化。因此，除了检查性能，还要确认原地修改是否符合调用约定，以及异步使用期间这份存储是否保持有效。

转置示例见[第 9.4 节](#jd-q9-transpose)；view、reshape 与 contiguous 的行为依据 [PyTorch 2.15 Tensor Views](https://docs.pytorch.org/docs/2.15/tensor_view.html)。特定后端的隐式物化可结合 [GLM 状态布局案例](../../自我准备/projects/GLM5-3-flash-project.md)核对，不将其推广为所有非连续输入都会回退。

### E3. 为什么等待设备流不一定等于 Host 数据已经准备好？

关联[第 4 题](#jd-q4)。

> 因为 Host 准备数据和设备执行任务是两个阶段。如果后台线程还在完成 CPU Padding，H2D 拷贝尚未提交到设备流，此时等待设备流，只能依据当时已经建立的依赖判断完成，不能自动包含后面才提交的工作。
>
> 需要保证的顺序是：CPU 数据准备完成，拷贝任务完成提交，设备拷贝完成，然后消费者读取。Host 侧要有办法确认准备和提交已经完成，再根据同流顺序或跨流事件建立设备依赖。具体采用哪种通知和等待方式，要看后端的任务封装与 Runtime 接口。
>
> 数据就绪和内存生命周期还需要分别处理。消费者必须等数据写好才能读取；源缓冲、临时缓冲和目标缓冲，也必须在各自最后一次访问之前保持有效。一个机制负责记录缓冲的使用时间，并不自动代表消费者已经等待了数据完成。
>
> 在我处理的异步 H2D 问题中，后台 CPU Padding 与后续拷贝提交没有被原等待完整覆盖。我在框架和后端层补齐 Padded Tensor 的异步任务标记与等待，让消费者能够等待相关前置阶段。这个修复使用已有 Runtime 能力，具体接口需要按项目实现说明。

实际经历依据[异步 H2D 案例](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)。内部后台任务不能假定为 Python 层可直接取得的 Future；Host 通知、设备等待与缓冲持有的具体对应继续沿用[核查项 C013、C014](实机核查清单.md#c013)。

### E4. 怎样证明一个算子真正命中了目标后端？

关联[第 7 题](#jd-q7)、[第 8 题](#jd-q8)、[第 15 题](#jd-q15)。

> 我会先固定算子、输入条件和运行模式，确认预期经过哪条分发和实现路径。Tensor 标记为某个设备，或者注册表里存在一个实现，只能提供排查线索；最终还需要观察这次调用实际执行了什么。
>
> 我会在目标实现处增加测试计数或调用记录，并结合 Trace、调用栈或设备 Kernel 记录检查后续执行。如果入口内部还有形状判断、布局转换或回退，也需要继续检查。只进入了一个包装函数，还不能说明完成计算的是预期实现。
>
> 在 GLM 的 mHC 验证中，我遇到过 native 和 fused 两侧都回退，数值比较仍然通过的情况。后来增加调用计数断言，才确认融合路径确实被调用。这个例子说明，结果正确和执行路径正确需要分别验证。
>
> 对允许回退的输入，我会单独说明触发条件，并检查回退后的正确性、搬运和性能；对要求必须使用目标实现的用例，则把路径命中作为明确断言。不支持的输入也要有明确行为，避免它们在测试里悄悄绕过需要验证的功能。

项目依据：[GLM 融合算子接入与验证](../../自我准备/projects/GLM5-3-flash-project.md)。注册机制见 [PyTorch Dispatcher 说明](https://docs.pytorch.org/tutorials/advanced/dispatcher.html)；特定目标后端的实际调用链继续按[核查项 C017](实机核查清单.md#c017)核对。

### E5. Chunked Prefill、KV Cache 和 FlashAttention 各减少什么？

关联[第 5 题](#jd-q5)、[第 11 题](#jd-q11)、[第 12 题](#jd-q12)。

> KV Cache 主要减少生成步骤之间的重复计算。对于普通因果 Transformer，同一请求已经计算过的历史位置，其各层 K、V 可以继续使用。后续 Decode 主要计算新位置，再读取历史 KV 完成当前 Attention。这里说的是同一请求的复用；不同请求之间的前缀共享还要满足另外的匹配条件。
>
> Chunked Prefill 主要调整长输入的执行和调度粒度。它把一个长 Prefill 分成多个执行块，让调度器有机会与其他请求的 Decode 一起安排，减少单个长输入对其他请求的持续占用。输入 token 仍需计算，历史 KV 也仍需保留；chunk 大小需要结合首 token 延迟、生成间隔和吞吐取舍。
>
> FlashAttention 处理的是 Attention 内部的计算和存储组织。通过分块、在线 Softmax 和融合累积，减少完整分数矩阵与概率矩阵的物化及 HBM 往返。它保持普通稠密 Attention 的数学语义，并不直接承担请求调度或跨生成步骤的缓存管理。
>
> 三者可以在同一条链路中配合：调度器分块执行长输入，每个块读取已有的历史 KV 并产生新的 KV，块内 Attention 可以使用适合该形状的 FlashAttention 实现。进入 Decode 后继续复用历史 KV。最终收益还要看实际后端、输入长度和并发负载，不能把三项优化的收益简单相乘。

机制分别见[生成与缓存时序](#jd-q11-generation)、[在线 Softmax](#jd-q12-online-softmax)与 [vLLM v0.26.0 Chunked Prefill 说明](https://docs.vllm.ai/en/v0.26.0/configuration/optimization/#chunked-prefill)。参考版本用于说明机制，不作为历史项目配置。

### E6. FlashAttention 是否一定逐位等于朴素实现？

关联[第 12 题](#jd-q12)。

> 不一定。FlashAttention 计算的是相同的注意力数学表达，但它改变了分块和累积顺序，具体实现还可能采用不同的内部精度。浮点运算存在舍入，因此数学等价并不保证每个输出位都相同。
>
> 比较之前，我会先对齐 Q、K、V、scale、Mask 和有效序列长度，确认两边使用相同的因果位置关系。推理对照时通常关闭 Dropout；如果验证训练路径，则要控制相同的 Dropout 掩码或按对应的随机语义设计测试，不能把随机差异当成数值误差。
>
> 数值检查会同时关注绝对误差、相对误差和 NaN、Inf，并按数据类型、输入范围和任务要求选择判据。接近零的参考值要结合绝对误差判断；需要时使用更高精度的参考路径缩小原因，再检查模型级输出。训练场景还要单独验证梯度。
>
> 如果偏差集中在特定位置、Mask 边界或某类长度上，我会优先检查索引、有效范围和布局对应，不能直接把这些现象归为普通舍入差异。容差应当有数值依据，不能为了让测试通过而掩盖结构性错误。

依据：[FlashAttention 原论文](https://arxiv.org/html/2205.14135v2)与 [PyTorch 2.15 数值精度说明](https://docs.pytorch.org/docs/2.15/notes/numerical_accuracy.html)。这是通用验证方法，不新增本人已实现某代 FlashAttention Kernel 的经历。

### E7. 平均带宽利用率低，就该修改硬件吗？

关联[第 3 题](#jd-q3)、[第 10 题](#jd-q10)、[第 14 题](#jd-q14)。

> 我会先确认这个平均值怎样计算。分子是逻辑上需要的数据量，还是硬件实际搬运的字节数？分母是 Kernel 真正执行的时间，还是包含 Host 准备、同步和队列空闲的整个窗口？这几种口径反映的问题不同，不能直接互换。
>
> 如果设备频繁等待 Host 提交工作，即使局部 Kernel 的访存效率正常，整个窗口的平均带宽也可能很低。如果 Kernel 内部的有效带宽低，还要继续检查访问连续性、数据复用、并发访存数量，以及短任务或依赖链造成的延迟，判断限制究竟在哪里。
>
> 我会把可疑操作提取出来，固定数据量与计算语义，对比布局、批量和提交方式，再回到模型时间线验证。比如 GLM 状态搬运的排查，就是通过连续池与打包页 view 的对照，确认了布局触发的 Host fallback。这个结果支持先修改软件布局，不需要先推断硬件峰值带宽不足。
>
> 如果软件组织已经改善，多个代表性负载仍然受某类存储或访问能力限制，再把具体访问模式、实际流量和端到端影响交给硬件团队评估。是否增加带宽或改变访存机制，还要与成本、功耗和其他瓶颈一起比较。

案例依据：[GLM 状态布局与时间线分析](../../自我准备/projects/GLM5-3-flash-project.md)。本例不声称已恢复硬件带宽计数器；ECG 权重布局的具体访存归因继续沿用[核查项 C027](实机核查清单.md#c027)。收益取舍可结合[第 14.4 节 Amdahl 估算](#jd-q14-amdahl)。

### E8. AI 生成的测试全绿，交付前还缺什么？

关联[第 15 题](#jd-q15)。

> 我会先核对这些测试证明了什么：预期值有没有独立依据，输入是否覆盖本次修改的支持范围，以及要求执行的用例是否确实运行。预期跳过的用例和必须通过的用例要分别记录，避免只根据一行汇总结果判断完成。
>
> 接着检查实际执行路径，确认目标分支已经被调用，回退没有掩盖缺失的实现。同时审查代码中测试不容易直接观察的部分，例如缓冲区所有权、错误传播、异常清理和异步完成依赖。这些仍然需要结合调用链理解。
>
> 对关键风险，我会在隔离测试中构造错误条件，例如缺少一次必要等待，或者让边界索引暴露出来，再检查测试是否能捕获问题。并发用例还需要控制相关执行顺序；一次没有复现错误，不能证明测试已经覆盖了那个时间窗口。
>
> 最后完成模型级正确性与性能回归，确认局部修改没有破坏完整链路。性能比较使用一致的模型、输入和运行配置，并在关闭额外诊断干扰后复测。交付记录写清版本、支持范围、已验证模式和剩余限制，让后续维护能够复现这些结论。

目标路径验证见[扩展 E4](#jd-extra-e4)；生命周期与非默认流验证可对照[异步 D2H 回归](../../自我准备/projects/async-d2h-project.md)。PyTorch 官方也将参考数值对照与注册检查分开，见[算子测试说明](https://docs.pytorch.org/tutorials/advanced/cpp_custom_ops.html#testing-an-operator)；这些通用方法不等于本场面试时已执行全部步骤。
