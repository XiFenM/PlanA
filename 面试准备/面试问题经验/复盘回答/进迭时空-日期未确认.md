## 1. 框架组职责与分工

### 1.1 问题与现场细节

面试官问组内定位、主要职责，以及与算子、Runtime、编译器团队的分工。原答说明自己负责 PyTorch／vLLM 接入、精度与性能、客户交付，底层由其他团队承担。这里是职责题，不重写自我介绍。

### 1.2 原回答的优点与不足

分层较清楚，也没有把所有底层工作归为己有。可以进一步把“适配”落到本人修改的对象、交给其他团队的输入和验收责任，而不只按组织名称划线。底稿没有代码证据，不能据此判断独立完成了整个后端。

### 1.3 更好的回答方式与参考回答

按“本人交付 → 接口与协作 → 结果验证”组织。

> 我主要负责模型与框架侧接入，让模型的执行、数据布局和设备调用在自研后端上正确运行，并定位精度、显存和端到端性能问题。我的修改可能在模型调用、权重处理、Tensor 布局或框架与算子接口之间，具体以项目说明。
>
> 算子团队负责专用 Kernel 的计算与访存实现，Runtime、驱动和编译器也有各自负责人。我会提供真实 Shape、dtype、复现输入、预期结果和测量条件，与他们共同确定问题所在，再把修改接回模型验证。比如 Conv3D 案例中，我负责复现、布局与调用调整，Kernel 由算子同事实现；我仍负责确认接口与模型回归，而不是把问题交出去就结束。

## 2. Conv3D 的 OOM 与首 token 优化

### 2.1 问题与现场子追问

面试官要求解释多模态模型 OOM、首 token 慢的定位与优化，并追问具体算子逻辑及协作。原答联系小通道、末维对齐和布局，明确底层算子由同事实现。底稿中的卡数、显存和 `512 bytes／256／1280` 未统一，不用它们还原精确配置。

### 2.2 原回答的优点与不足

因果方向和职责边界值得保留。不足是没有把逻辑 Shape、实际分配、元素数与字节数分开，也没有完整说明变换等价性及测量口径。底稿“整体显存扩大数百倍”属于过度概括，不能作为本人已经说错的确定事实。

### 2.3 更好的回答方式

使用已确认的[案例卡](../../自我准备/projects/multimodal-inference-project.md#project1-conv3d-case-card-v1)：先定位物理缓冲，再解释输入／权重共同映射，最后分开单算子、图片模型回归和视频 OOM。后补项目事实用于当前答法，不倒填成现场已全部展示。

### 2.4 参考回答

> 我处理过 Qwen2.5-VL-32B 视频输入的 Conv3D OOM。调用栈指向视觉 Encoder，我提取真实输入构造单例，把内部重排移到调用前检查显存 snapshot，观察到重排后占用跃升。
>
> 原输入按视觉块展平为 `[N,K]`，其中 `K=C×T×H×W`。view 本身复用存储，后续通道末置却产生新缓冲；通道很小，目标后端对大量小通道段分别补齐，导致物理存储和搬运膨胀。我保留二维输入、传递原维度，并在初始化时按同一顺序展平权重。算子同事负责让专用 Kernel 按新接口读取与计算，二维末维对齐仍然存在。
>
> 输入和权重的窗口内元素必须保持配对，不能任意拼维。已有视频 Shape 单例与 CPU Conv3D 在既定容差下比较；图片模型级回归比较了 10 例输出，视频模型级精度未覆盖。最初 OOM 的视频没有优化前 TTFT，不能拿另一模型或图片组替代。收益属于布局与 Kernel 的联合方案，不拆成个人独立加速比。

现场关于“算子内部怎样做”的追问可直接补充：“我能说明框架侧接口与验证，专用 Kernel 的内部 SRAM 调度由算子同事负责，不将未掌握的实现细节补成自己的工作。”

## 3. 小 batch MatMul 与权重预排布

### 3.1 问题与现场细节

面试官问另一客户模型的优化是否与 Conv3D 类似。原答讨论小 batch MatMul、加载期权重重排与 NZ 类比；模型专名和 bank conflict 的原话仍不确定。

### 3.2 原回答的优点与不足

识别权重读取压力、将转换放到加载阶段，是合理的工程思路。格式名称不能证明瓶颈：NZ 类比不代表自研平台使用完全相同的地址映射，也不能据此确定 HBM、DMA 或片上 bank 哪一层受限。

### 3.3 更好的回答方式与参考回答

先说负载和访问方式，再说明本人修改与联合结果。当前事实采用[ECG 布局案例卡](../../自我准备/projects/ECG-project.md#ecg-layout-case-card-v1)。

> 这个案例更偏静态权重的读取方式。ECG 模型使用 Transformers 执行链路，在常规优化后，小批量矩阵乘仍是热点。对于 `[b,K]×[K,N]`，计算量约为 `2bKN`，低 batch 时权重读入不易被足够多的 token 摊销；这只是初步模型，还要看缓存复用和真实 Profile。
>
> 我们选择 blocked Col-major：Tile 内行优先、Tile 间列优先，保持 Tile 大小不变。我负责 Tensor 扩展和加载后的预排布，算子同事处理底层访存；Prefill、Decode 中使用静态权重的相关层复用新布局，不包括 QKᵀ 等动态矩阵乘。
>
> 验证既看同设备新旧 MatMul 输出，也看模型 logits 和生成结果。现有口述支持所测范围内一致，但不能推广所有输入。布局转换、Kernel 和前期优化需要分开计时；当前没有足以把收益唯一归因于 bank conflict 的证据，所以我只说改善了相应权重访问路径，不声称打满带宽。

这段引用现有案例作为当前准备素材，不把底稿待确认的“ECG”专名直接升级为本场已准确听辨的词。

## 4. 异步拷贝导致的偶发输出异常

### 4.1 问题与现场细节

面试官追问乱码、EOS 异常怎样定位到同步问题。底稿记载候选人将“内存屏障”改述为异步拷贝／流同步；没有原简历，不能进一步评价整份简历。增加 Dump 后异常改变是定位线索，不是独立的竞态证明。

### 4.2 原回答的优点与不足

保留输出比对、控制异步等级和检查 Host 准备的路径。需要补充哪种完成事件保护哪块缓冲、拷贝何时入队，以及最终修复是否撤掉诊断同步后仍成立。底稿补出的锁页双缓冲和“无未知项”不采用。

### 4.3 更好的回答方式与参考回答

当前项目事实见[异步 H2D 案例卡](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)，顺序为 `CPU Padding 完成 → H2D 提交 → 拷贝完成 → 消费`。

> 我先固定请求和生成配置，寻找第一次输出分叉，比较对应 logits 和中间张量，避免追踪后续差异的连锁放大。大量 Dump 后异常消失，说明调试可能改变时序；再将 H2D 单独改成阻塞路径，异常也消失，把调查收窄到这条异步链。
>
> 后续项目记录确认，后台先在 CPU 准备 Padded Tensor，再提交设备拷贝。原等待只覆盖已经进入设备流的任务；如果 CPU 准备尚未完成、拷贝还未入队，等待空流可能先返回。缺的不是一个笼统的“屏障”，而是从数据准备到提交、完成和消费的依赖。
>
> 我在框架／后端层补齐 Padded Tensor 的异步标记和等待，Runtime 无需修改。修复后恢复原异步配置，撤掉临时阻塞与额外诊断等待，对现场 168 条请求重放 5 轮未再观察到原异常。这个结果来自后来确认的项目口述，不是本次重新测试，也不代表 840 个独立场景或所有负载零故障。

设备流只能等待相应已建立的工作依赖；CUDA 的[异步执行说明](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)可作通用对照，不能当成自研 Runtime 的真实 API。

## 5. Chunked Prefill

### 5.1 问题与原回答

面试官问为什么需要 Chunked Prefill。原答说明长 prompt 分块、在调度中穿插 Decode，避免生成请求等待过长。这一主旨正确，不需要为了复盘强行增加错误。

### 5.2 需要补清的条件

chunk 大小、每轮 token 预算、TTFT 和 ITL 的取舍未展开。分块保持原请求上下文，不是几个互不相关的新请求，也不自动解决完整历史 KV 超出容量的问题。

### 5.3 更好的回答方式与参考回答

> Chunked Prefill 把一次长输入的前向分到多轮调度，限制单轮新增计算量，使正在 Decode 的请求也有机会推进。已处理的 KV 或递推状态保留，后续 chunk 使用原始逻辑位置和正确的因果关系继续计算，不能把每段当成从零开始的新上下文。
>
> 较小 chunk 可以缩短一次长 Prefill 对 Decode 的阻塞，但会增加调度和部分执行开销，也可能让长请求更晚完成 Prefill。较大 chunk 可能提高计算效率，却拉长单轮时间。共享预算下还要考虑同时到达的请求，不能承诺 TTFT、ITL 和吞吐一起改善。
>
> 如果限制来自一次计算的临时激活或 token 预算，分块可能缓解；普通 full attention 最终仍需保存合法历史 K/V，所以完整缓存超过容量时，还要另行处理准入、缓存精度或其他配置。我会用长短请求混合负载比较尾延迟、吞吐与内存，决定预算。

依据：[vLLM v0.26.0 调优说明](https://docs.vllm.ai/en/v0.26.0/configuration/optimization/)。此版本仅用于参考机制，不作为现场版本。

## 6. 多轮图文与 embedding 对应

### 6.1 问题与现场子追问

面试官问多张图片怎样进入多轮上下文，并再次确认插入关系。原答介绍视觉编码、投影及文本占位位置；patch size、视觉 token 数和具体模型版本未可靠确认。

### 6.2 原回答的优点与不足

总体流程合理，但不能将一个模型的占位与投影方式推广到所有 VLM。需要说明占位符扩展、图像顺序和特征数量的对应，而不只是说“把 embedding 拼起来”。

### 6.3 更好的回答方式与参考回答

> 以把视觉特征并入语言模型序列的模型为例，首先由对应版本的 processor 处理对话、图片和视频，生成文本 token、媒体张量以及必要的尺寸或网格信息。视觉 Encoder 及模型规定的投影或合并模块得到视觉特征，再把它们放到输入序列中对应的媒体占位位置。
>
> 占位符不一定是一个 token 对应整张图。它可能展开成多个视觉位置，数量取决于模型与输入处理。我会检查各媒体的顺序、分组长度与特征数一致，并按模型要求构造 position 和 mask；不能给所有图文模型套同一个 patch 大小或 M-RoPE 规则。
>
> 多轮时仍按对话模板保留图文关联。是否重算历史视觉特征、是否复用前缀，取决于实际输入、缓存与模型契约，不能认为图片在上一轮出现过就自动安全复用。验证时除了输出效果，还会检查占位数量、索引和位置映射，避免形状恰好相同但图像顺序错位。

依据：[vLLM 多模态接入说明](https://docs.vllm.ai/en/stable/contributing/model/multimodal/)。已有个人范围见[多模态项目口述](../../自我准备/projects/multimodal-inference-project.md#project1-oral-baseline-20260902)，本题不新增具体适配版本。

## 7. PrivateUse1 机制

### 7.1 问题与原回答

面试官问 PyTorch 的 PrivateUse1 如何抽象第三方后端。底稿记载尚在研究，没有展开。合理结论是这段未展示机制解释，不能扩大为没有框架工程能力，也不能照搬底稿“PyTorch 2.0 才引入”的说法。

### 7.2 更好的回答方式

先区分预留的设备／分发机制与完整后端工程，再用 `empty → copy → add` 的窄链说明对象、内存与执行如何接上。

### 7.3 参考回答

> PrivateUse1 提供第三方设备接入所需的一组预留类型和 dispatch 入口，让扩展可以注册设备实现。给设备改名或注册 Python 模块只是入口的一部分，不会自动获得内存分配、拷贝、算子或训练支持。
>
> 我会从最小执行链解释：创建张量要确定 device、dtype、shape 和 Storage 的分配方式；拷贝要实现 Host／Device 传输及完成语义；调用 add 时，dispatcher 根据 Tensor 和当前运行状态选择注册的实现，再进入设备算子。还需要设备切换、流、事件和资源释放等运行时接口。未支持的路径要明确报错或采用可观察的 fallback，不能把静默回退 CPU 当作设备实现成功。
>
> 如果目标包含训练、混合精度或编译，还要分别验证 Autograd、Autocast、Fake／Meta 和图编译等接口。是否完成这些能力应按实际调用与测试说明，不因使用了 PrivateUse1 这个名称就宣称完整兼容。

机制与 `TORCH_LIBRARY_IMPL` 入口见[官方 PrivateUse1 教程](https://docs.pytorch.org/tutorials/advanced/privateuseone.html)；当前文档接口需要与目标 PyTorch 版本核对。这是标准答法，不表示本场已完成上述模块。

## 8. 后端插件化的实现路径与阶段

### 8.1 问题与现场追问

面试官问插件化做到了哪一步、怎样做，并确认是否参考 torch_npu。原答说刚开始，使用 AI 辅助，参考成熟后端再接入自研 Runtime。完成模块、本人审查范围未明确。

### 8.2 原回答的优点与不足

说明参考来源与进行中状态是正确的。只说“替换接口”不足以说明语义兼容；参考代码里的设备数量、流、allocator、线程和异常假设不能原样迁移。不能从使用 AI 推断实现一定错误，也不能把已有 vLLM 插件项目当作 PyTorch 后端已经完成。

### 8.3 更好的回答方式与参考回答

> 我会先说明这是哪个层次的插件，以及当前已验证的范围。本场讨论的是 PyTorch 后端插件化，目标是减少直接修改主仓库带来的升级成本；参考成熟实现可以帮助理解结构，但不能靠批量替换 Runtime 名称就认定适配完成。
>
> 技术上我会把迁移拆成算子分发、张量存储与分配、数据拷贝、设备和流管理等边界。对每个边界列出原实现假设、目标平台能力、需要保留的调用语义和验证方法，先跑通少量真实算子，再扩大覆盖。内存释放和异步完成尤其要核对，不能只验证返回值形状。
>

## 9. Tensor 的 Host／Device 描述

### 9.1 问题与原回答

面试官问 Tensor 的 Host／Device“描述符”。底稿只记录不太了解，且没有澄清这里指 PyTorch 对象还是设备 Kernel descriptor。因此参考回答先说明层级，不补成一个确定的原题。

### 9.2 更好的回答方式

对通常的稠密张量，区分 Host 侧元数据对象、Storage 及底层缓冲，再解释后端怎样把元数据转换成 Kernel 参数；不声称所有 Tensor 都有同一种物理表示。

### 9.3 参考回答

> 如果指 PyTorch 常见稠密 Tensor 的对象关系，Tensor 是一个句柄，底层 TensorImpl 保存大小、stride、storage offset、类型及分发相关信息，并关联 Storage。StorageImpl 持有 DataPtr，DataPtr 包含数据指针、释放上下文及设备信息；由 allocator 提供分配与释放机制。
>
> 因此 Tensor 的元数据可以由 CPU 管理，而实际数据位于设备内存。改变 view 的 shape 或 stride 可能共享原 Storage，并不必然搬运数据。设备指针也不能当作 Host 可直接解引用的物理地址。
>
> 如果您说的是算子 descriptor，后端会根据 shape、stride、dtype、设备地址及布局要求组织调用参数。这是另一层表示，须满足目标 Runtime 与 Kernel 的合同。异步调用还要保证元数据和数据缓冲在最后使用之前有效；Python 引用消失不等于设备已经用完。

依据本地核验的 PyTorch `460948b96a67`：[TensorImpl](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/c10/core/TensorImpl.h)、[StorageImpl](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/c10/core/StorageImpl.h)、[Allocator／DataPtr](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/c10/core/Allocator.h)。不将常见稠密路径外推到 meta、稀疏等全部 Tensor。

## 10. 性能与精度分析工具

### 10.1 问题与原回答

原答介绍 Runtime／算子 cycles、日志分析脚本和逐层激活比对。具体 cosine、L1／L2 指标可能来自模型扩写，不认定都在现场说过；没有采用某个知名 profiler 也不等于没有测量能力。

### 10.2 原回答的优点与不足

工具服务于热点与精度定位，方向明确。需要补计时域、异步提交与执行完成、重叠是否允许相加，以及 Dump 对时序的干扰。只报“某算子 cycle 占比”无法自动解释整模墙钟耗时。

### 10.3 更好的回答方式与参考回答

> 性能上，我用实际可用的框架、Runtime 和算子信息对齐一条请求时间线：先区分 Host 准备、提交、拷贝、设备计算和通信，再找关键路径上的等待或热点。cycles 需要明确时钟域和含义；不同引擎可能重叠，不能把所有算子时间相加当作端到端时间。异步执行还要避免只测到提交耗时。
>
> 精度上先固定输入、预处理与采样条件，定位第一个明显分叉的 token 或中间节点，再比较同一逻辑 Tensor 的结果。比较前核对 dtype、shape、layout 和位置，按运算选择绝对／相对误差及模型级判据，不能只用一个余弦相似度阈值覆盖所有情况。

> 最后回到没有额外诊断干扰的路径确认结论。Dump 可能引入拷贝和同步，使竞态暂时消失，所以它既是工具也可能改变被测系统。我会保留开关对照，不把加了日志后稳定直接当成修复。

## 11. KV Cache 为什么成立

### 11.1 问题与原回答

面试官问 Attention 使用 KV Cache 加速的逻辑。原答抓住因果解码、历史 K/V 不随新 token 改变的主旨，值得保留；底稿中的复杂度扩写不能反推为本人现场说过。

### 11.2 更好的回答方式

先说明缓存成立条件，再说明每步仍做什么。普通 causal Transformer 的解释不自动适用于双向编码器、不同位置语义或任意跨请求复用。

### 11.3 参考回答

> 在参数和有效前缀不变的因果自回归推理中，历史位置不能看到后来追加的 token，因此它们在各层已经算出的表示与 K/V 不必重新计算。我们缓存每层历史 K/V；下一步只为新进入前向的位置计算 Q/K/V，让当前 Q 对合法历史及当前位置做 Attention，再追加新 K/V。
>
> 省掉的是反复执行整个历史前缀，不是让当前 Attention 不再依赖历史。对一个 head，历史长度为 n、维度为 d 时，普通 dense attention 的单步 `qKᵀ` 和加权求和仍约为 O(nd)，缓存也随历史增长。完整生成过程与单步成本必须分别讨论。
>
> 还要区分本步计算位置和刚采样的输出 token：输出通常在下一次前向时才产生自己的 K/V。若前缀、模型权重、位置规则或其他影响表示的条件改变，旧缓存不能直接沿用；跨请求共享还需要额外的身份、兼容性与生命周期检查。

依据：[Transformers KV Cache 机制](https://huggingface.co/docs/transformers/cache_explanation)。概念上的追加不要求物理 Tensor 每步重新拼接，分页或预分配实现可以避免搬移旧数据。

## 12. FlashAttention

### 12.1 问题与原回答

面试官问 FlashAttention 为什么快。原答已涉及 tiling、online softmax 和避免完整矩阵物化，中途表示细节记忆不全。底稿“HBM 复杂度从二次降到线性”是技术扩写错误，不据此给现场回答扣分。

### 12.2 更好的回答方式

主线是减少片外中间数据往返，保持标准 dense attention 的计算语义。以一行 query 为例，维护已处理部分的最大分数 `m`、指数和 `l`、未归一化加权和 `u`；新块分数为 `s_j`、对应 value 为 `v_j`：

```text
m' = max(m, max_j s_j)
l' = exp(m-m') * l + Σ_j exp(s_j-m')
u' = exp(m-m') * u + Σ_j exp(s_j-m') * v_j
最终输出 = u / l
```

公式假定有有效 key，mask 后的无效项不贡献求和；实际 Kernel 还需处理全 mask 等边界。依据：[FlashAttention 原论文](https://arxiv.org/html/2205.14135v2)。

### 12.3 参考回答

> 标准 Attention 若把 QKᵀ 和 softmax 概率矩阵写到 HBM，会产生很大的中间存储和往返流量。FlashAttention 把 Q/K/V 分块搬到片上，在块内完成分数、softmax 更新与 value 累积，避免物化完整的 N×N 中间矩阵。
>
> online softmax 的关键是，加入新块后最大值可能增大，所以旧的归一化分母和加权和都要按新最大值重新缩放，再加新块贡献。这样最终得到与整行 softmax 相同的数学结果，浮点计算顺序则可能产生正常数值差异。
>
> 它仍在计算 dense attention，主要减少 I/O 和中间内存，不能说算术工作量变成线性。实际收益取决于序列长度、head dimension、片上容量和并行组织；片上分块也不等于全模型不再访问 HBM。若进一步比较不同代际，我会单独讨论线程和工作划分，不把一个原理当成所有实现细节。

## 扩展问题与参考回答

以下均是补充准备，不作为现场已问或原答缺陷。

### E1. 只有总显存够，为什么模型仍可能 OOM？

关联第 2、7、9 题。

> 要按每个 rank 的实际分配核算，而非只加总所有卡容量。除权重与有效 KV 外，还有整块容量、布局补齐、视觉激活、workspace、通信和 graph 缓冲；它们的生命周期可能在某一步重叠。先定位失败分配及当时存活对象，再决定是减少临时物化、调整缓存预算还是改变并行配置。静态估算足够不等于分配峰值足够。

### E2. 有 view，为什么还要检查 stride 和真实搬运？

关联第 2、3、9 题。

> view 只是用不同元数据解释共享存储；后续 Kernel 不一定支持该 stride。若后端先连续化、补齐或复制，就会新增内存与带宽成本。应检查生产者输出、消费者合同和真实执行路径，而不能因 Python 里只有一个 reshape 就判断零成本。共享 Storage 也意味着别名写入可能影响另一视图。

依据：[PyTorch Tensor Views 固定版本文档](https://github.com/pytorch/pytorch/blob/0bd89deb431509d893177a84cfa4768aa0399809/docs/source/tensor_view.md)。

### E3. 为什么等待设备流不一定等于 Host 数据已经准备好？

关联第 4 题。

> 同步通常针对已经建立的队列或事件依赖。若 Host 后台任务尚未完成，也尚未把拷贝提交到被等待的流，等待不能凭空包含这段未来工作。必须让数据准备完成先于提交，提交后再建立设备完成与消费关系，并保护源、目标缓冲直到各自最后使用。具体原语由目标 Runtime 的合同决定，不能只选一个名字像 guard 或 barrier 的 API。

### E4. 怎样证明一个算子真正命中了目标后端？

关联第 7、8、15 题。

> 除比较输出，还应检查实际分发入口、设备类型和调用记录，必要时给目标实现加测试计数或用可控 stub 证明路径。对允许的 fallback 单独标明性能与数据搬运；对不支持的功能明确拒绝。仅看到 Tensor 在设备上，或模型最后输出正确，都不足以证明每个热点算子走了预期实现。

依据：[PyTorch Dispatcher 注册与 fallback](https://docs.pytorch.org/tutorials/advanced/dispatcher.html)。

### E5. Chunked Prefill、KV Cache 和 FlashAttention 各减少什么？

关联第 5、11、12 题。

> KV Cache 跨生成步骤复用历史层状态，减少重复前向；Chunked Prefill 改变长输入的执行与调度粒度，控制对其他请求的干扰；FlashAttention 改变 Attention 内部的计算与存储组织，减少中间矩阵的 HBM 往返。三者可以组合，但任何一项都不自动免除另外两项的成本或验证。

### E6. FlashAttention 是否一定逐位等于朴素实现？

关联第 12 题。

> 它计算相同的 dense attention 数学表达，但分块、归约顺序和内部精度可能改变舍入结果。应使用相同 mask、scale、dtype 与 dropout 条件做数值对照，再按误差与任务要求判断。数学等价不代表所有平台逐位相同，也不能容忍索引或 mask 错误造成的结构性差异。

依据：[FlashAttention 原论文](https://arxiv.org/html/2205.14135v2)。

### E7. 平均带宽利用率低，就该修改硬件吗？

关联第 3、10、14 题。

> 不一定。先区分搬运量、访问连续性、并发度、提交间隙、同步和计量窗口。低利用率可能来自供给不足或软件串行化，而不是峰值带宽不够。用小范围对照确认限制，再比较软件优化与硬件修改的收益、覆盖负载和成本，避免拿一个平均数直接推导架构结论。

### E8. AI 生成的测试全绿，交付前还缺什么？

关联第 15 题。

> 先核对测试是否覆盖真实合同、预期值是否独立、路径是否命中，再审查测试没有观察到的资源和异常行为。对关键不变量加入故意破坏后的反例，确认测试会报错；最后记录配置、覆盖范围和未验证项。测试全绿只说明这些检查没有发现错误，不能把未覆盖的并发、设备完成或长期稳定性自动判为正确。
