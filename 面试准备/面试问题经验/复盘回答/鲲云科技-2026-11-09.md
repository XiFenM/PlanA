## 1. vLLM 如何发现插件，并选择自定义 Worker？

### 1.1 题意与材料边界

本题考察 Python 包安装后的插件发现，以及插件怎样影响 Worker 类的选择和实例化。现有材料只有问题，没有现场答稿，不能判断当时答对、答错或是否经过提示。下面按题意拆解同题细节，不将拆解项补写成面试官逐字追问。

技术依据固定为 `vLLM v0.26.0@568afb3a13806beb53bb2e6bd518269357b237c0`，通过 `git show` 核对；不将参考源码当作用户私有插件或历史版本。

### 1.2 必须答清的机制

| 同题细节 | 准确回答 |
| --- | --- |
| 安装后怎样被发现？ | 打包声明 entry points，安装后形成分发元数据。`importlib.metadata.entry_points(group=...)` 枚举相应组，`entry_point.load()` 导入注册回调；不是扫描任意源码目录 |
| 平台插件与 general 插件有什么区别？ | `vllm.platform_plugins` 的回调返回可用 Platform 的限定类名或 `None`；`vllm.general_plugins` 执行模型注册等初始化动作，其返回值不用于选择平台 |
| 多个平台可用怎么办？ | 本版本先探测内置和外部平台。两个及以上外部平台激活时报错；恰有一个外部平台时优先选择它；没有外部平台才检查内置平台是否唯一，否则报冲突或选择 `UnspecifiedPlatform` |
| Worker 在哪里确定？ | 配置初始化调用 `current_platform.check_and_update_config`，平台可将 `parallel_config.worker_cls` 从 `auto` 设置为具体类路径；显式配置还需按平台规则检查兼容性 |
| 最后怎样构造对象？ | `WorkerWrapperBase.init_worker` 先加载 general 插件，再解析 Worker 字符串路径，并以配置和 rank 等参数实例化；Worker 负责后续设备初始化、模型加载与执行 |

发现与注册见[插件 loader](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/plugins/__init__.py#L36)，平台判定与惰性实例化见[平台选择](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/platforms/__init__.py#L211)。配置调用见[VllmConfig](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/config/vllm.py#L1454)；CUDA 默认 Worker 的赋值是一个[具体示例](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/platforms/cuda.py#L308)，不是所有设备都使用该类。

### 1.3 完整参考回答

> 我会把发现、平台选择、配置和实例化分开。插件首先作为 Python 包安装，在打包元数据中声明 vLLM 的 entry-point group。vLLM 按组枚举并加载回调；平台回调检查当前环境，可用时返回 Platform 类的完整路径，不适用时返回 None。安装可见只证明能发现它，不证明驱动、算子和硬件已经可用。
>
> current_platform 在首次访问时惰性解析并在进程内缓存。这个版本会处理平台冲突，并让唯一可用的外部平台优先于内置平台。配置初始化随后调用平台的 check_and_update_config，由它校验设备条件，并通常在 worker_cls 为 auto 时填入自定义 Worker 类路径。
>
> 执行进程中的 WorkerWrapper 再根据这个字符串导入类，传入配置和 rank 等参数创建 Worker。这里要区分两种字符串：entry point 用 module:callback；Platform 返回值和 worker_cls 用 package.module.ClassName，解析器按最后一个点拆分模块和类名，不能直接换成冒号写法。
>
> 多进程下，不能假定主进程的手动注册在所有子进程都自动可用。Worker 初始化会调用 general 插件加载；平台在该进程内尚未初始化时，于首次访问触发解析，进程启动方式可能影响是否继承已有状态。因此相关包、依赖和配置要在执行进程可见，注册回调应能安全重复调用。general 插件的模型注册与平台选择是两条职责不同的路径。

Worker 的解析、general 注册和构造分别见[初始化入口](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/worker/worker_base.py#L230)、[实际实例化](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/worker/worker_base.py#L317)、[点号路径解析器](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/utils/import_utils.py#L104)。多进程执行器在 [WorkerProc](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/executor/multiproc_executor.py#L596) 中构造 wrapper 并调用初始化。

### 1.4 环境变量与子进程细节

`VLLM_PLUGINS` 是逗号分隔的 **entry-point 名称** 白名单，不是包名或 Worker 类名。该版本通用 loader 将它用于 general、platform 等组；未设置时加载这些组发现的全部插件，空字符串通常不匹配任何名称。它不屏蔽独立调用的内置平台探测，也不是全局“指定硬件”开关。若平台和模型注册使用两个名称，白名单需包含两者。依据：[loader 的过滤条件](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/plugins/__init__.py#L40)、[环境变量解析](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/envs.py#L1100)。

general 加载使用进程内全局标志去重；fork 可能继承已初始化的标志和平台对象，具体加载行为需结合启动方式。平台回调在探测与最终选择时还可能被再次调用。应在初始化前准备环境，不能假设修改环境变量后已缓存的平台会自动重选。API、EngineCore 与 Worker 都需具备相应的包、依赖与配置。另一类 endpoint 插件有额外显式启用规则，不能把上述“未设置则全加载”扩大到所有插件类型。

### 1.5 最小绑定示意

以下名称均为示例占位，不是用户的私有实现。省略硬件探测、Worker、Attention backend 等必要实现，不能作为完整可运行插件。

```toml
# pyproject.toml 中的节选
[project.entry-points."vllm.platform_plugins"]
demo_accel = "demo_plugin:register_platform"
```

```python
# demo_plugin/__init__.py：platform_is_usable 是待实现的探测函数
def register_platform():
    if not platform_is_usable():
        return None
    return "demo_plugin.platform.DemoPlatform"

# demo_plugin/platform.py：只展示 Worker 绑定
from vllm.platforms.interface import Platform

class DemoPlatform(Platform):
    @classmethod
    def check_and_update_config(cls, config):
        if config.parallel_config.worker_cls == "auto":
            config.parallel_config.worker_cls = "demo_plugin.worker.DemoWorker"
```

打包语法参照[Python Entry Points 规范](https://packaging.python.org/en/latest/specifications/entry-points/)；平台回调与 Worker 接口参照[vLLM 版本化官方指南](https://docs.vllm.ai/en/v0.26.0/design/plugin_system/)及[同提交指南](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/docs/design/plugin_system.md)。`worker_extension_cls` 用于扩展已选 Worker 的方法，不替代本题的 Worker 类选择。

## 2. PyTorch 插件怎样被发现，需要对接哪些 Runtime 接口？

### 2.1 已记录题意与准备范围

简记明确包含插件发现与 Runtime 对接两个子问，没有现场作答，不能评价原回答。下文以 PrivateUse1 设备后端为例；普通自定义算子扩展、vLLM 硬件插件与完整 PyTorch 设备后端的接入范围不同。

### 2.2 版本与插件加载

主要源码固定为 PyTorch `460948b96a67002b7257ac4f3d6a192f70d61d27`，其 `version.txt` 为 `2.15.0a0`；另核对公开 `v2.5.0` 的自动加载代码。当前官方文档仅作补充，不认定历史项目或目标平台具备全部新接口。

插件被使用需要分别完成**加载、注册和设备可用性查询**：

1. **显式加载。** `import 厂商扩展包` 可以加载其 C++ 扩展；也可由 `torch.ops.load_library` 加载共享库。库中的 `TORCH_LIBRARY_IMPL(aten, PrivateUse1, m)` 注册器在静态初始化时把实现加入 dispatcher。它不是等待用户第一次调用算子才去扫描驱动。[共享库加载](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/torch/_ops.py#L1563)、[静态注册宏](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/torch/library.h#L1056)
2. **可选自动加载。** 已安装包可以声明 `torch.backends` entry point。已核对的 `v2.5.0` 和固定快照均在 `import torch` 的初始化末段枚举入口、加载并调用 hook，默认启用；在导入前设置 `TORCH_DEVICE_BACKEND_AUTOLOAD=0` 可关闭。入口模块的导入本身也会执行初始化，所以 OpenReg 的 hook 函数为空仍可完成注册。不同版本的精确顺序、厂商初始化与循环导入处理要单独核对，不假定所有包都已配置入口。[v2.5.0 源码](https://github.com/pytorch/pytorch/blob/v2.5.0/torch/__init__.py#L2394)、[固定快照](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/torch/__init__.py#L3478)
3. **命名与模块暴露。** `rename_privateuse1_backend("foo")` 提供设备名称；`_register_device_module("foo", module)` 暴露 `torch.foo`。它们不自动实现算子、分配器或驱动。设备是否存在、数量及初始化状态，仍由后端对接 Runtime 查询。[OpenReg 初始化实例](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/test/cpp_extensions/open_registration_extension/torch_openreg/torch_openreg/__init__.py)

### 2.3 Runtime 对接的细节表

表中是 PyTorch 侧的职责和抽象，不是用户私有 SDK 的函数名单。适配层需要把它们映射到厂商实际能力，并处理错误、对象生命周期和不支持的情况；具体功能按目标范围接入。

| 层次 | PyTorch 侧需要说明什么 | Runtime／后端承担什么 |
| --- | --- | --- |
| 设备 | hooks 的初始化／可用性；guard 的 `deviceCount`、`getDevice`、`setDevice`、`exchangeDevice` | 枚举、选择、切换设备，正确恢复原设备；设备 guard 不等于同步器 |
| Stream／Event | 当前／默认流、切换流、事件记录／等待／查询、流或设备同步 | 保存流状态、建立跨流依赖，区分提交成功与工作完成 |
| 分配器 | `Allocator::allocate` 返回含设备与释放上下文的 `DataPtr`，由 Storage 管理 | 分配、释放或缓存复用、对齐与 OOM；不能只返回没有释放约定的地址 |
| 拷贝与存活期 | H2D／D2H／D2D，pinned Host 内存；allocator 的 Stream 使用记录或对应机制 | 保证源与目标未被提前复用；`recordStream` 类保护不代替消费者等待，非阻塞条件不满足时要有正确处理 |
| 算子 | schema 与 `PrivateUse1` 实现，Shape／dtype／stride／别名契约 | 调用设备 Kernel；缺失算子明确报错或使用可观察的 fallback |
| 随机数 | 需要随机算子时接入 Generator、每设备默认生成器、seed／state | 维护随机状态及并发语义，不因设备改名就自动支持随机数 |
| 训练与 AMP | 按目标支持 Autograd、`AutogradPrivateUse1`、`AutocastPrivateUse1` 等路径 | 提供相应反向或复用可用机制，维护混合精度策略；不是 train/eval 一个开关完成 |
| 分布式与编译 | ProcessGroup 后端、异步 Work；Fake／Meta、图编译与后端执行 | 分别接通信库与编译／运行系统，不由基础设备注册自动获得 |

固定接口见 [DeviceGuardImplInterface](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/c10/core/impl/DeviceGuardImplInterface.h)和 [PrivateUse1HooksInterface](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/aten/src/ATen/detail/PrivateUse1HooksInterface.h)。[官方 PrivateUse1 教程](https://docs.pytorch.org/tutorials/advanced/privateuseone.html)、[Accelerator Hooks](https://docs.pytorch.org/docs/2.14/accelerator/hooks.html)与 [Autoload 文档](https://docs.pytorch.org/docs/main/accelerator/autoload.html)可交叉阅读；OpenReg 是 CPU 模拟的接入参考，不是高性能生产后端。

### 2.4 最小调用链与完整参考回答

最小验证链为：

`empty(device="foo") → 后端创建 Tensor 与 Storage／分配 → CPU 数据 copy 到设备 → add 命中设备实现 → copy 回 CPU → 确认完成后读取`

创建算子可以根据 `device` 选后端，不能说必须先有设备 Tensor 才能分发。后续 `add` 根据 Tensor 的 dispatch keys 和线程局部状态选择路径；原地／非原地、拷贝的具体算子路由以版本为准。验证既检查结果，也确认没有静默使用 CPU fallback。

> 我会分开回答插件怎样加载，以及设备能力怎样接入。显式导入扩展包或加载共享库后，注册代码把算子实现、设备管理和分配能力接入 PyTorch；支持自动加载的版本还可以通过已安装包的 entry point 执行这一步。改设备名和注册 Python 模块只解决使用入口，设备枚举仍要进入后端 Runtime。
>
> Runtime 对接从设备、流与事件、内存分配和拷贝开始。每个接口都要明确提交、完成、消费和回收的关系，再注册算子与需要的随机数能力。训练、混合精度、分布式和编译属于继续扩展的能力，分别接入验证。
>
> 我会用创建张量、传入数据、设备加法、结果回传串起最小路径，核对设备和分发、数值、同步及释放，再扩展到真实模型。我的 D2H 实现与 H2D 修复可以说明拷贝和生命周期问题；GLM 项目属于既有 vLLM 插件中的模型接入，不能据此声称独立完成整个 PyTorch 后端。

个人事实仅引用现有 [D2H 项目](../../自我准备/projects/async-d2h-project.md)、[H2D 核心案例](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)及 [GLM 项目](../../自我准备/projects/GLM5-3-flash-project.md)；以上通用接入链不是私有实现还原，也不是本次实际运行的测试结果。

## 3. vLLM V1 请求如何调度？PagedAttention 怎样工作？

### 3.1 已记录问题与原回答边界

简记明确列出请求调度和 PagedAttention，作为同题的两个部分。没有现场答稿，不能判断当时是否混淆调度、缓存管理或 Attention 计算。下面以固定 vLLM v0.26.0 提交 568afb3 的 V1 为参考，先讨论普通 full attention，不把特定源码版本认定为本人项目版本。

### 3.2 需要回答的细节

| 层次 | 应说明什么 | 容易混淆的地方 |
| --- | --- | --- |
| 请求接入 | 输入处理后进入 EngineCore，由请求状态和执行进度参与调度 | API 接收请求不等于立即执行模型 |
| 本步预算 | 已计算 token 与待推进 token 的差值，受本轮预算、长度及其他约束限制 | 统一 token 计数不表示 Prefill 与 Decode 的成本相同 |
| 队列与资源 | 参考路径先遍历运行请求，再考虑等待请求，受缓存和编码器等限制 | running 请求也可能是未完成的 Prefill，不能机械等同于 Decode |
| KV 分配 | KV 管理器安排本步所需槽位，缓存命中减少重复计算 | 按需领取池内块编号不等于每步重新申请设备显存 |
| 执行与回传 | Executor、Worker、ModelRunner 准备输入和 metadata，执行并回传，更新请求状态 | Scheduler 的 CPU 决策与 Kernel 的设备计算分开 |
| PagedAttention | 逻辑位置通过块表找到离散 KV，按有效长度读取并正确归一化 | 分页不等于跨请求 Prefix Cache，也不表示消除全部内存浪费 |

### 3.3 更好的回答方式

沿一次请求的循环回答：

**请求与已计算进度 → 分配本轮 token 预算 → 检查缓存与取得新槽 → 生成执行计划 → 模型执行及采样 → 更新状态、输出或结束。**

普通非投机示例中，长 prompt 可以分多轮计算；Decode 请求通常每轮推进一个位置。真实实现还会处理投机候选、异步占位、编码器预算和特殊状态，因此不能只用“批大小乘一步”解释全部情况。缓存不足时可能延后调度或按策略抢占；不能把默认行为概括为总会转存到 CPU。

固定源码入口：[Scheduler.schedule](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/sched/scheduler.py#L423)、[EngineCore.step](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/engine/core.py#L576)。这些条件说明当前参考路径，不表示所有版本的请求优先级或批处理细节相同。

### 3.4 子问题：PagedAttention 与逻辑／物理块

请求使用逻辑连续的 token 位置，设备 KV 可以放在不连续的物理块中。先限定无 CP、无跨层 KV 共享，且管理块大小与 Kernel 读取块大小相同；设每块容纳 B 个 token 位置，位置 p 的简单映射为：

~~~text
逻辑块号 = p // B
物理块号 = block_table[逻辑块号]
槽编号 = 物理块号 × B + p % B
~~~

例如 B=16，某请求的块表为 [7,42]，位置 16 对应物理块 42 的偏移 0。这个槽编号不是字节地址；本层的 head、feature、stride 和布局继续决定实际访问位置。不同层一般保存不同 K/V 值，即使共用相同的块表。

本步新 K/V 通过 slot mapping 写入；历史读取结合 block table、有效长度和因果 mask。Kernel 不需要先把全部历史 KV 拷成连续数组，但必须让 Softmax 的归一化范围覆盖全部合法位置。分块实现可以维护最大值、指数和与加权输出；不能把每块单独归一化后的结果简单相加。

按普通路径，尾块有空位就继续使用，跨边界再分配新块。请求结束后解除引用，待执行依赖允许再回收或复用；有前缀缓存时，内容可能暂留，不等于马上释放整份设备缓冲。刚采样出的 token 通常在下一次前向才产生自己的 K/V，输出计数与已经写入的缓存位置应区分。

依据：[固定版本 slot mapping](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/worker/block_table.py#L347)、[PagedAttention 原论文](https://arxiv.org/abs/2309.06180)。现代 backend 可以用不同 Attention Kernel 消费分页缓存，不要求所有后端使用原论文中的同一 Kernel。

### 3.5 标准参考回答

> V1 调度可以从请求的计算进度理解：每个请求有已经计算的 token 数和接下来需要推进的位置，Scheduler 在本轮 token 预算及缓存等约束下，决定每个请求计算多少新 token。长 Prefill 可以分轮，普通 Decode 通常推进一个位置，完成或取消的请求退出，新的请求按资源条件加入。
>
> 以参考版本为例，Scheduler 在 EngineCore 一侧，调用 KV 管理器查询已有缓存并安排新槽，再把计划交给执行端。Worker 管设备和模型，ModelRunner 准备输入、位置、序列边界、块表等 metadata。执行与采样结果回传后，EngineCore 更新请求进度和结束状态。调度不能只看 token 数，还要考虑可用 KV、运行请求数和模型特定的其他限制。
>
> PagedAttention 解决的是请求逻辑序列与设备 KV 存储的对应。每个请求的历史由块表指向多个物理块，Kernel 通过索引读取有效 K/V，并在全部合法历史范围内完成 Attention，不要求历史数据连续，也不需要每增加一个 token 都搬移旧缓存。
>
> 它减少最大长度预留和连续分配带来的浪费，但仍有尾块、对齐和其他缓冲成本。PagedAttention、Prefix Cache 和请求调度分别处理寻址、重复计算复用和执行选择，可以配合使用，但不是同一个机制。

## 4. Prefix Cache 怎样命中，未满 block 怎样处理

### 4.1 现场题目与材料限制

问题是“Prefix Cache 怎样命中？一个 block 未满时如何处理？”。现有[面试简记](../原始素材/鲲云科技/2026-11-09-面试简记.md)没有现场作答，因此只整理考察细节与参考回答，不评价原回答。

以下以 `vLLM v0.26.0@568afb3a13806beb53bb2e6bd518269357b237c0` 为依据。主线限定普通 full attention、单个 KV cache group、开启 Prefix Cache、无 CP／投机预留，且 hash 粒度等于物理 token block 大小；Hybrid 状态不能直接套用全部规则。

### 4.2 需要说明的细节

- **匹配的是前缀计算条件。** 块 hash 由父块 hash、本块 token IDs 和 extra keys 组成，因此同一段 token 出现在不同前文后，不应直接共用 K/V。该版本的附加键包括 LoRA 名称、多模态标识及块内相对位置、prompt embeddings 数据；可选 `cache_salt` 在首块加入并经父 hash 传递。缓存索引再结合 group ID；模型与布局兼容仍由缓存实例的使用条件保证，不要声称 hash 必然包含所有配置。[hash 生成源码](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/kv_cache_utils.py#L558)
- **常规全注意力查最长连续前缀。** 从首块向后匹配，在首次缺块处停止。一个已匹配块之后的内容不能作为孤立后缀直接跳过计算；跨 cache group 还需共同满足各自状态的命中规则。[查找实现](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/single_type_kv_cache_manager.py#L654)
- **hash、计算完成和保留引用分别管理。** Request 可以在前向之前生成 token hash；管理器按可缓存 token 边界登记完整块，排除可能被拒绝的草稿，异步外部加载可延迟登记。登记动作不等于一次设备完成通知，复用仍须满足执行依赖。命中后增加引用；请求结束解除引用，归零后可进入空闲队列，但 hash 与内容可保留到再次命中或淘汰。[登记边界](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/kv_cache_manager.py#L481)、[引用与淘汰](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/block_pool.py#L647)

### 4.3 用 300-token 请求区分两种尾块问题

这是机制示例，不是个人项目配置。设 `B=256`，hash 粒度也为 256；源请求已有 300 个位置的有效 KV，相关缓存尚未淘汰；新请求也有 300 个 token，满足相同前缀与复用条件。这里的 300 包含 prompt，指已经写入 KV 的总位置数；如果只说“生成了 300 个输出 token”，还需加上 prompt，并注意最后刚采样出的 token 通常尚未产生自身 KV。

| 情况 | 常规路径的处理 |
| --- | --- |
| 新请求复用源请求的前缀 | 命中前 256 个位置，尾部 44 个位置重新计算；不是 300 个全部失效 |
| 同一请求从已计算 299 个位置推进到 300 个 | 在自身既有第二块中写第 300 个位置，零基 offset 为 43；不用因尾块未满重算已有 299 个位置 |
| 同一请求超出两块容量 | 为新增位置申请下一块；历史 KV 不因物理地址不连续而整体搬移 |

第二行假设尾块为本请求可写的私有块。“未满块不按完整块跨请求命中”，不等于“不保存尾部 KV”或“当前请求不能继续使用它”。

#### 4.3.1 请求在 300 个有效 KV 位置结束，最后 44 个位置怎么办？

**在上述普通完整块路径中，44 个位置的 KV 不能作为 Prefix Cache 被其他请求命中，但承载它们的物理块可以回收后重新分配。**

| 物理块 | 请求结束时的有效内容 | 后续处理 |
| --- | --- | --- |
| 第一块 | 256 个位置，已满 | 已登记的 hash 与 KV 可保留，供相同前缀命中；也可能在重新分配时被淘汰 |
| 第二块 | 44 个位置，余下 212 个槽位未使用 | 不登记为完整前缀缓存块；满足释放条件后归还块池 |

该路径以 `num_tokens // block_size` 确定完整块数，所以 300 个位置只对应一个可登记的完整块。依据：[完整块登记](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/single_type_kv_cache_manager.py#L403)。

尾块的后续生命周期是：

1. **解除原请求的引用。** 在执行依赖允许释放后，引用归零的块进入空闲队列。本版本把没有 hash 的块放到优先重新分配的位置；“空闲”表示可以分配，不代表物理字节已经清零。
2. **按整块重新分配。** 新请求取得可写存储空间，计算并写入自己的 K/V。旧内容即使还在同一地址，也不能作为新请求的有效缓存直接使用。
3. **不为缓存而补满原尾块。** 不额外生成 212 个 token，也不把其他请求的数据接到这 44 个位置后面拼成共享块。

因此，新请求若与源请求的前 300 个 token 相同且第一块仍可命中，就会**复用前 256 个位置，重新计算后 44 个位置，并写入为它分配的尾块**。即使恰好拿回原第二块的物理地址，也只是复用了内存空间，不能省略这 44 个位置的计算。依据：[释放与空闲队列](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/block_pool.py#L719)、[新块分配](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/block_pool.py#L647)。

### 4.4 参考回答

> 我会先区分当前请求保存 KV，与其他请求复用前缀。普通全注意力路径里，Prefix Cache 根据前文、本块 token 和影响计算的附加信息生成链式 hash，再查找可用缓存。从开头连续匹配到最长可复用位置，剩余部分继续计算。
>
> 如果匹配粒度和物理块都是 256，源请求已经算过 300 个位置，新请求的相同前缀通常可复用前 256，尾部 44 重新计算。这不妨碍源请求继续使用自己的未满尾块；它增长到下一位置时仍可向尾块追加，只有容量不够才申请新块。
>
> 共享块需要引用和写入隔离，请求结束只解除自己的引用，不能覆盖其他请求还在使用的数据。已经登记的完整块在引用归零后可以暂留，后续命中时重新持有，或者在分配时被淘汰。对于这个例子中没有登记的 44-token 尾块，满足释放条件后归还块池；后来重新分配的是存储空间，其他请求仍需计算自己的 K/V，不会为了缓存而把原尾块补满。
>
> 还要注意完整 prompt 的最后一个位置。这个参考版本为了得到下一 token 的 logits，将最大复用长度限制为请求长度减一；按完整块对齐后，实际可能重算整个末块，而不只是一个 token。它不是有缓存就能省掉全部前向。更细粒度的尾块支持则取决于具体 coordinator、状态类型和后端，不能一概说所有 vLLM 都不支持或默认支持。
>
> 物理块大小与匹配粒度也可能不同。支持更小物理块时，可以沿用完整块缓存；某些 Hybrid 路径则允许匹配到物理块内部，但需要相应状态已经保存，并保护后续追加写入。这个固定版本的部分尾块分支登记最后一个 prompt hash 边界，不是将任意 Decode 结束位置向下取整就自动缓存。

最后位置的处理见 [`get_computed_blocks`](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/kv_cache_manager.py#L207)。这里讨论采样所需的最后输入位置，不把刚采样出的输出 token 自动计为已经写入 KV。

### 4.5 固定版本中的细粒度分支

#### 4.5.1 物理块大小与前缀匹配粒度不是同一概念

物理块大小决定存储分配单位，匹配粒度决定可查找的前缀边界。以下沿用 300 个有效 KV 位置的示例，各行都要求相同前缀、缓存未淘汰且执行依赖已满足；数字用于说明机制，不代表任意模型和后端都支持这些配置。

| 情况 | 物理块大小 | 匹配粒度 | 可能复用到哪里 |
| --- | --- | --- | --- |
| 普通完整块缓存 | 256 | 256 | 前 256 个位置 |
| 后端支持更小的完整块 | 16 | 16 | 前 288 个位置，剩余 12 个位置重算 |
| 支持细粒度匹配的特殊路径 | 256 | 例如 32 | 相应状态已保存且各组允许时，可能到块内部的边界，例如 288；不能只凭总长度推定 |

第二行仍是完整块缓存，只是分配单位变小。第三行才是物理块未满时，其中一段也可能作为可复用前缀；索引需要表达有效前缀边界，相应的 KV 或其他模型状态必须实际存在，继续追加时还需写入隔离。

#### 4.5.2 哪些配置可以进入细粒度路径？

该版本存在 `prefix_match_unit`，但不能据字段存在就认为所有模型都能启用。单组 [Unitary coordinator](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/kv_cache_coordinator.py#L435)要求 hash 与块大小相同；[Hybrid coordinator](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/kv_cache_coordinator.py#L554)要求至少两个不同 cache spec 的分组，其中存在 `MambaSpec` 的 `align` 模式、其块大于 hash 单位且 DCP 为 1 时启用部分 hash 命中，另要求 PCP 为 1、各组块大小能被 hash 单位整除。

这些条件下还需有实际保留的状态边界，各组协商共同可恢复长度；不是任意细粒度位置都已保存。Hybrid 模型的滑窗层可能只保留窗口内缓存，递推层需要相应状态检查点，因此不能只看全注意力层命中了多少。命中共享部分尾块后，[COW 路径](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/single_type_kv_cache_manager.py#L321)会复制到私有可写块再追加，并保护复制生命周期。已有 GLM 的混合状态案例不能直接等同于此参考配置。另见[版本化 Hybrid 缓存说明](https://docs.vllm.ai/en/v0.26.0/design/hybrid_kv_cache_manager/)。

#### 4.5.3 为什么 hash 粒度为 32，也不能断言生成到 300 就复用到 288？

该固定版本的部分尾块登记边界是 `num_prompt_tokens // hash_block_size * hash_block_size`，即**最后一个 prompt hash 边界**。边界需已经计算，且位于物理块内部；同一物理块内更早的 hash 边界不会因此全部登记。它不是根据任意 Decode 结束长度生成尾块缓存。依据：[`_cache_partial_tail_block`](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/single_type_kv_cache_manager.py#L765)。

- 如果 **prompt 本身长 300**，hash 粒度为 32，最后一个 prompt hash 边界是 288；还需确认该边界的 KV、其他组状态和缓存条目确实可用，才可能复用到这里。
- 如果 **prompt 是其他长度，只是后来生成到总长度 300**，不能据此推断尾块自动缓存到 288。需按真实 prompt 边界与实际保存状态判断。

因此，原问题在普通 `256/256` 路径下的结论仍是：44 个尾部位置不进入完整块前缀缓存，物理块可回收再分配。其他路径只有在实现、配置和状态保存条件都满足时，才能给出不同的复用结论。

### 4.6 细粒度命中后的 COW：300-token 例子

这是对第 4 题的补充准备，不标记为现场已问。以下继续依据 `568afb3`：物理块大小为 **256**，hash 粒度为 **32**，满足前述 Hybrid 路径条件；源请求的 **prompt 长度为 300**，且 **288 边界的各组状态已经保存并可恢复**。新请求也有 300 个 token，前 288 个相同，后 12 个可以不同。这里的边界来自 prompt 与实际保存状态，不能从任意 Decode 结束长度推定。

以下 token 位置从 1 开始编号，块内 offset 从 0 开始。图表只展开全注意力组；递推层需恢复对应的状态检查点，不能把其状态理解为逐 token 排列的 K/V。

#### 4.6.1 为什么需要复制尾块？

源缓存与新请求的命中范围如下：

| 物理块 | 对应 token 位置 | 新请求能够复用的部分 |
| --- | --- | --- |
| P0 | 1–256 | 全部 256 个位置 |
| P1 | 257–512 | 257–288，共 32 个位置 |

新请求接下来计算第 289–300 个 token，产生的 K/V 也要写入第二个逻辑块。如果直接写共享的 P1，多个请求的不同后缀可能占用相同槽位。例如两个请求的第 289 个 token 不同，却都写入 P1 的 offset 32，就会互相覆盖。即使源请求已经结束，仍需保护可供其他请求命中的缓存内容。

COW 因此为新请求建立私有尾块，保留已命中的前缀，并隔离后续写入；前面的完整块 P0 继续共享。

#### 4.6.2 分配私有块，修改块表，登记复制任务

管理器识别到 288 不是 256 的整块边界，在容量检查中预留一个额外块。分配时取出新物理块 P2，将新请求块表的第二项从 P1 改为 P2，并登记 `P1 → P2` 的复制任务。原 P1 的内容保持不变。

```text
源缓存：          [ P0 ][ P1 ]

新请求 COW 前：   [ P0 ][ P1 ]
新请求 COW 后：   [ P0 ][ P2 ]

复制方向：          P1 → P2
```

这里只复制尾块，不复制前面已共享的 P0；块表重定向与实际设备复制是两个步骤。依据：[额外容量预留](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/single_type_kv_cache_manager.py#L217)、[分配与块表修改](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/single_type_kv_cache_manager.py#L321)。

#### 4.6.3 实际复制整页，但只认可命中的有效范围

**该版本的 worker 按整张物理页复制字节，并非只复制命中的 32 个 token。** `copy_kv_cache_blocks_inplace` 将 backing storage 视为 `[num_blocks, page_bytes]`，按源、目标 block ID 复制整行。

因此，P1 中其他位置的字节也可能一起进入 P2，但新请求的已计算长度仍然是 **288**。字节已经搬到目标地址，不等于相应位置已经成为新请求可直接复用的有效 KV。依据：[整页复制实现](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/worker/utils.py#L541)。

| token 位置 | 新请求的处理 |
| --- | --- |
| 1–256 | 读取共享的 P0，无需复制或重算 |
| 257–288 | 使用 P2 中复制过来的有效 KV，对应 offset 0–31 |
| 289–300 | 重新计算并写入 P2 的 offset 32–43 |
| 301–512 | 尚不属于新请求的有效 KV，后续计算时再写入 |

即使源请求与新请求的全部 300 个 token 都相同，在本例只命中到 288 的条件下，最后 12 个位置仍要计算，不能因为源页中已有相同字节就直接跳过。

#### 4.6.4 执行顺序与复制期间的释放保护

worker 的执行顺序是：**新块清零（若配置要求）→ COW 复制 → 后续前向计算**。这样不会在复制之后又清掉结果，前向也按执行依赖读取已复制的前缀。依据：[worker 的清零与复制顺序](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/worker/gpu_model_runner.py#L1195)。

复制的源和目标还必须避免被提前回收再分配。`_apply_cow` 保留源块的命中引用，并给目标块增加一个复制期间的额外引用；Scheduler 收集复制任务及这些临时引用。在 `defer_block_free` 开启且相应 step 尚未完成时，按 step fence 延迟释放；不能概括成所有配置都等待 GPU 完成后才减少引用。依据：[复制端点引用](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/single_type_kv_cache_manager.py#L381)、[复制任务收集](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/kv_cache_manager.py#L741)、[延迟释放保护](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/sched/scheduler.py#L2263)。

相比普通 `256/256` 路径重算尾部 44 个位置，本例少算其中 32 个，只重算 12 个；代价是额外的私有尾块、物理页复制和依赖管理。因此细粒度命中节省计算，但不意味着没有复制成本，也不能只根据命中长度推断实际加速。

#### 4.6.5 COW 追问的参考回答

> 如果细粒度路径允许命中到 288，而物理块大小是 256，那么第一个块可以完整共享，第二个块中有 32 个位置可复用。新请求还要计算第 289–300 个 token，不能直接写共享尾块，否则不同请求的后缀可能覆盖同一槽位。
>
> 管理器会分配私有尾块，修改新请求的块表，并安排从原尾块到新块的复制。这个参考版本实际复制整张物理页，但逻辑上只认可命中范围，所以最后 12 个位置仍要重新计算并写入私有块。原来的尾块不被新请求改写，前面的完整块也不需要复制。
>
> 执行上要保证清零、复制、前向的顺序，并保护复制期间源和目标的生命周期。这个例子用一次尾块复制换取少算 32 个位置，是否更快还取决于复制和计算成本；前提是 288 边界的各组状态确实可恢复，不能只看总长度和 hash 粒度。

## 5. Python 装饰器与生成器

### 5.1 已记录问题与原回答边界

本题包括装饰器原理、使用方式、应用位置，以及生成器。现有材料没有现场答稿；以下按常见 Python 语义准备，不添加“当时答错”的判断。语言与标准库引用固定为 Python 3.13，示例用于说明同步函数与普通生成器。

### 5.2 装饰器的原理与执行时机

装饰器是定义执行时的对象变换和名称绑定。对普通函数，装饰器获得函数对象并返回替代对象，函数名随后指向返回值。常见的包装方式会返回一个 wrapper，但装饰器也可以用于注册并返回原函数，或者返回其他合适对象。

~~~python
@outer
@inner
def f():
    pass

# 不考虑装饰器表达式自身的副作用时，可理解为：
# f = outer(inner(f))
~~~

多个装饰器的表达式按源代码从上到下求值，装饰动作从内向外应用。带参数的装饰器多一层工厂调用。模块顶层函数通常在模块执行时被装饰；以后调用的是返回对象，并非每次重新执行装饰动作。嵌套函数定义再次执行时，则可以再次产生并装饰新的函数对象。

依据：[函数定义与装饰器规则](https://docs.python.org/3.13/reference/compound_stmts.html#function-definitions)。

### 5.3 怎样使用，能用在哪里

以下示例只包装普通同步函数，说明参数、返回值、异常和元数据怎样处理：

~~~python
from functools import wraps

def trace_call(fn):
    @wraps(fn)
    def wrapper(*args, **kwargs):
        print("before")
        try:
            return fn(*args, **kwargs)
        finally:
            print("after")
    return wrapper

@trace_call
def add(x, y):
    return x + y

result = add(2, 3)  # 打印 before、after；result 为 5
~~~

适用对象包括函数、方法和类；常见用途是日志、计时、参数或权限检查、缓存、注册等。方法还涉及绑定，classmethod、staticmethod、property 使用描述符语义，不能都理解成同一种普通函数 wrapper；重试和缓存也需考虑副作用、可哈希参数与并发等条件。

functools.wraps 用于复制名称、文档等元数据并设置 __wrapped__，便于检查原函数；它不自动保证包装后的业务行为、异步协议或生成器协议与原函数相同。依据：[functools.wraps](https://docs.python.org/3.13/library/functools.html#functools.wraps)。

### 5.4 子问题：生成器是什么，怎样使用

普通函数体包含 yield 时，调用它得到生成器对象，函数体在开始迭代时才执行。生成器在 yield 处交出一个值并暂停，保留继续执行需要的局部状态；next 或其他迭代操作恢复执行。结束时通过 StopIteration 表示耗尽，for 循环会处理这一结束信号。

~~~python
def squares(n):
    for i in range(n):
        yield i * i

g = squares(3)  # 创建对象，尚未执行循环
assert iter(g) is g
assert next(g) == 0
assert list(g) == [1, 4]
assert list(g) == []  # 同一对象已经耗尽
~~~

生成器适合逐项生产结果、分批读取和流式处理，避免必须先建立完整结果列表。但它会保留自己的状态和对象引用，不能据此承诺零内存或所有场景更快。需要重复遍历时，要创建新生成器或按需求保存结果。

send 可将值送回暂停处的 yield 表达式，未启动的生成器通常先用 next 或 send(None) 推进；yield from 可以委托给子迭代器。close 与异常处理可触发清理，但提前停止消费时不应只依赖垃圾回收及时释放资源。普通生成器不是线程，也不自动并行；异步生成器使用另一套协议。

依据：[生成器与 yield](https://docs.python.org/3.13/reference/expressions.html#yield-expressions)、[生成器方法](https://docs.python.org/3.13/reference/expressions.html#generator-iterator-methods)。

### 5.5 更好的回答方式与标准参考回答

先分清“定义时、调用时、迭代时”，再用一个例子说明。这样既能回答装饰器，也能解释装饰器包装生成器时的时机差异。

> 装饰器在定义执行时接收对象并返回替代对象，名称绑定到返回值。常见函数装饰器返回 wrapper，以后调用时由 wrapper 执行额外逻辑，再调用原函数。多个装饰器按嵌套顺序应用；带参数的装饰器还多一次创建装饰器的调用。
>
> 我可以用它处理日志、计时、参数检查、缓存或注册，也可以装饰方法和类。实现时要保持参数、返回值和异常行为，使用 wraps 保存需要的元数据；缓存、重试和权限处理还需各自的业务约束，不能只保证示例能执行。
>
> 生成器由 yield 暂停并保留状态，调用生成器函数先得到对象，迭代时才逐步执行，耗尽后结束。它适合流式产生数据或按需读取，减少一次建立完整结果列表的需求；同一个生成器通常只能消费一次，持有资源时还需要明确清理。
>
> 两者可以组合，但要看执行阶段。普通 wrapper 只包住生成器对象的创建，不一定覆盖后续迭代。若要统计整个生成过程或保持异常和关闭行为，需要相应的生成器包装设计，不能直接把普通函数计时装饰器套上就认为测到了全部执行。

装饰器如何注册插件中的函数，是调用时机的一种应用；Python 的装饰器语法本身不会扫描、发现或加载整个插件包，仍需要前两题说明的加载与注册流程。

## 扩展问题与参考回答

以下为关联主题的补充准备，不标记为本场已问，也不评价不存在的原回答。

### E1. vLLM 插件已经安装，为什么仍未选中？

关联第 1 题。

> 我会按发现、探测和选择三层排查。先在实际运行环境中检查安装包的 entry-point 元数据和组名，再看名称是否被 VLLM_PLUGINS 过滤、入口能否导入、注册回调返回什么。返回 None 可能是环境探测不满足，也要区分导入错误和多个平台同时激活的冲突。
>
> 最后确认 current_platform 是否已经在修改配置前被初始化并缓存，以及所选平台有没有设置预期的 worker_cls。插件能安装、回调可导入、设备驱动可用和算子能运行，是不同证据，不能只检查一个 pip 包名就认为链路正常。

参考：[插件发现与过滤](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/plugins/__init__.py)、[平台选择](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/platforms/__init__.py)。

### E2. 单进程可用，为什么 Worker 子进程会失败？

关联第 1 题。

> 先核对执行进程使用的 Python 环境、插件版本、动态库依赖和配置，再检查 Worker 类路径能否导入，初始化是否依赖主进程中的临时对象。不同机器或进程可能没有同样的包和环境，不能假定主进程的一次手动注册会自动覆盖全部执行环境。
>
> 注册与设备初始化也要分开。回调应能安全重复调用，导入阶段尽量避免不必要的设备初始化副作用；进程启动方式会影响继承状态和初始化要求。应定位到 discovery、导入、注册、设备初始化还是实际执行失败，再处理对应层次。

参考：[WorkerWrapper 初始化](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/worker/worker_base.py#L230)。本题不指示在未知私有环境中更换进程模式或绕过初始化检查。

### E3. PyTorch 扩展可以导入，为什么 empty 失败或算子仍走 CPU？

关联第 2 题。

> 成功导入只说明相关模块代码执行到了某个位置。创建设备张量还需要设备可用性、创建算子和分配器等能力；运行 add 还需相应 dispatch 注册及正确的输入设备。应分别检查注册是否生效、设备是否初始化、内存怎样分配、最终执行了哪个实现。
>
> 如果设置了 fallback，还要观察数据是否回到 CPU 计算，并记录额外拷贝。只看最终数值相同不足以证明目标 Kernel 已实现。测试应同时验证结果、设备和路径命中，不支持的能力要有明确行为，不能静默掩盖缺失实现。

参考：[PrivateUse1 后端接入](https://docs.pytorch.org/tutorials/advanced/privateuseone.html)、[PyTorch Dispatcher](https://docs.pytorch.org/tutorials/advanced/dispatcher.html)。

### E4. DeviceGuard 或 recordStream 能否替代同步？

关联第 2 题。

> DeviceGuard 主要管理当前设备的切换与恢复；recordStream 一类机制告诉分配器某块存储还在某条流上使用，防止过早回收。它们与消费者等待数据准备完成是不同职责。
>
> 一条异步拷贝路径要同时保证 Host 数据已准备、拷贝已提交、设备完成后消费者才能读，以及源与目标在最后一次使用前有效。生命周期保护不自动建立所有执行依赖，等待某条设备流也不自动覆盖尚未提交的 Host 后台任务。私有 guard 如果封装了其他行为，应按其真实合同说明。

依据：[标准 DeviceGuard](https://github.com/pytorch/pytorch/blob/460948b96a67002b7257ac4f3d6a192f70d61d27/c10/core/DeviceGuard.h)及已有[H2D 核心案例](../../自我准备/projects/vLLM-V1-async-H2D-project.md#vllm-v1-async-h2d-case-card-v1)。

### E5. token 预算有剩余，为什么请求仍可能不能调度？

关联第 3 题。

> token 预算只限制本轮新增计算量。请求还可能受 KV 空间、最大运行请求数、模型长度、编码器预算、外部缓存加载或其他依赖限制。需要检查具体拒绝或等待条件，而不是只看一个 max_num_batched_tokens 值。
>
> 对普通 V1 的内存抢占路径，被抢占请求可以释放相应缓存、回到等待队列，之后根据保留的请求内容和可复用状态继续或重算。应区分已经返回给用户的输出和仍需重建的计算状态，并计入额外延迟；不能把抢占说成没有代价，也不能默认所有路径都采用 CPU swap。

依据：[参考 Scheduler 资源检查与抢占](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/sched/scheduler.py)。

### E6. 为什么不能只 hash 当前块的 token？

关联第 4 题。

> 同一 token 块放在不同前文后，通常会产生不同隐藏表示和 K/V。父 hash 把前面的上下文纳入标识，附加键继续区分影响计算的 LoRA、多模态内容或隔离域。改变前文之后，后续块即使 token IDs 相同，也不能作为独立相同计算直接复用。
>
> 命中还要满足模型、缓存格式与执行完成等条件。哈希键用于识别，引用和生命周期用于保护数据，两者不能相互替代。

依据：[固定版本缓存 hash](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/kv_cache_utils.py#L558)。

### E7. Prefix Cache 命中率提高，TTFT 就一定下降吗？

关联第 4 题。

> 不一定。需要区分请求命中比例和实际复用 token 数，观察省下多少前向计算，同时计入查找、管理、尾部重算和排队成本。即便输入对应的缓存都存在，也可能为最后位置的 logits 重新计算一部分。
>
> 我会固定模型和请求分布，比较命中长度、实际计算量与 TTFT。更细的粒度可能增加管理成本，缓存竞争也可能改变结果；不能只凭一个高命中百分比承诺服务更快。

### E8. 普通计时装饰器包装生成器，测到的是哪段时间？

关联第 5 题。

> 普通同步 wrapper 调用生成器函数时，通常只得到生成器对象；真正的函数体在以后迭代时执行。因此这个 wrapper 的计时可能只覆盖创建对象，不能代表消费完整序列的耗时。
>
> 若需要观察整个生成过程，可以在迭代或生成器包装层处理，但要明确测量是否包括消费者暂停的时间，并正确传播返回、异常与关闭行为。使用 try/finally 管理清理，提前停止时安排明确的关闭，不依赖对象何时被垃圾回收。异步函数和异步生成器还需要对应的 await 或异步迭代协议，wraps 不会自动完成这些转换。

依据：[Python 生成器方法](https://docs.python.org/3.13/reference/expressions.html#generator-iterator-methods)、[functools.wraps](https://docs.python.org/3.13/library/functools.html#functools.wraps)。
